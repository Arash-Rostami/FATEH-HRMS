# Tenant/company branding convention

Multi-company white-labeling: switching one env var (`APP_TENANT`) repoints brand text, logos (app + company variants), favicon, per-panel background images, logo reversal, and the auth-page video playlist — no code changes to onboard a new tenant. See also `resources/assets/assetPattern.md` for the underlying folder/file convention.

**First business-logic consumer (2026-09-04):** `App\Services\PersolTeamService` (Energy module's team-visibility rule engine — see `app/Livewire/Dashboard/Energy/Chart.php::teamMembersData()`) is bespoke Persol org-chart logic — literal department codes (`MA`/`MK`/`HC`/`HR`/`CP`/`CX`/`WP`/`CH`/`SO`/`AS`) and two hardcoded employee-name carve-outs. It now gates on `config('app.tenant') === 'persol'`: under the `persol` tenant it runs the full department/name-based rule set unchanged; under any other tenant it falls straight through to the generic default (`applyDefaultRules` — a department head sees only their own department). The one universal branch (`isTopExecutive()` → manager-rank-and-above, company-wide) is rank-based, not department-code-based, so it applies identically regardless of tenant. `tests/Feature/Services/PersolTeamServiceTest.php` covers both branches. This is the first place `config('app.tenant')` gates actual feature behavior rather than an asset/branding value — if a future tenant needs its own bespoke visibility rules (not just the generic default), follow this same shape (an explicit tenant-slug branch in the service), not a new tenant-config key, until a second bespoke-rule tenant makes a config-driven approach worth the lift.

**`.env.testing` carries `APP_TENANT=persol`** (added same date) to match `tests/Feature/Services/PersolTeamServiceTest.php`'s Persol-specific fixtures — this whole test suite already assumes Persol data/rules throughout (see `useMysql()`'s deliberate real-dev-DB connection in `livewireTestPattern.md` §1). Before this, `config('app.tenant')` was never read by any test, so the gap was invisible; any future test that needs the *other* tenant's behavior overrides `config(['app.tenant' => '...'])` locally and restores it in a `finally` block (see `PersolTeamServiceTest`'s `test_non_persol_tenant_*` tests) — never flip the `.env.testing` default itself for that.

## Active tenant
`APP_TENANT` env var (default `fateh`), exposed as `config('app.tenant')`.

## `config/tenants.php` is the single source of truth
Every fact about a tenant — text, computed asset paths, behavioral flags — lives in one array keyed by tenant slug; nothing is split across other files. Its own PHPDoc block documents every env var that can override a tenant value. `config/app.php` is a thin two-layer resolver only: `env('APP_X', $tenant['x'])` — env wins if set, otherwise the active tenant's own value, nothing else. There is deliberately no third hardcoded literal fallback in `app.php`; if a key is missing from a tenant's array with no matching env var, it resolves to `null`/an undefined-key warning — acceptable since only `fateh`/`persol` are ever expected as valid `APP_TENANT` values.

`$tenant = (require __DIR__.'/tenants.php')[env('APP_TENANT', 'fateh')] ?? []` in `app.php` is a plain `require`, not `config('tenants...')`, because `app.php` loads alphabetically before `tenants.php` and would read an empty repository otherwise.

Asset-path values inside `config/tenants.php` are computed once per tenant via `tenantAsset(string $tenant, string $type, string $role, ?string $fallback)` / `tenantVideos(string $tenant)` (`app/Helpers/index.php`) — both take the tenant slug explicitly (not read from `env()` internally), since `tenants.php` builds every tenant's full profile up front, not just the active one.

`.env`/`.env.example` brand-text keys (`APP_NAME`, `APP_NAME_EN`, `APP_NAME_ALT`, `APP_ORGANIZATION(_EN)`, `APP_SLOGAN(_EN)`) must stay **commented out**, not blank — Laravel's `env()` treats a present-but-empty key as "set" (returns `''`, not the tenant fallback), so a blank line silently defeats tenant switching for that field. Same rule for `COMPANY_LOGO`/`APP_LOGO_*`/`APP_FAVICON`/`APP_BACKGROUND_IMAGE`.

## Nested tenant setting groups — the source shape, not the consumed shape

Each tenant's array in `config/tenants.php` groups its ~24 settings into eight keys (`app`, `company` — which itself nests `social` — `background`, `videos`, `backdrop`, `logo_display`, `ai_assistant`) instead of one flat list of siblings — but this is a **source-only** reorganization. `config/app.php` stays the sole reader of the nested shape (`$tenant['app']['name']` instead of `$tenant['name']`, etc.) and continues producing the exact same flat `config('app.name')`/`config('app.company_logo')`/... output keys it always has, at the exact same resolution precedence (env override → tenant default). Every one of the 20+ Blade/PHP consumers across the app (`meta-tags.blade.php`, `auth.blade.php`, `brand.blade.php`, `FilamentPanelCustomizer`, `tenantLogo()`, presenters, widgets, ...) keeps reading `config('app.*')` completely unchanged — none of them were touched by this reorganization, and none of them should ever read `config('tenants.*')` directly (only `config/app.php` and `tests/Feature/Config/{AppConfigTest,TenantsConfigTest}.php` do, since those two are the only things that need the raw per-tenant source rather than the resolved-and-flattened output).

**`app` vs `company` — a real distinction, not a naming accident.** `app` holds the SaaS product's own identity: `name`/`name_en` (the product's own display name — "اینتــرا"/"Interra" for the `fateh` tenant), `alt_name` (a longer branded phrase built from that same product name — this was the old flat `company_name` key, which despite its name was never the tenant's company at all: `config('app.company_name')`'s only two consumers, `account-widget.blade.php` and `ReleaseRequestInfolistPresenter.php`, both use it as a fallback *for the app's own name* — `config('app.name') ?? config('app.company_name')` — confirming it, renamed here to remove that confusion at the source even though the still-flat `config('app.company_name')` output key is unchanged), `slogan`/`slogan_en`, and the app's own visual identity (`logo_light`/`logo_dark`/`favicon`). `company` holds the actual organization that bought/deployed this tenant — its real name (`name`/`name_en`, the old `organization_name`/`organization_name_en`) and its own logo (`logo`, the old `company_logo` — the one asset with no light/dark variant, swapped in for the app logo only when `logo_display.*_use_company` is set). The two identities are deliberately kept as separate groups because they answer different questions ("what product is this" vs. "whose deployment is this") and can diverge freely — `fateh`'s `app.name` ("اینتــرا"/Interra) is not `fateh`'s `company.name` ("شرکت توسعه معادن و صنایع معدنی فاتح"/Fateh), and neither should a future tenant assume they'll ever be the same string.

**`logo_display`** groups the six reverse/use-company-logo behavioral flags (`admin_reverse`, `user_reverse`, `admin_auth_reverse`, `user_auth_reverse`, `admin_use_company`, `user_use_company` — see the "Behavioral flags" section below for what each one does; only the tenants.php-side key names lost their `_logo` suffix since it's now redundant under the `logo_display` group). **`company.social`** groups `instagram`/`linkedin` as a nested sub-group of `company` rather than its own top-level sibling — social accounts belong to the real organization, not the product, the same reasoning that keeps `company` itself separate from `app`. **`background`** groups `user`/`admin` (the old `background_image`/`admin_background_image`). **`ai_assistant`** groups `access`/`lang` (the old top-level `ai_assistant`/`ai_assistant_lang`). `videos` and `backdrop` were already single keys (or, for `backdrop`, already its own nested group — see "Dynamic user-panel backdrops" below) and are unchanged.

Onboarding a new tenant still means filling in the same facts, just organized: copy `fateh`'s or `persol`'s full eight-group array as a template, never introduce a new top-level group without a real multi-key reason (a single new setting is still just one more key inside the group it conceptually belongs to — `company.social` itself is the precedent: a new social platform is a new key inside `social`, not a new top-level group).

**`config('app.instagram')`/`config('app.linkedin')` visible consumers — `resources/views/components/ui/social-links.blade.php`.** Before this component existed, the two links were consumed only by `meta-tags.blade.php`'s JSON-LD `"sameAs"` array (SEO metadata, never rendered as visible UI). `<x-ui.social-links/>` is the single shared component that actually renders clickable icons — `background.blade.php`... no, `footer.blade.php` (compact, Material-token colors, the component's default `linkClass`) and `layouts/auth.blade.php`'s left-side hero panel (larger, `link-class="text-white/70 hover:text-white hover:bg-white/10"` override, since that panel sits over a dark photo/video backdrop where the Material surface tokens would be invisible). The component itself is tenant-agnostic — it reads `config('app.instagram')`/`config('app.linkedin')` directly and `array_filter`s out whichever is empty, so a tenant that sets only one social link (or neither) never renders a dead icon or an empty wrapper. `size`/`icon-size`/`link-class` are the three overridable props; a third consumer should reuse this component rather than hand-rolling another set of brand SVGs — the Instagram/LinkedIn path data lives in exactly one file.

## Behavioral flags (bool, no env override) — every flag comes in an `admin_*`/`user_*` pair
- `admin_reverse_logo` / `user_reverse_logo`, their auth-page-only counterparts `admin_auth_reverse_logo` / `user_auth_reverse_logo`, and `admin_use_company_logo` / `user_use_company_logo` are all resolved by one shared helper, `tenantLogo(bool $dark, string $scope = 'user', bool $auth = false): string` (`app/Helpers/index.php`):
```php
function tenantLogo(bool $dark, string $scope = 'user', bool $auth = false): string
{
    if ($scope === 'admin' && config('app.admin_use_company_logo')) {
        return config('app.company_logo');
    }

    $reversed = config('app.' . $scope . ($auth ? '_auth_reverse_logo' : '_reverse_logo'));
    $showDark = $reversed ? !$dark : $dark;

    return config($showDark ? 'app.app_logo_dark' : 'app.app_logo_light');
}
```
  - The `$auth` param picks which of the two flags per scope governs the swap: `false` (the default) reads `{scope}_reverse_logo`, `true` reads `{scope}_auth_reverse_logo`. The two flags are fully independent — flipping one never affects the other — so a tenant can invert the login-page logo color without touching the rest of the panel, or vice versa.
  - `admin_reverse_logo`, via `tenantLogo($dark, 'admin')` (called from `FilamentPanelCustomizer::logoHtml()` for every admin page): swaps light-for-dark/dark-for-light across the authenticated admin panel. `admin_auth_reverse_logo`, via `tenantLogo($dark, 'admin', true)` (`logoHtml()` passes `$auth = request()->routeIs('filament.admin.auth.login')`): governs the swap on the admin login page only, independently of `admin_reverse_logo`. Both `fateh` and `persol` currently set `admin_auth_reverse_logo` to `false` (persol's login page has historically rendered un-reversed even while `admin_reverse_logo` is `true` for the rest of its admin panel — the new flag makes that an explicit, independently-editable setting instead of an implicit route-detection quirk baked into the helper).
  - `user_reverse_logo`, via the default `tenantLogo($dark)` (scope `'user'`, `$auth = false`): consumed by the dashboard header `brand.blade.php`. `user_auth_reverse_logo`, via `tenantLogo($dark, 'user', true)`: consumed by `card-no-signup.blade.php` (the user-panel auth-page card), the only `user`-scope logo slot that ever sits on an auth page. Both pairs use the same two-slot shape — `asset(tenantLogo(true, ...))` for the `dark:block` slot, `asset(tenantLogo(false, ...))` for the `dark:hidden` slot — the helper decides which actual file (`app_logo_dark`/`app_logo_light`) fills which slot, so the Blade markup never hardcodes the mapping.
  - `admin_use_company_logo` / `user_use_company_logo` replace the *app* logo (the light/dark-varying product brand mark) with the single, fixed `company_logo` in one specific slot each — **`company_logo` has no light/dark variant and never should**, it's one file. The two flags are **not** symmetric inside the helper:
    - `admin_use_company_logo` short-circuits `tenantLogo($dark, 'admin', ...)` itself — returns `company_logo` fixed, skipping the reverse-logo branch (auth or not) altogether.
    - `user_use_company_logo` is deliberately **not** checked by `tenantLogo()` in the `user` scope — it's read directly by `brand.blade.php`, which renders a click-to-flip card (vertical `rotate-x-180` axis) whose front is the fixed `company_logo` and whose back is the app-logo light/dark pair (`tenantLogo(true)` `dark:block` / `tenantLogo(false)` `dark:hidden`); when `false` it renders just that app-logo light/dark pair statically (no flip, no `company_logo`). `tenantLogo()` always returns the plain app-logo variant for the `user` scope regardless of this flag — the flip is the Blade template's job, not the helper's.
  - These are independent of the reverse-logo flags by construction — a *different* slot (header vs. the light/dark toggle-badge pair), so there's no interaction to keep in sync when one changes.

There is no `app_logo_initial` role — it was removed entirely (deleted from `config/tenants.php`, `config/app.php`, the env-var PHPDoc block) since it was never consumed anywhere in the codebase; dead config, not a mechanism. Don't re-add a key without a real Blade/PHP consumer already in mind.

## Plan-tier feature flags (three-state, env override allowed) — a different shape from the bool flags above

`ai_assistant_access` (`config/tenants.php` per-tenant key `'ai_assistant'`, resolved to `config('app.ai_assistant_access')`) is the first flag of a genuinely different shape than §"Behavioral flags" above: three states (`true`/`false`/`'lock'`, not a plain bool), absent-key defaults to `false` (not cast, so `?? false` — never wrap this one in `(bool)` the way the logo flags are, `'lock'` must survive as a string), and it **does** allow an env override (`AI_ASSISTANT_ACCESS`) since a plan-tier gate is exactly the kind of thing ops may need to flip per-deployment without touching `tenants.php`. Consumed by `resources/views/components/dashboard/ai-assistant.blade.php` (only renders the working panel when `=== true`) and `resources/views/components/dashboard/navbars/top/ai-assistant.blade.php` (renders the full trigger when `=== true`, a dimmed icon + lock badge + upgrade toast when `=== 'lock'`, nothing at all otherwise) — see `resources/views/viewPattern.md` §8.9 for the full widget mechanism. Both `fateh` and `persol` currently set this to `true`.

`ai_assistant_lang` (tenant key `'ai_assistant_lang'`, resolved to `config('app.ai_assistant_lang')`, env override `AI_ASSISTANT_LANG`, default `'fa'` when a tenant omits it) rides the same three-layer resolution shape. Sent as the iframe's `&lang=` param (see `viewPattern.md` §8.9) — deliberately a separate setting from Fateh's own `app()->getLocale()`, since a tenant's preferred AI-chat language and its whole-app UI locale are different concerns that could diverge. Both `fateh` and `persol` currently set this to `'fa'`.

## Files (auto-discovered, never listed in code) — `resources/assets/{img,video}/<tenant>/`
- **Images**: one file per role, matched by basename regardless of extension — `logo.*`, `light.*`, `dark.*`, `favicon.*`, `user-background.*`, `admin-background.*`. Resolved via `tenantAsset()`, which globs `resources/assets/{type}/{tenant}/{role}.*` and returns the `build/assets/...` path for `asset()`. Missing file for a tenant → falls back to the literal default passed at the call site in `tenants.php`. Note: the glob only checks the tenant's immediate folder, not subfolders — any `extra/` subfolder a tenant keeps for unused/reference assets is correctly ignored.
- **Videos**: any number of files, named `1.<ext>`, `2.<ext>`, ... — no fixed count, a tenant can have 2 or 20. Resolved via `tenantVideos()`, `natsort()`'d into `config('app.videos')`. `auth.blade.php` loops this into its Alpine video-rotation array.

## Two distinct backgrounds, not one shared role
`user-background.*` and `admin-background.*` are separate per-tenant roles (not a single shared `background.*`) since the user-panel auth page and the admin login page are different surfaces that may want different imagery:
- `config('app.background_image')` — consumed directly by `auth.blade.php`'s non-video background fallback `<img>`.
- `config('app.admin_background_image')` — consumed only via the CSS bridge below, since the admin background lives in a compiled CSS file, not Blade.

**Known gap:** neither generic fallback (`resources/assets/img/user-background.*` / `admin-background.*`, no subfolder) exists on disk yet — only hit if a tenant is unset/unknown or missing its own role file, so nothing is broken for `fateh`/`persol` today.

## Dynamic user-panel backdrops (quick-settings "پس‌زمینه پویا")

A third per-tenant image role, distinct from the single-file `user-background`/`admin-background` roles above: `img/<tenant>/bg/` holds an arbitrary number of files (any name, extension-agnostic, matched by `glob("{$dir}/*.*")` and `natsort()`'d — same discovery shape as `video/<tenant>/`, but keyword-named rather than sequentially numbered). The image list comes from `tenantBackdrops(string $tenant): array` (`app/Helpers/index.php`, cached per tenant like its siblings), but the tenant entry itself nests everything backdrop-related under one `'backdrop'` array key rather than a flat sibling per setting — `'backdrop' => ['images' => tenantBackdrops($slug), 'mode' => 'tabs'|'time', 'opacity' => 0.0-1.0, 'blur' => 0, 'brightness' => 1, 'contrast' => 1, 'grayscale' => 0, 'width' => '85%'|'100%', 'fit' => 'top' (optional — absent means 'cover')]` — resolved as one unit to `config('app.backdrop')` (`config/app.php`: `$tenant['backdrop'] ?? [...same shape, neutral defaults...]`, no env override). Nesting under one key (rather than a `backdrop_images`/`backdrop_mode`/`backdrop_opacity`/... flat-sibling family) means a new per-tenant backdrop setting is one new array entry, not a new top-level config key plus a new `config('app.*')` line plus a new spot in the window-global payload.

`mode` picks how the client cycles through that tenant's backdrop set:
- `'tabs'` (fateh): one image per dashboard tab, crossfading as the user switches tabs (`resources/js/components/alpine/data/background.js`'s `updateState()`, keyed against `$store.background.tabsOrder`) — fateh's 8 files are plain numbered (`backdrop1.png`...`backdrop8.png`), order-driven, no filename semantics.
- `'time'` (persol and any future tenant that doesn't opt into `'tabs'`): one fixed image for the whole session, picked once at page load by the visitor's local hour via `timeOfDayKey()` (`morning` 5-11, `noon` 12-16, `evening` 17-19, `night` 20-4) matched against each backdrop URL's filename — so a `'time'`-mode tenant's files MUST be named `morning.*`/`noon.*`/`evening.*`/`night.*` (any one/some/all four; a missing bucket just never gets picked). No tab-based crossfade, no re-check mid-session.

The remaining five keys tune how the active image actually renders — all data values consumed client-side, never Tailwind utility classes baked into Blade markup, so a tenant can tune them without touching the component:
- `opacity` — strength of the surface-color tint overlay painted over the active image (`background.blade.php`'s `:style="{ opacity: $store.background.opacity }"` on the overlay div). **Tenant-dependent by design, not a shared default**: fateh's `0.85` was tuned for 8 small abstract shapes cycling on a per-tab crossfade (a faint moving texture is the intent); persol's photographic time-of-day scenes are shown statically for the whole session, so that same strength washed them out almost completely (a high tint leaves only a sliver of the image visible). Persol's own value is being hand-tuned live against the actual photos rather than pinned once — check `config/tenants.php` for its current figure, don't assume the number here is current. Any future `'time'`-mode tenant with real photos should start from persol's value, not fateh's.
- `blur`/`brightness`/`contrast`/`grayscale` — plain CSS `filter` inputs (`blur(Npx)`, `brightness(N)`, `contrast(N)`, `grayscale(N)`), composed by `data/background.js`'s `imageStyle()` into one `filter:` string per active image, skipped entirely when at their neutral value (`0`/`1`/`1`/`0`) so a tenant that doesn't need them pays no extra style cost. `contrast` was added 2026-09-11 specifically so a tenant can pair it with a lowered `brightness` to darken a backdrop without the result looking flat/washed-out (brightness alone desaturates toward gray; contrast restores punch to the darkened image). Both current tenants ship neutral (no visual change from before these keys existed).
- `width` — the active image's inset: `'100%'` (persol, full-bleed — appropriate for a single hero photo) vs `'85%'` (fateh, centered with `my-5` vertical margin — the original "framed" look fateh's crossfading shapes always had). Applied only to whichever image is currently `activeIndex` (`imageStyle()` again), via plain inline `width`/`marginInline`/`marginBlock` styles rather than a Tailwind arbitrary-value class, since Tailwind's JIT can't compile a class for a value that only exists at runtime in `config/tenants.php`.
- `fit` — how the cover-scaled image is anchored: absent/`'cover'` (fateh — `bg-cover bg-center`, the original behavior) vs `'top'` (persol, added 2026-09-24). A `contain` variant was tried first and rejected by the user the same day ("very bad" — the letterbox band read worse than any crop), so the kept behavior is cover fill with the crop taken from the BOTTOM only: `bg-top` anchors the image's top edge to the layer's top, keeping the top of the photo maximally visible instead of center-cropping both edges. Additionally (same day, user-directed: "the start point must be as equal height as header"), under `'top'` the backdrop layer's top starts BELOW the header band — `background.blade.php` binds the layer to `top-[124px] lg:top-[144px]` (the header's exact combined height: brand row `h-[60px] lg:h-[80px]` + navbar `h-16` — keep these in sync if the header heights ever change) instead of `top-0`, so the photo begins right under the navbar rather than wasting its top sliver behind the opaque header. Consumed in `background.blade.php` via runtime `:class` ternaries (`'bg-top'` vs `'bg-center'` on the image divs, the top-offset pair vs `'top-0'` on the layer — all literals in source so Tailwind's JIT compiles them; the static classes stay `bg-cover` / `inset-x-0 bottom-0`, and an absent `fit` renders `top-0`, byte-identical to the old `inset-0`).

The whole nested object reaches the client the same way `window.__moduleChunks` does — a plain inline `<script>` in `layouts/app.blade.php` right after `<x-dashboard.module-chunks/>`: a `@php ... @endphp` block builds `$backdrop = array_merge(config('app.backdrop'), ['images' => array_map('asset', config('app.backdrop.images'))])` (merge, not a hand-listed key set, so a new key added to the tenant array reaches the client automatically), then `window.__tenantBackdrop = @json($backdrop)` — one object, one script tag, read synchronously into `stores/background.js`'s `BACKDROP` module-level constant (destructured into `IMAGES`/`BACKDROP_MODE`/`BACKDROP_OPACITY`/`BACKDROP_BLUR`/`BACKDROP_BRIGHTNESS`/`BACKDROP_CONTRAST`/`BACKDROP_GRAYSCALE`/`BACKDROP_WIDTH`/`BACKDROP_FIT`) before the deferred Vite module script runs (same ordering guarantee as the chunk map). This replaced eight literal `import bg1 from '../../../../assets/img/bg/backdrop1.png'`-style JS imports, which were a pre-existing violation of `resources/assets/assetPattern.md`'s "never import from `resources/assets/` in JS" rule.

**`@php(...)` single-statement shorthand corrupted this exact block once — use the `@php ... @endphp` block form for anything with a following directive that depends on normal parsing resuming.** See `resources/js/scriptPattern.md`'s note under "Tenant-driven backdrop mode" for the full failure mode (`Undefined variable $viteEntries` surfacing at a completely unrelated line).

Onboarding a new tenant's backdrop set is purely additive, same as the other roles: drop files into `img/<slug>/bg/`, add a `'backdrop' => ['images' => tenantBackdrops('<slug>'), 'mode' => ..., 'opacity' => ..., 'blur' => 0, 'brightness' => 1, 'contrast' => 1, 'grayscale' => 0, 'width' => ...]` entry to its `config/tenants.php` array. A tenant with no `bg/` folder at all just gets an empty `images` array (the Blade `x-for` renders nothing, background stays the plain surface color) — no crash, no fallback file, unlike the single-role image/video helpers.

**`'time'`-mode tenants only ever fetch their one active image, not the whole set (2026-09-24 fix).** The `x-for` in `background.blade.php` iterates `data/background.js`'s `renderIndices` getter, not the raw image count: `'tabs'` mode returns every index (needed for crossfade — any tab's image can become active), `'time'` mode returns just `[this.activeIndex]` (or `[]` if `images` is empty). Before this, `'time'` mode still rendered one `<div>` per image with its own `background-image` inline style, so the browser fetched all four morning/noon/evening/night JPEGs on every page load even though three of them can never become visible in that mode (the tab watcher is never registered — see `resources/js/scriptPattern.md`'s "Tenant-driven backdrop mode"). Any new backdrop mode must decide up front whether it's a "one fixed image" or "any image can become active" shape and feed `renderIndices` accordingly — don't go back to rendering the full set unconditionally.

## Admin login background (CSS, not Blade)
`resources/css/core/filament.css`'s `.fi-simple-layout::before` (Filament's built-in login-page background) is a Tailwind-compiled static asset — it can't call `config()` at request time. Bridged via a CSS custom property: the rule reads `background-image: var(--tenant-bg-image, url('/build/assets/img/admin-background.jpg'))`, and `FilamentPanelCustomizer` (applied from `AdminPanelProvider` via `FilamentPanelCustomizer::apply($panel)`) registers `->renderHook(PanelsRenderHook::HEAD_END, fn() => self::tenantBackgroundStyle())`, which emits `<style>:root{--tenant-bg-image:url("...")}</style>` from `config('app.admin_background_image')`, scoped to only the login route (guarded by `request()->routeIs('filament.admin.auth.login')`, matching `tenantLogo()`'s admin-scope guard). The value is escaped for CSS-string context (`addcslashes(..., '"\\')`), not HTML-entity escaped, since `<style>` is a raw-text element and HTML entities aren't decoded inside it.

## Favicon
`FilamentPanelCustomizer` uses Filament's own `->favicon(fn() => asset(config('app.favicon')))` panel method — not a manually-placed `<link>` tag — since the admin panel renders its own layout and never includes the user-panel's shared `meta-tags.blade.php` partial (which has its own separate `<link rel="icon">` for the user panel).

## Web manifest
`meta-tags.blade.php`'s `<link rel="manifest" href="{{ asset('site.webmanifest') }}">` is served dynamically by `GET /site.webmanifest` (`routes/web.php`, public/no-auth) → `resources/views/components/manifest.blade.php` via `view('components.manifest')` with `Content-Type: application/manifest+json; charset=utf-8`. It reads `config('app.name'/'name_en'/'slogan_en')` and `asset(config('app.favicon'))`, so it is tenant-aware (no static `public/site.webmanifest` — a real file there would shadow the route). The file lives in the components folder but is rendered as a plain Blade view from the route, not as a `<x-manifest>` component. `theme_color`/`background_color` are fixed default-theme literals (`#4e5f66`/`#08191e`) since the manifest is installed once and cannot follow the live theme/mode toggle. Only the `.ico` favicon is listed as a stopgap icon — add 192/512 PNGs to `resources/assets/img/<tenant>/` and reference them here when proper maskable PWA icons are needed.

## Testing
`tests/Feature/Helpers/HelpersTest.php` covers `tenantAsset()`, `tenantVideos()`, and `tenantLogo()` (both scopes, both the normal and `$auth = true` reverse-logo flags) directly against the real `fateh`/`persol` fixture folders — pure-logic, no DB, per `tests/Feature/coreTestPattern.md`. `tests/Feature/Support/FilamentPanelCustomizerTest.php` covers `logoHtml()`'s route-driven `$auth` wiring for the admin scope. `tests/Feature/Config/TenantsConfigTest.php` pins each tenant's flag values.

## Onboarding a new tenant
1. Add `resources/assets/img/<slug>/` with whichever role files apply (any missing role silently falls back to the generic default — no crash).
2. Add `resources/assets/video/<slug>/` with `1.mp4`, `2.mp4`, ... as many as needed.
3. Add one entry to `config/tenants.php` with all the same keys as `fateh`/`persol` — text, computed asset calls, and flags.
4. Set `APP_TENANT=<slug>` in `.env`.
