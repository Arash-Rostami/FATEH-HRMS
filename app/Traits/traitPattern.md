# Trait Pattern Guide

The single source of truth for **when shared logic becomes a trait instead of a Service**, and which of the three trait categories in this codebase a new one belongs to. Read this before adding any file to `app/Traits/`, and read `app/Services/servicePattern.md` first if the question is "trait or service" — they are complementary, not competing.

---

## 1. The one rule that decides everything

> **A trait exists because the shared logic must execute *inside* the consuming class — it needs `$this` to already be that class.** If the logic could run standing alone, given plain arguments, it is a Service, not a trait.

This is a hard boundary, not a style preference:

- A **Service** method is called as `app(Foo::class)->bar($x, $y)` from anywhere — a Livewire component, a Job, a Console command, another Service.
- A **trait** method is compiled directly into the consuming class. It can read `$this->composer`, call `$this->dispatch(...)`, declare a `#[Computed]` property, or hook a Livewire lifecycle method (`updated()`, `mount...()`) — none of which a Service can do, because a Service is never "the component itself."

**Correcting a common misreading of the Action/Service rule (§ of `servicePattern.md`):** "shared across modules → Service" applies to portable write/query logic. It does **not** apply to Livewire-component behavior. `App\Traits\ChatComposer` is shared by Channel and Contact and is correctly a trait, not a Service — moving it to a Service would strand its `#[Computed] groupedMessages()` and `dispatch('attachments-updated')` calls, which only make sense as literal members of a Livewire component. The same is true for `FocusOnRecord` (used by Channel, Contact, TaskBoard, Project, Ths, Reservation) and `ManagesTaskModal` (TaskBoard, Project). Being reused across modules is necessary but not sufficient for "should be a Service" — the deciding question is always "does this need to be inside the class."

## 2. Three trait categories in this codebase — know which one you're writing

### 2.1 Livewire-component behavior traits
Mixed directly into a `Livewire\Component` class. Hold `#[Computed]` properties, `dispatch()` calls, `#[Js]` methods, or lifecycle hooks (`updated()`, `mount...()`). **Cannot be Services** — see §1.

| Trait | Shared by | What it holds |
|---|---|---|
| `ChatComposer` (53 ln) | `Channel\Main`, `Contact\Main` | `updated()` hook on `composer.attachments`, `syncAttachments()`, `removeAttachment()`, `#[Computed] groupedMessages()`, `#[Js] cancelReply()` |
| `FocusOnRecord` (52 ln) | `Channel`, `Contact`, `TaskBoard`, `Project`, `Ths`, `Reservation` | `#[Url] $open`, `mountFocusOnRecord()` deep-link dispatch, `isFocusing()`, `clearFocus()` — the `?open={id}` global-search/menu deep-link contract every focusable module implements |
| `ManagesTaskModal` (325 ln) | `TaskBoard\Main`, `Project\Main` | The unified task create/edit modal — form state, checklist/label array sync, tab badges, attachment staging |
| `PreparesAdminTaskCreate` (2026-10-09) | admin `TaskResource\Pages\CreateTask` and `ProjectResource\RelationManagers\TasksRelationManager` | Admin-side create preparation so the Filament panel obeys the same rulebook: `prepareTaskCreate()` asserts assignable people against the chosen project's roster, validates labels against the project vocabulary, applies the SLA default deadline and computes `rank`; `ensureTaskDetail()` creates the detail row and applies the project's single default department |
| `HasDateSpan` (2026-10-16) | `TaskBoard\Main`, `Ths\Main`, `Dms\Main` — **deliberately NOT** `Reservation\Main` (its span has no created/updated basis and returns `[start, end]` without a column, so it keeps its own private `dateParts()`/`dateSpan()`) | The toolbar date-span filter: public `$dateBasis` (`created`\|`updated`) + `$fromYear..$toDay`, `#[Locked]` `$appliedDateParts`/`$appliedBasis` (only applied values reach the query), `setDateBasis()`, `applyDateSpan()` (validates through `jalaliSpanFromParts()`, toasts on an invalid range), `clearDateSpan()`, `dateSpanActive()`, protected `dateParts()` and `dateSpan()` => `[column, start, end]\|null`. The consumer implements the abstract protected `afterDateSpanChange()` hook: THS `perPage = 10`, DMS `resetAndReload()`, TaskBoard pages back to 1 + `loadTasks()`; its query does `->when($this->dateSpan(), fn($q, $span) => $q->whereBetween($span[0], [$span[1], $span[2]]))`. A trait because it owns Livewire public props and reads `$this`. |
| `HasProjectMembers` | `Project\Activity` (@mention list) | `projectMemberUsers`/`projectMemberIds` now come from `Project::charter()->rosterQuery()` (owner + members + department members, active and non-guest), not raw `member_ids` |

**`ChatComposer::lastMessageId()` removed 2026-10-09** (edit/delete now show on every own message inside the 600s window — see channelPattern §9 / contactPattern §6.2). A project-wide search (app, resources, JS, built bundles, service worker, tests, routes, config) found no reader apart from the removed edit/delete gate in `messaging/message-actions.blade.php`; the island refresh, adaptive poll, typing dot and receive sound read other state (`peerTyping`/`typingMembers`, the `data-rf` of the last rendered row, `_readUnread()`), not this computed. To restore it: add to `ChatComposer` `#[Computed] public function lastMessageId(): ?int { $id = collect($this->messages)->max('id'); return $id === null ? null : (int) $id; }`, re-add `$this->lastMessageId` to the `unset(...)` in `Contact\Main::invalidateMessageCache()`, and re-add `&& $msg['id'] === $this->lastMessageId` to the `can_edit`/`can_delete` conditions in `message-actions.blade.php`.

**`FocusOnRecord::$open` is a SHARED signal, not a free "which record is highlighted right now" scratch variable — repurposing it for an unrelated in-page UI concern breaks the global focus-chip.** Every consumer's root view `@include`s `components/dashboard/header/focus-chip.blade.php`, which renders "نتیجهٔ جستجو" (search result) + a clear button on the bare condition `!empty($open)` — it has no way to know *why* `$open` is set, only that it is. Real bug (2026-09-15, `Reservation`): the avantgarde dossier's card-deck UI (`deck.js`'s `deckOpen()`/`deckCycleAndOpen()`) called `$wire.set('open', id)` directly to track "which card is currently the big expanded face" — a purely local, in-page concept with nothing to do with search — so every card click made the chip claim the user had arrived via a search deep-link. **Fix pattern for any future module that wants to reuse `$open`'s existing float-to-front/`data-rf` scroll-marker plumbing for a non-search-origin trigger:** add a plain (non-`#[Url]`) companion boolean (e.g. `Reservation\Main::$deckOnly`) set alongside `$open` by a dedicated method (`focusDeck(int $id)`), never by writing the property directly from JS; override `clearFocus()` to reset the companion flag too, via trait-method aliasing (`use FocusOnRecord { FocusOnRecord::clearFocus as protected baseClearFocus; }` then a new `clearFocus()` that resets the flag and calls `$this->baseClearFocus()` — traits can't be reached with `parent::`, aliasing is the only way to still run the original body); and pass the override into the chip's own include (`@include('components.dashboard.header.focus-chip', ['open' => $deckOnly ? null : $open])`) rather than editing the shared component (which ~15 other modules include with zero params and must stay unaffected).

### 2.2 Presenter/view-shaping mixins
Composed into multiple **Presenter** classes (stateless, `new Presenter()` per render — see `livewirePattern.md`), not into the Livewire component itself. Technically *could* be Services (no Livewire dependency), but stay traits because Presenters already compose several of these fluently (`use HasAvatar, BuildsChatBubbles;`) and call each other's methods via `$this->` inside one shaping pass — injecting a Service per presenter method would fragment that into DI ceremony for zero behavioral gain.

| Trait | Shared by | What it holds |
|---|---|---|
| `BuildsChatBubbles` (81 ln) | `ChannelPresenter`, `ContactPresenter`, `ProjectPresenter` | `bubbleRadius()`, `attachments()`, `linkify()`, `replyPreview()`, `typeFlags()` — the universal chat-bubble primitives (`typeFlags($msg)`: space-separated content-type flags `t/i/v/p/f` for the client-side chat type filter, 2026-09-14) |
| `BuildsMessageGroups` (133 ln, `use BuildsChatBubbles`) | `ChannelPresenter`, `ProjectPresenter` — **deliberately NOT** `ContactPresenter` (its `read_at`-boolean read model and lack of `@mention` don't fit the per-member-cursor `readersMap` shape this trait assumes; see `contactPattern.md` §16C.5) | `messageGroup()`, `messages()` (per-message view row: is_mine/is_first/is_last/can_edit/can_delete/readers/mentions_you; `sender_online` mapped from the raw `sender.online` key — 2026-10-05, feeding the `is_last` avatar's presence dot, `viewPattern.md` §8.31 — ContactPresenter mirrors the same mapping in its locally-defined `messages()`). **2026-10-04 (corrected same day post-review; UI merged same day):** `messages()` also enriches each `is_mine` attachment with `viewers`/`viewer_count` when its raw entry carries a `views: {uid: isoTimestamp}` map, self-view excluded — resolved against `$readersMap` in O(views). Despite the name, `DownloadChannelAttachmentAction` is NOT Channel-exclusive: Project's `TeamChat` calls the same action (it's backed by a real `Channel` row), so `views` is written there too; it stays inert in Project's UI only because `TeamChat` hardcodes `readersMap = []`, not because of any guard in this trait — don't assume isolation from the name alone. The raw `views` key is always stripped from the shaped `attachments` output for every message (presenter-boundary hygiene), not just `is_mine`. The message-level `readers[]` entries also carry `read_at` (sourced from `$readersMap[uid]['read_at']`, itself `channel_members.updated_at` — an approximation of "last read-cursor sync", not a true per-message read time). `viewers`/`readers` are rendered together in ONE popover by `channelPattern.md` §9, not two separate UI elements. `readerSummary()` |
| `HasTimelineMonths` (18 ln) | Timeline-style module presenters (Links/Gallery/Feeds — see `project_timeline_modules_second_view`) | `months()` — buckets a collection into distinct "Month Year" labels, sorted desc |
| `RiskEscalationChip` | `ProjectPresenter`, `TasksheetPresenter`, `TicketPresenter` (Ths) | `riskToneClasses(string $tone)` — the success→warning→error chip-tone primitive extracted from `ProjectPresenter`'s header risk/deadline chips so `TasksheetPresenter`'s project-health chip and `TicketPresenter`'s `deadlineChip()` reuse the exact same escalation classes, not a second copy; see `app/Livewire/Dashboard/Tasksheet/tasksheetPattern.md` |

**Rule for this category:** before composing a new one of these into a fourth presenter, re-check the assumptions the trait bakes in (e.g. `BuildsMessageGroups`'s per-member cursor) actually hold for the new consumer — Contact's exclusion above is the proof this isn't automatic.

### 2.3 Model traits
Mixed into Eloquent models, not Livewire components or Presenters. Static or instance helpers tied to a model's own lifecycle hooks (`booted()`, `forceDeleted`).

| Trait | What it holds |
|---|---|
| `CleansAttachedFiles` (101 ln) | `deleteStoredFiles()`, `deleteStoredDirectory()` — safe (path-traversal-guarded) storage cleanup called from a model's `forceDeleted`/`deleted` boot hook. Used by `Channel`, `ChannelMessage`, etc. |
| `StoresAttachedFiles` | `storeAttachment()` — normalizes an `UploadedFile` into the canonical `{path, name, mime, size}` shape (see `project_attachment_writers_footprint` memory); `storeAttachments(array $files, string $directory, Closure|string|null $fileName = null)` (optional name resolver, e.g. `FileNamer::stored(...)`, passed to every file) — batch wrapper with rollback (`deleteStoredFiles` on partial failure). **Composition requirement:** the rollback calls `CleansAttachedFiles::deleteStoredFiles()`, so any class calling `storeAttachments()` must use both concerns (every current caller does). |
| `HasReminders` | `reminders(): MorphMany` — the polymorphic relation a host model exposes to the Reminder widget (see `app/Livewire/Dashboard/Reminder/reminderPattern.md`); boots a `deleting` hook that iterates and deletes each reminder individually (`$model->reminders->each->delete()`) rather than a bulk `MorphMany::delete()`, so per-row Eloquent events still fire on cascade. **Guarded against soft-delete data loss** (2026-09-14 fix): `if (method_exists($model, 'isForceDeleting') && !$model->isForceDeleting()) return;` — on `Task`/`Project` (both `SoftDeletes`), a plain `->delete()` trashes the host without touching its reminders (recoverable via `restore()`); reminders are only cascade-deleted on `->forceDelete()`. On `Ticket`/`DMS`/`Reservation` (no `SoftDeletes`), the guard is a no-op (`isForceDeleting` doesn't exist) and `->delete()` still cascades immediately, since that delete is already permanent. Attached to `App\Models\Task`, `Ticket`, `Project`, `DMS`, and `Reservation` (5 models). |
| `HasActive` (2026-10-16, `app/Models/Concerns/`) | `scopeActive`/`scopeInactive` plus `initializeHasActive()` merging the `boolean` cast and `active` fillable (no per-model `$casts`/`$fillable` edit). `active = false` hides a record from the **user panel only** (lists, nudges, search, deep links); admin always sees everything and engagement data/`pinned` are untouched. Used by `Ad` and, through `HasAudience`, `Feed`, `Post`, `Photo`, `Report`. |
| `HasAudience` (2026-10-16, `app/Models/Concerns/`; `use HasActive`) | The department-audience contract: `departments` JSON (null/`[]` = public; cast + fillable merged by `initializeHasAudience()`), `scopeVisibleTo($dept)`, `scopeForViewer($user = null)` (= `active()->visibleTo(viewer dept)` — the ONE call every user-panel list, count and search `scope()` makes), `audienceCodes()`, `isVisibleTo($dept)` (false when inactive — used where a single record is picked, e.g. `Posts::selectPost()`), `audienceUsers()` (active users in the audience — what the nudges' `for()` returns) and the `is_public` / `audience_departments` accessors. A model that also keeps a legacy single `department_id` as audience opts in with `public const AUDIENCE_INCLUDES_DEPARTMENT_ID = true` (only `Photo`); `Report::department_id` is the report's *subject*, not its audience, so `Report` does not opt in. Used by `Feed`, `Post`, `Photo`, `Report`. |

### 2.4 Cross-domain mixins (Auth / Filament — out of scope for the Livewire-dashboard modules, listed for completeness)
`AuthValidationRules`, `AuthorizesByPermission` (the one-true-admin-model `permits()` gate — see `skillsPattern.md`'s "Ownership-bypass" note), `InteractsWithNotifications`, and the twelve `Filament*` traits (`FilamentActions`, `FilamentAdminGuide`, `FilamentDateHandler`, `FilamentEditHeading`, `FilamentFilters`, `FilamentFormDivider`, `FilamentHeaderActions`, `FilamentIconOptions`, `FilamentPageBehavior`, `FilamentPreferences`, `FilamentVisibility`, `FilamentWorkflowPresenter` — shared columns/actions/infolist for the two workflow RelationManagers; since 2026-10-09 also `forceAdvanceWorkflowAction()` and `reassignWorkflowStepAction()`, both shown only when `ProjectResource::canEdit($record)` and the cycle is active) are admin-panel/Resource/Page mixins governed by `app/Filament/filamentPattern.md`, not this doc. `App\Filament\Traits\HandlesDroppedFiles` (in `app/Filament/Traits/`, built on `CleansAttachedFiles`) deletes the files an admin edit removed or replaced — see filamentPattern rule 78.

`FilamentAdminGuide` also carries `shouldRegisterNavigation()` (2026-10-24): `parent::shouldRegisterNavigation() && !tenantOffName(static::getSlug())` hides an off module's admin sidebar entry (view-only, no permission change) — see `config/tenantPattern.md`.

`FilamentVisibility` (2026-10-16) is the admin half of `HasActive`/`HasAudience`, used by `FeedResource`, `PostResource`, `GalleryResource`, `ReportResource`, their `List*` pages and `*Exporter`s (the traits are `use`d in all three): static builders `activeToggle()`/`activeColumn()` (a `ToggleColumn`, disabled unless `canEditAny()`)/`activeEntry()`/`activeFilter()`/`activeGroup()`/`activeExportColumn()`, `departmentsSelect()`/`audienceColumn()`/`audienceEntry()`/`audienceFilter()`/`visibilityFilter()`/`audienceExportColumn()` (Feed/Post only; Gallery/Report keep their own department fields), `activeTabs(Closure $stats)` (needs `active_count`/`inactive_count` in the page's stats query) and `bulkVisibilityActions()`. Details: `app/Filament/filamentPattern.md` → "Active / audience visibility".

### 2.5 Small single-concern helper traits
Sometimes a trait exists purely to DRY two Actions in the *same* module without becoming a full Service (§ of `servicePattern.md` — no second module needs it, no non-Livewire caller exists). Example: `ResolvesTaskDeadline` — two private methods shared between the create/update Task Actions: `resolveDeadline(TaskForm $form): ?Carbon` (the form's Jalali Y/M/D fields into a Carbon instant, always at 12:00:00) and `resolveTaskDeadline(Form $form, ?Project $project, ?Carbon $current = null, bool $projectChanged = false): ?Carbon` (replaced `guardProjectDeadline` 2026-10-09: a blank deadline gets the project's SLA default via `charter()->defaultDeadline()`; a typed deadline must be in a sane Jalali year, not in the past, and — only when it actually changed or the project changed — within the project cap via `charter()->assertDeadline`; both Actions call it, the update path included, so the cap can't be dodged by editing and a legacy over-cap task stays editable). This is legitimately a trait-sized helper, not a Service-in-waiting — promote it only if a second module needs the same conversion/guard.

`ResolvesReminderDueDate` follows the same shape one level down — a single method, `resolveDueAt(ReminderForm $form): Carbon`, shared between `Create`/`UpdateReminderAction` to convert the form's Jalali Y/M/D + time fields into one Carbon instant. No guard counterpart needed (reminders have no parent-deadline cap to enforce).

## 3. Where traits live (convention differs from Actions/Services)

Unlike Actions (nested per-module under `app/Livewire/Dashboard/{Module}/Actions/`) and Services (grouped per-domain under `app/Services/{Domain}/`), **traits live flat in `app/Traits/`** regardless of how many modules consume them — even a trait used by exactly one module today (e.g. a future TaskBoard-only Livewire mixin) still goes in `app/Traits/`, not inside the module folder. This is existing, consistent convention — don't nest a new trait under a Livewire module folder to "match" the Actions pattern.

**The one exception: Eloquent-only model traits live in `app/Models/Concerns/`** (namespace `App\Models\Concerns`), not `app/Traits/` — and every file there is named `Has*` (`HasModelCache`, `HasReplies`, `HasMenuState`, …). A trait consumed **only** by classes under `app/Models/` goes there; cross-domain traits that models share with Filament/Resource classes (e.g. `CleansAttachedFiles`, `StoresAttachedFiles`, consumed by both `App\Models\*` and `App\Filament\*`) stay in `app/Traits/` under this doc's rules.

## 4. Do / Don't

**DO**
- Ask "does this need `$this` to already be the consuming class" before reaching for a trait — if no, it's a Service (`servicePattern.md`).
- Put a new Livewire-component-behavior trait in `app/Traits/` flat, even for a single current consumer.
- Re-verify a Presenter mixin's baked-in assumptions before composing it into a new Presenter (§2.2).
- Keep Model traits scoped to model-lifecycle concerns (storage cleanup, static query scopes) — not business rules that belong in an Action.

**DON'T**
- Don't treat "used by multiple modules" alone as proof something belongs in `app/Services/` — Livewire-bound behavior stays a trait no matter how many modules mix it in (§1).
- Don't add Livewire-specific code (`dispatch()`, `#[Computed]`, Form properties) to a class under `app/Services/` — that class is secretly a trait that hasn't been renamed yet.
- Don't create a per-module trait subfolder — traits are flat in `app/Traits/` by convention (§3).
- Don't force `HasDateSpan` onto a module whose span shape differs (Reservation: no basis, no column) — re-check the trait's `[column, start, end]` contract first (§2.1).
- Don't assume a two-Action helper trait like `ResolvesTaskDeadline` should immediately become a Service — wait for a real second module, same as the Action→Service rule.
