# Providers — View Composer convention (2026-10-06)

## Class-based composers live in `app/View/Composers/`, registered in `ViewServiceProvider::boot()`

Any view data that requires real branching logic (more than a one-line `$view->with(...)`) gets its own class — never grows as an inline closure in `ViewServiceProvider`. Each composer is a plain class with one public `compose(View $view): void` method, registered via `View::composer($viewName, ComposerClass::class)` — Laravel resolves and calls `compose()` automatically, same mechanism as a closure composer, just testable in isolation and free of logic living inside a service provider's `boot()`. **Uniform house style since 2026-11-02 (matching the user's `AccountOnboardingComposer` refactor):** dependencies come in via promoted constructor injection (never `app()` mid-method), `auth()->user()` is read once at the top of `compose()`, branchy computation lives in `private` helper methods so `compose()` stays a short read, and multiple view variables ship in a single `$view->with([...])` array rather than chained `->with()` calls. All seven composers follow it; new ones copy the shape.

A trivial one-liner (no branching, just `$view->with('key', some_call())`) can stay an inline closure — `MenuStateComposer`/`ErrorTraceComposer` were converted to classes anyway for consistency (2026-10-06 cleanup), but that's a style choice, not a hard rule; don't force a class onto something that's genuinely one line forever.

**Gotcha: the view name passed to `View::composer()` is NOT always the component-prefix name.** `components.*` is only for actual Blade components (`resources/views/components/...`, invoked as `<x-...>`). A plain extended layout like `resources/views/layouts/app.blade.php` — reached via `->extends('layouts.app')` from every Livewire full-page component — is registered as `'layouts.app'`, not `'components.layouts.app'`. Get this wrong and the composer silently never fires (no error, the view data is just missing).

**Example — `ModuleChunkComposer` (`layouts.app`):** replaced an inline `@php` block that computed `$moduleChunk`/`$maxScope` from the current route + `?tab=` query param (used for the lazy per-module JS chunk `@vite` entry and the `data-max-scope` attribute the maximize-persistence feature reads — see `resources/js/scriptPattern.md`'s "Pre-paint flash avoidance" section). Moving it to a composer made the route→scope resolution independently testable (`tests/Feature/Providers/ViewServiceProviderTest.php`) without rendering the full layout by hand in every module's own test file — `EnergyTest.php`'s pre-existing `data-max-scope` assertion for the `/energy` route still passes unchanged, proving the refactor is behavior-identical to the inline block it replaced.

**`AccountOnboardingComposer` (`components.dashboard.navbars.top.account`):** replaced the inline `@php` block computing `$exclusiveOnboarding` (`Cache::remember` keyed via `ModelCacheVersion::key(Onboarding::class, 'exclusive:'.auth()->id())`, 1-day TTL, `first(['updated_at'])` only) and the derived `$onboardingHighlighted` boolean. Key/TTL/column-selection preserved byte-for-byte — this cache key is shared with other onboarding-reading code paths, do not touch it casually. Since 2026-11-02 it also supplies `$profileCompletion` (the Profile-shortcut's percentage badge) via `ProfilePresenter::completion(auth()->user())`, `100` for guests — same presenter as the Profile page's nudge, same already-loaded profile relation, zero extra queries; guarded by `NavbarTest`'s `profile_completion` pair.

**`OccasionComposer` (`components.dashboard.modal.occasion`):** replaced the inline `@php` block that resolves a one-shot birthday/anniversary greeting via `isSpecialDay()` and marks it "shown" via `cache()->put(...)`. This composer has real side effects (it mutates cache state on a qualifying page load, not just reads) — the quote arrays are unchanged from the inline version. Since 2026-10-26 the shown-mark TTL is `now()->endOfDay()` (dies at midnight → exactly one show per day; a reload late the same day no longer re-shows as the old 12h window allowed). The composer's own `cache()->has` pre-checks were dropped — `isSpecialDay()` already owns that check and now tests the date BEFORE the cache key, so a normal-day page load costs zero cache round-trips (previously 4). Behavior pinned in `tests/Feature/View/OccasionComposerTest.php`.

**`ModuleAssetChunksComposer` (`components.dashboard.module-chunks`):** replaced the inline `@php` loop building the `$chunks` array fed to `window.__moduleChunks` via `Vite::asset()` per module, silently skipping any module whose compiled asset is missing (`try`/`catch` preserved as-is).

**`NavUnreadComposer` (`components.dashboard.navbars.top` + `components.dashboard.navbars.top.notification`, 2026-10-30):** replaced the inline `@php($navHasUnread = auth()->check() && auth()->user()->unreadNotifications()->exists())` in top.blade.php and the same query as the `$lit ??` fallback in notification.blade.php — one unread-existence DB query per full-page render, now computed once by the composer for both views (the notification bell's fallback previously had NO `auth()->check()` guard; the composer's guarded bool is strictly safer). Freshness after initial paint is unchanged: the bell dot still tracks the `bell-unread` browser event (viewPattern.md §8.35). **Gotcha: a composer variable must not collide with a component `@props` name** — notification.blade.php declares `@props(['lit' => null])`, and an un-passed prop is assigned null after the composer runs, masking any `$lit` a composer might supply; hence the composer variable is `navHasUnread` and the blade falls back as `$lit ?? $navHasUnread`.

**`bottom.blade.php`'s pagination logic went to `TabPresenter::bottomNavPaging()`, not a new composer or a method on `Tabs.php` directly.** `TabPresenter` already exists as the one-presenter-per-Livewire-module convention for `App\Livewire\Dashboard\Tab\*` (see `rankedOnlineUsers`/`stats`/`tools`/`shortcuts` — all pure, take already-available data, no fresh queries), and the bottom-nav paging (`array_chunk` splitting `$tabs` into two swipeable pages) is pure array transformation of the already-computed `tabs()` `#[Computed]` result, exactly the shape every other `TabPresenter` method takes — so it belongs there rather than forking a second presentation mechanism for one Livewire component. `Tabs::render()` calls `(new TabPresenter())->bottomNavPaging($this->tabs, $this->activeTab)` the same way every sibling `Main.php`/`Tab/*.php` instantiates its presenter inline in `render()`.

## Everything else in `app/Providers/`

The other providers (`AppServiceProvider`, `FilamentServiceProvider`, `FortifyServiceProvider`, `ModelCacheServiceProvider`, `NudgeServiceProvider`, `EdgeServiceProvider`, `Filament/`) are standard Laravel/Filament bootstrapping — package registration, macro definitions, Filament panel config. No project-specific convention beyond normal Laravel service-provider usage; nothing here warrants its own doc section unless a future addition introduces real branching logic the way `ModuleChunkComposer` did.

**One addition to `FilamentServiceProvider` (2026-10-28, folded 2026-10-29):** the `ViewAction::configureUsing` registration and its `MODAL_CUSTOM_CONTENT_BEFORE` render hook (BMS-CM's trick: panel-wide Create/Edit/Delete shortcut buttons in every infolist view-modal footer + icon-only quick actions in the modal header) live INSIDE `registerComponentHooks()`, alongside the panel's other render hooks — one uniform registration block in `boot()`, no separate call site. All logic lives in the trait (`app/Traits/FilamentViewActionDefaults.php` — only the static helpers `viewModalShortcuts()`/`quickActionIcons()`; its former `registerViewActionDefaults()` entry point was absorbed by the provider), documented in `filamentPattern.md` §3.5 — the provider itself stays free of branching logic.

**Deferred tables panel-wide (2026-11-02):** `FilamentServiceProvider::registerTableDefaults()`'s existing `Table::configureUsing` now ends with an unconditional `->deferLoading()` — EVERY Filament table (resource lists, relation managers, table widgets) renders its shell/skeleton first and fetches rows in a second quick request (`wire:init` → `loadTable()`). One lever, no per-presenter edits, deliberately no config switch and no per-table opt-out (user decision 2026-11-02: all tables, not selective). Test harness only: `Tests\TestCase::setUp()` registers a later `Table::configureUsing(fn ($t) => $t->deferLoading(false))` so the ~400 existing record assertions keep working without a `loadTable()` per test — it never runs in production; `LinkResourceTest::test_deferred_table_stays_empty_until_loaded_as_the_panel_default_ships` re-registers `deferLoading()` and pins the real deferred flow (empty until `loadTable()`, then rows).

**Named limiter `icon-miss` (2026-11-03):** `FortifyServiceProvider::boot()` next to `login`/`two-factor` — two limits (20/min per IP + 60/min global, no `by()`) used by `POST /icon-miss` (`throttle:icon-miss`), so a botnet or a shared proxy IP cannot flood the cache or log; see `app/Http/httpPattern.md`.

**One exception — `AppServiceProvider::boot()` carries the tenant module-off route guard (2026-10-24):** `Event::listen(RouteMatched::class, …)` aborts 404 when `tenantOffName()` matches the module slot of the matched route name (or, for `livewire.update`, of each payload component name). It is a listener, not route middleware, because a closure in a route group breaks `route:cache`. See `config/tenantPattern.md` "Module `off` list".
