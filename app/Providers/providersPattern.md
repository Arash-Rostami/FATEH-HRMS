# Providers — View Composer convention (2026-10-06)

## Class-based composers live in `app/View/Composers/`, registered in `ViewServiceProvider::boot()`

Any view data that requires real branching logic (more than a one-line `$view->with(...)`) gets its own class — never grows as an inline closure in `ViewServiceProvider`. Each composer is a plain class with one public `compose(View $view): void` method, registered via `View::composer($viewName, ComposerClass::class)` — Laravel resolves and calls `compose()` automatically, same mechanism as a closure composer, just testable in isolation and free of logic living inside a service provider's `boot()`.

A trivial one-liner (no branching, just `$view->with('key', some_call())`) can stay an inline closure — `MenuStateComposer`/`ErrorTraceComposer` were converted to classes anyway for consistency (2026-10-06 cleanup), but that's a style choice, not a hard rule; don't force a class onto something that's genuinely one line forever.

**Gotcha: the view name passed to `View::composer()` is NOT always the component-prefix name.** `components.*` is only for actual Blade components (`resources/views/components/...`, invoked as `<x-...>`). A plain extended layout like `resources/views/layouts/app.blade.php` — reached via `->extends('layouts.app')` from every Livewire full-page component — is registered as `'layouts.app'`, not `'components.layouts.app'`. Get this wrong and the composer silently never fires (no error, the view data is just missing).

**Example — `ModuleChunkComposer` (`layouts.app`):** replaced an inline `@php` block that computed `$moduleChunk`/`$maxScope` from the current route + `?tab=` query param (used for the lazy per-module JS chunk `@vite` entry and the `data-max-scope` attribute the maximize-persistence feature reads — see `resources/js/scriptPattern.md`'s "Pre-paint flash avoidance" section). Moving it to a composer made the route→scope resolution independently testable (`tests/Feature/Providers/ViewServiceProviderTest.php`) without rendering the full layout by hand in every module's own test file — `EnergyTest.php`'s pre-existing `data-max-scope` assertion for the `/energy` route still passes unchanged, proving the refactor is behavior-identical to the inline block it replaced.

**`AccountOnboardingComposer` (`components.dashboard.navbars.top.account`):** replaced the inline `@php` block computing `$exclusiveOnboarding` (`Cache::remember` keyed via `ModelCacheVersion::key(Onboarding::class, 'exclusive:'.auth()->id())`, 1-day TTL, `first(['updated_at'])` only) and the derived `$onboardingHighlighted` boolean. Key/TTL/column-selection preserved byte-for-byte — this cache key is shared with other onboarding-reading code paths, do not touch it casually.

**`OccasionComposer` (`components.dashboard.modal.occasion`):** replaced the inline `@php` block that resolves a one-shot birthday/anniversary greeting via `isSpecialDay()` and marks it "shown" via `cache()->put(...)`. This composer has real side effects (it mutates cache state on a qualifying page load, not just reads) — the quote arrays are unchanged from the inline version. Since 2026-10-26 the shown-mark TTL is `now()->endOfDay()` (dies at midnight → exactly one show per day; a reload late the same day no longer re-shows as the old 12h window allowed). The composer's own `cache()->has` pre-checks were dropped — `isSpecialDay()` already owns that check and now tests the date BEFORE the cache key, so a normal-day page load costs zero cache round-trips (previously 4). Behavior pinned in `tests/Feature/View/OccasionComposerTest.php`.

**`ModuleAssetChunksComposer` (`components.dashboard.module-chunks`):** replaced the inline `@php` loop building the `$chunks` array fed to `window.__moduleChunks` via `Vite::asset()` per module, silently skipping any module whose compiled asset is missing (`try`/`catch` preserved as-is).

**`bottom.blade.php`'s pagination logic went to `TabPresenter::bottomNavPaging()`, not a new composer or a method on `Tabs.php` directly.** `TabPresenter` already exists as the one-presenter-per-Livewire-module convention for `App\Livewire\Dashboard\Tab\*` (see `rankedOnlineUsers`/`stats`/`tools`/`shortcuts` — all pure, take already-available data, no fresh queries), and the bottom-nav paging (`array_chunk` splitting `$tabs` into two swipeable pages) is pure array transformation of the already-computed `tabs()` `#[Computed]` result, exactly the shape every other `TabPresenter` method takes — so it belongs there rather than forking a second presentation mechanism for one Livewire component. `Tabs::render()` calls `(new TabPresenter())->bottomNavPaging($this->tabs, $this->activeTab)` the same way every sibling `Main.php`/`Tab/*.php` instantiates its presenter inline in `render()`.

## Everything else in `app/Providers/`

The other providers (`AppServiceProvider`, `FilamentServiceProvider`, `FortifyServiceProvider`, `ModelCacheServiceProvider`, `NudgeServiceProvider`, `EdgeServiceProvider`, `Filament/`) are standard Laravel/Filament bootstrapping — package registration, macro definitions, Filament panel config. No project-specific convention beyond normal Laravel service-provider usage; nothing here warrants its own doc section unless a future addition introduces real branching logic the way `ModuleChunkComposer` did.

**One exception — `AppServiceProvider::boot()` carries the tenant module-off route guard (2026-10-24):** `Event::listen(RouteMatched::class, …)` aborts 404 when `tenantOffName()` matches the module slot of the matched route name (or, for `livewire.update`, of each payload component name). It is a listener, not route middleware, because a closure in a route group breaks `route:cache`. See `config/tenantPattern.md` "Module `off` list".
