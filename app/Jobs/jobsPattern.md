# `app/Jobs` — queued reconcile/sync jobs

Nine jobs, all `ShouldQueue`, `tries = 3`, `backoff = [10, 30]` (the deliberate exceptions are `SendNotifyRule`, `SendNotifyChunk` and `SendReminderSms`: `tries = 1`, a retry would re-send), plain `queue:work` workers (the queue connection is env-dependent — `.env.example` ships `database`, production uses redis). Rule: a job is a thin wrapper around a Service/Model method; it holds no business rules and re-finds its model by id (a missing row is a silent no-op).

| Job | Dispatched from | Notes |
|---|---|---|
| `ReconcileNudge(ruleKey, subjectClass, subjectId)` | `NudgeService` on every registered trigger event, `Profile::saved` (open tickets; on a department move also Post/Feed/Report/Photo whose audience holds the old/new code), `User::saved` (ticket heads), `Reminder` | `ShouldBeUniqueUntilProcessing`, `uniqueFor = 2`s, id = `rule|class|subject` — a burst of saves on one record queues ONE reconcile. Calls `NudgeService::reconcile`. Master-class kinds (`TaskNudge`, `ProjectNudge`) share the job; the rule key tells them apart. |
| `ReconcileEdge(...)` | `NudgeService`-style edge (toast) rules | Same contract for Signal 3; not unique. |
| `ReconcileReminderDue(reminderId)` (2026-10-26) | `Reminder::queueDueReconcile()` — called from the model's `saved` hook and from `reminders:sweep-due` — as `dispatch(...)->delay($at)->afterCommit()` where `$at = max(due_at, snoozed_until)` when that moment is ≤ 24 h away (already-past moments run at once) | Runs at the reminder's due moment: FIRST `Reminder::deliverDue()` (outside the transaction; sends the email/SMS once, guarded by `notified_at`), then `NudgeService::reconcile('reminders-controller:due-nudge', …)` (inside the same `DB::transaction(…, 3)` as `ReconcileNudge`) then `EdgeService::reconcile('reminders-controller:due-today-edge', …)`. Not unique on purpose (`Cache::add` already de-duplicates per (reminder, due moment), so a `ShouldBeUnique` lock with a day-long `uniqueFor` would add nothing). De-duplicated at dispatch by `Cache::add("reminder-due-queued:{id}:{atTimestamp}")` (future moment: key lives until `$at`; a past moment within the last 24 h on a reminder with an email/SMS channel: dispatched at once and the key lives one minute, so repeated saves within a minute queue one job; older past moments and in-app-only past moments are not dispatched), so each (reminder, future due moment) is queued once however many saves or hourly sweeps see it; a redis flush clears both the delayed job and the key, and the next hourly sweep re-queues it. Idempotent: a stale job (reminder edited/completed/deleted since) just re-evaluates `show()`. |
| `SyncTaskCalendarEventJob(taskId)` | `HasTaskActivityLog` saved hook (Task and TaskDetail) | `afterCommit()` in the constructor (dispatched inside the save transaction otherwise ran before the row was visible and missed events) and `ShouldBeUniqueUntilProcessing` with `uniqueFor = 5`s so create + detail-save dispatch once. Delegates to `EventSyncService::sync`; done/archived/deadline-less tasks purge their calendar event. |
| `SyncProjectChannelMembershipJob(projectId)` | `Project::saved` (members/departments/owner changed), `Profile::saved` (department move touches every project that targets the old/new department) | `afterCommit()`. Audience = `Project::charter()->rosterIds()` (owner + members + department members, active non-guest); adds missing members with a fresh read cursor, detaches the rest except the owner, and re-points `channel.owner_id` to the project owner. A project-linked channel cannot be deleted or made Open by hand (`Channel::isProjectLinked`). |
| `LogMissingSkillJob` | Skills directory | Unchanged. |
| `SendNotifyRule(ruleId, payload)` — COORDINATOR (2026-10-27) | `NotifyService::handle()` — one job per live matching `NotifyRule`, `dispatch(...)->afterCommit()`, from the `HasNotifyEvents` model trait; also the admin one-off «ارسال پیام» action (`SendMessageAction`, plain `dispatch()` with a `values`-carrying payload and no `event`) | **`tries = 1`, no backoff, `timeout = 60`, on purpose:** a retry would re-mail every recipient that already got the message. Never sends. Carries a light payload (no record values for created/updated; deleted keeps its snapshot) and re-reads the record. Re-finds the rule (missing or `is_active = false` = no-op), re-checks the rule's `conditions` against the freshly re-read record for created/updated (`$rule->matches($record)`; a deleted snapshot skips it) — on mismatch it writes ONE summary row (`batch.conditions_changed`) and sends nothing — builds the message, `RecipientResolver::resolveWithSkips()`, refuses runs above `notify.ceiling` (summary row only), writes the summary + skipped `NotifyLog` rows and dispatches the chunks. An exception becomes the summary row's error. |
| `SendNotifyChunk(ruleId, runId, channelKey, message, addresses, detailed, event, recordId)` (2026-10-27) | `SendNotifyRule` — one per channel slice (`notify.chunk.mail` 20 / `notify.chunk.sms` 200), `->delay(index * notify.delay)` (3 s, index across channels) | `tries = 1`, `timeout = notify.timeout` (60), `failOnTimeout`. Calls `NotifyChannel::sendMany()` and writes its sent/failed rows with ONE `NotifyLog::insert`; channel off / unconfigured / any throwable = one `failed` row with `count` N; `failed()` (worker kill/timeout) writes the same row. `SendNotifyRule::failed()` writes a summary row with the run-failed error. Per-person `sent` rows only when `detailed` (channel recipients ≤ `notify.detail_below`), else one aggregated row. See "Batch pipeline" in `app/Services/Notify/notifyPattern.md`. |
| `SendReminderSms(reminderId)` (2026-10-27) | `Reminder::deliverDue()` (from `ReconcileReminderDue` and the `reminders:sweep-due` safety net) when the reminder has the SMS channel on and the tenant has `notify:sms` | `tries = 1`. Sends one SMS (title line + notes) through `SmsChannel`; no-op when the reminder, the number or the provider is missing. |

Gotchas
- **`ReconcileNudge::handle` wraps `NudgeService::reconcile` in `DB::transaction(..., 3)` (restored 2026-10-25 — the 2026-10-23 version was lost uncommitted).** The hourly sweeps queue a burst, and two workers' `delete from notifications where data->menu_key/item_id` (JSON filter, no index) deadlocked (MySQL 1213) once per hour, costing a 10 s backoff retry; `transaction()`'s attempts arg retries a deadlock instantly. Keep it on any job whose body deletes by a JSON path.
- Dispatch raw/bulk-written changes yourself: `DB::table`/query `update` fires no model event, so no job runs (the overhaul replaced those with per-model updates; the nightly `ArchiveStaleDoneTasks` bumps the `Task` cache version explicitly).
- `afterCommit` jobs dispatched with `dispatch(...)->afterCommit()` outside a transaction run immediately — safe either way.
- Queue workers keep code in memory: after changing a job or a nudge class run `php artisan queue:restart`, not just an FPM reload.
