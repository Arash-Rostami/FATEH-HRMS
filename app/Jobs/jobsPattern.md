# `app/Jobs` — queued reconcile/sync jobs

Thirteen jobs, all `ShouldQueue`, `tries = 3`, `backoff = [10, 30]` (the deliberate exceptions are `RefreshLaunchpadJob` (`tries = 1`, always succeeds), `SendNotifyRuleJob`, `SendNotifyChunkJob`, `SendReminderSmsJob`, `GenerateReportJob`, `GenerateCorrespondenceJob` and `SendCorrespondenceJob`: `tries = 1`, a retry would re-send or re-call the provider), plain `queue:work` workers (the queue connection is env-dependent — `.env.example` ships `database`, production uses redis). Rule: a job is a thin wrapper around a Service/Model method; it holds no business rules and re-finds its model by id (a missing row is a silent no-op).

| Job | Dispatched from | Notes |
|---|---|---|
| `ReconcileNudgeJob(ruleKey, subjectClass, subjectId)` | `NudgeService` on every registered trigger event, `Profile::saved` (open tickets; on a department move also Post/Feed/Report/Photo whose audience holds the old/new code), `User::saved` (ticket heads), `Reminder` | `ShouldBeUniqueUntilProcessing`, `uniqueFor = 2`s, id = `rule|class|subject` — a burst of saves on one record queues ONE reconcile. Calls `NudgeService::reconcile`. Master-class kinds (`TaskNudge`, `ProjectNudge`) share the job; the rule key tells them apart. |
| `ReconcileEdgeJob(...)` | `NudgeService`-style edge (toast) rules | Reconciles Signal 3 (`EdgeService::reconcile`) with the same `(ruleKey, subjectClass, subjectId)` arguments, but is NOT unique (no `ShouldBeUniqueUntilProcessing`, unlike `ReconcileNudgeJob`). |
| `ReconcileReminderDueJob(reminderId)` (2026-10-26) | `Reminder::queueDueReconcile()` — called from the model's `saved` hook and from `reminders:sweep-due` — as `dispatch(...)->delay($at)->afterCommit()` where `$at = max(due_at, snoozed_until)` when that moment is ≤ 24 h away (already-past moments run at once) | Runs at the reminder's due moment: FIRST `Reminder::deliverDue()` (outside the transaction; sends the email/SMS once, guarded by `notified_at`), then `NudgeService::reconcile('reminders-controller:due-nudge', …)` (inside the same `DB::transaction(…, 3)` as `ReconcileNudgeJob`) then `EdgeService::reconcile('reminders-controller:due-today-edge', …)`. Not unique on purpose (`Cache::add` already de-duplicates per (reminder, due moment), so a `ShouldBeUnique` lock with a day-long `uniqueFor` would add nothing). De-duplicated at dispatch by `Cache::add("reminder-due-queued:{id}:{atTimestamp}")` (future moment: key lives until `$at`; a past moment within the last 24 h on a reminder with an email/SMS channel: dispatched at once and the key lives one minute, so repeated saves within a minute queue one job; older past moments and in-app-only past moments are not dispatched), so each (reminder, future due moment) is queued once however many saves or hourly sweeps see it; a redis flush clears both the delayed job and the key, and the next hourly sweep re-queues it. Idempotent: a stale job (reminder edited/completed/deleted since) just re-evaluates `show()`. |
| `SyncTaskCalendarEventJob(taskId)` | `HasTaskActivityLog` saved hook (Task and TaskDetail) | `afterCommit()` in the constructor (dispatched inside the save transaction otherwise ran before the row was visible and missed events) and `ShouldBeUniqueUntilProcessing` with `uniqueFor = 5`s so create + detail-save dispatch once. Delegates to `EventSyncService::sync`; done/archived/deadline-less tasks purge their calendar event. |
| `SyncProjectChannelMembershipJob(projectId)` | `Project::saved` (members/departments/owner changed), `Profile::saved` (department move touches every project that targets the old/new department) | `afterCommit()`. Audience = `Project::charter()->rosterIds()` (owner + members + department members, active non-guest); adds missing members with a fresh read cursor, detaches the rest except the owner, and re-points `channel.owner_id` to the project owner. A project-linked channel cannot be deleted or made Open by hand (`Channel::isProjectLinked`). |
| `LogMissingSkillJob` | Skills directory | Unchanged. |
| `SendNotifyRuleJob(ruleId, payload)` — COORDINATOR (2026-10-27) | `NotifyService::handle()` — one job per live matching `NotifyRule`, `dispatch(...)->afterCommit()`, from the `HasNotifyEvents` model trait; also the admin one-off «ارسال پیام» action (`SendMessageAction`, plain `dispatch()` with a `values`-carrying payload and no `event`) | **`tries = 1`, no backoff, `timeout = 60`, on purpose:** a retry would re-mail every recipient that already got the message. Never sends. Carries a light payload (no record values for created/updated; deleted keeps its snapshot) and re-reads the record. Re-finds the rule (missing or `is_active = false` = no-op), re-checks the rule's `conditions` against the freshly re-read record for created/updated (`$rule->matches($record)`; a deleted snapshot skips it) — on mismatch it writes ONE summary row (`batch.conditions_changed`) and sends nothing — builds the message, `RecipientResolver::resolveWithSkips()`, refuses runs above `notify.ceiling` (summary row only), writes the summary + skipped `NotifyLog` rows and dispatches the chunks. An exception becomes the summary row's error. |
| `SendNotifyChunkJob(ruleId, runId, channelKey, message, addresses, detailed, event, recordId)` (2026-10-27) | `SendNotifyRuleJob` — one per channel slice (`notify.chunk.mail` 20 / `notify.chunk.sms` 200), `->delay(index * notify.delay)` (3 s, index across channels) | `tries = 1`, `timeout = notify.timeout` (60), `failOnTimeout`. Calls `NotifyChannel::sendMany()` and writes its sent/failed rows with ONE `NotifyLog::insert`; channel off / unconfigured / any throwable = one `failed` row with `count` N; `failed()` (worker kill/timeout) writes the same row. `SendNotifyRuleJob::failed()` writes a summary row with the run-failed error. Per-person `sent` rows only when `detailed` (channel recipients ≤ `notify.detail_below`), else one aggregated row. See "Batch pipeline" in `app/Services/Notify/notifyPattern.md`. |
| `SendReminderSmsJob(reminderId)` (2026-10-27) | `Reminder::deliverDue()` (from `ReconcileReminderDueJob` and the `reminders:sweep-due` safety net) when the reminder has the SMS channel on and the tenant has `notify:sms` | `tries = 1`. Sends one SMS (title line + notes) through `SmsChannel`; no-op when the reminder, the number or the provider is missing. |
| `GenerateReportJob(reportId)` (2026-11-05) | `GenerateReportAction` after the row is `generating` and quota is consumed | `tries = 1`, `failOnTimeout`, no `SerializesModels` — the payload is the id plus the run token (unique id `{id}:{run}`). Constructor sets `timeout` to `2 * (AiClient::setting('report', 'timeout') + AiClient::setting('report', 'connect_timeout')) + 30` (`ai.report.timeout` / `connect_timeout` in `config/ai/report.php`, falling back to the `config/ai.php` gateway), then clamps it to the default connection's `retry_after - ai.report.job.retry_margin` (`config/queue.php` ships `retry_after` 310 for redis and database) when that key exists and is lower; `uniqueFor` is `timeout + 30`. Re-finds the row (missing or not `generating` = delete tmp and return). After that check passes, `touch()` restarts the stale clock. Before the provider call, non-empty extractor `skipped` and `notes` are stored on the last version entry. On success writes spec/title/model/tokens and drops `parent_spec` from the last version. Failures call `AiReport::markFailed` (the only quota refund; `too_large` and `blocked` are in `ai.report.no_refund` and do not refund) and map to the closed fail codes. Provider HTTP logs only status, Retry-After on 429, and error type/code — never the raw body or any message text. `finally` always deletes `ai-report/tmp/{id}`. |
| `GenerateCorrespondenceJob(letterId, run)` (2026-11-09) | `Correspondence\Actions\GenerateAction::start()` after the row is `generating` and quota is consumed | Same contract as `GenerateReportJob`: default queue, `tries = 1`, `failOnTimeout`, `afterCommit()`, `ShouldBeUniqueUntilProcessing` (id `letterId:run`, `uniqueFor = timeout + 30`), payload = ids only. `timeout = 2 * (AiClient::setting('correspondence', 'timeout') + 'connect_timeout') + job.padding` (= 290 s) clamped to `retry_after - job.retry_margin (10)` of the default connection — **the clamp would cut a `retry_after` of 180 to 170 s, so `config/queue.php` now ships `retry_after = 310` for the redis and database connections (no env needed; `REDIS_QUEUE_RETRY_AFTER` / `DB_QUEUE_RETRY_AFTER` only override it)**. Re-finds the row (not `generating`, other `run`, tenant `correspondence:ai` off, confidential or non-out type = no-op / `markFailed('disabled')`); writes under `lockForUpdate` only when the run is still current. Failures go through `Correspondence::markFailed` (only refund path, `no_refund` = too_large, blocked); `failed()` maps `TimeoutExceededException` to `timeout`. Never logs the body or key. See `app/Livewire/Dashboard/Correspondence/correspondencePattern.md` §11. |
| `SendCorrespondenceJob(letterId, partyIndexes, resend, userId)` (2026-11-09) | `Correspondence\Actions\DeliverLinkAction()` (send / remind) on an approved outgoing letter | `tries = 1`, `timeout = 150`, `failOnTimeout`, `afterCommit()`, default queue (150 s fits the shipped `retry_after` of 310). A run mails at most 5 outside parties and re-dispatches the rest; claim and finish are separate locked transactions around the mail (no mail/PDF inside a transaction), delivery state is written with `writeQuiet` (no hooks, no `updated_at`). `failed()` and any exception call `stampError('send_failed')`, which only touches parties still `sending`. Re-checks status, classification, `wet_signed` and `tenantOff('correspondence')` at run time. Needs `storage/app/mpdf-tmp` writable by the worker user and worker `memory_limit` >= 256M (512M with images) for mPDF. See `correspondencePattern.md` §12. |
| `RefreshLaunchpadJob(id)` (2026-11-17) | `RefreshLaunchpadAction::plan()` (the 05:01 `launchpad:refresh-plan` scheduler line, delayed 1, 2, 3… minutes, limit 43), `CreateLaunchpadAction` right after commit, and `refreshNow` (`canManage`, once per item per cooldown) | `tries = 1`, `timeout = 120`, `ShouldBeUniqueUntilProcessing` per item id (`uniqueFor` 3600; the lock frees when the run starts, so a replace dispatched mid-fetch is not dropped), payload = the id only, no `SerializesModels`. Re-checks `tenantOff('launchpad')`, calls `RefreshLaunchpadAction::execute($id)` and catches everything: the job ALWAYS succeeds (a failed call writes `data.json` with `ok:false`, so no `failed_jobs` row), and the only log line is `{item id, code: error}` — never a URL, body or message. See `launchpadPattern.md` §8. |

Gotchas
- Naming: queued job classes are verb-first and end in `Job` (`ReconcileNudgeJob`, `SendNotifyRuleJob`); their tests are `<Job>Test` (`ReconcileNudgeJobTest`).
- Removal date: on or after 2026-12-10 (30 days after the 2026-11-10 rename deploy, matching the `queue:prune-failed --hours=720` schedule; later deploy = deploy date + 30 days), per client, after its own check below.
- Temporary compatibility shim: `AppServiceProvider::register()` aliases the six pre-rename names (`ReconcileEdge`, `ReconcileNudge`, `ReconcileReminderDue`, `SendNotifyChunk`, `SendNotifyRule`, `SendReminderSms`) to their `*Job` classes through `AliasLoader`, so an old serialized payload (a `failed_jobs` row retried later) still unserializes. Guarded by `tests/Feature/Jobs/LegacyJobAliasTest.php`. Remove the loop and the test once the table holds no row with an old name: `SELECT COUNT(*) FROM failed_jobs WHERE payload REGEXP '(ReconcileEdge|ReconcileNudge|ReconcileReminderDue|SendNotifyChunk|SendNotifyRule|SendReminderSms)\"'` returns 0.
- Scheduler times, the failure-logging rule and the `storage:prune-tmp` temp sweeper: `routes/consolePattern.md` "Logic of the layout" (times table and sweeper section follow it).
- Dispatch raw/bulk-written changes yourself: `DB::table`/query `update` fires no model event, so no job runs (the overhaul replaced those with per-model updates; the nightly `ArchiveStaleDoneTasks` bumps the `Task` cache version explicitly).
- `afterCommit` jobs dispatched with `dispatch(...)->afterCommit()` outside a transaction run immediately — safe either way.
- Queue workers keep code in memory: after changing a job or a nudge class run `php artisan queue:restart`, not just an FPM reload.
