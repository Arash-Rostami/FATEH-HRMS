# Reservation — resource booking + calendar sync

## `Main::historyReservations()` — SQL-level hard cap, not true pagination

The user-panel history tabs (previous/cancelled/released/upcoming) fold recurring-series occurrences
into one representative row (`groupBy(fn($r) => $r->parent_id ?? $r->id)`) with an accurate
`series_count` — needing every occurrence of a series in PHP to count correctly, so the query can't
`->limit($historyLimit)` at the SQL level the way `resources()`/`totalResources()` do. Before the fix
this meant `$query->get()` had **no SQL limit at all**: `scopeCancelled()`/`scopePrevious()`/
`scopeReleased()` carry no time window, so a long-tenured user's ENTIRE lifetime history in that status
was fetched, hydrated (with `resource` eager-loaded), and grouped/mapped in PHP on every page load of
the tab — only to discard everything past `$historyLimit` (5, +5 per "load more") via `->take()`.
Confirmed via direct code read, not a log symptom.

**Fix applied is a quick safety cap, not a true fix**: `private const HISTORY_QUERY_CAP = 500;`
applied as `$query->limit(self::HISTORY_QUERY_CAP)->get()` before the PHP-side grouping. This bounds
the worst case (truly unbounded growth) but does **not** make the tab genuinely paginated — every load
still fetches up to 500 rows regardless of `$historyLimit`. **Known, accepted tradeoff**: if a single
recurring series has more occurrences than fit before the 500-row cutoff (e.g. 500+ historical rows in
one status where the cutoff lands mid-series), that series' `series_count` badge could undercount — a
cosmetic edge case, not a functional bug, only reachable well past what any UI session realistically
pages through. A real fix would push the series-grouping and counting into SQL (e.g. a
`COALESCE(parent_id, id)` group-by + window function) so only `$historyLimit` rows are ever fetched —
deliberately not done; flagged as a future architecture change if this tab's cost ever becomes real
rather than theoretical. Regression test:
`ReservationTest::test_history_query_applies_hard_ceiling_before_series_folding` (asserts the actual
executed SQL contains `limit 500` via `DB::listen()`, not just that the component renders).

## `EventSyncService` — meeting bookings become one shared calendar Event, not two mirrored ones

`Reservation::booted()` calls `EventSyncService::sync()` on every `saved` and `EventSyncService::purge()`
on `deleted`, regardless of whether the reservation was created via the admin `ReservationResource` or
the user-panel `Dashboard\Reservation\Main` Livewire component — one model hook, both entry points, no
per-entry-point duplication.

### Shape

For an **active** reservation on a **Meeting**-type resource, `sync()`:
- `Event::updateOrCreate`s exactly **one** `Event`, owned by the booker (`user_id = $booker->id`),
  keyed on `(user_id, description)` where `description` embeds the reservation id
  (`"جلسه برنامه‌ریزی شده از طریق سیستم رزرواسیون #{id}"` — the stable identity key across repeat syncs).
  `private = true`. Title is party-agnostic (`"جلسه {booker} و {related}"`) since both viewers see the
  same row.
- `EventShare::firstOrCreate`s a share for the resource's `relatedUser` (`Resource::relatedUser()`,
  matched by `name`) — this rides the **already-existing** `App\Services\Menu` shared-events
  infrastructure (`app/Services/Menu/statePattern.md`) instead of building new notification plumbing:
  the invited colleague gets the `shared-events:nudge` bell immediately (`SharedEventsNudge`,
  `date >= now`) and the `shared-events` badge dot within 24h of the meeting
  (`EventShare::hasImminentFor`).
- Both writes go through **Eloquent** (`updateOrCreate`/`firstOrCreate`/model `->delete()`), never a
  bulk query, because `HasMenuState`'s flush and `NudgeServiceProvider`'s triggers are bound to Eloquent
  model events — a bulk `Event::query()->delete()` or `EventShare::insert()` here would silently break
  the badge/nudge wiring.

### Superseded design

Before this, `sync()` created **two** independent private `Event` rows (one per `user_id`, booker and
related) — an unlinked mirror, not a share. That meant the invited person got a silent calendar entry
with **zero** notification (no `EventShare` row, so `SharedEventsNudge`/`SharedEvents` never fired), and
each party could edit/delete their own copy independently. The new shape trades that independent-edit
capability for the existing, already-shipped nudge+badge visibility — the invited person's calendar
entry is a **shared, read-only** view (`Calendar.php`'s `editEvent()`/`deleteEvent()` are ownership-gated
to `user_id = Auth::id()`, so only the booker can edit/cancel; the related person sees it via the same
`orWhereHas('shares', ...)` clause any other shared event uses).

### `pruneOtherOwners()` — legacy-row cleanup, not resource-dependent

Both `sync()` and `purge()` delete any `Event` row matching this reservation's `description` but **not**
owned by the booker (`pruneOtherOwners()`), independent of whether `Resource::relatedUser()` currently
resolves. This both consolidates any pre-existing row left over from the old two-Event scheme (the next
time that reservation is saved or cancelled) and stays correct if the resource is later renamed/deleted
such that the name-match breaks — `purge()` no longer needs to load `resource.relatedUser` at all.

### Timing — nudge vs. badge are decoupled, by the existing system's own design

This decoupling is existing, unmodified behavior from `app/Services/Menu/statePattern.md` §
`SharedEvents` — the reservation flow simply now participates in it rather than introducing new
notification timing.

### Not yet backfilled

Reservations that were active before this change may still carry a leftover related-user-owned `Event`
row from the old scheme. It self-heals the next time that reservation is saved or cancelled
(`pruneOtherOwners()` runs on both paths) — no migration/backfill command has been run against
production data for this.

### Calendar UI — reservation-linked events are read-only, not just read-only-by-convention

`EventSyncService::isReservationEvent(?string $description)` / `::reservationIdFrom(?string $description)`
are the single source of truth for "was this `Event` produced by a reservation" (checked against the
`description` prefix, `DESCRIPTION_PREFIX`) — `Calendar.php` uses them rather than re-deriving the marker
string. Without this guard the booker could open the normal edit/share modal on a reservation-generated
`Event` and change its title/date/shares directly in the UI; those changes would either get silently
clobbered on the next `sync()` (title/date/the one canonical share) or drift permanently out of sync with
the reservation (extra manual shares — `sync()` prunes any share not belonging to the resource's current
`relatedUser`).

`Calendar::editEvent()`, `::deleteEvent()`, and `::openShareModal()` each early-return with an error toast
for a reservation-linked event instead of performing the action, even though the booker is technically the
`Event` owner. `events.blade.php` mirrors this: the normal share/edit/delete button row is swapped for a
single "مشاهده رزرو" (view reservation) link — `route('reservation')`, and a day-list tag distinguishes
these rows from an ordinary shared event. The calendar legend documents this row type alongside the
existing private/public/ownership rows.

**Not** `route('dashboard', ['tab' => 'reservation', ...])`: unlike `feed`/`gallery`/`post`/etc., `reservation`
is not one of `Tabs::tabs()`'s keys — it is registered in `TabPresenter::shortcuts()` as its own dedicated
route (`routes/web.php`: `Route::get('/reservation', Reservation::class)->name('reservation')`), so a
`dashboard?tab=reservation` URL silently falls back to the `home` tab via `Tabs::normalizeTab()`. The
`?open={id}` `FocusOnRecord` deep-link convention doesn't carry over either: `Reservation\Main::focusRecord()`
resolves `open` against `Resource::find($id)` (for highlighting a bookable resource from search), not
`Reservation::find($id)` — there is no UI wiring today to scroll to/highlight one specific past reservation
by id. `selectedDayEvents()` still exposes `reservation_id` per event for a future such deep-link; until
that's built, the link only routes to the reservation module's landing page.

## Long-hold (range) booking mode — one record, continuous span

A continuous hold of a resource (e.g. "reserve this seat for a whole year") is stored as **one** `Reservation` row with `start_time` today and `end_time` months/years ahead. No new column, no migration — `end_time` is already a `timestamp`. Range mode is **elevated-only (admin or developer) by construction**: only the Filament admin form (`ReservationFormPresenter`) — reachable by both `admin` and `developer` roles (`User::canAccessPanel` returns `true` for both; `developer` is super-by-role and bypasses `AuthorizesByPermission`) — exposes a free `end_time`; the user panel derives `end` from `selectedDuration` (minutes, bounded by `max_duration_minutes`), so a regular user can never produce a multi-day span.

### Deriving `isRange` — duration, not calendar-span

`BookingContext::isRange()` and `Reservation::isRange()` both compute `!is_full_day && start->diffInDays(end) >= 1`. This is a **>=24h elapsed** check, deliberately not a calendar-day (`isSameDay`) check: a legitimate short overnight slot (22:00→01:00, ~3h, crosses midnight) returns `diffInDays ≈ 0.08` → **not** range → stays under the normal intraday validators (`Duration` max/min, `AllowedHours`). Only holds ≥ ~1 day become range. A year is 365 days → range.

### Validators relaxed vs. kept in range mode

In range mode these **early-return** (a continuous hold isn't bound to working hours/days or intraday caps): `Duration`, `AllowedHours`, `ResourceSchedule`, `AllowedDays`, and the `window_days`/`window_hours` future-cap inside `TimeWindow`. `TimeWindow`'s **past-start guard is kept** even in range (no backdated starts).

These **stay enforced** in range: `ResourceAvailability` (the per-resource double-book guard — the seat is exclusively held for the whole span; nobody else can book it), `TypeActive`, `ResourceActive`, `FullDay`, `Recurrence`, `UserActive`, `BookingPermission`. `UserConflict` is **skipped** in range: it is per-(user, resource-type) and would lock the user out of *every* same-type booking for the year; `ResourceAvailability` already prevents true per-resource double-booking, so the per-type lockout serves no purpose for an elevated-assigned (admin or developer) hold.

`ActiveLimit` (`max_per_user`) counts a range **once**, in its start month — elevated-authoritative (admin or developer) ranges are exempt from the monthly cap for later months (documented, accepted).

### Form guards (`ReservationFormPresenter::isRangeState`)

When the form's `start_time`/`end_time` form a range (`!is_full_day && diffInDays >= 1`): the `is_full_day` toggle is `disabled()` (with `->dehydrated()` so `false` persists) — you can't flip a range to full-day; `is_recurring` + `recur_pattern` + `recur_count` are `disabled()` and hidden — you can't combine range + recurring (which would otherwise make `GenerateSeriesAction` shift the year-long `end` per child into overlapping year-long holds). `end_time` and `start_time` pickers carry `->maxDate(now()->addYears(10))` to reject absurd spans.

### Page hooks

`CreateReservation::afterCreate` guards `GenerateSeriesAction` with `!$this->record->isRange()`. `EditReservation::mutateFormDataBeforeSave` forces `is_full_day = false` for a range and only applies the same-day `startOfDay/endOfDay` pin when **not** range — so editing a range never truncates it to a single day.

### Event sync — no meeting event for a range

`EventSyncService::sync` routes a range through the same `purge()` branch as a non-meeting/non-active reservation: no `Event::updateOrCreate` (a seat/desk hold is not a calendar meeting), and the `DB::afterCommit` `countdown:active`/`StateService::flush` still runs. The countdown is `Event::activeCountdownEvent()`-driven, not reservation-`end_time`-driven, so a far `end_time` never produces a "525600 minutes remaining" artifact.

### Cancel / partial release — one record, whole-only by design

A range hold is one record. **Whole-cancel** (status → cancelled) and **shorten** (move `end_time` earlier) both work in one step. **Release** (`releaseAction`) on an **ongoing** range (start in the past) truncates `end_time` to now and sets status `released` — the remainder of the span is freed for others; on a **future** range (not yet started) it sets status `released` only (does *not* free — use cancel to free a not-yet-started hold). A mid-range **single day/time-slot cannot be excluded** from within the one record — there is no per-day exception mechanism. To free a mid-span gap: truncate `end_time` to the gap start, then create a second reservation for the remainder (two records). This is the accepted tradeoff vs. the 365-discrete-records approach (which silently truncated on `window_days`/`max_per_user`/non-working-days and lied about coverage). If real per-day blackouts inside a span are later required, a child `reservation_exceptions` table is the documented extension point — not built.

### Rendering

`Reservation::displayTime` shows the end **date** when end is on a later day than start (`date • H:i تا end_date H:i`), covering the user-panel history card (`history.blade.php` uses `$reservation->display_time`). The admin list table gained an `endTime()` column (`toJalaliSmart`, toggleable, hidden by default).

### Calendar rendering of long holds — boundary markers, not a per-day pill (2026-09-05)

Left unhandled, a range reservation of any length repeats its `event_seat` pill/bar on **every** day/week it spans (§"Calendar private reservation injection" in `app/Livewire/livewirePattern.md`) — fine for a few days, pure noise for a months-long hold. `Reservation::isLongHold()` (`spanInDays() >= self::LONG_HOLD_DAYS` — const, `7`; since 2026-09-15 both `isRange()`/`isLongHold()` delegate to the private `spanInDays()` helper instead of each computing its own `diffInDays`, semantics unchanged) marks the cutoff; below it, rendering is byte-identical to any other range reservation (no regression).

For a long hold, `CalendarPresenter`:
- **`userReservationsByDay()`** stops fanning the reservation into every day key in its span — it emits the reservation into `byDay` only on its **start** day-key and/or its **end** day-key, and only when that boundary actually falls inside the currently-rendered `[start, end]` window. Both the month-grid dot/count and the day/week in-grid pill inherit this for free — they all read this one method.
- **`userReservationsSpanning()`** (the week-view cross-column bar) skips long holds entirely — a bar that redraws itself fresh every single week for months would be its own kind of noise.
- **`reservationPill()`** takes an optional `$dayKey` and, for a long hold, appends `· شروع` (start) or `· پایان` (end) to the title when that day IS the boundary being rendered — so the one or two pills that do appear read as a start/end marker, not a mystery one-off booking. The **start** pill only also carries `long_hold_days` (int, `start->diffInDays(end)`) and `long_hold_end_date` (Jalali short date, e.g. `۰۴ بهمن`); both `null` on every other pill, including the end boundary.
- **`buildMonthDays()`** derives a per-day `longHoldDays` (nullable int) straight from the same `userReservationsByDay()` result it already fetches for `hasReservations`/`eventCount` — zero extra query. `month.blade.php`'s day cell renders it as a tiny sage number next to the `event_seat` dot, only on the reservation's start day.
- **`calendar/events.blade.php`** (the per-day event list — the one place that lists everything happening that day in full) reads `long_hold_end_date` off the reservation entry and renders a dedicated badge — `event_seat` icon + "از طریق رزرو" + "- تا {end date}" — placed **before** the private/public badge whenever the day's entry is reservation-linked, on its own row (`flex-wrap`, so a long resource name never gets clipped).

No standalone "ongoing holds" strip exists in the header — one was built (a persistent `long-holds.blade.php` partial + a separate `longHolds()` query, included in `view-header.blade.php` above the grid) and removed the same day: the month-grid badge and the events-list badge together cover "how long" and "until when" without an always-visible extra chrome element or a second query. If a persistent cross-navigation surface is wanted again later, re-derive it from `buildMonthDays()`'s data rather than a separate query. Tests: `CalendarTest` (`test_long_hold_*`, `test_selected_day_events_shows_long_hold_duration_only_on_its_start_day`).

The 7-day threshold and the sidebar/grid badges reuse the existing sage/`--tool-sage-*`/`--md-sys-color-tertiary*` token convention already used by `reservation-banner.blade.php` and `events.blade.php`'s own reservation badge, so the new UI reads native, not bolted on. Calendar's own legend (`calendar/legend.blade.php`, rules tab, "از طریق رزرو" row) documents this for end users.

## Admin form date handling — shared `PersianDateFieldService` + `FilamentDateHandler`

The reservation admin form is now consistent with the other 6 Filament modules (Task, Ths, Event, Gallery, Profile, Report): date/datetime fields use `PersianDateFieldService` (Jalali year/month/day dropdowns → hidden `Y-m-d`) + a native `type('time')` TextInput, merged by the `FilamentDateHandler` trait — **no raw `DatePicker`/`DateTimePicker`**. `ReservationFormPresenter` was the last holdout.

- `start_time`/`end_time` are split in the form as `{field}_date` (`PersianDateFieldService::make`, `fullWidth: true`, `yearTo: now+10y`) + `{field}_time` (TextInput, default 09:00/17:00). `end_time_date`/`end_time_time` are `visible` only when `!is_full_day`; `start_time_date` is always visible (full-day needs the start date; end is implicit `endOfDay`).
- `ReservationResource\Pages\CreateReservation` and `EditReservation` `use FilamentDateHandler` with `datetimeFields() = [start_time, end_time]` (`default_time '00:00'`).
- **Lifecycle gotcha (do not regress):** the merge + validation + isFull-day/range normalization all happen inside `mutateFormDataBeforeCreate`/`mutateFormDataBeforeSave` (which receive the `$data` that is actually persisted via `handleRecordCreation`/`handleRecordUpdate`). There is **no `beforeCreate`/`beforeSave`** — those hooks read `$this->data` which, for Create, is NOT the same array as the persisted `$data`, so validating there would see un-merged split fields (`start_time` null) and diverge from what is saved. Keep the merge+validate+normalize in the `mutateFormDataBefore*` method.
- Carbon `startOfDay()`/`endOfDay()` mutate in place — in the isFull-day branch use `$start->startOfDay()` then `$end = $start->copy()->endOfDay()` (copy before endOfDay) so `validateEdit` receives `$start=00:00:00`, not the mutated `23:59:59`.
- `isRangeState(Get)` (form guard) assembles from the raw `start_time_date_year/_month/_day` and `end_time_date_year/_month/_day` parts via `PersianDateFieldService::assemble()`, not `start_time`/`end_time` (those only exist post-merge) nor the bare `start_time_date`/`end_time_date` hidden fields (those only carry the assembled value at dehydration/validation time, since `PersianDateFieldService`'s `->live()` production-timeout fix — see `filamentPattern.md` — moved assembly off the per-pick interaction path).
- Range `maxDate(now+10y)` became `PersianDateFieldService`'s `yearTo: Jalalian::now()->getYear() + 10` (the service's native cap, not a chained `->maxDate`).
- Strings: `fields.start_time_time` / `fields.end_time_time` added to `lang/fa/resources/reservation/strings.php`.
- **Gotcha (caught 2026-09-23, resolved the ERP-native way):** this migration renamed the presenter's date-field methods, but two `RelationManager`s reusing `ReservationFormPresenter` (`ResourceResource\RelationManagers\ReservationsRelationManager` and `UserResource\RelationManagers\ReservationsRelationManager`) were never updated — they kept calling the old `fullDayDate()`/`startTime()`/`endTime()` names, which no longer exist, making their edit/create actions a guaranteed PHP fatal error. A `RelationManager` in another resource's directory tree is easy to miss during a presenter refactor since it isn't exercised by the main `ReservationResource` form or its own tests. Final fix (same day): both RMs declare `$relatedResource = ReservationResource::class` and their `form()`/`infolist()` overrides are deleted — the Edit table action becomes a URL link to the real `EditReservation` page (where `FilamentDateHandler` runs; no CreateAction exists on either RM), the ViewAction stays a modal rendering `ReservationResource`'s own form/infolist via vendor delegation. Both RM tables carry `->toolbarActions([])` so the delegation does not inherit the main table's bulk delete/exporter (user decision 2026-09-24); their redundant `getModelLabel()`/`getPluralModelLabel()` overrides are deleted (delegation supplies identical labels). No RM-level schema duplication remains to drift. When renaming/removing any `*FormPresenter` static method, grep for the method name across `Pages/`, `RelationManagers/`, and `Schemas/` in every resource, not just the owning one.

## Range is elevated-only (admin or developer) — server-side guard in `BookAction`

Range mode is elevated-only (admin or developer) **by construction** (only the Filament admin form exposes a free `end_time`; the user panel derives `end` from `selectedDuration` bounded by `max_duration_minutes`). As defense-in-depth against a misconfigured `max_duration_minutes >= 1440` (which would let a regular user pick a 24h+ duration and create a range), `BookAction::execute` (user-panel entry point, called only from `Reservation\Main::book()`) rejects up front using `hasElevatedRole()` (admin **or** developer — developers are not blocked):

```php
if (!$user->hasElevatedRole() && !$isFullDay && $start->diffInDays($end) >= 1) {
    throw new \Exception('رزرو بلندمدت فقط از طریق پنل ادمین قابل ثبت است.');
}
```

`Main::book()` catches the exception and toasts the message (no 500). This guard lives in `BookAction`, NOT in the shared `ValidationService` pipeline, because `validateBooking` runs with `enforceAllRules=true` on elevated create too — a shared `skip_admin` rule would still run for elevated users (admin or developer) on create (the `skip_admin` optimization only applies to `validateEdit`) and wrongly reject elevated ranges. The user-panel-only `BookAction` is the correct place. Test: `RangeBookingTest::test_book_action_rejects_range_for_non_admin`.

## Range length cap — `max_range_days` policy + `RangeDuration` validator

The intraday `Duration` (`max_duration_minutes`) is skipped in range mode (a continuous hold isn't an 8h meeting), so without a separate cap a 20-day hold sails through. The `max_range_days` policy (per resource type, in `reservation_policies`, configurable in `ReservationPolicyResource` form next to `max_per_user`) closes that gap: the `RangeDuration` validator (registered in `ValidationService::$bookingRules` with `skip_admin => false`, so admin create **and** edit are both bound) rejects a range whose `start->diffInDays(end) > max_range_days` with `ReservationError::RangeTooLong` (ERR-025, "حداکثر مدت رزرو بلندمدت N روز است"). Unset/`null` ⇒ no cap. Only applies in range mode (`isRange()` early-return for ≤1-day). This also bounds the 24h threshold discontinuity from the range side. Tests: `RangeBookingTest::test_range_duration_*` (blocks exceeding, allows within, no-cap-when-unset, ignored-for-non-range).

## Avantgarde edge-case fixes (2026-09-15)

Four gaps found by an adversarial edge-case sweep of the avantgarde view, all fixed minimally:

- **`focusRecord()` bypassed permission/kill-switch gating.** Unlike `switchTab()`, the search-deep-link (`?open={id}`) handler reassigned `$this->activeTab` to the resource's type with no `canBookTab()` check — a stale/shared link into a locked or unpermitted type rendered a fully bookable-looking UI the server would reject at submit. Fixed with the same guard `switchTab()` already uses: `if (! $resource || ! $this->canBookTab($resource->type)) return;`.
- **Avantgarde was missing the recurring-booking toggle entirely.** `booking-panel.blade.php` never included `recurring.blade.php` — `$isRecurring`/`recurPattern`/`recurCount`/`recurPreview()`/`allowsRepeat()` were all already live on `Main` and rendered in classic, but avantgarde users had no way to create a recurring series without switching views. Fixed with one `@include('livewire.dashboard.reservation.recurring')` after the time-rail include, before the hints chip row — `recurring.blade.php` is a fully self-contained partial (own `wire:key="recurring-panel"` root), zero new PHP.
- **Command Grid's "maximize" state survived switching to the Booking Canvas**, hiding header/nav/footer with no visible way to un-toggle (Esc still worked, just wasn't discoverable). Fixed with one attribute on the canvas tab-selector's wrapping div in `avantgarde.blade.php`: `x-on:click="if (max) toggleMaximize()"` — resets `max` (from the shared `maximizeMixin()` on the root `x-data="reservation()"`) on any click in that area, including the canvas-tab buttons themselves.
- **A focused/open resource could silently swap to a different one** once it dropped out of the currently-rendered `resources()` window (booked out, deactivated, or `resourcesLimit` reset back to 6 by a date/floor/time change) — `deckReconcileOpen()` client-side only re-fronts `open` while it's still in `deckOrder`; once gone, whatever id is now first renders as the "open" face with no click. Fixed server-side in `invalidateResourceCache()`: after the existing unset/refetch, `if ($this->open && ! $this->resources->contains('id', $this->open)) $this->clearFocus();` — guarded on `$this->open` being set, so the common (nothing focused) path pays nothing extra; the `resources()` re-evaluation this forces was already going to happen at render time regardless (Livewire `#[Computed]` caches it), so no added query.

Regression tests: `ReservationTest::test_focus_record_ignores_locked_type`, `::test_focus_record_ignores_unpermitted_type`, `::test_open_resource_clears_when_it_drops_from_filtered_list`, `::test_avantgarde_booking_panel_includes_recurring_toggle`. The maximize-reset fix is pure client-side Alpine state with no server round-trip to assert against — not covered by this suite (PHPUnit/Livewire testing has no DOM/JS execution here).

**Six more minor polish fixes (2026-09-15), same sweep:** `updatedGridPinned()` now resets `$this->gridLimit = self::GRID_PER_PAGE` (a pin toggle re-sorts the grid, so staying on a stale load-more position could strand a row); `booking-panel.blade.php`'s type-selector renders `<x-ui.empty icon="lock" .../>` instead of a blank dropdown when `$tabs` is empty (zero booking permission); `book()`/`cancel()` each gained a `catch (\Illuminate\Database\Eloquent\ModelNotFoundException $e)` before the generic `\Exception` catch, dispatching a fixed Persian toast instead of leaking the model's English message; `dossier.blade.php` gained a `sr-only focus:not-sr-only` skip link to `#dossier-card-{id}` (shown only when a resource is open and more than one resource is listed); `command-grid.blade.php`'s action-icon cluster got a `.reservation-action-cluster` class with a `.app-density-compact` override in `dashboard.css` (mirrors the file's existing `.reservation-command-table tbody td` compact rule); a pin-count hint appears above the grid when `gridPinned` exceeds the 50-row cap `historyGroups()` already enforces. The cross-tab `$store.pinned`/`$store.tagged` localStorage race (two open tabs can clobber each other's pin/color choices) was left unfixed — it needs a `storage`-event listener in `resources/js/**`, out of scope while those files are being hand-edited elsewhere.

## Dynamic metadata facet filtering — zero-maintenance, model-owned discovery (2026-09-15)

Superseded an earlier, hand-built floor+unit filter (two hardcoded `#[Computed]` methods, two hardcoded blade blocks, gated to `activeTab === 'seat'||'spot'`) with a fully generic mechanism that requires **zero code changes** when an admin adds a new resource type or a new `metadata` field to an existing one. Design reviewed by Fable 5 before implementation; two thresholds below were explicit user sign-off, not arbitrary picks.

- **`Resource::metadataFacets(string $type): array`** (in `app/Models/Concerns/HasResourceMetadata.php`, beside the pre-existing `FIELD_CONFIG`) is the single source of truth. It pulls every active resource's `metadata` for the type, and for every scalar top-level key (plus every scalar entry inside the `custom` KeyValue bag, unwrapped to `custom->{key}`) computes presence-ratio and distinct-value-count. A key becomes a facet only when **presence ≥ `FACET_MIN_PRESENCE` (0.4)** and **2 ≤ distinct values ≤ `FACET_MAX_OPTIONS` (15)**. Array-valued keys (`available_days`, `time_slots`) are skipped automatically — they fail `is_scalar()`, no denylist entry needed; `notes` is the one entry in `FACET_SKIP` (free text, never facet-worthy). The whole thing is `ModelCacheVersion::remember(static::class, "facets:{$type}", ...)` — Tier V, auto-invalidated by the project-wide `ModelCacheServiceProvider` listener on any `Resource` save/delete, no manual cache wiring.
- **Why 0.4/15, not "any field, any cardinality":** a field only 2/50 resources have filled in would make a filter button that narrows to almost nothing — noise, not a filter. A field with 30+ distinct values (e.g. `card`/`extension`, near-unique identifiers) would render 30 chips, an unusable UI — it degrades gracefully to search-only instead (see below) once a type's fleet crosses the cap. Both numbers are consts next to `FIELD_CONFIG`, changeable in one place, not per-key code.
- **Floor keeps its bespoke labels** ("طبقه منفی N" for negative, "همکف" for zero) via `facetValueLabel()`, a `match()` keyed on `$key === 'floor'` inside the SAME model file — the user's constraint was "no meta-conditionals in Blade," not "no config anywhere"; a future bespoke label for a new key is one more `match` arm here, still zero Blade changes.
- **`Main.php`**: `$filterFloor`/`$filterUnit`/`availableFloors()`/`availableUnits()`/`setFloor()`/`setUnit()` deleted entirely (not layered — floor/unit re-emerge from discovery automatically given the real data shape). Replaced by one `array $facetFilters = []` (key→value), one `#[Computed] facets(): array` delegating to `Resource::metadataFacets($this->activeTab)`, one `setFacet(string $key, string $value)` (same toggle-clears-on-reselect idiom `setFloor`/`setUnit` used), and `applyFacets($query)` — resolves each `facetFilters` entry against the CURRENT `$this->facets`' `key => path` map before building a `where("metadata->{$path}", $value)`, so a stale/tampered filter key that isn't a real discovered facet is silently dropped rather than reaching the query as an arbitrary JSON path.
- **`Resource::scopeAvailable()`** lost its `$floor`/`$unit` params entirely — availability (type/status/day/time-slot/conflict) is the scope's only job now; facet filtering lives in `Main::applyFacets()`, applied on top of `Resource::available(...)`.
- **`filter.blade.php`** is now one generic `@foreach($this->facets as $facet) ... @foreach($facet['options'] as $opt) ...` — zero key- or type-specific `@if`s. Included, unconditionally once reached, inside `<x-ui.forms.filters>` (the same reusable search+dropdown-filter component already used by Command Grid/Dms/Ths) in BOTH `reservation.blade.php` (classic) and `booking-panel.blade.php` (avantgarde — the first time either a filter or a resource search has ever existed there), each wrapped in an `@if(count($this->facets) > 0)` with its own static `wire:key` (`resv-facets-panel-classic` / `resv-facets-panel-booking`) per the morph-safety rule — a type with no discoverable facets shows no filter panel at all, not an empty one.
- **Resources became searchable as a side effect of the reuse**: `resourceSearch` (bound via `<x-ui.forms.filters>`'s `searchModel`) matches both `name` and, as the high-cardinality-identifier fallback, `metadata` itself — so `extension`/`card` values that fall out of the facet-chip UI past the 15-option cap stay findable by typing them. Uses `INSTR(name, ?) > 0` / `INSTR(CAST(metadata AS CHAR), ?) > 0` (plus the `json_encode`-escaped needle variant for Persian `metadata` content), not `LIKE`, per `livewirePattern.md`'s `getBaseQuery()` free-text-search rule — same two bugs (`%`/`_` over-matching, `\uXXXX`-escaped Persian under-matching on the JSON-cast column) apply here as documented there.
- **Tests**: `tests/Feature/Models/ResourceModelTest.php` covers `metadataFacets()` directly — discovers floor+unit, excludes notes/array fields/low-presence/single-value keys, unwraps `custom`, empty-type → `[]`, floor's special labels. `tests/Feature/Livewire/Dashboard/ReservationTest.php` covers the Livewire-level wiring — `setFacet()` toggle, reset clears `facetFilters`, a facet genuinely narrows `resources()`, `resourceSearch` narrows by name, `focusRecord()`/open-drop-out both reset/react to `facetFilters` (not the deleted floor/unit properties). The two `metadataFacets()` fixture tests use a synthetic `zz-seat-facet-test` type rather than the real `seat` type — the dev DB already carries ~90 active `seat` resources with real `floor` values, which polluted both the distinct-option-count assertion and the single-value-exclusion assertion when run against real `seat`/`spot` types (coreTestPattern.md §6's baseline-delta rule). `facetValueLabel()`'s negative-floor branch (`'طبقه منفی ' . abs($n)`) was concatenating a raw ASCII int instead of running it through `convertToPersian()` like every other digit in this file — fixed to `convertToPersian(abs($n)) ?? abs($n)`, matching the digit-conversion convention used everywhere else in `HasResourceMetadata`.

Not a `wire:key` issue — keys only govern morph identity, not layout order. **Fix:** decouple visual position from DOM position entirely via CSS `order`, reactive off the same client state that already drives `col-span-full`: `:style="` + "`order: ${deckDepth({{ $resource->id }})}`" + `"` on the card root. Since `deckDepth()` returns 0 for whichever id is currently front-of-deck, the open card always renders first regardless of its DOM slot, and every other tile's `order` follows its own `deckOrder` position too — so the WHOLE grid's visual sequence tracks the client-side cycle state instantly, with the (harmless, invisible) DOM reorder catching up silently once the round-trip lands.

**Open/close face-swap animation — tried twice, removed entirely (2026-09-15).** First attempt: a slide+fade (`translate-x-4`→`0` on enter, reverse+further on leave) on both `x-show` faces, meant to read as continuous leftward motion — reported as "two animations fighting" because `col-span-full`/`order:` (the grid-position fix above) are discrete, non-animatable grid properties, so the outer card box snaps to its new size/position in a single frame while the inner content tried to slide inside a box that had already jumped. ## Monthly quota (`max_per_user`) and the per-user override (2026-10-19)

`ActiveLimit` is a **monthly quota per resource type**, not a "simultaneous" cap: it counts the user's `active` + `released` reservations of the booked type whose `start_time` falls in the booking's start month/year, and rejects at `count >= max` (ERR-012). Other types and cancelled rows never count. The admin label/hint were misleading ("همزمان") and now read «سقف رزرو ماهانه».

**Per-user override:** each `users.booking` entry may carry an optional `max` (`{key: seat, value: true, max: 5}`). `User::bookingMax($type)` reads it from the raw JSON (the `booking` accessor flattens to `key => bool`, so it cannot carry `max`); `ActiveLimit` and `Main::activeLimitUsage` both resolve `bookingMax($type) ?? policies['max_per_user']`, so the override replaces the policy cap in either direction and the user-panel usage bar always shows the number actually enforced. **Precedence: the type's own `max` → the `all` row's `max` (user-wide default for every type with no own value, new types included; resolved at check time inside `bookingMax`, never copied into rows) → the policy cap.** The `all` default deliberately replaces low policy caps too (a user-wide 10 lifts `meeting`/`frnch_prs` from 1 to 10 unless those rows carry their own `max`) — the form hint says so; each blank type field shows the inherited number as its placeholder. Blank/absent `max` everywhere = policy cap, so nothing changes for existing users. Same count query, no extra query. Admin edit still skips `ActiveLimit` (`skip_admin`).

The edit form must hydrate from `User::bookingRows()` (raw JSON), not from the filled state: Filament fills from `attributesToArray()`, which runs the flattening `booking` accessor and would silently drop every `max` on the next save (caught in review; `UserResourceTest::test_edit_form_round_trip_keeps_per_type_booking_max`). The booking toggle cascade and the inherited-`max` placeholder read/write the repeater through `Get`/`Set` with the **`../`** path (one level up from a field inside a repeater item — `../../` returns the whole form), never `$livewire->data['booking']`: the Department relation manager's edit action keeps its form at `mountedActions.N.data`, so `$livewire->data` throws there (`DepartmentResourceTest::test_users_relation_manager_booking_toggle_cascades_without_a_data_property`). A user whose `booking` is null/empty hydrates the repeater's default rows (all types) instead of an empty list (`UserResourceTest::test_edit_form_hydrates_defaults_for_a_user_without_booking_data`). A key outside the registry stays selectable for its own row (no blank select / failed `in:` rule),.

## Last-minute booking (`last_minute_hours`) — use-it-or-lose-it exception to the monthly quota (2026-10-19)

A per-**type** policy key (key/value row in `reservation_policies`, like every other policy; empty/NULL = off). When a user has reached their monthly cap (policy `max_per_user`, or their personal `bookingMax`), `ActiveLimit` no longer throws ERR-012 if the booking's `start <= now() + last_minute_hours` — so a spot nobody took in the final stretch can still go to someone out of quota. It is a **3-line change inside `ActiveLimit`**, deliberately not a new pipeline rule: the block/allow decision lives at the exact line that throws, and a separate validator could not un-throw it.

- **It only relaxes the quota.** `ResourceAvailability` (double-booking), `TimeWindow`, `AllowedHours/Days`, `UserConflict`, permissions etc. run unchanged, so only genuinely free resources can be taken. The booking is a normal reservation, so it **counts toward the cap afterwards** (the user stays blocked outside the window).
- **Band, not a sum:** `window_hours` (TimeWindow, ERR-004) is when booking *closes* (min notice); `last_minute_hours` is the far edge of the exception. A capped user can book only when `window_hours <= hours-until-start <= last_minute_hours`. `last_minute_hours` must therefore be **greater** than `window_hours` — enforced by a closure rule on the policy form field (`PolicyFormPresenter::lastMinuteHours`, int 1–720, nullable); a smaller/equal value would leave an empty band. (A bare `gt:window_hours` rule was rejected: it fails on int/string state mismatches and on a blank `window_hours`.)
- **Full-day types count to midnight:** `start` of a full-day booking is `startOfDay`, so for parking `last_minute_hours = 24` opens the day before from 00:00 — not 24h before a time of day. The same is already true of `window_hours`.
- **Applies to personal caps too:** the check is on "cap reached", whatever the cap's source (policy, a type's own `max`, the user's `all` row).
- **Recurring series:** each occurrence is validated by its own `start`, so only near-term occurrences pass for a capped user. Admin edits still skip `ActiveLimit`.
- **User panel:** `Main::lastMinuteHours()` (policy read) and `bookingBlockReason()` — the cap message now appears only when the selected start is beyond the window, with the window mentioned in the message; `reservation.blade.php` adds a one-line hint (`wire:key="reservation-last-minute-hint"`) under the quota bar while the user is at the cap. `lastMinuteHours` is in `resetFilters()`'s unset list (policies change on tab switch).
- **Provisioning / SQL:** `TypeProvisioner` writes `last_minute_hours => null` for every new type; existing types get the row from `database/migrations/2026_10_19_000001_add_last_minute_hours_policy.sql` (idempotent `INSERT IGNORE ... SELECT DISTINCT resource_type ...` (the unique `(resource_type,key)` index skips existing rows), to run by hand on production). The key does not need to exist to work — `EditPolicy::handleRecordUpdate` upserts it on first save — the row only keeps the policy list uniform.
- **Not built (by decision):** a cap on how many last-minute bookings a user may take. If nobody else wants the resource, letting the user have it is the point; abuse is bounded by physical availability.

Tests: `ReservationValidatorsTest::test_active_limit_last_minute_*`, `ReservationPolicyResourceTest::test_last_minute_hours_*`, `ReservationTest::test_booking_block_reason_*last_minute*`.

## Release on a range — truncate ongoing, not future

`releaseAction` is range-aware: an **ongoing** range (`isRange() && start_time->isPast()`) is truncated to `end_time = now()` + `status = released` — the remainder of the span is freed for others (the `start_time->isPast()` guard prevents `end_time < start_time` for a not-yet-started range, which would be an invalid record). A **future** range (start in the future) falls back to the existing `status = released` only — it does *not* free the resource (use cancel for that), matching the existing intraday release semantics (released still blocks unless `allow_overlap_release`). Note the prior guide text claiming release "frees the resource" was inaccurate for intraday (it only frees when `allow_overlap_release` is on) — the statuses + admin-ops guide hints were rectified to match the actual `ResourceAvailability` behavior (`released` blocks unless `allow_overlap_release`). ## Server-correctness round (2026-10-22)

- **Atomic booking:** `BookAction::execute` runs `validateBooking` INSIDE `DB::transaction` after `Resource::whereKey()->lockForUpdate()`, so two simultaneous bookings serialize on the resource row and the second fails `ResourceAvailability`. `BookAction::$skipped` counts recurring occurrences dropped by validators; `Main::book` shows a warning toast with the count, `GenerateSeriesAction::execute` returns the same count for the admin `CreateReservation` notification. The admin create path validates in `mutateFormDataBeforeCreate` (no lock possible there; accepted, low volume).
- **`TimeWindow`:** the past check for full-day uses `end->isPast()` (today is bookable until the day ends); hourly keeps `start->isPast()`. `window_days` horizon is `now + N days` at END of that day (matches `CalendarPresenter`). `window_days = 0` therefore means "today only".
- **Admin rules:** on CREATE (`enforceAllRules`) admins skip only the validators flagged `'bend' => true` in `ValidationService::$bookingRules` — `AllowedDays`, `AllowedHours`, `ResourceSchedule`, `Duration` (schedule/length rules an admin may deliberately bend); permission, past-start (`TimeWindow`), user conflict, caps and the integrity rules (`TypeActive`, `ResourceActive`, `RangeDuration`, `ResourceAvailability`) still apply, so bending can never create past-dated, unpermitted or double-booked data. On EDIT every `skip_admin` rule is skipped as before. `validateEdit` takes the newly selected `Resource`; `EditReservation` skips validation when the saved status is cancelled (it still validates `active` and `released`, which hold the slot).
- **Cancel:** users cannot cancel once the booking has started (hourly: `start_time` past; full-day: `end_time` past). `cancelLimitStats` counts `DISTINCT cancelled_at` (a series cancel stamps every row with one timestamp, so it costs ONE against `max_cancel_count`, while separate partial cancels still count separately); `CancellationLimit` delegates to it (single count site). `CancelAction::seriesReservations` cancels only active occurrences whose `end_time` is in the future.
- **Small:** `AllowedHours` treats `{start:null,end:null}` as no restriction; `EventSyncService` never shares a meeting event with its own booker; `Main::domainMessage` hides raw `QueryException` text.
