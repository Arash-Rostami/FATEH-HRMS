# Module locks and the position lock (admin panel)

An extra gate on top of `Permission`: a holder sets a secret code per admin module; an ordinary admin must enter any valid code once per session. The user panel is never locked.
## Rules
- Table `locks` (`database/migrations/2026_11_12_000001_create_locks_table.php`): `lockable_type` = module key (`AuthorizesByPermission::moduleKey()`, e.g. `contact`), `lockable_id` 0 = whole module, > 0 = one record of `Lock::RECORD_MODULES` (`channel` today), `slot` = `master` (developer) / `ceo` / `chairman` / `owner` (per-record only, set by the record's owner), `secret_hash` (bcrypt), `extra` json (spare). Unique `(lockable_type, lockable_id, slot)`.
- No row for a module = open. Any row = locked; ANY set slot's code unlocks; an unset master slot does not open the module.
- Holders (developer role, or profile position chairman/ceo) bypass every lock but still need their normal permissions. A holder manages only their own slot; a developer manages all (`Lock::slotFor($user, $requested)` is the single resolver and allow-list; `LockPolicy::manages()` is its yes/no form).
- Codes are only ever hashed: never shown, logged, cached or put in the session. The cache (`Lock::moduleMap()`, `HasModelCache`) holds fingerprints only; the session holds `locks.{module} = "{userId}:{lockId}:{fingerprint}"` (bound to the account, so a grant never transfers when another account logs in on the same session), and changing one slot's code ends exactly the sessions that code opened. Cache is bumped by the global `ModelCacheServiceProvider` listener AND again `DB::afterCommit` in `HasLockHooks::refreshPolicy()` (the admin panel wraps writes in transactions, so the first bump can precede the commit).
- Codes are limited to `Lock::MAX_CODE_BYTES` (72, bcrypt's limit; Persian letters are 2 bytes each) in `SetModuleLock` and in the manager form. Unlock attempts are reserved with `RateLimiter::hit()` BEFORE hashing.
- Known, accepted: the dashboard chart widgets (`StructuralChart`, `OperationalChart`, `Hr*Chart`) show aggregate counts and are not permission-gated per module today, so they are not lock-gated either; `UnmetSkillDemandTable` keeps only its own `canView()` (`SkillResource::canViewAny()`, which is lock-aware when it first loads).
- Kill switch `config('locks.disabled')` (env `LOCKS_DISABLED`), emergency only. A missing `locks` table reads as "no locks": the query failure is caught in `Lock::moduleMap()` and never cached, so migrating takes effect immediately.

## Where it is enforced
1. `AuthorizesByPermission::permits()` returns false while `LockPolicy::blocks(moduleKey())` — covers nav, `canViewAny`/`canAccess`, row/bulk/header action authorization and global search.
2. `GuardsModuleLock` (`bootedGuardsModuleLock`: Livewire runs `booted{Trait}` after mount AND after property hydration on every update, so the owner record of a relation manager is always set) on the four resource page bases, `RelationManager` and `ListNotifyLogs` — aborts 403 on an already-open page (Livewire update requests, including a locked record: `X-Livewire` requests always get the plain 403); only a FIRST page request for a locked record is redirected to the unlock page, via a plain `Illuminate\Http\RedirectResponse` thrown as `HttpResponseException` (inside Livewire the `redirect()` helper is Livewire's own Redirector and cannot be wrapped).
3. Scope (owner decision): ONLY the locked module's own resource pages and its relation-manager tables. Dashboard widgets, analytics tabs and the module guide are deliberately NOT gated.
4. `GuardsModuleLock` also resolves a relation manager's INFERRED related resource (`relatedModelResource`), not only a declared `getRelatedResource()`. `ManageLocks` re-checks holder status in `boot()` on every request.
5. Record locks: `LockPolicy::blocksRecord($module, $record)` gates per-row (ChannelResource only today); the record's owner (`owner_id`) and every holder bypass; a record's unlock grant is its own session key (`locks.{module}:{id}`), so it never opens another record. `SetModuleLock::handleRecord` (404 unless `Lock::ownsRecord`), `UnlockModule::handle(..., $recordId)` (allow-list `RECORD_MODULES`, same one-per-user budget), `LockPolicy::lockedRecordIds` drives the `UnlockModules?record=` deep-link. `Lock::recordMap()` is the lockable_id > 0 twin of `moduleMap()`. Channel-owner key, end to end: the owner sets/changes/clears it from the user-panel channel info panel (`SetChannelKeyAction`, blank code = clear, per-owner limiter `channel-key:{id}`, the code only ever travels as a method argument and is wiped client-side); it is a row `channel` + channel id + slot `owner` (`Lock::SLOT_OWNER`, deliberately NOT in `Lock::SLOTS` so a developer cannot write it through `slotFor`). Enforcement: `AuthorizesByPermission::permits($action, $record)` (every record-taking `can*` and `getAuthorizationResponse` pass the record: row actions, view modal, row links), `GuardsModuleLock::guardRecordLock()` called from the booted hook AND from the `authorizeAccess()` overrides in the app `EditRecord`/`ViewRecord` (so the redirect fires before Filament's own 403), and `ChannelResource` bulk delete uses `authorizeIndividualRecords()`. A blocked admin who has the module permission is redirected to `UnlockModules?record=<id>` (toast + preselected «گروه: name» option); without module permission it stays a plain 403. The channel's own owner is exempt even if he is an admin; developer/CEO/chairman bypass as always; a channel under both a module key and its own key needs both. A developer sees the keyed channels in the manager list through the slot filter «کلید مالک گروه» plus an owner-name filter (only owners who currently have a key), with «گروه»/«مالک» columns, and can clear a forgotten owner key; CEO and chairman never see these rows.
Not used on purpose: request middleware (the panel auth middleware is not persistent, it never runs on `/livewire/update`), exporter edits (exports sit behind the page), a `LockResource` (it would leak into the permission form's module list).

## Operations (`app/Services/Lock`, one small class each)
`SetModuleLock`, `ClearModuleLock`, `UnlockModule` (one budget per user, 5 / 15 min, key `lock-unlock:{id}`, NOT per module, so the brute-force budget never scales with module count: an attempt is reserved with `hit()` before hashing and refunded with `decrement()` on success, so successes cost nothing and never reset the failures; unlocking a module that has no key just returns true without touching the budget; logs carry user, module, slot, never the code). The «تنظیم کد» form is a plain multi-select dropdown (all options rendered up front, no lazy search; sorted alphabetically in Persian by `LockPolicy::lockableModules()` via `Collator('fa_IR')`) that only offers modules the signed-in holder's slot has NOT locked yet (`availableModules()`, so no duplicates — per slot only: a key another holder set on a module never removes it from your list, each holder can add their own key on the same module; already-locked ones are edited via the row/bulk «تغییر کد») and whose first entry «همهٔ ماژول‌ها» (`*`) means every module still available: one key for one, several or ALL modules in one go (`SetModuleLock::handleMany` hashes ONCE and writes every module in a single transaction; an unknown module in the batch aborts the whole batch with 404), and the table has a search box (matches the Persian module label or the module key) and bulk «تغییر کد» (one new key for every selected row the user manages, grouped by slot, one hash per group) and «حذف کد» (`ClearModuleLock` per selected manageable row). So the same flexibility applies to editing: set or change one, several or all at once, or one by one from the row buttons. The form has no slot picker: the slot is derived from the signed-in holder (`Lock::slotFor`: developer = master, CEO = ceo, chairman = chairman); a developer changes or clears another holder's slot only from that row's own actions. Pages: `ManageLocks` (holders only, 404 for everyone else, no nav item for others) and `UnlockModules` (only modules locked for the user AND that they may view).

## Position lock
`App\Support\TopPositionPolicy`: only a developer (or no actor: console, seeder, queue) may set, change, clear or delete the `chairman`/`ceo` position, or move `user_id` of such a profile (`HasProfileHooks`). `ProfileFormPresenter::position()` disables the two options and freezes the field on such records; the same message is the form rule. `HasUserHooks`: a non-developer cannot change a holder's email/password/role/status/type, delete a holder, or give/take the developer role.

## Decisions on record
- `lockForUpdate()` in the persisted-state lookups only holds when the save runs inside a transaction (admin panel yes; user panel and tests no). Accepted; deadlock risk is narrow (one request moving a profile's `user_id` while another edits that user).
- The holder-only «قفل ماژول‌ها» card in Profile > credentials (`credentials.blade.php`, gated by `LockPolicy::isHolder`, static `wire:key`) sits SECOND, right after the own-password card and before the sign-code card, and opens the admin manager in a new tab (`target="_blank" rel="noopener noreferrer"`).
- Scope is one lock set per install: this app runs one tenant per deployment and database (`APP_TENANT`), so the global `locks` table is per tenant in practice; `lockableModules()` only hides tenant-off modules from the pickers.
- `ClearModuleLock` is deliberately NOT limited to `lockableModules()`: a holder must be able to clear a stale lock on a module that was later switched off. The slot is still identity-enforced (`Lock::slotFor`).
- `ManageLocks` lists only the signed-in holder's own slot rows. A developer's list opens with a slot filter set to `master` (own keys) and can switch it to the CEO's or chairman's slot, or clear it to see all; the filter is hidden for everyone else. Bulk «تغییر کد» / «حذف کد» act only on the selected rows of the current view, so a bulk click never reaches another holder's keys unless the developer deliberately switches the filter. A CEO or chairman never sees which other slots exist.
- Rows of a module that is no longer lockable (switched off by the tenant) stay in the list: «حذف کد» still works, but «تغییر کد» (row and bulk) skips them (`mayChange()`), so one stale row never makes a whole batch abort with 404.
- Code rules: 8 bytes minimum (form `minLength(8)` and `SetModuleLock::MIN_CODE_BYTES`), 72 bytes maximum (bcrypt).
- Tests: `tests/TestCase.php` sets `config('locks.disabled', true)` so no test depends on whatever lock rows exist in the live dev database; the lock tests switch it back on in their `setUp` (or at the top of the lock case) and clear the `locks` table inside their rolled-back transaction.
- The chairman/ceo rule has one source: `Position` enum → `TopPositionPolicy::LOCKED` → `Lock::SLOT_*`, `User::isTopExecutive()`. A holder account (developer/ceo/chairman) cannot be deleted, or have email, password, role, status or type changed, by a non-developer — not even by the holder themself for deletion.
- Known limit (accepted): the lock covers a module's own pages, actions and relation managers only. Names and ids of a locked module's records can still appear in widgets and in OTHER modules' relationship selects (e.g. the task form's project picker), same as `Permission` today.
- Fail closed: only the MySQL "table does not exist" state (`Lock::MISSING_TABLE_STATE`) reads as "no locks"; any other query failure propagates.
- Authority is read from persisted state: `HasUserHooks` judges the actor by `getOriginal('role')` (Eloquent fills attributes before `saving`, so a self-promotion would otherwise authorize itself) and restores the original attributes before rejecting; `HasProfileHooks` re-reads the persisted position with `lockForUpdate()` (one `persistedPosition()` helper for both the save and the delete guard) and `HasUserHooks` re-reads the target's persisted role and profile position the same way (`persistedRole()` / `isPersistedHolder()` for both its save and delete guards), so a stale model can neither overwrite a protected value nor change or delete a freshly promoted holder.
- `LockPolicy::lockableModules()` is memoised in a flat static for the request; it is reset only by `flush()` or a Lock write, so a test that changes tenant-off config must call `LockPolicy::flush()`.
- `LockPolicy::map` keeps its per-user `WeakMap` memo on purpose: a flat static memo would leak stale maps between tests and long-running workers.

## Never
Mention the manager page, the credentials-tab card or this doc's rules in a user legend, admin guide or release note (non-holders must not know it exists).
