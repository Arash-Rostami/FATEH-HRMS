# Livewire Module Pattern

## Target Structure

```
ComponentName/
├── Main.php
├── Forms/
│   └── SomethingForm.php
├── Actions/
│   └── DoSomethingAction.php
├── Validators/
│   └── SomethingValidator.php
└── Presentation/
    └── SomethingPresenter.php
```

---

## Step 1 — Audit the existing component

Categorize every method/property (and trait methods) into: **Form state** (`wire:model`-bound props), **Validation** (`validate()`, rules, messages), **Persistence** (DB writes, file storage), **Component state** (`activeTab`/`perPage`/search/modal flags), **Livewire hooks** (`mount`/`updated*`/`#[Computed]`), **Presentation** (`sprintf`/`diffForHumans`/label lookups), **Traits** (state+logic mixes — removal candidates).

## Step 2 — Create Form Objects (one per UI form)

```php
namespace App\Livewire\{Module}\Forms;

use Livewire\Form;

class SomethingForm extends Form
{
    #[Validate('...')]
    public string $field = '';

    protected function messages(): array { ... }

    public function validated(): array
    {
        return $this->validate();
    }
}
```

Move all `wire:model` fields, `rules()`, `messages()` from the component/traits into the Form Object. Keep only this form's fields. Livewire auto-instantiates — no `new`/`mount`. `wire:model="form.field"` works identically — **no Blade changes** except the prefix.

> **`#[Validate]` array-rule gotcha:** `#[Validate([...])]`'s array form is parsed as a key-value rules map (`Livewire\Features\SupportValidation\BaseValidate::boot()`) only when its **first key is non-numeric**. `#[Validate(['array', 'collaborators.*' => 'exists:users,id'])]` puts `'array'` at numeric key `0`, so the whole array silently collapses into one malformed rule — the wildcard never registers, no error/warning. Key every entry explicitly: `#[Validate(['collaborators' => 'array', 'collaborators.*' => 'exists:users,id'])]`.

## Step 3 — Create Actions (one per write operation)

```php
namespace App\Livewire\{Module}\Actions;

class DoSomethingAction
{
    public function __construct(private SomethingValidator $validator) {}

    public function execute(SomethingForm $form): void
    {
        $this->validator->validate(...);
        // DB writes, file storage, etc.
    }
}
```

Single public `execute()`. Receives Form Objects and/or models — never `$this`. No `dispatch`/session/redirect (those side effects stay in `Main`). Inject via method injection: `public function submit(DoSomethingAction $action)`. If pre-conditions are complex (4+ checks, DB lookups, policy resolution), delegate to a Validator (Step 3a).

## Step 3a — Create Validators (only if needed)

Only when an Action's pre-condition logic is numerous/complex/multi-DB-check. Single public `validate()` — throws `Exception` on failure, returns `void` on pass. No writes/side effects. Container auto-resolves into the Action's constructor.

```php
class DoSomethingAction
{
    public function __construct(private SomethingValidator $validator) {}

    public function execute(...): Model
    {
        $this->validator->validate(...);
        // persist
    }
}
```

**Do not create** for 1–2 simple guards — inline them:

```php
public function execute(Reservation $reservation, User $user): void
{
    if ($reservation->status !== 'active')
        throw new Exception("...");

    if (!$user->hasElevatedRole() && $reservation->user_id !== $user->id)
        throw new Exception("...");

    // persist
}
```

## Step 4 — Create Presenter (only if needed)

Only if Blade calls `$this->getSomething()` display methods. Pure read-only — no writes/DB/state.

```php
namespace App\Livewire\{Module}\Presentation;

class SomethingPresenter
{
    public function formatThing(mixed $data): string { ... }
}
```

Pass via `render()`: `view('livewire.path', ['presenter' => new SomethingPresenter()])`. The view follows the module name (`dms` → `dms.blade.php` + `dms/` partials). If the formatting is a one-liner used once, inline it in Blade with `@php`.

## Step 5 — Clean up Main

After extraction `Main` contains only:

```php
class Main extends Component
{
    public SomethingForm $form;
    public string $activeTab = 'default';
    public ?array $selectedItem = null;
    public int $perPage = 10;
    public string $search = '';

    public function mount(): void { /* set initial form values */ }

    public function submit(DoSomethingAction $action): void
    {
        $action->execute($this->form);
        // side effects only: dispatch, reset, tab change
    }

    public function updated($prop): void { ... }
    public function updatedFormField($value): void { ... }

    #[Computed]
    public function items() { ... }

    public function switchTab(string $tab): void { ... }
    public function viewItem($id): void { ... }

    public function render()
    {
        return view('livewire.path');
    }
}
```

Remove from Main: state+logic traits, DB calls outside Actions, validation rules (→ Form Objects), formatting methods (→ Presenter), `persistX`/`storeX`/`validateX` private methods.

## Step 6 — Update Blade

Only two change types: (1) form field prefix `wire:model="subject"` → `wire:model="form.subject"`; (2) presenter calls `{{ $this->getFormattedId($item) }}` → `{{ $presenter->formatId($item) }}`. Everything else (`$activeTab`, computeds, `$this->items`, event listeners) is unchanged.

## Checklist

- One Form Object per form (fields+rules+messages); one Action per write op (`execute()` only); Validator only for 4+ guards/complex DB pre-checks; Presenter only if Blade calls formatting methods on `$this`
- `Main` = state, mount, hooks, computed, navigation, render only; Blade changes only the field prefix and presenter calls
- No `$this->reset()` wiping just-set state — use scoped `$this->form->reset()`
- Actions receive Form Objects/models — never `$this`; side effects (toast/redirect/tab) stay in `Main`
- Public properties holding an Eloquent model or record id are `#[Locked]` unless the client is meant to change them — prevents id-swapping onto another user's record (IDOR)
- Bulk-action Actions (client-supplied id array, e.g. `selectedTasks`) filter loaded models through the same `can_*` accessor the single-record method uses, *inside* the Action — e.g. `Task::whereIn('id', $taskIds)->get()->filter(fn($t) => $t->can_change_status)`. The accessor is server-side from `auth()->id()`, so unowned ids are silently dropped, not acted on
- When Blade hides a button under an *extra* condition beyond the `can_*` accessor (e.g. `@if($task['is_delegator'] && $column !== 'done')`), that extra condition must be re-checked inside the Action too — a UI-only restriction is not a server-side guard. Found via `UndoTaskAssignmentAction` (checked `is_delegator` but not `status !== 'done'`)

## What NOT to do

- No Actions for reads (those are `#[Computed]`); no `$this` into an Action; no `dispatch()`/`redirect()` inside an Action
- No Presenter for values already available as model attributes/computed properties
- No Form Object for never-submitted state (search/pagination/tab — stay on `Main`)
- No Validator for 1–2 simple guards — inline them
- Don't over-split: one simple form + no formatting helpers → Form Object + Action is enough

## Data-bag Presenter + lazy render (Feeds)

`Feeds` extends Step 4's Presenter to a **data-bag** shape: `FeedPresenter` returns small arrays bundling everything a Blade region needs in one call, so the view does one `@php $flags = $presenter->feedFlags($feed) @endphp` instead of re-deriving fields inline.

- `feedFlags($feed)` → `['isPoll','showComments','showReactions','settings']` (one call gates the whole card).
- `pollData($feed)` → `['isMultiple','options','total','counts','userVotes']` (computed once before the option loop); `optionState($index, $pollData)` → `['count','pct','isMine']` per option reusing the bag.
- `commentMeta($comment, $editingCommentId)` → `['user','avatarUrl','hasPhoto','isOnline','isOwner','isEditing']` per comment row.
- `mediaGrid($media)` → `['items','images','cols','rows']`; `$media` is `$feed->media_urls` (pre-resolved URLs — see asset-URL convention below), so the grid is pure layout and the view never calls `Storage::`.
- `categoryValue($category)` normalizes the raw-DB-string `category` (not cast to `FeedCategory` enum) via `($category?->value ?? $category)` — `?->value` on a non-null string returns `null` in PHP 8 (no throw), so `?? $category` recovers the string. Used by `categoryEmoji`/`feedFlags` instead of repeating the idiom in Blade.

`render()` passes `['presenter' => new FeedPresenter()]`. `timeline` → `item` → `header`/`comments`/`media` are all `@include`s, so `$presenter` is inherited by every partial (Laravel `@include` forwards all current vars); no per-include plumbing. The Presenter is pure (no DB, no state): `pollResults/pollChoices/pollSettings` operate on eager-loaded `polls`/`poll_options`; avatar/online read eager-loaded `profile`/`last_seen`.

**Lazy comment render-gate:** comments were `@include`d for every feed inside an `x-show` (CSS-hidden but server-rendered), so a feed with many comments rendered every card on initial load. Now `item.blade.php` gates the `@include` behind a Livewire flag: `@click="open = !open; if (open && !loaded) { $wire.openComments(feedId); loaded = true; }"` (Alpine tracks `open`/`loaded` locally; survives Livewire morph), `@if($openedCommentFeeds[$feedId] ?? false)` wraps the `@include`. `openComments($feedId)` only flips the flag — comments stay eager-loaded in `feeds()`, so the badge count and write-method refreshes (`addComment`/`deleteComment`/`updateComment` still `unset($this->feeds)` → re-eager-load) are unchanged. Initial load renders zero comment cards.

**`withCount` vs a scoped eager-load are independent counts.** `feeds()` eager-loads `comments` through a closure scoping top-level only (`fn($q) => $q->whereNull('parent_id')->latest()`), so `$feed->comments->count()` in the badge counted **top-level** — but admin `FeedTablePresenter::commentsCount()` uses `->counts('comments')` over the unscoped base relation (`hasMany(Comment::class)->latest()`), counting **all incl. replies**. Fix: add `->withCount('comments')` to the same `feeds()` query and read `$feed->comments_count` in the badge — `withCount` always counts the **base relation definition**, ignoring eager-load closure scope, so it matches admin exactly while the scoped `comments` collection still drives the visible thread. Rule: when a relation is eager-loaded with a display scope but you also need the true total for a badge/counter, add `withCount` — never derive the total from the scoped collection.

## Layout-injected global banner (broadcast across all pages)

For a UI element on **every** user-panel page (not one route), mount a single Livewire component once in the shared layout — `resources/views/layouts/app.blade.php` — via `@livewire(\App\Livewire\Dashboard\Countdown::class)`, inside the existing `@unless(View::hasSection('minimal_layout'))` block so minimal/auth layouts stay bare. Do NOT pepper every page; one layout mount broadcasts everywhere.

`Countdown` is the reference. Rules:

- **Guest-guarded, cached lookup:** `render()` returns early with an empty placeholder for guests; for authed users it calls one cached model lookup (`Event::activeCountdownEvent()`, `Cache::remember` 60s, public upcoming + PHP-filtered `countdown.enabled`) and returns `event => null` when nothing is active — the blade renders an empty `<div wire:key>` so the slot collapses cleanly.
- **Per-user dismissal is a preference, not a column:** `dismiss()` writes `preferences.countdown_dismissed_at` via the matched `getPreference('x')` / `setExtraValue('preferences.x', v)` pair on `User` (see User-preferences note in filamentPattern), compared against `today()->toDateString()` so dismissal expires at local midnight. Guarded by `abort_unless(auth()->check(), 401)`; `save()` wrapped in try/catch + `report($e)` so a preference write failure never 500s the page.
- **No new state on `Main`:** no Form Object / Action / Validator — only renders and dismisses; active-record selection lives in the model (cached).
- **Asset:** the confetti library is a vendored browser-global loaded once in the shared layout `<head>` (`<script defer src="{{ asset('assets/js/lib/confetti.browser.min.js') }}">` in `app.blade.php`), NOT inside the banner blade — the banner blade must keep a single root element (Livewire `RootTagMissingFromViewException`), so an inline `<script>` sibling is illegal. Copied to `public/assets/js/lib/` via the `viteStaticCopy` `resources/assets/js` target (assetPattern §10). The Alpine factory (`resources/js/components/alpine/data/countdown.js`, imported into `main.js` and registered `Alpine.data('countdown', countdown)`) reads the event payload via `@js($event['date_iso'])` / `@js($event['messages'])` / `@js($event['mood'])` / `@js($event['confetti'])` — never `{{ }}` in a JS string literal. Confetti renders to an in-card `<canvas x-ref="confettiCanvas">` via `window.confetti.create(canvas, {resize, useWorker:false})` (behind content at `z-index:1`), gated by the `confetti` payload flag — mourning keeps confetti but `confettiColors()` switches the palette to black grays and the banner gets `countdown-banner--mourning` (floral icon + somber muted CSS variant). The countdown JSON column uses bare sub-keys (`enabled`/`mood`/`confetti`/`messages`) — never `countdown_*`-prefixed; `HasCountdown::packCountdown`/`unpackCountdown` are canonical read/write, `activeCountdownEvent()` re-derives `mood`/`confetti` for the payload.

## Asset URL resolution convention

User-panel blades never call `Storage::` to build image/file URLs — that re-stats the filesystem per render. Files can live in two places (the `public` disk at `/storage/...`, or hand-placed under `public/...` served as `/...`), so resolution is **two-tier**: storage-disk-first, `asset()` fallback. Single source = `HasPublicAssetUrl` trait (`app/Models/Traits`): `public static resolvePublicAssetUrl(?string $path): string` (blank→`''`, `http(s)://`/`//`→as-is, `Storage::disk('public')->exists()`→`->url()`, else `asset()`). Models expose cached accessors over it (`Post`/`Link::imageUrl`, `Photo::imageUrls`, `Feed::mediaUrls` — all `->shouldCache()`). Presenters pull the trait directly (`use HasPublicAssetUrl` + `self::resolvePublicAssetUrl($path)`) — `DocumentPresenter::parseAttachments`, `OnboardingPresenter` (videos/thumbnail/guides), `ContactPresenter::attachments`, `SuggestionPresenter::attachmentUrl`; elsewhere `Model::resolvePublicAssetUrl($path)` (`Ticket` files via `Ths/Main::resolveTicketFileUrls`). Distinct from `HasAvatar::resolveImageUrl` (prefix-routed avatars). The trait ships only a static method, so applying it to a model has **no Filament side effect** — no new virtual attribute; only models that own an image column add an accessor. `Storage::path()/exists()/download()/delete()` (DMS + Contact downloads, `DeleteProfileImageAction`) are filesystem I/O, not display URLs — left as-is.

**Always name the disk explicitly on these calls** — `filesystems.default = local` (root `storage/app/private`, no `url`), so a bare `Storage::exists()`/`Storage::download()` checks the private disk and misses anything saved to `storage/app/public`. `Reports::download()` hit exactly this: `Storage::exists()`/`Storage::download()` (default disk) for files the admin FileUpload saves to the `public` disk → every admin-uploaded report fell through to the "not found" toast — fixed to `Storage::disk('public')->exists()/->download()` as tier 1, keeping `storage/app/<path>` and `public/<path>` fallbacks for legacy/hand-placed files. The same default-disk bug class hit **display-URL accessors**: `Resource::displayImageUrl` and `Report::thumbnail` both used bare `Storage::url($col)` (default `local`, no `url`) for `public`-disk files → 404 — fixed to `self::resolvePublicAssetUrl($col)` with `->shouldCache()` (matching `Post`/`Link::imageUrl`). A parallel raw-column bug hit **avatar display bags**: `Tab/Calendar` birthday/anniversary packed `'avatar' => $p->image` (raw DB column) into the events list, and the Filament `feed/comment-thread`/`comment-reply` partials bound `:existingImage="optional(auth()->user()?->profile)->image"` — both bypassed `HasAvatar::resolveImageUrl`, so stored paths like `profiles/images/x.jpg` rendered as bare relative `src` and 404'd. Fixed to `$p->getImageUrl()` and `auth()->user()?->getProfileImageUrl()` respectively (the `ContactPresenter::avatar` / user-panel `comments.blade.php` precedent). Rule: any image column bound into an `<img src>` or display array must pass through the matching resolver (`getImageUrl`/`getProfileImageUrl` for avatars, `resolvePublicAssetUrl`/a cached accessor for other public-disk files) — never the raw column, never bare `Storage::url()`. Filament's `feed/video-preview` blade and the Filament-only `Message::attachmentUrls()` are out of scope.

## Persian (Jalali) date convention

Dates are **stored as Gregorian `Y-m-d`**, converted to Jalali only at the edges. Matches the Filament side (`PersianDateFieldService`), so a date saved in one panel round-trips in the other.

- **On submit** (Action): assemble Jalali y/m/d into Gregorian — `Jalalian::fromFormat('Y/m/d', sprintf('%04d/%02d/%02d', $y, $m, $d))->toCarbon()->format('Y-m-d')`. Wrap in `try/catch` returning `null` (a flat 1–31 day list can submit an invalid Jalali date).
- **On hydrate** (`mount`): `Jalalian::fromCarbon(Carbon::parse($value))` → `getYear()/getMonth()/getDay()`. The `x-ui.forms.date` select **option values are non-padded** (`range`/`$i+1`/`range(1,31)` → `"5"` not `"05"`), so hydrate parts must be non-padded — `getYear()/getMonth()/getDay()` (ints → `"5"`) land correctly; when splitting a zero-padded `Y-m-d` string (e.g. seeding `EventForm` from `selectedDate`), strip padding via `(string)(int)$part`. The assembled **submit** string is the zero-padded inverse (`sprintf('%04d-%02d-%02d', …)`). `Tab/Calendar` (`EventForm`) follows this triplet; its action reassembles `Y-m-d` then combines with `time` via `Jalalian::fromFormat('Y-m-d H:i', "$date $time")->toCarbon()` (date+time variant).
- **Validation**: gate parts all-or-nothing with `required_with`; validate calendar validity with `CalendarUtils::checkDate($y, $m, $d, true)` (leap-year aware) inside a closure rule.
- **Display**: `toJalali($value, 'Y/m/d')` is calendar-safe (returns already-Jalali strings untouched, converts Gregorian) — tolerates legacy mixed-format rows. `toJalaliSmart($value)` is the "drop midnight" variant: `Y/m/d` when time is `00:00`, else `Y/m/d H:i` — right for most date columns but **wrong for all-day events**, where the user panel intentionally shows a uniform `00:00` chip (regular events render `Jalalian::fromCarbon($event->date)->format('H:i')`, so an all-day event stored at midnight shows `00:00`; birthdays/anniversaries hardcode `00:00`). To make admin Event table/infolist match, `EventTablePresenter::date()`/`EventInfolistPresenter::date()` use `toJalali($state, 'Y/m/d H:i')` (always shows time) instead of `toJalaliSmart($state)`. Pick `toJalaliSmart` for normal fields, the explicit `Y/m/d H:i` form when a `00:00` time is meaningful and must not be hidden.
- **Chat message smart timestamp** (cross-module — Contact `ContactPresenter::messages`, Channel `ChannelPresenter::messages`): per-message `time` = `$createdAt->isToday() ? $createdAt->format('H:i') : toJalali($createdAt->toDateTimeString(), 'Y/m/d H:i')`. Day-group separator label uses `toJalali($date, 'j F Y')` (Jalali day month year, NOT `translatedFormat('j F Y')` which renders Gregorian with translated month). Keep `امروز`/`دیروز` for today/yesterday. The `datetime` (ISO) field is unchanged for the `<time datetime>` attribute.
- **User-panel display standard — uniform `j F Y`**: user-panel date displays default to `toJalali($value, 'j F Y')`, with carve-outs: **(a) precise timestamps** keep full time — Contact/Channel chat balloons + read-receipt tooltips (`Y/m/d H:i`), Profile document upload (`Y/m/d H:i`), error page (`Y/m/d H:i:s`); **(b) shorter functional forms** — Gallery month filter keys (`F Y`, the `x-show`/dropdown `key` the timeline filter matches) and Reservation calendar day labels (`j F`, year implicit within a single month view); **(c) relative/presence** via `toJalaliRelative()`/`since()` for last-seen/online. Do not introduce a new format string outside these — use `j F Y`. Admin has its OWN standard (`toJalaliSmart` via `HasJalaliAdminLabels`; see `filamentPattern.md`); the two panels intentionally differ.
- **Chat read-receipts** (cross-module — Contact 1:1, Channel group): for `is_mine && is_last` messages, the presenter emits `readers` (array of `['avatar','name']`, up to 3), `read_count`, `is_read` (`read_count > 0`), `is_read_by_all` (`read_count === total_members`, where `total_members` is an internal non-sender counter that is `0` when no other members exist, so the boolean is false on empty membership — not an emitted field). The readers map is built by ONE memoized query in the component (`Main::readers()` for Channel; contact uses a per-message `read_at`), passed into the presenter's `messages()`/`messageGroup()` — never queried inside the presenter loop. The blade renders `done_all` (primary when `is_read_by_all`, muted when `is_read`), `done` (muted when not read), plus an avatar stack (up to 3 `<x-ui.avatar>` + `+N` chip). Zero non-sender members → no check/avatars (vacuous-truth guard).
- **Cross-panel consistency**: if a model exposes its own formatted-date accessor (e.g. `Task::createdFormatted`/`deadlineFormatted` via `$appends`), that accessor remains the **user-panel** source of truth — Blade reads it directly (`$task['created_formatted']`, `j F Y`). The **admin** side no longer calls the accessor: it uses `HasJalaliAdminLabels` (`createdLabel()`/`adminDateLabel()`, `toJalaliSmart`) so admin is uniform `Y/m/d H:i` while user panel keeps `j F Y`. The old `TaskResource` admin (`Y/m/d`) vs Kanban card (`j F Y`) drift was resolved by giving each panel its own format.
- **Font**: dates render in the **natural/system font, never `font-mono`**. Monospace is reserved for code-like values — IDs/serials (`SN-20260101-000001`, ticket `#0001`), document codes/versions (`DOC-1 - 2.0`), credentials/passwords, emails, version badges (`β.5`), calculator/keycap displays, and numeric counters (`tabular-nums` counts/pagination, which is `font-variant-numeric`, not a mono family). Stripped `font-mono` off every calendar-date/event-time/timeline-date/release-date display so they inherit the body font; `tabular-nums` left in place.

## Calendar event sharing + StateService-driven notification

An event owner shares an event with coworkers; recipients get a menu badge via `StateService` (the same indicator→`BadgeSyncService` chain Suggestion uses). The badge is **pull-only** — appears on the recipient's next menu render, not pushed at share time. Sharing reuses `StateService::flush()` — a **global cache-version bump only** (the `purgeMenuNotifications()` global wipe was removed; see badge-vs-notification below). The sharer gets an in-app **toast** only; no persistent confirmation notification is written.

- **Data** — `event_shares(event_id, user_id recipient, shared_by, timestamps)` with `unique(event_id,user_id)`; `EventShare` model; `Event::shares()` HasMany. Shares created **only by the owner** (guarded in `ShareEventAction` and again in `Calendar::openShareModal`/`sharingEvent`), so the visibility query `where user_id=me OR private=false OR whereHas shares user_id=me` cannot leak a private event; public events were already visible (sharing a public event is redundant but harmless).
- **Action** — `ShareEventAction::execute($eventId, $sharerId, $recipientIds)` owner-guards (`Event::where('user_id',$sharerId)->find`), drops the sharer and non-positive IDs, validates recipients against real `User` rows, then **diff-syncs** (`array_diff` add/remove against current pluck) so an unchanged selection touches no rows. After the diff calls `StateService::flush()` (global cache-version bump only) — one primitive reused from Suggestion, no separate `invalidate()`/push, no row purge. Recipients from `User::getCachedActiveOptions()->except(auth)` (same staff picker TaskBoard uses), passed as Livewire array `shareRecipientIds`; pre-fill casts to `(string)` to match checkbox `value=""` attrs (Alpine array binding uses strict `===`). The bulk `insertOrIgnore()`/query-`delete()` deliberately bypass `EventShare` model events, then `flush()` explicitly — so the model `booted()` hooks never double-fire on the user-panel flow. `insertOrIgnore` (not `insert`) makes the unique `(event_id,user_id)` constraint race-safe: a concurrent same-event share skips the duplicate instead of throwing `QueryException`, and the returned row count drives `added` so an idempotent re-share reports `added=0`. `Calendar::shareEvent` catches the intended `InvalidArgumentException` (owner guard → inline `@error('share')`) and adds a `catch (\Throwable)` backstop that `report()`s + emits an error toast.
- **Sharer feedback (toast + self-nudge)** — sharer gets the immediate toast (action summary) plus a **persistent self-nudge** bell row («رویداد شما به اشتراک گذاشته شد: X») via the per-record nudge layer — one per event, only while it still has ≥1 share and is upcoming. `Calendar::shareEvent` maps the summary: `added>0` → «رویداد «X» با N نفر به اشتراک گذاشته شد.», `removed>0` → «اشتراک رویداد برای N نفر لغو شد.», else info «تغییری در اشتراک‌گذاری اعمال نشد.». `ShareEventAction` stays pure share-domain orchestration returning the summary — it does not build Filament `Notification`s; it just dispatches `ReconcileNudge('shared-events:nudge', Event::class, $event->id)->afterCommit()` after `flush()` so the nudge engine writes the bell rows for both sharer and recipients. Full sharer-vs-recipient message + per-event keying logic is in `app/Services/Menu/statePattern.md`.
- **Notification (proximity badge, both parties)** — `Indicators\SharedEvents implements MenuBadge` (`key=shared-events`), registered in `StateService::$indicators`, **structurally identical** to `ActiveAds`/`PendingSuggestions` (no per-user method, no sub-interface). `isActive()` lights for **both** sides of a share when the event is **imminent** (within 24h, not the whole upcoming span): recipient via `EventShare::hasImminentFor($user)` (`where('user_id', me)->whereHas('event', fn $q => $q->whereBetween('date', [now, now+24h])->exists()`), owner via `Event::hasImminentSharedFor($user)` (`where('user_id', me)->whereHas('shares')->whereBetween('date', [now, now+24h])->exists()`). Pure SQL `whereBetween`, no PHP loop. `title`/`body` are party-agnostic («رویداد مشترک نزدیک است» / «…در ۲۴ ساعت آینده است…»). Deliberately **stateless** (no `read_at`): the badge naturally clears once the event leaves the 24h window, avoiding any write-side-effect in the read-only `selectedDayEvents` computed. **Pull-only**: `flush()` bumps the global cache version, so each recipient's next `StateService::get()` recomputes `SharedEvents` and `BadgeSyncService::sync()` reconciles the per-user DB notification — the same model `PendingSuggestions` uses. No `isActiveFor`/`UserMenuBadge` (removed as redundant: `sync` already creates/clears the row on recompute). **Sync cadence**: `sync()` runs **once per version**, inside `StateService::get()`'s `Cache::remember` closure (only on a cache miss) — not on every render. A cache hit costs a single cache read and **zero DB queries** (previously `sync()` fired per render with SELECT + dedup-DELETE per active indicator). Each `sync()` is wrapped in `try/catch` so a notification-DB failure degrades gracefully. **Badge vs notification (two signals)**: the menu **dot** is driven by the cached `$menuState[key]` bool (`menu.blade.php` `@js($menuState)[item.id]`), stays lit the whole time the condition is true, is **not** dismissable — a permanent status signal independent of the bell. The **bell entry** is the Filament DB notification row; a one-time **nudge**: fires once (created unread) when the condition first becomes active, user can mark it read ("حذف اعلان" → `markAsRead`). **`sync()` never re-unreads an existing row** — its logic is *active + no row → create; active + row exists → leave it alone (preserve `read_at`); inactive → delete*. A dismissed nudge **never resurfaces** while the condition stays continuously active — `flush()` is a pure version bump (no purge), so the dismissed row survives every flush and `sync()` leaves it read. The old code both reset `read_at=null` on version change *and* globally purged all menu-badge rows on `flush()`; both were removed. When the condition goes inactive the row is deleted; if it later re-occurs, a fresh unread row is created. No `version`/`cleared` bookkeeping fields are written — the payload carries only `menu_key` plus static title/body/action.
- **Model-side sync** — `EventShare::booted()` hooks `created`/`deleted` and `Event::booted()` hooks `updated`/`deleted` to call `StateService::flush()` (both wrapped in `DB::afterCommit()`), so shares and **event edits/deletes** through the **model** bump the version. `Event::booted()` makes the **badge** reflect an owner's date edit/deletion promptly (the nudge side was already covered by the `Event` trigger) instead of lagging the ≤2h TTL. The user-panel `ShareEventAction` bypasses these via bulk ops + its own explicit `flush()` (and short-circuits before it on an empty diff) — no double-fire.
- **Admin panel** — no standalone resource: an **`EventSharesRelationManager`** on `EventResource` renders a per-event "اشتراک‌های این رویداد" table (`recipient.name`, `sharer.name`, Jalali `created_at`). **Read-only** (`isReadOnly()` → no create/edit/attach) because shares originate only from the user-panel flow; the one allowed write is a custom plain `Action::make('revoke')` (not a `DeleteAction`, so it isn't caught by the read-only deny-list) that calls `$record->delete()` (firing the model `deleted` hook → `flush()`). `canViewForRecord` hides the table on events with no shares; the revoke button is gated by `EventResource::canDeleteAny()`.

- **Calendar grid signs (shared + imminent)** — `calendar/grid.blade.php` marks shared days and imminent shared days. `Calendar::calendarDays` eager-loads `shares:user_id,event_id` and computes per day `hasShared` (any event the auth user owns-with-shares OR is a recipient of) and `hasImminentShared` (a shared event whose `date` is within `[now, now+24h]` — the same 24h window as the badge). The cell appends a tiny `group` glyph after the `+N` counter: **outlined** in `--md-sys-color-secondary` for a shared-but-not-near day, **filled** in `--md-sys-color-error` when imminent; an imminent non-selected, non-today cell also gets a thin `ring-1 ring-[var(--md-sys-color-error)]/70`. - **Per-record nudges (`NudgeService`)** — a **separate, additive** bell-nudge layer alongside the badge/dot: one new notification row **per qualifying record** (new active ad, suggestion entering an attention stage, new shared event) instead of one per indicator. Declarative registry + dumb engine — each rule is a `MenuNudge` class in `Notifications\` (declares key, triggers, show/for/title/body, refresh); `NudgeService::register(new ...Nudge())` binds its Eloquent events and reconciles per-record under a lock, `->afterCommit()`, with a `:nudge`-suffixed `menu_key` so it never collides with the badge namespace. One new class + one `register()` line adds a rule; the engine is never edited. […] : null`, so a stale `isRecurring=true` can never reach `Recurrence` and throw ERR-010. All five policy-derived computeds (`dateWindow`, `allowedDays`, `durationBounds`, `activeLimitUsage`, `allowsRepeat`, plus `availableTimeSlots`/`minNoticeHours`) are unset together in `resetFilters()` (called by `switchTab`); `setDate` additionally unsets `activeLimitUsage`. They reuse the cached `getPolicies()` (`Cache::remember`, flushed by `ReservationPolicy::saved/deleted`).

Four interconnected asymmetries closed so user + admin panels and the validator share one source of truth.

- **Released history tab (#1)** — released reservations still count against the monthly quota (`activeLimitUsage` queries `Active`+`Released`, unchanged) but had nowhere to be seen. Add a 4th tab: `getHistoryTabs()` gains `['id'=>'released','icon'=>'autorenew','label'=>'آزادشده']`; `historyReservations()`/`totalHistoryReservations()` gain a `'released' => $query->released()` branch (ordered by `start_time` desc); `Reservation::scopeReleased` is `where('status', ReservationStatus::Released->value)`. ## Reservation smart-default date + safe dedupe batch

A two-part change to `Main` initialization, validated by an adversarial 3-subagent unanimous-confidence gate (dispatch 3 independent `general-purpose` agents with the exact diff + framing, implement only if unanimous ≥99%; re-dispatch on a no-output glitch). The dedupes were the no-op half (all 3 passed 99%+); the smart default is an intentional behavior change.

- **Smart default date (`mount`)** — `mount()` now sets the date from `$this->availableDates[0]['value'] ?? now()->toDateString()` instead of always `now()->toDateString()`. When today's weekday is disallowed by `allowed_days`, the default becomes the **first allowed future day within the horizon**; when today is allowed, it stays today (byte-identical); when **no** allowed day fits the horizon (e.g. window=2, next allowed is +3d), it falls back to today via `??`. Load-bearing detail: **ordering** — `resetMonthCursor()` **must run first**, because `availableDates()`' windowed branch reads the typed-no-default `public int $currentYear; public int $currentMonth;` (`new Jalalian($this->currentYear, $this->currentMonth, 1)`). The old order (date-first) accessed `availableDates` before the cursor was set → `Error: Typed property must not be accessed before initialization`, swallowed by `availableDates`' `catch(Throwable)` → returned `[]` → fallback today → the feature was silently **inert** for windowed tabs. Correct order: `resetMonthCursor() → smart date → syncDefaultTimes()`. `availableDates` never reads `$this->date` (no circular dependency); `#[Computed]` access in `mount()` is fine because Livewire hydrates `#[Url] activeTab` **before** `mount()` runs; `switchTab`→`resetFilters` unsets `availableDates`/`dateWindow`/`allowedDays`. `goToday()` is intentionally **not** changed — its `now()->toDateString()` is correct because "today" is by definition allowed on that path.
- **Dedupe A — `allowedHoursBounds()`** — `availableTimeSlots()` and `syncDefaultTimes()` both parsed `allowed_hours['start'??'08:00']` / `['end'??'20:00']` with the same `if ($end <= $start)` guard. Extracted to `private function allowedHoursBounds(?array $allowed): array` returning `[$startCarbon, $endCarbon]`; both callers do `[$start, $end] = $this->allowedHoursBounds($policies['allowed_hours'] ?? null)`. Verified byte-identical across 6 `allowed_hours` shapes (null, normal, wrapped, missing start, missing end, equal). Zero logic change.
- **Dedupe B — `forUser` scope alignment** — `activeLimitUsage()` and `cancelLimitUsage()` both wrote `Reservation::where('user_id', auth()->id())`. Switched both to `Reservation::forUser(auth()->id())` (the existing `scopeForUser` is exactly `where('user_id', $userId)` with an `int` typehint). Identical query.
- **Dedupe C — `resetMonthCursor()`** — `mount()`, `goToday()`, and `resetFilters()` each inlined `Jalalian::now()` → `getYear()`/`getMonth()`. Extracted to `private function resetMonthCursor(): void`; called in each, preserving the exact original order. `Jalalian::now()` reads the real clock each call, so extracting changes nothing about timing.

A standalone diff harness (replicated `availableDates` exactly, ran old-vs-new `mount` across 7 scenarios) confirmed: today-allowed → identical (A/C/E); today-disallowed + next-in-horizon → NEW jumps to that future day (B/D/F); today-disallowed + none-in-horizon → NEW falls back to today == OLD (G). 3 changed, 4 identical.

## Reports dual load-more pattern (one canonical infinite-scroll idiom)

Reports uses **two load-more shapes in one component**: the **list view** has an explicit `<x-ui.buttons.load-more action="loadMore">` button (FAQ-style, click to load), the **card view** uses a gallery/feed-style sentinel `<div x-ref="loadTriggerCard"><x-ui.loaders.spinner/></div>` with **no button**. Because the sentinel's `wire:key` changes each load (count-based), the observer MUST be re-bound via `Livewire.hook('morph', ({component, el}) => { if (component.id === this.$wire.__instance.id) this.$nextTick(() => { if (this.$refs.loadTriggerCard) this.setupIntersectionObserver(); }); })` — `setupIntersectionObserver` disconnects the prior observer before re-creating. This session added four Presenter methods, all following the Step-4 "Data-bag Presenter" shape (bundling multiple derived values a Blade region needs in one call):

## Universal aggregate fold (UnreadNotifications)

`UnreadNotifications extends Filament\Notifications\Livewire\DatabaseNotifications` and folds the bell modal so >4 unread rows sharing a `data.menu_key` collapse to one or two **synthetic** `DatabaseNotification` rows rendered natively by Filament's modal — a UI-side anti-flood cap, zero engine change, applies to **every** nudge key (DMS, posts, tasks, feeds, …), not only DMS. Admin is untouched: `isPaginated()` returns true only for `admin`, so `getNotifications()` and `getUnreadNotificationsCount()` early-return the parent result; the non-admin `getNotificationsQuery()` adds `->unread()`.

- **Fold rule** (`getNotifications`) — `countBy` the parent collection by `data.menu_key`; iterate (parent relation `morphMany->latest()`, so first-encountered = most-recent). Per group: `count <= AGGREGATE_THRESHOLD(4)` ⇒ keep individual; `>4` ⇒ emit one aggregate and skip the rest (`$emitted[$key]` dedupe). **DMS** is special-cased to **two** aggregates — `agg:dms-controller:nudge:sign` (count = `DMS::needsSignCount`) and `agg:dms-controller:nudge:read` (count = `DMS::needsReadCount`). **Every other** over-threshold group ⇒ one generic aggregate titled «{count} اعلان جدید», body `«آخرین: {most-recent row title}»` (the "آخرین:" prefix is load-bearing — without it the body reads as "5 of that one item"). **DMS both-zero guard**: if `sign===0 && read===0` but stale rows exist (the `afterCommit` reconcile window before `ReconcileNudge` clears them), do **not** fold — keep individuals and skip the count adjustment, so `list == count == bell-dot` (the dot is a separate raw `unreadNotifications()->count()` and would otherwise stay lit while the modal went empty).
- **Header count** (`getUnreadNotificationsCount`) — start from `parent::getUnreadNotificationsCount()`, then a grouped SQL (`->reorder()->selectRaw("JSON_UNQUOTE(JSON_EXTRACT(data,'$.menu_key')) as menu_key, COUNT(*) as cnt")->groupBy('menu_key')`) adjusts each over-threshold group: DMS ⇒ `+= (sign>0?1:0)+(read>0?1:0) - cnt` (skipping on both-zero guard); generic ⇒ `+= 1 - cnt`. `->reorder()` is mandatory — the `notifications()` relation is `morphMany->latest()`, so an inherited `ORDER BY created_at` collides with `groupBy` under `sql_mode=only_full_group_by` (1055). `max(0, …)` floor.
- **Synthetic row** (`makeAggregateRow`) — `new DatabaseNotification(['id' => 'agg:{key}[:{mode}]', 'type' => FilamentDatabaseNotification::class, 'data' => Notification::make()->title()->body()->warning()->persistent()->getDatabaseMessage(), 'read_at'=>null, 'created_at'=>now()])`. The **deterministic `agg:` id** is load-bearing: `Notification::fromDatabase` sets `getId()` from `DatabaseNotification::getKey()`, and the inline view builds `wire:key = "{id}.notifications.{id}"` — a `Str::uuid()` id regenerates every render ⇒ `wire:key` churns ⇒ Alpine re-mounts + replays the enter transition every 30s poll; the stable `agg:` id stops the flicker. No `actions` key ⇒ no per-row action buttons, but the **close X is unconditional** (`x-on:click="close"` → `notificationClosed` with `notification.id`), so dismissing a synthetic via the base `removeNotification` would delete-by-id (0 rows) and reappear next render (vanish-then-return).
- **Honest dismiss** (`removeNotification` override, `#[On('notificationClosed')]`) — `str_starts_with($id,'agg:')` ⇒ parse `menu_key` out of the id (strip `agg:` prefix, then strip a trailing `:sign`/`:read` mode suffix — only DMS uses a mode and no nudge key ends in `:sign`/`:read`, so `preg_match('/:(?:sign|read)$/')` is unambiguous) and `$this->getNotificationsQuery()->where('data->menu_key',$key)->update(['read_at'=>now()])` — **mark-read, never delete**, so the aggregate stays dismissed. Real rows fall through to `parent::removeNotification`. DMS dismiss marks the whole DMS group read (sign+read rows share one `menu_key`, the sign/read split is computed at render from the `reads` table) — acceptable because the **DMS badge (Signal 1, pull-based `hasPendingFor`)** persists independently of the bell rows.
- **`dmsCounts` instance memo** — `DMS::needsSignCount`/`needsReadCount` are plain statics called in **both** `getNotifications()` and `getUnreadNotificationsCount()` on the same render; `once()` won't share across two call sites (distinct closure objects). `protected ?array $dmsCountsCache = null` + `dmsCounts(int $userId): array` (`??= [needsSignCount, needsReadCount]`) memoizes per-render — Livewire does not persist protected properties across requests, so it resets each request and the second call site is free.

## `@island` rules — memoized islands, reduced scope, and the tinker mask

The Channels module (`app/Livewire/Dashboard/Channel`) **uses `@island(name:'sidebar')` + `@island(name:'messages')`** per `.claude/plans/channels-master-plan.md`. The traps below are **general guidance for any `@island` use** — reviewers MUST reason about island behavior statically; tinker PASS does not acquit.

- **Island auto-scoping keys off `action.origin`, which only `wire:click`/`wire:model` directives set — `x-on:click` (Alpine) → `this.$wire.method()` does NOT.** Livewire's `interceptAction` (`dist/livewire.esm.js:13778`) auto-scopes an action to its enclosing island ONLY if `action.origin` is set; `wire:click`/`wire:model` call `setNextActionOrigin({el, directive})`, but an Alpine `x-on:click` that calls `this.$wire.method()` reaches `fireAction` with `outstandingActionOrigin = null` → `interceptAction` returns early → no island metadata → the server does a FULL render → every `@island` whose `always:` is false emits a `mode:'skip'` empty fragment (`HandlesIslands::renderSkippedIsland`) → the island DOM is left untouched. This is why `loadOlder`/`setFilter`/`search`/`removeAttachment` (all `wire:click`/`wire:model`) worked while `send`/`saveEdit`/`deleteMessage`/`undoDelete`/`selectChannel`/navigations (all `x-on:click → $wire.method()`) did not — the DB wrote and `#[Computed]` was unset, but the messages island showed nothing. **Rule: every Alpine-triggered action that must update an island is explicitly scoped with `$wire.$island('name').method()` — scope the action ITSELF so the method runs and `renderIsland('name')` fires in one request (server `call` hook sees `metadata.island` → `skipRender()` + `renderIsland()`), then chain a refresh of the other island only if its UI also changed.** The Channels pattern: `selectChannel` is `$wire.$island('messages').selectChannel(id).then(() => $wire.$island('sidebar').refreshUnread())`; `send`/`saveEdit`/`deleteMessage` are `$wire.$island('messages').<method>()`; navigations (`toggleBrowse`/`openCreate`/`closeCreate`/`backToList`/`leaveChannel`/`createChannel`/`joinChannel`) are `$wire.$island('messages').<method>().then(() => $wire.$island('sidebar').refreshUnread())`. `undoDelete` is scoped in the blade (`x-on:click="$wire.$island('messages').undoDelete()"`). Do NOT use `$wire.$island('name').$refresh()` — `$refresh()` is a magic action, not a real method; scope a real method instead. `wire:click`/`wire:model` triggers need NO explicit scoping — they auto-scope; only Alpine `x-on:click → $wire.method()` triggers need `$island()`.
- **Island `$refresh()` runs in REDUCED scope.** On `$island('messages').$refresh()` the island re-renders with: ✅ public properties as bare vars, ✅ `$this`, ✅ `$__livewire`. ❌ bare `#[Computed]` variables are NOT injected — `$activeChannel`, `$messages`, `$groupedMessages`, `$joinableChannels`, `$presenter` are undefined on refresh. **Rule: inside any `@island` template, access computeds via `$this->` — `$this->activeChannel`, `$this->messages`, `$this->presenter` — never the bare name.** The header/info/browse/messages islands had to be converted from `$activeChannel` → `$this->activeChannel` after a real browser island-refresh threw "Undefined variable $activeChannel".
- **`@php(...)` parenthesized form breaks inside islands.** `@php($a = 1; $b = 2)` compiles differently in Livewire's `ExtendedCompilerEngine` island compile path vs a full render, producing "syntax error, unexpected token ;". The block form `@php ... @endphp` compiles identically in both paths. **Rule: inside `@island` templates, always use the block form `@php ... @endphp`, never `@php(...)`.** The parenthesized form is fine outside islands.
- **`@entangle` and nested anonymous Blade components (`<x-...>`) do NOT work inside islands.** Nested anonymous components don't inherit `$__livewire`, so `@entangle($model).live` (used by `<x-ui.forms.search>`) fatals inside an island. **Rule: inside `@island` templates, use plain `wire:model` / `wire:model.live` + Alpine `x-model` for inputs, never `<x-ui.forms.search>` or any component that relies on `@entangle`.** The sidebar search is a plain `wire:model.live.debounce.200ms` input.
- **`Livewire::test()->html()` and tinker full-render MASK every island-only bug.** A full render shares scope globally (computeds injected as bare vars, `@php(...)` compiles the full-render way, the whole component renders as one tree) — so `Livewire::test(...)->call('send')->html()` shows the new message, the edited body, the restored row, all correct; the island `$refresh()` path is never exercised. **Rule: a tinker/test PASS is not evidence the island works.** Reviewers MUST reason statically — `grep` island templates for bare computed names, `@php(`, `@entangle`/`<x-ui.forms.search` inside `@island`, and mutations for a missing `$island(...).$refresh()` or `messages-updated`-style dispatch — because the runtime test that would catch these is a real browser island-refresh, which the gate does not perform. This is why 59 reviewers green-lit a module that errored on first browser use.
- **`x-ref` inside `@island` throws on the first island re-render and aborts Alpine's whole init pass — "works after refresh, dies after first change."** Registering `x-ref` walks up `findClosest(el, i => i._x_refs …)` to the nearest Alpine root to write `_x_refs[name]`. During an island morph, Alpine's `cloneNode`/`initTree` clones the new subtree while its ancestor chain is mid-detach, the walk returns `undefined`, and it throws `Cannot read properties of undefined (reading '_x_refs')` (Alpine `module.esm.js:3436`, `$refs` magic → `getArrayOfRefObject`). The throw aborts `initTree` partway, so every directive AFTER the ref element (toolbar buttons, `x-on:click` handlers, `x-if` clones further down) never initializes — the island looks frozen even though the morph completed. First cold load survives; the first `send`/`saveEdit`/`deleteMessage` that re-renders dies. **Rule: never use `x-ref` inside an `@island` template.** Reach the element by `document.getElementById(...)` (the Channels module's `msg-viewport`/`msg-ta` access pattern in `channel.js`) or, for reactive sibling state, a scoped `<div x-data="{ len: 0 }" x-effect="len = ($wire.composer.body || '').length">` wrapper feeding `x-on:input="len = $el.value.length"` — no ref walk, morph-safe. `grep -rn 'x-ref=' resources/views/livewire/dashboard/channel/` MUST return empty.
- **`<template x-if>` inside `@island` renders dead buttons when the condition is true at morph time.** Alpine's morph plugin clones `<template x-if>` content into the DOM during the island morph but does NOT reliably re-run `x-on:click` handler init on the cloned content — buttons render but clicks do nothing. The trap is specific to x-if conditions **TRUE at morph time** (content cloned during the morph): the Channels message bubble used `<template x-if="!(isEditing && editingMsgId === {{ $msg['id'] }})">` (true while not editing → toolbox cloned at morph → dead). An x-if **FALSE at morph time** (e.g. the composer's `<template x-if="replyingTo">`, false until `startReply`) is fine — its content is cloned later by Alpine's reactive system, which inits correctly. **Rule: inside `@island`, prefer `x-show` over `<template x-if>` for any toggle whose visible branch contains interactive elements.** `x-show` keeps both branches in the DOM (one `style="display: none;"`), Alpine inits them once, handlers survive every morph. With `x-show`, replace `x-init` with `x-effect` for behavior that must re-run each time the toggle becomes active — e.g. `x-effect="if (isEditing && editingMsgId === {{ $msg['id'] }}) $nextTick(() => { $el.focus(); $el.selectionStart = $el.selectionEnd = $el.value.length })"`.
- **`ChannelMessage::lastIdForChannel(int): ?int` returns null for empty channels — null-guard every caller.** `MarkChannelReadAction` did `orWhere('last_read_message_id', '<', $lastId)` with `$lastId === null`, which Laravel rejects with "Illegal operator and value combination". **Rule: any caller of `lastIdForChannel` (or any nullable-id lower-bound filter) must `if ($lastId === null) return;` before the query.** Empty-channel `markRead` is a no-op, not a crash.
- **`WithFileUploads` inside `@island` skips the island on upload-finish, so the staged-attachment preview never paints — bridge it with a `->self()` dispatch the island's own Alpine `$wire.on` catches, then re-render via a real island-scoped method (NOT `$refresh()`).** `startUpload`/`finishUpload` are Livewire-internal calls that don't carry island origin metadata, so the upload-finish response is a full render where the island's DOM diff is skipped. The composer property (`composer.attachments`) IS set server-side and the client model IS updated, but the staged-preview `@if(count($composer->attachments))` lives inside the island template — its HTML never morphs in, so the user picks a file, sees nothing, and only sees it after `send`. The fix is a two-call dance: (1) a Livewire `updated(string $name)` hook on the root fires when `composer.attachments` changes and dispatches `attachments-updated` `->self()` — `->self()` events are delivered at component level even when the island DOM was skipped, so Alpine `$wire.on('attachments-updated', ...)` always catches it; (2) that listener calls `$wire.$island('messages').syncAttachments()`, a real non-empty island-scoped method (e.g. `unset($this->groupedMessages)` — non-empty, non-looping, no extra query, matches the `unset($this->X)` computed-invalidation idiom; do NOT touch `composer.attachments` inside it or `updated()` re-fires into an infinite loop), which issues a fresh island-scoped request and the preview paints. **Never use `$wire.$island('name').$refresh()` here — it's the forbidden magic action; scope a real method instead.** Same trap hits any `wire:model` on a file input inside an `@island`.

## Passing PHP values into Alpine handlers — `data-*` + `$el.dataset`, not `@js()` or Blade directives inside the attribute

When a Blade-rendered list row needs to hand a server value (DB id, slug, key) to an Alpine `x-on:click` handler, **serialize it through an HTML attribute and read it back from the DOM** — never inline `@js($value)` and never embed Blade control directives inside the Alpine attribute.

- **The pattern:** put the value on the element with `data-id="{{ $value }}"`, then call `x-on:click="handler($el.dataset.id)"`. `{{ }}` HTML-escapes and stringifies, the DOM `dataset` API returns a plain string, and the Alpine handler receives it as a normal arg. Concrete Channel use: in-chat message-search result buttons (`search.blade.php`) — `data-id="{{ $r['id'] }}"` + `x-on:click="focusSearchResult($el.dataset.id)"` → `focusSearchResult(id)` → `$wire.$island('messages').focusMessage(id)`.
- **Why not `@js($value)`:** `@js()` emits a raw JS literal *directly into the attribute string*. For an int that's `123` (fine), but for any string value (UUID, slug, anything carrying quotes) `@js` emits `"abc-123"` — the embedded double-quotes **break the surrounding `x-on:click="..."` attribute**, silently corrupting the handler. The `data-*` route is immune to quoting regardless of value type, because the value lives in its own attribute (HTML-escaped by `{{ }}`), not inside a JS expression embedded in another attribute.
- **Type round-trip:** `dataset.id` is always a string. For a Livewire method typed `int $id`, Livewire JSON-wires the string and PHP's type-hint coerces it back to int — the int round-trips correctly. One micro-note: a JS `if (!id)` guard treats string `"0"` as truthy (unlike `@js(0)` which yields falsy `0`), so a `0`/missing id makes one extra round-trip before the server guard returns null; in practice list rows never carry `0`, and the server guard handles it safely, so no change needed. If you ever want to close that gap, `focusSearchResult(Number($el.dataset.id))`.
- **Same principle for the island-safe `search-field` partial:** inside Alpine attributes (`x-on:keydown.escape`, `x-on:click`) interpolate **only safe scalar identifiers** (`$model`) or a **precomputed plain string** built in `@php` (`$closeExpr`) — never Blade control directives. The earlier broken form embedded `@if($refreshSidebarOnClose)...@endif` directly inside `x-on:keydown.escape="..."`, which made the Blade compiler emit `<?php ... endif; ?>` inside the attribute and produced `syntax error, unexpected token "endif", expecting end of file` (a hard fatal, not a quoting edge case). The fix builds the close expression once in `@php` — `$closeExpr = "{$model}Fullscreen = false; \$wire.{$model} = {$model}Value" . ($refreshSidebarOnClose ? "; \$wire.\$island('sidebar').refreshUnread().catch(() => {})" : '')` — and echoes `{{ $closeExpr }}` into the attribute. One source of truth, no Blade directives inside the JS string.
- **Rule:** inside any Alpine attribute (`x-on:*`, `x-bind:*`, `x-show`, `:class`), (a) pass server values via `data-*` + `$el.dataset` rather than `@js()`, and (b) keep all conditional/loop logic in `@php` and interpolate only the resulting plain string — never put `@if`/`@foreach`/`@php(...)`/`@js(...)` inside the attribute value. This is the island-safe generalization of the `@entangle`/`<x-ui.forms.search>` ban (see the `@island` rules above): the island-safe `search-field` partial exists precisely because the shared `<x-ui.forms.search>` relies on `@entangle`, and it must stay self-contained — parameterize only by `$model` (a safe identifier) plus precomputed strings, with a unique `wire:key="search-overlay-{{ $model }}"` on the teleported overlay.

## Alpine `:class`/expression bindings on a Livewire property must read `$wire.propertyName`, never a bare variable (DMS filter buttons)

DMS's filter buttons (`dms/filters.blade.php`) had correct server-side reactivity — `updatedActiveFilter()` reset `open` and reloaded docs, `getBaseQuery()`'s JSON `whereJsonContains` matching was correct — yet users reported "filters not working, clicking does nothing." The bug was purely visual: `:class="activeFilter === 'all' ? ... : ..."` referenced a **bare** `activeFilter`, but the page root is `x-data="dms()"` (`resources/js/components/alpine/data/dms.js`), whose factory defines no `activeFilter` property at all. Alpine evaluates `:class` expressions in `try/catch` and **swallows the `ReferenceError` silently** — no console error, no visible failure — so the binding just never updated and the active-state highlight never moved, reading to the user as "the click did nothing."

Every other filter partial in the codebase (`ads/filters.blade.php`, `tab/status/filters.blade.php`, `authority/filters.blade.php`, `tab/feeds/filters.blade.php`, `tab/faqs/filters.blade.php`) already used `$wire.propertyName` correctly — DMS was the sole outlier, introduced by copy-pasting a bare-variable pattern that only works when that exact name is ALSO defined in the same page's local `x-data()` factory. The shared `<x-ui.forms.filters>` wrapper (`resources/views/components/ui/forms/filters.blade.php`) and its `filters()` Alpine factory (`resources/js/components/alpine/data/filters.js`) confirm the convention: `activeCondition`/`clearAction` props default to `this.$wire.get("activeFilter") !== "all"` / `this.$wire.set(...)`.

**Rule:** inside any Alpine attribute (`:class`, `:style`, `x-show`, `x-on:*`) that needs to read or react to a **Livewire public property**, always use `$wire.propertyName` (or `$wire.get('propertyName')`) — never a bare identifier — unless that identical name is genuinely declared inside that page's own local `x-data({...})` object or `.js` Alpine factory. Because Alpine swallows expression errors silently, this class of bug produces zero error output anywhere (browser console, Livewire, logs) and must be caught by code review/grep (`:class="\w+ ===` bare-variable patterns), not by watching for exceptions. See regression tests in `tests/Feature/Livewire/Dashboard/DmsTest.php` (`test_filter_buttons_bind_to_livewire_scope_not_bare_alpine_variable` and the filter-narrowing tests).

## `hasMore` / `hasOlder` flag — the +1-probe idiom (no unbounded COUNT, no separate exists)

A Livewire component that gates a "load more" button on a boolean flag (`hasMore`, `hasOlder`, `hasPreviousPage`) is asking a **threshold** question — "are there more than N rows beyond the current window?" — NOT a count question. The cheap, correct way to answer it is the **+1 probe**: fetch `N + 1` rows, set the flag from `count() > N`, then trim back to `N` for display. One indexed query, no extra round-trip, no unbounded scan.

```php
$rows = Model::query()->latest('id')->take($this->limit + 1)->get();
$this->hasMore = $rows->count() > $this->limit;
$rows = $rows->take($this->limit)->sortBy('id')->values();
```

**Why not the alternatives:**
- **`COUNT(*)` / `Model::count()`** — unbounded. A `WHERE id >= X` (or `WHERE id < X`) range-scans the whole tail/head of the table just to return a number the caller only compares to N. `take(N + 1)` caps the scan at N+1 rows — once the DB has produced N+1 it stops, because the answer is already "yes".
- **A separate `->exists()` for the flag** — a second round-trip for information the +1 probe already extracts from the rows you're fetching anyway.
- **`>=` instead of `>` for the flag** — `count() >= N` is a fencepost bug: it returns `true` at the exact boundary (exactly N rows, no more), showing a "load more" button that fetches nothing. The flag is `count() > N` strictly.

**Rule:** any `hasMore`-style flag in a `#[Computed]` or Livewire method uses `take(N + 1) → count() > N → take(N)`. Never `COUNT(*)`, never a separate `exists()`, never `>=`. The same idiom answers "is row X within the first N?" guards (`take(N + 1)->pluck('id')->count()` compared to N) — capped, no unbounded scan. Concrete variants (recent-N window, anchor window, focus-target in-window guard) are implemented in the Channels module — see `app/Livewire/Dashboard/Channel/channelPattern.md` §3.3 and §7 `FocusChannelMessageAction`.

When two sibling chat modules (Contact `/contacts`, Channel `/channels`) need a mutual "switch over, you have N unread" cue, the minimal, non-polluting pattern is a **single shared nested Livewire component that polls only itself** — NOT a new `StateService` indicator, `Nudge` class, `HasMenuState` trait, or `notifications` row. The bell/indicator pipeline is for cross-cutting menu dots and per-record bell entries; reaching for it for a simple live count over-engineers AND pollutes the Filament bell (non-nudge rows desensitize users). ## `#[Computed]` is not auto-injected into Blade as a bare variable — and `Cache::flexible` for rate-limited third-party APIs (Navbar Weather)

`Navbar\Weather` silently showed the default `-- °C` placeholder forever, regardless of whether the OpenWeatherMap call actually succeeded. Root cause: `render()` returned `view('livewire.dashboard.navbar.top.weather')` with no data array, and the Blade template read a **bare** `$weatherData['temperature'] ?? '--'` — not `$this->weatherData`. Confirmed in `vendor/livewire/livewire/src/Mechanisms/HandleComponents/HandleComponents.php:449` — a component's view only auto-receives `Utils::getPublicPropertiesDefinedOnSubclass($component)`, i.e. **public properties**, never `#[Computed]` method results. `Weather` has zero public properties, so `$weatherData` was undefined; PHP's `??` swallows undefined-variable access silently (no warning, nothing logged), so the bug produced no error trail at all. **Rule: a `#[Computed]` value is only visible in Blade via `$this->propName` — if the template needs a bare `$propName`, `render()` must pass it explicitly: `view(..., ['weatherData' => $this->weatherData])`.**

Separately, `#[Computed(cache: true, seconds: N, key: '...')]` (`BaseComputed::handleCachedGet()`) is a plain `Cache::remember($key, $seconds, $closure)` — **not stampede-safe**: concurrent requests that all see a cache-miss at the TTL boundary each independently re-run the closure, each firing a real API call. For any `#[Computed]` that wraps a rate-limited third-party API, do the caching **inside the Action**, not via the Livewire attribute, using `Cache::flexible($key, [$freshSeconds, $staleSeconds], $callback)` (Laravel 11+, confirmed available — `vendor/laravel/framework/.../Cache/Repository.php:622`, DB `cache_locks` table present): fresh window serves instantly with zero work; the stale window still serves the last value instantly but defers exactly one background refresh guarded by `Cache::lock()`, so concurrent traffic at expiry never produces more than one outbound call. `FetchWeatherAction` derives the key from the configured city (`'weather.' . Str::slug($city)`) rather than hardcoding it, so a future `OPENWEATHER_CITY` change can't collide with a stale differently-labeled cache entry. **Rule: never wrap a rate-limited external API call in `#[Computed(cache: true)]` — cache it inside the Action with `Cache::flexible()` so the built-in atomic lock caps concurrent refreshes at one, and leave the component's own `#[Computed]` uncached (plain per-request memoization only).**

## Read a `TemporaryUploadedFile`'s metadata BEFORE `store()`/`storeAs()`, never after — same-disk moves relocate it out from under you

Production attachment sends (`.docx` files, Channel + Contact) failed with `League\Flysystem\UnableToRetrieveMetadata` — "no such file exists" — while local dev never reproduced it. Root cause is in Livewire's own `TemporaryUploadedFile::storeAs()` (`vendor/livewire/livewire/src/Features/SupportFileUploads/TemporaryUploadedFile.php:175`):

```php
// Same disk and no extra options — move instead of copy for performance.
if ($this->disk === $disk && empty($options)) {
    Storage::disk($disk)->move($this->path, $newPath);   // physically relocates the file
} else {
    Storage::disk($disk)->put($newPath, $this->storage->readStream($this->path), $options);
}
```

When the temp-upload disk (`config('livewire.temporary_file_upload.disk')`, falling back to `filesystems.default`) is the **same** disk as the destination passed to `storeAs()`, Livewire takes a same-disk fast path and **moves** (renames) the file instead of copying it — the object's own `$this->path`/`$this->disk` are never updated to reflect the new location. Every `storeAttachments()` in this codebase called `getClientOriginalName()`/`getMimeType()`/`getSize()` **after** `$file->storeAs(..., 'public')` — those calls read `$this->storage->mimeType($this->path)`, i.e. the **old, now-relocated** `livewire-tmp/{hash}.ext` path, which the move just vacated. Locally this never surfaced because dev's temp-upload disk resolves to `local` (different from the `public` destination), so `storeAs()` took the safe copy branch and left the original in place — the bug is dormant until temp-disk and destination-disk happen to coincide, which is exactly what production's config does. Reproduced by forcing `Config::set('livewire.temporary_file_upload.disk', 'public')` locally — the same send failed identically, confirming the mechanism, not just a production quirk.

Fixed in `Contact\Actions\SendMessageAction`, `Channel\Actions\SendChannelMessageAction`, `TaskBoard\Actions\CreateTaskAction`/`UpdateTaskAction` — capture `getClientOriginalName()`/`getMimeType()`/`getSize()` into local variables **before** the `store()`/`storeAs()` call. **Rule: any `storeAttachments()`-style mapper over `TemporaryUploadedFile` objects must read every metadata accessor (`getClientOriginalName`, `getMimeType`, `getSize`, `extension`, etc.) before calling `store()`/`storeAs()`/`storePublicly()` on the same object — never after. This holds regardless of what disk config says today; relying on temp-disk ≠ destination-disk to stay true is exactly the fragile assumption that broke in production.**

## Dynamic file-input array keys MUST be dot-free — `wire:model="form.files.{{ $key }}"` is a dotted path, a dotted key splits it

The THS ticket form generates one file-input slot per "add attachment" click, storing a unique key in `$form->fileInputs` and binding the input with `wire:model="ticket.files.{{ $key }}"` (plus `@error('ticket.files.' . $key)` and a JS clear via `$wire.set('ticket.files.{{ $key }}', null)`). The keys were produced with `uniqid('', true)`, which returns a string **containing a dot** (e.g. `65f2a1b3c4d5e7.89101234`). Livewire parses a `wire:model` expression as a dotted property path, so `ticket.files.65f2a1b3c4d5e7.89101234` is read as the nested path `files → 65f2a1b3c4d5e7 → 89101234`, not the flat array entry `files['65f2a1b3c4d5e7.89101234']`. The uploaded `TemporaryUploadedFile` lands one nesting level deeper than `submitTicket`/`SubmitTicketAction` iterates, so `$form->files` looks empty at submit time and the attachment is silently dropped — the "Submit Ticket Request" button appears to do nothing when a file is attached (the ticket may still create, minus its file). The dot is the entire defect; the same key flows into the `@error` bag name and the `$wire.set` path, so those silently miss too.

Fixed in `Ths\Main` (`addFileInput`/`mount`/`submitTicket`) and `Ths\Actions\SubmitTicketAction` — keys are now `Str::random(13)` (alphanumeric, guaranteed dot-free), and the dead `is_array ? reset($f) : $f` unwrap that existed only to pop the spurious nesting back up was removed (replaced by `collect($files)->filter()->values()->all()` for a clean 0-indexed array). **Rule: any key interpolated into a `wire:model`/`wire:set`/`@error` dotted path — file-input slots, repeater rows, dynamic subforms — must be dot-free and Livewire-path-safe (alphanumeric). Never `uniqid('', true)`; use `Str::random()`. A dot in a key is invisible in the rendered HTML but silently reframes the binding as a nested path, and the symptom (value looks unset server-side, button "doesn't work") gives no error trail.**

## A modal with TWO entry points — navbar `wire:click` + an Alpine `$dispatch` window event — converges on ONE `open(?string $type = null)` (Release Request / support modal)

A single Livewire modal can be triggered from two unrelated surfaces: a navbar tile (direct `wire:click="open"`) and a CTA inside an Alpine-only component that has NO Livewire backing (the release-notes `release.blade.php`, pure `x-data` + `config('releases')`). The proven DOM-event path — NOT a Livewire bus `#[On]`, which does NOT catch Alpine `$dispatch` (verified in `CommandPalette`) — is: the CTA fires `@click="$dispatch('open-release-request', { type: 'recommendation' })"`, and the Livewire component root carries `@open-release-request.window="$wire.open($event.detail?.type)"`. Both paths hit the same `open(?string $type = null)`. **Rule: a second trigger for an existing modal that lives outside Livewire (pure Alpine/Blade) dispatches a window event the Livewire root listens for — never reach for `#[On]` (it won't fire from Alpine `$dispatch`).**

Three hardening rules inside that one method, all required to avoid stale-state and injection bugs: (1) `open()` resets the form AND clears validation FIRST (`$this->form->reset(); $this->resetValidation();`) before setting anything, so re-opening after a failed submit doesn't show old errors/values; (2) the type arg is resolved via `ReleaseRequestType::tryFrom($type ?? '')` with a `?? ReleaseRequestType::Recommendation` fallback — a tampered/unknown event detail (`$event.detail?.type`) can never inject a raw string into `$form->type`, it falls back to the default case; (3) `close()` mirrors the reset (`$this->show = false; $this->form->reset(); $this->resetValidation();`). The release-note CTA additionally closes its own modal first (`@click="open = false; $dispatch(...)"`) so the two teleported overlays never stack.

The type segmented toggle is **enum-`cases()`-driven**, not hand-written buttons: `Main` exposes `#[Computed] function types(): array { return ReleaseRequestType::cases(); }` and the Blade loops `@foreach($this->types as $type)` rendering one `type="button"` (NEVER omit — a bare button inside `wire:submit` double-submits) `wire:click="$set('form.type', '{{ $type->value }}')"` per case, with active state read from **server** state `$form->type === $type->value` (not Alpine `$wire.form.type`). Adding a new `ReleaseRequestType` case is now ONE enum case — it auto-appears in the toggle, auto-validates via `Rule::enum(ReleaseRequestType::class)` in the Form's `rules()` method (NOT a hardcoded `in:` string, which would silently reject the new case), and auto-renders its Farsi label/color/icon in admin via the enum's `HasLabel/HasColor/HasIcon`. **Rule: an extensible single-select UI is a `@foreach` over the enum's `cases()` with `Rule::enum()` validation — never a hardcoded button list + `in:a,b,c` rule, which both have to be hand-edited per new case.** Reference: `Dashboard\ReleaseRequest\Main` + `release-request.blade.php` (navbar trigger + release-note CTA → one modal).

## Release-note sync — every new module/feature gets a `config/releases.php` checkpoint AFTER its pattern doc is updated

`config/releases.php` is the single source of the in-app release notes, rendered by `components/dashboard/modal/release.blade.php` as `collect(config('releases', []))->reverse()` — so the **last** array entry is the **newest** checkpoint (`$loop->first` after reverse gets the newest primary treatment + the `'جدیدترین'` badge). The release-note modal ALSO carries a static CTA card that dispatches `open-release-request { type: 'recommendation' }` to the user-panel suggestion modal — so "suggest a new module" is reachable from inside the release note itself; a new module that wants its own in-release-note trigger mirrors that `@click="open = false; $dispatch('open-release-request', { type: '...' })"` card (placed after the checkpoints `@endforeach`, before the Module Summaries accordion), not a new mechanism.

When a new module or feature ships, the doc-sync order is: (1) update the module's pattern doc(s) first (`livewirePattern.md` / `filamentPattern.md` / the relevant `<topic>Pattern.md`) with the new reusable pattern; (2) THEN append a release-note checkpoint to `config/releases.php` in the proper place. The proper place is always the **end of the array** (so it becomes newest). A checkpoint shape is: `id` (kebab, unique), `version` (increment the β.N series), `badge` => `'جدیدترین'`, `period` (current Jalali month, e.g. `'تیر ۱۴۰۵'`), `icon` + `theme_icon` (Material Symbols names), `color` (a `--md-sys-color-*` token key; newest is forced to `primary` by the renderer anyway), `theme_title` (Farsi theme line), and `items` = a list of `['title' => …, 'desc' => …]` Farsi pairs covering the module + its notable sub-features. **Demotion step: the previously-newest entry is no longer newest — change its `badge` from `'جدیدترین'` to a real category badge (e.g. `'ارتباطات'`, `'پایه'`) before appending the new one, so only ONE entry ever carries `'جدیدترین'`.** Rule: a new module/feature = pattern-doc sync first, then a `config/releases.php` checkpoint appended last with `'جدیدترین'`, and the previous newest re-badged — never edit an old checkpoint in place, never leave two `'جدیدترین'` badges.

## Presence status — `PresenceStatus` enum is the single source

The user's presence (onsite/remote/mission/busy/grumpy/angry/leave) is one backed enum: `App\Enums\PresenceStatus`. Every consumer reads from it, so adding a status is **one enum case + filling its `match` arms** — it auto-propagates to the navbar `StatusSwitcher` dropdown, the Status-board filter chips + grid cards, the contact sidebar, and the admin User form `Select` / table `SelectFilter` / `Group`, all of which `@foreach`/`collect()` over `PresenceStatus::cases()` (via the `presenceCases()` helper in `app/Helpers/index.php`) or call the enum's `label/icon/color/hex/heroicon/cardClasses/...` methods. The icon must exist in **both** icon sets the app uses — Material Symbols (user panel, `icon()`) and Heroicons (admin/Filament, `heroicon()`) — verified against `vendor/blade-ui-kit/blade-heroicons/resources/svg/` and the Material Symbols codepoints before picking (e.g. `Leave` = `sunny` + `heroicon-m-sun`; `palm_tree`/`vacation`/`briefcase`/`luggage` don't exist in both). `decor/status.blade.php` renders an ambient CSS layer per `effectType()` via `x-if` templates; a new `effectType` with no matching template simply renders no ambient layer (clean fallback — no JS/edit needed), and `ambient.js` only special-cases `angry`.

The ONE trap: `Tab/Status::stats()` builds the per-status counts the filter chips show. It MUST stay `PresenceStatus::cases()`-driven (`collect(PresenceStatus::cases())->mapWithKeys(fn($s) => [$s->value => $counts[$s->value] ?? 0])`), NOT a hardcoded `['onsite'=>…,'remote'=>…,…]` list — a hardcoded list silently drops any new status from the filter chip counts even though the chip itself (which loops `presenceCases()` and reads `stats[$value] ?? 0`) still appears with a stuck `0`. `users.presence` is a plain string column cast to the enum (no CHECK constraint), so no migration is needed for a new case.

**No presence literal anywhere — every consumer is enum-led.** A presence value string (`'onsite'`/`'busy'`/…) must never be written by hand; reference the enum case instead so a rename or new case can't silently drift. The enum-led sites: `StatusSwitcher` property default + mount fallback use `PresenceStatus::Onsite->value` (enum-case `->value` is a valid PHP 8.1+ constant expression in property defaults); `QuickSettings::setFocusMode` writes `PresenceStatus::Busy`/`PresenceStatus::Onsite` instances to `presence` (Laravel's enum cast accepts the instance on set and serializes `->value` on save — same pattern as `StatusSwitcher::changeStatus`); `User::$attributes` default is `PresenceStatus::Remote->value`; `ModuleAnalytics::usersData()` binds `presence = ?` with `PresenceStatus::Onsite->value` rather than an inline SQL literal (parameterized + enum-led). **Deferred residuals (intentionally left, lower severity):** the `users` migration `->default('remote')` is a raw DB default that cannot reference a PHP enum; the `decor/status.blade.php` `x-if="type === 'angry'/'grumpy'/'busy'/'remote'/'onsite'"` templates and `ambient.js`'s `type === 'angry'` compare the `effectType()` string as bare JS literals (JS can't import the PHP enum — these are the documented PHP↔JS contract); `UserFactory` seeds `randomElement(['remote','office'])` (and `'office'` isn't even a valid case — `tryFrom`→null→Onsite fallback, harmless but stale); test fixtures seed `presence => 'onsite'/'remote'/'busy'` as known values. Rule: any NEW presence logic references `PresenceStatus::<Case>` or `->value`; never introduce a bare presence literal in PHP.

## Widget sizing — fit-first, scroll-as-fallback, never clip

Any maximizable/wide user-panel widget (DMS table, taskboard kanban) must **fit the space it's given and shrink**, using horizontal scroll only as a genuine fallback — never a permanent desktop scrollbar, and never `overflow-hidden` on the same element that should scroll (that clips content unreachably instead of scrolling it). Two traps seen and fixed:

- **`min-w-max` on a table container** forces `max-content` width, so an `overflow-x-auto` parent always shows a scrollbar. Fix: `w-full` container + `w-full min-w-full` table. Correct nesting (mirror `ths/list.blade.php`): outer card owns `overflow-hidden rounded-2xl border shadow-sm` (clips corners only) → inner wrapper owns `w-full overflow-x-auto` (the scroll layer) → table `w-full min-w-full`. The maximize button is a **sibling of the scroll layer** (pinned, doesn't scroll away), `absolute` at the RTL start corner (`right-2 top-2`; the first `th` reserves clearance with `pr-14`).
- **A hard `md:min-w-[…]` floor on flex columns** (taskboard) defeats `md:flex-1`/`md:w-1/3` distribution: 3×350px+gaps overflows a narrow desktop row and trips the parent `overflow-x-auto`. Fix: relax the **desktop** floor to `md:min-w-0` (this is what clears flexbox's `min-width:auto`/min-content floor so `flex-1` columns share the row) on **both** the wrapper and the column root — relaxing only one still overflows. Keep mobile floors (`min-w-[280px] sm:min-w-[320px]`) for the `snap-x snap-mandatory md:snap-none` carousel, and keep the container's `overflow-x-auto` as the never-clip fallback.

Maximize is orthogonal: `.max-widget` (fixed, `inset:1.5rem`) and `.max-widget-column` (fixed, `width:clamp(60vw,70vw,75vw) !important`) in `dashboard.css` override width/position with `!important`, so `w-full`/`min-w-0` changes never affect the maximized state.

## `profile_details` catalog — `admin_only` keys (unit/section), no migration, user-panel-excluded

`profile_details` is a generic key/value table (`profile_id` + `key` unique, `section` group) driven by one static catalog: `App\Services\ProfileDetailCatalog::definitions()`. ## Shared access policy + one embeddable widget — Ths ticket assign/reply/effectiveness, in both panels

When a capability (assign a ticket, reply, set effectiveness) must work identically from the admin Filament panel AND the user-panel Livewire module, do **not** repeat the Suggestion module's mistake: `SuggestionAccessPolicy` (admin-only, static class) and `Suggestion/Detail.php`'s `#[Computed]` gates independently re-derive the *same* `canDecide/canGiveFeedback/canMarkComplete` rules from scratch — two hand-written copies of one rule that can silently drift. The Ths ticket workspace instead uses:

1. **One shared policy class outside any panel namespace** — `App\Support\TicketAccessPolicy` (`canView/canReply/canAssign/canSetEffectiveness/canClose`), composing existing model methods (`Ticket::currentActionRecipient()`, `User::highestRankingInDepartment()`) rather than re-deriving recipient logic. Placing it under `App\Support\` (not `Filament\Resources\ThsResource\Actions\...`) is deliberate — a policy that reads as "the admin panel's" invites exactly the copy-instead-of-call mistake Suggestion made.
2. **One embeddable Livewire component mounted in both panels** — `Ths\Workspace` (reply thread + assign/effectiveness controls), embedded into the admin `ThsResource` form via `Filament\Schemas\Components\Livewire::make(Workspace::class, fn(?Ticket $record) => ['ticketId' => $record?->id ?? 0])` (guard `->visible(fn(?Ticket $record) => $record !== null)` on the wrapping Section — no record on the Create page), and mounted directly in the user-panel ticket modal via `<livewire:dashboard.ths.workspace :ticket-id="..." :key="'ticket-workspace-'.$id" />`. Same UI, same policy calls, one implementation — not a per-panel reimplementation.

**Trap: a Livewire component nested inside another Livewire component (Filament's page) must always render a stable single root element — never wrap the entire template in a top-level `@if`.** `Workspace`'s blade originally opened with `@if($this->ticket) <div>...</div> @endif`; if the guarded condition is ever falsy during a render pass, the component emits zero HTML, and Livewire's nested-component tracker (`SupportNestingComponents`) extracts the child's tag name via `preg_match('/<([a-zA-Z0-9\-]*)/', $html, ...)` to remember for the next partial re-render — no match (or a comment/whitespace-led match) stores an invalid/empty tag, and the *next* Filament form interaction (e.g. a `->live()` field like `status`) throws `Invalid Livewire child tag name` trying to reuse it. Fix: always render the outer `<div>`, move the `@if` **inside** it to guard only the content.

**Reply-thread model — shared trait, not a per-model system.** One polymorphic table (`replies`: `repliable_type`/`repliable_id`, `user_id`, `body`, `files` json) + `App\Models\Traits\HasReplies` (`replies()` morphMany, `addReply()`, `latestReply()`, `otherReplyParticipant(array $participantIds)`), mixed into both `Ticket` and `Task` — neither model gets its own bespoke thread storage. `otherReplyParticipant()` is the one piece of cross-module-shared logic (given a model's two participant-id columns, returns whichever one didn't author the latest reply); each nudge class still owns which two columns count as "the participants" for its model.

**File-attachment metadata order — capture before `storeAs()`, every time.** `HasReplies::storeReplyFiles()` reads `getClientOriginalName()/getMimeType()/getSize()` **before** calling `$file->storeAs(...)`, matching the established `SendChannelMessageAction::storeAttachments()` idiom — not the Filament `saveUploadedFileUsing` order (which stores first, reads metadata after, safe only for that specific `TemporaryUploadedFile` callback shape). Reading metadata after `storeAs()` on a plain array-bound Livewire upload risks reading from a file the disk driver has already moved.

**Notification triggers fold into the existing per-module nudge class — never a sibling `*ReplyNudge` class.** A `Reply::created` event resolves to its parent (`Ticket`/`Task`) via the same `SuggestionNudge`-precedent `subject` closure (`fn(Reply $r) => $r->repliable_type === Ticket::class ? $r->repliable : null`), registered as a **second trigger inside `ThsNudge`/`TaskNudge`** sharing the same key — not a new `ths-controller:reply-nudge` key. `for()`/`show()`/`title()`/`body()` branch on whether the recipient *is* the lifecycle recipient (`currentActionRecipient()`/owner — existing copy, existing rule, untouched) versus a reply participant who isn't (new "پاسخ جدید" copy); the reply's own author is excluded from the reply-branch entirely (`$latestReply->user_id === $user->id` short-circuits to the lifecycle-only check) so nobody self-notifies on their own message. `ThsBadge`/task badges stay untouched — a badge means "unclosed action required," a reply is conversational, so it never lights the dot.

**Effectiveness required to close — enforced once, in a model `saving` hook, not duplicated per panel.** `Ticket::booted()`'s `saving` closure throws `TicketError::EffectivenessRequired->throw()` (this project's enum-`throw()` domain-error convention, see `ReservationError`) only when `isDirty('status') && isClosingStatus($status) && blank($effectiveness)` — the `isDirty('status')` guard is what keeps this backward-compatible: an already-closed legacy ticket (closed before this feature existed, no effectiveness) can still be freely edited as long as `status` itself isn't the field being changed. Both panels share one `Ticket::isClosingStatus($status)` predicate for early inline validation (Filament: `->required(fn (Get $get) => Ticket::isClosingStatus($get('status')))`; user panel: same check before calling the close action) — the model hook is the actual backstop either way, so a future third caller can't bypass it.

**Auto-generated closing summary, not a manual field.** `action_result` stays in the schema/table/export for backward compatibility, but is now system-composed from the full reply thread at the moment of closing (`Ticket::composeActionResultFromReplies()`, called from the same `saving` hook) — the Filament field becomes `->disabled()->dehydrated(false)` (read-only display), nobody types into it directly anymore.

**"Public Support" auto-hide — derive the condition from data, no manual switch.** `Department::anyHasCustomTicketOptions()` (cached, reusing the existing `scopeExcludingEmptyTicketOptions()`) gates a single `@unless(...)` around the `N/A` option in `ths/create.blade.php` — hides the moment *any* department configures its own ticket types, no admin setting to maintain, no code change per department.

**Ticket → TaskBoard linked-task mirror — one nullable FK, no two-way sync.** `AssignTicketAction::syncLinkedTask()` creates (or updates, on reassignment) exactly one `Task` per ticket via a nullable `tasks.ticket_id` FK, the moment a ticket is assigned: `user_id` = the ticket's `requester_id`, `assigned_to` = the new assignee. This rides TaskBoard's *existing* tab scoping unmodified — the requester sees it under "محول شده" (creator with an assignee ≠ self), the assignee sees it under "وظایف من" (`assigned_to = me`) — no new tab, no new query. `title`/`description` are stamped once at creation (`description` includes the formatted ticket ID plus a truncated snippet of the ticket's own `description`, so same-day tickets to the same assignee stay visually distinguishable — a generic title alone isn't enough). Deliberately one-directional and decoupled to avoid Suggestion-style rewiring: moving the task's board column is personal tracking only (never written back to the ticket), and reassigning/deleting/editing the linked task from the TaskBoard side is blocked (`AssignTaskAction`/`BulkAssignTasksAction`/`UndoTaskAssignmentAction`/`UpdateTaskAction`/`DeleteTaskAction`/`BulkDeleteTasksAction` all gate on `$task->ticket_id`) so the mirror can never drift from — or unilaterally vanish out from under — the real assignee recorded on the ticket — the only two things you can still do to a linked task are drag it between board columns and open a "مشاهده و پاسخ در تیکت" deep-link (`route('ths', ['open' => $ticket_id])`, the same `?open=` convention `FocusOnRecord`/global search already use) that jumps straight into the ticket's own reply thread rather than growing a second, competing conversation UI inside TaskBoard.

## Rendering text/HTML in Blade — `superClean()` vs `Str::sanitizeHtml()` vs a plain shape-normalize guard

Three distinct tools exist for three distinct problems. Picking the wrong one either shows broken tag-soup, opens a stored-XSS hole, or leaves a crash risk in place.

- **`superClean(?string $text, int $limit = 100, bool $nl2br = false)`** (`app/Helpers/index.php`) — for **excerpts/previews of anything that might contain HTML**, rich or plain. It `strip_tags()`s FIRST, then truncates, so it never cuts mid-tag and never needs escaping (output is plain text, safe inside `{{ }}` or string concatenation). Use it whenever you need a short, tag-free snippet: card/grid excerpts (`posts/grid.blade.php`, `reports/list.blade.php`), notification titles/bodies (`PostNudge::title()`, `UnreadNotifications::genericAggregateRow()`), anywhere HTML would land in a non-HTML context (attribute, notification bell text, aggregate string). Never use it for the *full* display of a RichEditor field — it discards all formatting. Caveat: with `nl2br=false` (the default) it does NOT escape its output — it only `strip_tags()`s and decodes entities, so a source string containing an HTML-entity-encoded tag (e.g. an admin literally typing `&lt;script&gt;` as text) can decode back to a raw, unescaped `<script>` in the return value. Safe to use this way only when the consumer itself re-sanitizes before final render (e.g. Filament's `Notification` class does, which is why `PostNudge::title()`/`UnreadNotifications::genericAggregateRow()` can pass it straight through) — never treat `superClean(nl2br: false)` alone as a full sanitizer against untrusted input outside such a context.
- **`Str::sanitizeHtml($html)` / `Str::of($html)->sanitizeHtml()`** (Filament-registered macro, `vendor/filament/support/src/SupportServiceProvider.php`, backed by Symfony's `HtmlSanitizer` with `allowSafeElements()` + explicit allow-listed `class`/`data-color`/`style`) — for the **full, formatted render of a column that a Filament `RichEditor` writes to**, rendered with `{!! !!}`. This is mandatory (not optional) whenever the SAME column can also be written as plain text by an ordinary user-facing form (dual-authored — e.g. `Suggestion.description` via `SuggestionForm::$descriptionSelf`, `Comment.content` via the feed comment composer) — never blindly flip `{{ }}` to `{!! !!}` on a dual-authored column, that's a stored-XSS hole (a user typing `<script>` gets it rendered unescaped to every viewer). Sanitize-then-render is the only safe way to preserve admin rich-formatting (including Tiptap's `<span data-color>` color marks) while still neutralizing anything a plain-text author could have typed. Reference: `suggestion/detail.blade.php` (description), `renderComment()` in `app/Helpers/index.php` (feed comments) — note `Str::limit()` truncates BEFORE `sanitizeHtml()` runs, which is safe because the sanitizer's lenient HTML5 parser self-heals a mid-tag cut rather than leaving dangerous dangling markup. A column that is **admin-only** authored (e.g. `Post.body`, `Onboarding.*`, `Report.description`, `FAQ.answer`) doesn't have the dual-authorship risk and can render with a plain `{!! $value !!}` — no sanitize call needed, since only Filament's own RichEditor ever writes to it.
- **A bare `is_array($v) ? implode(...) : $v` shape-normalize guard** — for **array/json-cast columns that are never HTML**, just a scalar-map shape that a Filament `Repeater`'s custom `saveRelationshipsUsing()`/`afterStateHydrated()`/`dehydrateStateUsing()` flattens or unflattens (e.g. `Profile.about_me`, `Feed.poll_options`). These columns have no markup and no XSS surface — the risk is a **shape mismatch** (a nested array landing where a scalar is expected), which crashes a typed Livewire `Form` property (`data_set()` throws `TypeError` on a typed `?string`) or a hard-typed helper (`superClean(?string $text, ...)`) rather than leaking anything. Guard at the read boundary by coercing (not silently dropping, if the array's index alignment feeds vote counts or similar — see `Feed::normalizePollChoices()`) any non-scalar value to a joined string before it reaches a scalar-typed consumer. This is a distinct bug class from the two above — no sanitizer needed, no HTML involved, just defensive type coercion. Reference: `About::mount()` + `ProfileFormPresenter::aboutMe()` (`about_me`), `Feed::extractPollSettings()`/`normalizePollChoices()` (`poll_options`).

**Rule of thumb:** HTML column, single author (admin only) → plain `{!! !!}`. HTML column, dual author (admin RichEditor + user plain-text form) → `Str::sanitizeHtml()` then `{!! !!}`. Any column (HTML or not) shown as a short excerpt/snippet/notification string → `superClean()`. Array/json column feeding a typed scalar consumer → a shape-normalize guard at the boundary, unrelated to sanitization.
