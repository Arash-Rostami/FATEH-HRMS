# Livewire Module Pattern

## Target Structure

```
ComponentName/
├── Main.php
├── Forms/
│   └── SomethingForm.php
├── Actions/
│   └── DoSomethingAction.php
├── Validators/
│   └── SomethingValidator.php
└── Presentation/
    └── SomethingPresenter.php
```

---

## Step 1 — Audit the existing component

Categorize every method/property (and trait methods) into: **Form state** (`wire:model`-bound props), **Validation** (`validate()`, rules, messages), **Persistence** (DB writes, file storage), **Component state** (`activeTab`/`perPage`/search/modal flags), **Livewire hooks** (`mount`/`updated*`/`#[Computed]`), **Presentation** (`sprintf`/`diffForHumans`/label lookups), **Traits** (state+logic mixes — removal candidates).

## Step 2 — Create Form Objects (one per UI form)

```php
namespace App\Livewire\{Module}\Forms;

use Livewire\Form;

class SomethingForm extends Form
{
    #[Validate('...')]
    public string $field = '';

    protected function messages(): array { ... }

    public function validated(): array
    {
        return $this->validate();
    }
}
```

Move all `wire:model` fields, `rules()`, `messages()` from the component/traits into the Form Object. Keep only this form's fields. Livewire auto-instantiates — no `new`/`mount`. `wire:model="form.field"` works identically — **no Blade changes** except the prefix.

> **`#[Validate]` array-rule gotcha:** `#[Validate([...])]`'s array form is parsed as a key-value rules map (`Livewire\Features\SupportValidation\BaseValidate::boot()`) only when its **first key is non-numeric**. `#[Validate(['array', 'collaborators.*' => 'exists:users,id'])]` puts `'array'` at numeric key `0`, so the whole array silently collapses into one malformed rule — the wildcard never registers, no error/warning. Key every entry explicitly: `#[Validate(['collaborators' => 'array', 'collaborators.*' => 'exists:users,id'])]`.

## Step 3 — Create Actions (one per write operation)

```php
namespace App\Livewire\{Module}\Actions;

class DoSomethingAction
{
    public function __construct(private SomethingValidator $validator) {}

    public function execute(SomethingForm $form): void
    {
        $this->validator->validate(...);
        // DB writes, file storage, etc.
    }
}
```

Single public `execute()`. Receives Form Objects and/or models — never `$this`. No `dispatch`/session/redirect (those side effects stay in `Main`). Inject via method injection: `public function submit(DoSomethingAction $action)`. If pre-conditions are complex (4+ checks, DB lookups, policy resolution), delegate to a Validator (Step 3a).

## Step 3a — Create Validators (only if needed)

Only when an Action's pre-condition logic is numerous/complex/multi-DB-check. Single public `validate()` — throws `Exception` on failure, returns `void` on pass. No writes/side effects. Container auto-resolves into the Action's constructor.

```php
class DoSomethingAction
{
    public function __construct(private SomethingValidator $validator) {}

    public function execute(...): Model
    {
        $this->validator->validate(...);
        // persist
    }
}
```

**Do not create** for 1–2 simple guards — inline them:

```php
public function execute(Reservation $reservation, User $user): void
{
    if ($reservation->status !== 'active')
        throw new Exception("...");

    if (!$user->hasElevatedRole() && $reservation->user_id !== $user->id)
        throw new Exception("...");

    // persist
}
```

## Step 4 — Create Presenter (only if needed)

Only if Blade calls `$this->getSomething()` display methods. Pure read-only — no writes/DB/state.

```php
namespace App\Livewire\{Module}\Presentation;

class SomethingPresenter
{
    public function formatThing(mixed $data): string { ... }
}
```

Pass via `render()`: `view('livewire.path', ['presenter' => new SomethingPresenter()])`. The view follows the module name (`dms` → `dms.blade.php` + `dms/` partials). If the formatting is a one-liner used once, inline it in Blade with `@php`.

## Step 5 — Clean up Main

After extraction `Main` contains only:

```php
class Main extends Component
{
    public SomethingForm $form;
    public string $activeTab = 'default';
    public ?array $selectedItem = null;
    public int $perPage = 10;
    public string $search = '';

    public function mount(): void { /* set initial form values */ }

    public function submit(DoSomethingAction $action): void
    {
        $action->execute($this->form);
        // side effects only: dispatch, reset, tab change
    }

    public function updated($prop): void { ... }
    public function updatedFormField($value): void { ... }

    #[Computed]
    public function items() { ... }

    public function switchTab(string $tab): void { ... }
    public function viewItem($id): void { ... }

    public function render()
    {
        return view('livewire.path');
    }
}
```

Remove from Main: state+logic traits, DB calls outside Actions, validation rules (→ Form Objects), formatting methods (→ Presenter), `persistX`/`storeX`/`validateX` private methods.

## Step 6 — Update Blade

Only two change types: (1) form field prefix `wire:model="subject"` → `wire:model="form.subject"`; (2) presenter calls `{{ $this->getFormattedId($item) }}` → `{{ $presenter->formatId($item) }}`. Everything else (`$activeTab`, computeds, `$this->items`, event listeners) is unchanged.

## Checklist

- One Form Object per form (fields+rules+messages); one Action per write op (`execute()` only); Validator only for 4+ guards/complex DB pre-checks; Presenter only if Blade calls formatting methods on `$this`
- `Main` = state, mount, hooks, computed, navigation, render only; Blade changes only the field prefix and presenter calls
- No `$this->reset()` wiping just-set state — use scoped `$this->form->reset()`
- Actions receive Form Objects/models — never `$this`; side effects (toast/redirect/tab) stay in `Main`
- Public properties holding an Eloquent model or record id are `#[Locked]` unless the client is meant to change them — prevents id-swapping onto another user's record (IDOR)
- Bulk-action Actions (client-supplied id array, e.g. `selectedTasks`) filter loaded models through the same `can_*` accessor the single-record method uses, *inside* the Action — e.g. `Task::whereIn('id', $taskIds)->get()->filter(fn($t) => $t->can_change_status)`. The accessor is server-side from `auth()->id()`, so unowned ids are silently dropped, not acted on
- When Blade hides a button under an *extra* condition beyond the `can_*` accessor (e.g. `@if($task['is_delegator'] && $column !== 'done')`), that extra condition must be re-checked inside the Action too — a UI-only restriction is not a server-side guard. Found via `UndoTaskAssignmentAction` (checked `is_delegator` but not `status !== 'done'`)
- **Every user-panel module ships a `legend.blade.php`** (taskboard pattern, non-obvious nuggets only); **every admin resource ships a `FilamentAdminGuide`**. Module on both sides → both surfaces; one side → that side only. MANDATORY pipeline step — like doc-sync + test-coverage, never skip. See "User-panel legend pattern" below + filamentPattern.md §3.4.

## What NOT to do

- No Actions for reads (those are `#[Computed]`); no `$this` into an Action; no `dispatch()`/`redirect()` inside an Action
- No Presenter for values already available as model attributes/computed properties
- No Form Object for never-submitted state (search/pagination/tab — stay on `Main`)
- No Validator for 1–2 simple guards — inline them
- Don't over-split: one simple form + no formatting helpers → Form Object + Action is enough
- No legend content that states the obvious or adds visual noise — nuggets must be non-obvious + valuable; if a module has too little non-obvious content, omit the legend rather than pad it

## User-panel legend pattern (MANDATORY pipeline step)

Every user-panel Livewire/Dashboard module ships a `legend.blade.php` — a help modal the user opens from the page. This is a **mandatory pipeline step** (treated like doc-sync + test-coverage): never ship or modify a user-panel module without authoring/refreshing its legend. If the module also has an admin Filament resource, that resource gets a `FilamentAdminGuide` too (see filamentPattern.md §3.4) — both sides → both surfaces; one side → that side only.

Pattern (reference `resources/views/livewire/dashboard/taskboard/legend.blade.php` + `reservation/legend.blade.php`):
- Tabbed modal via Alpine `x-data="{ tab: '…' }"` + a pill tab bar: `flex p-1 mb-5 bg-[var(--md-sys-color-surface-variant)]/40 rounded-2xl border border-[var(--md-sys-color-outline-variant)]/30`; active pill `bg-[var(--md-sys-color-primary)] text-[var(--md-sys-color-on-primary)] shadow-md`; inactive `text-[var(--md-sys-color-on-surface-variant)] hover:bg-[var(--md-sys-color-surface-variant)]/60`.
- Panels via `x-show="tab === '…'"` + `x-cloak`.
- Content rows = bordered cards: `rounded-xl border border-[var(--md-sys-color-outline-variant)]/40 bg-[var(--md-sys-color-surface-container-low)] px-4 py-3` + an `h-8 w-8 rounded-lg` icon chip + bold label + text. Status colors may use the `--tool-*` palette (sapphire/gold/amethyst/sage) via a `match`; other chips use `--md-sys-color-{primary|secondary|tertiary|error}-container`.
- A «نکات» notes tab of `info`-icon info rows.
- Trigger: a help button on the page opening an `x-ui.modals.dialog` (see `reservation.blade.php` / `channel.blade.php`).

Non-negotiable rules:
- Content = NON-OBVIOUS, valuable nuggets only. No obvious statements. No visual noise. Default to having a legend; omit only if there is too little non-obvious content.
- Icons: `material-symbols-rounded` (Google) — real ligatures only, each verified with `grep -xF "name" .claude/material-symbols-ligatures.txt` (source of truth = the woff2 ligature table, NOT `index.d.ts`, which omits legacy aliases like `done`/`email`/`tips_and_updates`/`remove_circle` that the font still renders — trusting it yields false positives). Never use: `shield_check`/`checklist_partial`/`event_share`/`event_add`/`widget` (singular) — use `verified_user`/`rule`/`share`/`event`/`widgets`. Admin Filament-native icon props use Heroicons. See filamentPattern.md §3.4 icon convention.
- Tailwind JIT-safe: NEVER Blade interpolation inside arbitrary-value brackets (`bg-[var(--md-sys-color-{{ $c }}-container)]` is invisible to Tailwind's source scanner → unstyled). Use a `match` returning full literal class strings.
- No comments. `convertToPersian()` for digits.

## Data-bag Presenter + lazy render (Feeds)

`Feeds` extends Step 4's Presenter to a **data-bag** shape: `FeedPresenter` returns small arrays bundling everything a Blade region needs in one call, so the view does one `@php $flags = $presenter->feedFlags($feed) @endphp` instead of re-deriving fields inline.

- `feedFlags($feed)` → `['isPoll','showComments','showReactions','settings']` (one call gates the whole card).
- `pollData($feed)` → `['isMultiple','options','total','counts','userVotes']` (computed once before the option loop); `optionState($index, $pollData)` → `['count','pct','isMine']` per option reusing the bag.
- `commentMeta($comment, $editingCommentId)` → `['user','avatarUrl','hasPhoto','isOnline','isOwner','isEditing']` per comment row.
- `mediaGrid($media)` → `['items','images','cols','rows']`; `$media` is `$feed->media_urls` (pre-resolved URLs — see asset-URL convention below), so the grid is pure layout and the view never calls `Storage::`.
- `categoryValue($category)` normalizes the raw-DB-string `category` (not cast to `FeedCategory` enum) via `($category?->value ?? $category)` — `?->value` on a non-null string returns `null` in PHP 8 (no throw), so `?? $category` recovers the string. Used by `categoryEmoji`/`feedFlags` instead of repeating the idiom in Blade.

`render()` passes `['presenter' => new FeedPresenter()]`. `timeline` → `item` → `header`/`comments`/`media` are all `@include`s, so `$presenter` is inherited by every partial (Laravel `@include` forwards all current vars); no per-include plumbing. The Presenter is pure (no DB, no state): `pollResults/pollChoices/pollSettings` operate on eager-loaded `polls`/`poll_options`; avatar/online read eager-loaded `profile`/`last_seen`.

**Lazy comment render-gate:** comments were `@include`d for every feed inside an `x-show` (CSS-hidden but server-rendered), so a feed with many comments rendered every card on initial load. Now `item.blade.php` gates the `@include` behind a Livewire flag: `@click="open = !open; if (open && !loaded) { $wire.openComments(feedId); loaded = true; }"` (Alpine tracks `open`/`loaded` locally; survives Livewire morph), `@if($openedCommentFeeds[$feedId] ?? false)` wraps the `@include`. `openComments($feedId)` only flips the flag — comments stay eager-loaded in `feeds()`, so the badge count and write-method refreshes (`addComment`/`deleteComment`/`updateComment` still `unset($this->feeds)` → re-eager-load) are unchanged. Initial load renders zero comment cards.

**`withCount` vs a scoped eager-load are independent counts.** `feeds()` eager-loads `comments` through a closure scoping top-level only (`fn($q) => $q->whereNull('parent_id')->latest()`), so `$feed->comments->count()` in the badge counted **top-level** — but admin `FeedTablePresenter::commentsCount()` uses `->counts('comments')` over the unscoped base relation (`hasMany(Comment::class)->latest()`), counting **all incl. replies**. Fix: add `->withCount('comments')` to the same `feeds()` query and read `$feed->comments_count` in the badge — `withCount` always counts the **base relation definition**, ignoring eager-load closure scope, so it matches admin exactly while the scoped `comments` collection still drives the visible thread. Rule: when a relation is eager-loaded with a display scope but you also need the true total for a badge/counter, add `withCount` — never derive the total from the scoped collection.

## Layout-injected global banner (broadcast across all pages)

For a UI element on **every** user-panel page (not one route), mount a single Livewire component once in the shared layout — `resources/views/layouts/app.blade.php` — via `@livewire(\App\Livewire\Dashboard\Countdown::class)`, inside the existing `@unless(View::hasSection('minimal_layout'))` block so minimal/auth layouts stay bare. Do NOT pepper every page; one layout mount broadcasts everywhere.

`Countdown` is the reference. Rules:

- **Guest-guarded, cached lookup:** `render()` returns early with an empty placeholder for guests; for authed users it calls one cached model lookup (`Event::activeCountdownEvent()`, `Cache::remember` 60s, public upcoming + PHP-filtered `countdown.enabled`) and returns `event => null` when nothing is active — the blade renders an empty `<div wire:key>` so the slot collapses cleanly.
- **Per-user dismissal is a preference, not a column:** `dismiss()` writes `preferences.countdown_dismissed_at` via the matched `getPreference('x')` / `setExtraValue('preferences.x', v)` pair on `User` (see User-preferences note in filamentPattern), compared against `today()->toDateString()` so dismissal expires at local midnight. Guarded by `abort_unless(auth()->check(), 401)`; `save()` wrapped in try/catch + `report($e)` so a preference write failure never 500s the page.
- **No new state on `Main`:** no Form Object / Action / Validator — only renders and dismisses; active-record selection lives in the model (cached).
- **Asset:** the confetti library is a vendored browser-global. At runtime `countdown.js`'s `init()` lazy-loads it via a dynamic `<script>` injection (`s.src = '/js/lib/confetti.browser.min.js'`, appended to `document.head`) only when the `confetti` payload flag is true and `window.confetti` is not already present — NOT a `<script>` tag in the layout or banner blade (the banner blade must keep a single root element: Livewire `RootTagMissingFromViewException`, so an inline `<script>` sibling is illegal). The runtime-loaded copy is `public/js/lib/confetti.browser.min.js` (served at `/js/lib/...`, the exact URL `s.src` uses); the source lives at `resources/assets/js/lib/confetti.browser.min.js`. The Alpine factory (`resources/js/components/alpine/data/countdown.js`, imported into `main.js` and registered `Alpine.data('countdown', countdown)`) reads the event payload via `@js($event['date_iso'])` / `@js($event['messages'])` / `@js($event['mood'])` / `@js($event['confetti'])` — never `{{ }}` in a JS string literal. Confetti renders to an in-card `<canvas x-ref="confettiCanvas">` via `window.confetti.create(canvas, {resize, useWorker:false})` (behind content at `z-index:1`), gated by the `confetti` payload flag — mourning keeps confetti but `confettiColors()` switches the palette to black grays and the banner gets `countdown-banner--mourning` (floral icon + somber muted CSS variant). The countdown JSON column uses bare sub-keys (`enabled`/`mood`/`confetti`/`messages`) — never `countdown_*`-prefixed; `HasCountdown::packCountdown`/`unpackCountdown` are canonical read/write, `activeCountdownEvent()` re-derives `mood`/`confetti` for the payload.

## Asset URL resolution convention

User-panel blades never call `Storage::` to build image/file URLs — that re-stats the filesystem per render. Files can live in two places (the `public` disk at `/storage/...`, or hand-placed under `public/...` served as `/...`), so resolution is **two-tier**: storage-disk-first, `asset()` fallback. Single source = `HasPublicAssetUrl` trait (`app/Models/Traits`): `public static resolvePublicAssetUrl(?string $path): string` (blank→`''`, `http(s)://`/`//`→as-is, `Storage::disk('public')->exists()`→`->url()`, else `asset()`). Models expose cached accessors over it (`Post`/`Link::imageUrl`, `Photo::imageUrls`, `Feed::mediaUrls` — all `->shouldCache()`). Presenters pull the trait directly (`use HasPublicAssetUrl` + `self::resolvePublicAssetUrl($path)`) — `DocumentPresenter::parseAttachments`, `OnboardingPresenter` (videos/thumbnail/guides), `ContactPresenter::attachments`, `SuggestionPresenter::attachmentUrl`; elsewhere `Model::resolvePublicAssetUrl($path)` (`Ticket` files via `Ths/Main::resolveTicketFileUrls`). Distinct from `HasAvatar::resolveImageUrl` (prefix-routed avatars). The trait ships only a static method, so applying it to a model has **no Filament side effect** — no new virtual attribute; only models that own an image column add an accessor. `Storage::path()/exists()/download()/delete()` (DMS + Contact downloads, `DeleteProfileImageAction`) are filesystem I/O, not display URLs — left as-is.

**Always name the disk explicitly on these calls** — `filesystems.default = local` (root `storage/app/private`, no `url`), so a bare `Storage::exists()`/`Storage::download()` checks the private disk and misses anything saved to `storage/app/public`. `Reports::download()` hit exactly this: `Storage::exists()`/`Storage::download()` (default disk) for files the admin FileUpload saves to the `public` disk → every admin-uploaded report fell through to the "not found" toast — fixed to `Storage::disk('public')->exists()/->download()` as tier 1, keeping `storage/app/<path>` and `public/<path>` fallbacks for legacy/hand-placed files. The same default-disk bug class hit **display-URL accessors**: `Resource::displayImageUrl` and `Report::thumbnail` both used bare `Storage::url($col)` (default `local`, no `url`) for `public`-disk files → 404 — fixed to `self::resolvePublicAssetUrl($col)` with `->shouldCache()` (matching `Post`/`Link::imageUrl`). A parallel raw-column bug hit **avatar display bags**: `Tab/Calendar` birthday/anniversary packed `'avatar' => $p->image` (raw DB column) into the events list, and the Filament `feed/comment-thread`/`comment-reply` partials bound `:existingImage="optional(auth()->user()?->profile)->image"` — both bypassed `HasAvatar::resolveImageUrl`, so stored paths like `profiles/images/x.jpg` rendered as bare relative `src` and 404'd. Fixed to `$p->getImageUrl()` and `auth()->user()?->getProfileImageUrl()` respectively (the `ContactPresenter::avatar` / user-panel `comments.blade.php` precedent). Rule: any image column bound into an `<img src>` or display array must pass through the matching resolver (`getImageUrl`/`getProfileImageUrl` for avatars, `resolvePublicAssetUrl`/a cached accessor for other public-disk files) — never the raw column, never bare `Storage::url()`. Filament's `feed/video-preview` blade and the Filament-only `Message::attachmentUrls()` are out of scope.

## Persian (Jalali) date convention

Dates are **stored as Gregorian `Y-m-d`**, converted to Jalali only at the edges. Matches the Filament side (`PersianDateFieldService`), so a date saved in one panel round-trips in the other.

- **On submit** (Action): assemble Jalali y/m/d into Gregorian — `Jalalian::fromFormat('Y/m/d', sprintf('%04d/%02d/%02d', $y, $m, $d))->toCarbon()->format('Y-m-d')`. Wrap in `try/catch` returning `null` (a flat 1–31 day list can submit an invalid Jalali date).
- **On hydrate** (`mount`): `Jalalian::fromCarbon(Carbon::parse($value))` → `getYear()/getMonth()/getDay()`. The `x-ui.forms.date` select **option values are non-padded** (`range`/`$i+1`/`range(1,31)` → `"5"` not `"05"`), so hydrate parts must be non-padded — `getYear()/getMonth()/getDay()` (ints → `"5"`) land correctly; when splitting a zero-padded `Y-m-d` string (e.g. seeding `EventForm` from `selectedDate`), strip padding via `(string)(int)$part`. The assembled **submit** string is the zero-padded inverse (`sprintf('%04d-%02d-%02d', …)`). `Tab/Calendar` (`EventForm`) follows this triplet; its action reassembles `Y-m-d` then combines with `time` via `Jalalian::fromFormat('Y-m-d H:i', "$date $time")->toCarbon()` (date+time variant).
- **Validation**: gate parts all-or-nothing with `required_with`; validate calendar validity with `CalendarUtils::checkDate($y, $m, $d, true)` (leap-year aware) inside a closure rule.
- **Display**: `toJalali($value, 'Y/m/d')` is calendar-safe (returns already-Jalali strings untouched, converts Gregorian) — tolerates legacy mixed-format rows. `toJalaliSmart($value)` is the "drop midnight" variant: `Y/m/d` when time is `00:00`, else `Y/m/d H:i` — right for most date columns but **wrong for all-day events**, where the user panel intentionally shows a uniform `00:00` chip (regular events render `Jalalian::fromCarbon($event->date)->format('H:i')`, so an all-day event stored at midnight shows `00:00`; birthdays/anniversaries hardcode `00:00`). To make admin Event table/infolist match, `EventTablePresenter::date()`/`EventInfolistPresenter::date()` use `toJalali($state, 'Y/m/d H:i')` (always shows time) instead of `toJalaliSmart($state)`. Pick `toJalaliSmart` for normal fields, the explicit `Y/m/d H:i` form when a `00:00` time is meaningful and must not be hidden.
- **Chat message smart timestamp** (cross-module — Contact `ContactPresenter::messages`, Channel `ChannelPresenter::messages`): per-message `time` = `$createdAt->isToday() ? $createdAt->format('H:i') : toJalali($createdAt->toDateTimeString(), 'Y/m/d H:i')`. Day-group separator label uses `toJalali($date, 'j F Y')` (Jalali day month year, NOT `translatedFormat('j F Y')` which renders Gregorian with translated month). Keep `امروز`/`دیروز` for today/yesterday. The `datetime` (ISO) field is unchanged for the `<time datetime>` attribute.
- **User-panel display standard — uniform `j F Y`**: user-panel date displays default to `toJalali($value, 'j F Y')`, with carve-outs: **(a) precise timestamps** keep full time — Contact/Channel chat balloons + read-receipt tooltips (`Y/m/d H:i`), Profile document upload (`Y/m/d H:i`), error page (`Y/m/d H:i:s`); **(b) shorter functional forms** — Gallery month filter keys (`F Y`, the `x-show`/dropdown `key` the timeline filter matches) and Reservation calendar day labels (`j F`, year implicit within a single month view); **(c) relative/presence** via `toJalaliRelative()`/`since()` for last-seen/online. Do not introduce a new format string outside these — use `j F Y`. Admin has its OWN standard (`toJalaliSmart` via `HasJalaliAdminLabels`; see `filamentPattern.md`); the two panels intentionally differ.
- **Chat read-receipts** (cross-module — Contact 1:1, Channel group): for `is_mine && is_last` messages, the presenter emits `readers` (array of `['avatar','name']`, up to 3), `read_count`, `is_read` (`read_count > 0`), `is_read_by_all` (`read_count === total_members`, where `total_members` is an internal non-sender counter that is `0` when no other members exist, so the boolean is false on empty membership — not an emitted field). The readers map is built by ONE memoized query in the component (`Main::readers()` for Channel; contact uses a per-message `read_at`), passed into the presenter's `messages()`/`messageGroup()` — never queried inside the presenter loop. The blade renders `done_all` (primary when `is_read_by_all`, muted when `is_read`), `done` (muted when not read), plus an avatar stack (up to 3 `<x-ui.avatar>` + `+N` chip). Zero non-sender members → no check/avatars (vacuous-truth guard).
- **Cross-panel consistency**: if a model exposes its own formatted-date accessor (e.g. `Task::createdFormatted`/`deadlineFormatted` via `$appends`), that accessor remains the **user-panel** source of truth — Blade reads it directly (`$task['created_formatted']`, `j F Y`). The **admin** side no longer calls the accessor: it uses `HasJalaliAdminLabels` (`createdLabel()`/`adminDateLabel()`, `toJalaliSmart`) so admin is uniform `Y/m/d H:i` while user panel keeps `j F Y`. The old `TaskResource` admin (`Y/m/d`) vs Kanban card (`j F Y`) drift was resolved by giving each panel its own format.
- **Font**: dates render in the **natural/system font, never `font-mono`**. Monospace is reserved for code-like values — IDs/serials (`SN-20260101-000001`, ticket `#0001`), document codes/versions (`DOC-1 - 2.0`), credentials/passwords, emails, version badges (`β.5`), calculator/keycap displays, and numeric counters (`tabular-nums` counts/pagination, which is `font-variant-numeric`, not a mono family). Stripped `font-mono` off every calendar-date/event-time/timeline-date/release-date display so they inherit the body font; `tabular-nums` left in place.

## Calendar event sharing + StateService-driven notification

An event owner shares an event with coworkers; recipients get a menu badge via `StateService` (the same indicator→`BadgeSyncService` chain Suggestion uses). The badge is **pull-only** — appears on the recipient's next menu render, not pushed at share time. Sharing reuses `StateService::flush()` — a **global cache-version bump only** (the `purgeMenuNotifications()` global wipe was removed; see badge-vs-notification below). The sharer gets an in-app **toast** only; no persistent confirmation notification is written.

- **Data** — `event_shares(event_id, user_id recipient, shared_by, timestamps)` with `unique(event_id,user_id)`; `EventShare` model; `Event::shares()` HasMany. Shares created **only by the owner** (guarded in `ShareEventAction` and again in `Calendar::openShareModal`/`sharingEvent`), so the visibility query `where user_id=me OR private=false OR whereHas shares user_id=me` cannot leak a private event; public events were already visible (sharing a public event is redundant but harmless).
- **Action** — `ShareEventAction::execute($eventId, $sharerId, $recipientIds)` owner-guards (`Event::where('user_id',$sharerId)->find`), drops the sharer and non-positive IDs, validates recipients against real `User` rows, then **diff-syncs** (`array_diff` add/remove against current pluck) so an unchanged selection touches no rows. After the diff calls `StateService::flush()` (global cache-version bump only) — one primitive reused from Suggestion, no separate `invalidate()`/push, no row purge. Recipients from `User::getCachedActiveOptions()->except(auth)` (same staff picker TaskBoard uses), passed as Livewire array `shareRecipientIds`; pre-fill casts to `(string)` to match checkbox `value=""` attrs (Alpine array binding uses strict `===`). The bulk `insertOrIgnore()`/query-`delete()` deliberately bypass `EventShare` model events, then `flush()` explicitly — so the model `booted()` hooks never double-fire on the user-panel flow. `insertOrIgnore` (not `insert`) makes the unique `(event_id,user_id)` constraint race-safe: a concurrent same-event share skips the duplicate instead of throwing `QueryException`, and the returned row count drives `added` so an idempotent re-share reports `added=0`. `Calendar::shareEvent` catches the intended `InvalidArgumentException` (owner guard → inline `@error('share')`) and adds a `catch (\Throwable)` backstop that `report()`s + emits an error toast.
- **Sharer feedback (toast + self-nudge)** — sharer gets the immediate toast (action summary) plus a **persistent self-nudge** bell row («رویداد شما به اشتراک گذاشته شد: X») via the per-record nudge layer — one per event, only while it still has ≥1 share and is upcoming. `Calendar::shareEvent` maps the summary: `added>0` → «رویداد «X» با N نفر به اشتراک گذاشته شد.», `removed>0` → «اشتراک رویداد برای N نفر لغو شد.», else info «تغییری در اشتراک‌گذاری اعمال نشد.». `ShareEventAction` stays pure share-domain orchestration returning the summary — it does not build Filament `Notification`s; it just dispatches `ReconcileNudge('shared-events:nudge', Event::class, $event->id)->afterCommit()` after `flush()` so the nudge engine writes the bell rows for both sharer and recipients. Full sharer-vs-recipient message + per-event keying logic is in `app/Services/Menu/statePattern.md`.
- **Notification (proximity badge, both parties)** — `Indicators\SharedEvents implements MenuBadge` (`key=shared-events`), registered in `StateService::$indicators`, **structurally identical** to `ActiveAds`/`PendingSuggestions` (no per-user method, no sub-interface). `isActive()` lights for **both** sides of a share when the event is **imminent** (within 24h, not the whole upcoming span): recipient via `EventShare::hasImminentFor($user)` (`where('user_id', me)->whereHas('event', fn $q => $q->whereBetween('date', [now, now+24h])->exists()`), owner via `Event::hasImminentSharedFor($user)` (`where('user_id', me)->whereHas('shares')->whereBetween('date', [now, now+24h])->exists()`). Pure SQL `whereBetween`, no PHP loop. `title`/`body` are party-agnostic («رویداد مشترک نزدیک است» / «…در ۲۴ ساعت آینده است…»). Deliberately **stateless** (no `read_at`): the badge naturally clears once the event leaves the 24h window, avoiding any write-side-effect in the read-only `selectedDayEvents` computed. **Pull-only**: `flush()` bumps the global cache version, so each recipient's next `StateService::get()` recomputes `SharedEvents` and `BadgeSyncService::sync()` reconciles the per-user DB notification — the same model `PendingSuggestions` uses. No `isActiveFor`/`UserMenuBadge` (removed as redundant: `sync` already creates/clears the row on recompute). **Sync cadence**: `sync()` runs **once per version**, inside `StateService::get()`'s `Cache::remember` closure (only on a cache miss) — not on every render. A cache hit costs a single cache read and **zero DB queries** (previously `sync()` fired per render with SELECT + dedup-DELETE per active indicator). Each `sync()` is wrapped in `try/catch` so a notification-DB failure degrades gracefully. **Badge vs notification (two signals)**: the menu **dot** is driven by the cached `$menuState[key]` bool (`menu.blade.php` `@js($menuState)[item.id]`), stays lit the whole time the condition is true, is **not** dismissable — a permanent status signal independent of the bell. The **bell entry** is the Filament DB notification row; a one-time **nudge**: fires once (created unread) when the condition first becomes active, user can mark it read ("حذف اعلان" → `markAsRead`). **`sync()` never re-unreads an existing row** — its logic is *active + no row → create; active + row exists → leave it alone (preserve `read_at`); inactive → delete*. A dismissed nudge **never resurfaces** while the condition stays continuously active — `flush()` is a pure version bump (no purge), so the dismissed row survives every flush and `sync()` leaves it read. The old code both reset `read_at=null` on version change *and* globally purged all menu-badge rows on `flush()`; both were removed. When the condition goes inactive the row is deleted; if it later re-occurs, a fresh unread row is created. No `version`/`cleared` bookkeeping fields are written — the payload carries only `menu_key` plus static title/body/action.
- **Model-side sync** — `EventShare::booted()` hooks `created`/`deleted` and `Event::booted()` hooks `updated`/`deleted` to call `StateService::flush()` (both wrapped in `DB::afterCommit()`), so shares and **event edits/deletes** through the **model** bump the version. `Event::booted()` makes the **badge** reflect an owner's date edit/deletion promptly (the nudge side was already covered by the `Event` trigger) instead of lagging the ≤2h TTL. The user-panel `ShareEventAction` bypasses these via bulk ops + its own explicit `flush()` (and short-circuits before it on an empty diff) — no double-fire.
- **Admin panel** — no standalone resource: an **`EventSharesRelationManager`** on `EventResource` renders a per-event "اشتراک‌های این رویداد" table (`recipient.name`, `sharer.name`, Jalali `created_at`). **Read-only** (`isReadOnly()` → no create/edit/attach) because shares originate only from the user-panel flow; the one allowed write is a custom plain `Action::make('revoke')` (not a `DeleteAction`, so it isn't caught by the read-only deny-list) that calls `$record->delete()` (firing the model `deleted` hook → `flush()`). `canViewForRecord` hides the table on events with no shares; the revoke button is gated by `EventResource::canDeleteAny()`.
- **UI** — `share.blade.php` is an `x-ui.modals.action` with the `modal-inner-card !w-full !max-w-none` + scoped-defer pattern (identical to `create.blade.php`); a checkbox list bound to `shareRecipientIds`. The owner-only `share` button sits next to edit/delete in `events.blade.php`; recipients see a `مشترک` chip via the `is_shared` flag (`$event->shares->contains('user_id', Auth::id())`) plus the sharer's name (`shared_by_name`, resolved via `$event->shares->firstWhere('user_id', Auth::id())?->sharer?->name`) after eager-load `with(['shares' => fn($q) => $q->select('id','user_id','event_id','shared_by')->with('sharer:id,name')])` in `selectedDayEvents()` to avoid an N+1 on the day list. `calendarDays()`'s separate month-grid eager-load stays the lighter `shares:user_id,event_id` — the sharer identity is only needed on the day-detail list, not the grid dots.
- **Calendar grid signs (shared + imminent)** — `calendar/grid.blade.php` marks shared days and imminent shared days. `Calendar::calendarDays` eager-loads `shares:user_id,event_id` and computes per day `hasShared` (any event the auth user owns-with-shares OR is a recipient of) and `hasImminentShared` (a shared event whose `date` is within `[now, now+24h]` — the same 24h window as the badge). The cell appends a tiny `group` glyph after the `+N` counter: **outlined** in `--md-sys-color-secondary` for a shared-but-not-near day, **filled** in `--md-sys-color-error` when imminent; an imminent non-selected, non-today cell also gets a thin `ring-1 ring-[var(--md-sys-color-error)]/70`. The legend gains two chips (`مشترک` outlined-secondary, `نزدیک` filled-error) reusing the sidebar's `group`/secondary vocabulary. Glyph/ring are suppressed on the selected and today cells.
- **Per-record nudges (`NudgeService`)** — a **separate, additive** bell-nudge layer alongside the badge/dot: one new notification row **per qualifying record** (new active ad, suggestion entering an attention stage, new shared event) instead of one per indicator. Declarative registry + dumb engine — each rule is a `MenuNudge` class in `Notifications\` (declares key, triggers, show/for/title/body, refresh); `NudgeService::register(new ...Nudge())` binds its Eloquent events and reconciles per-record under a lock, `->afterCommit()`, with a `:nudge`-suffixed `menu_key` so it never collides with the badge namespace. One new class + one `register()` line adds a rule; the engine is never edited. Full mechanism + logic (both badge and nudge) is in `app/Services/Menu/statePattern.md` — read that before editing anything in `App\Services\Menu` or wiring a new trigger.

## Calendar event reminder — pure client-side, no bell/nudge/badge, rides the existing manual alarm tool

An event owner (or an admin, for public events) can set `events.remind_hours` (nullable tinyint, `Event::REMIND_HOURS_OPTIONS = [1,2,3,6,12,24]`) — deliberately a **ceiling**, not the alert moment: the countdown becomes visible/armed starting `remind_hours` before the event, but the **alarm rings at the event's actual start time**, not at the `remind_hours` mark. This is a user-requested semantic (confirmed explicitly — do not "simplify" it back to alarm-fires-at-the-offset without re-confirming). No `Notification::make()->sendToDatabase()`, no `NudgeService`/`MenuBadge`, no scheduled command, no second persisted "reminded" flag — explicitly rejected by the user in favor of reusing the site's existing manual countdown/alarm tool (`stopwatch.js`, the "آلارم / تایمر دستی" hamburger-menu tool) end to end.

- **Server query** — `Event::nextReminderFor(User $user): ?array` (`app/Models/Event.php`): `whereNotNull('remind_hours')`, `where('date', '>', now())` (event hasn't started), `whereRaw('DATE_SUB(date, INTERVAL remind_hours HOUR) <= ?', [now()])` (the arming window has opened — inclusive `<=`, no off-by-one), the SAME private/public/shared visibility clause `selectedDayEvents()` uses (`user_id = me OR private = false OR whereHas shares user_id = me`) so no scope broadening, `orderBy('date')->first()` — the single nearest in-window event. Returns `{id, title, event_at_iso}` where `event_at_iso` is the event's own `date` (the alarm target), or `null`. No caching (per-user, and the user explicitly didn't want cache-store ambiguity) — the `events` table is small (dozens of rows), a single indexed query per page load is cheap, same cost class as `Countdown`'s existing per-render lookup.
- **Client component** — `App\Livewire\Dashboard\EventReminder` mirrors `Countdown`'s exact shape (auth-guarded, one query in `render()`, no other state) and is mounted right next to it in `layouts/app.blade.php`: `@livewire(\App\Livewire\Dashboard\Countdown::class)` then `@livewire(\App\Livewire\Dashboard\EventReminder::class)`, both inside the same `@unless(View::hasSection('minimal_layout'))` block near the top of the layout — so it re-runs fresh on **every full-page load, anywhere in the app**, not just the Calendar tab. That's what makes the arming reliable despite this app having no `wire:navigate`: the target is recomputed from live data on each page view instead of depending on JS state surviving navigation.
- **Bridging to the stopwatch — `window.__eventReminder`, not a `CustomEvent`:** `event-reminder.blade.php`'s `x-init` sets a plain global (`window.__eventReminder = @js(['eventAtIso' => ..., 'title' => ...])`), and `stopwatch.js`'s `init()` reads it directly (`if (window.__eventReminder) this.armReminder(window.__eventReminder)`) rather than listening for a dispatched event. Reason: `EventReminder` mounts earlier in the DOM (top of the layout) than the stopwatch (`<x-dashboard.global/>`, later in the same layout file) — Alpine initializes components in DOM order, so a `window.addEventListener('arm-reminder', ...)` registered inside the stopwatch's own `init()` could miss an event dispatched by the earlier-initializing producer. A plain global read is order-independent: whichever side runs first just writes/reads a value, no race. See `resources/js/scriptPattern.md` §3.4 for the absolute-timestamp (`armedUntil`) resumption technique this then feeds into.
- **`stopwatch.js`'s `armReminder({eventAtIso, title})`** — no-ops if `this.timer.running` is already true (never interrupts a user's own manually-running countdown; since event ordering by `date` is stable, a farther event can never "become nearer" while a nearer one is already armed, so this guard never starves a more urgent reminder). Computes `seconds = Math.max(0, Math.round((new Date(eventAtIso) - Date.now())/1000))`, bails safely if the parsed date is `NaN`. Sets `reminderTitle` (shown in both the full modal heading and the minimized dock pill's label — `label-expr="reminderTitle ? 'یادآوری: ' + reminderTitle : (timer.running ? '...' : '...')"`) and **`minimized = true`** (not `open`) so the unobtrusive dock pill is already present the moment it's armed — no full-modal popup, but never fully invisible either (a `minimized:true`-but-never-shown reminder would ring with zero visual feedback if the browser also blocks the alarm's `Audio.play()` autoplay, since there's no prior user gesture on a fresh page load). `reminderTitle` is cleared on `resetTimer()`/`setTimerPreset()`/`closeModal()` (the user reclaiming manual control) but preserved across `restoreState()` (a page reload while armed). `formatSeconds()` renders `h:mm:ss` once >= 3600s (a bare `mm:ss` would show a 3-hour reminder as "180:00").
- **Calendar UI** — `selectedDayEvents()` includes `remind_hours` in the mapped array; `events.blade.php` renders an alarm-icon chip ("N ساعت قبل") next to the existing private/shared/reservation-linked badges, guarded by `!empty($event['remind_hours'])` (safe: `0` is unreachable through both admin and user forms, whose Selects only offer `Event::REMIND_HOURS_OPTIONS`). `calendar/legend.blade.php` gained a matching row (icon `alarm`, a new `'error'` chip-color case reusing `--md-sys-color-error`/`error-container` rather than inventing a 5th `--tool-*` token) explaining the ceiling-vs-alarm-timing semantic in plain language. The month grid (`grid.blade.php`) intentionally has no reminder glyph — scoped to the day-detail list only, matching where the badge itself lives.
- **Known, accepted limitations of the client-only design** (do not "fix" without a product conversation — each is a direct tradeoff of the "no DB/bell/nudge" constraint): only the single nearest in-window event is ever armed (the stopwatch has one countdown, not a queue) — a second event's window can open and close unseen if the user never reloads a page in between; an already-armed countdown doesn't know if its event is later deleted/rescheduled/had its reminder removed (no push channel to cancel it, fires on stale data until it completes or is manually reset); multiple open tabs each independently play the alarm sound when the same countdown completes; the alarm audio can be silently blocked by browser autoplay policy on a page with zero prior interaction (the dock badge is the visual fallback for that case, which is why `armReminder` always sets `minimized = true`).

## Persian official holidays (تعطیلات رسمی) — static dataset, no DB, no external API

`app/Services/HolidayService.php` is a plain static-array class — `private const HOLIDAYS` keyed by zero-padded Jalali `'Y-m-d'` (matches `Calendar::calendarDays`'s `sprintf('%04d-%02d-%02d', ...)`), each value an array of `['title', 'type' ('ملی'|'مذهبی'), 'hijri']` (a day can carry more than one, e.g. Eid overlapping Norouz). Same shape as `QuoteService` — no DB table, no HTTP call, no cache (opcode-cached PHP constant, O(1) lookup, ~0.05µs/call). Only two methods: `getAll()` (test-only, `array_key_first` for stable regression dates) and `getHolidaysForDate(string $date): array` (the one production call site); every other candidate helper (`getHolidaysByType`, `getHolidaysForYear`, `getHolidaysForYearAndType`, `isHoliday`) was deleted as unused dead code.

- **Wiring** — `Calendar::calendarDays()` calls `HolidayService::getHolidaysForDate($dateString)` per day, sets `hasHoliday`/`holidayTitle` (first entry's title only if a day has 2+ holidays; `selectedDayEvents()` still lists every entry). `selectedDayEvents()` prepends a `type: 'holiday'` collection (mapped from `getHolidaysForDate($this->selectedDate)`, `id: 'holiday-{index}'`) ahead of events/birthdays/anniversaries.
- **Grid + legend** — `calendar/grid.blade.php` extends the Friday rose-tint (`$index % 7 === 6`) to also fire on `hasHoliday`, adds an `event_busy` rose icon (checked before birthday/anniversary/event, so a holiday's icon wins if a day has both), a `title` tooltip, and a thin rose ring; the legend gains a `تعطیل` chip in the same vocabulary. `events.blade.php` and `getEventStyles()` (`app/Helpers/index.php`) both grew a `'holiday'` branch alongside `birthday`/`anniversary`, styled `bg-rose-50 text-rose-600 ring-1 ring-rose-100` — holiday entries carry `is_owner: false` so owner-only share/edit/delete buttons never render.
- **A future live-API swap (`persiancalapi.ir`/`hpez/persiancalapi`) was evaluated and rejected** — small, unreviewed community project (single-commit fork, no independent accuracy audit, data scraped live from `time.ir` on every request with no caching); a static admin-curated dataset was judged the better fit; revisit only if accuracy drifts and a maintained source appears.

## Reservation date strip — policy-derived horizon, Jalali-month paged

The user-panel reservation date strip (`Livewire/Dashboard/Reservation/Main.php::availableDates`) is driven by **the same admin policy the validator enforces** — one source of truth. It reads `window_days` from `ValidationService::getPolicies($activeTab)`, the exact call `TimeWindow` uses, so admin → `ReservationPolicy` → strip + validator cannot drift; `ReservationPolicy::saved/deleted` boot flush (`flushPolicyCache`) keeps the cache in sync. `window_days` set → the strip **pages by Jalali month** (`$currentYear`/`$currentMonth`, `nextMonth`/`prevMonth` with 1↔12 wrap — same idiom as `Tab/Calendar`), rendering only days in `[today, now+windowDays]`. `canPrevMonth` hides + disables the back arrow past the current Jalali month (TimeWindow blocks past → ERR-019); `canNextMonth` hides + disables forward once the next month's first day exceeds the horizon (else ERR-003). Blade renders `{{ $canX ? '' : 'hidden disabled' }}`; `nextMonth`/`prevMonth` re-check server-side, so a tampered client cannot navigate out of bounds. Every visible date is genuinely bookable. `window_days = null` (unrestricted) → flat **21 days from today**, no month-jumper (`@if($this->dateWindow !== null)` gate in `reservation/date.blade.php`). Jump is **view-only**: `$this->date` changes only via `setDate()`, so browsing months never disturbs the booking flow. The within-strip scroll chevrons (`scrollPrev/scrollNext`, Alpine-only) are separate from the month-jump buttons (Livewire state).

- **Time picker** (`reservation/time.blade.php`, `@includeWhen($activeTab == 'meeting', ...)`): `availableTimeSlots()` reads `allowed_hours` (`['start','end']`) and renders 30-min slots in `[start, end)`, falling back to 08:00–19:30 when unset/misconfigured (`end <= start`). Closes the drift the old hardcoded 08–19:30 had with `AllowedHours`. A `window_hours` notice badge (`minNoticeHours()` computed) renders above the pickers when `window_hours > 0` — informative only, does not disable slots. Full-day tabs (seat/spot/car) skip `AllowedHours` (validator returns early for `isFullDay`), so picker/badge are meeting-only; `window_hours` still applies to full-day bookings through `TimeWindow` (`start` is `startOfDay`) but is not previewed on the date strip.
- **The remaining four policies are each a `#[Computed]` reading `getPolicies($activeTab)`, never a DB write, so admin stays the sole writer.** `allowed_days` → the strip skips disallowed weekdays via `allowedDays()` (normalizes to lowercase weekday keys matching `lang/.../strings.php` `days`, e.g. `saturday`), applied as one extra `continue` in **both** branches of `availableDates()`. Mirrors `AllowedDays` exactly: `null`/non-array ⇒ no filtering, an array (even empty) ⇒ `in_array(strtolower($date->englishDayOfWeek), …)` — so the strip never shows a day the validator would reject (ERR-005) nor hides one it would accept. Additive filter; the horizon is untouched. `min_duration_minutes` / `max_duration_minutes` → passive hint chip (`durationBounds()`) above the meeting pickers, three text forms (both ⇒ "مدت مجاز: N تا M دقیقه", min-only, max-only), nothing when both unset; `Duration` still enforces. `max_per_user` → active counter chip (`activeLimitUsage()`) under the strip, mirroring `ActiveLimit`'s exact query (user_id, `whereHas('resource', type)`, Gregorian `whereMonth`/`whereYear` of the **selected** `$this->date`'s `start_time`, status `Active`+`Released`, `toBase()->count()`), returning `['count','max','near']` where `near = count >= max` is the same threshold that throws ERR-012 — so the chip turns error-colored exactly when the next booking would be rejected. `null` when `max_per_user` unset; invalidated on `setDate`/`switchTab`. `allow_repeat` → the recurring toggle (`recurring.blade.php`) is wrapped in `@if($this->allowsRepeat)`, where `allowsRepeat()` is `(bool)(policies['allow_repeat'] ?? true)` — the same default-true `Recurrence` uses. Because Livewire public state can go stale, `book()` builds recurrence as `($this->isRecurring && $this->allowsRepeat) ? […] : null`, so a stale `isRecurring=true` can never reach `Recurrence` and throw ERR-010. All five policy-derived computeds (`dateWindow`, `allowedDays`, `durationBounds`, `activeLimitUsage`, `allowsRepeat`, plus `availableTimeSlots`/`minNoticeHours`) are unset together in `resetFilters()` (called by `switchTab`); `setDate` additionally unsets `activeLimitUsage`. They reuse the cached `getPolicies()` (`Cache::remember`, flushed by `ReservationPolicy::saved/deleted`).

### Reservation UX-batch — preview computeds (read-only hints, validator stays authoritative)

A second layer of `#[Computed]` hints previews *what the validator will do* without enforcing. All reuse `getPolicies($activeTab)` and the existing policy computeds — never a second source of truth. Unset alongside the policy computeds in `resetFilters()`/`invalidateResourceCache()`.

- **`recurPreview()`** — when `isRecurring && allowsRepeat`, mirrors `BookAction::generateOccurrences` exactly: `intervalDays = weekly ? 7 : 1`, `count = max(2, min(52, recurCount))`, dates from `$date` stepping the interval, each `ok = >= startOfToday && (dateWindow null || <= horizon endOfDay) && (allowedDays null || in_array(weekday))`. Rendered as chips in `recurring.blade.php` ("تاریخ‌های برنامه‌ریزی‌شده"); ok primary-container, !ok surface + strikethrough + `block` icon. Labeled *planned* — cannot preview DB conflicts, only policy/weekday/horizon, so a !ok chip means "the validator would drop this occurrence" and the action still skips failures with `continue`. Empty array when not recurring or `allow_repeat` off (`@if(!empty($this->recurPreview))`-gated).
- **`selectedDuration()` / `humanizeMinutes()`** — meeting-only; `minutes = start->diffInMinutes(end)`, `valid = minutes > 0 && within min/max_duration_minutes` (null ⇒ unbounded), text is `humanizeMinutes` ("<60 ⇒ "N دقیقه", exact hours ⇒ "N ساعت", else "N ساعت و M دقیقه", all `convertToPersian`'d) or "زمان پایان باید بعد از شروع باشد" when `<= 0`. Badge in `time.blade.php`, error-colored when `!valid`. `null` for non-meeting tabs.
- **`bookingBlockReason()`** — pre-submit guard on each card (`image.blade.php`): returns the active-limit message when `activeLimitUsage['near']` (priority), else for meeting the end-before-start message when `minutes <= 0`, else `durationBounds` (or generic out-of-bounds) when `!valid`; `null` when bookable. Card shows the reason + `disabled` submit (`{{ $blocked ? 'disabled' : '' }}`). Composes only existing computeds, so across N cards it resolves once per render (Livewire `#[Computed]` caching) — the quota query runs once, not per card.
- **`startSlotMeta()`** — server-authoritative time-of-day dimming applied to **both** start and end pickers: today ⇒ each slot is `past` (`< now`), `soon` (`< now + window_hours` — the same minNotice `TimeWindow` enforces), or `ok`; a future date ⇒ all `ok`; returns `['states'=>[…], 'first'=>first-ok-time-or-null]`. Blade reads `$state = $slotMeta['states'][$time] ?? 'ok'` for **both** pickers (end mirrors start: dimming end slots before `now + minNotice` is correct since a valid end must be `> start ≥ now + minNotice`). Blocked slots get `disabled` + line-through + a past/soon `title`; the selected-but-past slot keeps blocked styling. Dimming is a **hint**, not a guard — `BookAction`/`TimeWindow` still reject past bookings (ERR-019) server-side; server clock is authoritative. Uses server `now`, matching the validator.
- **`syncDefaultTimes()`** — called from `mount()` and `resetFilters()` (not per-render): picks a sane default start from `allowed_hours` + `window_hours`. Today ⇒ first 30-min slot `>= now + window_hours`; a future date ⇒ the first slot of the day; clamps end to `dayEnd` when the next slot overshoots; returns early (keeps prior defaults) when no slot remains today (late evening) — `startSlotMeta` then dims the stale default as `past` and the validator rejects it. Deliberately **not** called on `setDate` so a chosen time persists across date navigation.

### Reservation UX-batch — Blade affordances

- **Quota progress bar** (`reservation.blade.php`) replaces the active-limit text chip: `pct = max>0 ? min(100, round(count*100/max)) : 100`, track `h-1.5 bg-surface-variant`, fill `width:%` `bg-primary` or `bg-error` when `near` — "N / M this month" with the bar going red at the rejection threshold (ERR-012).
- **"امروز" pill** (`date.blade.php`) — `wire:click="goToday"` next to the month-jumper, `disabled` + opacity-40 when `$this->date` is already today. `goToday()` resets `date` to today, snaps `currentYear/Month` to now, unsets date computeds (routes through `setDate`, so resource + quota caches invalidate), dispatches `scroll-to-selected`. The strip's scroll container carries `@scroll-to-selected.window="$el.querySelector('[data-selected]')?.scrollIntoView({inline:'center',block:'nearest',behavior:'smooth'})"`; the selected button carries `data-selected`. Clicking today (enabled only when `date != today`) smoothly swipes the strip back to center the current date — the browser event fires after the morph, so the newly-selected button is found. Alpine `.window` listeners live inside the root `x-data="reservation()"` tree, never emitted through `{{ }}`.

## Reservation smart-default date + safe dedupe batch

A two-part change to `Main` initialization, validated by an adversarial 3-subagent unanimous-confidence gate (dispatch 3 independent `general-purpose` agents with the exact diff + framing, implement only if unanimous ≥99%; re-dispatch on a no-output glitch). The dedupes were the no-op half (all 3 passed 99%+); the smart default is an intentional behavior change.

- **Smart default date (`mount`)** — `mount()` now sets the date from `$this->availableDates[0]['value'] ?? now()->toDateString()` instead of always `now()->toDateString()`. When today's weekday is disallowed by `allowed_days`, the default becomes the **first allowed future day within the horizon**; when today is allowed, it stays today (byte-identical); when **no** allowed day fits the horizon (e.g. window=2, next allowed is +3d), it falls back to today via `??`. Load-bearing detail: **ordering** — `resetMonthCursor()` **must run first**, because `availableDates()`' windowed branch reads the typed-no-default `public int $currentYear; public int $currentMonth;` (`new Jalalian($this->currentYear, $this->currentMonth, 1)`). The old order (date-first) accessed `availableDates` before the cursor was set → `Error: Typed property must not be accessed before initialization`, swallowed by `availableDates`' `catch(Throwable)` → returned `[]` → fallback today → the feature was silently **inert** for windowed tabs. Correct order: `resetMonthCursor() → smart date → syncDefaultTimes()`. `availableDates` never reads `$this->date` (no circular dependency); `#[Computed]` access in `mount()` is fine because Livewire hydrates `#[Url] activeTab` **before** `mount()` runs; `switchTab`→`resetFilters` unsets `availableDates`/`dateWindow`/`allowedDays`. `goToday()` is intentionally **not** changed — its `now()->toDateString()` is correct because "today" is by definition allowed on that path.
- **Dedupe A — `allowedHoursBounds()`** — `availableTimeSlots()` and `syncDefaultTimes()` both parsed `allowed_hours['start'??'08:00']` / `['end'??'20:00']` with the same `if ($end <= $start)` guard. Extracted to `private function allowedHoursBounds(?array $allowed): array` returning `[$startCarbon, $endCarbon]`; both callers do `[$start, $end] = $this->allowedHoursBounds($policies['allowed_hours'] ?? null)`. Verified byte-identical across 6 `allowed_hours` shapes (null, normal, wrapped, missing start, missing end, equal). Zero logic change.
- **Dedupe B — `forUser` scope alignment** — `activeLimitUsage()` and `cancelLimitUsage()` both wrote `Reservation::where('user_id', auth()->id())`. Switched both to `Reservation::forUser(auth()->id())` (the existing `scopeForUser` is exactly `where('user_id', $userId)` with an `int` typehint). Identical query.
- **Dedupe C — `resetMonthCursor()`** — `mount()`, `goToday()`, and `resetFilters()` each inlined `Jalalian::now()` → `getYear()`/`getMonth()`. Extracted to `private function resetMonthCursor(): void`; called in each, preserving the exact original order. `Jalalian::now()` reads the real clock each call, so extracting changes nothing about timing.

A standalone diff harness (replicated `availableDates` exactly, ran old-vs-new `mount` across 7 scenarios) confirmed: today-allowed → identical (A/C/E); today-disallowed + next-in-horizon → NEW jumps to that future day (B/D/F); today-disallowed + none-in-horizon → NEW falls back to today == OLD (G). 3 changed, 4 identical.

## Reports dual load-more pattern (one canonical infinite-scroll idiom)

Reports uses **two load-more shapes in one component**: the **list view** has an explicit `<x-ui.buttons.load-more action="loadMore">` button (FAQ-style, click to load), the **card view** uses a gallery/feed-style sentinel `<div x-ref="loadTriggerCard"><x-ui.loaders.spinner/></div>` with **no button**. Because the sentinel's `wire:key` changes each load (count-based), the observer MUST be re-bound via `Livewire.hook('morph', ({component, el}) => { if (component.id === this.$wire.__instance.id) this.$nextTick(() => { if (this.$refs.loadTriggerCard) this.setupIntersectionObserver(); }); })` — `setupIntersectionObserver` disconnects the prior observer before re-creating. Guard `if (!this.$refs.loadTriggerCard) return` so the list view (no sentinel) does nothing. This matches `gallery.js` verbatim. Pattern: one canonical infinite-scroll idiom (sentinel + IntersectionObserver + morph re-bind), reused per module — do not invent a second one.

## Presenter extraction — additions + do-not-over-split rule

This session added four Presenter methods, all following the Step-4 "Data-bag Presenter" shape (bundling multiple derived values a Blade region needs in one call):
- `FaqPresenter::badge()` + `questionText()` — badge derivation + question display text.
- `GalleryPresenter::months(Collection):Collection` — `filter → map → unique('key') → sortByDesc('sort') → values()`. The filter→map→unique pipeline belongs in the Presenter, not the blade.
- `FeedPresenter::categoryLabels():array` — static map of category → label.

Rule: only extract presentation logic that bundles **multiple derived values** a Blade region needs. Do NOT create a Presenter for raw model attributes or single computed properties — those stay as model accessors or inline `@php`. The Data-bag Presenter replaces several per-row `@php` blocks with one call; if a candidate method only returns one scalar, it does not justify a Presenter.

## Dead state rule — remove unread public Livewire properties

Do not leave public Livewire properties that no view reads. `Gallery::$assetsLoaded` was written in `mount()` but never read in any blade — it only bloated every Livewire snapshot (public properties are serialized into every request). Remove the property AND all its assignment sites. Before removing, grep `resources/views` for readers to confirm it is truly dead. A public property with no Blade reader is dead state, not a hidden feature.

## Universal aggregate fold (UnreadNotifications)

`UnreadNotifications extends Filament\Notifications\Livewire\DatabaseNotifications` and folds the bell modal so >4 unread rows sharing a `data.menu_key` collapse to one or two **synthetic** `DatabaseNotification` rows rendered natively by Filament's modal — a UI-side anti-flood cap, zero engine change, applies to **every** nudge key (DMS, posts, tasks, feeds, …), not only DMS. Admin is untouched: `isPaginated()` returns true only for `admin`, so `getNotifications()` and `getUnreadNotificationsCount()` early-return the parent result; the non-admin `getNotificationsQuery()` adds `->unread()`.

- **Fold rule** (`getNotifications`) — `countBy` the parent collection by `data.menu_key`; iterate (parent relation `morphMany->latest()`, so first-encountered = most-recent). Per group: `count <= AGGREGATE_THRESHOLD(4)` ⇒ keep individual; `>4` ⇒ emit one aggregate and skip the rest (`$emitted[$key]` dedupe). **DMS** is special-cased to **two** aggregates — `agg:dms-controller:nudge:sign` (count = `DMS::needsSignCount`) and `agg:dms-controller:nudge:read` (count = `DMS::needsReadCount`). **Every other** over-threshold group ⇒ one generic aggregate titled «{count} اعلان جدید», body `«آخرین: {most-recent row title}»` (the "آخرین:" prefix is load-bearing — without it the body reads as "5 of that one item"). **DMS both-zero guard**: if `sign===0 && read===0` but stale rows exist (the `afterCommit` reconcile window before `ReconcileNudge` clears them), do **not** fold — keep individuals and skip the count adjustment, so `list == count == bell-dot` (the dot is a separate raw `unreadNotifications()->count()` and would otherwise stay lit while the modal went empty).
- **Header count** (`getUnreadNotificationsCount`) — start from `parent::getUnreadNotificationsCount()`, then a grouped SQL (`->reorder()->selectRaw("JSON_UNQUOTE(JSON_EXTRACT(data,'$.menu_key')) as menu_key, COUNT(*) as cnt")->groupBy('menu_key')`) adjusts each over-threshold group: DMS ⇒ `+= (sign>0?1:0)+(read>0?1:0) - cnt` (skipping on both-zero guard); generic ⇒ `+= 1 - cnt`. `->reorder()` is mandatory — the `notifications()` relation is `morphMany->latest()`, so an inherited `ORDER BY created_at` collides with `groupBy` under `sql_mode=only_full_group_by` (1055). `max(0, …)` floor.
- **Synthetic row** (`makeAggregateRow`) — `new DatabaseNotification(['id' => 'agg:{key}[:{mode}]', 'type' => FilamentDatabaseNotification::class, 'data' => Notification::make()->title()->body()->warning()->persistent()->getDatabaseMessage(), 'read_at'=>null, 'created_at'=>now()])`. The **deterministic `agg:` id** is load-bearing: `Notification::fromDatabase` sets `getId()` from `DatabaseNotification::getKey()`, and the inline view builds `wire:key = "{id}.notifications.{id}"` — a `Str::uuid()` id regenerates every render ⇒ `wire:key` churns ⇒ Alpine re-mounts + replays the enter transition every 30s poll; the stable `agg:` id stops the flicker. No `actions` key ⇒ no per-row action buttons, but the **close X is unconditional** (`x-on:click="close"` → `notificationClosed` with `notification.id`), so dismissing a synthetic via the base `removeNotification` would delete-by-id (0 rows) and reappear next render (vanish-then-return).
- **Honest dismiss** (`removeNotification` override, `#[On('notificationClosed')]`) — `str_starts_with($id,'agg:')` ⇒ parse `menu_key` out of the id (strip `agg:` prefix, then strip a trailing `:sign`/`:read` mode suffix — only DMS uses a mode and no nudge key ends in `:sign`/`:read`, so `preg_match('/:(?:sign|read)$/')` is unambiguous) and `$this->getNotificationsQuery()->where('data->menu_key',$key)->update(['read_at'=>now()])` — **mark-read, never delete**, so the aggregate stays dismissed. Real rows fall through to `parent::removeNotification`. DMS dismiss marks the whole DMS group read (sign+read rows share one `menu_key`, the sign/read split is computed at render from the `reads` table) — acceptable because the **DMS badge (Signal 1, pull-based `hasPendingFor`)** persists independently of the bell rows.
- **`dmsCounts` instance memo** — `DMS::needsSignCount`/`needsReadCount` are plain statics called in **both** `getNotifications()` and `getUnreadNotificationsCount()` on the same render; `once()` won't share across two call sites (distinct closure objects). `protected ?array $dmsCountsCache = null` + `dmsCounts(int $userId): array` (`??= [needsSignCount, needsReadCount]`) memoizes per-render — Livewire does not persist protected properties across requests, so it resets each request and the second call site is free.

## `@island` rules — memoized islands, reduced scope, and the tinker mask

The Channels module (`app/Livewire/Dashboard/Channel`) **uses `@island(name:'sidebar')` + `@island(name:'messages')`** per `app/Livewire/Dashboard/Channel/channelPattern.md`. The traps below are **general guidance for any `@island` use** — reviewers MUST reason about island behavior statically; tinker PASS does not acquit.

- **Island auto-scoping keys off `action.origin`, which only `wire:click`/`wire:model` directives set — `x-on:click` (Alpine) → `this.$wire.method()` does NOT.** Livewire's `interceptAction` (`dist/livewire.esm.js:13778`) auto-scopes an action to its enclosing island ONLY if `action.origin` is set; `wire:click`/`wire:model` call `setNextActionOrigin({el, directive})`, but an Alpine `x-on:click` that calls `this.$wire.method()` reaches `fireAction` with `outstandingActionOrigin = null` → `interceptAction` returns early → no island metadata → the server does a FULL render → every `@island` whose `always:` is false emits a `mode:'skip'` empty fragment (`HandlesIslands::renderSkippedIsland`) → the island DOM is left untouched. This is why `loadOlder`/`setFilter`/`search`/`removeAttachment` (all `wire:click`/`wire:model`) worked while `send`/`saveEdit`/`deleteMessage`/`undoDelete`/`selectChannel`/navigations (all `x-on:click → $wire.method()`) did not — the DB wrote and `#[Computed]` was unset, but the messages island showed nothing. **Rule: every Alpine-triggered action that must update an island is explicitly scoped with `$wire.$island('name').method()` — scope the action ITSELF so the method runs and `renderIsland('name')` fires in one request (server `call` hook sees `metadata.island` → `skipRender()` + `renderIsland()`), then chain a refresh of the other island only if its UI also changed.** The Channels pattern: `selectChannel` is `$wire.$island('messages').selectChannel(id).then(() => $wire.$island('sidebar').refreshUnread())`; `send`/`saveEdit`/`deleteMessage` are `$wire.$island('messages').<method>()`; navigations (`toggleBrowse`/`openCreate`/`closeCreate`/`backToList`/`leaveChannel`/`createChannel`/`joinChannel`) are `$wire.$island('messages').<method>().then(() => $wire.$island('sidebar').refreshUnread())`. `undoDelete` is scoped in the blade (`x-on:click="$wire.$island('messages').undoDelete()"`). Do NOT use `$wire.$island('name').$refresh()` — `$refresh()` is a magic action, not a real method; scope a real method instead. `wire:click`/`wire:model` triggers need NO explicit scoping — they auto-scope; only Alpine `x-on:click → $wire.method()` triggers need `$island()`.
- **Island `$refresh()` runs in REDUCED scope.** On `$island('messages').$refresh()` the island re-renders with: ✅ public properties as bare vars, ✅ `$this`, ✅ `$__livewire`. ❌ bare `#[Computed]` variables are NOT injected — `$activeChannel`, `$messages`, `$groupedMessages`, `$joinableChannels`, `$presenter` are undefined on refresh. **Rule: inside any `@island` template, access computeds via `$this->` — `$this->activeChannel`, `$this->messages`, `$this->presenter` — never the bare name.** The header/info/browse/messages islands had to be converted from `$activeChannel` → `$this->activeChannel` after a real browser island-refresh threw "Undefined variable $activeChannel".
- **`@php(...)` parenthesized form breaks inside islands.** `@php($a = 1; $b = 2)` compiles differently in Livewire's `ExtendedCompilerEngine` island compile path vs a full render, producing "syntax error, unexpected token ;". The block form `@php ... @endphp` compiles identically in both paths. **Rule: inside `@island` templates, always use the block form `@php ... @endphp`, never `@php(...)`.** The parenthesized form is fine outside islands.
- **`@entangle` and nested anonymous Blade components (`<x-...>`) do NOT work inside islands.** Nested anonymous components don't inherit `$__livewire`, so `@entangle($model).live` (used by `<x-ui.forms.search>`) fatals inside an island. **Rule: inside `@island` templates, use plain `wire:model` / `wire:model.live` + Alpine `x-model` for inputs, never `<x-ui.forms.search>` or any component that relies on `@entangle`.** The sidebar search is a plain `wire:model.live.debounce.200ms` input.
- **`Livewire::test()->html()` and tinker full-render MASK every island-only bug.** A full render shares scope globally (computeds injected as bare vars, `@php(...)` compiles the full-render way, the whole component renders as one tree) — so `Livewire::test(...)->call('send')->html()` shows the new message, the edited body, the restored row, all correct; the island `$refresh()` path is never exercised. **Rule: a tinker/test PASS is not evidence the island works.** Reviewers MUST reason statically — `grep` island templates for bare computed names, `@php(`, `@entangle`/`<x-ui.forms.search` inside `@island`, and mutations for a missing `$island(...).$refresh()` or `messages-updated`-style dispatch — because the runtime test that would catch these is a real browser island-refresh, which the gate does not perform. This is why 59 reviewers green-lit a module that errored on first browser use.
- **`x-ref` inside `@island` throws on the first island re-render and aborts Alpine's whole init pass — "works after refresh, dies after first change."** Registering `x-ref` walks up `findClosest(el, i => i._x_refs …)` to the nearest Alpine root to write `_x_refs[name]`. During an island morph, Alpine's `cloneNode`/`initTree` clones the new subtree while its ancestor chain is mid-detach, the walk returns `undefined`, and it throws `Cannot read properties of undefined (reading '_x_refs')` (Alpine `module.esm.js:3436`, `$refs` magic → `getArrayOfRefObject`). The throw aborts `initTree` partway, so every directive AFTER the ref element (toolbar buttons, `x-on:click` handlers, `x-if` clones further down) never initializes — the island looks frozen even though the morph completed. First cold load survives; the first `send`/`saveEdit`/`deleteMessage` that re-renders dies. **Rule: never use `x-ref` inside an `@island` template.** Reach the element by `document.getElementById(...)` (the Channels module's `msg-viewport`/`msg-ta` access pattern in `channel.js`) or, for reactive sibling state, a scoped `<div x-data="{ len: 0 }" x-effect="len = ($wire.composer.body || '').length">` wrapper feeding `x-on:input="len = $el.value.length"` — no ref walk, morph-safe. `grep -rn 'x-ref=' resources/views/livewire/dashboard/channel/` MUST return empty.
- **`<template x-if>` inside `@island` renders dead buttons when the condition is true at morph time.** Alpine's morph plugin clones `<template x-if>` content into the DOM during the island morph but does NOT reliably re-run `x-on:click` handler init on the cloned content — buttons render but clicks do nothing. The trap is specific to x-if conditions **TRUE at morph time** (content cloned during the morph): the Channels message bubble used `<template x-if="!(isEditing && editingMsgId === {{ $msg['id'] }})">` (true while not editing → toolbox cloned at morph → dead). An x-if **FALSE at morph time** (e.g. the composer's `<template x-if="replyingTo">`, false until `startReply`) is fine — its content is cloned later by Alpine's reactive system, which inits correctly. **Rule: inside `@island`, prefer `x-show` over `<template x-if>` for any toggle whose visible branch contains interactive elements.** `x-show` keeps both branches in the DOM (one `style="display: none;"`), Alpine inits them once, handlers survive every morph. With `x-show`, replace `x-init` with `x-effect` for behavior that must re-run each time the toggle becomes active — e.g. `x-effect="if (isEditing && editingMsgId === {{ $msg['id'] }}) $nextTick(() => { $el.focus(); $el.selectionStart = $el.selectionEnd = $el.value.length })"`.
- **`ChannelMessage::lastIdForChannel(int): ?int` returns null for empty channels — null-guard every caller.** `MarkChannelReadAction` did `orWhere('last_read_message_id', '<', $lastId)` with `$lastId === null`, which Laravel rejects with "Illegal operator and value combination". **Rule: any caller of `lastIdForChannel` (or any nullable-id lower-bound filter) must `if ($lastId === null) return;` before the query.** Empty-channel `markRead` is a no-op, not a crash.
- **`WithFileUploads` inside `@island` skips the island on upload-finish, so the staged-attachment preview never paints — bridge it with a `->self()` dispatch the island's own Alpine `$wire.on` catches, then re-render via a real island-scoped method (NOT `$refresh()`).** `startUpload`/`finishUpload` are Livewire-internal calls that don't carry island origin metadata, so the upload-finish response is a full render where the island's DOM diff is skipped. The composer property (`composer.attachments`) IS set server-side and the client model IS updated, but the staged-preview `@if(count($composer->attachments))` lives inside the island template — its HTML never morphs in, so the user picks a file, sees nothing, and only sees it after `send`. The fix is a two-call dance: (1) a Livewire `updated(string $name)` hook on the root fires when `composer.attachments` changes and dispatches `attachments-updated` `->self()` — `->self()` events are delivered at component level even when the island DOM was skipped, so Alpine `$wire.on('attachments-updated', ...)` always catches it; (2) that listener calls `$wire.$island('messages').syncAttachments()`, a real non-empty island-scoped method (e.g. `unset($this->groupedMessages)` — non-empty, non-looping, no extra query, matches the `unset($this->X)` computed-invalidation idiom; do NOT touch `composer.attachments` inside it or `updated()` re-fires into an infinite loop), which issues a fresh island-scoped request and the preview paints. **Never use `$wire.$island('name').$refresh()` here — it's the forbidden magic action; scope a real method instead.** Same trap hits any `wire:model` on a file input inside an `@island`.

## Passing PHP values into Alpine handlers — `data-*` + `$el.dataset`, not `@js()` or Blade directives inside the attribute

When a Blade-rendered list row needs to hand a server value (DB id, slug, key) to an Alpine `x-on:click` handler, **serialize it through an HTML attribute and read it back from the DOM** — never inline `@js($value)` and never embed Blade control directives inside the Alpine attribute.

- **The pattern:** put the value on the element with `data-id="{{ $value }}"`, then call `x-on:click="handler($el.dataset.id)"`. `{{ }}` HTML-escapes and stringifies, the DOM `dataset` API returns a plain string, and the Alpine handler receives it as a normal arg. Concrete Channel use: in-chat message-search result buttons (`search.blade.php`) — `data-id="{{ $r['id'] }}"` + `x-on:click="focusSearchResult($el.dataset.id)"` → `focusSearchResult(id)` → `$wire.$island('messages').focusMessage(id)`.
- **Why not `@js($value)`:** `@js()` emits a raw JS literal *directly into the attribute string*. For an int that's `123` (fine), but for any string value (UUID, slug, anything carrying quotes) `@js` emits `"abc-123"` — the embedded double-quotes **break the surrounding `x-on:click="..."` attribute**, silently corrupting the handler. The `data-*` route is immune to quoting regardless of value type, because the value lives in its own attribute (HTML-escaped by `{{ }}`), not inside a JS expression embedded in another attribute.
- **Type round-trip:** `dataset.id` is always a string. For a Livewire method typed `int $id`, Livewire JSON-wires the string and PHP's type-hint coerces it back to int — the int round-trips correctly. One micro-note: a JS `if (!id)` guard treats string `"0"` as truthy (unlike `@js(0)` which yields falsy `0`), so a `0`/missing id makes one extra round-trip before the server guard returns null; in practice list rows never carry `0`, and the server guard handles it safely, so no change needed. If you ever want to close that gap, `focusSearchResult(Number($el.dataset.id))`.
- **Same principle for the island-safe `search-field` partial:** inside Alpine attributes (`x-on:keydown.escape`, `x-on:click`) interpolate **only safe scalar identifiers** (`$model`) or a **precomputed plain string** built in `@php` (`$closeExpr`) — never Blade control directives. The earlier broken form embedded `@if($refreshSidebarOnClose)...@endif` directly inside `x-on:keydown.escape="..."`, which made the Blade compiler emit `<?php ... endif; ?>` inside the attribute and produced `syntax error, unexpected token "endif", expecting end of file` (a hard fatal, not a quoting edge case). The fix builds the close expression once in `@php` — `$closeExpr = "{$model}Fullscreen = false; \$wire.{$model} = {$model}Value" . ($refreshSidebarOnClose ? "; \$wire.\$island('sidebar').refreshUnread().catch(() => {})" : '')` — and echoes `{{ $closeExpr }}` into the attribute. One source of truth, no Blade directives inside the JS string.
- **Rule:** inside any Alpine attribute (`x-on:*`, `x-bind:*`, `x-show`, `:class`), (a) pass server values via `data-*` + `$el.dataset` rather than `@js()`, and (b) keep all conditional/loop logic in `@php` and interpolate only the resulting plain string — never put `@if`/`@foreach`/`@php(...)`/`@js(...)` inside the attribute value. This is the island-safe generalization of the `@entangle`/`<x-ui.forms.search>` ban (see the `@island` rules above): the island-safe `search-field` partial exists precisely because the shared `<x-ui.forms.search>` relies on `@entangle`, and it must stay self-contained — parameterize only by `$model` (a safe identifier) plus precomputed strings, with a unique `wire:key="search-overlay-{{ $model }}"` on the teleported overlay.

## Alpine `:class`/expression bindings on a Livewire property must read `$wire.propertyName`, never a bare variable (DMS filter buttons)

DMS's filter buttons (`dms/filters.blade.php`) had correct server-side reactivity — `updatedActiveFilter()` reset `open` and reloaded docs, `getBaseQuery()`'s JSON `whereJsonContains` matching was correct — yet users reported "filters not working, clicking does nothing." The bug was purely visual: `:class="activeFilter === 'all' ? ... : ..."` referenced a **bare** `activeFilter`, but the page root is `x-data="dms()"` (`resources/js/components/alpine/data/dms.js`), whose factory defines no `activeFilter` property at all. Alpine evaluates `:class` expressions in `try/catch` and **swallows the `ReferenceError` silently** — no console error, no visible failure — so the binding just never updated and the active-state highlight never moved, reading to the user as "the click did nothing."

Every other filter partial in the codebase (`ads/filters.blade.php`, `tab/status/filters.blade.php`, `authority/filters.blade.php`, `tab/feeds/filters.blade.php`, `tab/faqs/filters.blade.php`) already used `$wire.propertyName` correctly — DMS was the sole outlier, introduced by copy-pasting a bare-variable pattern that only works when that exact name is ALSO defined in the same page's local `x-data()` factory. The shared `<x-ui.forms.filters>` wrapper (`resources/views/components/ui/forms/filters.blade.php`) and its `filters()` Alpine factory (`resources/js/components/alpine/data/filters.js`) confirm the convention: `activeCondition`/`clearAction` props default to `this.$wire.get("activeFilter") !== "all"` / `this.$wire.set(...)`.

**Rule:** inside any Alpine attribute (`:class`, `:style`, `x-show`, `x-on:*`) that needs to read or react to a **Livewire public property**, always use `$wire.propertyName` (or `$wire.get('propertyName')`) — never a bare identifier — unless that identical name is genuinely declared inside that page's own local `x-data({...})` object or `.js` Alpine factory. Because Alpine swallows expression errors silently, this class of bug produces zero error output anywhere (browser console, Livewire, logs) and must be caught by code review/grep (`:class="\w+ ===` bare-variable patterns), not by watching for exceptions. See regression tests in `tests/Feature/Livewire/Dashboard/DmsTest.php` (`test_filter_buttons_bind_to_livewire_scope_not_bare_alpine_variable` and the filter-narrowing tests).

**Update:** the "همه" (All) button this section originally referenced was removed (`filters.blade.php`) — it was fully redundant with the shared `<x-ui.forms.filters>` wrapper's own "حذف فیلترها" (Clear Filters) button, whose default `clearAction` already does `$wire.set('activeFilter','all'); $wire.set('search','')` (a superset), shown exactly when `activeFilter !== 'all'` — i.e. exactly when the All button would have mattered. The regression test above now asserts the same `$wire.`-scoping invariant against a still-existing per-value filter button instead of the removed one.

## `getBaseQuery()` free-text search — `INSTR()`, not `LIKE`, for every free-text OR-clause

`Dms/Main.php`'s `getBaseQuery()` searches `title`/`code`/`version`/`revision` plus the `extra`/`tags` JSON columns (via `CAST(... AS CHAR)`) against one user-typed `$this->search` string. Two independent bugs, both traced to MySQL's `LIKE` operator specifically (not a query-builder or PHP-side issue), both fixed by switching every free-text clause from `LIKE '%...%'` to `INSTR(column, ?) > 0`:

1. **A literal `%`/`_` in the search term silently over-matches.** `LIKE` treats `%`/`_` as wildcards even when they arrive via a bound parameter (parameter binding prevents SQL injection, it does **not** disable `LIKE`'s own pattern-metacharacter semantics) — a search for `50%_report` would match far more than the literal string. `INSTR()` is a plain substring-position function with **no** metacharacter interpretation at all, so this class of over-matching is structurally impossible, not just guarded against.
2. **A `\uXXXX`-escaped needle silently under-matches (false negative, the more dangerous direction).** `extra`/`tags` are Eloquent `array`-cast columns, saved via `json_encode()` with no `JSON_UNESCAPED_UNICODE` flag — every non-ASCII character (all Persian content) is stored on disk as literal `\uXXXX` ASCII escape sequences, e.g. `{"notes":"رضا..."}`. Searching for the raw UTF-8 term (`رضایی`) against `CAST(extra AS CHAR)` never matches that escaped text, so the natural fix is to *also* search for the JSON-escaped form of the needle: `trim(json_encode($needle), '"')` turns `رضایی` into the literal string `رضا...` — the exact bytes present in the stored column. But `LIKE`'s **own** default escape character is `\`, so a pattern containing `ر...` gets its backslashes stripped/reinterpreted by `LIKE` itself before matching, silently corrupting the search — confirmed via direct `DB::select` with **no** query builder, **no** `CAST`, just plain `extra LIKE ?` against the raw column: still zero matches with the correctly-escaped needle. `INSTR()` has no escape-character concept whatsoever, so the escaped needle matches byte-for-byte once `LIKE` is out of the picture. This is the **same root MariaDB JSON/unicode-escaping problem family** documented in `app/Filament/filamentPattern.md`'s "MariaDB fails to match a JSON object key…" note (which covers `JSON_EXTRACT` path-matching specifically) — a *different* mechanism (LIKE-escape stripping, not JSON path encoding), same underlying cause (PHP's `json_encode` ASCII-escaping non-ASCII content), same fix direction (stop relying on MySQL to interpret the escaped bytes correctly, work with them explicitly in PHP instead).

**Current shape** (abridged — real method also repeats the `extra->Category`/`extra->type`/`extra->Type` `orWhereJsonContains` variants and the same `INSTR` pair for `tags`, omitted here for brevity; read `getBaseQuery()` directly before copying this pattern):
```php
$needle = $this->search;
$escapedNeedle = trim(json_encode($needle), '"');
$q->whereRaw('INSTR(title, ?) > 0', [$needle])
    ->orWhereRaw('INSTR(code, ?) > 0', [$needle])
    ->orWhereRaw('INSTR(version, ?) > 0', [$needle])
    ->orWhereRaw('INSTR(revision, ?) > 0', [$needle])
    ->orWhereJsonContains('extra->category', $needle) // exact-match specific keys, untouched — JsonContains has no LIKE-escape exposure
    ->orWhereRaw('INSTR(CAST(extra AS CHAR), ?) > 0', [$needle])       // ASCII/mixed substrings
    ->orWhereRaw('INSTR(CAST(extra AS CHAR), ?) > 0', [$escapedNeedle]); // Persian/non-ASCII substrings
    // ...same two INSTR lines repeated for `tags`, same four orWhereJsonContains repeated for extra->Category/type/Type
```
**Rule:** any future free-text `LIKE`-based search added to this codebase should default to `INSTR(column, ?) > 0` instead of `LIKE '%?%'` unless genuine wildcard matching (`%`/`_` as user-facing pattern syntax) is actually wanted — `INSTR` is strictly safer for "does this substring appear anywhere" searches and sidesteps this entire bug family by construction. Regression tests: `tests/Feature/Livewire/Dashboard/DmsTest.php` — `test_search_filters_by_persian_extra_value`, `test_search_with_literal_percent_and_underscore_does_not_wildcard_match`.

**Scale note:** `dms` sits at ~150 rows in practice, expected to plateau around 500–2000 — a 12-condition `OR` full scan at that size is sub-millisecond regardless of indexing. A generated-column + FULLTEXT-ngram rewrite was evaluated and explicitly rejected: the ngram parser is MySQL/Oracle-only and **not available on MariaDB** (this project's production engine — confirmed MariaDB 10.6.20 elsewhere in this doc set, vs. the plain MySQL 5.7.24 this was developed against locally), so it would work in dev and break in prod. Revisit only if `dms` genuinely grows into the tens-of-thousands range; if so, generated `STORED` columns for the *exact-match* JSON fields (`extra_type`, `extra_category`) are MariaDB-safe and worth it — the FULLTEXT/ngram half of that idea specifically is not.

## `getBaseQuery()` sort — read-state priority (unreceived → received-unread → read), then recency

The DMS workflow is two-stage per user, per document: **receive** (acknowledge existence, `ConfirmReadAction::execute($id)` → upserts a `reads` row with `read=true`) then **read** (`ConfirmReadAction::execute($id, increment: true)` → increments `read_count`). Three states follow directly from that, with no state column of their own — derived from whether a `reads` row exists and its `read_count`:

| State | Condition | Meaning |
|---|---|---|
| 0 — unreceived | no `reads` row for this user+doc | brand new, not even acknowledged |
| 1 — received, unread | `reads` row exists, `read_count = 0` | acknowledged, not yet reviewed |
| 2 — read | `reads` row exists, `read_count > 0` | fully handled |

`getBaseQuery()`'s order is this 3-tier state ascending (0 first — most-needs-action surfaces at the top) as the **primary** key, then a user-selectable column as the secondary tie-breaker *within* a tier, then `id desc` as the final deterministic tie-breaker. Read-state priority always wins over the column sort, by design (a just-updated-but-already-read doc must not outrank an older untouched one). The secondary sort is the in-tab `sortBy()` feature (title/code/updated), defaulting to `updated desc`. Implemented as a correlated subquery in `orderByRaw`, not a `JOIN`, specifically to avoid introducing a second `id` column into the query (`matchingDocIds()`'s `pluck('id')`/`select(['id','tags'])` calls right after `getBaseQuery()` would become ambiguous under a join):
```php
private function readPriorityExpression(): string
{
    return "COALESCE(
        (SELECT CASE WHEN read_count = 0 THEN 1 ELSE 2 END
            FROM `reads`
            WHERE `reads`.document_id = dms.id AND `reads`.user_id = ?
            LIMIT 1),
        0
    ) ASC";
}

private const SORT_COLUMNS = [
    'updated' => 'updated_at',
    'title' => 'title',
    'code' => 'code',
];

// ->orderByRaw($this->readPriorityExpression(), [auth()->id()])
//   ->orderBy($sortCol, $sortDir)   // from validSort(): whitelisted column + asc/desc
//   ->orderBy('id', 'desc');
```
**Security — `orderBy()` does not parameterize column names.** `$this->sort`/`$this->sortDir` are public Livewire properties (client-settable via the snapshot), so a raw `->orderBy($this->sort, $this->sortDir)` is an injection vector. `validSort()` resolves the column through the `SORT_COLUMNS` whitelist (unknown key → `updated_at`) and the direction through a strict lower-case `asc`/`desc` check (anything else → `desc`). `sortBy($column)` is itself a no-op for keys outside `SORT_COLUMNS`; calling it on the active column toggles direction, on a new column starts at `asc`. `sort` survives `switchTab` (a view preference); `pendingFilter` does not (reset per tab). `resetSort()` restores the `updated`/`desc` default and is a no-op when already there — wired to a `restart_alt` button beside the table's maximize toggle, dimmed + `disabled` at the default so it never fires a no-op round-trip.

**Gotcha — the inline `@php($expr)` Blade directive breaks `@forelse`/`@empty` compilation in this Livewire/Blade stack** when the expression contains `&&`/`===` (the compiled view throws `syntax error, unexpected token "endforeach", expecting end of file` at the later `@forelse`). Use the block form `@php … @endphp` for any multi-operator expression; reserve `@php($single = value)` for trivial single assignments only.
**Gotcha — `READS` is a reserved MySQL/MariaDB keyword** (used in stored-routine `READS SQL DATA` characteristics), so the bare, unquoted table name in a raw SQL fragment throws `SQLSTATE[42000]: syntax error ... near 'reads'` — the error points at the token *after* the real problem, not at `reads` itself, which makes this easy to misdiagnose as a paren-matching bug. Any future raw SQL referencing the `reads` table must backtick-quote it (`` `reads` ``); Eloquent's query builder backticks it automatically via `->table('reads')`/relationships, so this only bites hand-written `whereRaw`/`orderByRaw`/`DB::select` strings. Confirmed via direct `DB::select` reproduction with zero query-builder involvement.

Regression tests: `tests/Feature/Livewire/Dashboard/DmsTest.php` — `test_sort_prioritizes_unreceived_then_received_unread_then_read` (3-tier order via `search` to isolate from unrelated seeded rows), `test_sort_within_same_read_state_falls_back_to_most_recently_updated`, `test_sort_by_title_orders_docs_alphabetically_within_same_read_state`, `test_sort_by_same_column_toggles_direction`, `test_sort_by_new_column_resets_direction_to_asc`, `test_sort_by_unwhitelisted_column_is_silent_noop` (injection guard), `test_reset_sort_restores_default_and_reloads`, `test_reset_sort_is_noop_when_already_default`.

## Sticky `<thead>` is NOT viable on this table — load-more-grow wins (reverted)

A sticky table header was attempted and reverted. The DMS table's deliberate behavior is **unbounded vertical growth**: `loadMore()` appends rows and the table gets longer, scrolling the page (`dms.blade.php` root is the `overflow-y-auto` scroll container). A sticky `<thead>` requires a **height-capped scroll box** (`overflow-auto` + `max-h-[…]` on the table's wrapper) for the sticky cells to stick against — but capping the height is exactly the grow behavior the user explicitly wants kept, so the two are mutually exclusive on this markup. Two concrete failure modes confirmed: (1) `overflow-auto max-h-[65vh]` caps growth → load-more rows scroll *inside* instead of growing the page; (2) sticky `<thead th>` inside an `overflow-x-auto` horizontal-scroll wrapper produces header/body column-width mismatch. The page-level alternative (make the `dms` root the scroll container by removing the card's `overflow-hidden` and the wrapper's `overflow-x-auto`, switching the root to `overflow-auto`) would keep grow + sticky but restructures the page scroll model and the card's rounded-corner clipping — not done without an explicit decision. **Rule: do NOT re-add a sticky header to this table via an internal bounded scroll container; either accept no sticky, or restructure page-level scroll first.** Also: the `--md-sys-color-surface-container-high` token (without `-highest`) is **undefined** in `theme.css` — only `-highest` is generated — so any `bg-[var(--md-sys-color-surface-container-high)]` paints transparent; use `-highest` (or another defined token) for any header/cell that must be opaque.

## `hasMore` / `hasOlder` flag — the +1-probe idiom (no unbounded COUNT, no separate exists)

A Livewire component that gates a "load more" button on a boolean flag (`hasMore`, `hasOlder`, `hasPreviousPage`) is asking a **threshold** question — "are there more than N rows beyond the current window?" — NOT a count question. The cheap, correct way to answer it is the **+1 probe**: fetch `N + 1` rows, set the flag from `count() > N`, then trim back to `N` for display. One indexed query, no extra round-trip, no unbounded scan.

```php
$rows = Model::query()->latest('id')->take($this->limit + 1)->get();
$this->hasMore = $rows->count() > $this->limit;
$rows = $rows->take($this->limit)->sortBy('id')->values();
```

**Why not the alternatives:**
- **`COUNT(*)` / `Model::count()`** — unbounded. A `WHERE id >= X` (or `WHERE id < X`) range-scans the whole tail/head of the table just to return a number the caller only compares to N. `take(N + 1)` caps the scan at N+1 rows — once the DB has produced N+1 it stops, because the answer is already "yes".
- **A separate `->exists()` for the flag** — a second round-trip for information the +1 probe already extracts from the rows you're fetching anyway.
- **`>=` instead of `>` for the flag** — `count() >= N` is a fencepost bug: it returns `true` at the exact boundary (exactly N rows, no more), showing a "load more" button that fetches nothing. The flag is `count() > N` strictly.

**Rule:** any `hasMore`-style flag in a `#[Computed]` or Livewire method uses `take(N + 1) → count() > N → take(N)`. Never `COUNT(*)`, never a separate `exists()`, never `>=`. The same idiom answers "is row X within the first N?" guards (`take(N + 1)->pluck('id')->count()` compared to N) — capped, no unbounded scan. Concrete variants (recent-N window, anchor window, focus-target in-window guard) are implemented in the Channels module — see `app/Livewire/Dashboard/Channel/channelPattern.md` §3.3 and §7 `FocusChannelMessageAction`.

- **An absolute overlay that must "fill the space between header details and header buttons" is anchored inside the header's middle `flex-1 min-w-0` column, not centered over the pane.** `messaging/search.blade.php`'s root is `absolute top-0 left-0 right-0 z-40` and is `@include`d as the last child of `channel/header.blade.php`'s middle `<div class="flex-1 min-w-0 relative">` (between the avatar and the right-side button cluster), NOT loose inside `<main>`. `inset-x-0` makes it auto-fill exactly that column's width (no fixed `w-[min(...)]`), and the results dropdown overflows the header downward over the messages (the header is not `overflow-hidden`). **Rule: to make an overlay auto-fill the gap between two header clusters, make the middle column `relative` and anchor the overlay `inset-x-0` inside it — never center a fixed-width overlay over the whole pane.**

## `#[Computed]` is not auto-injected into Blade as a bare variable — and `Cache::flexible` for rate-limited third-party APIs (Navbar Weather)

`Navbar\Weather` silently showed the default `-- °C` placeholder forever, regardless of whether the OpenWeatherMap call actually succeeded. Root cause: `render()` returned `view('livewire.dashboard.navbar.top.weather')` with no data array, and the Blade template read a **bare** `$weatherData['temperature'] ?? '--'` — not `$this->weatherData`. Confirmed in `vendor/livewire/livewire/src/Mechanisms/HandleComponents/HandleComponents.php:449` — a component's view only auto-receives `Utils::getPublicPropertiesDefinedOnSubclass($component)`, i.e. **public properties**, never `#[Computed]` method results. `Weather` has zero public properties, so `$weatherData` was undefined; PHP's `??` swallows undefined-variable access silently (no warning, nothing logged), so the bug produced no error trail at all. **Rule: a `#[Computed]` value is only visible in Blade via `$this->propName` — if the template needs a bare `$propName`, `render()` must pass it explicitly: `view(..., ['weatherData' => $this->weatherData])`.**

Separately, `#[Computed(cache: true, seconds: N, key: '...')]` (`BaseComputed::handleCachedGet()`) is a plain `Cache::remember($key, $seconds, $closure)` — **not stampede-safe**: concurrent requests that all see a cache-miss at the TTL boundary each independently re-run the closure, each firing a real API call. For any `#[Computed]` that wraps a rate-limited third-party API, do the caching **inside the Action**, not via the Livewire attribute, using `Cache::flexible($key, [$freshSeconds, $staleSeconds], $callback)` (Laravel 11+, confirmed available — `vendor/laravel/framework/.../Cache/Repository.php:622`, DB `cache_locks` table present): fresh window serves instantly with zero work; the stale window still serves the last value instantly but defers exactly one background refresh guarded by `Cache::lock()`, so concurrent traffic at expiry never produces more than one outbound call. `FetchWeatherAction` derives the key from the configured city (`'weather.' . Str::slug($city)`) rather than hardcoding it, so a future `OPENWEATHER_CITY` change can't collide with a stale differently-labeled cache entry. **Rule: never wrap a rate-limited external API call in `#[Computed(cache: true)]` — cache it inside the Action with `Cache::flexible()` so the built-in atomic lock caps concurrent refreshes at one, and leave the component's own `#[Computed]` uncached (plain per-request memoization only).**

**Corollary — the `Cache::flexible()` callback must let real failures THROW, never catch-and-return-a-default internally.** `Repository::flexible()` (`vendor/laravel/framework/.../Cache/Repository.php:622`) unconditionally `putMany()`s whatever the callback returns — it has no way to distinguish "genuinely fresh data" from "the call failed and this is a swallowed fallback." `FetchWeatherAction::fetch()` used to `catch (\Exception $e) { report($e); return self::$default; }` internally; a single transient `cURL error 28` timeout during the deferred stale-window refresh got cached as the real result, silently overwriting the last known-good reading for the next `STALE_SECONDS` (6h) window — confirmed via a real production incident (`laravel.log`, `openweathermap.org` connect timeouts). Fixed by moving the try/catch OUT of `fetch()` and onto the `Cache::flexible()` call itself inside `execute()`: a deferred-refresh failure now propagates out of the callback, and Laravel's own `DeferredCallbackCollection::invokeWhen()` wraps every deferred callback in `rescue()` (`vendor/laravel/framework/.../Support/Defer/DeferredCallbackCollection.php:53`) — catches it, `report()`s it, and simply skips the `putMany()`, leaving the last-good stale value in cache untouched. The `execute()`-level catch still protects the one path `rescue()` doesn't cover: a cold-start call (no cache entry yet) runs the callback synchronously, so an uncaught exception there would otherwise propagate straight into the component. **Rule: when a `Cache::flexible()` callback can fail, let it throw — catch only around the `Cache::flexible()` call site, never inside the callback itself, or a transient failure gets permanently cached as if it were good data.** Regression tests: `NavbarTest::test_fetch_weather_action_preserves_stale_cache_when_deferred_refresh_fails` (seeds a stale-window cache entry, forces `fetch()` to throw via a `protected` override, manually invokes `app(DeferredCallbackCollection::class)->invoke()`, asserts the cache still holds the original value) / `::test_fetch_weather_action_returns_default_when_cold_start_fetch_throws` (no cache entry, same throwing override, asserts a graceful default instead of an uncaught exception).

**Corollary #2 — never let a third-party HTTP client's own exception message escape `report()` when the request URL embeds a secret.** `FetchWeatherAction::fetch()` builds its request URL as `?q={city}&appid={key}&units=metric` — Guzzle's connection/timeout exceptions (`GuzzleHttp\Handler\CurlFactory`) embed the full request URI verbatim in their message, and Laravel's `Psr7\Utils::redactUserInfo()` only strips HTTP Basic-auth userinfo, never query-string params — so every `cURL error 28` timeout was writing the real OpenWeatherMap `appid` key straight into `laravel.log` via `report($e)`. Fixed by catching **`\Throwable`** (not just `GuzzleException`) locally inside `fetch()` and re-throwing a sanitized `\RuntimeException('OpenWeatherMap request failed: ' . get_class($e) . ' (' . $e->getCode() . ')')` with **no `previous:` chain** — chaining the original exception would still leak it, since Laravel's exception logger walks and logs the full `getPrevious()` chain. Catching only `GuzzleException` is not sufficient: `GuzzleHttp\Client::get()` calls `Psr7\Utils::uriFor($url)` (`vendor/guzzlehttp/guzzle/src/Client.php:161`) synchronously, before any GuzzleException-wrapping transfer logic runs, and a malformed composed URL there throws `GuzzleHttp\Psr7\Exception\MalformedUriException` — which extends plain `\InvalidArgumentException`, NOT `GuzzleException` — with message `"Unable to parse URI: {$fullUrlIncludingKey}"`. A `catch (GuzzleException $e)` lets that specific exception (and its embedded key) escape uncaught, straight into `execute()`'s generic `catch (\Exception $e) { report($e); }`. **Rule: when a call to a third-party client embeds a credential in the URL/request, catch `\Throwable` (not a library-specific exception interface) at the call site and re-throw a new exception with a sanitized message and no previous-exception chain — a narrower catch type can leave non-library exception classes (URI parsing, stream-handler resource errors, etc.) with an unredacted, credential-bearing message free to reach `report()`.** Regression test: `NavbarTest::test_fetch_weather_action_sanitizes_api_key_out_of_thrown_exception_message` (points at a refused local port with a fake key configured, asserts the thrown message excludes the key and `getPrevious()` is null).

## Read a `TemporaryUploadedFile`'s metadata BEFORE `store()`/`storeAs()`, never after — same-disk moves relocate it out from under you

Production attachment sends (`.docx` files, Channel + Contact) failed with `League\Flysystem\UnableToRetrieveMetadata` — "no such file exists" — while local dev never reproduced it. Root cause is in Livewire's own `TemporaryUploadedFile::storeAs()` (`vendor/livewire/livewire/src/Features/SupportFileUploads/TemporaryUploadedFile.php:175`):

```php
// Same disk and no extra options — move instead of copy for performance.
if ($this->disk === $disk && empty($options)) {
    Storage::disk($disk)->move($this->path, $newPath);   // physically relocates the file
} else {
    Storage::disk($disk)->put($newPath, $this->storage->readStream($this->path), $options);
}
```

When the temp-upload disk (`config('livewire.temporary_file_upload.disk')`, falling back to `filesystems.default`) is the **same** disk as the destination passed to `storeAs()`, Livewire takes a same-disk fast path and **moves** (renames) the file instead of copying it — the object's own `$this->path`/`$this->disk` are never updated to reflect the new location. Every `storeAttachments()` in this codebase called `getClientOriginalName()`/`getMimeType()`/`getSize()` **after** `$file->storeAs(..., 'public')` — those calls read `$this->storage->mimeType($this->path)`, i.e. the **old, now-relocated** `livewire-tmp/{hash}.ext` path, which the move just vacated. Locally this never surfaced because dev's temp-upload disk resolves to `local` (different from the `public` destination), so `storeAs()` took the safe copy branch and left the original in place — the bug is dormant until temp-disk and destination-disk happen to coincide, which is exactly what production's config does. Reproduced by forcing `Config::set('livewire.temporary_file_upload.disk', 'public')` locally — the same send failed identically, confirming the mechanism, not just a production quirk.

Fixed in `Contact\Actions\SendMessageAction`, `Channel\Actions\SendChannelMessageAction`, `TaskBoard\Actions\CreateTaskAction`/`UpdateTaskAction` — capture `getClientOriginalName()`/`getMimeType()`/`getSize()` into local variables **before** the `store()`/`storeAs()` call. **Rule: any `storeAttachments()`-style mapper over `TemporaryUploadedFile` objects must read every metadata accessor (`getClientOriginalName`, `getMimeType`, `getSize`, `extension`, etc.) before calling `store()`/`storeAs()`/`storePublicly()` on the same object — never after. This holds regardless of what disk config says today; relying on temp-disk ≠ destination-disk to stay true is exactly the fragile assumption that broke in production.**

## Dynamic file-input array keys MUST be dot-free — `wire:model="form.files.{{ $key }}"` is a dotted path, a dotted key splits it

The THS ticket form generates one file-input slot per "add attachment" click, storing a unique key in `$form->fileInputs` and binding the input with `wire:model="ticket.files.{{ $key }}"` (plus `@error('ticket.files.' . $key)` and a JS clear via `$wire.set('ticket.files.{{ $key }}', null)`). The keys were produced with `uniqid('', true)`, which returns a string **containing a dot** (e.g. `65f2a1b3c4d5e7.89101234`). Livewire parses a `wire:model` expression as a dotted property path, so `ticket.files.65f2a1b3c4d5e7.89101234` is read as the nested path `files → 65f2a1b3c4d5e7 → 89101234`, not the flat array entry `files['65f2a1b3c4d5e7.89101234']`. The uploaded `TemporaryUploadedFile` lands one nesting level deeper than `submitTicket`/`SubmitTicketAction` iterates, so `$form->files` looks empty at submit time and the attachment is silently dropped — the "Submit Ticket Request" button appears to do nothing when a file is attached (the ticket may still create, minus its file). The dot is the entire defect; the same key flows into the `@error` bag name and the `$wire.set` path, so those silently miss too.

Fixed in `Ths\Main` (`addFileInput`/`mount`/`submitTicket`) and `Ths\Actions\SubmitTicketAction` — keys are now `Str::random(13)` (alphanumeric, guaranteed dot-free), and the dead `is_array ? reset($f) : $f` unwrap that existed only to pop the spurious nesting back up was removed (replaced by `collect($files)->filter()->values()->all()` for a clean 0-indexed array). **Rule: any key interpolated into a `wire:model`/`wire:set`/`@error` dotted path — file-input slots, repeater rows, dynamic subforms — must be dot-free and Livewire-path-safe (alphanumeric). Never `uniqid('', true)`; use `Str::random()`. A dot in a key is invisible in the rendered HTML but silently reframes the binding as a nested path, and the symptom (value looks unset server-side, button "doesn't work") gives no error trail.**

## A modal with TWO entry points — navbar `wire:click` + an Alpine `$dispatch` window event — converges on ONE `open(?string $type = null)` (Release Request / support modal)

A single Livewire modal can be triggered from two unrelated surfaces: a navbar tile (direct `wire:click="open"`) and a CTA inside an Alpine-only component that has NO Livewire backing (the release-notes `release.blade.php`, pure `x-data` + `config('releases')`). The proven DOM-event path — NOT a Livewire bus `#[On]`, which does NOT catch Alpine `$dispatch` (verified in `CommandPalette`) — is: the CTA fires `@click="$dispatch('open-release-request', { type: 'recommendation' })"`, and the Livewire component root carries `@open-release-request.window="$wire.open($event.detail?.type)"`. Both paths hit the same `open(?string $type = null)`. **Rule: a second trigger for an existing modal that lives outside Livewire (pure Alpine/Blade) dispatches a window event the Livewire root listens for — never reach for `#[On]` (it won't fire from Alpine `$dispatch`).**

Three hardening rules inside that one method, all required to avoid stale-state and injection bugs: (1) `open()` resets the form AND clears validation FIRST (`$this->form->reset(); $this->resetValidation();`) before setting anything, so re-opening after a failed submit doesn't show old errors/values; (2) the type arg is resolved via `ReleaseRequestType::tryFrom($type ?? '')` with a `?? ReleaseRequestType::Recommendation` fallback — a tampered/unknown event detail (`$event.detail?.type`) can never inject a raw string into `$form->type`, it falls back to the default case; (3) `close()` mirrors the reset (`$this->show = false; $this->form->reset(); $this->resetValidation();`). The release-note CTA additionally closes its own modal first (`@click="open = false; $dispatch(...)"`) so the two teleported overlays never stack.

The type segmented toggle is **enum-`cases()`-driven**, not hand-written buttons: `Main` exposes `#[Computed] function types(): array { return ReleaseRequestType::cases(); }` and the Blade loops `@foreach($this->types as $type)` rendering one `type="button"` (NEVER omit — a bare button inside `wire:submit` double-submits) `wire:click="$set('form.type', '{{ $type->value }}')"` per case, with active state read from **server** state `$form->type === $type->value` (not Alpine `$wire.form.type`). Adding a new `ReleaseRequestType` case is now ONE enum case — it auto-appears in the toggle, auto-validates via `Rule::enum(ReleaseRequestType::class)` in the Form's `rules()` method (NOT a hardcoded `in:` string, which would silently reject the new case), and auto-renders its Farsi label/color/icon in admin via the enum's `HasLabel/HasColor/HasIcon`. **Rule: an extensible single-select UI is a `@foreach` over the enum's `cases()` with `Rule::enum()` validation — never a hardcoded button list + `in:a,b,c` rule, which both have to be hand-edited per new case.** Reference: `Dashboard\ReleaseRequest\Main` + `release-request.blade.php` (navbar trigger + release-note CTA → one modal).

## Response + attachments on user-submitted requests (Release Request)

`ReleaseRequest` gained two admin-only-writable fields — `attachments` (json) and `response` (text, general-purpose — NOT status-specific, see below) — plus a `Rejected` status case, all additive (no migration on existing columns). The user-panel side is submit-only (`Main::submit()` only ever creates; there is no user-facing edit), so it mirrors HALF of the Task attachment pattern (`livewirePattern.md`/`filamentPattern.md` Rule 40): a plain `public array $attachments = []` on the Form, `Main::removeAttachment(int $index)` unsetting+reindexing it, and `SubmitReleaseRequestAction` doing `storeAttachments()` (canonical `{path,name,mime,size}` shape, `$file->store('release_request/attachments', 'public')`) + `validateAttachments()` (`Validator::make` with `max:5` items / `max:4096` KB / fixed `mimes:` list) — there is no `existingAttachments`/`removeExistingAttachment` pair because there's nothing to edit. **Gotcha caught by the test suite, not by inspection:** the Livewire component MUST `use Livewire\WithFileUploads;` for `wire:model` on a `<input type="file">` to work at all — omitting it throws `MissingFileUploadsTraitException` only at runtime (on the first `_startUpload` call), not at mount, so a form that "looks right" and passes every non-upload test still 500s the moment a real file is attached; `Task`'s `Main` already had the trait so this was easy to forget on a fresh component.

`response` is server-decided only — the user panel never lets a user set or clear it, it is pure read-only display — but it is deliberately NOT coupled to the `Rejected` status: an admin can leave a response when resolving/approving a request too (via the always-optional `ReleaseRequestFormPresenter::response()` Textarea on the regular Edit form), not just when rejecting via the dedicated `reject()` Action (whose own `response` field is also optional, not required — a rejection can exist with no note). The history-tab card renders it as a labeled callout gated purely on `@if(filled($item->response))` — status plays NO role in whether the callout renders, only in its color/icon (`error`/`cancel` when `status === Rejected`, `primary`/`forum` otherwise) — matching the admin-panel infolist's equivalent `response()` entry, which is likewise `->visible()`-gated to `filled($record->response)`, not to any status check (Rule 61 in `filamentPattern.md` — this field was originally named `rejection_reason` and gated to `Rejected` only; generalizing it to any status was a deliberate course-correction, not the original design). Attachments already on a request (admin-attached or user-attached) render as plain download links (`asset('storage/'.$attachment['path'])`, `target="_blank"`) in the same history card, unconditionally (not gated by status or by `response`) — a request can carry a proof-of-concept attachment regardless of its resolution. **Rule: an admin-response field on a user-submitted-request module defaults to "optional in every situation, shown to the user purely on `filled()`" — do not coalesce it into "reason for rejection" unless the product genuinely never needs an admin note on any other outcome; reuse the create-only half of the dual-panel attachment pattern when the user can only submit (never edit) the record, and don't forget `WithFileUploads` on the hosting component — that specific omission has no compile-time or mount-time signal.** Reference: `Dashboard\ReleaseRequest\Main`/`Forms\ReleaseRequestForm`/`Actions\SubmitReleaseRequestAction`, `release-request.blade.php` (submit-tab uploader + history-tab response callout + attachment links).

## Release-note sync — every new module/feature gets a `config/releases.php` checkpoint AFTER its pattern doc is updated

`config/releases.php` is the single source of the in-app release notes, rendered by `components/dashboard/modal/release.blade.php` as `collect(config('releases', []))->reverse()` — so the **last** array entry is the **newest** checkpoint (`$loop->first` after reverse gets the newest primary treatment + the `'جدیدترین'` badge). The release-note modal ALSO carries a static CTA card that dispatches `open-release-request { type: 'recommendation' }` to the user-panel suggestion modal — so "suggest a new module" is reachable from inside the release note itself; a new module that wants its own in-release-note trigger mirrors that `@click="open = false; $dispatch('open-release-request', { type: '...' })"` card (placed after the checkpoints `@endforeach`, before the Module Summaries accordion), not a new mechanism.

When a new module or feature ships, the doc-sync order is: (1) update the module's pattern doc(s) first (`livewirePattern.md` / `filamentPattern.md` / the relevant `<topic>Pattern.md`) with the new reusable pattern; (2) THEN append a release-note checkpoint to `config/releases.php` in the proper place. The proper place is always the **end of the array** (so it becomes newest). A checkpoint shape is: `id` (kebab, unique), `version` (increment the β.N series), `badge` => `'جدیدترین'`, `period` (current Jalali month, e.g. `'تیر ۱۴۰۵'`), `icon` + `theme_icon` (Material Symbols names), `color` (a `--md-sys-color-*` token key; newest is forced to `primary` by the renderer anyway), `theme_title` (Farsi theme line), and `items` = a list of `['title' => …, 'desc' => …]` Farsi pairs covering the module + its notable sub-features. **Demotion step: the previously-newest entry is no longer newest — change its `badge` from `'جدیدترین'` to a real category badge (e.g. `'ارتباطات'`, `'پایه'`) before appending the new one, so only ONE entry ever carries `'جدیدترین'`.** Rule: a new module/feature = pattern-doc sync first, then a `config/releases.php` checkpoint appended last with `'جدیدترین'`, and the previous newest re-badged — never edit an old checkpoint in place, never leave two `'جدیدترین'` badges.

**Optional `fixes` array — a checkpoint's SECOND, visually distinct list, added 2026-08-13.** A checkpoint may carry `'fixes' => [['title' => …, 'desc' => …], …]` alongside `items`, same `{title, desc}` shape. `release.blade.php` renders it as its own sub-card ("رفع اشکالات و بهبودهای پایداری" heading, `build_circle` icon, `secondary` color token) directly below the `items` card, inside the same checkpoint — visually separating shipped features from bug/quality fixes without a second checkpoint. Purely additive: `@if(!empty($checkpoint['fixes']))`, so every prior checkpoint (which has no `fixes` key) renders unchanged. Use `items` for user-visible features/capabilities, `fixes` for corrections to something that was already there (validation gaps, stale copy, safeguards, performance/UX polish) — the same `items`-only shape still works fine for a checkpoint with no fixes to report.

**Splitting an oversized checkpoint — same rules as a fresh append, but retroactive.** If a checkpoint accumulates too many unrelated `items` before it ships (judgment call, no hard count), split it into two: keep the first half under the original `id`/`version`, move the rest into a NEW checkpoint appended after it with a new `id`/`version`. Only the new (later) one keeps `'جدیدترین'`; re-badge the original to a real category badge, exactly as the demotion step above. `theme_title`/`theme_icon` on each half should reflect what that half actually contains, not the original combined theme. Reference: β.14 (13 items, "مدارک، بازخورد و تقویم") was split 2026-08-13 into β.14 (7 items, kept theme, re-badged `'مدارک و بازخورد'`) + β.15 (6 original items + 2 new guide items + a `fixes` array, `theme_title` "تسک‌بورد، پیام‌رسان و راهنماها", `'جدیدترین'`) — `ReleasesConfigTest::test_exactly_one_release_carries_the_newest_badge_and_it_is_the_last_entry` is the regression guard.

## Presence status — `PresenceStatus` enum is the single source

The user's presence (onsite/remote/mission/busy/grumpy/angry/leave) is one backed enum: `App\Enums\PresenceStatus`. Every consumer reads from it, so adding a status is **one enum case + filling its `match` arms** — it auto-propagates to the navbar `StatusSwitcher` dropdown, the Status-board filter chips + grid cards, the contact sidebar, and the admin User form `Select` / table `SelectFilter` / `Group`, all of which `@foreach`/`collect()` over `PresenceStatus::cases()` (via the `presenceCases()` helper in `app/Helpers/index.php`) or call the enum's `label/icon/color/hex/heroicon/cardClasses/...` methods. The icon must exist in **both** icon sets the app uses — Material Symbols (user panel, `icon()`) and Heroicons (admin/Filament, `heroicon()`) — verified against `vendor/blade-ui-kit/blade-heroicons/resources/svg/` and the Material Symbols codepoints before picking (e.g. `Leave` = `sunny` + `heroicon-m-sun`; `palm_tree`/`vacation`/`briefcase`/`luggage` don't exist in both). `decor/status.blade.php` renders an ambient CSS layer per `effectType()` via `x-if` templates; a new `effectType` with no matching template simply renders no ambient layer (clean fallback — no JS/edit needed), and `ambient.js` only special-cases `angry`.

The ONE trap: `Tab/Status::stats()` builds the per-status counts the filter chips show. It MUST stay `PresenceStatus::cases()`-driven (`collect(PresenceStatus::cases())->mapWithKeys(fn($s) => [$s->value => $counts[$s->value] ?? 0])`), NOT a hardcoded `['onsite'=>…,'remote'=>…,…]` list — a hardcoded list silently drops any new status from the filter chip counts even though the chip itself (which loops `presenceCases()` and reads `stats[$value] ?? 0`) still appears with a stuck `0`. `users.presence` is a plain string column cast to the enum (no CHECK constraint), so no migration is needed for a new case.

**No presence literal anywhere — every consumer is enum-led.** A presence value string (`'onsite'`/`'busy'`/…) must never be written by hand; reference the enum case instead so a rename or new case can't silently drift. The enum-led sites: `StatusSwitcher` property default + mount fallback use `PresenceStatus::Onsite->value` (enum-case `->value` is a valid PHP 8.1+ constant expression in property defaults); `QuickSettings::setFocusMode` writes `PresenceStatus::Busy`/`PresenceStatus::Onsite` instances to `presence` (Laravel's enum cast accepts the instance on set and serializes `->value` on save — same pattern as `StatusSwitcher::changeStatus`); `User::$attributes` default is `PresenceStatus::Remote->value`; `ModuleAnalytics::usersData()` binds `presence = ?` with `PresenceStatus::Onsite->value` rather than an inline SQL literal (parameterized + enum-led). **Deferred residuals (intentionally left, lower severity):** the `users` migration `->default('remote')` is a raw DB default that cannot reference a PHP enum; the `decor/status.blade.php` `x-if="type === 'angry'/'grumpy'/'busy'/'remote'/'onsite'"` templates and `ambient.js`'s `type === 'angry'` compare the `effectType()` string as bare JS literals (JS can't import the PHP enum — these are the documented PHP↔JS contract); `UserFactory` seeds `randomElement(['remote','office'])` (and `'office'` isn't even a valid case — `tryFrom`→null→Onsite fallback, harmless but stale); test fixtures seed `presence => 'onsite'/'remote'/'busy'` as known values. Rule: any NEW presence logic references `PresenceStatus::<Case>` or `->value`; never introduce a bare presence literal in PHP.

## Widget sizing — fit-first, scroll-as-fallback, never clip

Any maximizable/wide user-panel widget (DMS table, taskboard kanban) must **fit the space it's given and shrink**, using horizontal scroll only as a genuine fallback — never a permanent desktop scrollbar, and never `overflow-hidden` on the same element that should scroll (that clips content unreachably instead of scrolling it). Two traps seen and fixed:

- **`min-w-max` on a table container** forces `max-content` width, so an `overflow-x-auto` parent always shows a scrollbar. Fix: `w-full` container + `w-full min-w-full` table. Correct nesting (mirror `ths/ticket-table.blade.php`): outer card owns `overflow-hidden rounded-2xl border shadow-sm` (clips corners only) → inner wrapper owns `w-full overflow-x-auto` (the scroll layer) → table `w-full min-w-full`. The maximize button is a **sibling of the scroll layer** (pinned, doesn't scroll away), `absolute` at the RTL start corner (`right-2 top-2`; the first `th` reserves clearance with `pr-14`).
- **A hard `md:min-w-[…]` floor on flex columns** (taskboard) defeats `md:flex-1`/`md:w-1/3` distribution: 3×350px+gaps overflows a narrow desktop row and trips the parent `overflow-x-auto`. Fix: relax the **desktop** floor to `md:min-w-0` (this is what clears flexbox's `min-width:auto`/min-content floor so `flex-1` columns share the row) on **both** the wrapper and the column root — relaxing only one still overflows. Keep mobile floors (`min-w-[280px] sm:min-w-[320px]`) for the `snap-x snap-mandatory md:snap-none` carousel, and keep the container's `overflow-x-auto` as the never-clip fallback.

Maximize is orthogonal: `.max-widget` (fixed, `inset:1.5rem`) and `.max-widget-column` (fixed, `width:clamp(60vw,70vw,75vw) !important`) in `dashboard.css` override width/position with `!important`, so `w-full`/`min-w-0` changes never affect the maximized state.

## `profile_details` catalog — `admin_only` keys (unit/section), no migration, user-panel-excluded

`profile_details` is a generic key/value table (`profile_id` + `key` unique, `section` group) driven by one static catalog: `App\Services\ProfileDetailCatalog::definitions()`. Each entry = `['section','label','type','options', …]`. The admin Profile form edits it via a `Repeater::make('details')->relationship()` whose `value_select` resolves options from the catalog. **To add a new admin-set, user-invisible field, register it in the catalog with `'admin_only' => true` and (if its options depend on another field) resolve them dynamically in the repeater's `value_select` closure — no migration, no model column.** Pattern in action: `unit`/`section` (`واحد`/`بخش`) are department-driven (options come from `Department::find($get('../../department_id'))?->unitsOptions()/sectionsOptions()`), admin-only.

The user panel must never see or set these. The catalog exposes paired user-facing variants that **reject `admin_only`** — `userDefinitions()`/`userGrouped()`/`userRules()`/`userAttributes()` — and every user-panel site reads those, not the full `definitions()`/`grouped()`/`rules()`/`attributes()` (which the admin still uses so `unit`/`section` appear in the admin key-picker). The two non-obvious user-panel sites that ALSO had to switch to the user-variants (not just the obvious presenter/form): `Details::mount()` seeds `$form->values` from the catalog keys — must use `array_keys(userDefinitions())`, else admin_only keys leak into Livewire state; and `SaveDetailsAction::getFormattedValues()` iterates the catalog to pick submitted values — must iterate `userDefinitions()`, else a crafted POST (`form.values.unit=…`) persists an admin_only key despite there being no validation rule for it (validation passes silently → the save loop was the only gate). **Rule: when adding an `admin_only` catalog key, grep every consumer of `definitions()`/`keys()`/`grouped()`/`rules()`/`attributes()` and route the user-facing ones to the `user*` variants — the save path and the mount-seed path are the two that get missed.**

**A catalog key with NO `admin_only` flag is automatically both-sided for free** — it appears in the admin `Repeater::make('details')` key picker AND the user-panel `Details` form, no extra wiring, since both already iterate the catalog generically. Used for `display_title` (`عنوان نمایشی`, section `employment`): an optional free-text override that either side (admin HR or the employee) can fill, read via `Profile::getDisplayPositionAttribute()` = `$this->detailsMap()->get('display_title') ?: $this->position_label` — falls back to the real `Position` enum label when empty, never touches `HasProfileHierarchy::RANKS` or any rank/permission logic (display-only). Consumer sites read `$profile->display_position`/`displayPosition` instead of `position_label`/`positionLabel` (Contact header/info, Status board grid, the user's own profile header) — admin-side `ProfileTablePresenter`/`ProfileInfolistPresenter`/`ProfileExporter` deliberately keep reading the raw enum (with its color/icon) since HR needs to see the actual assigned position, not the employee's display override. Any site reading `display_position` must eager-load `profile.details` (same as any `detailsMap()` consumer) — a single-record fetch (e.g. `Contact::activeContact()`) just adds `'profile.details'` to its existing `with()`; a list context (Status board) already carries it since `Status.php` loads `profile.details` for the unrelated `unit`/`section` classifier tags.

## Shared access policy + one embeddable widget — Ths ticket assign/reply/effectiveness, in both panels

When a capability (assign a ticket, reply, set effectiveness) must work identically from the admin Filament panel AND the user-panel Livewire module, do **not** repeat the Suggestion module's mistake: `SuggestionAccessPolicy` (admin-only, static class) and `Suggestion/Detail.php`'s `#[Computed]` gates independently re-derive the *same* `canDecide/canGiveFeedback/canMarkComplete` rules from scratch — two hand-written copies of one rule that can silently drift. The Ths ticket workspace instead uses:

1. **One shared policy class outside any panel namespace** — `App\Support\TicketAccessPolicy` (`canView/canReply/canAssign/canSetEffectiveness/canClose`), composing existing model methods (`Ticket::currentActionRecipient()`, `User::highestRankingInDepartment()`) rather than re-deriving recipient logic. Placing it under `App\Support\` (not `Filament\Resources\ThsResource\Actions\...`) is deliberate — a policy that reads as "the admin panel's" invites exactly the copy-instead-of-call mistake Suggestion made.
2. **One embeddable Livewire component mounted in both panels** — `Ths\Workspace` (reply thread + assign/effectiveness controls), embedded into the admin `ThsResource` form via `Filament\Schemas\Components\Livewire::make(Workspace::class, fn(?Ticket $record) => ['ticketId' => $record?->id ?? 0])` (guard `->visible(fn(?Ticket $record) => $record !== null)` on the wrapping Section — no record on the Create page), and mounted directly in the user-panel ticket modal via `<livewire:dashboard.ths.workspace :ticket-id="..." :key="'ticket-workspace-'.$id" />`. Same UI, same policy calls, one implementation — not a per-panel reimplementation.

**Trap: a Livewire component nested inside another Livewire component (Filament's page) must always render a stable single root element — never wrap the entire template in a top-level `@if`.** `Workspace`'s blade originally opened with `@if($this->ticket) <div>...</div> @endif`; if the guarded condition is ever falsy during a render pass, the component emits zero HTML, and Livewire's nested-component tracker (`SupportNestingComponents`) extracts the child's tag name via `preg_match('/<([a-zA-Z0-9\-]*)/', $html, ...)` to remember for the next partial re-render — no match (or a comment/whitespace-led match) stores an invalid/empty tag, and the *next* Filament form interaction (e.g. a `->live()` field like `status`) throws `Invalid Livewire child tag name` trying to reuse it. Fix: always render the outer `<div>`, move the `@if` **inside** it to guard only the content.

**Reply-thread model — shared trait, not a per-model system.** One polymorphic table (`replies`: `repliable_type`/`repliable_id`, `user_id`, `body`, `files` json) + `App\Models\Traits\HasReplies` (`replies()` morphMany, `addReply()`, `latestReply()`, `otherReplyParticipant(array $participantIds)`), mixed into both `Ticket` and `Task` — neither model gets its own bespoke thread storage. `otherReplyParticipant()` is the one piece of cross-module-shared logic (given a model's two participant-id columns, returns whichever one didn't author the latest reply); each nudge class still owns which two columns count as "the participants" for its model.

**File-attachment metadata order — capture before `storeAs()`, every time.** `HasReplies::storeReplyFiles()` reads `getClientOriginalName()/getMimeType()/getSize()` **before** calling `$file->storeAs(...)`, matching the established `SendChannelMessageAction::storeAttachments()` idiom — not the Filament `saveUploadedFileUsing` order (which stores first, reads metadata after, safe only for that specific `TemporaryUploadedFile` callback shape). Reading metadata after `storeAs()` on a plain array-bound Livewire upload risks reading from a file the disk driver has already moved.

**Notification triggers fold into the existing per-module nudge class — never a sibling `*ReplyNudge` class.** A `Reply::created` event resolves to its parent (`Ticket`/`Task`) via the same `SuggestionNudge`-precedent `subject` closure (`fn(Reply $r) => $r->repliable_type === Ticket::class ? $r->repliable : null`), registered as a **second trigger inside `ThsNudge`/`TaskNudge`** sharing the same key — not a new `ths-controller:reply-nudge` key. `for()`/`show()`/`title()`/`body()` branch on whether the recipient *is* the lifecycle recipient (`currentActionRecipient()`/owner — existing copy, existing rule, untouched) versus a reply participant who isn't (new "پاسخ جدید" copy); the reply's own author is excluded from the reply-branch entirely (`$latestReply->user_id === $user->id` short-circuits to the lifecycle-only check) so nobody self-notifies on their own message. `ThsBadge`/task badges stay untouched — a badge means "unclosed action required," a reply is conversational, so it never lights the dot.

**Effectiveness required to close — enforced once, in a model `saving` hook, not duplicated per panel.** `Ticket::booted()`'s `saving` closure throws `TicketError::EffectivenessRequired->throw()` (this project's enum-`throw()` domain-error convention, see `ReservationError`) only when `isDirty('status') && isClosingStatus($status) && blank($effectiveness)` — the `isDirty('status')` guard is what keeps this backward-compatible: an already-closed legacy ticket (closed before this feature existed, no effectiveness) can still be freely edited as long as `status` itself isn't the field being changed. Both panels share one `Ticket::isClosingStatus($status)` predicate for early inline validation (Filament: `->required(fn (Get $get) => Ticket::isClosingStatus($get('status')))`; user panel: same check before calling the close action) — the model hook is the actual backstop either way, so a future third caller can't bypass it.

**Auto-generated closing summary, not a manual field.** `action_result` stays in the schema/table/export for backward compatibility, but is now system-composed from the full reply thread at the moment of closing (`Ticket::composeActionResultFromReplies()`, called from the same `saving` hook) — the Filament field becomes `->disabled()->dehydrated(false)` (read-only display), nobody types into it directly anymore.

**"Public Support" auto-hide — derive the condition from data, no manual switch.** `Department::anyHasCustomTicketOptions()` (cached, reusing the existing `scopeExcludingEmptyTicketOptions()`) gates a single `@unless(...)` around the `N/A` option in `ths/create.blade.php` — hides the moment *any* department configures its own ticket types, no admin setting to maintain, no code change per department.

**Ticket → TaskBoard linked-task mirror — one nullable FK, no two-way sync.** `AssignTicketAction::syncLinkedTask()` creates (or updates, on reassignment) exactly one `Task` per ticket via a nullable `tasks.ticket_id` FK, the moment a ticket is assigned: `user_id` = the ticket's `requester_id`, `assigned_to` = the new assignee. This rides TaskBoard's *existing* tab scoping unmodified — the requester sees it under "محول شده" (creator with an assignee ≠ self), the assignee sees it under "وظایف من" (`assigned_to = me`) — no new tab, no new query. `title`/`description` are stamped once at creation (`description` includes the formatted ticket ID plus a truncated snippet of the ticket's own `description`, so same-day tickets to the same assignee stay visually distinguishable — a generic title alone isn't enough). Deliberately one-directional and decoupled to avoid Suggestion-style rewiring: moving the task's board column is personal tracking only (never written back to the ticket), and reassigning/deleting/editing the linked task from the TaskBoard side is blocked (`AssignTaskAction`/`BulkAssignTasksAction`/`UndoTaskAssignmentAction`/`UpdateTaskAction`/`DeleteTaskAction`/`BulkDeleteTasksAction` all gate on `$task->ticket_id`) so the mirror can never drift from — or unilaterally vanish out from under — the real assignee recorded on the ticket — the only two things you can still do to a linked task are drag it between board columns and open a "مشاهده و پاسخ در تیکت" deep-link (`route('ths', ['open' => $ticket_id])`, the same `?open=` convention `FocusOnRecord`/global search already use) that jumps straight into the ticket's own reply thread rather than growing a second, competing conversation UI inside TaskBoard.

**Both panels sync via two Action entrypoints with distinct auth — `syncLinkedTask()` is private.** User-panel `Ths\Workspace::assign()` → `execute()`, which gates on `TicketAccessPolicy::canAssign` (head of the ticket's target department) and validates the assignee belongs to that department. Admin Filament `ThsResource` save → `EditTicket::afterSave` / `CreateTicket::afterCreate` → `syncForAdmin()` (gated by Filament admin-panel access; the `assignedTo` Select already constrains its options to the target department, so the membership check is redundant there). The admin hook fires only when `assigned_to` is dirty (edit) or filled (create), so editing other fields never spuriously rewrites the task. `syncForAdmin` also mirrors **unassign**: clearing `assigned_to` in admin nulls the linked task's `assigned_to` (`tasks.assigned_to` is nullable), and creating a ticket with no assignee creates no task — a requested-but-unassigned ticket has no taskboard row by design. Without this admin hook, tickets assigned only from the admin panel never reached the TaskBoard — the original bug; the user-panel `execute()` path was always wired, the admin save path simply wasn't.

## Shared Service across panels — HR Analytics

When the exact same data/analysis must render in **both** the admin Filament panel and the user-panel Livewire module, don't port a Filament widget wholesale or duplicate its query logic — extract the computation into a plain, framework-agnostic Service both sides call.

**Why not embed the Filament widget directly.** A `Filament\Widgets\ChartWidget` (e.g. `Hr*Chart`) leans on Filament's Schema/Actions system for its filter UI (`filtersSchema()`, `Action`) and expects a Filament panel context (assets, current-panel resolution) — rendering it raw inside the user-panel's own Blade/Alpine layout risks breaking or visually clashing with that panel's bespoke Material Design 3 styling. The DRY-correct split is: **Service owns the data, each panel owns its own thin presentation.**

Reference: `App\Services\HrAnalyticsService` — 17 public `getHr{A..Q}Data()` methods (Chart.js-shaped `['datasets','labels']`), plus the private helpers they need (`positionAxis`/`positionMap`/`bucketSeries`, and the `DepartmentAxis` trait — already framework-agnostic, just `use`d, not duplicated). Two consumers:
1. **Admin** — the 4 `Hr*Chart` widgets (see `app/Filament/Widgets/widgetsPattern.md`), each `get{Key}Data()` body reduced to `return app(HrAnalyticsService::class)->getHrXData();`, keeping their own `#[Computed(seconds: 300, cache: true)]` boundary (caching stays per-consumer, not inside the Service).
2. **User panel** — `App\Livewire\Dashboard\Analytics\Main`, a single `#[Computed(seconds: 300, cache: true)] chartData()` method calling all 17 Service methods once and returning them keyed by module id (`['hr_a' => [...], ...]`) — one cache entry, not 17. `App\Livewire\Dashboard\Analytics\Presentation\AnalyticsPresenter` independently ports each widget's `filtersSchema()` labels / `getDescription()` / `getType()` / `getOptions()` logic into plain PHP methods (`categories()`, `description()`, `chartType()`, `chartOptions()`, `chartConfig()`) — this metadata is duplicated on purpose (it's UI config, not data), with one deliberate deviation: the chart font is `'Yekan, system-ui'` (matching this panel's existing `energyChart.js` convention) instead of the admin widgets' `'Yekan Bakh, Yekan, Tahoma, sans-serif'`.

**Client-side-only switching, one Livewire load.** All 17 datasets are cheap aggregate queries, so `Main` loads them ALL once (one Computed, one cache entry) and passes the full payload to Alpine (`resources/js/components/alpine/data/analyticsChart.js`, modeled on `energyChart.js`'s dynamic `import('../../../core/chart.js')` + `getCssVar()` theming pattern). Category and module switching afterward is pure Alpine state (`switchCategory`/`switchModule`) — no further Livewire round-trips. `switchModule` destroys the category's existing Chart.js instance before creating a new one on the same `<canvas>` (type/data can change per module; Chart.js doesn't support in-place type swaps).

**`resources/js/core/chart.js` is Chart.js's UMD build (`chart.umd.js`), not an ES module — never destructure `{ Chart }` off its dynamic import.** `!function(t,e){"object"==typeof exports&&...}(...)` has zero `export` statements; in a real browser (native ESM `import()`, no bundler CJS interop applied to this plain project-local file) its only effect is a runtime side-effect assignment to `window.Chart`. So `const { Chart } = await import('../../../core/chart.js')` always yields `Chart === undefined` — confirmed directly (`node -e "import(...).then(m => console.log(Object.keys(m)))"` returns `[]`), not assumed. The bug is easy to miss because failure modes differ by call site: `analyticsChart.js` had a defensive `if (!el || !this.Chart) return;` guard, so the destructured `undefined` just made every chart silently never render, no console error at all; `energyChart.js` had no such guard, so it would throw `Chart is not a constructor` the moment a chart tries to draw. Both were fixed the same way: `await import('../../../core/chart.js');` for the side-effect only, then read `window.Chart` directly (verified: `window.Chart` is a real constructor once the import has executed in a `window`-having environment) — never `const { Chart } = await import(...)`. Any future chart component reusing `core/chart.js` must follow this same pattern.

**Full-page route component still gets the `$isLazy` treatment — via `#[Lazy]`, not skipped.** Filament's `Hr*Chart` widgets all declare `$isLazy = true`; the equivalent for a Livewire component mounted directly via `Route::get('/analytics', Analytics::class)` (not a nested `<livewire:x />` tag) is the `#[Livewire\Attributes\Lazy]` class attribute + a `placeholder()` method. Both `render()` and `placeholder()` must independently chain `->extends('layouts.app')->section('content')` — Livewire's full-page-component support hooks both the `render` and `render.placeholder` events the same way, so the placeholder is a genuine skeleton response on the initial GET, not a blank page.

**View path must stay flat at the panel-root level, matching every sibling module.** `resources/views/livewire/dashboard/<module>.blade.php` is the root view (`dms.blade.php`, `authority.blade.php`, `energy.blade.php`) — a `<module>/` subfolder holds only partials/sub-views (`energy/chart.blade.php`, `analytics/placeholder.blade.php`). A first pass at the Analytics module nested its main view at `analytics/main.blade.php` instead of the required flat `analytics.blade.php` — caught and fixed post-build; check this convention explicitly for any new standalone module rather than assuming a `main.blade.php`/`index.blade.php` filename is fine.

## Rendering text/HTML in Blade — `superClean()` vs `Str::sanitizeHtml()` vs a plain shape-normalize guard

Three distinct tools exist for three distinct problems. Picking the wrong one either shows broken tag-soup, opens a stored-XSS hole, or leaves a crash risk in place.

- **`superClean(?string $text, int $limit = 100, bool $nl2br = false)`** (`app/Helpers/index.php`) — for **excerpts/previews of anything that might contain HTML**, rich or plain. It `strip_tags()`s FIRST, then truncates, so it never cuts mid-tag and never needs escaping (output is plain text, safe inside `{{ }}` or string concatenation). Use it whenever you need a short, tag-free snippet: card/grid excerpts (`posts/grid.blade.php`, `reports/list.blade.php`), notification titles/bodies (`PostNudge::title()`, `UnreadNotifications::genericAggregateRow()`), anywhere HTML would land in a non-HTML context (attribute, notification bell text, aggregate string). Never use it for the *full* display of a RichEditor field — it discards all formatting. Caveat: with `nl2br=false` (the default) it does NOT escape its output — it only `strip_tags()`s and decodes entities, so a source string containing an HTML-entity-encoded tag (e.g. an admin literally typing `&lt;script&gt;` as text) can decode back to a raw, unescaped `<script>` in the return value. Safe to use this way only when the consumer itself re-sanitizes before final render (e.g. Filament's `Notification` class does, which is why `PostNudge::title()`/`UnreadNotifications::genericAggregateRow()` can pass it straight through) — never treat `superClean(nl2br: false)` alone as a full sanitizer against untrusted input outside such a context.
- **`Str::sanitizeHtml($html)` / `Str::of($html)->sanitizeHtml()`** (Filament-registered macro, `vendor/filament/support/src/SupportServiceProvider.php`, backed by Symfony's `HtmlSanitizer` with `allowSafeElements()` + explicit allow-listed `class`/`data-color`/`style`) — for the **full, formatted render of a column that a Filament `RichEditor` writes to**, rendered with `{!! !!}`. This is mandatory (not optional) whenever the SAME column can also be written as plain text by an ordinary user-facing form (dual-authored — e.g. `Suggestion.description` via `SuggestionForm::$descriptionSelf`, `Comment.content` via the feed comment composer) — never blindly flip `{{ }}` to `{!! !!}` on a dual-authored column, that's a stored-XSS hole (a user typing `<script>` gets it rendered unescaped to every viewer). Sanitize-then-render is the only safe way to preserve admin rich-formatting (including Tiptap's `<span data-color>` color marks) while still neutralizing anything a plain-text author could have typed. Reference: `suggestion/detail.blade.php` (description), `renderComment()` in `app/Helpers/index.php` (feed comments) — note `Str::limit()` truncates BEFORE `sanitizeHtml()` runs, which is safe because the sanitizer's lenient HTML5 parser self-heals a mid-tag cut rather than leaving dangerous dangling markup. A column that is **admin-only** authored (e.g. `Post.body`, `Onboarding.*`, `Report.description`, `FAQ.answer`) doesn't have the dual-authorship risk and can render with a plain `{!! $value !!}` — no sanitize call needed, since only Filament's own RichEditor ever writes to it.
- **A bare `is_array($v) ? implode(...) : $v` shape-normalize guard** — for **array/json-cast columns that are never HTML**, just a scalar-map shape that a Filament `Repeater`'s custom `saveRelationshipsUsing()`/`afterStateHydrated()`/`dehydrateStateUsing()` flattens or unflattens (e.g. `Profile.about_me`, `Feed.poll_options`). These columns have no markup and no XSS surface — the risk is a **shape mismatch** (a nested array landing where a scalar is expected), which crashes a typed Livewire `Form` property (`data_set()` throws `TypeError` on a typed `?string`) or a hard-typed helper (`superClean(?string $text, ...)`) rather than leaking anything. Guard at the read boundary by coercing (not silently dropping, if the array's index alignment feeds vote counts or similar — see `Feed::normalizePollChoices()`) any non-scalar value to a joined string before it reaches a scalar-typed consumer. This is a distinct bug class from the two above — no sanitizer needed, no HTML involved, just defensive type coercion. Reference: `About::mount()` + `ProfileFormPresenter::aboutMe()` (`about_me`), `Feed::extractPollSettings()`/`normalizePollChoices()` (`poll_options`).

**Rule of thumb:** HTML column, single author (admin only) → plain `{!! !!}`. HTML column, dual author (admin RichEditor + user plain-text form) → `Str::sanitizeHtml()` then `{!! !!}`. Any column (HTML or not) shown as a short excerpt/snippet/notification string → `superClean()`. Array/json column feeding a typed scalar consumer → a shape-normalize guard at the boundary, unrelated to sanitization.

## Page-level primary tab selector → always `#[Url(as: 'tab')]` (consistency rule)

Any full-page routed Livewire component whose primary UI is the shared `x-ui.buttons.tab-selector` component must bind its `$activeTab` (or equivalent) property with `#[Livewire\Attributes\Url(as: 'tab')]`, using that exact key name everywhere — never a module-specific alias. This makes every module's tab state shareable, bookmarkable, and refresh-safe, and keeps `?tab=` a single predictable convention across the whole user panel rather than N different ad-hoc ones.

Currently wired: `Dashboard\Tabs` (home/post/feed/calendar/status/gallery/reports/links/faqs), `Profile\Main`, `Reservation\Main`, `Dms\Main`, `Authority\Main`, `Ths\Main`, `TaskBoard\Main`, `Energy\Main`. All eight were audited together (2026-08-03) — before that, only 4 had it and 4 didn't, for no functional reason; the other four were missing it by omission, not by design, and adding it required no other code changes since each already reads `$this->activeTab` reactively (`when($this->activeTab === ..., ...)` in query builders, `#[Computed]` methods, or Alpine `x-show="activeTab==='x'"` via `@entangle(...).live`) rather than only setting derived state inside `switchTab()` — so a value arriving via URL hydration (which runs before `mount()`) behaves identically to a value arriving via a click.

**Exception — never `#[Url]`-bind a component that isn't a routed page.** `ReleaseRequest\Main` deliberately does NOT get this treatment: it has no dedicated route (no `Route::get(...)` targets it) — it's a modal (`components/dashboard/modal/release.blade.php`) embedded in the navbar (`components/dashboard/navbars/top.blade.php`) and rendered on every page. Binding its `$activeTab` to `?tab=` would write that query param onto whatever unrelated page the user currently has open the moment the modal renders, polluting URLs app-wide. Before adding `#[Url]` to any tab property, confirm the component is mounted via its own `Route::get()` entry, not included globally in a layout/navbar.

**Don't extend this to secondary/nested tab-like state.** `Ths\Main::$modalTab` (its ticket-detail modal's request/response toggle, also driven by the same `x-ui.buttons.tab-selector` component via an overloaded `switchTab()`) and `Reservation\Main`'s history sub-tabs are intentionally NOT URL-bound — they're transient, modal/sub-view-local state, not the page's primary navigable view. Only the one property that represents "which top-level page section is the user looking at" qualifies.

## `FocusOnRecord` / global search deep-links — the `data-rf` contract and why it fails silently

A search result (from `ContentService`, or a nudge notification's `route(..., ['open' => $id])`) navigates to `?open={id}` and relies on `App\Traits\FocusOnRecord` to actually land the user ON the record, not just on the page. Three parts, all required, verified end-to-end 2026-08-03 across all 17 focus-capable modules:

1. **`#[Url] public ?int $open`** (the trait) is hydrated from the querystring *before* Livewire calls `mount{TraitName}()` — `mountFocusOnRecord()` — **automatically**, for every component using the trait. This is Livewire's own trait-lifecycle-hook convention (any method literally named `mount{TraitBaseName}()`/`boot{TraitBaseName}()`/etc. auto-fires); no explicit call in the component's own `mount()` is needed or present anywhere in this codebase (confirmed on `Ads\Main`, which has no `mount()` at all and still focuses correctly).
2. **The query/listing method must not silently exclude the focused record.** Pagination/filters/limits are for the *normal* browsing view only — every working module bypasses them when `$open` is set, either via a `->when($this->open, fn($q) => $q->whereKey($this->open), fn($q) => ...normal filters...)` pin (`Dms`, `Faqs`, `Authority`) or a `mount()`-time short-circuit that replaces the loaded-ids array with just `[$this->open]` after an explicit visibility check (`Feeds`, `Gallery`: `if ($this->open && $this->getBaseQuery()->whereKey($this->open)->exists()) { $this->photoIds = [$this->open]; ... }`). `Suggestion`/`TaskBoard` take a third, equally valid path — their detail pane/modal (`selected()`/`editTask()`) fetches the record directly by ID, completely independent of the paginated list, so the content always shows even though the list-row highlight (step 3) only fires if that row happens to be in the currently-loaded page.
3. **`recordFocusType()` (defaults to `strtolower(class_basename(static::class))`, override when the class name doesn't match) dispatches a `record-focus` Livewire event**, caught by `resources/js/core/record-focus.js`, which looks for `[data-rf="{type}-{id}"]` in the DOM and scrolls+flashes it (`.record-focus-flash`, retries for ~3s to tolerate lazy/async rendering, then **gives up with zero error, zero console warning** — the URL is already correct, the page already navigated, so nothing *looks* broken, it just silently doesn't scroll/highlight). This is the step that's invisible in casual testing and was found missing in 7 modules on first audit (Dms, Suggestion, TaskBoard, Feeds, Calendar, Faqs, Gallery all had the trait + working step-2 pinning, but their list/card blade template had no `data-rf` attribute at all) — fixed by adding `data-rf="{recordFocusType()}-{id}"` to each module's row/card root element, matching the 10 modules that already had it correctly (Posts, Reports, Links, Credentials, Ads, Authority, Reservation, Contact, Channel, Ths).

**The search Resource's `$type` property (e.g. `PostResource::$type = 'post'`) is cosmetic — it labels the search-result row's icon/group, and is NOT what `record-focus.js` matches against.** The actual wire is component-`recordFocusType()` ↔ blade `data-rf` prefix; these two only need to agree with *each other*, not with any search Resource. `Tab\Posts` (search type `'post'`) still correctly dispatches/matches on `'posts'` (its own default class-derived type) — no bug, just two independent naming schemes that happen to collide in most modules but don't have to.

**Nested-record deep-links (a message inside a conversation/channel) layer a second query param, `focus_msg`, read separately via `request()->query('focus_msg')` inside `focusRecord()`** (mount-only — a later AJAX update won't re-read it) — `ContactMessage`/`ChannelMessage` search results carry both `?open={conversationOrChannelId}&focus_msg={messageId}`. The nested `focusMessage($id)` method must itself bypass the message list's normal load-limit when the target is older than what's currently loaded — both `Contact\Main` and `Channel\Main` do this via a `focusAnchorId`/`focusOlder` pair: when the target is beyond the initial window, `messages()` fetches a fixed window *around* the anchor (`newer: id >= anchor take 6`, `older: id < anchor take focusOlder+1`) instead of just the latest N — verified empirically by seeding 20 messages and focusing the oldest one (which is outside any default 10-message window) in both modules.

**Nested focus double-dispatch (found 2026-08-03, after the "verified end-to-end" pass above — `Contact`/`Channel` only):** `mountFocusOnRecord()` used to *unconditionally* dispatch its own `record-focus` (parent-row type, e.g. `people-{id}`/`channel-{id}`) even when `focusRecord()` had already dispatched a nested one (`message`/`channel-message`) via `focusMessage()`. `record-focus.js`'s global flash-cleanup (`document.querySelectorAll('.record-focus-flash').forEach(remove)`) then wiped the message's flash a beat later to scroll+flash the sidebar row instead — the double jump/flash behind the "record not clear on landing" complaint. Fixed by having `focusRecord()` return `bool` (`true` = "I already dispatched, skip the trait's own dispatch") in `Contact\Main`/`Channel\Main` only; every other module's `focusRecord(): void` still casts to `false` and gets the trait's unconditional dispatch exactly as before — no behavior change outside the two nested-message modules.

**`channel.js`'s local `scrollToMessage()` (in-conversation message-search click) drifted from the `contact.js`/`record-focus.js` reference pattern:** it skipped the global `.record-focus-flash` cleanup sweep (so a previous jump's flash lingered on an old message) and cleared the class via an `animationend` listener — dead code, since `.record-focus-flash` (`dashboard.css`) only defines a `transition`, not a keyframe `animation`, so that event never fires. Aligned with `contact.js`: global sweep + `scrollIntoView` + add the class, no animationend listener.

**`el.style.animation = 'none'` in all three flash call sites is required, not dead code — verified by removing it and reproducing the regression.** Every message row also carries `bubble-enter` (`animation: bubbleIn 0.25s … both`, `dashboard.css`) with a per-row `style="animation-delay: {{ $msg['animation_delay'] }}s"` stagger. `both` fill-mode applies the keyframe's `0%` state (`opacity: 0`) *backwards* for the entire duration of that delay — so a row further down the list (larger delay) sits invisible until its own delay elapses. Setting `el.style.animation = 'none'` on the jumped-to row removes the animation outright, which drops it back to its un-animated computed style (fully visible, normal position) immediately, regardless of where it was in its delay/keyframe cycle. Without it, `scrollToRecord`/`scrollToMessage` can scroll a row into view while it's still sitting in its pre-delay invisible state — reproduced as "scroll happens but the record isn't visible." Keep this line in all three call sites (`record-focus.js`, `contact.js`, `channel.js`).

**Found via this same audit: an unresolved git merge-conflict block (`<<<<<<< Updated upstream` / `=======` / `>>>>>>> Stashed changes`) had been sitting live in `channel/messages.blade.php`**, undetected because it only broke Blade's PHP compilation of the `@class([...])` array + the delete-button `@if` inside a narrow branch that most manual testing never reaches (the focused/anchored older-message render path specifically — normal recent-message viewing recompiles fine since the conflict block still happens to be syntactically-adjacent valid-looking PHP most of the time... in this case it 500'd outright once actually hit). Resolved in favor of "Updated upstream" for both hunks, confirmed correct two ways: (1) the sibling `contact/messages.blade.php` — no conflict, never touched — independently has the exact same `openActionsId` binding and `$this->lastMessageId` comparison; (2) `channelPattern.md` §20 documents `openActionsId` (mobile tap-to-toggle toolbar) as a deliberate, already-shipped feature in the exact shape kept, and `Channel\Main` has zero occurrences of `is_last` (the discarded side's field) anywhere — that side would have silently hidden the delete button for every message, forever. **Rule: `grep -rn "^<<<<<<< \|^=======$\|^>>>>>>> "` across the tree is worth running after any rebase/stash/merge — a leftover marker inside a rarely-exercised branch compiles fine for the common path and only surfaces as a 500 down the narrow one, exactly the kind of thing that hides for weeks.**

## Testing `@island` content — `Livewire::test()->call(...)->assertSeeHtml()` is unreliable; render the shared partial directly

Extending the `@island` rules above with a concrete testing gotcha hit while adding coverage for the Fancybox attachment lightbox (`messaging/message-attachments.blade.php`, included inside both Contact's and Channel's `messages` island): a plain `Livewire::actingAs($user)->test(Main::class)->call('selectContact', $id)->assertSeeHtml(...)` returned an EMPTY `mode:skip` fragment for the island — the call reaches the method and the DB state is correct, but the island's HTML never lands in `$this->html()`, so the assertion fails even though the feature works. This matches Rule 376's mechanism (a non-`$island()`-scoped call carries no island metadata → server treats it as unscoped → `@island` emits a skip fragment) — a test-harness `->call('methodName', ...)` is exactly that unscoped case, same as an Alpine `x-on:click="$wire.method()"` would be. **Don't fight this**: for a Blade partial rendered inside an island, test the partial in isolation — `view('livewire.dashboard.messaging.message-attachments', ['msg' => [...]])->render()` + `assertStringContainsString(...)` — decoupled from island timing/scoping entirely, faster, and it's testing the actual thing that changed. Reserve full-component Livewire tests (as the rest of `ContactTest`/`ChannelTest` already do) for asserting the underlying PHP state/computed data (`$component->instance()->messages()`), never for asserting island-rendered HTML fragments. Reference: `MessagingTest::test_image_attachment_partial_renders_fancybox_grouped_by_message`.

**Hand-written links to a tab MUST use the `#[Url]` alias, never the raw PHP property name.** `#[Url(as: 'tab')]` on `public string $activeTab` means Livewire only ever hydrates from `?tab=` — a hardcoded `href="?activeTab=info"` or `url('/profile?activeTab=info')` is a silent no-op, not an error: the link still resolves, the page still loads, it just never selects the intended tab, and this masks itself completely whenever the target tab happens to equal the property's own default value (exactly why it went unnoticed here — `info` is `Profile\Main`'s default). Found and fixed two live instances doing this (2026-08-03): `resources/views/livewire/dashboard/profile/header.blade.php` (profile-completion nudge) and `resources/views/components/dashboard/navbars/top/account.blade.php` (navbar account dropdown) — both wrote `?activeTab=info` instead of `?tab=info`. Regression-guarded in `tests/Feature/Livewire/Dashboard/ProfileTest.php::test_profile_header_completion_link_uses_tab_query_key_not_active_tab` and `NavbarTest.php::test_account_dropdown_profile_link_uses_tab_query_key_not_active_tab`. Any new hardcoded `href`/`url()` targeting a `#[Url(as: 'tab')]`-bound page must use `tab=`, never the bare property name — `resources/js/components/alpine/data/menu.js`'s nav links already get this right and are the reference to copy.

## TaskBoard ambient urgency — one `--urgency` scalar fuses deadline proximity + idle age, pure CSS rail

The TaskBoard card surfaces two neglected-work signals as ONE ambient marker instead of two widgets. A single `urgency_state` accessor on `Task` (appended via `$appends`, so it rides every `toArray()` like the other formatted labels) returns `['score'=>0..1, 'kind'=>'overdue'|'due'|'idle'|null, 'label'=>string|null]`. `kind`/`label` are the discrete human text; `score` is a continuous scalar the card emits as an inline `style="--urgency:{{score}}"` on the card root. The `::before` rail in `dashboard.css` is the **single colored signal**: `background: color-mix(in srgb, var(--md-sys-color-primary) calc((1 - var(--urgency, 0)) * 100%), var(--md-sys-color-error))` — a theme-anchored **primary → error** ramp, with a glow that scales with urgency (`box-shadow: 0 0 calc(var(--urgency, 0) * 14px) color-mix(in srgb, var(--md-sys-color-error) calc(var(--urgency, 0) * 55%), transparent)`). This ramp was chosen over a `--tool-gold-*` warning hue after checking the theme set (Jade/Magneta/Ember/Obsidian): `--tool-gold-color` is a fixed gold family that goes muddy on Ember's orange `primary-container` and foreign on Magneta's pink, whereas `primary` is each theme's own anchor and `error` is the universal MD3 danger every theme tunes to harmonize with its primary — so the ramp escalates within the theme's own family in every theme (Jade green→red, Ember orange→red, etc.). `--tool-gold-*` stays reserved for its intended sparse analytics/premium/highlight use, not a per-card kanban signal. The pills stay **neutral** (`--md-sys-color-surface-container-highest`/`on-surface-variant`) so the rail is the only colored element — the `hourglass_top` "چند روز بی‌تغیر" pill and the deadline badge carry the *text* meaning, the rail carries the *color* urgency. Deadline proximity: overdue → score 1.0 / kind `overdue` / label `n روز تأخیر`; ≤3 days → 0.7 / `due` / `امروز`·`فردا`·`n روز دیگر`, and the existing deadline badge swaps its date text for this relative label via `in_array($urgency['kind'],['overdue','due'],true)` (overdue keeps the pre-existing `--md-sys-color-error-container`/`on-error-container` badge bg). Idle age (the kanban-rot signal nobody else surfaces): `updated_at` ≥7d → 0.45 / `idle` / `چند روز بی‌تغیر`, ≥3d → 0.22 / `idle`, rendered as a separate `hourglass_top` micro-pill in the badge row (the row guard is widened `|| $urgency['kind']==='idle'`). `overdue` wins over `idle` (max score; `kind ??=`/`label ??=` preserve the deadline verdict). `done`/`pending` short-circuit to a zero state so the done column and the pending column's own error-pulse stay clean — never double-signaling. NOT cached (`now()`-relative, unlike the formatted-label accessors which use `shouldCache()`). Zero new queries: `updated_at` was added to `TaskBoard\Main::$columnsToSelect` (the only query-side change) so the idle calc has the timestamp; everything else is local-column math on a row already fetched. No migration, no new state, no nudge/bell entry — pure presentation of `updated_at`+`deadline`, matching the no-nudge-badge preference. Tests: `tests/Feature/Models/TaskModelTest.php` (11 accessor cases incl. done/pending suppression + overdue-wins-over-idle) and `tests/Feature/Livewire/Dashboard/TaskBoardTest.php` (3 Livewire cases proving `urgency_state` flows through `loadTasks`→`toArray`, incl. the `updated_at`-projected regression guard) — they assert `kind`/`label` only, so the rail/pill token choice is free to evolve without touching tests. Reference: `Task::urgencyState()`, `card.blade.php`, `dashboard.css` `.taskboard-card--urgent::before`.

## TaskBoard archive — a `archived_at` column + model `updating` invariant, not a status enum case or SoftDeletes

The done column lets a user archive a finished task (hide it from the active done list) and unarchive it later — a "put away" gesture distinct from both the 45-day done-window (`showAllDone`) and soft-delete. It is a single nullable `archived_at` timestamp on `tasks` (nullable + indexed, defined in the `create_tasks_table` migration), NOT a new `TaskStatus::Archived` enum case and NOT a second SoftDeletes-style tombstone. Reasons: (1) `TaskStatus` is the kanban column axis — adding `archived` would either invent a hidden 5th column or require every status-comparison site to exclude it; the existing `test_update_task_status_with_invalid_status_is_ignored` / `test_bulk_move_status_with_invalid_status_leaves_tasks_unchanged` regression tests pin `'archived'` as a *rejected* status string, so an enum case of that name would break them. (2) SoftDeletes is already used for real deletion; repurposing a second delete-timestamp for "archive" would conflate two lifecycles and fight `Prunable`/`forceDeleting`. A plain nullable column keeps archive orthogonal to both. **Invariant: `archived_at !== null ⇒ status === 'done'`.** Enforced by a `static::updating()` hook in `Task::booted()` (the shared-source lever — covers every `$task->update(...)` path incl. admin form save, which the Action classes can't see): if `status` is dirty, leaving `done`, and `archived_at` is set, it nulls `archived_at` in the same UPDATE. So reopening an archived done task (drag back to in-progress, edit-status, bulk-move out of done) auto-unarchives — one hook, no per-call-site clearing. The one bypass is `BulkMoveTasksAction`'s `Task::whereIn(...)->update(...)` (bulk query updates skip model events), so it explicitly sets `archived_at => null` in the payload when `$status !== TaskStatus::Done->value` (enum-backed compare, since that Action already imports `TaskStatus` for `tryFrom` — the only place the enum is used for this; the Model/Action layers keep the `'done'` literal like `urgencyState()` does, because importing a Filament-resource enum into the core Model would be a worse layering smell). `UpdateTaskStatusAction` needs NO change — the model hook covers its `$task->update`. **Livewire Actions** (`ArchiveTaskAction`/`UnarchiveTaskAction`, mirroring `DeleteTaskAction`'s shape) re-check every UI-extra condition inside `execute()` per the line-166 rule: archive guards `!can_delete || ticket_id || status !== 'done' || archived_at !== null`; unarchive guards `!can_delete || archived_at === null`. UI gating in `card.blade.php` is intentionally redundant with the Action (defense in depth, not a substitute). **Board query:** `TaskBoard\Main::archivedScope()` returns a closure that, unless `search !== ''`, applies `whereNotNull('archived_at')` when `showArchived` else `whereNull('archived_at')` — tapped onto the done column's count + list queries only (non-done columns never carry `archived_at` by invariant, so the scope is a no-op there and not applied). `doneWindowScope()` early-returns null when `showArchived` (archive view has no 45-day window), and both scopes no-op on search so a search finds archived done tasks regardless of the toggle (matching how search already bypasses the done-window). `showArchived` and `showAllDone` are **mutually exclusive** — each toggle resets the other to false, so the three done-column modes (windowed default / show-all / archive) never stack. `switchTab` resets `showArchived` like it resets `showAllDone`. The done column's `orderBy` switches to `archived_at desc` when `showArchived` (most-recently-archived first) else `updated_at desc` as before. **Admin sync** (per the "admin panel stays synced" rule): `archived_at` is surfaced read-only — `TaskTablePresenter::archivedAt()` (toggleable, hidden by default), `isArchived()` boolean icon column, `archivedFilter()` `TernaryFilter` (`is_archived` key, `queries(true: whereNotNull, false: whereNull)`), `TaskInfolistPresenter::archivedAt()` entry, `TaskExporter` column, `HasJalaliAdminLabels::archivedLabel()`, and the `TasksRelationManager` column+filter — all wired into `TaskResource` and the RM. Deliberately NO admin archive/unarchive Actions: archiving is a user-panel gesture; admin sees the result (visibility/filter/export), not the lever. **Card UX:** archived cards render `opacity-70 grayscale`, non-draggable (`:draggable`/`@dragstart`/cursor class all gated `&& !$task['is_archived']`), with delete/assign/edit/view buttons hidden — only the `unarchive` button (`unarchive` icon) shows; the `archive` button (`archive` icon) shows on non-archived done cards owned by the viewer. The done column header gains an `archive`/`unarchive` toggle (tertiary container when active) next to the history toggle, which is hidden while `showArchived` (the archive view replaces the window view, not layers on it); title swaps to `آرشیو`, subtitle to `· آرشیو`, and the empty-state gets a dedicated `مورد آرشیو شده‌ای نیست` branch ahead of the 45-day "show older" nudge. No nudge/bell entry — archiving is silent presentation, matching the no-nudge-badge preference. Tests: `TaskModelTest` (accessor + reopening-clears + non-status-update-keeps), `TaskBoardTest` (10 cases: hide/reveal/unarchive, only-done/non-owner/ticket guards, page+tab resets, search bypass, reopen-clears), `TaskResourceTest` (`is_archived` filter). Reference: `Task::booted()` updating hook, `ArchiveTaskAction`/`UnarchiveTaskAction`, `Main::archivedScope`/`loadTasks`, `card.blade.php`/`column.blade.php`, `TaskTablePresenter::archivedAt`/`archivedFilter`/`isArchived`.

## Birthday/anniversary occasions — `Profile\HasOccasions` trait, zero extra queries, Status spotlight row + Contact stats tile

Surfaces a colleague's exact-day birthday/work-anniversary (from `profiles.birthdate`/`start_date`) beyond the Calendar module, on the Status board and in the Contact empty-state stats — pure presentation, no new nudge/badge/notification (matches the no-nudge-badge preference).

**Single source of truth — `App\Models\Traits\HasOccasions` (mixed into `Profile`).** `isBirthdayToday()`/`isAnniversaryToday()` use Carbon's own `isBirthday()` (month+day match, leap-year aware) guarded by the existing `!isTerminated()` check — a distinct mechanism from `App\Services\Menu\Indicators\SpecialDays`' raw SQL `whereMonth`/`whereDay` (that one powers the Calendar menu-dot badge and stays untouched; the two agree on every real date including Feb 29, verified against Carbon's source, but aren't the same code path — this is a presentational feature, not required to share the badge's exact query). `todaysOccasionType(): ?string` returns `'birthday'|'anniversary'|null` (birthday wins the tie if both match). `occasionTone(string $type): array` (static) is the one shared icon/color/label map — `cake`/`--tool-gold-*`/«تولد» and `workspace_premium`/`--tool-sage-*`/«سالگرد کاری» — currently consumed only by the Status spotlight row, kept static/shared so a future consumer never has to invent its own copy.

**Status board (`Tab\Status`)** — `#[Computed] todaysOccasions()` filters the board's own already-loaded `$this->users` collection (which is `visibleOnBoard()`-scoped — Guest-type excluded, same as the rest of the board) and maps each match to `{user, type}`; **zero extra queries**, since `$this->users` is accessed via property syntax from both the grid and this computed, hitting Livewire's per-request memo either way. `status/occasions.blade.php` renders a spotlight row above the filters — gated `@if(count($this->todaysOccasions))`, so it's simply absent on an ordinary day — with a corner badge icon on each avatar and a small `auto_awesome` pulse beside the name, both from `Profile::occasionTone()`. A small count badge (`celebration` icon + count) sits in the page title's `actions` slot, gated the same way, that smooth-scrolls to `#todays-occasions` on click (via an Alpine `x-ref`) — so the signal is still visible even after scrolling past the row itself.

**Contact — both a per-row chip AND an aggregate stat (the per-row signal was removed, then explicitly restored).** `Contact\Main::contacts()` adds `'occasion' => $user->profile?->todaysOccasionType()` to the raw per-row array (the `profile` relation is already eager-loaded by `FetchContactsAction`, so this is zero extra queries too); `ContactPresenter::contact()` passes it straight through into the shaped row the sidebar reads (`$contactList = $p->sidebar($this->contacts, ...)` in `contact/sidebar.blade.php`); `ContactPresenter::totalOccasions(array $contacts): int` separately counts the non-null ones from the *raw* array for `contact/empty.blade.php`'s stats row (همکاران / آنلاین / خوانده‌نشده / «تولد/سالگرد», the 4th tile gated `@if($totalOccasions)` so it never shows a stray "0"). **The per-row UI is a static chip, not an interactive icon/button** — `sidebar.blade.php` renders `Profile::occasionTone($contact['occasion'])` as an always-visible rounded pill (icon + label text) right next to the contact's name, deliberately not wrapped in a `<button>`/click handler: an earlier interactive version (small icon only, native `title=""` tooltip, later a `toast()`-on-tap fix) was removed for being touch-hostile and over-built, then a no-icon-at-all version was tried and rejected as *too* quiet — the always-visible chip is the settled middle ground, needing no interaction to be understood. **Deliberately Contact-only, not Channel** — confirmed with the user rather than assumed, to avoid reintroducing the exact kind of cross-module inconsistency this session's `visibleOnBoard()` audit was about; Channel's `empty.blade.php` did get a matching *visual* restyle of its own pre-existing stats row (SVG-icon grid cards, matching Contact's new stat-tile look) but carries no occasion tile.

**Two reverted attempts along the way, don't repeat either:**
1. **Pinning the occasion person's card to the top of the Status *grid*** (not just the spotlight row) via a wrapping `<div style="order:-1">` plus a `background-image` wash on `<x-ui.decor.status>`. Two real lessons survive even though the grid change itself was reverted (the user wanted the spotlight row to be "enough," not layered onto every card too):
   - **Splitting `@if(...)`/`@endif` across a Blade *component* tag's (`<x-...>`) attribute list breaks its tag compiler** — `syntax error, unexpected token "endif"` — because component tags go through a dedicated attribute-parsing step full HTML tags and `@include`d partials don't. Compute the conditional value as a plain string in `@php` first, then interpolate it as one always-present attribute (`style="{{ $value }}"`, empty string when unset) — the same fix already documented for `@php(...)`-vs-`@forelse` elsewhere in this file.
   - **`<x-ui.decor.status>`'s caller-supplied attributes never reach its true outer grid-item element** — its template explicitly consumes `$attributes` on an *inner* div (`$attributes->except('wire:key')->class(...)`), so anything relying on the component's root being a flex/grid item (like CSS `order`) needs an explicit wrapping `<div>` at the call site instead; the component has no other consumers, but modifying its own template was avoided in favor of a page-local wrapper to keep the blast radius at zero.
2. **An interactive per-row icon (button + click handler) in the Contact sidebar, plus a clickable header count badge.** Built, removed, then partially rebuilt as the *static chip* described above — the interactive/clickable shape specifically is what stays reverted. Two things worth remembering from that detour: (a) a plain `title=""` attribute on a touch-primary surface (this is a mobile-first PWA chat sidebar) technically renders correctly but is functionally invisible — no touch equivalent, ~1s hover-and-hold on desktop — and a `str_contains($html, 'title="...")` test proves the markup is right without proving a human ever sees it; the eventual fix wasn't a better tooltip, it was making the label *always visible text* so no interaction is needed at all. (b) **verify against the file on disk, not against what you last wrote** — this file got hand-edited multiple times mid-session (a `<span title>` → interactive `<button>` fix was silently reverted back to the plain span by a later edit before anyone weighed in on removing it; later, a render check for the restored icon was run *before* the presenter-layer half of the restore had landed, briefly reading as "still broken" when it was actually just sequencing) — re-reading current state before trusting "I already fixed that" mattered more than usual here.
