# Profile module — tab registry, and the Settings tab's shared-state gotcha

## Tab registry — single source, no routing

`ProfilePresenter::tabs()` is the ONLY place tabs are declared — a keyed array (`label`, `icon`, `sub`, `title`, `component`, `key`, `lazy`). `tabs.blade.php` renders the sidebar from it; `profile.blade.php` renders the active one via `<livewire:dynamic-component :component="$tabs[$activeTab]['component']" ... :lazy="$tabs[$activeTab]['lazy']" />`, keyed on `Main::$activeTab` (`#[Url(as: 'tab')]`). Adding a tab is exactly: one array entry + one component class + one blade view + one `#[Lazy]` placeholder — no route changes, ever.

Sub-tabbed modules (Notifications, Tickets, Settings) layer a SECOND, internal switcher on top of this: a public `activeSection` property + a whitelist-guarded `switchTab(string $section)` method + `wire:key="profile-{module}-section-{name}"` on every branch (never a row id in the key — see `livewirePattern.md` Morph-safety).

## Settings tab — Focus Mode is server-backed, everything else is browser-only

`app/Livewire/Dashboard/Profile/Settings.php` and the navbar's `QuickSettings.php` are two separate Livewire components that both `use App\Traits\HasFocusMode` — the ONLY piece of this feature that touches the database. Everything else the Settings tab surfaces (theme, density, background/pattern, font size, reading ruler, double-click-copy, notification mutes, column visibility) is pure `localStorage`/Alpine store state, unique per browser, with zero server round-trip. The Settings tab does not introduce a new storage location for any of these — it's a second UI pointed at the exact same global stores the navbar's quick-settings/palette dropdowns already read/write, so a toggle changed from either place is the same setting.

**`focus_until` is deliberately its own column, never `extra`.** `User::extra()`'s `mergeExtra()` routes every top-level key except `preferences` into the `admin` bucket (the same bucket `UserResource\Pages\EditUser`'s KeyValue field replaces wholesale on save) — anything stored there would be silently wiped the next time an admin edits that user's notes. `focus_until` (nullable timestamp, no index — never queried across users, only read for the one user viewing/being viewed) sits on its own, completely outside the `preferences`/`admin` two-bucket system that backs the admin panel's `ManagePreferencesWidget`. The two systems are intentionally unrelated: an admin can be in Focus Mode (server column) and separately have their own admin-panel chrome preferences (`extra['preferences']`) with no interaction between them.

`HasFocusMode::activateFocusMode(?int $minutes)`/`deactivateFocusMode(?string $restorePresence)` only ever act on `Auth::user()`, clamp `$minutes` to 1–240 server-side regardless of client input, and validate `$restorePresence` via `PresenceStatus::tryFrom()` (safe `Onsite` fallback) — never written raw. Both dispatch `statusSwitcher-updated` so `StatusSwitcher`'s own presence pill stays in sync without any direct coupling.

### The multi-mount gotcha — mixins hold behavior, stores hold state

The quick-settings panel (`data/settings.js`'s `settings()` factory) is mounted FOUR times concurrently on the Profile page: desktop navbar, mobile navbar, `resources/views/livewire/dashboard/profile.blade.php` (the whole-page wrapper, mounted regardless of active tab), and the Settings tab itself. Anything kept as per-instance Alpine data (not a store) exists that many separate times, with that many separate `document`-level listeners. This was already a live bug for the two navbar copies before the Settings tab existed; adding a third and fourth copy made it load-bearing enough to fix (for focus state and font/ruler/copy) rather than defer — but the same factory's background-pattern `$watch`es (`initPattern()` triggers) were NOT moved into a store and still run once per mount; treat that as known, pre-existing, unfixed debt in this exact file, not something this session's extraction covers.

The fix: `stores/accessibility.js` (font size, reading ruler, double-click-copy) and `stores/focus.js` (Focus Mode's on/off flag AND its countdown timer — `schedule()`/`clear()`) are the single, module-level-listener-owning source of truth; `data/settings.js` now only exposes getters/thin methods that read/call through to them, so `toggle-row.blade.php`/`font-size-control.blade.php` needed zero changes despite the state moving. `mixins/focusMode.js` holds the shared ACTIONS (`activateFocus`/`deactivateFocus`/`initFocusFromSnapshot`), spread into both `settings()` and any future consumer, but never owns the timer itself — only the `focus` store does, so exactly one timer exists no matter how many components are mounted.

**Guard this pattern whenever adding a new toggle to `settings()`:** if it needs a `document`/`window`-level listener or must stay visually in sync across all three mount points, it belongs in a store's own one-time `init()`, never in the data factory — the data factory's `init()` runs once per mount, not once per app session.

The background-pattern `$watch`es in `data/settings.js` predate this convention and were left as global side-effect triggers (not per-instance state), so redundant re-registration doesn't cause visible bugs — but it did mean up to 4 concurrent `initPattern()` calls per toggle. Fixed minimally with a module-level `watcherOwner` reference (set on first `init()`, released back to `null` in `destroy()` only by whichever instance currently owns it) rather than moving the watch into `background.js` itself — cheaper than a full store migration, and correctly hands ownership to another still-mounted instance if the original owner unmounts.

`deactivateFocus()` starts with `if (!this.$store.focus.active) return;` — this is what makes it safe for all three mounted components' `focus-mode-expired` listeners to fire on the same timer expiry: the first to run flips the flag and does the real restore + `$wire` call; the rest see it already `false` and no-op. Removing this guard reintroduces the exact bug it fixes (the server presence getting redundantly overwritten by the second/third listener).

## Cross-tab sync is per-store, not automatic

Two distinct sync problems exist and only one has a general fix. The multi-mount problem above (same tab, several components) is solved by moving shared state into a store. Cross-TAB sync (same browser, two separate tabs/windows) is NOT solved by that — each tab has its own JS execution context and its own in-memory copy of every store, hydrated once from `localStorage` at that tab's `init()`. `theme.js`/`theme-manager.js` already solved this for theme/mode via a `window.addEventListener('storage', ...)` listener; `sound.js` now does the same for mute state (`chat-muted-channels`/`-contacts`/`-projects`) since a stale mute state across tabs is a correctness issue users notice immediately. `density`, `background`, `colVisibility`, `accessibility`, and `push` do NOT have this listener — toggling one of those in one tab won't visually update another already-open tab until it reloads (the underlying `localStorage` value is still correct either way). Add the same `storage` listener to any of those stores if this becomes a reported problem for them too; don't add it speculatively to all of them at once.

## Teammate-visible focus signal — `User::isFocusing()` is the single source

The admin panel's read-only "متمرکز تا HH:MM" indicator (`UserTablePresenter`/`UserInfolistPresenter`) only reaches admins, not the teammates a user actually works with day to day. `App\Livewire\Dashboard\Tab\Presentation\StatusPresenter::nodeData()`/`gridData()` (the org-chart and directory-grid views everyone uses to glance at colleagues' presence) now carry the same signal — the small presence dot swaps to a `self_improvement` icon with a "متمرکز تا HH:MM" tooltip, and the grid card's existing native `title` tooltip gets the same text appended after a "·" divider alongside the normal presence sublabel, instead of replacing it.

**Never check `focus_until?->isFuture()` directly anywhere new — always call `User::isFocusing(): bool`.** It requires BOTH `presence === PresenceStatus::Busy` AND a future `focus_until`. This guard exists because `StatusSwitcher::changeStatus()` can change presence away from Busy at any time without touching `focus_until` (it's a separate write path, deliberately — see `HasFocusMode`) — a user could manually switch to Angry mid-focus-session, and without the presence check, every focus indicator across the app would keep showing a calm "focused" icon stacked on Angry's own bounce animation and red styling. All three current call sites (admin table, admin infolist, Status board node+grid) already route through this one method — keep it that way if a fourth surface is ever added.

Do NOT add a new animation for the focus indicator anywhere — `PresenceStatus::Busy` already animates via `imageClasses()`/wherever it's applied; the focus signal is icon + tooltip only, layered on top of whatever animation the underlying presence already has.

## Backup/restore and resets — allowlist-only

`exportSettings()`/`importSettings()` in `data/settings.js` operate on a fixed `EXPORT_KEYS` allowlist (theme/density/background/font/ruler/copy/column-visibility/mute keys) — deliberately excludes `focus-snapshot`, pins, tags, taskboard/menu/recent-item keys (personal content curation and transient UI state, not "settings"). `importSettings()` ignores any key in the uploaded file that isn't in that same allowlist — a crafted import file cannot write arbitrary `localStorage` keys. `resetApp()` (full wipe) is `confirm()`-gated; `resetAppearance()`/`resetNotifications()`/`resetTables()` are scoped resets calling only the relevant store methods, added specifically so the one destructive full-wipe button isn't the only reset option.
