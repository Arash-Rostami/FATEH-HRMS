# Skills (Talent Pool Directory) — folded 2-table model, ghost-demand capture, SQL tier-sort

Employee-run skills catalog + peer endorsement layer, reachable from the Profile "استعدادها" tab (inserted before "about" via `ProfilePresenter::tabs()`) and merged into the Status board as a directory filter. Two tables only — `skills` (catalog + unmet-demand ghosts) and `skill_user` (membership + denormalized endorsements) — no `skill_endorsements`/`missing_skills_log` tables, no Policy classes.

## Data model

- **`skills`**: `is_active`+`is_ghost` together encode three states — active catalog row (`true,false`), inactive proposal draft (`false,false`), unmet-demand ghost (`false,true`). `unique(name)` (CI via `utf8mb4_unicode_ci`) means a ghost and a real skill can never coexist under the same name — a search that matches ANY row (active/draft/ghost) is not unmet demand. `Skill::activate()` flips a draft/ghost to the live catalog (idempotent); `recordSearch()` bumps `search_count`/`last_searched_at`, only ever called on ghost rows.
- **`skill_user`**: dedicated `Model` (not `Pivot`) but uses the `AsPivot` trait so `Skill::members()->using(SkillUser::class)` works without inheriting `Illuminate\Database\Eloquent\Relations\Pivot`'s stricter semantics — `AsPivot::setKeysForSelectQuery`/etc. early-exit to normal `Model` behavior once the row has an `id`, so this doesn't change any of `SkillUser`'s own query/save/delete paths. `unique(user_id, skill_id)` — ONE row per pair, ever. `endorsers` (JSON array of user ids) + `endorsements_count` (denormalized int, kept in sync on every write) avoid a join for the hot "does X endorse Y" / "how many endorsements" reads; endorser uniqueness is enforced app-level via `lockForUpdate()` inside `EndorseSkillAction`/`RevokeEndorsementAction`, not a DB constraint.

## Propose → approve/reject → re-request lifecycle

`RequestSkillAction` never inserts a second row for the same `(user_id, skill_id)` pair — a rejected row is REOPENED (status→pending, `rejected_reason`→null, `approved_at`/`approved_by`→null, `created_at`→now), never re-created. A proposal (`requested_name` set) resolves-or-creates an inactive draft skill by CI name (de-ghosting it if a ghost already held that name), inside a transaction with a duplicate-key catch+requery for the race window. `SkillService::approve()` gates `$skill->activate()` on `$row->requested_name !== null` — NOT on the skill's current `is_active`/`is_ghost` state — so approving a catalog pick can never silently reactivate a skill an admin deliberately deactivated in between; only proposal approvals promote their draft.

**Re-request UI gotcha**: the "درخواست مجدد" button must branch on `requested_name` — a rejected catalog pick re-request sets `form->skillId`, a rejected proposal re-request sets `form->proposedName` (the underlying skill is still `is_active=false`, so treating it as a catalog pick throws `SkillRequestValidator`'s "not available" error). `Skills::reRequest(int $skillUserId, ...)` takes the `skill_user` row id (not `skill_id`) specifically so it can read `requested_name` to decide the branch.

## Tier computed on read, SQL-sorted, never a collection sort

`SkillTier` (Endorsed/Active/Unused) is never stored — `SkillUser::stateTier()` derives it from `endorsements_count >= ENDORSEMENT_SATURATION_CAP` (4, NOT `ENDORSEMENT_THRESHOLD`=1 — see below) then `last_used_at` within the active window (`SkillUser::ACTIVE_WINDOW_DAYS` — plain class constants, no config file or Settings wrapper; `SkillUser::NEW_BADGE_UNTIL`/`newBadgeUntil()` likewise backs `ProfilePresenter::newBadgeVisible()`). Any directory-style listing (Status board join) sorts via `orderByRaw('(su.endorsements_count >= ?) DESC', ...)` + a `last_used_at` recency raw clause + a `LEAST(endorsements_count, cap) DESC` tiebreaker — never `Collection::sortBy` — because the denormalized `endorsements_count` column makes it index-friendly without a join to a separate endorsements table. `Skills::ownSkills()` (the one collection-sort exception, scoped to a single user's own small list) mirrors the same tuple: `[non-approved-last, tier, -min(count, cap), -last_used_at]`.

**Gotcha, real bug once caught in review: every branch of a `sortBy` comparison-array closure must return the SAME number of elements.** PHP compares arrays element-count-first, only falling through to element-by-element comparison when counts match (`[1, 0, -5] <=> [0, 1, -4, -9]` is `-1` — the shorter array always "wins" regardless of its actual values). `ownSkills()`'s non-approved branch briefly returned a 3-element tuple while the approved branch returned 4 (after the tiebreaker elements were added), which silently sorted every pending/rejected row ABOVE every approved row — the exact opposite of the leading `0`/`1` flag's intent — and went undetected because both existing sort-order tests only ever used all-approved fixtures (equal-length tuples never triggered the count mismatch). Fixed by padding the non-approved branch with a trailing `0` to match arity; regression test: `ProfileTest::test_own_skills_computed_sorts_approved_rows_before_pending_and_rejected` (asserts across mixed-status fixtures, not just same-status ones). Whenever either branch's tuple grows, grow the other to match.

### Endorsement saturation cap — "Endorsed" requires 4+, not 1

`ENDORSEMENT_THRESHOLD` (1) and `ENDORSEMENT_SATURATION_CAP` (4) are deliberately two different constants, not a rename. `ENDORSEMENT_THRESHOLD` still means "has at least one endorsement" (used by `isEndorsed()`'s default/legacy call sites); `ENDORSEMENT_SATURATION_CAP` is the new bar `stateTier()` actually gates "Endorsed" on. A skill with 1–3 endorsements sits in the `Active` tier (if recently used) same as an unendorsed-but-active skill — endorsement count only breaks the tie *within* that tier via the sort tuple above, it doesn't change the badge. Only 4+ endorsements earns the top-tier "تأییدشده" badge. This was a deliberate behavior change (previously any single endorsement reached top tier).

### Dormant — an orthogonal flag, not a fourth tier

`SkillUser::isDormant()` = `stateTier() === Endorsed && !isActive()`. It's the ONLY tier/activity combination that needs a distinct visual treatment beyond the 3 tier badges, because `Active` tier is BY DEFINITION recently-used (so it can never be dormant), and `Unused` tier already communicates "not recently used" via its own label — adding a redundant "dormant" chip there would be noise. So the "کم‌فعالیت" chip + row opacity fade (`skill-row.blade.php`) only ever appears on an `Endorsed`-tier row that has gone stale. Kept as a boolean model method rather than a 4th `SkillTier` case specifically to avoid duplicating the tier enum's presentation surface (label/icon/color) for a concept that's really "Endorsed, plus one bit."

### Sole vs. multiple endorsement — a definitive, single-source mechanism

Three things all read from the SAME two model methods (`SkillUser::endorsementLabel()`, `::endorsementMetalClasses()`) rather than each re-deriving the count→wording/color mapping independently: the user-panel row (`skill-row.blade.php`, silver/gold `military_tech` chip + Persian singular "تأیید یک همکار" vs plural "تأیید N همکار (از 4)"/"تأیید N همکار" wording), `SkillsRelationManager`'s `endorsements_count` column, and `SkillRequestTablePresenter::endorsementsCount()`. Silver = 1..cap-1 endorsements (not yet saturated); gold = cap+ (matches the `Endorsed` tier threshold exactly, by design — the metal chip is a miniature preview of the tier the skill is approaching/has reached). `SkillUser::isSoleEndorsement()` (`endorsements_count === 1`) is the explicit boolean for "exactly one" if a future UI needs to branch on it directly instead of via the label/color helpers.

## Status board directory merge (`Tab\Status`)

`$skillId`/`$skillSearch`/`$mentorOnly` add an INNER `join('skill_user as su', ...)` (approved + non-private + skill match, optionally `is_mentoring`) to the existing `visibleOnBoard()` grid query, swapping the default rank/last-seen order for the tier-sort raw clauses only when `$skillId` is set. `?skill={id}` deep-links via `mount()` reading `request()->query('skill')`, validated through `Skill::activeCatalog()` (invalid/inactive ids are silently cleared, never a hard 404, and never logged as unmet demand). **Trap**: any extra join added to a `visibleOnBoard()`-scoped query must double check every column reference on that base scope is table-qualified — `User::scopeActive()`'s `where('status', 'active')` was ambiguous the moment a second table with a `status` column (`skill_user`) entered the join; it is now `where('users.status', 'active')`. Re-check this whenever a new join is added to any `User` query that rides `visibleOnBoard()`.

Free-text `$skillSearch` uses `LIKE '%term%'` against `name`/`name_en` for candidate chips (UX-facing, needs multiple matches) — a **separate, intentionally asymmetric** concern from `LogMissingSkillJob`'s own exact-match dedup lookup inside its `handle()`. Zero LIKE-candidates for a committed search dispatches the job once per normalized term per component instance (`$loggedSkillSearches` dedup array, a plain public property, survives Livewire's snapshot round-trip with no extra wiring).

## Shared owner/viewer partial — `skill-row.blade.php`

One partial (`resources/views/livewire/dashboard/profile/skill-row.blade.php`) renders a skill row (icon, tier badge, endorsement count + avatar stack, last-used + context, mentor label) and conditionally an endorse/revoke button (`$viewer->isNot($owner) && status===Approved && !is_private`). It is `@include`d from two places: `Skills`'s own-skills list (`$owner=$viewer=Auth::user()`, endorse button naturally hidden) and the Status board's about-me modal (`$owner`=the viewed colleague, `$viewer`=Auth::user()) — nowhere else yet. **Any Livewire component that includes this partial MUST implement `endorse(int, EndorseSkillAction)`/`revokeEndorsement(int, RevokeEndorsementAction)`** (mirroring `Skills.php`) — the partial's `wire:click` calls resolve against whichever component rendered it, so omitting these methods on a new host component 500s the moment a viewer clicks endorse. `SkillUserPresenter::preloadEndorsers()` must be called once per render before the partial's `endorsersAvatarStack()` loop runs, or every row re-queries its own avatar `whereIn` (N+1).

## Notifications — Cache-based, NOT the sitewide `notifications`/bell mechanism

A `Cache::lock()`-guarded per-user dedupe-keyed map (7-day TTL, key `skill_notices:{userId}`) stands in for a real notification store. The write side is `SkillUser::notify()`; the read/drain side is `Skills::dismiss()` (private, called from `mount()` after dispatching each queued toast) — split across the two classes that actually use each half rather than kept in a standalone `App\Services\TalentPool\Notice` (deleted; it only ever held `dispatch()`, and `dismiss()` had already migrated onto `Skills` independently). This is a **deliberate deviation** from the rest of the app's `Notification::make()->sendToDatabase($user)` pattern (cf. `AssignTaskAction`) — skill approve/reject/endorse notices do NOT appear in the Filament bell, only inside the Skills tab itself. Known limitation, not a bug: a user who never revisits that tab never sees the notice. If this needs bell visibility later, migrate the three `SkillUser::notify()` call sites (`SkillService::approve/reject`, `EndorseSkillAction::execute`) to `sendToDatabase()` — do not add a second parallel notice mechanism.

## Admin `ProfileResource` Skills tab — deliberately bypasses the request queue

`ProfileFormPresenter::skills()`/`ProfileInfolistPresenter::skills()` add a "مهارت‌ها" tab to `ProfileResource`'s form/infolist, letting admin staff add/edit/delete a user's `skill_user` rows directly — this is the ONE admin entry point that skips the propose→approve/reject workflow above entirely; an admin-authored row defaults to `status=approved` (with `approved_at`/`approved_by` stamped server-side whenever the saved status is Approved) since the admin IS the approval authority for this path. Not a real Eloquent relationship on `Profile` — `SkillUser` FKs to `users.id`, not `profiles.id`, and `HasManyThrough` has no `create()`/`save()` (verified against `vendor/laravel/framework` source), so Filament's `Repeater::relationship()` can't bind it. Instead the Repeater mirrors `aboutMe()`'s manual pattern: `afterStateHydrated()` reads `$record->user?->skillUsers()->with('skill')->latest('id')->get()`, a custom `saveRelationshipsUsing()` diffs existing/kept/deleted rows against `$user->skillUsers()`. The `skill_id` Select is grouped-by-category with the Farsi name + English name in parens (`"{$skill->name} ({$skill->name_en})"`), sourced from `Skill::cachedActiveCatalog()` — the SAME cached query the user-panel `Skills::catalog()` computed property consumes, so both surfaces can never drift out of sync on ordering/labels. See `filamentPattern.md` for the Filament-specific gotchas (`ViewField`/`ViewEntry` `->state()` lifecycle crash to avoid, relationship-Repeater alternatives).

## Ghost catalog is cached, and browsable via a List tab (not just the dashboard widget)

`Skill::cachedActiveCatalog()` caches the active-catalog query (`Cache::remember('skill_active_catalog', now()->addDay(), ...)` wrapped in `once()`, busted on `Skill::saved`/`Skill::deleted` in `booted()` — `recordSearch()`'s `increment()` only fires `updating`/`updated`, never `saved`, so per-search cache churn is a non-issue). `SkillResource::getEloquentQuery()` still hard-excludes ghosts (`is_ghost=false`) for ordinary browsing/edit/global-search, but `ListSkills` adds a dedicated "ghosts" tab (badged with the live ghost count) alongside the default "catalog" and "inactive" tabs — see `filamentPattern.md` rule 58 for why this needed a `getTableQuery()` override (a List tab can't un-apply a `where()` the Resource's base query already baked in) and why `EditAction` had to be explicitly hidden on ghost rows (page-navigation actions still resolve through the Resource's restrictive `getEloquentQuery()` and would 404). The Dashboard `UnmetSkillDemandTable` (a `Filament\Widgets\TableWidget` — NOT plain `Widget` — ordered by `search_count` desc, genuinely paginated via `->paginated([10, 25, 50])`, with a `promote` row action reusing `SkillFormPresenter::category()`/`::icon()`) remains the primary promote workflow; the List tab is a plain browse/monitor surface, no bulk actions. See `filamentPattern.md`'s "Approval-queue resource pattern" section for why this widget must extend `TableWidget` rather than echo a raw `Action::make()` in a hand-rolled Blade loop (the latter never registers with Filament's action resolver and silently fails on click).

## Cross-panel consistency notes

- **Ownership-bypass reuses `SkillRequestResource::canEdit()`, not a bespoke role check.** The 5 own-vs-other-user actions (`EndorseSkillAction`, `RevokeEndorsementAction`, `MarkSkillUsedAction`, `ToggleMentoringAction`, `ToggleSkillPrivacyAction`) gate non-owner access via `SkillRequestResource::canEdit($row)` — the exact same `permits('update')` evaluator the admin panel's approve/reject actions already use for the `skill_request` module. This rides the project's one true admin model (`adminPanelPermissionLogicPattern.md`): `isDeveloper()` bypasses unconditionally, everyone else needs a `Permission` row granting `skill_request:update`. Do NOT reintroduce a role-string check (`isAdmin()`/`role === 'admin'`) here — that was tried and diverged from every other admin-bypass site in the app. No new `Permission` module registration was needed: `Permission::availableModules()` already auto-discovers `skill`/`skill_request` from the existing `*Resource.php` files on disk (1-day cache, no auto-bust — a stale `permission_modules` cache needs `Cache::forget` or a worker restart to pick up newly added Resources).
- **Skill name/name_en dedup is centralized in `Skill::scopeMatchingName()`.** All four places that need to ask "does a skill already exist under this name" — `LogMissingSkillJob` (ghost capture), `SkillRequestValidator::validate()`, `RequestSkillAction::resolveOrCreateDraft()`, and admin `SkillResource\Pages\CreateSkill::handleRecordCreation()` — call `Skill::matchingName($name)` rather than each independently deciding whether to check `name` alone or `name` OR `name_en`. `name_en` still carries no DB unique constraint (only `name` does), so the scope is what keeps the four call sites from drifting apart again, not the schema. If a fifth "does this skill exist" call site is ever added, it must use the scope too — a bare `where('name', ...)` there was a real, reproduced bug (admin-create colliding on `name_en` created a duplicate row), not a hypothetical.
- **`matchingName()`'s "only one row can match" invariant is enforced by app-level validation, not a DB constraint (deliberate choice).** Because only `name` (not `name_en`) is unique at the schema level, `where(name=$X) orWhere(name_en=$X)` could in principle find one row via `name` and a completely different row via `name_en`. Rather than add a `name_en` unique index/migration, this is prevented at the point where `name`/`name_en` are ever actually set by a human — the admin Create/Edit Skill form — via `SkillFormPresenter::noNameConflictRule()`: both the `name` and `name_en` fields attach the `UniqueActiveSkillName` `ValidationRule` (`app/Rules/UniqueActiveSkillName.php`), which calls `Skill::matchingName($value)` (excluding the record being edited) and fails with a clear field-level error (`resources/skill/strings.errors.name_conflict`) if it matches any other row. The rule is operation-aware: on **create**, only a match against an already-**active** row fails (a match against a ghost/draft is meant to promote it via `CreateSkill::resolveCollision()`, not be blocked here); on **edit**, any other row matching fails outright, since editing never merges two rows into one. This closes the gap prospectively (no new ambiguous pair can be created through the one place `name_en` is ever set) without a schema change — it does not retroactively fix any such pair that might already exist. There is no separate user-panel change needed: users never set `name_en` (`SkillsForm` only has `proposedName`), and `RequestSkillAction`/`SkillRequestValidator` already route every proposal through the same `matchingName()` scope, so once the admin side can't create the ambiguous state, the user-panel lookups can't encounter it either.
- **Fixed: `CreateSkill` now blocks (doesn't silently merge) on an active-skill name collision.** `handleRecordCreation()`'s `resolveCollision()` throws `ValidationException::withMessages(['name' => ...])` when `Skill::matchingName()` matches an already-**active** catalog skill, mirroring `SkillRequestValidator`'s "already exists, pick from the list" treatment. `promoteExisting()` (the silent reuse-and-overwrite path) is now reached ONLY for inactive draft/ghost matches, where overwriting blank fields is the intended promote behavior. Test: `assertHasFormErrors()` with no key (a `ValidationException` thrown from this hook doesn't map to Filament's `data.*` field-error namespace — same reason `CreateSuggestion`'s identical technique also asserts generically; don't try to assert a specific field key here).
- **Cross-panel label order is intentionally different, not a bug**: `ProfileFormPresenter::skillCatalogOptions()` (admin) renders `"{name} ({name_en})"`; `Skills::catalog()` (user panel) renders `"({name_en}) {name}"`. Same cached catalog (`Skill::cachedActiveCatalog()`), cosmetic order difference only — left as-is.
- **Fixed: admin views now surface the computed `SkillTier` too.** `SkillsRelationManager`, `SkillRequestTablePresenter::tier()`, and `ProfileInfolistPresenter::skillsState()`'s `tier`/`endorsements_count` keys all add this. `SkillTier` gained `color()`/`heroicon()` methods alongside its existing `label()`/`icon()`/`badgeClasses()` — `icon()` stays Material-Symbols (Livewire/blade), `heroicon()` is the separate Filament-compatible id, mirroring the same split `SkillRequestStatus` already has (`icon()`-less, `heroicon()` only) and why one wasn't just reused for the other.
- **`stateTier()` must always be gated on `status === Approved`, everywhere it's called.** `SkillUser::stateTier()` itself has no such guard (it just derives a badge from `endorsements_count`/`last_used_at`, both of which are DB columns an admin's `ProfileFormPresenter::skills()` Repeater form can set to any status). Every actual call site enforces the gate at the call site instead of inside the method: `Skills::ownSkills()` only calls it in its `status===Approved` sort branch; `skill-row.blade.php` (and therefore `isDormant()`/`endorsementLabel()`/the metal chip, all reachable only through that partial) is only ever `@include`d for approved rows (`skills.blade.php`'s `@if($skillUser->status->value === 'approved')`, `Status::aboutMeSkills()`'s hard filter); the three admin surfaces above all do `$record->status === SkillRequestStatus::Approved ? $record->stateTier() : null` explicitly. **This was a real, caught-in-review bug**: `SkillsRelationManager`'s tier column originally computed `stateTier()` unconditionally, so a pending/rejected row (always 0 endorsements, never `last_used_at`) silently rendered an "آماده مشارکت" (Unused-tier) badge — reading as "reviewed and found lacking" when the row hadn't been reviewed at all. Regression test: `UserResourceTest::test_skills_relation_manager_shows_dash_tier_for_pending_row_not_a_misleading_unused_badge`. If a sixth tier-consuming call site is ever added, it needs this same guard — `stateTier()` gaining its own internal guard was considered and rejected, since `isDormant()` and the sort tuples need the *raw* derived tier for their own already-gated contexts, not a silently-`null`-coalescing one.
- **Deliberately NOT gated the same way: `endorsementLabel()` on the three admin surfaces.** Unlike `tier`, the `endorsements_count` column/field always calls `endorsementLabel()` regardless of status. In normal operation this is harmless — a pending/rejected row's `endorsements_count` is always 0 (nothing else can set it), so it just shows "بدون تأیید", which is accurate. The only state where this could look inconsistent with the (gated) tier column next to it is if an admin uses `ProfileFormPresenter::skills()`'s Repeater — which allows setting ANY status on ANY row with no workflow guard — to flip an already-Approved-and-endorsed row back to Pending/Rejected without the payload touching `endorsers`/`endorsements_count`. Gating the label too would fix that one near-impossible admin-authored state at the cost of showing an uninformative "-" on every normal, legitimately-zero pending row — not worth it. Documented here so it reads as a considered trade-off, not an oversight.

## Dashboard stats — `ModuleAnalyticsWidget::skillsData()`

The admin dashboard's per-module stats-overview widget has a `skills` tab covering all six real varieties, not just "total" + "active": `Skill` rows split into `active`/`draft` (`is_active=0 AND is_ghost=0`)/`ghost` (`is_ghost=1`, mutually exclusive and exhaustive over the `(is_active, is_ghost)` state space), and `skill_user` rows split into `pending`/`approved`/`rejected` (exhaustive over `SkillRequestStatus`). ## `last_used_context` is VARCHAR(255) — validated at both the component and the Action

`skill_user.last_used_context` (free-text "used it for..." note, set via `Skills::markUsed()` → `MarkSkillUsedAction`) is capped at 255 chars in the schema. A note over that limit used to hit the DB directly and 500 on `SQLSTATE[22001]` (strict-mode truncation) instead of failing cleanly. Fixed with two independent layers, matching how every other `.max` field in this app surfaces its message (inline `@error()`, not a toast): `Skills::markUsed()` calls `$this->validate(['markUsedContext' => 'nullable|max:255'], [...])` before the try block so a violation renders inline under the textarea (`x-ui.forms.textarea` already supports `@error($name)`) rather than being swallowed by the method's generic `catch (\Exception $e)` toast handler; `MarkSkillUsedAction::execute()` keeps its own `mb_strlen() > 255` guard (throwing `\RuntimeException`, the same style as its existing approved-only check) as defense-in-depth for any future caller that bypasses the Livewire component. The admin `ProfileResource` Skills-tab Repeater (`ProfileFormPresenter::skills()`) never exposes `last_used_context` as an editable field at all (only `last_used_at`), so there's no matching admin-side write path to guard. Regression tests: `ProfileTest::test_mark_used_rejects_context_over_255_chars_with_error_toast` (256 chars, `assertHasErrors`) + `::test_mark_used_accepts_context_at_exactly_255_chars` (boundary-pass companion).

## `Skills.php` only `report()`s genuinely unexpected exceptions, not business-rule rejections

Every write method on `Skills` (`requestSkill`, `markUsed`, `togglePrivacy`, `toggleMentoring`, `endorse`, `revokeEndorsement`) follows a `try { ... } catch (HttpException $e) { throw $e; } catch (\Exception $e) { report($e); toast(error) }` shape. Every Validator/Action in this module (`SkillRequestValidator`, `EndorsementValidator`, `MarkSkillUsedAction`, `ToggleSkillPrivacyAction`, `ToggleMentoringAction`, `RequestSkillAction`) exclusively throws `\RuntimeException` for expected, user-facing business-rule rejections (e.g. "already tried", "not yet approved", "over 255 chars") — never for genuine bugs/infra failures. Because the old catch chain treated every `\Exception` identically, `report()` was firing (and polluting `laravel.log` with ERROR-level entries) on completely normal, expected validation rejections — which is exactly why several of those messages showed up in a production log sweep alongside actual bugs, with no way to tell them apart from the log alone. Fixed by inserting a `catch (\RuntimeException $e) { toast(error) }` (no `report()`) ahead of the generic `catch (\Exception $e)` in all six methods — the toast/UX behavior is byte-identical, only the log-noise is removed. **Rule: in this module (and any other that establishes `\RuntimeException` as its "expected validation failure" signal type), a catch chain that both toasts AND `report()`s must split `\RuntimeException` out from `\Exception` — `report()` only the latter, or the error log can't distinguish real bugs from working-as-intended rejections.** This same widespread `catch (\Exception $e) { report($e); toast(...) }` shape also exists in `Contact/Main.php`, `Channel/Main.php`, `Ths/Main.php`, `Tab/Status.php`, `Reservation/Main.php` — not yet audited/fixed, since none of their thrown exceptions were implicated in the log sweep that prompted this fix.

**Gotcha caught in review: `Illuminate\Database\Eloquent\ModelNotFoundException extends RecordsNotFoundException extends \RuntimeException`**, so the five methods that call `SkillUser::findOrFail()` directly (not via an Action/Validator — `markUsed`, `togglePrivacy`, `toggleMentoring`, `endorse`, `revokeEndorsement`) had a stale-tab/deleted-row 404 silently absorbed by the new `\RuntimeException` catch, losing a signal that WAS reported before this fix. Restored via a dedicated `catch (ModelNotFoundException $e) { report($e); toast(...) }` inserted between the `HttpException` and `\RuntimeException` catches in those five methods (order matters — a subclass catch must come before its parent's). **Rule: before adding a broad catch on any exception TYPE (not just the ones this module itself throws), grep for every framework/library call in the same try-block that can throw a subclass of that type — `findOrFail()`, `firstOrFail()`, and similar Laravel "or throw" helpers are the most common source of an unintentionally-swallowed subclass.**

**Second-pass catch caught in independent review: the rule above wasn't applied to `requestSkill()`/`reRequest()`.** `Skills::requestSkill()` doesn't call `findOrFail()` directly, but the `RequestSkillAction::execute()` it invokes does — `Skill::lockForUpdate()->findOrFail($form->skillId)` — reachable via a narrow TOCTOU race (the skill deleted between `SkillRequestValidator`'s existence check and the locked `findOrFail` a few milliseconds later inside the transaction). Worse, `RequestSkillAction::resolveOrCreateDraft()` explicitly `throw $e;`s a raw `Illuminate\Database\QueryException` for any non-duplicate-key DB failure — and `QueryException` also `extends \RuntimeException`. Both were falling into `requestSkill()`'s `catch (\RuntimeException $e)` (no `report()`) instead of being logged, meaning a genuine DB failure — exactly the kind of "real bug" this whole fix exists to keep visible — went silently unreported. Fixed with `catch (ModelNotFoundException|QueryException $e) { report($e); toast(...) }` ahead of `\RuntimeException` in `requestSkill()` too. Takeaway: "doesn't call `findOrFail()` directly" isn't sufficient — the grep must follow into every Action/Validator the method delegates to, not stop at the method's own body.
