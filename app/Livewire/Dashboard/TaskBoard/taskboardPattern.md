# TaskBoard module pattern

The TaskBoard ("برد وظایف") is the user-panel kanban: a four-column board (todo / in-progress / pending / done) with fractional-index drag-reorder, a rich create/edit/view modal shared with Project's Kanban tab via the `ManagesTaskModal` trait, weighted-checklist progress, ambient urgency, archive, calendar sync, and a full admin Filament mirror. This doc is the single source for every TaskBoard-specific rule; the general Livewire/Filament conventions live in `app/Livewire/livewirePattern.md` and `app/Filament/filamentPattern.md`.

Route: `routes/web.php` line 50 — `Route::get('/tasks', TaskBoard::class)->name('tasks')` where `TaskBoard = App\Livewire\Dashboard\TaskBoard\Main`. Module registration: `config/modules.php` line 161 — `'id' => 'taskboard'`.

Layering rule: **Models + Services + Actions own all business logic; the Livewire component is a thin HTTP/Livewire adapter; the Presenter is a pure, stateless data-bag builder; blades are dumb renderers; Alpine owns only instant client-side UI feedback.** Filament-resource enums (`TaskStatus`/`TaskPriority`/`TaskState`) live under `app/Filament/Resources/TaskResource/Enums/` and are imported into the core Model/Service layer — an accepted layering choice (the Filament resource owns the enum vocabulary, the core layer consumes it).

## 2. `Main` — the board orchestrator

`app/Livewire/Dashboard/TaskBoard/Main.php` — `#[Lazy] class Main extends Component`, uses `FocusOnRecord`, `ManagesTaskModal`, `WithFileUploads`.

Constants/state:
- `DONE_WINDOW_DAYS = 45` — the done-column visibility window.
- Four per-column public arrays keyed by status: `$tasks`, `$totalCount`, `$doneTotalCount`, `$page` (each `['todo','in-progress','pending','done']`-keyed). `$perPage = 4`.
- `$columns = ['todo','in-progress','pending','done']` (the kanban axis; `archived` is deliberately NOT a column — see §10).
- `$activeTab` — `#[Url(as: 'tab')]`, values `'my-tasks'` / `'assigned-tasks'` (the two board scopes).
- `$showAllDone` / `$showArchived` — done-column modes, **mutually exclusive** (each toggle resets the other to `false`); `switchTab()` resets `showArchived` like `showAllDone`.
- `$selectionMode` / `$selectedTasks` — bulk-action state.
- `$columnsToSelect` — 15 task columns (`id`,`title`,`description`,`status`,`deadline`,`created_at`,`updated_at`,`archived_at`,`user_id`,`assigned_to`,`ticket_id`,`project_id`,`labels`,`priority`,`rank`) including `rank` and `updated_at` (the latter feeds the idle-urgency calc, the only query-side change urgency needed).
- `$relationsToLoad` — `assignee`, `creator`, `project`, `detail` (+ nested `detail.responsibleUser`). The `detail` select list includes the physical string columns `project,unit,section` plus `meta` (NOT relations — they are `TaskDetail` columns; `project:id,name,owner_id,settings` is the separate relation, its select now carrying `owner_id`+`settings` for the approval chip / meta-chip labels / urgency branches without extra queries) so the card can render the free-text project override, the unit/section department-popover lines, the approval state, and meta chips without extra queries.

Key methods:
- `loadTasks()` — per-column paginated query; applies done-window + archive scopes; runs `collaboratorLookup()` once across the whole board (one `User::whereIn` batch) and `LastTouchResolver::resolve()` once (the board's single new query vs. pre-approval build), then splices `collaborator_users` into each task's `detail` array and `last_touched` onto the task array after `toArray()`.
- `scopedQuery()` — tab + search + deadline + project + priority + label (multi-select AND) + `whereHas('detail', …)` for responsible/department/scheme/unit/section/actionSource + assignee filters. The whole `whereHas('detail', …)` block is gated by one `->when($anyFilter, …)` so an empty filter rail costs no detail-join.
- `archivedScope()`, `doneWindowScope()`, `deadlineFilterScope()` — query-scope closures tapped only onto the done column (non-done columns never carry `archived_at` by invariant, so the scopes are no-ops there).
- `personalTaskScope()` — narrows the my-tasks/assigned-tasks tab scope.
- CRUD/board actions: `archiveTask`/`unarchiveTask`/`assignTask`/`undoAssignment`/`deleteTask`/`cyclePriority`/`reorderTask`/`updateTaskStatus`/`bulkAssign`/`bulkDelete`/`bulkMoveStatus`/`exportTasks` — each delegates to a single-purpose Action class; `cyclePriority` follows the no-toast `reorderTask`/`updateTaskStatus` shape (frequent/interactive), while `archiveTask`/`assignTask` toast on success (deliberate CRUD actions).
- `addLabelFilter(string $label)` — pushes onto the `$labelFilter` array (dedup via `in_array(..., true)`) rather than `$set('labelFilter', $label)` which would overwrite the array. On Project's board the card counterpart is `addKanbanLabelFilter`; Project's Kanban label-filter *dropdown* UI additionally uses `toggleKanbanLabelFilter(string $label)` (add-or-remove, re-indexed), while `addKanbanLabelFilter` is kept for the card chips via `cardMeta`'s `labelFilterMethod`.
- `jumpToPage`/`nextPage`/`prevPage` — per-column pager.
- `#[Computed]` — `deadlineFilterCounts`, `schemeOptions`, `unitOptions`, `sectionOptions`, `assigneeOptions`, `actionSourceDomainOptions`, `actionSourceOptions`. `schemeOptions`/`unitOptions`/`sectionOptions` all delegate to one cached `ReportingService::boardDetailOptions()` (a single `TaskDetail::whereHas('task', $scope)->get(['scheme','unit','section'])` query → PHP-side unique/sort) — three accessors, one DB hit, one shared cache entry (the personal-task scope is bounded to one user's rows, so materializing the 3 short columns is cheaper than three DB-level DISTINCT round-trips).
- `refreshAfterTaskSave()` — the `ManagesTaskModal` hook contract; calls `loadTasks()`.
- `recordFocusType()` returns `'task'`; `placeholder()` returns the lazy-load placeholder view.
- `render()` returns `view('livewire.dashboard.taskboard', ['presenter' => new TaskBoardPresenter(), 'dmsPresenter' => new DmsPresenter()])`.

## 3. Presenter data-bag pattern — `TaskBoardPresenter`

`app/Livewire/Dashboard/TaskBoard/Presentation/TaskBoardPresenter.php` — a plain class (not a Filament presenter; no inheritance), instantiated fresh in `render()` and re-passed into the shared `form.blade.php` `@include` from Project. **Pure presentation only**: it reads already-hydrated array shapes (the task `toArray()` + spliced `collaborator_users`), never queries the DB. Every method returns a small array/shape consumed directly by blades.

Methods (signatures verbatim):
- `priorityChip(?string $priority): ?array` — `['label','isUrgent','class']`; maps `TaskPriority` onto MD3 container tokens (Urgent→error-container, High→tertiary-container, Medium→secondary-container, Low→surface-container-highest). Returns `null` for an unset priority.
- `stateChip(?string $state): ?array` — `['label','icon','class']`; maps `TaskState` directly onto `warning`/`error`/`success` container tokens (Extension→warning, Suspension→error, Completion→success) with icons `calendar_month`/`pause_circle`/`task_alt`. These dedicated tokens didn't exist when `priorityChip` was written, so `priorityChip` remaps through `tertiary`/`secondary` while `stateChip` uses the direct ones.
- `columnConfig(): array` — the 4 columns: `title` (from `TaskStatus::getLabel()`), `icon` (emoji), `color` (semantic token name: primary/secondary/error/tertiary), `lightGradient`, `darkGradient`.
- `columnState(string $status): array` — `columnConfig()[$status] ?? columnConfig()['todo']` (defensive fallback to todo).
- `emptyStateFlags(string $column, bool $showAllDone, bool $showArchived, string $search, array $doneTotalCount): array` — `['windowActive','olderExist','archiveEmpty']`; `windowActive` only when done + neither toggle + no search; `olderExist` flags the 45-day "show older" nudge; `archiveEmpty` flags the dedicated archive empty-state.
- `defaultTaskFormTab(array $tabs, ViewErrorBag $errors): string` — returns the first tab whose `errors` list has a validation error, else `tabs[0]['key'] ?? 'content'`. This is how the modal re-opens on the tab that failed validation.
- `taskFormTabs(): array` — 6 tabs, each `['key','label','icon','errors'=>[...]]`; `reply` and `history` additionally carry `'description'` (rendered as a native `title=` tooltip on its tab button). Tabs, in display order: `content` (جزئیات وظیفه, `edit_note` — title/description/deadline/assignee/project/priority), `followup` (اقدام و پیگیری, `task_alt` — checklist + attachments + `state`/تعیین‌تکلیف, merged 2026-08-28 so the receiver has one "do the work + prove it + mark disposition" tab), `reply` (نظرات, `forum` — renamed from گفتگوی وظیفه for naming consistency with Project's activity tab), `info` (اطلاعات تکمیلی, `list_alt` — classification fields + action-source fields + labels, merged so every non-actionable reference field about the task lives in one place), `meta` (دیتای سفارشی, `sell` — universal per-task meta, schema mode vs free mode, see §19; unconditional — present with or without a linked project), `history` (تاریخچه, `history` — see §16). Badge counts and error-routing were re-derived for the new tab boundaries; `checklist`/`classification`/`action` are retired tab keys — don't reintroduce them.
- `tabBadgeCounts(EloquentCollection $comments): array` — now returns only `['reply' => comments count]`; takes `$this->taskComments` (the نظرات-only split, §16), NOT the raw `editingTask->replies` count, so the badge isn't inflated by mixed-in `history`-type system entries (status/deadline/priority/label/project changes). The `followup`/`info` tab badges moved to the client (see `taskForm.js` below) since they need to react instantly to Alpine-side array edits (checklist/attachments/labels/collaborators) without a round trip, matching the pre-existing `actionBadge` pattern. `checklistBadge()` was removed from the presenter — it combined checklist+labels for a tab that no longer exists.
- `columnPagerMeta(int $taskCount, int $perPage, int $currentPage = 1): array` — `['lastPage','isFirstPage','isLastPage']`.
- `replyAttachmentMeta(array $file): array` — `['url' => Reply::resolvePublicAssetUrl($file['path'] ?? null), 'isImage' => str_starts_with($file['mime'] ?? '', 'image/')]`.
- `deadlineFilterOptions(array $dfCounts): array` — 3 options (overdue/today/week) each with a `count`.
- `toolbarSurface(): string` / `toolbarButtonClass(): string` / `utilityClass(bool $active): string` / `columnButtonBase(): string` / `columnButtonIcon(): string` — the toolbar/column CSS class strings (surface card, toolbar button, active+inactive utility, column header/pager buttons). Moved here from the tools/column blade `@php` blocks so blades carry no class-string definitions; `utilityClass(true/false)` is the active/inactive pair.
- `cardMeta(array $task, bool $isPersonalBoard, array $departmentOptions): array` — **the single card data-bag, 28 keys**: `urgency`, `colState`, `checklist`, `checklistTotal`, `checklistDone`, `attachments`, `attachmentsCount`, `stateChip`, `responsibleUser`, `departmentLabel`, `unit`, `section`, `projectLabel`, `projectHasLink`, `collaboratorUsers`, `canCyclePriority`, `labelFilterMethod`, `hasDeadline`, `deadlineTitle`, `isPending`, `isPendingApproval`, `canApprove`, `isUrgent`, `metaChips`, `actionSourceChip`, `lastTouchedBy`, `isFavoriteExpression`, `showTaskExpression`. `actionSourceChip` (2026-08-30) — `['label','source','domain']` or `null` when both `detail.action_source`/`action_source_domain` are blank; `label` prefers `source`, falls back to `domain`. Requires both fields to actually be present in the eager-loaded `detail:` column list — they were silently absent from both `TaskBoard\Main::$relationsToLoad` and `Project\Kanban::KANBAN_RELATIONS`'s hand-picked column whitelists until this fix (a real bug: the chip's PHP logic was correct from day one, but the underlying columns were never selected, so it never had data to render). The four org-card keys: `unit`/`section` (passed through from `detail.unit`/`detail.section` for the department-popover sub-lines), `projectLabel` (free-text `detail.project` ALWAYS overrides the linked `project.name` when filled; falls back to `project.name` only when the free text is empty), `projectHasLink` (truthy iff `project_id` is set — drives whether the project chip is a `wire:navigate` link to the project workspace or a non-clickable dashed chip). The v2 keys (§19): `isPendingApproval` (done + no `approved_at` + project `requires_approval`), `canApprove` (pending && project owner), `metaChips` (`[{key,label,value}]`, label falls back to raw key, scalar non-empty values only), `lastTouchedBy` (`['user_name','ago']` from the board-spliced `last_touched`, or null). Two keys are **JS expression strings emitted into Alpine bindings**: `isFavoriteExpression` = `'isFavorite(' . $taskId . ')'` on the personal board, `'false'` on Project; `showTaskExpression` = `'!showFavoritesOnly || isFavorite(' . $taskId . ')'` on the personal board, `'true'` on Project. `labelFilterMethod` = `'addLabelFilter'` on the personal board, `'addKanbanLabelFilter'` on Project — the card's label chip calls `$wire[labelFilterMethod]($label)` so the same blade serves both hosts.

Rule: **`cardMeta` is the only thing `card.blade.php` consumes.** It is computed per-card in the blade (a plain function call, not cached) from the already-hydrated task array, so it costs zero queries. New card-visible fields get added here first, then surfaced in `card.blade.php`.

## 5. Actions

All Actions live under `app/Livewire/Dashboard/TaskBoard/Actions/` (board-action wrappers) and `app/Services/ProjectTask/` (core services). Each is a single-purpose class with an `execute()` method. **Every UI-extra condition is re-checked inside `execute()`** (the line-166 rule from `livewirePattern.md`): the blade's `@if` gating is defense-in-depth, not a substitute for the Action guard.

Board Actions (guard → effect):
- `ArchiveTaskAction::execute(int $taskId): bool` — guards `!can_delete || ticket_id || status !== 'done' || archived_at !== null`; sets `archived_at = now()`.
- `UnarchiveTaskAction::execute(int $taskId): bool` — guards `!can_delete || archived_at === null`; sets `archived_at = null`.
- `ArchiveStaleDoneTasks` (`app/Console/Commands/`, `tasks:archive-stale-done`, scheduled daily 02:30 in `routes/console.php`) — the auto-archive sweep: approved done tasks (`whereNotNull('approved_at')` — pending-approval tasks are never archived, §19.3) older than the project's `auto_archive_days` setting (default 45) get `archived_at` stamped. `chunkById(200)` with `project:id,settings` eager-loaded, threshold-grouped `whereIn` bulk updates executed **inside** the chunk callback (bounded memory + bounded WHERE IN — both the ID accumulation and the update statement stay chunk-sized; reviewer-caught deviation from the plan's verbatim body, which collected all IDs first); raw `DB::table` updates skip the updating-hook invariant, which holds trivially here since only already-done rows are touched. One `StateService::flush()` when anything was archived. Anchor is `approved_at`, not `updated_at` — later touches don't reset the clock. Orthogonal to the done-column 45-day **visibility** window (`doneWindowScope` hides, never archives). Tests: `ConsoleCommandsTest` (stale/fresh/override/default-45/pending-excluded/project-less).
- `AssignTaskAction::execute(int $taskId, ?int $userId): ?Task` — guards `!can_change_status || ticket_id`; updates `assigned_to`; sends `Notification::sendToDatabase()` to the assignee if `$userId && $userId !== auth()->id()`.
- `UndoTaskAssignmentAction::execute(int $taskId): bool` — guards `!is_delegator || status === 'done' || ticket_id`; sets `assigned_to = null`.
- `DeleteTaskAction::execute(int $taskId): bool` — guards `!can_delete || ticket_id`; soft-deletes.
- `ForceDeleteTaskAction::execute(Task $task): bool|null` — `$task->forceDelete()`.
- `BulkDeleteTasksAction::execute(array $taskIds): int` — filters `can_delete && !ticket_id`; `Task::whereIn(...)->delete()`; `DB::afterCommit(fn() => StateService::flush())`.
- `BulkAssignTasksAction::execute(array $taskIds, ?int $userId): int` — filters `can_change_status && !ticket_id`; `DB::transaction` per-task update; `DB::afterCommit` flush.
- `BulkMoveTasksAction::execute(array $taskIds, string $status): array` — returns `['moved'=>int,'skipped'=>int]`; `tryFrom` guard; partitions out done-without-state (skipped); sets `archived_at => null` when `$status !== Done` (bulk query updates skip model events — the one bypass of the updating-hook invariant, §10); `DB::transaction`.
- `ExportTasksAction::execute(int $userId): StreamedResponse` — **all** of the user's tasks (`assigned_to` OR `user_id = $userId`; ignores tab/search); eager-loads creator/assignee/project/detail.department/detail.responsibleUser; collaborator names batch-resolved from `TaskDetail.collaborators` via one `User::whereKey` (no N+1); streamed `.xlsx` via OpenSpout — `lazyById('id')` streaming, bold header, 23 columns incl. all detail fields + checklist progress + attachment count; filename `tasks-Y-m-d.xlsx`. `userId` is supplied by the Livewire caller (`auth()->id()`); the action trusts the caller for auth.
- `CyclePriorityAction::execute(int $taskId): ?Task` — `ORDER = [Low, Medium, High, Urgent]`; guards `!can_change_status || ticket_id || is_archived`; `DB::transaction`; `next = ORDER[(currentIndex+1) % count]`; updates `priority` + `rank` (via `rankForPriority`). **`null` is deliberately excluded from `ORDER`** — cycling forward from Urgent wraps to Low, not to `null`, so the priority chip (gated `@if($chip)`) stays permanently reachable once any priority is set; an unset task enters the cycle at Low via the edit modal (accepted scope boundary).

Core services:
- `CreateTaskAction::execute(...)` — `validate()` + `guardProjectVisibility()` (one `Project::visibleTo(...)->first(['id','settings'])` — visibility AND settings in a single row read) + `resolveDeadline()` + **`ResolvesTaskDeadline::guardProjectDeadline()`** (the shared `app/Traits/` guard — rejection past the project `deadline` setting → `ValidationException` on `form.deadline`, §19.4; both write Actions call it, trait cataloged in `traitPattern.md` §2.5); `DB::transaction`; `Task::create` with `status = Todo` and `rank = rankForPriority(..., $form->priority)`; `detail()->create($form->detailAttributes() + storeAttachments(...))`. A new unprioritized task lands below existing prioritized ones (behavior change from the old `nextRank()` always-top).
- `ApproveTaskAction::execute(Task, User): bool` — the approval lifecycle's single writer (§19.2); lives here, NOT in `TaskBoard/Actions/`, because three callers (user modal, Kanban, admin record action) DI it.
- `UpdateTaskAction::execute(...)` — `abort_if(!can_change_status || ticket_id)`; `validate()`; `guardProjectVisibility()` (returns the `Project` row — one `first(['id','settings'])`, the create path's shape) + **`ResolvesTaskDeadline::guardProjectDeadline()`** (update-path cap enforcement, §19.4); **stale guard** via `guardTaskNotStale()`/`guardDetailNotStale()` (`lockForUpdate` timestamp compare against `taskUpdatedAt`/`detailUpdatedAt`); branches on `$bucketChanged`/`$priorityChanged` → `rankForPriority(new bucket, new priority[, excludeId: $task->id])`; neither → `rank` unchanged (zero extra query, the common case); `updateOrCreate` detail with `[...existingAttachments, ...storeAttachments(...)]`.
- `ReorderTaskAction::execute(...)` — `abort_unless can_change_status`; `status = tryFrom(...)`; done-without-state guard; `DB::transaction`; siblings `inRankColumn` `lockForUpdate` `orderByRaw('rank IS NULL, rank')` reject self; `before`/`after`; `rebalanceInsert()` fallback; updates `status` + `rank`.
- `UpdateTaskStatusAction::execute(...)` — `tryFrom` guard; `!can_change_status` → false; done-without-state → false; same-status → true; `DB::transaction` update `status` + `nextRank()`.
- `RankGenerator` — `ALPHABET = '0123456789abcdefghijklmnopqrstuvwxyz'`, `MAX_LENGTH = 40`; `between(?before, ?after)` throws `InvalidArgumentException`/`RuntimeException` if `before >= after` or length exceeds 40; `rebalanceInsert(array $orderedIds, int $insertIndex): array` returns `['assignments' => [id => rank], 'insertRank' => string]` (pure sequence math, DB-agnostic — the shared safety net for both `rankForPriority` and `ReorderTaskAction::rebalance()`); `sequence(count)`, `midpoint()`, `digitAt()`.

## 6. `ManagesTaskModal` trait — shared with Project

`app/Traits/ManagesTaskModal.php` — the PHP-trait+shared-blade-folder pattern (see `livewirePattern.md` "Sharing a whole modal/feature across independently-rendered Livewire components"). Shared by `TaskBoard\Main` and `Project\Main`.

Properties: `TaskForm $form`, `ReplyForm $taskReplyForm`, `#[Locked] ?int $editingTaskId`, `array $staffMembers`/`$departmentOptions`, `bool $isModalOpen`/`$isEditMode`/`$isReadOnly`, `string $newMetaKey`/`$newMetaValue` (the free-mode meta add-row state, §19.3).

Methods:
- `mountManagesTaskModal()` — seeds `$staffMembers` via `User::getCachedActiveOptions()->except(auth()->id())`; `$departmentOptions` via `Department::getCachedOptions()`.

## 9. JS/Blade interplay rules

1. **`$wire.set('form.x', value, false)`** — the deferred (non-live) set is used for the three Form-object arrays (`labels`/`checklist`/`existingAttachments`) that have a client-side Alpine-reactive mirror seeded once per modal-open via `syncFormArrays()`. The `false` third arg skips `queueUpdate`/the network round trip; the mutation is already in `ephemeral` (the reactive Proxy over the same underlying object) and is picked up on whatever real Livewire request comes next (the final submit, or an earlier `.live` field's round trip). Server-side `#[Validate]` rules are the real enforcement; the client mirrors the same caps (`MAX_LABELS = 10`, `Set`-backed strict-equality dedupe) purely for instant UI feedback. **Never use the deferred set to skip validation, and never introduce it for a value with no genuine per-click UI feedback to gain.** (Full rule in `livewirePattern.md`.)
2. **`Object.defineProperties` instead of `...taskFormMixin()`** — `taskFormMixin()` has getters (`actionBadge` reads `this.$wire.form.attachments`); spreading it into a host literal evaluates the getter immediately with `this` bound to the bare mixin (no `$wire`) and **throws `TypeError` synchronously, killing the entire `x-data` init** — every directive on the page goes dead. Fix: `return Object.defineProperties(host, Object.getOwnPropertyDescriptors(taskFormMixin()))` as the last step after building the host literal. (Full rule in `livewirePattern.md` "object spread evaluates getters immediately".)
3. **`x-ui.hover-popover`** — the first true-hover primitive in the app (teleported, `x-teleport="body"`, `position: fixed`, rect from `$refs.trigger.getBoundingClientRect()`). Used on the card for attachment-count/checklist-ring/responsible+department chips. `@mouseenter`/`@mouseleave`/`@click.away` with a `closeTimer` to bridge the trigger/body gap; tap-to-open for touch. **Inside a `truncate`/`overflow-hidden` ancestor the popover is clipped** — narrow the `truncate` to just the overflowing segment (the `#id • date` span) and keep popover-bearing badges as `shrink-0` siblings in a `min-w-0` non-truncating flex container. (Full rule in `livewirePattern.md`.)
4. **`--urgency` CSS scalar** — the card emits `style="--urgency:{{score}}"` (0..1); `dashboard.css` `.taskboard-card--urgent::before` is the single colored rail: `background: color-mix(in srgb, var(--md-sys-color-primary) calc((1 - var(--urgency,0)) * 100%), var(--md-sys-color-error))` — a theme-anchored primary→error ramp (chosen over `--tool-gold-*` which goes muddy on Ember's orange). Pills stay neutral so the rail is the only colored element. NOT cached (`now()`-relative).
5. **`x-bind:class` with a PHP-emitted JS expression string** — `cardMeta`'s `isFavoriteExpression`/`showTaskExpression` are JS expression strings (e.g. `'!showFavoritesOnly || isFavorite(42)'`) rendered into `x-bind:class`/`x-show` attributes. This lets the same card blade serve both hosts (personal board gates on favorites; Project always `'true'`) without a blade `@if` branch.

`app/Models/Task.php` — uses `HasFactory`, `HasJalaliAdminLabels`, `HasMenuState`, `HasReplies`, `SoftDeletes`, `Prunable`, `HasPrunableStatus`, `CleansAttachedFiles`, `HasTaskActivityLog` (`app/Models/Concerns/HasTaskActivityLog.php` — see below). `MENU_STATE_EVENTS = ['created','updated','deleted','restored','forceDeleted']`.

An ordered walk is the correctness requirement — manual drag-reorder and priority are independent axes, so a column is not guaranteed tier-sorted, and a naive `MAX(rank WHERE tier>=x)`/`MIN(rank WHERE tier<x)` pair can pick a `$before` that sorts after `$after`, throwing on `between()`'s ordering invariant. `rebalanceInsert()` is the shared safety net.

Scopes: `scopeForUser`, `scopeInRankColumn`, `scopeStatus`. `prunable()` — `whereNull('project_id')` + `deleted_at <= now()-subDays()`; `prune()` calls `ForceDeleteTaskAction`.

`boot()`:
- `forceDeleting` — `deleteStoredFiles` on detail attachments, delete replies, `EventSyncService::purge`.
- **`updating` hook (the `archived_at ⇒ status=done` invariant)** — if `status` is dirty, leaving `done`, and `archived_at` is set, nulls `archived_at` in the same UPDATE. The shared-source lever: covers every `$task->update(...)` path including admin form save, which the Action classes can't see. The one bypass is `BulkMoveTasksAction`'s `Task::whereIn(...)->update(...)` (bulk query updates skip model events), so it explicitly sets `archived_at => null` when `$status !== Done`.
- `saved` hook (Task's own) — only clears `detail.project` when `project_id` becomes null. Activity logging and calendar sync moved out of this hook — see `HasTaskActivityLog` below.

**`HasTaskActivityLog` trait (`app/Models/Concerns/HasTaskActivityLog.php`), mixed into both `Task` and `TaskDetail`** — replaced the two models' near-identical hand-written `saved`-hook `if ($model->wasChanged('x')) {...}` chains with one shared, declarative implementation. Each model declares `public array $activityMap` (changed-field → `TaskActivityType`) and `public array $calendarTriggers` (fields whose change should re-dispatch `SyncTaskCalendarEventJob`); the trait's single `saved` listener reads those two arrays, computes calendar-relevance the same way for both models, and — for genuinely changed+mapped fields — calls `ActivityLogger::logMappedChanges()`. `Task::$activityMap` covers `status`/`assigned_to`/`archived_at`/`deadline`/`priority`/`labels`/`project_id` (see §16); `TaskDetail::$activityMap` covers `collaborators`/`responsible_user_id`/`department_id`/`state`. `ActivityLogger::logMappedChanges()` batches every mapped field changed in one save into a **single** `Reply::insert()` (not one query per field), followed by one explicit `ModelCacheVersion::bump(Reply::class)` (raw inserts skip Eloquent's `saved` event, so the version bump — normally automatic per `modelPattern.md` — must be manual here; this is the documented "bulk/raw write ⇒ one manual bump()" rule, not a new pattern) and one heartbeat bump. Observable behavior (which fields log, what payload shape, when calendar sync fires) is unchanged from the pre-trait implementation — this was a pure duplication/query-count refactor, verified via the existing `TaskModelTest`/`TaskDetailModelTest` lifecycle-hook tests. **Real regression caught 2026-08-29, since fixed:** the raw `Reply::insert()` batch also silently skips `Reply::created`, which is `TaskNudge`'s (the "task assigned to you" / "task completed" bell) second trigger (`['class' => Reply::class, 'on' => ['created'], 'subject' => fn($r) => $r->repliable_type === Task::class ? $r->repliable : null]`, `app/Services/Menu/Notifications/TaskNudge.php`) — so the bell silently stopped reconciling for every status/assignment/collaborator/etc. change logged through the batch path. Fixed by `logMappedChanges()` explicitly dispatching `dispatch(new ReconcileNudge((new TaskNudge())->getKey(), Task::class, $repliable->id))->afterCommit()` once per batch (matching the exact call shape `NudgeService::register()`'s own Eloquent-event binding uses) — but **only when `$source instanceof TaskDetail`, not `Task`** (`if ($repliable instanceof Task && !($source instanceof Task))`). Reason: `TaskNudge::triggers()` already includes a plain `Task::class => ['updated']` trigger, which fires natively for every Task-field save — `logMappedChanges()` dispatching again for that same case would be a harmless but redundant second reconcile job (caught in review 2026-08-29). `TaskDetail` changes never touch the Task row at all, so the native `Task::updated` trigger never fires for them — that's the one case this explicit dispatch is load-bearing. Covered by `ActivityLoggerTest::test_task_driven_change_does_not_redundantly_dispatch_reconcile_nudge_from_log_mapped_changes` (isolates via `NudgeService::reset()` in setUp, since the native `TaskNudge` trigger's own Eloquent-event wiring is separately covered by `ReconcileNudgeTest`/`MenuServiceTest` and is order-dependent-flaky to assert on directly in an unrelated test file — a pre-existing test-infrastructure trait, not a production bug) and `..._when_task_detail_changes`. **Rule going forward: any future raw/bulk write on a model that another `MenuNudge`/`MenuEdge` triggers on must get the same explicit reconcile-dispatch treatment — raw writes never fire Eloquent events, so the trigger-binding in `NudgeService`/`EdgeService` silently never fires for them — but check whether a plain-model-event trigger on the SAME class already covers it before adding the dispatch, to avoid the redundant-job version of this same mistake.**

Accessors: `canChangeStatus`/`canDelete`/`isDelegator` now delegate to `App\Support\TaskAccessPolicy` (`canChangeStatus`/`canDelete`/`canUndoAssignment` respectively — same logic, just centralized; see §15's `TaskPolicy` note, now resolved) instead of inlining `auth()->id()` comparisons. `createdFormatted`/`deadlineFormatted` (`toJalali`, `shouldCache`), `delegatorName`/`assigneeName` (`shouldCache`), `isArchived` (bool), `status` (set: enum→value).

**`progressPercent(): int` — the single source for task progress.** Rule: done → 100; empty checklist → todo 0 / in-progress 50 / pending 75; `totalWeight <= 0` → `done/count*100`; else sum of weights of done items. **Checklist never triggers status** (Jira/Asana/Monday rule) — only manual "done" sets 100%.

**`urgencyState(): array` — the ambient-urgency single source.** Returns `['score'=>round(2), 'kind', 'label']`. `done`/`pending` short-circuit to zero (never double-signal). Deadline: overdue → 1.0 / `overdue` / `n روز تأخیر`; ≤3d → 0.7 / `due` / `امروز`·`فردا`·`n روز دیگر`. **v2 project branches (§19.5, between deadline and priority floor, inside a `relationLoaded('project') && $this->project` guard):** SLA breach → 0.9 / `sla` / `نقض SLA`; task deadline past the project deadline → 0.5 / `project-deadline-exceeded` / `فراتر از مهلت پروژه`. Priority floor (after deadline, before idle; monotonic `max` semantics, never reduces): Urgent → 0.85, High → 0.55, Medium/Low → 0.0 — deliberately does NOT set `kind`/`label` so a priority-only floor doesn't relabel the deadline badge. Idle: `updated_at` ≥7d → 0.45 / `idle` / `چند روز بی‌تغیر`, ≥3d → 0.22 / `idle`. `overdue` wins over `idle` (max score; `kind ??=`/`label ??=` preserve the deadline verdict). NOT cached (`now()`-relative). Zero new queries: `updated_at` was added to `$columnsToSelect`; the v2 branches read `project.settings` off the eager-load select.

`app/Models/TaskDetail.php` — `$fillable`: `task_id`/`department_id`/`unit`/`section`/`project`/`scheme`/`action_source_domain`/`action_source`/`collaborators`/`responsible_user_id`/`state`/`attachments`/`checklist`/`meta` (§19.3). ## 15. Gotchas

- **`archived_at ⇒ status=done` invariant is in `Task::boot()` `updating` hook, not the Actions** — covers admin form save too. The only bypass is `BulkMoveTasksAction`'s bulk query update, which explicitly sets `archived_at => null` when leaving done.
- **`null` priority excluded from `CyclePriorityAction::ORDER`** — cycling forward from Urgent wraps to Low, not `null`; the chip (gated `@if($chip)`) never vanishes. An unset task enters the cycle via the edit modal.
- **`rankForPriority` is an ordered walk, not `MAX/MIN`-by-tier** — a column is not tier-sorted (drag and priority are independent axes); a naive scalar query can throw on `between()`'s ordering invariant.
- **`progressPercent` is the single source** — checklist never triggers status (Jira/Asana/Monday rule). Only manual "done" → 100.
- **`urgencyState` is NOT cached** (`now()`-relative), unlike the formatted-label accessors which use `shouldCache()`. `updated_at` was added to `$columnsToSelect` so the idle calc has the timestamp — the only query-side change urgency needed.
- **Carbon `startOf*()` mutates in place and returns `$this`** — calling `$this->deadline->startOfDay()` on a cast model attribute silently truncates it to midnight for every later read of that attribute in the same model instance (raw DB string is untouched, so nothing persists corrupted — in-memory aliasing only). Always `$this->deadline->copy()->startOfDay()`. Same class of bug as the `now()->diffInHours($past)` signed-negative gotcha (§19.5): Carbon's fluent API looks immutable and isn't.
- **`urgencyState()`/`progressPercent()` are split into named `apply*`/`calculate*` methods** (deadline → project → priority floor → idle, one concern each) — same output as the old 60-line inline closures; keep new urgency branches as their own `apply*` method rather than growing one closure.
- **`cardMeta` returns two JS expression strings** (`isFavoriteExpression`/`showTaskExpression`) rendered into Alpine `x-bind:class`/`x-show` — the same card blade serves both hosts without a blade `@if` branch.
- **`labelFilterMethod` is a method-name string** from `cardMeta` — `addLabelFilter` on the personal board, `addKanbanLabelFilter` on Project. The card's label chip calls `$wire[labelFilterMethod]($label)`.
- **`Object.defineProperties` not `...taskFormMixin()`** — spreading the mixin evaluates getters immediately (one reads `this.$wire`) and throws, killing the whole `x-data` init. (See `livewirePattern.md`.)
- **`$wire.set('form.x', value, false)`** only for Form-object arrays with a client-side Alpine mirror seeded via `syncFormArrays()` and still covered by server-side `#[Validate]` — never to skip validation.
- **`x-ui.hover-popover` inside `truncate`/`overflow-hidden` is clipped** — narrow the `truncate` to the overflowing segment; keep popover-bearing badges as `shrink-0` siblings.
- **`ManagesTaskModal::editingTask` was widened to collaborators** (so they can open the modal to reply) but `editTask`/`viewTask` were NOT widened — collaborators can reply, not edit.
- **`HasTaskActivityLog`'s activity-logging branch requires `!wasRecentlyCreated`** (calendar-sync fires on create too, activity logging does not) — initial creation-time values never spam the activity feed.
- **`department_id`/`state` never dispatch calendar sync** — a department has no date/attendee semantics.
- **`BulkMoveTasksAction` returns `['moved','skipped']`** (changed from `int`) — partial bulk-move reports skipped count.
- **`TaskAccessPolicy` centralizes ownership checks (§13), but admin (`TaskResource`) is intentionally not gated by it** — its coarse permission-based access is unchanged by design.
- **Closures are illegal inside `#[Validate]` attributes** — PHP attributes only accept constant expressions, so `#[Validate(['meta' => ['array', function...]])]` is a *parse-fatal* ("Constant expression contains invalid operations"), not a runtime skip. Any rule needing a closure goes in the Form's `rules()` method, which Livewire **merges** with the `#[Validate]` attributes (`HandlesValidation::getRules()` → `array_merge(rulesFromComponent, rulesFromAttributes)` — it does NOT override them); rule *objects* (`new Enum(...)`) remain legal in attributes. Found via `php -l` after a hand-edit consolidated a `rules()` closure into an attribute.
- **`tests/` is gitignored** — don't `git add -f` test files.

## 16. Task-level chronology — the `history` tab and the 4 extra activity types

Extends the existing `TaskActivityType`/`ActivityLogger`/`Renderers` machinery (see `app/Services/servicePattern.md` §3 — "adding a ninth activity type means adding one Renderer class and one array entry, nothing else changes") with 4 more types, and closes a real display gap for standalone (no-project) tasks.

- **The gap this closes:** the `saved`-hook activity logging (now `HasTaskActivityLog`, §10) already wrote `StatusChange`/`Assignment`/`Archive`/etc. system entries for every task, project or not — but the only reader, `ActivityLogger::feedFor(Project $project)`, is Project-scoped. A standalone task's system entries were written to the DB and never shown anywhere; TaskBoard's own `reply-row.blade.php` only ever rendered comments. This module adds the missing reader, scoped to one task.
- **4 new `TaskActivityType` cases + Renderers** (`app/Enums/TaskActivityType.php`, `app/Services/ProjectTask/Renderers/`): `DeadlineChange` (`event`), `PriorityChange` (`flag`), `LabelChange` (`label`, added/removed diff — same shape as the existing collaborator diff), `ProjectChange` (`drive_file_move`). Logged via `Task::$activityMap` (§10) alongside the existing 3.
- **Deliberately NOT logged:** `rank` (drag-order, not history), raw `title`/`description` edits (free-text diffs are noise with no diff-viewer), per-item `checklist` toggles (the checklist progress ring already shows live state — logging every checkbox would flood the feed), direct `task_details.attachments` column edits (already covered via the comment/attachment flow).
- **`ManagesTaskModal::taskComments()` / `taskHistory()`** (`app/Traits/ManagesTaskModal.php`) — both split the already-eager-loaded `editingTask->replies` collection in PHP (zero extra queries): `taskComments` keeps `Comment`/`Attachment` types for the نظرات tab, `taskHistory` takes everything else and renders each via `ActivityLogger::render()` for the تاریخچه tab. This intentionally mirrors Jira's own Comments-vs-History split, not a Fateh invention.
- **`history` tab (`TaskBoardPresenter::taskFormTabs()`, last tab) is gated to standalone tasks only** — `form.blade.php` skips it (`@continue`) when `!$editingTaskId || $task->project_id !== null`. A task that belongs to a project keeps its chronology in that project's own "فعالیت‌ها و نظرات" tab (which already aggregates every task in the project via `ActivityLogger::feedFor()`) — the two views are never shown redundantly for the same task. **This tab is TaskBoard-only in effect, even though `taskFormTabs()`/the modal are shared with `Project\Main`** — Project's own task-edit modal simply never satisfies the gate, since every task it opens has a `project_id`.
- **Rendering** reuses the exact visual shape `project/activity.blade.php` already established for system (non-comment) entries — a centered pill (`icon` + `body`) with a relative timestamp below, `<x-ui.empty icon="timeline">` for the empty state — not a new visual language.

Docs: `taskboard/legend.blade.php` (notes tab) and `filament/resources/task/guide/user.blade.php` both mention the extended activity coverage and the project-vs-standalone split. Tests: `TaskBoardTest` (§ activity log) covers each new `wasChanged` branch, the `taskComments`/`taskHistory` split, and the tab-visibility gate.

## 17. "Turn into Project" level-up tool — deferred creation, no orphan risk

Lives in `ManagesTaskModal` (shared by `TaskBoard\Main` and `Project\Main` — a Livewire-component-behavior trait per `traitPattern.md` §2.1, not a Service, since it needs `$this->form`/`$this->dispatch()`), not either module's own `Main.php` — a real bug (2026-08-29) shipped when it was first added directly to `TaskBoard\Main` only: `Project\Main` renders the exact same `taskboard/form.blade.php` partial via the trait, so opening its own create-task modal with no active project (`form.projectId` null) crashed on `Undefined variable $showLevelUpForm`. **Rule: any new state/method added to the shared task-modal blade goes in `ManagesTaskModal`, never in `TaskBoard\Main` or `Project\Main` directly — grep both trait consumers before assuming one component "owns" the shared partial.**

**Creation is deferred to the task's own save transaction — never on button click.** `toggleLevelUpForm()`/`createProjectFromTask()` only validate the name and stash it on the *Task* form (`TaskForm::$pendingProjectName`/`$pendingProjectMemberIds`/`$pendingProjectDepartments` — transient, not persisted as task columns). No `Project` row exists yet. `CreateTaskAction`/`UpdateTaskAction` resolve `$projectId = $form->projectId ?: $this->resolvePendingProject($form)` inside their own `DB::transaction()`, calling `CreateProjectAction::create()` (the plain-scalar sibling of `execute(ProjectForm $form)`, added alongside this fix so both the Project-module form flow and this scalar-args flow share one creation body) only at that point. **This was a real bug catch, not a preemptive design**: the original button-click-creates-immediately version left a genuine orphan `Project` row behind whenever the user closed the modal without saving the task — no save → no project, by construction, is the fix, not a cleanup-on-cancel patch (which can't catch every dismiss path: browser refresh, navigate-away, etc.). `cancelPendingProject()` clears the stash; `populateFormFromTask()` explicitly resets the three pending fields too, so a stash from an abandoned create session can never leak into an unrelated edit session on the same component instance. Tests: `TaskBoardTest`/`ProjectTest` (`test_create_project_from_task_stashes...`, `test_closing_the_modal_after_stashing_a_pending_project_leaves_no_orphan_project`, `test_saving_a_task_with_a_pending_project_creates_and_links_it`, `test_stashing_a_pending_project_from_the_project_module_modal_creates_no_orphan_row`).

## 18a. Three findings from a 2026-08-29 review pass — validated, fixed

- **`DuplicateTaskAction` was lossy.** It copied `title`/`description`/`labels`/`priority`/`project`/department fields but silently dropped checklist item `weight` (mapping each item to `['text','done']` only — with no `weight` key, `Task::progressPercent()`'s `$item['weight'] ?? 0` defaults every item to 0, so a duplicated weighted checklist silently becomes equal-weighted) and never copied `collaborators`/`responsibleUserId` at all. Fixed: the checklist map now carries `weight` through unchanged, and `collaborators`/`responsibleUserId` are copied from the source `TaskDetail`. `state` (resolution/disposition) is deliberately NOT copied — a duplicate is a fresh, unresolved task, carrying over the source's resolution would be wrong. Tests: `TaskBoardTest::test_duplicate_task_preserves_checklist_weights_instead_of_silently_unweighting_them`, `..._copies_collaborators_and_responsible_user`.
- **`EventSyncService::sync()` shared calendar events with inactive users.** Its recipient query (`User::whereIn('id', $candidateIds)`) had no `->active()` scope, unlike every `MenuNudge`'s own recipient query elsewhere in `App\Services\Menu\Notifications\*`. Fixed: `User::active()->whereIn('id', $candidateIds)`. Test: `EventSyncServiceTest::test_sync_excludes_an_inactive_assignee_or_collaborator_from_shares`.
- **Soft-deleting a task left its calendar `Event`/`EventShare` live.** `EventSyncService::purge()` was wired only to `Task::forceDeleting` — a plain `delete()` (soft) never purged it, and a project-linked task never reaches the standalone-only `prunable()` scope, so the ghost event could linger indefinitely (not just briefly, until force-delete/prune). Fixed: added a `Task::deleting` hook that purges when `!$task->isForceDeleting()` (guards against a redundant-but-harmless double-purge on an actual force-delete, since `forceDelete()` fires both `deleting` and `forceDeleting`), and a `Task::restored` hook that re-`sync()`s so a restored task with a live deadline gets its calendar entry back immediately rather than waiting for its next unrelated save. Tests: `TaskModelTest::test_soft_deleting_a_task_purges_its_calendar_event`, `..._force_deleting_a_task_does_not_double_purge_in_a_way_that_errors`, `..._restoring_a_task_re_syncs_its_calendar_event`.

**Findings from the same pass that were checked and did NOT hold up** (kept here so they aren't re-raised without new evidence): `ForceDeleteProjectAction` "leaving stale calendar events" — false, `Event`/`EventShare` are keyed by task id and built from the task's own deadline/assignee/collaborators, none of which unlinking `project_id` touches; nothing becomes stale. `TasksRelationManager`'s progress column being N+1 — false, `ReportingService::progressPercent()` is exactly the thin `$task->progress_percent` wrapper it should be, and the RM's `modifyQueryUsing` already eager-loads `detail`. `Project.departments` "not validated" as a departments-specific gap — narrower than claimed: `ProjectForm`'s `exists:departments,code` rule validates it at save time same as `member_ids`' `filterExistingUserIds()`; the real (unfixed, by choice) gap is symmetric — neither field gets cleaned up if the referenced department/user is deleted *after* a project already references it, and `filterExistingUserIds()` doesn't check `active` either, only existence.

## 19. Project settings + approval lifecycle + universal meta + deadline cap (2026-08-29 v2 plan)

Four coupled features, one migration pair. Single source for the v2 spec details; the inline sections above carry the per-location facts.

### 19.1 Project `settings` — 4 keys, one accessor
`Project::setting(string $key)` reads the `settings` JSON column (null-safe). Exactly 4 keys, nothing else nested in: `requires_approval` (bool — gates the approval lifecycle), `sla` (int hours), `deadline` (date — the cap), `custom_schema` (array `key => ['label' => …, …]` — labels for the meta tab/chips). `ProjectSettings::bag()` (`app/Services/ProjectTask/ProjectSettings.php`) normalizes form input into the persisted bag. Persisted from the user panel (`ProjectForm` + Create/Update actions) AND admin (`ProjectFormPresenter::settings()` incl. the deadline field) — full parity. Every `settings` change (either panel) writes a `settings_change` row into the project activity feed via `Project::logSettingsChangesIfNeeded()` (2026-08-30, the `logMembershipChangesIfNeeded` pattern; `SettingsChangeRenderer` — the 15th renderer, after §19.3's `MetaChangeRenderer` — lists the changed keys with Persian labels, `TaskActivityType::SettingsChange`).

### 19.2 Approval lifecycle
- **State:** `tasks.approved_at`/`approved_by` (nullable, migration `2026_08_29_000003`); `Task::approvedBy()` BelongsTo; **`isPendingApproval()` is a PLAIN method, deliberately NEVER in `$appends`** — appended it would serialize into every toArray() and leak pending state into caches/exports; all consumers call it explicitly.
- **Semantics:** only a task whose project sets `requires_approval` enters the pending state — `isPendingApproval() = status done && approved_at null && project.requires_approval`. Everything else is "بدون نیاز به تأیید". Setting `requires_approval` off later does NOT retro-unpend (existing rows keep approved_at stamped; pending rows resolve because the gate check goes false).
- **`ApproveTaskAction::execute(Task, User): bool`** (`app/Services/ProjectTask/` — Service not TaskBoard/Action, multi-caller: user modal + Kanban + admin Filament record action all DI it). Re-checks `canApprove` + `isPendingApproval` inside `execute()` (the line-166 rule); stamps `approved_at`/`approved_by`, logs `TaskActivityType::Approval` via the existing `HasTaskActivityLog`/`ActivityLogger` machinery (`ApprovalRenderer` is the 13th renderer; `Task::$activityMap` has `approved_at => Approval`).
- **`TaskAccessPolicy::canApprove(task, user)`** — project owner only (mirrors `canChangeStatus`-style centralization, §13).
- **Wiring:** `ManagesTaskModal::approveTask()` (user modal), `Project\Kanban::approveTask()` (thin delegate — same Service), `TaskResource::table()` record action `approve` (first position, visible only when pending + `canApprove`).
- **Surfaces:** card pending-approval chip (faded card + warning chip + approve button, popover shows requestor/age), admin infolist `approval` entry, `TaskApprovalNudge` (bell to the project owner; `getKey 'tasks-controller:approval-nudge'`; escalation prefix in `title()`: `''` → `'یادآوری: '` at >24h → `'⏰ فوری: '` at >48h, anchored on `updated_at`), `TasksPendingApproval` indicator (`app/Services/Menu/Indicators/`, bell-only key `'tasks-pending-approval'`, registered in `StateService`).
- **Legacy backfill:** `taskboard:backfill-legacy-projects` stamps already-done tasks `approved_at/approved_by` (project owner) when linking, so pre-feature done rows never show as pending.

### 19.3 Universal per-task `meta`
- **State:** `task_details.meta` JSON (migration `2026_08_29_000002`); `TaskDetail` fillable + array cast; universal — every task, project or not.
- **Two render modes in `meta-fields.blade.php`** (the `meta` tab body): **schema mode** when the linked project defines `custom_schema` (labeled inputs keyed to schema, one `#[Computed] customSchema()` read per modal-open — plan §E's accepted one-query-per-open, NOT visibleTo-scoped); **free mode** otherwise (add/remove key-value rows via `ManagesTaskModal::addMetaKey()/removeMetaKey()` + `newMetaKey`/`newMetaValue` props).
- **Key safety layering — the load-bearing invariant:** every write path enforces `^[a-z0-9_]+$` on keys (`TaskForm` `#[Validate]` closure, `addMetaKey()`, both `ProjectForm` customSchema guards, admin `TaskFormPresenter::metaKeyPattern()` KeyValue rule). Because quotes/dots can never be stored, the `wire:click="removeMetaKey('{{ $key }}')"` / `wire:model="form.meta.{{ $key }}"` interpolation in the blade is safe with no view-level escaping.
- **Surfaces:** card `metaChips` (label falls back to raw key; `database` Material icon; native `title=` — no hover-popover per the scope-UI-complexity rule), Report tab expanded row `meta_chips` (`ReportingService::presentRow()`, labels via the eager-loaded `project:id,name,settings`), admin form `meta` KeyValue + infolist `meta` badges + table `meta` column (toggleable, hidden).
- **N+1:** zero added per-card queries — `meta` rides the existing `detail` eager-load; schema labels ride the `project.settings` select.
- **Activity chain:** `meta` is mapped in `TaskDetail::$activityMap` → `TaskActivityType::MetaChange` (2026-08-30), so every add/remove/update of a key writes a `meta_change` row into the task's activity tab through the standard `HasTaskActivityLog` → `logMappedChanges` path (and dispatches the usual `ReconcileNudge`); `ActivityLogger::resolvePayload('meta')` diffs by key into `added`/`removed`/`changed` key lists (no-op saves log nothing), `MetaChangeRenderer` renders them (icon `database`, matching the chip icon).

### 19.4 Project deadline cap
- **`Project::deadlineCapExceeded(?Carbon $deadline): bool`** — THE single source for the comparison (null-safe both ways: no cap set or no task deadline → false). Three consumers, zero duplication: `ResolvesTaskDeadline::guardProjectDeadline(?Carbon, ?Project)` — the guard shared by both write Actions (moved out of `CreateTaskAction` when `UpdateTaskAction` gained the call 2026-08-30 — the cap can no longer be dodged by editing a task into an over-cap deadline; `UpdateTaskAction::guardProjectVisibility()` was restructured to `Project::visibleTo(...)->first(['id','settings'])`, the create path's one-row shape, so visibility + settings still cost **zero added queries**); `Task::applyProjectUrgency()` (§19.5); and the admin Filament form — **`app/Rules/ProjectDeadlineCap`** (2026-08-30), passed to `PersianDateFieldService::make(carrierRule:)` from `TaskFormPresenter::deadlineDate()` so it fires on the hidden `deadline_date` carrier field for BOTH admin create and edit (the old page-level `CreateTask::mutateFormDataBeforeCreate` Halt+Notification duplicate was removed — it covered create only and gave a generic toast instead of the field-level error). The Jalali selects are UI-only; the carrier field's state is already Gregorian `Y-m-d` (`assemble()` converts), so `Carbon::parse` in the rule sees real dates. The rule's outer closure resolves the project via `$get('project_id') ?: $record?->project_id` with one `Project::find($id, ['id','settings'])`. Guard violations → `ValidationException` with message `resources/task/strings.validation.project_deadline_cap`; the Filament rule `$fail`s with the same key. The comparison treats the project deadline as running to **`endOfDay()`** — task deadlines are noon-anchored (`12:00:00`), the project deadline string parses to midnight, so same-day tasks must compare against 23:59:59, not 00:00:00 (else the deadline's own day falsely rejects/flags).
- **No clamping, ever:** shrinking a project's deadline never mutates existing task rows — already-saved over-cap tasks are only flagged by `urgencyState()['kind'] === 'project-deadline-exceeded'` (0.5 / `فراتر از مهلت پروژه`).
- **Remaining bypass gap (plan F5):** `BulkMoveTasksAction` only — it never changes deadlines, so its gap is approval routing (§19.2), not the cap. The admin-Filament cap half of F5 was closed 2026-08-30 by the `ProjectDeadlineCap` rule.
- **Tests:** `Rules/ProjectDeadlineCapTest` (7 cases — over-cap fails, cap-day passes, before-cap passes, no-cap project/null projectId/missing project/non-`Y-m-d` values pass) + `Filament/TaskResourceTest` create-reject / create-cap-day-pass / edit-reject cases. `fillForm` deliberately fills the hidden `deadline_date` carrier with the Gregorian `Y-m-d` that `assemble()` produces at runtime — `fillForm` disables state-update hooks, so the Jalali selects' `syncDate` can't be driven through it.
