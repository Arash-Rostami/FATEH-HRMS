# Channels Module Pattern Guide

Slack/Telegram-style **one-to-many broadcast channels**, fully isolated from the 1:1 `contacts` chat. One channel → many members → messages broadcast to all members. Built with Livewire v4.1 islands, Filament v5 admin, Laravel 12, PHP 8.2. MySQL 5.7-compatible baseline (production 8+).

This doc is the **single source of truth** for every file, contract, rule, and gotcha in the module. Read it before touching anything channel-related. The canonical **general** rules for `@island` scope/memoization, the `syncAttachments` upload-bridge, and the `lastIdForChannel` null-guard live in `app/Livewire/livewirePattern.md`; this doc covers the Channels-specific architecture, contracts, and the action-extraction / perf patterns specific to this module (with the concrete island instance retained in §3.1 as the lesson that motivated those general rules).

## 1. Stack & compatibility (verified)

- **Livewire `^4.1`** (NOT v3) — `@island`, `#[Async]`, `#[Js]`, `#[Computed]`, `#[Locked]`, `#[Isolate]` + `#[Lazy]` (both class-level, on `Main`), Livewire `Form` objects, `$wire.$island('name').$refresh()`. `#[Lazy]` was added to close a gap against the standing project rule (`app/Livewire/livewirePattern.md:803`) that every full-page route component gets it — `Main` is routed directly (`Route::get('/channels', Main::class)`) and previously had neither `#[Lazy]` nor a `placeholder()`, unlike every sibling module. `placeholder()` mirrors `render()`'s own `->layout('layouts.app')` chaining (not `->extends()->section()`) and is orthogonal to the `@island`/`#[Isolate]` mechanism — Lazy only governs the initial full-page mount, islands govern in-page partial re-render.
- **Filament `v5`** — `Filament\Schemas\Schema`, `FilamentHeaderActions`, `FilamentFilters`, `AuthorizesByPermission` traits.
- **Laravel 12.55.1**, **PHP 8.2.16** (NO property hooks — `ContentSanitizerService` mutator on `ChannelMessage::body()` stays).
- **MySQL**: dev 5.8 / prod 8+. No `JSON_TABLE`, no window functions, no enforced `CHECK`. `ROW_FORMAT=DYNAMIC`, composite/covering indexes, `leftJoinSub`, `unionAll`, `orderByRaw`, `insertOrIgnore`, `nullOnDelete`/`cascadeOnDelete` are all used and safe.
- `users.id` = `bigIncrements` → all FKs are `unsignedBigInteger`.

## 2. The one invariant that drives everything

> **A user can only see/open a channel if a `channel_members` row exists for them.**

Everything flows from this:

- **Sidebar list** = your memberships (`FetchChannelsAction` joins `channel_members` on `user_id = viewer`).
- **`selectChannel`** guards on membership — no row, no open (silent `return`, not a 403).
- **Unread** = messages with `id > your last_read_message_id` (index-only COUNT via covering index; no delta arithmetic).
- **`markRead`** advances `last_read_message_id` **forward-only** (#[Async], fire-and-forget).
- **Owner auto-membership** = the `Channel::created` boot hook (`memberUsers()->attach($owner_id, [joined_at, entered_at=now(), last_read_message_id=null, created_at, updated_at])`). This is the **single source of truth** for "the owner can see their own channel" across **every** creation path (Filament admin, user-panel, future seeder). Without it, Filament-created channels were invisible to their owner — that was the original gap. The hook itself is guarded `if ($channel->owner_id)` — a channel saved with no owner gets zero members and no recovery path (no owner exists to add anyone). `ChannelFormPresenter::owner()` is `->required()` (2026-09-12) specifically to stop the admin form from producing this state; the `owner_id` column stays DB-nullable (line below) since the guard is form-level, not schema-level.

## 3. Architecture — the rules that matter

### 3.1 Islands (the critical lesson — read twice)

Two islands: `@island(name:'sidebar')` and `@island(name:'messages')`.

**Island scope rule (hard-won):** on an **island-scoped method call** (e.g. `$wire.$island('messages').selectChannel(id)`, which re-renders the messages island natively after `selectChannel` — no manual `$refresh()`), the island re-renders with a **reduced scope**:
- ✅ Available: public properties (as bare vars: `$activeChannelId`, `$browseMode`, `$createMode`, `$mobileShowChat`, `$filter`, `$search`, `$loadedLimit`, `$hasOlder`) **and** `$this` (the component instance) **and** `$__livewire`.
- ❌ NOT available as bare vars: `#[Computed]` properties (`$activeChannel`, `$channels`, `$messages`, `$joinableChannels`, `$groupedMessages`, `$presenter`).

**Therefore:** inside islands and their `@include` partials, **always** reach computeds via `$this->` (e.g. `$this->activeChannel`, `$this->channels`, `$this->presenter`), never the bare variable. `sidebar.blade.php` does this (`$p = $this->presenter; $p->sidebar($this->channels, auth()->id())`). A bare `$activeChannel` in an island partial throws "Undefined variable $activeChannel" on the refresh path. `Livewire::test()->html()` does a **full render** that shares scope globally and **masks this bug** — only the real browser refresh exposes it.

**Nested anonymous Blade components (`<x-...>`) inside an island do NOT inherit `$__livewire`.** So `@entangle($model).live` (used by `<x-ui.forms.search>`) fatals inside an island. Use plain `wire:model` + Alpine for in-island inputs. `wire:model`/`wire:click`/Alpine `$wire` work fine (HTML attributes / Alpine scope, no Blade-scope `$__livewire` needed).

### 3.2 Unread (index-only, no delta)

`idx_channel_messages_covering (channel_id, deleted_at, id)` — the unread subquery counts messages `id > COALESCE(last_read_message_id, 0)` with `deleted_at IS NULL`, fully served by the covering index. No `last_read_message_id` arithmetic on the message side; the cursor is forward-only.

### 3.3 Growing-LIMIT prepend + the +1-probe `hasOlder` (no cursor, no array, no unbounded COUNT)

`Main::messages()` has two modes, **both** using the same `take(N + 1) → count() > N → take(N)` +1-probe idiom so `hasOlder` costs zero extra queries beyond the rows already fetched:

- **Recent-N** (`focusAnchorId = null`): ONE indexed query `latest('id')->take(loadedLimit + 1)`, keep `loadedLimit`, `hasOlder = count() > loadedLimit`, `sortBy('id')` so oldest-first (recent stay at bottom).
- **Anchor** (`focusAnchorId` set by `focusMessage`): TWO indexed queries — `where('id','>=',anchor)->oldest('id')->take(6)` (anchor + up to 5 newer) + `where('id','<',anchor)->latest('id')->take(focusOlder + 1)`; `hasOlder = older.count() > focusOlder`; trim older to `focusOlder`, merge, `sortBy('id')`. (Was 3 queries — a separate `exists()` for `hasOlder` plus an `$oldestId` lookup; the +1 probe collapsed it to 2.)

`loadOlder()` is two lines — anchor mode: `focusOlder += 10`; else `loadedLimit += 10`; then `unset($this->messages)` — the same query/queries now fetch the grown window, so older rows auto-**prepend** above recent in one indexed backward scan of `idx_channel_messages_covering (channel_id, deleted_at, id)`. No client array, no cap; mutations (`send`/`deleteMessage`/`saveEdit`/`undoDelete`) stay byte-identical — their existing `unset($this->messages)` re-queries the full grown window. Snapshot holds an `int`, not an array. `#[Computed] messages` caches per-request; `unset()` invalidates. The load-more affordance is the shared `<x-ui.buttons.load-more action="loadOlder">` (matches contact/FAQ/Report), gated by `x-show="$wire.hasOlder" x-transition`; `channel.js` also auto-fires `loadOlder` on scroll-to-top with scroll-anchoring (`overflow-anchor:none` + `scrollTop += delta`).

**Growing-window re-fetch cost, measured (2026-09-29/30) — same shape as Contact's, cheaper per-row but not immune.** `loadOlder()` re-fetches the WHOLE grown window every call and every poll tick while the channel is open, same as Contact (§3.3 of `contactPattern.md`). Benchmarked on an isolated `perf_benchmark` DB (seeded then dropped same session), one hot channel with 50,000 messages, EXPLAIN-verified `Using where` (no filesort — the single `channel_id` + `deleted_at` equality prefix on `idx_channel_messages_covering` resolves fully in-index, simpler than Contact's 3-column direction-split so consistently faster at the same N):

| Window size (`loadedLimit`) | Single fetch (median) |
|---|---|
| 10 (default) | ~0.8ms |
| 100 | ~1.1ms |
| 1,000 | ~5.8ms |
| 5,000 | ~212ms (high variance) |
| 10,000 | ~72ms |
| 25,000 | ~391ms |

**Verdict — same as Contact's:** negligible for typical scroll depth (hundreds of messages), genuinely costly only once a channel thread is scrolled tens of thousands of messages deep and left open through repeated poll ticks. This confirms the P3 sliding-window-cap fix applies identically to both modules — same trigger, same fix shape, same non-issue at normal usage.

**Why `take(N + 1)->count()` (not `COUNT(*)` or a separate `exists()`):** `hasOlder` is a *threshold* question ("are there more than N?"), not a count. `take(N + 1)` caps the index scan at N+1 rows — the DB stops once it has produced N+1, because the answer is already "yes". An unbounded `COUNT(*)` range-scans the whole tail/head of a high-traffic channel just to return a number compared to N; a separate `exists()` adds a round-trip. The +1 probe is strictly cheaper and behavior-identical — the same idiom `FocusChannelMessageAction` uses (§7).

### 3.4 Polling (Alpine, not wire:poll)

`channel.js` uses the shared adaptive scheduler in `mixins/chatBase.js` (2026-09-12) — a self-rescheduling `setTimeout` chain, not a flat `setInterval`: 10s floor, backs off (doubling) to 20s while a conversation is open / 30s when idle on the sidebar, resetting to 10s the instant something actually changes. Hard-halts on `document.hidden` (visibilitychange), with an instant, forced catch-up poll on resume — and the same forced, single-flight-guarded catch-up (`_repollNow()`, 2026-09-30) also fires on send/edit/delete/select now, not just visibility-resume; full mechanism (and the double-timer race it closes) documented in `contactPattern.md` §3.2, table above. **No `wire:poll`** — explicit scheduler + visibility gate is the project rule. Full base mechanism documented in `resources/js/scriptPattern.md`'s "Adaptive poll scheduler" section.

### 3.4a Poll digest (P1, 2026-09-30) — Channel's fan-out problem and how the sidebar leg avoids it

**Why Channel's digest can't just copy Contact's:** Contact's `dm:sv:{userId}` is bumped directly by the handful of Actions that write `messages` (§ equivalent in `contactPattern.md`) — trivial because a DM only ever affects two people. A channel message potentially affects *every member at once*; bumping a per-member key on every send would be an O(members) cache WRITE per message in a busy channel — exactly the cost-that-scales-with-fanout this whole day's work has been eliminating elsewhere. The design below avoids that by bumping ONE key per channel (O(1) regardless of member count) and computing each viewer's own digest number fresh, cheaply, from their own (typically small) membership list.

**Bump sites are model event hooks, not the four Livewire Actions — the one-file shared-source lever.** `ChannelMessage::booted()` bumps `ch:tv:{channel_id}` on `created`/`updated`/`deleted`; `Channel::booted()` bumps the same key on `updated` when `name`/`type`/`deleted_at` actually changed (`wasChanged(...)` gated — a rename or archive should move a member's sidebar row, an unrelated field update shouldn't). This is deliberately different from Contact's Action-level bumps: Channel has an admin/Filament write path too (`ChannelMessagesRelationManager`), so a model hook is the single place that automatically covers every writer — user-panel send/edit/delete/undo, admin edits, tinker, seeders — instead of four+ call sites that would each need remembering. Every bump is wrapped in `DB::afterCommit(fn() => ...)`: model events fire *before* the surrounding transaction commits, so an unwrapped bump could become visible to another user's digest check, get compared against, and be missed entirely if that check runs in the gap before commit — `afterCommit` is a no-op outside a transaction, so this is always safe to keep even if a future call site never wraps in one.

**Correction (2026-09-30, same-day fix, Fable-review-caught):** `Channel::booted()` ALSO needs `static::deleted(fn($channel) => DB::afterCommit(fn() => PollDigestService::bump("ch:tv:{$channel->id}")))` as a separate hook — `wasChanged(['name','type','deleted_at'])` inside the `updated` hook above only catches `deleted_at` moving via `restore()` (which internally calls `save()`, firing `updating`/`updated`). A soft `$channel->delete()` goes through `SoftDeletes::runSoftDelete()`, which performs a raw query-builder `update()` and never calls `save()` — so `updating`/`updated` never fire on delete, only `deleting`/`deleted` (fired unconditionally by the base `Model::delete()`, soft or hard). Without the `deleted` hook, deleting a channel a member is still subscribed to never moved their sidebar digest, so it kept showing in their group count/list until the unrelated 10th-tick fallback caught it.

**`MarkChannelReadAction` bumps two DIFFERENT keys, and deliberately never the shared `ch:tv`:** `ch:me:{userId}` (read by the sidebar digest, scoped to the reader only) and `ch:rv:{channelId}` (read by the *thread* stamp-probe, §3.4b below). Marking a channel read only changes what the reader sees — bumping the shared per-channel `ch:tv` from a read action would cause every *other* member's next poll tick to also pay for a real refresh for zero reason, every single time anyone reads anything, in every channel with more than one active member. Both bumps are gated on the pivot `update()` calls actually affecting a row (`$enteredNow > 0 || $markedRead > 0`) — re-opening an already-fully-read channel touches zero rows and correctly bumps nothing.

**Per-user sidebar digest formula:** `Main::pollDigest()` (`#[Renderless]`) sorts `$allChannelIds` first (stable fingerprint regardless of the join's row order), then returns `crc32(implode(',', $ids)) . ':' . crc32(implode(',', PollDigestService::versions(...))) . ':' . PollDigestService::version('ch:me:' . auth()->id())` — three segments joined as strings, never combined arithmetically. The `crc32` membership fingerprint is what closes a real gap a naive "just combine the versions" design has: being newly added to (or removed from) a channel that has never had a message (`ch:tv` still `'0'`) wouldn't move that segment at all — the fingerprint moves the instant the *set* of channel ids changes, independent of any channel's own activity level. Keeping the three segments as separate colon-joined strings (not added/multiplied together) matters for a subtler reason: if they were combined arithmetically, a change in one channel's version could coincidentally cancel a change elsewhere, silently hiding a real change.

**Correction (2026-09-30, same-day fix, Fable-review-caught):** the middle segment was originally shipped as `array_sum(PollDigestService::versions(...))` — summing the per-channel version *microtimes* — which reintroduced the exact cancellation risk the paragraph above warns against, just one level down: two channels' version deltas within the same sum could offset each other (and, separately, PHP's float→string precision loses sub-~10ms deltas once the sum passes roughly 1e11, i.e. a few dozen channels' worth of accumulated `microtime()` values). Fixed same day by crc32-hashing the comma-joined version list instead of summing it — a hash is sensitive to any single value changing at any position, so it cannot cancel the way a sum can.

**The messages leg (open channel) is not part of this digest at all** — same reasoning and same mechanism as Contact's, see the stamp-probe below.

### 3.4b Message-window stamp-probe (P3, 2026-09-30) — same mechanism as `contactPattern.md` §3.3a, channel-shaped

**Why a broadcast channel's stamp is wider than a DM's.** A DM's stamp only needs the newest row because edit/delete are gated to the very last message. A channel additionally has: (a) the typing indicator, which is *per-member*, not per-peer, so it folds in `implode(',', $this->typingMembers)` (the whole live-typing set, not a single name); (b) `MarkChannelReadAction`'s own bumps, which move read receipts/checkmarks without touching a single `ChannelMessage` row — so the stamp also folds in `PollDigestService::version("ch:rv:{$channelId}")`. Three segments, colon-joined: `"{$latest->id}:{$latest->updated_at}:{$latest->deleted_at}"` (or the literal string `'none'` if the channel has zero messages) `:` typing-set `:` read-version.

**Mechanism, gate, and reset story are identical to Contact's:** `#[Locked] ?string $pollStamp` + `MESSAGES_STAMP_THRESHOLD = 200`; `refreshActive()` computes the stamp only once `loadedLimit > 200` and `focusAnchorId === null`; equal stamp → `skipRender()` and return, no `unset($this->messages, $this->groupedMessages)`; different stamp → store it and fall through to the normal refresh. Same zero-reset-call-site property — a stale stamp only ever causes one harmless extra refresh, never a wrong skip.

**Deliberately NOT given its own "thread" leg inside `pollDigest()` (deviation from Fable's literal proposal).** Fable's draft suggested folding a channel-thread version into the same digest formula used for the sidebar. That would duplicate exactly what this stamp-probe already does — two independent mechanisms answering "did the open thread change?" — with no correctness benefit and a real risk of the two drifting out of sync. The stamp-probe is scoped to `refreshActive()` only; `pollDigest()` stays scoped to the sidebar only.

**Verified via `tests/Feature/Livewire/Dashboard/ChannelTest.php`:** `test_refresh_active_stamp_is_stable_when_unchanged_and_moves_when_a_channel_message_arrives`. **Not independently verified:** `skipRender()`'s actual wire-protocol-level suppression on a real island round-trip — no live browser in this session.

`Channel` and `ChannelMessage` use `Prunable` + `HasPrunableStatus`. `prunable()` selects soft-deleted rows past the retention window (`now()->subDays($this->getPruneDays())`, default 30, owned by the trait and overridable per model by redefining `getPruneDays()`); `prune()` delegates to `ForceDeleteChannel*Action` (which calls `forceDelete()`); the `forceDeleted` model hooks unlink storage. There is **no custom command** — pruning is driven by Laravel's built-in `model:prune`, scheduled **daily** in `routes/console.php`, which auto-discovers every `Prunable` model and calls its `prunable()` + `prune()`. The framework adds `withTrashed()` and chunks via `chunkById`, so `prunable()` carries only the date filter. `model:prune` also covers `Message` and `Task` (same pattern — `prune()` → `ForceDelete*Action`, `forceDeleted`/`forceDeleting` storage hooks).

### 3.6 What this module deliberately does NOT have

- **No `HasMenuState`** — channels are not wired into the menu-state/badge pipeline (no `HasMenuState` trait on any channel model).
- **No bare-key badge** — there is no `channels-controller` menu item or tab badge; the nudge below is `:nudge`-suffixed so it never matches a badge indicator query.
- **No cache layer** — computeds + DB only.
- **No nested Livewire component** — single `Main` + islands only.
- **Sanctioned nudge — `ChannelNudge`, key `channels-controller:nudge`** — ONE class carrying BOTH invite and unread signal on a single row per (channel, user), migrating between mutually-exclusive states on `entered_at` (like `ThsNudge`'s open→in-progress→closed; `show()/refresh() => true`, `for()` filters, `title()/body()` branch on state). `invited` = `entered_at IS NULL` via `Channel::invitedUserIds` (one indexed `channel_members` pluck, `whereNull('entered_at')`); `unread` = `entered_at IS NOT NULL` AND count > 0 via `Channel::unreadCountsFor` — one grouped `COUNT(*)` over `channel_members cm` ✕ `channel_messages msg` where `msg.id > COALESCE(cm.last_read_message_id, 0)`, `whereNotNull('cm.entered_at')`, **`whereNull('msg.deleted_at')`** (soft-deleted excluded — matches `ChannelMessage::totalUnreadFor`; without this the deleted-message trigger leaves a stale unread nudge), `groupBy cm.user_id`. `for($channel)` primes `$this->invited`/`$this->unread` and returns the union via one `User::whereIn` — **two indexed queries per reconcile, never per-recipient** (the `for()-primes-body()` idiom, same as `Message::unreadCountsFrom` / `DMS::signedUserIds`). `title()/body()` check `invited` first, so a `ChannelMessage` trigger firing while a user is still not-entered keeps the row as the invite message. **Triggers:** `Channel` `deleted`/`forceDeleted` (cleanup — subject = channel → `Channel::find` returns null when soft/force-deleted → engine prunes the channel's whole row set) + `ChannelMessage` `created`/`deleted` (subject = `$message->channel`; `updated` omitted — edits/attachments don't change unread; soft-`deleted` already excludes from counts so `forceDeleted` is redundant; a *restored* message re-counts but fires no caught event — self-corrects on the next `created`, §16). **Cleanup rides the three existing dispatch sites** — `MarkChannelReadAction` / `SyncChannelMembersAction` / `LeaveChannelAction` already dispatch `ReconcileNudge('channels-controller:nudge', Channel::class, $channelId)->afterCommit()`, reconciling BOTH states for free; **zero new dispatch sites, no edits to those actions or `SendChannelMessageAction`** (send covered by `ChannelMessage::created` → trigger → `afterCommit`). Sender self-exclusion is automatic: `SendChannelMessageAction` advances the sender's `last_read_message_id = $message->id` → unread = 0 → drops out of `unreadCountsFor`. Both enter paths (`MarkChannelReadAction`, `JoinChannelAction`) advance the cursor to latest → unread = 0 → the user leaves the recipient set → the engine's `whereNotIn('notifiable_id', $ids)->delete()` prunes the row (prune-then-recreate on the next message); a dismissed invite row is pruned the same way. The bell's existing `>4` folding (`UnreadNotifications::AGGREGATE_THRESHOLD`) collapses many channels into one "N اعلان جدید" entry — ≤4 show per-channel rows, >4 auto-aggregate. `badge_suppress` left default (no `channels-controller` bare badge → no-op). Still `:nudge`-suffixed: no bare badge key, no `HasMenuState`. The in-sidebar "not entered" dot (§10) is a **render flag from the existing query** — same category as the in-sidebar unread pill — NOT the HasMenuState/menu-badge pipeline.
- **No DB unique index on `slug`** — uniqueness enforced in the form layer (`Rule::unique('channels','slug')->whereNull('deleted_at')`) so soft-deleted slugs can be reused.

### 3.7 Owner-managed members + invite signal

The minimal invite flow: the **owner** adds/removes members (the membership row is the signal), and the recipient gets a **global `ChannelNudge` bell row** (§3.6, `channels-controller:nudge`) while they remain not-yet-entered — the former client-side ephemeral "you were added" toast (localStorage `channel-seen-invites`, `inviteToasts`, `data-channel-id/name` sidebar hooks) was REMOVED 2026-08-30 when the mention-toast moved to the global Edge pipeline (§21); the invite signal is bell-only now. The owner instead sees the pending list in the info panel (`pendingInvitees`, §6.2). The `entered_at` column (§4) distinguishes "invited" from "entered"; the nudge is pruned the moment the member enters (`MarkChannelReadAction` sets `entered_at`).

- **Server side (`SyncChannelMembersAction`, §7)** — owner-scoped diff-sync; **empty input purges all non-owner members** (no empty-guard — owner is still protected by the `[$ownerId]` exclude); owner protected both directions. Called from `Main::saveManageMembers` (owner re-checked via `channel->owner_id === auth()->id()`), opened from `Main::openManageMembers` (owner-checked). Both Open and Private channels — the toggle now lives in `create.blade.php` (two-button `$wire.set('create.type', …)`), and `createChannel()` no longer forces `type='open'` (the form value is respected; `openCreate()` only sets the default selection).
- **`memberCandidates` #[Computed]** — `User::getCachedActiveOptions()->except(auth()->id())` → `[id => name]` mapped to `[{id, name}]`. `getCachedActiveOptions` is the `once(Cache::remember('user_active_options', hour, …active()->orderBy('name')->pluck('name','id')))` one-query cache; `->except(auth()->id())` drops the owner from their own picker. Unset in `openManageMembers`/`saveManageMembers` so it refreshes.
- **Modal** — `manage-members.blade.php` clones the `share.blade.php` shape (`<x-ui.modals.action wire:model="isManageMembersOpen" action="saveManageMembers">` + the shared `<x-dashboard.member-picker>` `model="memberRecipientIds"` at `h-[50vh] md:h-64` over `$this->memberCandidates` — `viewPattern.md` §8.22). Included **OUTSIDE the islands** (parent scope, next to `<x-ui.modals.max-backdrop/>` in `channel.blade.php`) — `<x-ui.modals.*>` uses `@entangle` which needs `$__livewire` that nested components don't inherit inside `@island`, so it fatals there (see §16). Opened via the **parent `$wire.openManageMembers(id)`** (NOT `$wire.$island('messages')`) — a parent call re-renders the whole component so the parent-scope modal toggles. `memberCandidates` depends only on `getCachedActiveOptions`+`auth()->id()` (not `activeChannel`), so the unconditional parent-scope render is safe in create/browse/empty modes. Owner-only button in `info.blade.php` (`$isOwner = activeChannel && owner_id !== null && auth()->check() && (int)owner_id === (int)auth()->id()`); its `x-on:click="openManageMembers(id)"` calls the Alpine wrapper → `$wire.openManageMembers(id)`.
- **Admin (`ChannelMembersRelationManager`)** — `$relationship = 'memberUsers'` (belongsToMany on `channel_members`), so Filament's native `AttachAction`/`DetachAction` fit. `AttachAction` `mutateDataUsing` sets `joined_at`/`created_at`/`updated_at` explicitly (no `withTimestamps()`); `DetachAction` is **hidden for the owner row** (`record->id === ownerId`) so the channel can't be orphaned. Columns: `name`, `joined_at`, `pivot.entered_at`, `last_read_message_body` (a correlated subselect added via `modifyQueryUsing`/`addSelect` — `ChannelMessage::select('body')->whereColumn('channel_messages.id','channel_members.last_read_message_id')->limit(1)`, NOT a pivot column or model accessor), `pivot.updated_at`; `defaultSort('channel_members.created_at','desc')`.

## 4. Data model (3 tables)

### `channels` (`2026_09_19_000041`)
```
id (PK, bigIncrements)
name        string(100)
slug        string(120)            -- indexed, NOT unique-DB (form-layer unique)
description string(500) nullable
type        string(20) default('open')   -- 'open'|'private' (ChannelType enum)
owner_id    unsignedBigInteger nullable  -- FK users, nullOnDelete
timestamps, softDeletes
indexes: slug, owner_id, deleted_at
```
Model: `App\Models\Channel` — `SoftDeletes, Prunable, HasPrunableStatus, CleansAttachedFiles, HasFactory`. Fillable: `name,slug,description,type,owner_id`. Casts: `type=>ChannelType, deleted_at=>datetime`. Relations: `owner` (User), `members` (HasMany ChannelMember), `memberUsers` (belongsToMany User via `channel_members`), `messages` (HasMany ChannelMessage). `booted()`: `static::created` → `memberUsers()->attach($owner_id, [joined_at, entered_at=>now(), last_read_message_id=>null, created_at, updated_at])` (owner is entered immediately, never invite-nudged); `static::forceDeleted` → `CleansAttachedFiles::deleteStoredDirectory("channel_messages/{$id}")`. `prunable()` = soft-deleted >30 days; `prune()` → `ForceDeleteChannelAction`.

### `channel_messages` (`2026_09_19_000042`)
```
id (PK)
channel_id  unsignedBigInteger  -- FK channels cascadeOnDelete
sender_id   unsignedBigInteger nullable -- FK users nullOnDelete (message survives sender deletion, sender becomes "ناشناس")
body        text
attachments json nullable
reply_to_id unsignedBigInteger nullable -- FK self nullOnDelete
```

## 15. Dos and Don'ts (consolidated hard rules)

### DO
- ✅ Reach computeds inside islands via `$this->` (`$this->activeChannel`, `$this->channels`, `$this->presenter`). Public properties can stay bare (`$activeChannelId`, `$browseMode`, `$createMode`).
- ✅ Null-guard every `ChannelMessage::lastIdForChannel()` caller. It returns `?int`; empty channel → `null`.
- ✅ Re-throw `HttpException` in `send()` so `ensureMember`'s 403 propagates; only catch `ValidationException` + generic `\Exception`.
- ✅ Scope message edits/deletes by `sender_id = auth()->id()` (in both `Main::editMessage` and `SaveEditChannelMessageAction`).
- ✅ Use `insertOrIgnore` for member rows (composite PK, idempotent with the `Channel::created` boot).
- ✅ Use plain `wire:model` for in-island inputs (NOT `<x-ui.forms.search>` / `@entangle`).
- ✅ Route all force-deletes through `ForceDeleteChannel*Action` (so the `forceDeleted` storage hooks fire).
- ✅ Keep MySQL 5.7-safe: `leftJoinSub`, `unionAll`, `orderByRaw`, `insertOrIgnore`, composite/covering indexes — all fine. No `JSON_TABLE`, no window functions.
- ✅ Enforce slug uniqueness at the form layer (`Rule::unique(...)->whereNull('deleted_at')`) so soft-deleted slugs are reusable; no DB unique index.
- ✅ User-panel create supports both Open and Private (toggle in `create.blade.php`) AND picks initial members inline (`createRecipientIds` → `SyncChannelMembersAction` on `createChannel`); owner can also sync members later for either type via the info-pane modal (§3.7).
- ✅ No code comments (project rule). Inline Persian for partials; `lang/fa` keys only for Filament.

### DON'T
- ❌ Don't use a bare computed (`$activeChannel`, `$channels`, etc.) inside `@island` or its `@include` partials — it throws on the refresh path (masked by `Livewire::test`).
- ❌ Don't use `@entangle` / `<x-ui.forms.search>` / `<x-ui.modals.*>` inside an island — `@entangle` (in `components/ui/modals/base.blade.php` and `forms/search`) needs `$__livewire` which nested anonymous components don't inherit. **Modals go OUTSIDE the island** (parent scope, next to `<x-ui.modals.max-backdrop/>`); the open method is called on the **parent `$wire`** (e.g. `$wire.openManageMembers(id)`), NOT `$wire.$island('messages')` — a parent call re-renders the whole component so the parent-scope modal toggles. `memberCandidates` must not depend on `activeChannel` so the unconditional parent-scope render is safe in every mode.
- ❌ Don't trust `Livewire::test()->html()` alone for island code — it does a full render and shares scope globally, hiding island-only scope bugs. Add a real island-refresh check (see §17).
- ❌ Don't add `HasMenuState` / a bare-key badge / wire:poll / a cache layer / a nested Livewire component — none belong here. The single sanctioned nudge is `ChannelNudge` (`channels-controller:nudge`, §3.6, dual-state invite→unread migrating on `entered_at`, like `ThsNudge`); no OTHER nudge/badge may be added.
- ❌ Don't call `self::createdAtFilter()` in a Filament RM without `use App\Traits\FilamentFilters;` + `use FilamentFilters;`.
- ❌ Don't access `ChannelType` via `->label` — the enum implements `getLabel()` (and `getIcon/getColor`), not a `label` property.
- ❌ Don't write property hooks in models (PHP 8.2 runtime) — keep the `ContentSanitizerService` mutator on `ChannelMessage::body()`.
- ❌ Don't add a `DB::unique` on `channels.slug` — form-layer unique with `whereNull('deleted_at')` is the rule.
- ❌ Don't create a channel without enrolling the owner as a member (the `Channel::created` boot does this now; never bypass it).
- ❌ Don't let the owner leave/detach themselves from their own channel — `LeaveChannelAction` no-ops (`false`) for the owner regardless of caller; `header.blade.php`/`info.blade.php` additionally hide the Leave button via `$isOwner`.

## 16. Known edge cases / gotchas

1. **Empty channel + `markRead`** — `lastIdForChannel` returns `null`; `MarkChannelReadAction` early-returns (fixed). Without the guard, `orWhere(col,'<',null)` throws "Illegal operator and value combination".
2. **Filament-created channel invisible to owner** — fixed by `Channel::created` boot inserting the owner member. Existing channels were backfilled once.
3. **Bare `$activeChannel` in messages island** — fixed (use `$this->activeChannel`). All three island partials (header/messages/info) + the root conditional.
4. **`@entangle`/`<x-ui.forms.search>` in sidebar island** — fixed (plain `wire:model` input + Alpine clear).
5. **Sender soft-deleted** — `sender_id` is `nullOnDelete`, so the message survives and shows `ناشناس` ("unknown").
6. **Channel soft-deleted** — member row survives (FK is `cascadeOnDelete`=hard-delete only, no SoftDeletes on members), but `FetchChannelsAction` joins `channels` which excludes soft-deleted via the model; `selectChannel` guards with `withoutTrashed()`. `Main::myChannelMemberships()`/`totalUnread()` need their own explicit `whereNull('channels.deleted_at')` guards for the same reason (§6.2) — they're raw `DB::table()` queries, not Eloquent, so they don't inherit the model's SoftDeletes scope automatically (missed in the initial 2026-09-30 pass, fixed same day after Fable's review caught it).
7. **Undo after force-delete** — `UndoDeleteChannelMessageAction` falls back to recreating from the snapshot if the soft-deleted row was already force-deleted.
8. **Persian slug** — `Str::slug` returns empty for Persian; `CreateChannelAction::resolveSlug()` uses `preg_replace('/[^\p{L}\p{N}]+/u','-', mb_strtolower($name))` + `Str::random(6)` suffix for uniqueness. Slug generation runs **before** `$form->validate()` so the form's `slug.unique` rule validates the populated slug (moved out of `Main::createChannel` — Main no longer touches `Str`/slug).
9. **Edit + delete window** — 600s enforced in `SaveEditChannelMessageAction::EDIT_TIME_LIMIT` (edit) and `DeleteChannelMessageAction::execute($id, $editTimeLimit)` (delete), both mirrored as `Main::$editTimeLimit` for the presenter's `can_edit`/`can_delete` flags; keep all three in sync. Edit and delete are gated identically in the blade by `can_edit`/`can_delete` alone — every own message inside the window (2026-10-09; the former `id === lastMessageId` gate and the computed are gone, aligned with Contact).
10. **`SyncChannelMembersAction` empty-submit purge — RESOLVED by product decision, 2026-10-01.** An empty `$recipientIds` makes `toRemove = array_diff($current, [], [$ownerId])` = all non-owner members; owner survives via the `[$ownerId]` exclude, and the channel itself (with its full message history) is untouched — purging to zero members is NOT the same action as deleting the channel (`DeleteChannelAction`, §23). **This is deliberate, not a bug**: an owner may want to empty a room while keeping it (and its history) around to re-invite people into later. The only real risk was an *accidental* uncheck-all + save with no confirmation — fixed by a reusable opt-in guard on the shared `<x-ui.modals.action>` component (`components/ui/modals/action.blade.php`): new `confirmWhen`/`confirmPrompt` props (both default `null` — zero behavior change for the other 6 consumers), compiled via a `@php $clickExpr = ...; @endphp` block (never inline double-quoted PHP inside a component tag's `{{ }}` attribute — Blade's anonymous-component attribute extraction mis-parses embedded `"` before full PHP tokenization even runs; this exact mistake broke all 88 ChannelTest cases with a `syntax error, unexpected token "endif"` until caught and fixed the same pass). `manage-members.blade.php` opts in: `confirm-when="$wire.memberRecipientIds.length === 0"` + a RESULT-phrased prompt ("you'll be the only member left; the group and its messages stay") rather than an action-phrased one, so the confirm text stays accurate whether or not there was actually anyone to remove (the guard can't cheaply distinguish "emptied the room" from "saved while already empty" without extra plumbing — a correctly-worded prompt sidesteps needing that distinction). `confirmPrompt` is passed through `\Illuminate\Support\Js::from()` for safe JS-string escaping, not raw interpolation.
11. **Sidebar pagination (`$channelsLimit`) is now a real SQL `LIMIT` on `channels()` itself (superseded 2026-09-30 — was render-only slicing).** `FetchChannelsAction::execute()` takes `?int $limit` (`->limit($limit)`) and `?array $myChannelIds` (see the membership-scoping fix below); `Main::channels()` passes `$this->channelsLimit + 1` (+1-probe) and `$this->allChannelIds`, sets `$this->hasMoreChannels`, trims. `sidebar.blade.php` no longer slices — `$channelList` IS the page, `@forelse($channelList as $ch)` reads it directly, load-more gates on `$this->hasMoreChannels`. `$channelsLimit` is now `#[Locked]`. `$allChannelIds`/`$totalUnread`/`data-channel-count`/the type-breakdown subtitle were decoupled onto their own independent, membership-scoped computeds (§6.2: `myChannelMemberships`/`allChannelIds`/`totalUnread`/`myChannelsSummary`) so they stay org-membership-wide even though `channels()` itself is now page-bound. Identical change shipped to Contact same day (`contactPattern.md` §13.10) — the "deliberately not SQL-`LIMIT`-based" reasoning both docs used to share is retired for these two modules (Project's `$projectsLimit` is untouched, don't assume it applies there without checking).
   **Real bug found and fixed in the same pass: `lastMsgSub`/`membersSub` were aggregating over ALL channels org-wide, not just the viewer's memberships.** Both derived tables did `GROUP BY channel_id` over the entire `channel_messages`/`channel_members` tables before the outer query's `WHERE channel_members.user_id = viewer` ever applied — meaning MySQL had to compute a last-message-id and a member-count for every channel that exists anywhere in the org, discard almost all of it, then join the tiny remainder. Cost grew with total org-wide channel activity, not with how many channels the viewer is actually in. Fixed by adding `->whereIn('channel_id', $myChannelIds)` to both subqueries, where `$myChannelIds` is either the caller-supplied array (the common case — `Main::channels()` passes its already-computed `allChannelIds`, zero extra query) or, when called standalone with no array, a `channel_members WHERE user_id=$viewerId` subquery built internally. `unreadSub` was already viewer-scoped (`.where('channel_members.user_id', $viewerId)` inside it) and needed no change. **Rule: any subquery that will be joined back onto a viewer-scoped outer query must itself be scoped to the viewer (or the viewer's membership set) BEFORE the `GROUP BY`, never after — an unscoped aggregate-then-join still does the unscoped aggregation work even though the final result looks correctly scoped.**

## 21. @mention — zero-schema render-time highlight + composer autocomplete + persistent mention-toast

- **A+ zero-schema (id-resolved-at-render):** a mention is plain `@Name` text in the existing `channel_messages.body` (sanitized plain text, NOT html). No migration, no new column, no nudge/badge — `ChannelMessage::created` already fires every notification surface, so a mentioning message is just another message. `@all`/`@channel` broadcast is deliberately DEFERRED (sentinel-collision + every-viewer-scan cost ≠ value).
- **Render (`ChannelPresenter::messages()`):** builds one regex alternation `/(?<![\w@])@(name1|name2|...)(?![\p{L}\p{N}_])/u` from the CURRENT channel members (alternation-from-real-members ⇒ no false positives, no non-member leak), wraps matches in `<span class="mention">@Name</span>`, and sets a per-message `mentions_you` boolean. Mandatory build rules (all surfaced by review):
    - `preg_quote(e($name), '/')` EVERY name (a name like `C++`, `a.b`, `(QA)` otherwise injects metachars → broken regex).
    - sort name keys by `mb_strlen` DESC (PHP PCRE alternation is left-to-right, NOT longest-match; `@(Alice|Al)` so the full name wins). Use `mb_strlen`, not `strlen` (Persian-correct).
    - mentionify AFTER `linkify`, splitting on `/<a\s[^>]*>.*?<\/a>/us` and skipping link segments, so `https://x.com/@Name` is not double-wrapped.
    - map shape is `{name => [ids]}` (array), NOT `{name => id}` — PHP last-key-wins would collapse two members named "John"; the array preserves all ids so `mentions_you = in_array(authId, $map[$name], true)`. Residual by-design limitation: two same-named members both light up when `@Name` is typed (disambiguation would require ids in the body, which A+ rejects).
- **Departed member stops highlighting = by-design** (alternation = current members; the historical bell already fired at send time). Do not "fix" by persisting ids.
- **`Main::mentionMemberMap()` `#[Computed]`:** `activeChannel->memberUsers()->select('users.id','users.name')->orderBy('name')->get()` → `{name => [ids]}`; one indexed query, memoized; guarded on `$this->activeChannel` (null when a stale locked `activeChannelId` outlives membership removal). The presenter NEVER queries — Main fetches, presenter shapes. Threaded into `messageGroup()` as a 6th defaulted `array $mentionMap = []` arg (backward-compatible: only `channel/messages.blade.php` calls it; Contact uses its own `ContactPresenter`).

## 23. Owner self-delete — `DeleteChannelAction` (sole-member soft delete)

The owner can delete their own channel from the user panel, but **only once they are the sole remaining member** (`channel_members` count === 1, matching the owner's own row — `LeaveChannelAction` already no-ops for the owner, so they can never remove themselves from that count; every other member must have left or been removed first).

- **`Actions/DeleteChannelAction::execute(int $channelId, int $userId): bool`** — scopes the lookup by `owner_id = $userId` first (IDOR-safe, same shape as `SyncChannelMembersAction`), then guards `$channel->memberUsers()->count() === 1`; any guard failure returns `false` (no exception, no 403). On success, a **soft delete** (`$channel->delete()`) — NOT `ForceDeleteChannelAction`, which is the hard, unrecoverable admin-cleanup prune and stays untouched/unrelated. No snapshot/undo: unlike `DeleteChannelMessageAction`, a whole-channel delete has no cheap single-row undo shape, and the channel is still admin-restorable (soft delete) if genuinely needed back.
- **`Main::deleteChannel(DeleteChannelAction $action, int $channelId)`** — calls the action; on failure, silent `return` (matches `selectChannel`/`leaveChannel`'s guard-fail convention, not a toast/403). On success, mirrors `leaveChannel`'s post-action UX **exactly**: if the deleted channel was the active one, clears `activeChannelId`/`mobileShowChat`/`loadedLimit`/`hasOlder`/`focusAnchorId`/`focusOlder`/`messageSearch`, then `unset()`s the same computed set `leaveChannel` does, then a toast («گروه حذف شد»). The sidebar naturally drops the channel on its next `refreshUnread()` since `FetchChannelsAction` is membership-scoped and the owner's own membership row is gone the moment the channel is soft-deleted (`Channel::withoutTrashed()`/the model's default global scope hides it from every read path regardless of its still-physically-present `channel_members`/`channel_messages` rows — soft delete does not cascade).
- **UI (`info.blade.php`)** — owner-only «حذف گروه» control, gated `$isOwner && (int) $header['members_count'] === 1`, placed directly below the existing «مدیریت اعضا» button. Two-step inline confirm, mirroring the «در انتظار ورود» cancel-invite pattern (`confirmCancelInvite`/`doCancelInvite`) rather than the per-message `deletingId` pattern: `confirmingDeleteChannel` (Alpine boolean) toggles between a prompt button (`confirmDeleteChannel()`) and a confirm/cancel pair (`cancelDeleteChannel()` / `doDeleteChannel(id)`), both `x-show`-toggled (never `<template x-if>`, per the island morph rule).
- **`channel.js` wiring** — `doDeleteChannel(id)` is **island-scoped and wire-captured**: `const wire = this.$wire` captured before the call, reused for both `wire.$island('messages').deleteChannel(id)` and the trailing `wire.$island('sidebar').refreshUnread()` — load-bearing, because deleting the active channel replaces the `pane-active` branch (containing the very button that was clicked) with `pane-empty` in the SAME response, so a bare post-await `this.$wire` access would silently no-op (gotcha #16's bug class). `confirmingDeleteChannel` resets in `closeOverlays()` and `selectChannel()` alongside the module's other per-channel UI flags.
- **Known limitation (not fixed, by design):** `SyncChannelMembersAction`'s empty-submit purge defect (gotcha #10) is a separate, pre-existing, already-documented open issue — not touched by this feature. The sole supported "get down to 1 member" route is individual removals/`LeaveChannelAction`, not an empty bulk sync.
- **Tests** (`tests/Feature/Livewire/Dashboard/ChannelTest.php`): `test_owner_with_only_self_can_delete_channel`, `test_owner_with_other_members_cannot_delete_channel`, `test_non_owner_cannot_delete_channel`, `test_deleted_channel_disappears_from_sidebar_and_resets_active_id`.
- **Not independently verified (real-browser pass needed):** the two-step confirm UI's island-morph behavior and the `doDeleteChannel` wire-capture fix's actual network-tab behavior — `Livewire::test` proves the server-side guard/state/toast correctly but cannot exercise the island-scoped request or the post-morph `$wire` re-resolution, per §17.
