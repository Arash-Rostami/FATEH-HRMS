# Contact Module Pattern Guide

The internal **one-to-one messenger** (`/contacts`). Every active user is reachable by every other active user — there is **no membership gate** (unlike the sibling `channels` module, which is one-to-many broadcast with a `channel_members` gate). Built with Livewire v4.1 islands, Filament v5 admin, Laravel 12, PHP 8.2. MySQL 5.7-compatible baseline (production 8+).

This doc is the **single source of truth** for every file, contract, rule, and gotcha in the module. Read it before touching anything contact-related. The canonical **general** rules for `@island` scope/memoization live in `app/Livewire/livewirePattern.md`; this doc covers the Contact-specific architecture, contracts, and the island-migration history (with the concrete island instance retained in §3 as the lesson that motivated those general rules).

---

## 1. Stack & compatibility (verified)

- **Livewire `^4.1`** (NOT v3) — `@island`, `#[Computed]`, `#[Locked]`, `#[Isolate]` (class-level, on `Main` — Channel parity), `#[Lazy]` (class-level, on `Main` — Channel parity; closes the same gap documented in `channelPattern.md` against `app/Livewire/livewirePattern.md:803`'s full-page-route-component rule), `#[Async]` (fire-and-forget; `markRead`), `#[Js]` (pure client-side JS return; `cancelReply`/`cancelEdit`), Livewire `Form` objects, `$wire.$island('name').method()`.
- **Filament `v5`** — **correction (2026-09-30, Fable-review-caught): `ContactResource` DOES exist and writes `messages`** (`protected static ?string $model = Message::class`, with edit/restore/delete actions + bulk actions). The line above was wrong and had propagated into §3.2a's digest-bump design — see the correction there.
- **Laravel 12**, **PHP 8.2** (NO property hooks).
- **MySQL**: 5.7-compatible (dev) / 8+ (prod). `unionAll`, `leftJoinSub`, composite/covering indexes are used and safe. No `JSON_TABLE`, no window functions. `users.id` = `bigIncrements` → all FKs `unsignedBigInteger`.
- The `messages` table is **Contact-only** (`ChannelMessage` is a separate model on the separate `channel_messages` table; `Message` is the 1:1 model). Contact writes `messages` rows where `sender_id`/`recipient_id` are the two users.

## 2. The one invariant that drives everything

> **A user can message any active user. There is no membership gate — it is 1:1, not broadcast.**

Everything flows from this:

- **Sidebar list** = all colleague-visible users (`FetchContactsAction` returns `User::visibleOnBoard()` — excludes `UserType::Guest`, same scope the Status board uses — with `leftJoinSub` for last-message + unread; a user with no prior conversation still appears, with `last_message = null`, `unread_count = 0`). Contrast Channel, where the sidebar is your memberships only.
- **`selectContact`** guards only on `User::getCachedAllOptions()->has($userId)` (user exists/active) — no membership row, no `whereHas`. Silent `return` on fail (not a 403).
- **Unread** = messages where `recipient_id = me`, `read_at IS NULL`, `deleted_at IS NULL`, counted per contact (`unreadSub` in `FetchContactsAction`, already scoped to `visibleOnBoard()` senders via its base query). The two **sitewide** unread counters — `Message::hasUnreadFor()` (hamburger-menu dot, `UnreadMessages` indicator) and `Message::totalUnreadFor()` (the messaging-tab numeric pill, `FetchMessagingUnreadAction`) — are separately scoped the same way (`whereHas('sender', fn($q) => $q->visibleOnBoard())`, fixed 2026-09-04): before this fix, an unread message from a sender who later went inactive or Guest-type was invisible in the sidebar (so unreachable to mark read) yet still counted forever by these two, producing a "badge says unread, nothing to open" symptom.
- **Marking read** = `MarkMessagesAsReadAction` sets `read_at` on the contact's inbound messages to me, then explicitly dispatches `ReconcileNudge('contacts-controller:nudge', User::class, $contactId)` (a mass `Builder::update()` fires no `updated` Eloquent event, so the sitewide bell nudge — `App\Services\Menu\Notifications\ContactNudge`, see `App\Services\Menu\statePattern.md` — would otherwise never clear; Channel's `MarkChannelReadAction` is the precedent for this explicit-dispatch pattern; fixed 2026-09-04).
- There is **no create/browse flow** — every active user is already reachable. There is **no channel type**, no owner, no join/leave.

## 3. Architecture — the rules that matter

### 3.1 Islands (the critical lesson — read twice)

Two islands: `@island(name:'sidebar')` and `@island(name:'messages')`, wrapped in `contact.blade.php`.

**Island scope rule (hard-won, ported from Channel):** on an **island-scoped method call** (e.g. `$wire.$island('messages').selectContact(id)`, which re-renders the messages island natively after `selectContact`), the island re-renders with a **reduced scope**:
- ✅ Available: public properties (as bare vars: `$activeUserId`, `$search`, `$filter`, `$mobileShowChat`, `$hasOlder`) **and** `$this` (the component instance) **and** `$__livewire`.
- ❌ NOT available as bare vars: `#[Computed]` properties (`$activeContact`, `$contacts`, `$messages`, `$groupedMessages`, `$lastMessageId`, `$presenter`).

**Therefore:** inside islands and their `@include` partials, **always** reach computeds via `$this->` (e.g. `$this->activeContact`, `$this->contacts`, `$this->presenter`), never the bare variable. Each partial that needs the presenter opens with `@php($p = $this->presenter; ...)` and uses the **local** `$p`. A bare `$activeContact` in an island partial throws "Undefined variable $activeContact" on the refresh path. `Livewire::test()->html()` does a **full render** that shares scope globally and **masks this bug** — only the real browser refresh exposes it.

**This is Contact's own history, not just a copy of Channel's rule.** The pre-migration monolith injected `['activeContact' => $this->activeContact, 'p' => new ContactPresenter()]` into `render()` and every partial read the bare `$activeContact`/`$p`. The island migration (Phase B) replaced every one of those 29 reads with `$this->activeContact` / a local `$p = $this->presenter`, and only then — Phase A step 2, its own commit — dropped the `render()` injection. The grep audit in §10 is the artifact that proves §3 stays true going forward.

**Nested anonymous Blade components (`<x-...>`) inside an island do NOT inherit `$__livewire`.** So `@entangle` / `<x-ui.forms.search>` (which needs `$__livewire`) fatals inside an island. The sidebar search reuses the shared `<x-ui.forms.search-field>` component (`components/ui/forms/search-field.blade.php` — promoted from the `livewire.dashboard.messaging.search-field` partial on 2026-09-14 when Project became the third non-messaging consumer; all four consumers — channel/contact/project sidebars + in-chat `messaging/search.blade.php` — use the component tag) — island-safe: plain `wire:model.live.debounce` + Alpine clear + `x-teleport` overlay + `wire:ignore.self`; the `refreshSidebarOnClose` prop appends `$wire.$island('sidebar').refreshUnread()` to its close handler. **Alpine-state contract:** the component binds component-level Alpine state named `{model}Fullscreen` and `{model}Value` (e.g. `model='search'` → `searchFullscreen` / `searchValue`; `model='messageSearch'` → `messageSearchFullscreen` / `messageSearchValue`). The consumer's Alpine data object MUST declare both, or Alpine throws `... is not defined` on every island morph — which silently breaks the morph and stops new content (e.g. a sent message bubble) from rendering. `contact()` declares `searchFullscreen`/`searchValue` (sidebar) and `messageSearchFullscreen`/`messageSearchValue` (in-chat `messaging/search.blade.php`), mirroring `channel()` 1:1 (both via the `chatBase` mixin); `project()` declares them directly in `project.js` (no chatBase) — this exact omission silently killed Project's sidebar fullscreen search until fixed 2026-09-14.

### 3.2 Polling (D1 — why Contact's poll differs from Channel's)

**Index, 2026-09-30 — five fixes landed in this section the same day, in this order; each is its own paragraph below, this is just the map:**
1. **`_repollNow()` added** — action-triggered instant repoll instead of a `resetPollInterval()` that silently did nothing until the next scheduled tick.
2. **`_repollNow(true)` removed from send/saveEdit/deleteMessage, replaced by `_syncSidebarAfterOwnAction()`** — the forced tick was firing a redundant second request at the `messages` island, racing the action's own response and reverting edits/deletes back to stale content ("first change shows again").
3. **Timer-revival bug** — a hide/show bounce during an in-flight tick could kill the polling timer chain permanently; fixed by routing the queued-repoll recovery through `_repollNow()` instead of a bare tick call.
4. **Timer-doubling bug** — fixing #3 could instead leave TWO live timer chains running; closed with one `clearTimeout()` guard in `_schedulePollTick()`.
5. **`<template x-if>` → `x-show` conversion** — the actual cause of edits not visibly updating for ~10s: Livewire's morph never touches an inert `<template>`'s content, only `x-show`'s always-real DOM nodes. Channel already used `x-show`; Contact didn't. Also fixed a `$wire` magic re-resolution bug this same conversion exposed (`this.$wire` accessed after an `await`, once the triggering element had been removed by its own response's morph) — see `livewirePattern.md`'s `@island` rules for that one, it's a distinct, generalizable Livewire/Alpine gotcha, not Contact-specific.

**Contact and Channel both now poll two islands (2026-09-12 — historically Channel polled only the sidebar; that asymmetry was closed, see `resources/js/scriptPattern.md`'s "Adaptive poll scheduler" section for the full reasoning).**

`contact.js` uses the shared adaptive scheduler in `mixins/chatBase.js` — a self-rescheduling `setTimeout` chain (not a flat `setInterval`, no `wire:poll`), 10s floor, backing off to 20s while a conversation is open / 30s when idle on the sidebar, resetting to 10s on any real change. Each tick:
1. `$wire.$island('sidebar').refreshUnread()` — **always** (recompute the contact list → fresh unread counts + last-message previews for incoming messages).
2. `$wire.$island('messages').refreshActive()` — **only when `activeUserId` is set** (a conversation is open) — recompute the open thread so a new incoming message appears live without a manual reload.

**Why both:** Contact's open 1:1 conversation must reflect a new incoming message during the poll. The `activeUserId` guard avoids a wasted re-render when no conversation is open.

`visibilitychange` gates polling: `document.hidden` → `stopPolling()`, visible → `_repollNow()`. Both are wired in `init()` and torn down in `destroy()`.

**`_repollNow()` (`chatBase.js`, 2026-09-30) — the single mechanism behind every "check right now" trigger, single-flight guarded.** Before this, several call sites (`sendMessage`, `selectContact`) called bare `resetPollInterval()` on the assumption that resetting the interval variable alone would speed things up — it doesn't: the already-pending `setTimeout` still fires on its OLD (possibly backed-off) delay first, so a send/select gave close to zero real latency improvement. `_repollNow(tick = true)` fixes this properly: reset the interval, `stopPolling()` + `startPolling()` to restart the timer chain from the fresh base delay, and (when `tick` is true) immediately run a forced tick via `_runPollTick(true)` rather than waiting for that chain's first fire. Guarded by `_pollInFlight`/`_repollQueued` so a `_repollNow()` fired while a timer-driven tick is already mid-`await` doesn't spawn a second parallel polling chain (a real bug in the naive first draft — `stopPolling()`+`startPolling()` racing an in-flight tick's own `.finally` reschedule would leave two live timers forever); it queues one coalesced follow-up tick instead. `_repollNow(false)` (used by `selectContact`/`selectChannel`) resets and restarts the timer but skips the forced tick — the select flow already fires its own island call + `markRead`, so an immediate poll tick would just duplicate that work. Wired into: `selectContact()`/`selectChannel()` (no-tick variant) and the `visibilitychange` resume handler above. **Deliberately NOT wired into `detectMention()`** — see `scriptPattern.md`'s fancybox/mention section for the reasoning (keystroke cadence × a full island re-render below the 200-message threshold would be 2-3 serialized Livewire round-trips per character typed); it keeps the older bare `resetPollInterval()` only. `_destroyed` flag (set first line of `destroy()`) prevents a `_repollNow()` resolving after teardown from reviving a timer against a dead `$wire`.

**Correction, same day: `sendMessage()`/`saveEdit()`/`deleteMessage()` do NOT use `_repollNow(true)` — real bug found and fixed.** The first cut wired all three to the full forced tick, reasoning it would add a useful "receipt sync." It shipped a regression instead: `send`/`saveEdit`/`deleteMessage` are themselves `$wire.$island('messages').<method>()` calls (§7 above), so the action's own request already re-renders the messages island correctly, in order. `_repollNow(true)`'s forced `_pollTick` then fires a SECOND, independent request to that same island (`refreshActive()`) immediately after — and because Livewire Islands don't have this codebase's usual guarantees around concurrent/out-of-order responses (the `@island` rules section of `livewirePattern.md` documents a long list of exactly this class of fragility), the second response — built from a snapshot taken before the edit/send — could land after the first and morph the DOM back to the pre-action content. Symptom: editing or deleting a message, then immediately doing it again, would sometimes show the *first* change reappear. **Fix:** a new `_syncSidebarAfterOwnAction()` (`chatBase.js`) replaces `_repollNow()` at these three call sites — `_repollNow(false)` (reset+restart the timer, no forced tick) plus a direct, standalone `$wire.$island('sidebar').refreshUnread()` call (the pre-existing, already-safe original line these three call sites had before the whole `_repollNow` feature existed). The messages island is never force-refetched a second time after these three actions — it doesn't need to be, its own response already has the correct, current content. `_repollNow(true)` (the forced-tick, both-islands variant) is now used ONLY by the `visibilitychange` resume handler, where it's safe: resuming from a hidden tab isn't racing against an action's own just-issued island response.

**Known, not-yet-fixed residual of the same race class, found during the fix's own audit: `loadMoreMessages()` (scroll-triggered pagination) has no coordination against a concurrent PERIODIC (unforced) tick's `refreshActive()`.** `loadMoreMessages` guards only against itself (`_loadingOlder`), not against a same-moment periodic tick also hitting the `messages` island — the identical two-requests-one-island shape as the bug above, just via a different pair of call sites. Deliberately left open: this pairing existed in the original design (not introduced by today's fix), the window is far narrower (two independently-timed, low-frequency triggers landing sub-second apart, vs. today's bug which fired on nearly every edit), and the worst case is a self-correcting pagination-window flicker on the next tick (~10s later) rather than genuinely wrong content persisting. Closing it properly needs a per-island request lock spanning every method that touches `messages` (`loadMoreMessages`/`loadOlder`, `focusMessage`, `pingTyping`, `syncAttachments`, plus the tick itself) — real surface area, intentionally deferred rather than rushed into the same diff as the fix above.

**Second bug found in the same audit, fixed same day: the polling timer could die permanently after a hide/show bounce during an in-flight tick.** Sequence: a periodic tick is mid-`await` when the tab is hidden (`stopPolling()` nulls `_timer`, correctly lets the in-flight tick's own reschedule no-op when it resolves) — then the tab is shown again *before* that tick resolves, so `_repollNow()` sees `_pollInFlight` still true and only sets `_repollQueued`, without restarting anything. When the original tick's `finally` block picks up the queued flag, the old code called `_runPollTick(true)` directly — which runs one tick but never calls `startPolling()`, so the recurring `setTimeout` chain never re-establishes. Net effect: polling silently stops, indefinitely, until another hide/show cycle happens to land outside an in-flight window. Fix: that finally-block branch now calls `this._repollNow()` instead of `resetPollInterval()` + a bare `_runPollTick(true)` — since `_pollInFlight` is already false by that point, `_repollNow()` proceeds past its own guard and calls `stopPolling()`/`startPolling()` (re-establishing the chain) before the forced tick.

**Third bug, found verifying the second fix: that same recovery path could double the timer chain instead of restoring it.** `_schedulePollTick()`'s own self-reschedule (`F`, its `.finally`) runs as a microtask immediately after `_runPollTick()`'s finally block completes — so when the fix above calls `startPolling()` (setting `_timer` to a fresh id) INSIDE that finally block, `F` (still holding the ORIGINAL timer's now-stale id in its closure over `_timer`) runs right after, sees `_timer` non-null, and calls `_schedulePollTick()` again — overwriting `_timer` with yet another id WITHOUT clearing the one `startPolling()` just set. Two live `setTimeout` chains now run interleaved indefinitely (up to 2x poll requests), only occasionally deduped by the `_pollInFlight` guard when their timing happens to collide. Fix: `_schedulePollTick()` now calls `clearTimeout(this._timer)` before assigning a new one — `clearTimeout` on a stale/already-fired/null id is a spec-guaranteed no-op, so this changes nothing on any normal path, but structurally guarantees `_timer` can only ever track a single pending timeout no matter which code path called `_schedulePollTick()` or when. This is the actual root fix for the whole hide/show-mid-flight bug class — the second fix (`_repollNow()` in the finally) was necessary but insufficient without this guard.

### 3.2a Poll digest (P1, 2026-09-30) — the sidebar leg stops paying for "nothing changed"

**Problem this closes:** before this, every single poll tick — even the overwhelmingly common case where nothing happened since the last one — paid the full cost of `refreshUnread()`: recompute `contacts()` (the SQL-LIMIT-bound aggregation from §13.10), hydrate, shape via the presenter, stream the sidebar island, morph the DOM. At scale (many polling users), that recurring cost is the dominant load, not any single user's own activity.

**Mechanism:** `App\Services\Messaging\PollDigestService` — three static methods, deliberately mirroring the already-existing `App\Services\ProjectTask\ProjectHeartbeat` (same job for Project's cross-tab signal, same shape): `bump(string $key)` does `Cache::put($key, microtime(true), now()->addDay())` (a timestamp, not an incrementing counter — see the "why not increment" note below), `version(string $key)` reads it back (`'0'` default), `versions(array $keys)` batches via `Cache::many()`. No TTL-expiry risk in the sense that matters here: even if the 1-day TTL lapses during a genuinely idle stretch, the key resets to `'0'`, which still compares correctly against whatever the client had cached (differs → one harmless extra refresh, never a wrong skip).

**Why `Cache::put` (timestamp) and not `Cache::increment` (counter):** this is a pure equality check ("did this change since I last looked"), not a count — atomicity (increment's whole advantage) doesn't matter when losing an update still leaves the stored value different from the client's stale baseline. `increment()` also has driver-dependent behavior on a missing key (reliable on Redis, less so on file/database cache drivers) that `put()` sidesteps entirely by always unconditionally setting the value.

**Correction (2026-09-30, same-day fix, Fable-review-caught): bump site moved to `Message::booted()` model-event hooks.** Originally shipped as four direct `PollDigestService::bump()` calls inside `SendMessageAction`, `SaveEditAction`, `DeleteMessageAction`, `UndoDeleteAction` — reasoned (wrongly) to be a complete list because "there is no other write path to `messages`." That premise was false: `ContactResource` (§1) edits/deletes/restores `Message` rows via Filament, and never went through any of those four Actions, so an admin edit/delete/restore never bumped either party's digest — stale until the unrelated 10th-tick fallback. Fixed by moving the bump into `Message::booted()` (`created`/`updated`/`deleted` hooks, each wrapped in `DB::afterCommit(...)`), mirroring `ChannelMessage`'s pre-existing identical pattern exactly — now the single source of truth covering every writer (user-panel Actions, admin Filament, tinker, seeders) with one change. The four Actions' direct bump calls were removed as redundant. `UndoDeleteAction`'s two internal paths are both still covered: `Message::restore()` calls `save()` internally (fires `updated`), and its snapshot-recreate fallback (`forceFill(...)->save()` on a new instance) fires `created`.

**Correction (2026-09-30): `MarkMessagesAsReadAction` now DOES bump `dm:sv` for both parties, reversing the original "deliberately does not bump" call above.** That original reasoning only covered the *reader's own other device/tab* not needing a bump (`selectContact()` already re-renders their own view synchronously) — it never considered the **sender's** sidebar, which had no other path to learn "my message was just read" besides the 10-tick fallback. That asymmetry also broke the "Channel parity" invariant this doc claims throughout: `MarkChannelReadAction` has always bumped `ch:me`/`ch:rv` on read. Fixed by wrapping the bump for both `dm:sv:{contactId}` (sender) and `dm:sv:{viewerId}` (reader — harmless no-op for their own already-fresh view) in `DB::afterCommit`, gated on `$count > 0`. Underlying gotcha this also surfaces: the bulk `->update(['read_at' => now()])` above is a query-builder update, which fires **no Eloquent model events** — so `Message::booted()`'s hooks (§3.2a above) never see it either; this is a second, independent write path that needs its own explicit bump site, not covered by the `booted()` fix.

**Still-open, separate gap found while correcting the above (not fixed tonight):** the P3 stamp-probe's `latestMessageStamp()` (§3.3a) keys on `{id}:{updated_at}:{deleted_at}` — it does not include `read_at`, and the bulk update above does not touch `updated_at` either (query-builder updates don't auto-touch timestamps). So for a thread past the 200-message threshold that's left open, a read-receipt tick flipping from `done` to `done_all` will NOT by itself unfreeze `refreshActive()`'s skip — it'll only surface once something else changes the stamp, or on the `POLL_FALLBACK_EVERY` safety net. Below the threshold (the common case), `refreshActive()` runs unconditionally every tick regardless of any stamp, so this only matters for deep-scrolled long-lived open threads.

**Consumption:** `Main::pollDigest()` (`#[Renderless]`, zero re-render) returns `PollDigestService::version("dm:sv:" . auth()->id())` — one cache read, no DB query at all when nothing changed. `contact.js`'s `_pollTick(force = false)` calls this first; only calls `$wire.$island('sidebar').refreshUnread()` when the returned value differs from the last-seen one, OR every `POLL_FALLBACK_EVERY` (10th) tick regardless (self-healing safety net against any missed bump site — a future write path added without updating this list degrades to "stale for at most ~10 ticks," never silently forever), OR when `force = true` (the `visibilitychange` resume catch-up always does a real check, never trusts a digest value that predates the tab being hidden).

**The messages leg (open conversation) is NOT digest-gated the same way** — see §3.3a below, a different, self-contained mechanism (P3) that doesn't need a cache key at all.

### 3.3 Growing-LIMIT + anchor-window pagination (the +1-probe `hasOlder` — intentionally identical in shape to Channel §3.3)

`Main::messages()` has two modes, **both** using `take(N + 1) → count() > N → take(N)` so `hasOlder` costs zero extra queries:

- **Recent-N** (`focusAnchorId = null`, the default): direction-split `latest('id')->take(messagesLimit + 1)` per side (see "Direction-split query shape" below), merged, `hasOlder = count() > messagesLimit`, trim to `messagesLimit`, `sortBy('id')` oldest-first (recent stay at bottom).
- **Anchor** (`focusAnchorId` set by `focusMessage`): direction-split on both windows — `where('id','>=',anchor)->oldest('id')->take(6)` per side, merged+`sortBy('id')->take(6)` (anchor + up to 5 newer) + `where('id','<',anchor)->latest('id')->take(focusOlder + 1)` per side, merged+`sortByDesc('id')->take(focusOlder+1)`; `hasOlder = older.count() > focusOlder`; trim older to `focusOlder`, merge, `sortBy('id')`.

**Direction-split query shape (fixed 2026-09-29 — do not revert to a single OR query).** The original implementation ran ONE query with `where(sender=me AND recipient=peer) OR where(sender=peer AND recipient=me)`. Benchmarked against a synthetic 1.84M-row `messages` table (39,900-message hot thread, ~2.17% density — the realistic dilution for an org-wide table after sustained use across many users), that OR-query took **~9.5–12.9s** per fetch: MySQL's optimizer materializes the full OR-matched row set and filesorts by `id` before the `LIMIT` can apply (confirmed via `EXPLAIN` — `Using filesort`). Adding new mirrored composite indexes `(sender_id,recipient_id,deleted_at,id)` / `(recipient_id,sender_id,deleted_at,id)` did **not** help — MySQL didn't select them, same plan, ~8.3–10.4s.

The fix: split into two direction-scoped queries (one per side of the conversation) merged in PHP — top-K/bottom-K-of-union is provably equivalent to the single OR-query's result (a message matches exactly one direction, so no row can be missed or duplicated) — via a `$direction(senderId, recipientId)` closure in `Main::messages()` that adds `->from(DB::raw('`messages` FORCE INDEX (`idx_sent_covering`)'))`. The `FORCE INDEX` hint is required, not cosmetic: without it MySQL's optimizer unreliably picks a full backward table scan for one specific direction (cardinality misestimation at this data shape), costing ~2.2s on that half alone; with it, both halves are a pure equality-prefix seek on the existing `idx_sent_covering` (no new index needed). Measured result: **~1ms** per fetch (recent-N and anchor `id <` older direction), a ~10,000× reduction from the original OR-query, with row-for-row identical output verified across random anchors. If `idx_sent_covering`'s name ever changes, this closure's `FORCE INDEX` literal must be updated in lockstep — it is the one hidden coupling this fix introduces. The `$direction` closure itself carries no `->with()` — eager-loading `sender.profile`/`replyTo.sender` is deferred to a single `$rows->load(...)` call after the final merge/trim, so the round-trip count for eager loads stays fixed (one pass) regardless of how many direction/bound queries ran to build `$rows` (2 in recent-N mode, 4 in anchor mode).

**Same fix ported to `FocusMessageAction` and `SearchMessagesAction` (2026-09-29, same session — both had the identical pre-fix OR-query shape).** Neither action was touched by the original `messages()` fix even though both query the same hot `messages` table with the same `(sender=me AND recipient=peer) OR (sender=peer AND recipient=me)` predicate — `FocusMessageAction`'s over-limit probe (`where('id','>=',$messageId)->take($loadedLimit+1)`) is exactly as exposed as `messages()`'s recent-N branch was, since a deep-link/search-result click can land near the START of a hot thread, making `id >= $messageId` match nearly the entire conversation before MySQL can filter+limit; `SearchMessagesAction`'s full-text search adds a `MATCH(body) AGAINST(...)` filter on top of the same OR-predicate. Both now use the identical `$direction(senderId, recipientId)` closure shape (`Message::query()->from(DB::raw('\`messages\` FORCE INDEX (\`idx_sent_covering\`)'))->where('sender_id', $senderId)->where('recipient_id', $recipientId)`), running the query twice (once per direction) and merging in PHP — `FocusMessageAction` merges two independently-capped `take($loadedLimit+1)`-then-`pluck('id')` calls and counts (each direction capped at `loadedLimit+1` is sufficient to correctly answer the `count() > loadedLimit` boolean in every case, without needing the true uncapped total); `SearchMessagesAction` merges two `latest('id')->limit(LIMIT)` calls, `sortByDesc('id')->take(LIMIT)` to re-flatten to the global top-N, then a single `->load('sender:id,name')` (matching `messages()`'s deferred-eager-load convention — one relation-load pass regardless of how many direction queries ran). **Rule: any future query against `messages` filtered by "either direction of this conversation" MUST use this `$direction`-closure + `FORCE INDEX` shape, never a plain `where(...)->orWhere(...)` — the OR shape is the confirmed ~10,000× regression, not a micro-optimization.** Not yet benchmarked at the same 1.84M-row/hot-thread scale as `messages()` was — the fix is applied on the strength of the identical query shape, not a fresh benchmark; if either action is ever profiled and found to already perform acceptably at production scale (e.g. full-text's own index narrows the row set before the sender/recipient filter ever matters), that would be new information worth a follow-up note here, not a reason this port was wrong.

`loadMoreMessages()` is two lines — anchor mode: `focusOlder += 10`; else `messagesLimit += 10`; then `invalidateMessageCache()` — the same query/queries now fetch the grown window, so older rows auto-prepend above recent in one backward scan. No client array, no cap; mutations (`send`/`deleteMessage`/`saveEdit`/`undoDelete`) stay byte-identical — their existing `invalidateMessageCache()` re-queries the full grown window. `#[Computed] messages` caches per-request; `unset()` invalidates.

**Growing-window re-fetch cost, measured (2026-09-29/30) — the window is genuinely re-fetched from scratch every time, not appended to.** Confirmed by reading `loadMoreMessages()`: it does not fetch only the newest 10 rows — it grows `messagesLimit` and the very next `messages()` call re-runs the direction-split query at the new, larger `take($messagesLimit + 1)`, from row 1 again. The same full re-fetch also happens on every adaptive-poll tick (§3.2) while that conversation stays open, regardless of whether the user scrolled since the last tick. Benchmarked on an isolated `perf_benchmark` DB (seeded then dropped same session — not kept), hot 1:1 thread, 50,000 messages between two users, ~300K total `messages` rows for realistic index depth, MySQL EXPLAIN-verified `Using where` (no filesort — the 3-column equality prefix `sender_id, deleted_at, recipient_id` resolves fully in-index, `FORCE INDEX (idx_sent_covering)` unnecessary to force here but present to match production):

| Window size (`messagesLimit`) | Single fetch (median) | 10 consecutive re-fetches (simulating 10 poll ticks with the conversation left open) |
|---|---|---|
| 10 (default) | ~1.4ms | — |
| 100 (a few "load more" clicks — typical case) | ~3.1ms | ~3.15ms/tick sustained |
| 1,000 | ~97ms | — |
| 5,000 | ~86ms (high variance, up to ~590ms) | ~153ms/tick sustained |
| 10,000 | ~311ms | — |
| 25,000 | ~1,200ms | — |

**Verdict:** for typical usage (a handful of "load more" clicks, window in the low hundreds) the re-fetch cost is negligible — single-digit milliseconds, not worth optimizing on its own. The cost only becomes real once a user scrolls tens of thousands of messages deep into one thread and leaves it open: at that point every poll tick pays ~100ms–1.2s in DB time alone, repeated every 10–30s for as long as that tab stays open, and growth is visibly super-linear past ~2,000 rows (PHP-side `merge()->sortByDesc()->take()` over two several-thousand-row collections, not just the SQL cost, contributes here). This is the concrete, measured justification for the stamp-probe fix below (P3) — not a hypothetical worst case. It does **not** justify calendar-month pagination or any other restructuring of the happy path, which stays exactly as fast as this table shows for realistic scroll depths.

### 3.3a Message-window stamp-probe (P3, 2026-09-30) — caps the poll-tick cost of a deep-scrolled thread without touching the pagination UX

**What this does NOT do:** grow `messagesLimit` forever is untouched — "load more" still works exactly as before, at any depth, no cap on how far back a user can scroll. This fix only changes what an *automatic poll tick* costs once someone has scrolled deep and left the thread open.

**The key insight that makes a cheap probe possible and provably correct:** edit and delete are both gated to the absolute-last-message-in-the-thread only (§13, "delete gate"). That means the *entire* mutable surface of a conversation — has anything been added, edited, or removed — is fully observable from the newest row alone. A one-row index seek (`{id}:{updated_at}:{deleted_at}`) is a complete change detector, not a heuristic: if that triple is unchanged, nothing in the thread changed, full stop. (If that edit/delete gate is ever widened — e.g. editing any own message, not just the last — this stamp must widen with it, e.g. to a `MAX(updated_at)` over the window or an explicit mutation counter; it would silently stop detecting changes to older messages otherwise.)

**Mechanism:** `#[Locked] ?string $pollStamp = null` + `private const MESSAGES_STAMP_THRESHOLD = 200`. `refreshActive()` now, before doing anything else: if `messagesLimit > 200` AND not in anchor-jump mode (`focusAnchorId === null` — anchor mode already fetches a small bounded window regardless, no cost problem to solve there), compute `latestMessageStamp()` — reuses the exact same `$direction(senderId, recipientId)` closure from `messages()` (§3.3, same `FORCE INDEX`), but calls `->latest('id')->first(['id', 'updated_at', 'deleted_at'])` on each side instead of a full `take(N)` fetch, takes whichever side's row has the higher id, and appends the peer's typing-cache presence (`Cache::get("typing:dm:{peer}:{me}")`) so a gated skip can never freeze the typing indicator — that indicator is normally refreshed as a side effect of the very re-render this probe might skip. If the resulting stamp equals `$this->pollStamp`, call `$this->skipRender()` and return immediately — no `invalidateMessageCache()`, no `unset($this->activeContact)`, no island re-render, no DOM morph. If it differs, store the new stamp and fall through to the unchanged full-refresh path.

**Why this shape and not a reuse of anchor mode:** anchor mode (`focusAnchorId`/`focusOlder`, §3.3) already exists and *looks* reusable for "show a window around a point," but it's built for a different job — jump-to-one-message deep links — and its "newer" side is hardcoded to a small fixed count (6). Naively switching into anchor mode once `messagesLimit` crosses the threshold would shrink the visible window from however much the user scrolled down to 6 messages: a visible regression, not a fix. Properly fixing that would mean parameterizing anchor mode's window size and correctly resetting it at every one of anchor mode's several existing reset call sites (`selectContact`, `backToList`, `send`, `focusMessage`, …) — real risk of a missed-reset bug, the same class of bug that already bit this session twice elsewhere (a missed `.group` class, a wrong argument to a shared toggle). The stamp-probe was deliberately built as new, orthogonal state instead.

**Why `$pollStamp` needs zero reset call sites anywhere — the property this whole design is chosen for:** a stale or simply-wrong stamp value can only ever cause the equality check to fail, which triggers one ordinary full refresh and immediately self-corrects — it can never cause a wrong *skip*. Switching conversations without resetting `pollStamp` is harmless by the same logic: the new conversation's `messagesLimit` resets to 10 (far under the 200 threshold), so the guard is simply inactive until that conversation is also scrolled deep, at which point the first stamp computed for it is compared against the old conversation's leftover value — virtually guaranteed to differ, correctly forcing a real refresh. Nothing needs to touch `pollStamp` outside `refreshActive()` itself.

**Accepted trade-off, stated plainly:** while a thread is both past the threshold AND genuinely idle (stamp actually unchanged), read-receipt checkmarks, the peer's typing indicator (mitigated above by folding typing into the stamp), and the peer's presence dot (piggybacked on `refreshActive()` via `unset($this->activeContact)`) also stay frozen for that tick — because nothing re-renders at all. The instant anything real happens (a message, an edit, typing starts), the very next tick's stamp differs and everything catches up in one shot. Below the 200-row threshold — true for the overwhelming majority of real usage — none of this applies; behavior is byte-identical to before this fix.

**Verified via `tests/Feature/Livewire/Dashboard/ContactTest.php`:** `test_refresh_active_stamp_is_stable_when_unchanged_and_moves_when_a_message_arrives` — crosses the threshold via 20× `loadMoreMessages()` calls (can't `->set('messagesLimit', …)` directly in a test since it's `#[Locked]`), asserts `pollStamp` stays identical across two consecutive unchanged `refreshActive()` calls, then asserts it changes once a new message is created. **Not independently verified:** that `skipRender()` correctly suppresses the island's actual HTML output on a real island-scoped `$wire.$island('messages').refreshActive()` browser round-trip — Livewire's testing harness executes the method body identically whether or not `skipRender()` is called, so the property-level assertions above are the closest PHPUnit can get; the no-live-browser constraint on this session means the wire-protocol-level suppression itself is unverified. `skipRender()` is a long-standing, widely-used Livewire core method (`Component::skipRender()`), not new/experimental API, which is the basis for shipping this with reasonable confidence anyway.

**`FocusMessageAction::execute` returns `?bool`** (3-way): `null` = invalid/not-in-conversation/no-such-message → `Main::focusMessage` bails; `false` = the target is inside the recent window → clear any stale anchor + `invalidateMessageCache` + `dispatch('record-focus', type:'message')`; `true` = target is beyond the window → set `focusAnchorId=id`+`focusOlder=5` + `invalidateMessageCache` + dispatch. The 3-way return lets Main branch without re-querying; the over-limit check itself is a +1 probe (`take(loadedLimit + 1).count() > loadedLimit`).

### 3.4 What this module deliberately does NOT have

- **No modals** — true architectural fact (1:1 needs no create/manage-members modal; every active user is reachable).
- **No `HasMenuState` / bare-key badge added by Contact itself** — unread is surfaced only via `data-total-unread` on the sidebar `<aside>`, read by `contact.js`'s `MutationObserver` (`syncPushNotify`) to fire browser push notifications. Don't add a *new* nudge/badge row to `notifications` from within this module — see `feedback_no_nudge_badge_proposals`. This does NOT cover `App\Services\Menu\Notifications\ContactNudge` — a pre-existing, separate sitewide bell layer (`contacts-controller:nudge`, see `statePattern.md`) that already exists outside Contact's own architecture; `MarkMessagesAsReadAction` correctly reconciles it (§13.11), that is a bugfix to existing infra, not new badge surface.
- **No `wire:poll`** — replaced by JS `setInterval` + `visibilitychange` (§3.2) so polling is pauseable and island-scoped.
- **No `chat-ready` event / `dispatchReady` parameter** — removed (D2); see §3.5.
- **No membership gate / channel type / create-or-browse flow / owner concept.**

### 3.5 The D2 decision — `chat-ready` is gone, do not reintroduce it

The pre-migration code dispatched a `chat-ready` event from server-side `selectContact` whenever `dispatchReady = ($focusMsg <= 0)`, and `contact.js` listened `x-on:chat-ready.window` → `scrollToBottom(false)` (+ mobile textarea focus). This **raced** with `record-focus`'s `scrollIntoView` for a `focus_msg` deep link — both competed for `#msg-viewport`'s scroll position; the deferred `$nextTick` overrode the synchronous record-focus scroll. The `dispatchReady` flag was a patch on a fundamentally racy mechanism.

The migration **removed `chat-ready` entirely** (no event, no `dispatchReady` param, no `x-on:chat-ready` listener). The deep-link scroll-to-bottom is restored **race-free** instead: `contact.js init()` runs a **mount-only** block, gated on the exact old condition (`activeUserId set && focus_msg <= 0`), reading `focus_msg` from `window.location.search` and `activeUserId` from the snapshot. It is mutually exclusive with the `focus_msg` path (which uses `record-focus` message-scroll) and uses a different scroll container from `record-focus.js`'s `type:'people'` sidebar-row scroll — so no double-scroll, no race. See §13.2.

## 4. Data model (no new tables from this migration)

Contact rides the existing `messages` + `users` tables. No migration was added by the island migration. (The covering indexes that make `FetchContactsAction` fast — `idx_sent_covering` (`[sender_id, deleted_at, recipient_id, id]`) and `idx_received_covering` (`[recipient_id, deleted_at, read_at, sender_id, id]`) — live in the `2026_09_19_000026_create_messages_table.php` migration; `FetchContactsAction` went 1103ms → 8.8ms via `UNION ALL` + covering indexes. See `project_perf_audit_2026_06`. `idx_sent_covering` is also `FORCE INDEX`-hinted by `Main::messages()`'s direction-split queries — see §3.3 — a second hard dependency on this exact index name.)

`messages` columns Contact uses: `sender_id`, `recipient_id`, `body`, `attachments` (JSON), `is_edited`, `read_at` (nullable), `reply_to_id` (nullable FK → messages), `created_at`, `deleted_at` (SoftDeletes). `sender_id`/`recipient_id` are `onDelete('cascade')` (a deleted user's messages are removed, not orphaned); `reply_to_id` is `onDelete('set null')`. The `ناشناس` sender fallback in the presenter is defensive — unreachable under cascade (the FKs are defined in the same `2026_09_19_000026_create_messages_table.php` migration referenced above; no schema change was added by the island migration).

## 8. Forms catalog

- `MessageComposerForm`: `body` (`#[Validate('required_without:attachments|string|max:2000')]`), `attachments` (array, validated), `replyToId` (`#[Validate('nullable|exists:messages,id')]` — the reply target; `SendMessageAction::resolveReplyToId` re-scopes it to the conversation, so the form-level `exists` is a first-line guard only). `reset()` after send (clears `replyToId`). Channel parity (`ChannelMessageComposerForm::replyToId`). **Soft-deleted nuance:** Laravel's `exists` rule queries the raw table (no `SoftDeletes` scope), so a soft-deleted reply target *passes* `exists` — but `resolveReplyToId` uses `Message::withoutTrashed()`, so it's dropped to `null` and the reply link is silently not created. The double-layer is intentional; the action is the authoritative gate.
- `EditMessageForm`: `editingBody` (`#[Validate('required|string|min:1|max:2000', onUpdate: false)]`). **Correction, 2026-09-30: textarea binds plain `wire:model="edit.editingBody"` (deferred), NOT `.live` — real bug found and fixed.** The `.live` binding queued one request per keystroke, auto-scoped to the `messages` island (this textarea sits inside it) — Livewire processes same-island requests strictly in order, so a normal-length edit could queue 15-20 keystroke requests, and the Save click's own `saveEdit()` request landed at the END of that same queue, appearing to "hang" for several seconds before the save even reached the server (server-side `Main::saveEdit()`/`SaveEditAction` were never the bottleneck — both execute and invalidate the cache in one fast pass). Deferred `wire:model` eliminates the per-keystroke request entirely; the typed value syncs as part of whatever request fires next (the Save click itself). `onUpdate: false` stays relevant regardless of live/deferred — it's still about not validating `required` on an empty-mid-retype value the one time validation DOES run (on save). `reset()` after save.

**Two deliberate bare-`$wire` exceptions (Channel parity, NOT full re-renders to worry about):**
- `#[Js]` methods `cancelReply()`/`cancelEdit()` — bare `$wire.cancelReply()` / `$wire.cancelEdit()` execute **purely client-side** (Livewire ships the JS string to the browser and runs it there); **zero backend round-trip, zero re-render**. This is the lightest possible state clear.
- `replyTo(id)` — bare `$wire.replyTo(id)` IS a parent round-trip, but it mutates only `composer.replyToId`, which **no island blade reads during render** (the reply chip is Alpine-local `replyingTo`). Livewire only re-streams islands whose rendered output changed, so in practice no island HTML is re-streamed. Channel uses the identical bare `$wire.replyTo(id)`. (Do NOT infer from this that any bare `$wire` call is safe — it is safe here only because the mutated prop is render-invisible.)

**Bare `$wire.method()` from Alpine otherwise triggers a FULL re-render** — that's why the undo toast goes through `contact.js`'s `undoDelete()` (captured `wire`, `$island('messages').undoDelete()`, then `_syncSidebarAfterOwnAction(wire)`) instead of calling `$wire.undoDelete()` bare. Moved from an inline `x-on:click` chain in `messages.blade.php` to a component method 2026-10-01 — the inline form's `.then(() => $wire.$island('sidebar')...)` re-resolved `$wire` from a button inside the island the first call had just morphed, the exact post-`.then()` fresh-read the binding rule above forbids (see §13 entry 21).

## 12. Dos and Don'ts (consolidated hard rules)

### DO
- ✅ Reach computeds inside islands via `$this->` (`$this->activeContact`, `$this->contacts`, `$this->presenter`). Public properties can stay bare (`$activeUserId`, `$search`, `$filter`, `$hasOlder`).
- ✅ Use a **local** `$p = $this->presenter` inside a partial's `@php` block when calling presenter methods (`$p->sidebar(...)`, `$p->messageGroup(...)`).
- ✅ Poll **both** islands (sidebar `refreshUnread` always + messages `refreshActive` when a conversation is open) — D1, §3.2.
- ✅ Use `$wire.$island('messages').method()` for every Alpine-initiated server call (so it stays island-scoped, not a full re-render).
- ✅ Scope message edits/deletes by `sender_id = auth()->id()` (in `Main` and the actions).
- ✅ Reuse the shared `livewire.dashboard.messaging.search-field` partial for the sidebar search — it is island-safe (plain `wire:model` + Alpine, no `@entangle`).
- ✅ Keep MySQL 5.7-safe: `unionAll`, `leftJoinSub`, covering indexes — all fine.
- ✅ No code comments (project rule). Inline Persian for partials; `lang/fa` keys only for Filament.

### DON'T
- ❌ Don't use a bare computed (`$activeContact`, `$contacts`, `$messages`, `$presenter`) inside `@island` or its `@include` partials — it throws on the refresh path (masked by `Livewire::test`).
- ❌ Don't use `@entangle` / `<x-ui.forms.search>` / `<x-ui.modals.*>` inside an island — they need `$__livewire` which nested anonymous components don't inherit.
- ❌ Don't reintroduce `chat-ready` / `dispatchReady` — it raced with `record-focus` (D2, §3.5). The mount deep-link scroll is handled race-free in `contact.js init()`.
- ❌ Don't "fix" the dual-island poll back to Channel's sidebar-only pattern — it would lose live incoming-message updates in the open conversation (D1, §3.2).
- ❌ Don't use `wire:poll` — polling is JS `setInterval` + `visibilitychange` (pauseable, island-scoped).
- ❌ Don't call `$wire.method()` bare from an Alpine `x-on:click` — it triggers a full re-render. Wrap with `$wire.$island('<island>').method()`.
- ❌ Don't trust `Livewire::test()->html()` alone for island code — it does a full render and masks island-only scope bugs. Add a real island-refresh check (see §14).
- ❌ Don't add `HasMenuState` / a bare-key badge / a *new* nudge type to `notifications` from within this module — unread is surfaced only via `data-total-unread` + the push-notify observer. (The pre-existing `ContactNudge` bell layer is separate infra, not covered by this rule — see §3.4/§13.11.)
- ❌ Don't erase/truncate `fateh` DB data without explicit session approval; benchmark only in `perf_benchmark` DB.

## 13. Known edge cases / gotchas

1. **Bare `$activeContact` / `$p` in islands** — fixed (Phase B). All island partials use `$this->activeContact` / local `$p = $this->presenter`. The `render()` injection was dropped only after this was clean (Phase A step 2). See §10 for the audit table.
2. **`chat-ready` scroll race** — fixed (D2). `chat-ready` removed; mount deep-link scroll is race-free in `contact.js init()` (mutually exclusive with the `focus_msg` path; different scroll container from `record-focus` `type:'people'`). See §3.5.
3. **`@entangle`/`<x-ui.forms.search>` in sidebar island** — fixed by reusing the shared `messaging/search-field` partial (plain `wire:model` + Alpine, no `@entangle`).
4. **Sender deleted** — `sender_id`/`recipient_id` are `onDelete('cascade')` (a deleted user's messages are removed, not orphaned); `reply_to_id` is `onDelete('set null')`. The presenter's `ناشناس` sender fallback is defensive — unreachable under cascade.
5. **Edit window** — 600s is the `Main::$editTimeLimit` default, passed to `SaveEditAction`/`DeleteMessageAction` and the presenter's `can_edit`/`can_delete` flags; one source, no separate constant to keep in sync.
6. **Undo after force-delete** — `UndoDeleteAction` falls back to recreating from the snapshot if the soft-deleted row was already force-deleted.
7. **Delete gate** — only the absolute last message in the thread is deletable (`can_delete && id === $this->lastMessageId`); edit is gated identically by `can_edit && id === $this->lastMessageId` (same absolute-last window — edit/delete in sync).
8. **`downloadAttachment` from inside the island** — returns a `BinaryFileResponse` (non-standard Livewire response); file downloads bypass the DOM-morph response entirely, so island scoping is irrelevant. Manually verify (plan §6).
9. **`refreshUnread`/`refreshActive` `unset()` is redundant-but-harmless** — Livewire `#[Computed]` cache is per-request-only; `->call()` re-hydrates a fresh instance with an empty cache, so the round-trip itself surfaces new DB rows. The `unset()` is belt-and-suspenders (matches Channel). PHPUnit verifies the observable contract (a refresh round-trip surfaces new rows), not the invalidation mechanic — the real island-poll verification is the §14 browser pass.
10. **Sidebar pagination (`$contactsLimit`) is now a real SQL `LIMIT` on `contacts()` itself (superseded 2026-09-30 — was render-only slicing, see history below).** `FetchContactsAction::execute()` takes an optional `?int $limit` and appends `->limit($limit)`; `Main::contacts()` passes `$this->contactsLimit + 1` (the same +1-probe idiom used everywhere else in this codebase — §3.3), sets `public bool $hasMoreContacts = $users->count() > $this->contactsLimit`, then trims. `sidebar.blade.php` no longer slices anything — `$contactList = $p->sidebar($this->contacts, ...)` IS the page, `@forelse($contactList as $contact)` reads it directly, and the load-more button gates on `$this->hasMoreContacts`. `contactsLimit` is now `#[Locked]` (client can't inflate the LIMIT, matching `messagesLimit`'s existing precedent) — this also means a **test cannot `->set('contactsLimit', …)` to widen it**; use `->set('search', …)` to scope a specific row into the page instead (see the four tests fixed in this same pass). **Why the reversal:** `contacts()` used to compute and return the FULL matching list every render (including every 10–30s poll tick's `refreshUnread`) — cost scaled with total org headcount, unbounded. The original reasoning against a SQL `LIMIT` ("would require splitting the shared list query") turned out to be wrong on inspection: nothing about the query shape actually required the full list — `totalUnread`/`allContactIds`/`onlineContactsCount`/`totalOccasions` (the four things that genuinely need an org-wide, not page-wide, view) were decoupled onto their own cheap, independent queries instead (see §6.2's `visibleContactsBase` entry) — a "split the shared query" was never the only option. Test: `test_sidebar_load_more_visibility_matches_whether_the_list_exceeds_the_page_size` now asserts the `hasMoreContacts` flag directly rather than comparing `contacts()`'s returned array length against the page size, since that length can no longer exceed `contactsLimit` by construction. **Channel got the identical treatment same day** (`channelPattern.md` §13) — do not re-diverge the two.
    **History (superseded claim, kept for context):** this entry originally argued the render-only slice was deliberate because "splitting the shared list query isn't justified at current per-user list sizes," matching Project's `$projectsLimit` precedent (`livewirePattern.md`'s Project section). That reasoning is now retired for Contact/Channel specifically — Project's `$projectsLimit` is unaffected by this change and may still be render-only-sliced; port this same SQL-`LIMIT` treatment to Project only if it's ever shown to need it, don't assume it from this entry alone.
11. **Stale bell nudge after reading a conversation (fixed 2026-09-04).** `MarkMessagesAsReadAction`'s `read_at` write is a mass `Message::withoutTrashed()->...->update(...)` (Eloquent Builder, not a model instance) — mass updates fire **no** `updated` model event, so `App\Services\Menu\Notifications\ContactNudge`'s `Message` `updated` trigger (registered in `NudgeServiceProvider`) never reconciled on read. The bell's per-sender "N unread messages" notification (`contacts-controller:nudge`) stayed unread forever, even after the conversation was fully read and the sidebar dot/`data-total-unread` had already cleared correctly (those go through `StateService::flush()`, which the action always called). Scoped to `backToList()` only, not `selectContact()` (per explicit user request) — this is a deliberate, safe asymmetry (nothing else keys off client/server `mobileShowChat` lockstep). **Known residual risk (reviewer-flagged, not fixed):** no request-cancellation exists for overlapping `$island()` calls on the same component — a `backToList()` tap immediately followed by a `selectContact()` tap, on a slow connection, could theoretically have the `backToList()` response land *after* `selectContact()`'s and stomp its state back to "list view." Narrow, low-probability, UI-only; revisit only if actually observed.

Channel's identical refactor (`channelPattern.md` §16 gotcha 14) hit the equivalent bug in `doCancelInvite`, same root cause, same fix shape. **Takeaway for any future DRY-ing of `$wire.$island(...)` call sites: a helper method is safe for the first call in a chain only — every call after an `await`/`.then()` must use a captured reference, and "I added a helper so I don't need the capture anymore" is the exact reasoning that caused both regressions.** `selectContact()`'s `.then(() => this._sidebar())` chain was re-audited against this exact rule (2026-10-01, independent review) and found safe-by-reasoning despite the bare helper call after a `.then()`: the first call in that chain (`_isl().selectContact(id)`) only re-renders the **messages** island, never the **sidebar** island the triggering row lives in, so the row can't have been detached by the time `_sidebar()` resolves — the specific precondition for this bug class (the chain's own earlier call removing its own trigger) doesn't hold here. Not changed; documented so a future pass doesn't "fix" it into an unnecessary capture or, worse, assume it's broken without checking.

## 16. Channel↔Contact alignment audit (the full identical / similar / divergent map)

The 2026-08 alignment pass made Contact mirror Channel's `@island` architecture 1:1 everywhere functionality allows. This section is the authoritative diff map — read it before "fixing" a Contact/Channel asymmetry, because some divergences are deliberate (§16C).

### 16A. Identical (byte-for-byte or structurally same)

- **Two-island layout** — `@island('sidebar')` + `@island('messages')` in the root view; `#[Isolate]` on the class.
- **`#[Computed]` + `$this->`-in-islands rule** — computeds reached via `$this->`, local `$p = $this->presenter` in partials; bare computeds fatal on refresh (§3.1).
- **Shared `messaging/search-field` partial** — sidebar search reuses the same partial as Channel; Alpine-state contract `{model}Fullscreen`/`{model}Value` declared in both `contact()` and `channel()`.
- **`+1`-probe `hasOlder` pagination** — `take(N+1) → count() > N → take(N)`; recent-N + anchor-window modes (§3.3).
- **`focusMessage` 3-way `?bool`** + global `record-focus` standard; `FocusOnRecord` trait + `focus_msg` deep-link.
- **`#[Async] markRead`** — fire-and-forget read-marking on select (Channel: `markRead`; Contact: `markRead`).
- **`#[Js] cancelReply` / `cancelEdit`** — pure client-side state clear, zero backend round-trip.
- **Reply flow** — `composer.replyToId` form prop (Channel: `ChannelMessageComposerForm::replyToId`); `replyTo(int)` parent setter; `SendMessageAction::resolveReplyToId` scopes the reply target to the conversation (drops out-of-conversation IDs); reply chip is Alpine-local; `send()` reads the form, takes no replyToId arg; `composer->reset()` clears `replyToId` after send.
- **State-setter vs data-mutation call discipline** — state-setters (`replyTo`/`cancelReply`/`cancelEdit`) use bare parent `$wire.method()`; data mutations needing a re-render (`send`/`saveEdit`/`deleteMessage`/`focusMessage`/`loadMoreMessages`/`selectContact`) use `$wire.$island('messages').method()`.
- **Alpine local-state counter** — composer char counter uses `x-data="{ len: 0 }" x-effect="len = ($wire.composer.body||'').length"` + `x-on:input="len = $el.value.length"` (no `x-ref`/`$refs` — dead `x-ref` on morphed islands throws `Cannot read properties of undefined (reading '_x_refs')`).
- **No `x-ref` on morphed islands** — `#msg-viewport` / `#msg-ta` are `getElementById` lookups, not `$refs`.
- **`closeOverlays`** — calls local `cancelReply()`/`cancelEdit()`/`cancelDelete()` (each does Alpine-clear + server-sync).
- **Sender-scoped edit/delete guards** + 600s edit window; undo-delete snapshot; attachment path-traversal confinement; `downloadAttachment` non-standard response.
- **Polling shape** — JS `setInterval` + `visibilitychange` (no `wire:poll`); `refreshUnread`/`refreshActive` `unset()` belt-and-suspenders.
- **No nudge/badge/`HasMenuState`** — unread via `data-total-unread` + push-notify observer only.
- **Shared messaging partials (`livewire/dashboard/messaging/`)** — `legends` (badge+feature legend modal), `header-actions` (search + `filter_alt` type-filter toggle `typeFilterOpen` + highlight + maximize + info, + per-conversation sound-mute `@slot`), `empty-state` (empty shell + stats slot), and `quote-chip` (one blade, `useQuoteChip()` click) are centralized in one folder and `@include`/`@component`-rendered, not `<x-*>` (not used elsewhere → don't live in `components/`). `quote-chip` shares only after a JS alignment: `useQuoteChip()` is folded into `chatBase` (both inherit via `...chatBase()`) and Channel's `startReply` hides the chip (Contact's already did) — so both blades bind the identical `useQuoteChip()`. The in-chat message-search overlay (`search`) is shared too — both headers `@include` it with a `$placeholder`/`$overlayTitle` pair (the only two strings that differed). Three per-`$msg` blocks inside `messages.blade.php` are also shared via `@include(['msg' => $msg])`: `reply-quote` (reply preview, byte-identical), `message-attachments` (image/file list, byte-identical), and `message-actions` (hover copy/reply/edit/delete toolbar — param-free like the other two: the edit-button guard is inlined as `can_edit && $msg['id'] === $this->lastMessageId`, matching the delete gate `can_delete && $msg['id'] === $this->lastMessageId`; both absolute-last, in sync; its attachment-download button guards `count($msg['attachments'] ?? [])` — the `?? []` added 2026-10-01 after a test-fixture gap surfaced it, real presenter output always carries the key so this is a defensive hardening, not a behavior change). Canonical rule + `@component`/`Htmlable`-slot rationale: `channelPattern.md` §10.1.

### 16B. Similar (same intent, shape differs by 1:1-data-model necessity)

- **Sidebar population** — Channel: your memberships (`whereHas channel_members`); Contact: all colleague-visible users (`User::visibleOnBoard()`, no membership gate — §2). Both use `FetchContactsAction`/`FetchChannelsAction` with `UNION ALL` + `leftJoinSub` + covering indexes.
- **Select guard** — Channel: membership exists; Contact: `User::getCachedAllOptions()->has($id)`. Both silent-`return` on fail (not 403).
- **Polling legs** — both poll sidebar `refreshUnread` always; Contact ADDS `messages.refreshActive` when a conversation is open (D1, §3.2) because a 1:1 open thread must reflect incoming messages live. Channel's open pane re-renders on interaction only. Do NOT "fix" Contact back to sidebar-only.
- **Edit & delete gates (aligned 2026-08-04)** — both modules identical: edit `can_edit && id === lastMessageId`, delete `can_delete && id === lastMessageId` (absolute last message only; edit/delete share the same window — in sync).
- **Avatar** — Contact: avatar on the last-in-group bubble (both directions); Channel: every row.

### 16C. Divergent (deliberate, do NOT align — functionality-first)

1. **Edit-flow state model** — Channel: 4-field Alpine-local edit state (`isEditing`/`editingMsgId`/`editingBody`/`editingOriginal`); the edit textarea binds Alpine `editingBody`, and `startEdit` calls `$wire.editMessage(id)` (server-authoritative reload, single round-trip, instant because the textarea is Alpine-local). Contact: `editingMsg={id,body}` (Alpine, toggle-only) + the WIRE form prop `edit.editingBody` (the textarea binds `wire:model.live="edit.editingBody"`); `startEdit` sets `$wire.set('edit.editingBody', body)` for instant content and **does NOT call `$wire.editMessage(id)`**. Reason: Contact's textarea is wire-bound, so a server `editMessage` reload would flash the textarea empty until the round-trip resolves (a real UX regression), and `SaveEditAction` already validates sender-scoped — so `editMessage` would add a redundant second round-trip. Contact's path is one round-trip, instant, equally secure. This is the single structural divergence retained for functionality; everything else is 1:1.
2. **No membership gate / no create-or-browse / no channel type / no owner / no join-leave** — Contact is 1:1, every active user reachable (§2).
3. **Dual-island poll** — §3.2 (D1).
4. **`chat-ready` removed** — §3.5 (D2); Channel never had it.
5. **`BuildsChatBubbles` composition, not `BuildsMessageGroups`** — `ContactPresenter` composes the shared `App\Traits\BuildsChatBubbles` (§9), but keeps its own local `messageGroup()`/`messages()` rather than the shared `App\Traits\BuildsMessageGroups` that `ChannelPresenter`/`ProjectPresenter` compose. Contact's read model is `read_at`-based (a per-message boolean), not Channel/Project's per-member cursor + `readersMap`/`readerSummary` shape, and Contact has no `@mention` feature — the shared group-shaping pipeline doesn't fit and shouldn't be forced to (full rationale in `livewirePattern.md`'s "Shared chat-bubble/message-group traits" section). Composing `BuildsChatBubbles` also fixed a previously-dead feature: its `replyPreview()` includes `reply_to.id` (the replied-to message's id), which `messages.blade.php`'s reply-preview block already reads for its click-to-jump `scrollToMessage(id)` handler but, under the old locally-duplicated bubble code, never received correctly — the click-to-jump now works.

### 16D. Why the `#[Async]` / `#[Js]` / island patterns are lighter on the backend

- **`#[Js]` (`cancelReply`/`cancelEdit`)** — the method body is a JS string shipped to the browser and executed there; **no HTTP request, no re-render, no DB**. The client runs one `$wire.composer.replyToId = null` setter. Pure client load — a single property assignment — negligible.
- **`#[Async]` (`markRead`)** — from the browser, Livewire fires the call **without awaiting** it and **without re-rendering**; the server runs the action and returns nothing to re-stream. The user's next action isn't blocked on the read-marking query. (When called internally from `selectContact` server-side, it runs synchronously — same query, no extra cost.)
- **`$wire.$island('name').method()`** — only the named island's HTML is re-computed and streamed, not the whole component. `selectContact`/`send`/`saveEdit`/`loadMoreMessages` re-render just `messages` (or `sidebar` for `refreshUnread`), so the sidebar list isn't re-queried when you send a message, and vice versa.
- **`#[Computed]` + `unset()`** — computed caches are per-request; `unset()` marks them stale so the next read re-queries only what changed, once.

Net: the backend does **less per interaction** (smaller diffs, fewer full re-renders, fire-and-forget writes) and the client does a few extra one-line JS setters — a favorable trade, not a load shift onto the client.

## 17. Archived contacts filter — 4th sidebar tab (2026-10-01)

**The gap this closes:** §2's invariant ("every active user is reachable") has a silent corollary — once a colleague goes `inactive` or is reclassified `UserType::Guest`, `visibleOnBoard()` drops them from the sidebar entirely (§2, §7's `FetchContactsAction` row). Past conversations with that person didn't disappear from `messages`, but there was no way back to them: no archive, no search fallback (sidebar search filters the already-`visibleOnBoard()`-scoped list, so it can't surface someone outside that scope either).

**Query path — `FetchArchivedContactsAction` (new sibling Action, not a branch inside `FetchContactsAction`).** Mirrors the module's own precedent for "alternate list, same shape, different population" — `Channel\Actions\FetchJoinableChannelsAction` sits beside `FetchChannelsAction` the same way. The action reuses `FetchContactsAction`'s exact `UNION ALL` sent+received → `last_message_id` subquery shape (§7), with two changes: `joinSub` (**INNER**, not `leftJoinSub`) so only users with at least one non-soft-deleted message either direction survive — this is the "has existing message history" half of the spec, enforced at the join level rather than a post-filter; and `whereNot(fn($q) => $q->visibleOnBoard())` instead of `->visibleOnBoard()` — De Morgan's expansion of `active() && type != Guest` gives `status != 'active' || type == 'guest'`, exactly "excluded by `visibleOnBoard()`," without weakening or duplicating that scope's own definition (a change to `scopeVisibleOnBoard()` automatically propagates to both the normal and archived population with zero extra maintenance). No `online`/`unread` sub-filter parameter — neither is meaningful for an inactive/Guest population and the spec didn't ask for them.

**Wiring — one branch inside `contacts()`, not a sibling computed.** `Main::contacts()` picks the Action (`FetchArchivedContactsAction` vs `FetchContactsAction`) based on `$this->filter === 'archived'`; every line after the fetch — `+1`-probe `hasMoreContacts`, the `whereIn('id', $messageIds)` last-message hydration, the per-user shaping `->map()` — is untouched and shared across all four filter values. This was the deciding factor over a sibling `archivedContacts()` computed: the shaping logic is 100% identical regardless of population source (same output contract `{id,name,profile,unit,section,last_message,unread_count,is_online,presence,...}` that `ContactPresenter::sidebar()` already consumes), so a sibling computed would have duplicated that shaping verbatim for zero benefit. `setFilter('archived')` needed **no** special-casing of its own — it already does nothing but `$this->filter = $filter; $this->contactsLimit = 30;`, and `contacts()` being the single recompute point means the branch is the only place that needed to know about the new value.

**Pagination — identical `+1`-probe idiom, no new mechanism.** `contactsLimit + 1` passed to `FetchArchivedContactsAction::execute()`'s `$limit` exactly like the normal path; `hasMoreContacts` is set from the same `$users->count() > $this->contactsLimit` check regardless of which Action produced `$users`. The sidebar's `<x-ui.buttons.load-more island="sidebar">` button (§13.14) needed zero changes.

**Read-only-vs-sendable decision — resolved by existing code, not a new guard.** `Main::selectContact()`'s guard — `User::getCachedAllOptions()->has($userId)` (`self::orderBy('name')->pluck('name','id')`, `User.php`) — has **no** `active()`/`visibleOnBoard()` scoping, includes every user regardless of status/type. So selecting an archived contact from the new tab already works today, unguarded, the same as it always has for any user id — this feature doesn't open a new hole, it surfaces a path (the archived tab) to a selection guard that was already this permissive. **Sending**, however, is already blocked one layer down: `SendMessageAction::execute()` does `User::visibleOnBoard()->findOrFail($recipientId)` (§7) **before** writing anything — an archived recipient throws `ModelNotFoundException`, caught by `Main::send()`'s generic `\Exception` handler, which reports it and shows "خطای سیستمی رخ داده است." That guard is untouched by this feature — it was already there, already correct, already the authoritative security boundary. The only real gap was **UX**, not security: a user could type a message to an archived contact, hit send, and get a confusing generic-error toast instead of understanding why. Closed by `Main::activeContactArchived()` (`#[Computed]`, zero extra query) + a `composer.blade.php` branch: when true, the footer renders a plain archive-icon notice ("این مخاطب دیگر در فهرست فعال نیست؛ تاریخچهٔ گفتگو قابل مشاهده است اما امکان ارسال پیام جدید وجود ندارد") instead of the textarea/send button, both branches `wire:key`-ed (`composer-archived`/`composer-active`, morph-safety). Editing/deleting your own already-sent messages in an archived thread is deliberately left untouched — `SaveEditAction`/`DeleteMessageAction` only ever checked `sender_id = auth()->id()` + the time window, never the recipient's status.

**UI — plain 4th tab, no badge, matching `online`'s precedent.** `sidebar.blade.php`'s filter-tab `@foreach` gained `['archived','آرشیو']` (reusing TaskBoard's existing term for the same concept) alongside `all`/`unread`/`online`, same markup, same `wire:click="setFilter(...)"` (auto-scoped, no island wrapping needed — the tab button lives inside the `sidebar` island itself). No unread-style count badge — matches `online`'s own precedent and the project's standing "no new nudge/badge row" rule (§3.4/§12).

**Tests** — `tests/Feature/Livewire/Dashboard/ContactTest.php`: inactive-with-history → archived yes / all no; Guest-type-with-history → archived yes; inactive-without-history → neither; active-with-history → never archived; soft-deleted-only history → not archived; `+1`-probe `hasMoreContacts` true/false across the 30-row page boundary.
