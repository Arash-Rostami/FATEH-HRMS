# Project module — patterns & conventions

Consolidates Project-specific conventions for the user-panel `App\Livewire\Dashboard\Project\Main` and the admin `App\Filament\Resources\ProjectResource`. Cross-panel/general rules (chat-bubble traits, `FocusOnRecord`, `@island`, file-attachment preview, `ManagesTaskModal`) stay in `livewirePattern.md`; Project-audience handling stays here. Mirrors `channelPattern.md` in shape.

## Master-detail split view — reusing Channel/Contact's sidebar+workspace shell, and `@island` DOES nest

Project was rebuilt from a single stacked column into a Channel/Contact-style master-detail shell: `.chat-widget` (the shared full-width bordered-card flex row, `dashboard.css`) holding a right-side `<aside>` project list (`project/sidebar.blade.php`, same avatar-initial-chip row styling as `contact/sidebar.blade.php`) and a left-side `<main>` workspace (header + tab-selector + tab content). `.max-widget` + `maximizeMixin()` (spread into `project()`'s Alpine factory exactly like `dms()` does) gives the whole shell a fullscreen toggle via the header's `open_in_full`/`close_fullscreen` button — reuse, not a new mechanism.

**The workspace island's `@if($this->activeProject)`/`@else` branch roots are `wire:key`-ed `class="contents"` wrappers (`pane-active`/`pane-empty`, 2026-09-14)** — same morph cure as Channel/Contact (see channelPattern.md root entry): morphing between structurally different unkeyed branches left stale nodes in the DOM (Channel/Contact's "lingering shell at mobile width" flake); keyed wrappers make morph swap whole branches as units, `display:contents` keeps `<main>`'s flex layout untouched, and project switches still morph in place since the key stays `pane-active` (only the *branch*, not the project id, is keyed).

**`@island` blocks CAN nest** — confirmed against `vendor/livewire/livewire` v4.2.1's `SupportIslands/Compiler/IslandCompiler.php`, which tracks a nesting level and resolves deepest-first; no prior nested example existed in this codebase before Project. `project.blade.php` wraps the whole workspace in `@island(name: 'workspace')`, and the pre-existing per-tab `@island(name: 'activity'|'teamChat'|'projectCalendar', always: true)` blocks now live nested inside it — the heartbeat poller's existing `$wire.$island('activity').refreshActivity()`-style scoped calls keep working unchanged at the inner level.

**Selecting an item in the sidebar must NOT re-render the sidebar itself** — the actual optimization Channel/Contact rely on (matters at scale: hundreds of rows per user). The row's click handler is `x-on:click="selectProject(id)"` (an Alpine method), never `wire:click`. That method does `this.$wire.$island('workspace').selectProject(id)` (runs the real state change, returns only the workspace island's HTML) `.then(() => this.$wire.$island('sidebar').refreshSidebar())` (a second, cheap, near-empty-body call whose only job is to re-render the sidebar island against now-current server state, picking up the new `$activeProjectId` for the active-row highlight — mirrors `channel.js`'s `.then(() => $wire.$island('sidebar').refreshUnread())`). Two small targeted requests beat one full-component request when the untouched region (the list) is the expensive one to re-render. This is deliberately NOT applied everywhere — `switchTab`/`postComment`/`toggleReaction`/etc. stay plain `wire:click`/`wire:submit`, matching the pre-existing convention in every tabbed module app-wide.

**Plain `wire:click` inside a nested island auto-scopes to its nearest enclosing island — it does NOT trigger a full component render.** Livewire's client walks up the DOM from the clicked element (`closestIsland()`) to find island metadata; a `wire:click` fired from inside `workspace` (or the nested `activity`/`teamChat`/`projectCalendar`) only re-renders that island, same as an explicit `$wire.$island(...)` call would, just auto-detected instead of hand-specified. **Two traps this produces, both hit and fixed in Project:** (1) `sidebar`/`workspace` MUST carry `always: true` (matching the inner per-tab islands) — without it, any action whose triggering element is NOT inside an island (see next point) renders as unscoped, and an island with no `always: true` responds to an unscoped render with an empty `mode:'skip'` fragment, silently leaving stale DOM in place. `createProject`/`updateProject` hit this: their trigger lives inside `<x-ui.modals.base>`'s `<template x-teleport="body">`, which Alpine physically relocates to `document.body` at runtime, so `closestIsland()` finds no enclosing island and the request ships unscoped — the newly created/edited project silently failed to appear until an unrelated island-scoped action ran later. (2) A `wire:click` that genuinely NEEDS a full render (because it opens a modal living entirely outside both islands, whose non-`wire:model` content like `<x-ui.modals.action>`'s baked-in `:action="..."` won't refresh from an island-scoped response) must escape auto-scoping with `x-on:click="$wire.method()"` instead. `openCreate`/`openEdit` hit this: as plain `wire:click`, they auto-scoped to `sidebar`/`workspace` respectively, so the modal opened with correctly pre-filled `wire:model` fields but a stale title/save-action still bound to the previous mode — editing a project while `createProject` was still wired could silently create a duplicate instead of saving the edit.

**Sidebar list is search-filtered and page-limited, entirely inside the existing `sidebar` island — no new island, matching every other paginated list in this app.** `Main::myProjects()` now returns `['rows' => [...], 'hasMore' => bool, 'total' => int]` instead of a flat array (the two consumers, `sidebar.blade.php`'s `@forelse` and `project.blade.php`'s `<x-ui.title :count="...">`, read `['rows']`/`['total']` accordingly). `$search` filters `visibleProjectsWithMembership` in PHP (`str_contains` on lowercased name), NOT in the shared SQL query — filtering at the SQL level would also filter `pendingInviteProjects()`, which reads the same shared computed and must never be search-scoped (an invite toast has to surface regardless of what's currently typed in the search box; regression-guarded by `test_search_does_not_filter_pending_invite_projects`). `$projectsLimit` (default 30, `+30` per `loadMoreProjects()` click via the standard `<x-ui.buttons.load-more>` button — the same component `project/activity.blade.php`'s `loadOlderActivity` and `project/report.blade.php`'s `loadMoreReport` already use) truncates the filtered set client-visibly; `updatedSearch()` resets it to 30 so a new search always starts from page one. The search box is the shared `<x-ui.forms.search-field model="search" debounce="200">` component (adopted 2026-09-14 for full channel/contact parity — floating label + fullscreen maximize; `updatedSearch()` still resets pagination). `project()` MUST declare `searchFullscreen`/`searchValue` Alpine state for the maximize half to work (contactPattern.md's Alpine-state contract — omitted initially, fullscreen was dead until added). The load-more button stays a plain Livewire binding living inside `project/sidebar.blade.php`, which is already wrapped by `@island(name: 'sidebar')` — per the auto-scoping rule above, they need no `$wire.$island()` JS call and no dedicated island of their own.

Mobile back-nav mirrors Channel/Contact too: `Main::$mobileShowChat` (set true on `selectProject()`, false via `backToList()`) toggles `<aside>`/`<main>` visibility below `md:`, and the header's mobile-only back button calls an Alpine `backToList()` that does `this.$wire.backToList()` (a plain, unscoped call — full re-render is fine here since it's an infrequent nav action, not a hot path).

## Project report tab — expandable inline-detail row + filter toolbar + enriched summary, additive service enrichment

The Project گزارش tab was enriched with expandable inline-detail rows (Alpine single-open on `tbody`), a filter/sort toolbar, and a by-status/overdue summary bar — all additive, zero regression to the existing report.

**Filter toolbar is one row: search input, «همه» reset, then four `livewirePattern.md` solid-button dropdowns (scheme/department/مسئول/اولویت), each `x-data="{ open:false }" @click.outside`, selected-state = `primary` bg, with a per-dropdown clear button; search is `wire:model.live.debounce.300ms`.** The status filter is **not** in this row — it lives in the `report/summary` chips, which double as clickable filters (`wire:click="setReportStatusFilter(key)"`, `aria-pressed` + active ring when `$reportStatusFilter === key`); the «همه» reset button is `setReportStatusFilter('')`. This is a deliberate DRY collapse: the summary already shows per-status counts, so the status chips ARE the status filter (overdue chip stays display-only). The label filter and the action-source pair (حوزهٔ منبع اقدام + منبع اقدام) were removed from the report tab as unnecessary — `query()` retains only defensive dead `label`/`action_source` clauses, never fed anymore. Dropdown option values pass through `{{ \Illuminate\Support\Js::from($value) }}` (not raw string interpolation) so a value containing a quote can't break the `wire:click` directive. Row-detail label *display* chips keep the `crc32($label) % 4 → ['amethyst','sapphire','sage','gold']` tone mapping copied **verbatim** from `card.blade.php` (ground truth) so colors match across modules — but they are plain spans now, not filter buttons. The opened dropdown panel adopts the activity tab's mention-popup glass — `--tool-amethyst-bg`/`color`/`text`, `border-[var(--tool-amethyst-color)]/30`, the `shadow-[0_12px_32px_color-mix(in_srgb,var(--md-sys-color-scrim)_22%,transparent)]` scrim shadow, `rounded-2xl`, and the scale/translate `x-transition` — so every popup in this module shares one amethyst glass language. `reportLimit` is `#[Locked]` (server-side `loadMoreReport` still increments it) so a snapshot can't inflate the paginated `rows()` `take()` into a memory/DoS vector.

**No N+1 — all row detail comes from already-eager-loaded relations + aliased subqueries.** `query()` eager-loads `project`/`assignee`/`detail`/`creator` and adds `replies_count` as an `addSelect` COUNT subquery mirroring the existing `last_activity_at` MAX subquery (no relation-name dependency). `presentRow()` reads `$task->detail?->checklist`/`->attachments` (JSON columns on the eager-loaded `TaskDetail`) and appended accessors (`deadline_formatted`, `created_formatted`, `urgency_state`) — pure hydration, no per-row queries. `filterOptions(int $projectId)` uses `toBase()->get(['assigned_to','user_id'])` (one query, no model hydration) plus two `TaskDetail` distinct-plucks (departments, schemes) — returns only `assignees`/`departments`/`schemes` (the `labels` pluck and the action-source-domain/action-source queries were dropped when those filters were removed; saves 3 queries per report render), memoized via `#[Computed]` + `Cache::flexible` with a `ModelCacheVersion`-embedded key. Co-located partials: `summary`/`filters`/`row-detail`/`sort-th` under `livewire/dashboard/project/report/` (the main `report.blade.php` stays a thin composer). Tests: `ReportingServiceTest` (presentRow keys, summary `by_status`+`overdue`, filterOptions, search/priority filters, FIELD sort asc/desc + nulls-last, progressPercent regression) + a Livewire `ReportTest` (setReportSort flip/new-field, setReportFilter, clearReportFilters, reportData shape, reportFilterOptions, status-chip-as-filter reflow). Legend: `project/legend.blade.php` gained four rows (expandable row, sort, filter/search, summary bar).

## `CalendarRange` additive month-math (`WEEK_DAY_LABELS`, `advanceMonths`) — read-only calendar tab only

`app/Values/CalendarRange.php` gained two additive members, used exclusively by Project's month-grid calendar tab (`Project\Main::calendarDays()`/`prevMonth()`/`nextMonth()`):
- `public const WEEK_DAY_LABELS` — the 7 Sat-first Persian day labels (`ش`...`ج`).
- `public static function advanceMonths(string $navigationDate, int $deltaMonths): string` — try/catch-safe Jalali month arithmetic (`Jalalian::addMonths`/`subMonths`, falling back to today on a malformed input), returning the new `Y-m-d` navigation string.

These live on the value object rather than a new trait because only Project ever needed them — a trait implies multiple composers, and `CalendarRange` was already the natural, DB-free home for pure Jalali range math. **`Tab\Calendar` (the existing full scheduler) is deliberately untouched** — it keeps its own separate unwrapped `Jalalian::` calls and its own `CalendarPresenter`'s private `WEEK_DAY_LABELS` const (see `livewirePattern.md`'s Calendar Scheduler section); the two now happen to carry the identical 7-label array in two places because both independently need it, not because one delegates to the other. Project's calendar is a lightweight read-only month-grid (no drag/resize/multi-view) — a materially different feature from `Tab\Calendar`'s full scheduler — so consolidating them would couple two modules that don't otherwise interact.

## Project Activity tab enrichment — attachments, edit/delete-own-comment, date dividers, copy/pin/search/export (all additive, `Reply`-model-level)

Eight low-effort enrichments landed on Project's `activity` tab (the `Reply`-backed audit log merging user comments + system events), scoped deliberately to the audit-trail use case — none of it turns Activity into a second chat, matching the "Activity vs Team Chat" split documented in `project/legend.blade.php`.

**Two `DeleteReplyAction`/`SaveEditReplyAction` classes, mirroring `ToggleReplyReactionAction`'s exact shape (own-comment ownership + time window + project-visibility, `repliable_type`-dispatched heartbeat bump):**
- `DeleteReplyAction::execute(int $replyId, int $userId): bool` — hard-deletes (no `deleted_at` on `Reply`, so no undo-snapshot machinery, unlike Channel's soft-delete-backed equivalent). Gated to `whereIn('type', [Comment, Attachment])` at the query level — a `StatusChange`/`Assignment`/`Archive` system entry can never be deleted even by the user who triggered it, since those rows are the permanent audit record, not chat messages. File cleanup is already automatic via `Reply::booted()`'s `deleting` hook (`CleansAttachedFiles`) — untouched, no new logic needed there. **Also re-checks `Project::visibleTo($user)` on the reply's own project before deleting (2026-09-12)** — ownership + type + window alone let a user removed from the project still delete their own recent comment there; the visibility re-check closes that.
- `SaveEditReplyAction::execute(int $replyId, int $userId, string $body): bool` — same ownership/type/time-window/project-visibility gate. **"Edited" is tracked via `payload['edited_at']`, NOT `updated_at !== created_at`** — deliberately, because `ToggleReplyReactionAction::execute()` also calls `->save()` on the same row (to persist `reactions`), which would touch `updated_at` on every reaction toggle and falsely mark a never-edited comment as edited. Stamping `payload` (already a JSON column, empty for real user comments) avoids modifying `ToggleReplyReactionAction`'s already-shipped, already-tested behavior at all — a zero-regression constraint the user explicitly set for this whole feature batch.
- **Relocated to `App\Services\ProjectTask\` (from `TaskBoard\Actions\`) — see `app/Services/servicePattern.md`.** All three (`DeleteReplyAction`, `SaveEditReplyAction`, `ToggleReplyReactionAction`), plus `CyclePriorityAction`/`ReorderTaskAction`/`UpdateTaskStatusAction`, are called from both `TaskBoard\Main` and `Project\Main` — per `servicePattern.md`'s rule ("a second module already calls the same logic" ⇒ Service, not a module-private Action), a proven second consumer means these belong in the Services layer, not a Livewire module's own `Actions/` folder. The `Reply`-is-a-shared-domain-model reasoning that originally justified keeping them under `TaskBoard/Actions/` was correct about the sharing, just wrong about the folder — `App\Services\ProjectTask\` is the folder that reasoning actually points to (renamed 2026-08-29 from `App\Services\TaskBoard\`, once the namespace held enough genuinely cross-module classes — `ChannelProvisioner`, `CreateProjectAction` — that "TaskBoard" stopped describing its scope). Tests stay at `tests/Feature/Services/ProjectTask/<Action>Test.php` per `coreTestPattern.md`'s "one file per target" rule (`ToggleReplyReactionActionTest` is the sibling reference), in addition to the Livewire-level coverage in `ProjectTest.php`.

**`Project\Main` gained `use Livewire\WithFileUploads;`** — a real, previously-latent gap: `activityComposer`/`chatComposer` (`ReplyForm`) both had a `files`/`attachments` field from day one, but neither composer view ever wired an actual `<input type="file" wire:model>` to it, so the trait was never needed until Activity's composer got one. Without it, file uploads silently 500 (`MissingFileUploadsTraitException`) — caught by a test exercising `set('activityComposer.files', [...])->call('postComment')`, not by a lint.

**`activityFeed()`'s row map gained `user_id`/`can_modify`/`is_edited`; `groupedActivityFeed()` is new**, mirroring `groupedTeamChatMessages()`'s exact `groupBy(fn($e) => Carbon::parse($e['created_at'])->setTimezone(config('app.timezone'))->toDateString())` pattern for date-divider grouping — same "امروز"/"دیروز"/`toJalali('j F Y')` label logic already used for Contact/Team-Chat. `can_modify` is `false` for every non-`comment`-type entry unconditionally (not just gated by ownership), so a system entry can never show edit/delete UI regardless of whose `user_id` is on it. Every mutating method (`postComment`, `loadOlderActivity`, `toggleReaction`, `saveEditedComment`, `deleteComment`) unsets both `activityFeed` and `groupedActivityFeed` — the same computed-on-computed invalidation rule the team-chat section established in `livewirePattern.md` (Livewire does not auto-invalidate a `#[Computed]` that depends on another `#[Computed]`).

**Copy/pin/search/export are pure client-side additions, consolidated into the shared `project()` Alpine factory (`resources/js/components/alpine/data/project.js`), not a new isolated inline `x-data` block on the Blade root** — this codebase already migrated away from inline per-view `x-data` blocks once (see `scriptPattern.md`'s "Feed blades stay clean" note), so a second one would have been a regression of that cleanup, not a new pattern. `matchesActivityFilter(id, text)`/`anyActivityVisible(entries)`/`exportActivity(entries)` take their data as plain `@js()`-wrapped scalar/array arguments passed directly at each call site (the same safe, ubiquitous pattern as `togglePin(@js($id), @js('scope'))` elsewhere in this codebase — Laravel's `Js::from()` applies `JSON_HEX_QUOT|JSON_HEX_APOS|JSON_HEX_AMP|JSON_HEX_TAG`, so the encoded value is safe to embed directly inside an already-double-quoted HTML attribute), never a hand-built JS object-literal string. `Alpine.store('pinned')`'s `KEYS`/`sets` maps gained one additive `activity` scope (`pinned-activity` in localStorage) — the existing `isPinned`/`togglePin`/`getPinned` API needed no changes. Export respects the current search/pinned-only filter (exports what's currently visible, not unconditionally everything) — reuses the same `matchesActivityFilter` the render-time `x-show`s use, so there's exactly one filter predicate, not two that could drift.

**Activity coverage was extended to 4 more `TaskActivityType`s (`DeadlineChange`/`PriorityChange`/`LabelChange`/`ProjectChange`) — this Activity tab picks them up automatically, zero changes needed here.** Since `activityFeed()` reads through the shared, type-agnostic `ActivityLogger::feedFor()`/`render()` (§ above), any new `TaskActivityType` + Renderer registered in `App\Services\ProjectTask\ActivityLogger::RENDERERS` shows up in this feed for free the moment a project task's `deadline`/`priority`/`labels`/`project_id` changes — no Project-side code changed for this. The companion TaskBoard-only "تاریخچه" tab (a per-task chronology for tasks with **no** project, since this Activity tab already covers project tasks) is documented in `app/Livewire/Dashboard/TaskBoard/taskboardPattern.md` §16 — it never appears in Project's own task-edit modal (the same shared `form.blade.php`/`taskFormTabs()`), because its visibility gate requires `project_id === null`, which is never true for a task opened from within a project.

**Attachment display reuses the plain-link pattern already proven in `ths/reply-bubble.blade.php`** (`\App\Models\Reply::resolvePublicAssetUrl($file['path'])` + a direct `target="_blank"` anchor) — no new Action, no download route. This is simpler than Channel's `DownloadChannelAttachmentAction` on purpose: Channel's download needs a per-request authorization check because channel messages can be private 1:1/group conversations; `Reply` attachments on a project/task comment don't carry that extra visibility gate, so the direct-link pattern TaskBoard's own task-reply thread already uses (`taskboard/form.blade.php`'s reply tab) is the correct-weight precedent, not Channel's heavier one.

**Copy-link deep-focus (`?focus_entry={id}`) needed a dual client+server mechanism because `Project\Main` is `#[Lazy]`, unlike Contact/Channel.** The copy-link button builds `route('projects', ['open'=>.., 'tab'=>'activity', 'focus_entry'=>$id])`. Server-side, `focusRecord()` reads `focus_entry` and calls `focusActivityEntry($id)`, which bumps `activityLimit` past the target's rank (so it's actually in the rendered window) and dispatches `record-focus` type `activity` — mirroring Contact's `focusMessage()`/`focus_msg` pattern exactly, including returning `true` to suppress the trait's default `project`-type dispatch (the same double-dispatch-suppression rule from `livewirePattern.md`'s FocusOnRecord section), falling back to the default dispatch when the target id is invalid. **This alone was not enough**: `Project\Main::placeholder()` renders a wholly separate view with no `x-data="project()"` at all, so on a fresh full-page load the Lazy placeholder-to-real swap happens after `record-focus.js`'s global Livewire-event listener is already registered, but empirically the scroll still didn't fire reliably (verified against a real browser, not just tests — the server-rendered HTML and dispatch were both confirmed correct via `assertDispatched`/`assertSeeHtml('data-rf=...')`, ruling out a PHP-side bug). Fix: `project()`'s own `init()` (which only runs once the real, non-placeholder content is mounted — confirmed reliable specifically because that swap is what creates `x-data="project()"` in the first place) also reads `focus_entry` straight from `window.location.search` and drives its own retry-based `scrollToActivityEntry()`, a client-side mirror of `record-focus.js`'s `scrollToRecord`. Both mechanisms stay: the Livewire-dispatch path is what the other 17 focus-capable modules rely on and still matters for `wire:navigate` transitions to an already-mounted Project page (where `init()` does NOT re-run), while the URL-driven fallback is what actually closes the gap for a fresh full-page load of a `#[Lazy]` component. Not redundant cruft — two different navigation paths, each needing its own trigger.

**`project()` also gained `...clipboardMixin()`** (`resources/js/components/alpine/mixins/clipboard.js`) for the copy-text/copy-link buttons — `copyText(text, message)`, not a raw `navigator.clipboard.writeText()` call, so the secure-context guard, `execCommand` fallback, and the app-wide toast (`<x-ui.modals.toast/>`, `window.addEventListener('toast', ...)`) all fire consistently with every other copy button in the app.

## Project team-chat tab shares the Channel/Contact chat background UI, but each module picks its own pattern (2026-08-27; pattern picker added 2026-09-14, per-module storage split 2026-09-14)

The team-chat tab mirrors the Channel/Contact "chat bg" pattern: a `<x-ui.decor.chat-pattern x-show="backgroundPattern === 'on'"/>` overlay inside a `relative` root (`chat.blade.php`), plus a header trigger (`project/header.blade.php`, gated `@if($activeTab === 'teamChat')` so it only appears on the chat tab; the overlay only renders there too, since `chat.blade.php` is included only on that tab). The three modules share the same **UI and mechanism**, not the same **state** — each persists to its own `localStorage['chat-settings:<scope>']` key (`chat-settings:contact`, `chat-settings:channel`, `chat-settings:project`), `{isHighlighted, backgroundPattern, backgroundPatternType}` (`backgroundPatternType` added 2026-09-14, default `'mesh'`), so Channel/Contact/Project-teamChat can each be on a different pattern (or off) at the same time — turning it on in one does NOT light up the others. `chatBase(scope)` takes the scope as a parameter (`contact.js`/`channel.js` pass their existing `SCOPE` constant, e.g. `...chatBase(SCOPE)`) and closes over `` `chat-settings:${scope}` `` for `_persistChatSettings()`'s write; each of `contact.js`/`channel.js`'s own `init()` restore block reads the identically-templated key. ## Phase 2 spike (2026-08-28) — nested-in-island components: closed, don't retry without a materially different mechanism

`.claude/plans/project-refactor-plan.md`'s Phase 2 gate (§3/§5) asked whether a real, independently-defined `<livewire:...>` component could be nested inside an already-live `@island(..., always: true)` block and receive fresh mount-param props across that island's own scoped refresh, without losing the child's own internal state. **Verified FAIL, twice, empirically** (throwaway spikes, both fully deleted — nothing shippable from either): plain mount-param props go stale forever once the child's `wire:key` has been seen before by the parent (Livewire's `SupportNestingComponents` spoofs the re-mount with an empty stub); busting the key for fresh props forces a full remount (new `wire:id`, child state destroyed) — no middle ground.

**`#[Reactive]` does not close this gap either — the exact mechanism was traced and empirically retested.** `Livewire\Attributes\Reactive` (`SupportReactiveProps`/`BaseReactive`) is real and does exist in this Livewire version (4.2.1), and on paper looks like the fix (a `mount.stub` event captures fresh params during a spoofed mount, and `BaseReactive::hydrate()` is supposed to apply them to `#[Reactive]`-tagged properties). In practice it does nothing here: `SupportNestingComponents`'s `pre-mount` hook, when it detects the child was already rendered by this parent (`hasPreviouslyRenderedChild`), **hijacks the mount entirely** — the child's PHP component object is never instantiated, so `hydrate()` (the only place `#[Reactive]` applies a fresh value) never runs. The captured `mount.stub` params are silently discarded at the next `flush-state`. Confirmed via a real `Livewire::test(Main::class)` sequence: after a scoped `selectCalendarDay()` refresh, the nested child's response collapsed to `<div wire:id="..." wire:name="..." wire:key="..."></div>` — same `wire:id` (no remount), but zero content, no `wire:snapshot`, and the fresh prop value nowhere in the response.

**Conclusion at the time: don't attempt nested-in-island components for Calendar/Kanban/Activity/TeamChat with stock Livewire mount-param or `#[Reactive]` props — both are dead ends for this specific topology (a child re-synced via a still-live island's scoped refresh, not a fresh full-page mount).** This specifically killed **prop-pushing into an already-mounted nested child** — it did not, in hindsight, close the door on nested child components per se. See the next section — the door reopened once the actual requirement was reframed.

## Reopened, differently (2026-08-28) — always-rendered hidden children + `Livewire.dispatch()` bridge, no prop-pushing needed

A Fable 5 ideation pass (prompted by the Phase 2 dead end, requested via the Agent tool with `model: fable`) produced the key reframe: **none of the 4 remaining tabs actually need a prop pushed into an already-mounted child.** Enumerated per-tab: `activeProjectId` changing should force a full remount anyway (that's the *desired* behavior — `selectProject()` already resets every per-tab filter/limit manually); poll-triggered refreshes carry no value to push, just a "re-query" signal; shared computeds (`mentionCandidates` etc.) can be recomputed per-child, matching the already-shipped `HasReportSummary` trait precedent. So the Phase 2 spike disproved a mechanism nobody needs — not the underlying feasibility of nested children surviving a live island/workspace region.

**Proposed mechanics** (Fable's Proposal 2): each tab becomes its own component, mounted unconditionally (not gated by `@if($activeTab===...)`) with a `wire:key` tied ONLY to `activeProjectId` (stable across tab switches, changes — genuine remount — only on project switch), visibility toggled via a `hidden` CSS class rather than conditional rendering, and cross-tab refresh delivered via `Livewire.dispatch(eventName)` + `@eventName.window="$wire.method()"` on the child's own root — the same bridge Phase 1's `project-report-refresh` already proved for Report.

**Validated via a real, interactive, throwaway spike before committing** (per this project's "no UI change without live-browser verification" standard) — a genuine 7th "تست (موقت)" tab, `App\Livewire\Dashboard\Project\TestSpike` (now deleted, this section is what's kept), mounted unconditionally inside `workspace` exactly per the proposed mechanics above, exposing 3 unambiguous signals: a `mountedAt` timestamp (proves remount vs no-remount), a `counter` + increment button (proves local state survives), and a `refreshCount`/`lastRefreshedAt` pair (proves the dispatch bridge actually fires, independent of whether the underlying watched value — `liveTaskCount` — happened to change, which was ambiguous in an earlier version of the spike and corrected). **All three passed a real browser check**, confirmed directly by the user clicking through each scenario, not inferred from server-side tests alone.

**What this validates and what it doesn't — scope the next phases accordingly.** Confirmed: an always-rendered, hidden-via-CSS nested child inside `workspace` survives tab switches with state intact, remounts correctly on project switch via key change, and reliably receives `Livewire.dispatch()`-bridged refreshes. **Not yet exercised by the spike**: `WithFileUploads` inside this always-rendered-hidden-child topology (Activity/TeamChat both use it; `livewirePattern.md` already documents a related-but-different island-upload gotcha — verify fresh, don't assume it transfers), `kanbanDrag.js` tolerating a real child-component boundary, the task-modal-open cross-cutting concern (`openProjectTask` needs the same dispatch-bridge treatment Fable outlined, replacing direct `wire:click`), and 4 simultaneous key-change remounts firing together on one project switch. **Sequencing for the real implementation, lowest-risk first: Calendar (no composer/upload/drag state) → Kanban (drag + task-modal bridge) → Activity+TeamChat together (file uploads, composer drafts, shared `mentionCandidates`)** — same risk ordering the original plan used, just with the now-proven mechanism instead of the disproven one.

## Focus-chip was showing on ordinary project selection, not just search deep-links (2026-08-31)

Real bug, user-reported: the "نتیجهٔ جستجو" focus chip (`components.dashboard.header.focus-chip`,
shared across every module using `FocusOnRecord`) appeared after simply clicking a project in the
sidebar, and again on every subsequent tab switch. Root cause, one line:
`selectProject(int $projectId)` unconditionally did `$this->open = $projectId;` — and `selectProject()`
is called by both the genuine deep-link path (`focusRecord()` → `selectProject()`) **and** the
sidebar's ordinary `wire:click`/`wire.$island('workspace').selectProject(id)` path
(`resources/js/components/alpine/data/project.js`). Since `$open` is `#[Url]`-bound (from
`FocusOnRecord`), every ordinary click pushed a real `?open={id}` into the browser address bar — so
even a hard refresh re-hydrated it as a "genuine" deep link, `mountFocusOnRecord()` fired
`focusRecord()` again, and the chip kept reappearing. Confirmed as the true single-line cause by
checking every sibling `FocusOnRecord` consumer: `Channel::selectChannel()` / `Contact::selectContact()`
never touch `$open` for ordinary selection — they track "currently open" via their own dedicated
properties (`activeChannelId`-equivalent) and leave `$open` exclusively to the deep-link path. Project's
`selectProject()` was the only outlier.

**Fix: delete the line, nothing else.** `selectProject()` no longer writes `$this->open`. The genuine
deep-link path needs no compensating change — `mountFocusOnRecord()` already hydrates `$open` from the
URL *before* calling `focusRecord($projectId)`, which passes that same id into `selectProject()`; there
was never a need for `selectProject()` to re-assign it. No new property, no blade/JS change, no
`#[Url(except:)]` tuning — matches the already-correct Channel/Contact shape exactly.

**A more complex first attempt (shadow `focusedViaLink` flag gating the blade `open` var) was tried and
reverted** — it tested green in isolation but didn't fix the live symptom, because it only gated *what
rendered*, not the underlying `$this->open = $projectId` write. That write kept polluting the real
browser URL regardless of the blade-level gate, so a hard refresh on the polluted URL legitimately
re-hydrated `open` and re-showed the chip — looking like the fix failed when the actual leftover write
was simply never removed. Lesson: when a symptom is driven by a `#[Url]`-bound property, gating the
*display* is not enough if the underlying property is still being written on the wrong code path — the
write itself has to stop.

Tests: `test_select_project_updates_active_project_id_without_disturbing_open`,
`test_selecting_a_second_project_ordinarily_still_leaves_open_untouched`,
`test_arriving_via_a_genuine_search_deep_link_still_shows_the_focus_chip` (the two pre-existing
`assertSet('open', $project->id)` tests were rewritten — they had encoded the buggy behavior as the
expected contract).

## Known debt, flagged not fixed — `ManagesTaskModal::duplicateTask()` has no project-scoping (non-exploitable today, architectural decision needed)

## Placeholder root `x-data` must match the real view's root, or Alpine silently never binds it (2026-08-28)

Bug, real and reproduced (browser console `Alpine Expression Error: … is not defined`): `calendar.blade.php`'s and `kanban.blade.php`'s root `<div>` each carry a literal `x-data` (`{ calView: 'grid' }`, `{ moreOpen: false }`) that their `#[Defer]` placeholders (`calendar/placeholder.blade.php`, `kanban/placeholder.blade.php`) did not. The Defer swap (placeholder → real content) morphs the SAME root DOM node in place — it does not replace it — because that root is the component's own `wire:id`-tracked element. Alpine only binds `x-data` the first time it walks a node; once it walked the placeholder's root with no `x-data`, the attribute appearing later (after the morph swaps in real content) is never picked up, so every descendant `x-show`/`x-bind` reading that scope's state throws `is not defined` and breaks silently (the view-toggle, `moreOpen`-gated filter row, etc). `Report`/`Analytics`/`Activity`'s placeholders don't have this problem because their `x-data` (if any) lives on genuinely NEW nested DOM the morph creates, not on the preserved root. **Fix: any future `#[Defer]` component whose real view's root carries `x-data` must give its `placeholder()` view's root the exact same `x-data` literal** (copy-paste the object shape, don't just default it, since a mismatched shape re-triggers the bug in reverse). Verified inert while investigating: `calendar.blade.php`'s and `kanban.blade.php`'s own internal `wire:key="calendar-{{ $activeProjectId }}"`/`"kanban-{{ $activeProjectId }}"` root-div attributes are dead duplicates, not a contributing cause — traced through `vendor/livewire/livewire`'s `SupportNestingComponents::provide()`'s `mount` hook, which injects the REAL `wire:key` (the one from `project.blade.php`'s `<livewire:dynamic-component :wire:key="$this->tabs[$activeTab]['key']">` tag, e.g. `tab-projectCalendar-{id}`) via `Utils::insertAttributesIntoHtmlRoot()` — placed first in the tag, ahead of the template's own literal `wire:key`. Browsers drop later duplicate attributes on parse, and Livewire's own parent-child key bookkeeping (`SupportNestingComponents::setParentChild()`) lives in server-side store state, never re-derived from the child's own rendered HTML text — so the leftover inner `wire:key` was left in place, not removed, since removing it changes nothing.

**Second follow-up (2026-08-29): same root-preservation family, one level deeper — un-keyed sibling panes with a different shape than the placeholder's skeleton.** Reported symptom: `Project\Calendar`'s grid view rendered visually crumpled (squished into a narrow column) on true first paint (navigating directly to `?open={id}&tab=projectCalendar`, no prior click) and again on every subsequent full page reload — but a single real Livewire round-trip (`prevMonth`/`nextMonth`/`calendarToday`) always fixed it in place, and toggling back from list view to grid view then looked correct too. This is a DIFFERENT bug from the two above (verified: `calendar.blade.php`'s own `x-data`/refresh-listener on its root already matched the placeholder correctly) — root-caused by capturing the real Livewire `/livewire-*/update` network response and JSON-parsing it directly (not string-grepping the raw body, which produces false positives against other components' embedded placeholder HTML): the server ALWAYS sent correct HTML for `dashboard.project.calendar` in isolation — this is purely a client-side DOM-reconciliation bug, not a server/cache/CSS-timing one. `calendar/placeholder.blade.php`'s skeleton has 3 top-level children after the header row (header-skeleton, grid-skeleton, table-stripe-skeleton); the real content has 2 (`x-show="calView === 'grid'"` pane, `x-show="calView === 'list'"` pane) — neither pane carried a `wire:key`. Without keys, Livewire's morph on the placeholder→real swap matches un-keyed siblings by tag+position, so the real grid pane can get attribute-patched onto the placeholder's differently-shaped skeleton node instead of being cleanly inserted, corrupting the grid's DOM shape on that one swap. Any subsequent full re-render (a real `wire:click`) replaces the whole subtree cleanly, matching the exact "works after one interaction, breaks again on reload" symptom. **Fix: give divergent `x-show`-gated sibling panes their own `wire:key`** (`wire:key="calendar-grid-pane-{{ $activeProjectId }}"` / `wire:key="calendar-list-pane-{{ $activeProjectId }}"`) so the morph never conflates them with the placeholder's unrelated skeleton children — the same remedy as the `x-data`-matching fix above, one structural level lower. **Lesson generalized further: any `#[Defer]` component whose real view's top-level children have a different SHAPE (count/order/tag) than its placeholder's top-level children needs explicit `wire:key`s on those children, not just a matching root** — a placeholder is not obligated to visually mirror the real content 1:1, but every top-level child position it doesn't share with the real content is a silent morph-corruption risk.

## Workspace tab-height fill — pure flex chain, no percentage heights (2026-09-10)

The workspace content area (`project.blade.php`) is a height-bounded chain: `<main class="flex-1 flex flex-col">` → header (`flex-shrink-0`) → content wrapper (`flex-1 min-h-0 flex flex-col overflow-hidden`) → tab-selector row (`flex-shrink-0`) → team-chat wrapper (`flex-1 min-h-0 flex flex-col` + conditional `hidden`) → `chat.blade.php` root (`flex-1 min-h-0 flex flex-col`). The fix replaced the old `min-h-full` percentage fill on the chat root: a percentage height/min-height resolving against a *flexed* ancestor is the classic fragile link — it silently collapses to content height (visible symptom: the chat composer floated mid-page, worst in `.max-widget` fullscreen where the container is tallest). Rule: inside this workspace chain, fill height with `flex-1 min-h-0` at every level, never `h-full`/`min-h-full`, so the composer stays pinned to the bottom in both normal and maximized modes. `calendar.blade.php`'s root still carries `h-full` — tolerated legacy, not a contract to copy; switch it to `flex-1 min-h-0` if it ever misbehaves. Same pass made the chat-viewport scroll listener remount-proof: it attaches once on `project()`'s own `$el` in the CAPTURE phase (`scroll` doesn't bubble but does capture; target-filtered by `e.target.id === ID_CHAT_VP`, passive, removed in `destroy()`), re-resolving `#team-chat-viewport` by id inside the rAF — the old attach-once-at-init listener sat on a detached node after every project switch (`wire:key="team-chat-{id}"` remount) and never attached at all when landing on the page with no project open, freezing `showScrollFab`.

## Workspace-open feedback — `openingProject` overlay (2026-09-23)

Clicking a project row fires a JS `wire.$island('workspace').selectProject(id)` (then a sidebar-island `refreshSidebar()`); the perceived "slight delay" before anything changes is that server round-trip plus the workspace island morph — nothing on screen acknowledges the click until it lands. The fix is an `openingProject` Alpine flag on `project()` (set at click, cleared by a pure hard 1s timer — `_openingTimeout`, also cleared in `destroy()`) driving a `wire:ignore`d `x-show` scrim + `<x-ui.loaders.spin-badge text="در حال باز کردن پروژه..."/>` inside the workspace `<main>` (loadingPattern category 2, faqs' scrim vocabulary). Two hard-won gotchas: (1) vendor `$island(name)` (livewire.esm.js `wireProperty("$island")`) only attaches island metadata to the next action and returns `component.$wire` — it is NOT a promise itself, so the first version's promise-chain `.finally`/5s-timeout hide proved unreliable (overlay appeared stuck "non stop"); the hide is now purely timer-driven and hypothesis-proof. (2) the overlay div carries `wire:ignore` so the workspace island's morph never syncs/re-adds `x-show`/`x-cloak` attributes on the element mid-flight. Alpine-driven rather than `wire:loading` because the trigger is an island-scoped JS call, mirroring tab-selector's `navigating` mechanism. Server-side untouched — this is pure perceived-speed, not a faster query.
