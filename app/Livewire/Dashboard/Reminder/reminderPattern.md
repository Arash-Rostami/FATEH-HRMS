# Reminder module pattern — "ماژول یادآوری زمان" (Time-Reminder Module)

A standalone, module-agnostic **manual task-scheduler** that lives in the navbar, not in the module registry — conceptually this is "ماژول یادآوری زمان", a user-driven scheduling tool, not part of the automated Badge/Nudge/Edge notification system. It only *uses* that system as its delivery mechanism (see §6) once a user has manually scheduled something; it is never itself an automated signal like `TaskOverdueNudge` or `DmsBadge`. Any host model can attach reminders (`Task`, `Ticket`, `Project`, `DMS`, `Reservation`, via `HasReminders`) without the Reminder widget knowing anything module-specific about it — it only ever sees a polymorphic `remindable_type`/`remindable_id` pair. This doc is the single source for the widget's own architecture; general Livewire conventions live in `app/Livewire/livewirePattern.md`.

---

## 1. Not a page, not a config-driven module

There is no dedicated route and no legend — the widget mounts unconditionally in `resources/views/components/dashboard/navbars/top.blade.php` (`<livewire:dashboard.reminder.main wire:key="reminder-navbar"/>`) alongside the notification bell, available on every page the navbar renders on. It does have a **description-only `config/modules.php` entry** (`id => 'reminder'`, icon `alarm`, title «یادآوری‌ها», added 2026-09-14 at user request, replacing the folded-away `radio` row, with its matching `ModulesGuideWidget` icon/meta rows) — so it shows in the user-panel release modal's module summary and the admin guide widget's «سیستم‌ها و ابزارها» group, but it still has no route, no legend, and no `ModulesConfigTest` doc-sync obligation beyond the entry itself — the same shape as `notification-guide`/`others`, description-only. The radio description it replaced was folded into the `others` entry's text.

## 3. `Main::mount($for = null)` — the untyped parameter is deliberate

`$for` carries no type hint (not `?Model $for`). This is a previously diagnosed Livewire bug, not a stylistic lapse: type-hinting the abstract `Model` class on a Livewire component parameter made Livewire's container-based parameter resolution throw the moment `:for` was omitted (the common case — the navbar mount never passes it). Do not "fix" this by adding a type hint back; the untyped signature plus the runtime `if ($for instanceof Model)` guard inside the body is the correct, working shape.

`$remindableType`/`$remindableId` are `#[Locked]` (Livewire's client-write-block attribute, per `livewirePattern.md`'s IDOR rule for any id-holding public property) — `mount()` still assigns them server-side, `Locked` only prevents a tampered request payload from re-pointing an existing widget instance at another record. When `$for` is a `Model`, `mount()` captures `$for->getMorphClass()`/`$for->getKey()` into `$remindableType`/`$remindableId`, and every list query (`reminders()`, `dueCount()`) additionally scopes `->where('remindable_type', ...)->where('remindable_id', ...)` on top of the always-present `forUser(auth()->id())`. Omitting `:for` (the navbar's global mount) simply leaves both null, so the widget lists every reminder the user owns regardless of host record — the same is true for the per-instance badge dot each `<x-dashboard.reminder-trigger>` embed renders: it reflects only that host record's due reminders, not the user's global count.

`openCreate()` also seeds the form's date/time fields from the scoped host's own natural date column via `hostDueDate()` — `Task::deadline`, `Ticket::completion_deadline`, `Reservation::start_time` (`Project`/`DMS` have none, so it silently falls back to blank, same as unscoped). `seedDueFields(Carbon $due)` is the shared Carbon→Jalali-form-fields helper, used by both `openCreate()` and `edit()` (which used to inline the same `Jalalian::fromCarbon()` split before this was extracted) — this is presentation-only prefill, not a default value change on `Reminder::due_at` itself; the user still confirms/edits before saving.

Any view embedding a scoped trigger for its own model uses `<x-dashboard.reminder-trigger :for="$model" :tooltip-position="..."/>` — never the raw `<livewire:dashboard.reminder.main :for=".." wire:key="..">` tag. `tooltip-position` (default `bottom`) threads straight through to `Main::mount()`'s own `$tooltipPosition` prop, purely presentational. The component derives its own `wire:key` from `class_basename($for)` + `$for->getKey()`, so every call site gets a correctly-scoped, uniquely-keyed instance by construction instead of by convention. Ths, Project, DMS, Reservation, TaskBoard (`taskboard/form.blade.php`, next to the edit-modal's tab bar, `$this->editingTask`), and Suggestion (`suggestion/list.blade.php`, 2026-09-15, net-new — `App\Models\Suggestion` gained `HasReminders` for this) views all use it; the navbar's unscoped global mount (§1) is the one legitimate exception, since it has no `$for` to pass.

### 3c. `variant` prop — `'icon'` (default), `'corner'`, `'inline'` (2026-09-14/15)

`<x-dashboard.reminder-trigger>` accepts an optional `variant` (default `'icon'`), threaded through `mount(string $variant = 'icon')` to `Main::$variant`, purely presentational — it only picks which button markup `reminder.blade.php` renders, never touches `mount()`'s scoping/open()/edit() logic. `'icon'` is the original always-visible `w-10 h-10` alarm button (unchanged — Project/Ths-workspace/TaskBoard's own edit-modal still use it for single-record, non-list contexts, untouched by this addition).

Both `'corner'` and `'inline'` share the same visibility logic — `opacity-0` by default, revealed only when the row's own `.group` ancestor is hovered (`group-hover:opacity-100`, no Alpine, pure CSS) unless `Main::hasActiveReminder` is true, in which case the icon stays permanently visible in `text-[var(--md-sys-color-primary)]`, **no background, no border, no box in either state** (tried both filled and outlined, both rejected on user review) — just a colored/muted glyph that fades in and out. They differ only in size/shape and positioning model:

- `'corner'` — `h-10 w-10`, no self-positioning at all; every call site wraps it in its own `absolute` div and supplies `position:relative` on the ancestor. Rolled out to DMS, Ths, Reservation, Suggestion — a floating badge sitting outside the row's normal content flow. See the placement notes below.
- `'inline'` (2026-09-15) — `w-6 h-6 p-0 rounded-xl`, sized to match this app's small icon-rail buttons (pin/palette/delegate) and rendered as a normal flex child, no `absolute` at all — for a row/card that already has a footer/rail of same-sized hover-reveal icons and just needs the reminder to join that rail rather than float in a corner. First (and so far only) use: TaskBoard's kanban card footer (`taskboard/card.blade.php`'s `task-action-rail`).

The due-count red pulse dot (`dueCount > 0`) is preserved in both variants, scaled to each (`-top-1 -right-1 w-2 h-2` for `'corner'`, `-top-0.5 -right-0.5 w-1.5 h-1.5` for `'inline'`).

**The component itself does not position anything — every `variant="corner"` call site wraps it in its own small `absolute` div and supplies `position:relative` on the ancestor cell.** This split (component = look, call site = placement) exists because the two modules that use it need genuinely different placement: a lone badge (DMS) vs. a multi-icon cluster (Ths, below). Current convention, followed by both: the ancestor `<td>` gets `relative` added to its existing classes, and the trigger (or cluster) sits in `<div class="absolute left-2 top-2 z-20">...</div>` — a small inset from the cell's top-left corner (physical `left`, not logical `end` — deliberate, see the RTL note below), not flush against the edges.

`#[Computed] Main::hasActiveReminder(): bool` (2026-09-14) is `$this->existingHostReminder() !== null` — reuses the exact same private lookup `open()` already calls to decide edit-vs-create, so the corner icon's "is a reminder set for this record" question and `open()`'s "click here to edit the existing one" behavior are always the same answer by construction: whenever the icon shows primary-colored, clicking it is guaranteed to open the edit form for that already-existing reminder (never a duplicate blank create), because both read the same `existingHostReminder()` call. **Do not confuse this with `dueCount`** (`Reminder::dueBadgeCount()`, gated on the `badge` channel + due-today-or-overdue) — `hasActiveReminder` is "any uncompleted reminder exists at all" (snoozed counts as active, matching `existingHostReminder()`'s own definition), a different, broader boolean, used only to decide the icon's permanent-visibility + color, never the due-count dot.

**RTL corner placement — "left" is the row's true visual edge, not the first `<td>` in markup.** Both DMS and Ths embed the corner badge inside their *action* `<td>` (the last column in markup order) rather than the first/title column — under this app's RTL layout, table columns render right-to-left, so the *last*-in-markup `<td>` is the one that actually sits at the row's visual left edge. An earlier DMS draft placed it in the title cell's own top-left corner instead and was moved after live review; don't repeat that mistake for a future module — identify the *last* `<td>` (or the card's true left edge for a non-table layout), not the first one. **Reservation's history list (`reservation/history.blade.php`) is a card row, not a `<table>`** — the RTL column-reversal concern doesn't apply at all (`left`/`top` on a plain flex `<div>` are always physical, unaffected by `dir=rtl`), so the badge is embedded directly at `absolute left-0 -top-1` inside the card's own root div (flush to the card's left edge, nudged slightly above its top — no inset padding, unlike DMS/Ths's table cells) (which already had both `group` and `relative` from its pre-existing hover/tag styling — no ancestor changes needed). This card's root also has no `wire:click` of its own (only individual action buttons inside it do), so — unlike Ths — the reminder trigger needs no `<span @click.stop>` wrapper here.

**Suggestion (`suggestion/list.blade.php`) is a net-new integration — the model had no `HasReminders` at all — and it went through two design passes.** First pass (a corner badge, `variant="corner"`) hit a real HTML-validity gotcha: the card's clickable root was `<button wire:click="selectSuggestion(...)">`, and nesting the corner trigger's own `<button>` inside it is invalid HTML5 (browsers silently break the nested one out as a sibling during parsing). Fixed at the time by promoting the loop root to a wrapping `<div>` with the reminder as an absolutely-positioned sibling `<span>`, not a descendant. **Second pass (final, per user review): moved to `variant="inline"` inside the card's existing footer row**, alongside the reaction counts and the created-date — matching TaskBoard's footer-rail treatment instead of DMS/Ths's floating-corner treatment, with the reminder as the last child (rightmost group is reactions+date together, reminder alone occupies the other end — leftmost under RTL). Because the footer sits *inside* the clickable card body, the original button-nesting problem was still live at this new location — solved by demoting the card body itself from a real `<button>` to `<div role="button" tabindex="0" wire:click="selectSuggestion(...)" x-on:keydown.enter.prevent="..." x-on:keydown.space.prevent="...">`, restoring keyboard activation manually (Enter/Space) since a `<div>` doesn't get it for free. **Rule for any future module whose row/card root is itself a `<button>` and needs the reminder inside its content (not just floating over it):** the root can't stay a real `<button>` — demote it to a `role="button" tabindex="0"` div with explicit `wire:click` + Enter/Space keydown handlers, then the reminder trigger can live anywhere inside it like any other footer icon, wrapped in `<span @click.stop>` since it's now a true descendant of the row's own click target.

**TaskBoard (`taskboard/card.blade.php`, 2026-09-15) replaced a pre-existing, unrelated mechanism rather than adding a fresh one — see `taskboardPattern.md`'s reminder section for the full before/after.** The kanban card already had ITS OWN header-only alarm icon fed by a batched `#[Computed] taskIdsWithActiveReminder(): array` (one query per board render, hand-duplicated on both `TaskBoard\Main` and `Project\Kanban` since the card is `@include`d by both) — visible only when a reminder existed, and clicking it just jumped to the task's edit modal rather than opening the reminder widget. That whole mechanism (both computed methods, the header markup, its one dedicated test in `TaskBoardTest.php`) was removed in favor of the real `<x-dashboard.reminder-trigger variant="inline">`, embedded as the last child of the footer's `task-action-rail` (the rail's other icons — approve/edit/delegate/palette/pin/duplicate/copy/archive/delete — are all `w-6 h-6` hover-reveal buttons in normal flex flow already, so `'inline'`, not `'corner'`, is the right variant here; no `position:relative`/`absolute` needed anywhere). **`Task::make(['id' => $taskId])` builds the `:for` argument without a DB round-trip** — the card only has a presenter-shaped array (`$task['id']`, not an Eloquent instance), and `HasReminders`'s embed only ever calls `getMorphClass()`/`getKey()` on it, both satisfied by an unsaved, attribute-only model — so replacing the batched lookup did not reintroduce the per-card query it was built to avoid. This is the reusable trick for any future module whose row is array-shaped rather than a real model instance.

**Ths: reminder shares its corner with the pre-existing color-palette control, and reminder always sits last.** `ths/ticket-table-row.blade.php`'s row already had a "palette" (color-tag) button — previously living inline near the priority/date area, `x-store.tagged` — which the user asked to be pulled into the same corner cluster as the reminder badge. Both now live in one `<div class="absolute left-2 top-2 z-20 flex items-center gap-1">` inside the action `<td>` (`relative` added there, matching DMS): palette's own `<div x-data="{tagOpen:false}">` wrapper first, the reminder trigger (wrapped in `<span @click.stop>` — the row itself has `wire:click="viewTicket(...)"`, so every corner control needs its own stop-propagation guard) last. **Rule for any future module with more than one row-corner control: the reminder trigger is always the last child in the cluster's DOM order** (in RTL, that puts it at the visually-leftmost position within the cluster, outermost from the row's other icons) — this was an explicit, general instruction from the user, not a one-off for Ths. Palette's own color-swatch popup direction flipped from `bottom-full ... right-0` (its old inline position, near the top of the row, needed to open upward/rightward to avoid the table header) to `top-full mt-2 left-0` (now pinned at the row's own top-left corner, opening downward/rightward into the row is the only direction with room).

**Project (`project/sidebar.blade.php`, 2026-09-15) is a *project-level* reminder, not a per-task one — deliberately.** Project's Kanban tab shares `taskboard/card.blade.php` with `TaskBoard\Main` (see the TaskBoard paragraph above), but the new footer reminder trigger there is gated `@if($isPersonalBoard)`, so it never renders for Project's kanban cards — per-task reminders inside a project were explicitly rejected in favor of one reminder scoped to the whole project. That project-level trigger lives in the sidebar's project list, sharing the exact same corner cluster as `x-ui.row-actions`' pin/mute/palette (the same shared component Channel/Contact sidebars also use) rather than a separate floating badge: `x-ui.row-actions` gained a new optional `for` prop (default `null`) — when supplied, it renders `<x-dashboard.reminder-trigger :for="$for" variant="inline">` as the cluster's last child (same `pointer-events-none` container as pin/mute/palette, so `'inline'`'s existing `pointer-events-auto`/`pointer-events-none` toggle — added specifically for this — matters here: without it, an invisible/faded reminder icon would still swallow clicks meant for the row underneath). Channel and Contact's sidebars don't pass `for`, so they render byte-identical to before — this is additive-only, not a behavior change for their pin/mute/palette. Project's row is array-shaped (`$project['id']`, not an Eloquent instance), so `for="\App\Models\Project::make(['id' => $project['id']])"` uses the same zero-query trick as TaskBoard's `Task::make()` above.

TaskBoard's card-header alarm icon (`taskboard/card.blade.php`) is a **separate, unrelated integration** — it does not embed this widget at all. See `taskboardPattern.md` §6 for the batched `taskIdsWithActiveReminder` lookup that feeds it (one query per board render, not a per-card `<x-dashboard.reminder-trigger>`).

`open()` always lands on the `'form'` tab, never the list (unified 2026-09-14 at user request — it previously landed on `'list'` when unscoped). Scoped (`:for` set) first checks `existingHostReminder()` — the user's earliest-`due_at` uncompleted reminder on that host, where **snoozed counts as uncompleted but `completed_at` does not** — and opens it via `edit()` so clicking a host's trigger edits the already-scheduled reminder instead of offering a duplicate blank create; only when none exists does it fall back to `openCreate()`'s host-date-prefilled form. Unscoped (navbar/menu shortcut) skips that lookup entirely (no host) and always gets the blank create form. See `ReminderTest::test_scoped_open_edits_the_existing_uncompleted_reminder_instead_of_offering_a_blank_create` and `..._falls_back_to_a_blank_create_when_only_completed_reminders_exist`. The list is still one tab-click away, and a `hostUrl()` deep-link row ("مشاهده و ویرایش رکورد") sits above the tab bar when scoped.

The hamburger-menu footer (`components/dashboard/modal/menu.blade.php`, between the audio player and the divider) carries an `alarm` shortcut that `$dispatch('open-reminders')`es and closes the menu — caught by `#[On('open-reminders')] openFromShortcut()`, which no-ops on any `:for`-scoped instance so only the navbar's global widget ever opens from it.

## 3a. Presenter is component-level, never blade-level — and the list/form split fixes a real ExtendBlade compile bug

`ReminderPresenter` is constructed via `Main::presenter(Reminder $reminder): ReminderPresenter` (`return new ReminderPresenter($reminder)`), called per-row from the blade as `$this->presenter($reminder)` — matching `Suggestion\Main::presenter($suggestion)`, the established codebase idiom for a per-record (constructor-bound) presenter. This replaced an earlier shape that injected `ReminderPresenter::class` as a string through `render()`'s view data and reconstructed it inline in the blade (`new $presenter($reminder)`) — functionally workable but a one-off pattern with no other precedent; every stateless presenter in this codebase (`ProjectPresenter`, `ChannelPresenter`, `DmsPresenter`, etc.) already goes through a `#[Computed]` or plain method on its component, never `render()`-injection. `hostIcon(): string` (wraps `ReminderPresenter::hostIconFor($this->remindableType)`) exists for the same reason — the header deep-link icon used to call the fully-qualified `ReminderPresenter::hostIconFor(...)` inline inside the blade tag.

**Real bug found chasing this (2026-09-14):** with the presenter fully moved to the component, `reminder.blade.php` started throwing `ViewException: syntax error, unexpected token "endif"` from its *compiled* file, with the source's own `@if`/`@endif` count providing balanced (confirmed via a PHP-tokenizer stack tracer). This is the same `Livewire\Features\SupportMorphAwareBladeCompilation` (`ExtendBlade`) bug documented at the top of `app/Livewire/livewirePattern.md` — but a *second*, distinct trigger shape from the one already documented there: bisection (`blade.compiler`->compileString() + `php -l`, repeatedly on trimmed copies) proved it wasn't any single block — removing either the list-tab body or the form-tab body alone fixed it, and even shrinking one to a single trivial line while keeping the other full still failed, meaning it's sensitive to the *file's total compiled complexity*, not a specific `@php`-with-nested-control-flow shape. **The fix:** extract the list-tab and form-tab bodies into their own `@include`d partials (`reminder/list.blade.php`, `reminder/form.blade.php`) — each compiles independently, so neither ever accumulates enough complexity on its own to trip the heuristic. `$this->` calls (`$this->reminders`, `$this->presenter($reminder)`, `$this->suggestedTitles`) resolve correctly inside the `@include`d partials — Livewire binds `$this` per-render, not per-view-instance, confirmed by the existing precedent at `taskboard/form.blade.php` (itself `@include`d from two different components, `TaskBoard\Main` and `Project\Kanban`, and using `$this->` throughout). If a future edit to `reminder.blade.php`, `reminder/list.blade.php`, or `reminder/form.blade.php` reintroduces this error, don't re-inline the split as a "cleanup" — re-verify with the same compileString+php-l bisection before assuming a smaller shape is safe.

## 3b. Static view-shaping config lives on the Presenter, never as literal arrays in blade — single source of truth

`reminder/list.blade.php` and `reminder/form.blade.php` used to declare their own static config arrays inline in a top `@php` block — filter-pill labels, table column headers, snooze presets, the channel-toggle checkbox list — literal Persian-labeled arrays sitting in the view with no other owner. Moved (2026-09-14) to four stateless static methods on `ReminderPresenter`: `filterOptions()`, `columns()`, `snoozePresets()`, `channelToggles()`. `Main::render()` passes all four through the view-data array (`view('livewire.dashboard.reminder', ['filterOptions' => ReminderPresenter::filterOptions(), ...])`), the same shape `Suggestion\Main::render()` already uses for `SuggestionPresenter::workflowSteps()` — the second example of this convention in the codebase, not a one-off. Because Blade's `@include` shares the parent view's variable scope, both partials receive `$filterOptions`/`$columns`/`$snoozePresets`/`$channelToggles` automatically with no re-declaration and no `$this->` plumbing needed.

**Why this matters beyond tidiness:** before this, the labels/keys existed in exactly one place (the blade array), so nothing else could reference them without duplicating the literal strings. Now `ReminderPresenter::filterOptions()` etc. are the single source of truth — any other surface that ever needs "what are the reminder filter keys" (a future admin view, an API, a test) reads the same method instead of re-typing the array. The blade's own `@php` block is now flat CSS-class-string locals only (`$tdBase`/`$tdCenter`/`$iconBtn`) — legitimately view-only concerns, not data — which also keeps it clear of the ExtendBlade nested-control-flow trigger shape from §3a.

**The pattern to follow for any future static, page-level (not per-record) config a Reminder blade needs:** add a `public static function` on `ReminderPresenter` returning the array, wire it through `Main::render()`'s data array, never declare the literal array inside a blade `@php` block. This is distinct from §3a's `presenter(Reminder $reminder)` factory — that's for per-record instance methods (`dueLabel()`, `toneClasses()`, ...); static config methods don't take a `Reminder` and don't need an instance at all.

## 4. Ownership scoping lives in the Actions, not the Main component's read path

`Main::getReminder(int $id)` is a plain, unscoped `Reminder::query()->findOrFail($id)` — it does **not** filter by `user_id`. This is by design: every mutating entry point (`complete`, `snooze`, `delete`, `update`, `stopRecurrence`) passes the fetched row into its Action, and the Action is where `abort_if($reminder->user_id !== $userId, 403)` actually lives. Moving that check into `getReminder()` was tried and reverted — it turned a correct 403 into an uncaught `ModelNotFoundException` (404) for a row that legitimately exists but belongs to someone else, breaking a regression test that asserts the 403. Any new mutating method on `Main` must follow the same shape: fetch unscoped, let the Action enforce ownership.

`edit(int $id)` is the one exception to "let the Action enforce it" — it has no Action class (it only hydrates `ReminderForm`, a client-visible Livewire property, never writes to the DB), so it carries its own inline `abort_if($reminder->user_id !== (int) auth()->id(), 403)` right after the unscoped fetch, before any form property is populated. Without it, calling `edit()` directly with another user's reminder id would leak that reminder's title/notes/due date into the requesting user's Livewire response even though the later `update()` call would still 403 — a read-time disclosure the write-time check does not cover.

`:for="$task"` scoping (§3) only narrows the **list** to one host record's reminders — it is not an ownership boundary either. Two users who both have a reminder on the same shared task each see only their own row in that scoped list (via `forUser`), never each other's.

## 5. Two-tab modal, list tab rendered as a table

The panel is a full `<x-ui.modals.action>` modal, not a dropdown — `Main::$show` (default `false`) is entangled via `wire:model="show"` on the modal, flipped true by `open()`, the same shape as `ReleaseRequest`'s modal. Inside it, `Main::$activeTab` (`'list'` / `'form'`), switched via `switchTab()`/`openCreate()`/`edit()`/`closeForm()`, is rendered through `<x-ui.buttons.tab-selector>` — tab order is `['form', 'list']` (form first), matching §3's every-open-lands-on-form behavior. This replaced an earlier single-panel design where create/edit toggled a boolean over the same panel — the two-tab shape gives the list and the form each their own scroll/layout without a boolean flag steering conditional markup inside one panel.

The list tab renders an actual `<table>`, matching `dms/table.blade.php`'s visual convention, deliberately simplified — no sort, no column-toggle, no date-filter, since this is always a small per-user list. Empty state (2026-09-14): the shared `<x-ui.empty icon="alarm_off">` centered inside a `min-h-[300px]` card wrapper matching the table's own rounded/bordered/shadowed frame, so an empty list doesn't collapse the modal. Columns: عنوان (title + host tag from `hostLabel()`/`hostIcon()`) | سررسید (**merged** date+status — one `toneClasses()`-colored badge combining `dueLabel()`'s detailed text with `statusIcon()`, plus a completed/snoozed timestamp sub-line from `statusTimingLabel()` — this used to be two separate columns (سررسید text-only, وضعیت a 4-state chip), merged into one on user request) | تکرار (recurrence badge or `—`) | کانال‌ها (`channelBadges()`, icon-only) | اقدامات (color-coded per action: complete=success, snooze=secondary, edit=primary, stop-recurrence=warning, delete=error).

Filter pills: `active`/`today`/`overdue`/`week` (all through the `active()` scope family) plus two that deliberately bypass `active()` since it structurally excludes them — `completed` (`whereNotNull('completed_at')->orderByDesc('completed_at')`) and `snoozed` (`whereNull('completed_at')->where('snoozed_until', '>', now())`, soonest-first). `reminders()` branches on `$this->filter` for both before falling into the `active()`-scoped `match()` for the other four. **Without a dedicated filter, a snoozed-or-completed reminder is invisible in every other pill** — `active()`'s own definition (`whereNull('completed_at')` AND `whereNull('snoozed_until')->orWhere('snoozed_until','<=',now())`) excludes both by design; this was a real gap found during live testing, not a hypothetical.

Snooze presets (`1h`/`tonight`/`tomorrow`/`nextweek`) sit alongside a custom-hours option — `Main::snoozeHours(int $id, int $hours)`, a `<select>` (1–12) in the same dropdown, clamped server-side (`max(1, min(12, $hours))`) regardless of what the client sends.

## 6. `channels` — the single-source gating format

`reminders.channels` is a JSON array holding at most `'email'` (a flat token) and one `'inapp:...'` token, whose suffix is a comma-list drawn from `edge`/`badge`/`nudge` — e.g. `["inapp:edge,badge,nudge","email"]`. `Reminder::channelEnabled(array $channels, string $signal): bool` is the only parser for this shape; the three Menu classes (`ReminderBadge`, `ReminderOverdueNudge`, `ReminderDueTodayEdge`), `Reminder::dueBadgeCount()` (see below), `ReminderForm::fromChannels()`/`toChannels()` all go through it. Never re-split the `inapp:` string ad hoc at a new call site — add a new signal token to the existing suffix vocabulary and let `channelEnabled()` keep being the one place that understands it.

**`Reminder::dueBadgeCount(int $userId, ?string $remindableType = null, mixed $remindableId = null): int`** (2026-09-14, extracted in review) — the SINGLE SOURCE for "how many of the user's reminders are due (overdue or today) and badge-visible": `forUser` + optional host scope + `active()` + `due_at <= endOfDay`, then a collection filter `channelEnabled(channels, 'badge') && !hostTrashed()`. Three call sites that previously each re-implemented the query with drifting filters now all call it: `ReminderBadge::isActive()` (`dueBadgeCount > 0`), `Main::dueCount()` (the small red dot on the reminder-bell icon itself — a separate visual signal from the generic `$menuState['reminders-controller']` dot `ReminderBadge` feeds; optional host args preserve the `:for`-scoped widget's per-record count), and the Home tab's «یادآورهای سررسید» stat chip (`TabPresenter::stats()`), which previously counted raw with neither filter — a badge-disabled or trashed-host reminder lit the chip while the navbar dot stayed dark and the widget showed a different number. Any new "due reminders" surface must call this, not re-derive it.

`ReminderForm` itself never touches the raw array — it holds `emailEnabled`/`inAppEdge`/`inAppBadge`/`inAppNudge` booleans, and `toChannels()`/`fromChannels()` are the only two places that translate between those booleans and the stored JSON shape (used by `Main::edit()` and by `Create`/`UpdateReminderAction`).

## 6a. `Reminder::urlFor()`/`hostUrl()` — the single-source host-link resolver

`Reminder::urlFor(?string $remindableType, mixed $remindableId): ?string` is a static `match()` over the same 5 host types (`Task`/`Ticket`/`Project`/`DMS`/`Reservation`) each routing to `route('tasks'|'ths'|'projects'|'dms'|'reservation', ['open' => $remindableId])`, `null` for anything else (including a `null` type/id). `hostUrl(): ?string` is the instance shortcut (`static::urlFor($this->remindable_type, $this->remindable_id)`). `ReminderOverdueNudge::url()`, `ReminderDueTodayEdge::url()`, and `ReminderDueNotification::toMail()`'s action link all delegate here instead of each carrying its own duplicate `match()`. Never re-add a fourth `match()` at a new call site — extend `urlFor()`'s cases instead.

Reminders also surface read-only inside the Calendar module (month dot-count with its own alarm-icon day marker, day/week hourly grid or all-day strip depending on due-time, day-detail panel) via `CalendarPresenter`'s own per-request reminder cache (`remindersInRange()`) — never editable there. Unlike the Badge/Nudge/Edge signals, `remindersInRange()` (2026-09-14) only excludes `completed_at`, not `snoozed_until` — a snoozed reminder still shows on the calendar (its due date doesn't change just because notifications are suppressed), carrying an `is_snoozed`/`snoozed_hours` flag the rendering partials (`all-day-chip.blade.php`, `events.blade.php`, `event-block.blade.php`) use to append a small "(Nh)" text badge, deliberately icon-free (`all-day-chip.blade.php`) or minimally-iconed (`events.blade.php`, `event-block.blade.php`) to avoid stacking a second alarm-family icon next to the reminder's own.

**Day/week hourly-grid placement (2026-09-14).** `rangeEvents()` places any reminder whose due-time falls inside the grid window (`CalendarLayout::GRID_START_MINUTES`–`DAY_END_MINUTES`, i.e. 06:00–24:00) directly into `$byDay` as a proper timed pill — `start_minutes` from `due_at`'s time-of-day, a fixed 30-minute `duration_minutes` (a reminder is a point-in-time marker, not a real duration), `locked` always `true`. It goes through the same `CalendarLayout::pack()` column-packing as events/reservations, so it correctly shares space with same-time events instead of overlapping them. A reminder due **before** 06:00 falls back to the all-day strip (`buildAllDayEntries()`) exactly as before, since it has nowhere to sit in the grid — `rangeEvents()` tracks which reminder ids it placed in `$byDay` and filters those same ids out of `allDayEntries` so nothing renders twice. `event-block.blade.php` (the shared timed-pill renderer, previously events/reservations only) gained an `$isReminder` branch: alarm icon, a dedicated primary-container color (distinct from all 4 existing owner/shared/private/reservation variants — a reminder pill is none of those), and the click handler is guarded to no-op for reminders (`$wire.editEvent()` expects an integer event id; a reminder's id is the string `reminder-{id}` and must never reach it).

**`hostTrashed(): bool`** (2026-09-14, found in review) — a sibling instance method, not a `urlFor()` case: `false` when `remindable_type`/`remindable_id` is null or the host class has no `trashed()` method (Ticket/DMS/Reservation are never `SoftDeletes`), otherwise `$remindable_type::onlyTrashed()->whereKey($remindable_id)->exists()`. Gates `ReminderBadge::isActive()`, `ReminderOverdueNudge::show()`, `ReminderDueTodayEdge::show()`, and `SweepDueReminders`'s email-send branch — soft-deleting a Task/Project (see `app/Traits/traitPattern.md` §2.3's `HasReminders` guard) now correctly preserves the reminder row itself, but its Badge/Nudge/Edge/email signals stop firing while the host is trashed rather than pointing at a dead link; they resume automatically the moment the host is restored (no extra bookkeeping needed, since nothing about the reminder row changes either way).

## 7. Recurrence — `ReminderRecurrence::advance()` never spawns an instantly-overdue successor

`Reminder::complete()` on a recurring reminder creates the next instance via `$this->recurs->advance($this->due_at)` — stepping from the **original** due date, not from `now()`. `advance()` loops (`while ($next->isPast())`) so a reminder completed long after it was due (e.g. a daily reminder completed a week late) jumps forward past the current moment rather than reappearing already overdue. `StopRecurrenceAction` is the escape hatch — it just flips `recurs` to `None` on the existing row, no cascade into already-created future instances (there are none; the next instance doesn't exist until `complete()` runs).

This is the Todoist/Apple-Reminders recurrence model — one live instance at a time, the next spawned only on completion — not a calendar-RRULE model (Google Calendar/Outlook) that pre-projects every future occurrence upfront. There is no `parent_id`/`series_id` anywhere in the schema; each occurrence is a fully independent row, linked to its predecessor only by having been created from it (same `user_id`/`title`/`remindable_type`/`remindable_id`/`recurs`/`channels` copied forward at creation time).

## 9. Pruning — completed reminders only, never active ones

`reminders:prune-completed {--days=90}`, scheduled daily in `routes/console.php`, is the only thing that ever deletes a completed `Reminder` row — it deletes in `whereNotNull('completed_at')->where('completed_at', '<', now()->subDays($days))` batches. Active/uncompleted reminders are permanent history and are never touched by this command regardless of how old their `due_at` is.
