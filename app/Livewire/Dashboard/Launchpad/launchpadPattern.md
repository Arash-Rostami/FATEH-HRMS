# Launchpad Module Pattern Guide

Flat HTML file sets (index.html + sibling html/css/js/images/fonts/json, selected together, no zip, PHP never) uploaded as «پیشخوان برنامه‌ها» tiles (`/launchpad`), opened by viewers in a sandboxed iframe or added as a hero-deck slide. Create, safe edit (§10), activate/deactivate and delete; creating under a live title in the same department REPLACES it (owner/elevated). Admin panel is monitoring-only (Filament). Grade 2 "private by Apache" on the public disk. Livewire v4, Filament v5, Laravel 12. General rules live in `app/Livewire/livewirePattern.md`.

## 2. Storage

Documented exception to the `StoresAttachedFiles` rule: `CreateLaunchpadAction` and the refresh `store()` write straight to the public disk under hashed names (`Launchpad::storedName`) and clean up only through `CleansAttachedFiles::deleteStoredDirectory()`; keep that rollback contract when editing either write path.

`Storage::disk('public')` (grade 2): `launchpad/files/{ulid}/{sha1(mb_strtolower(name))}.{ext}` only. `storedName()` hashes `mb_strtolower($name)` — case-insensitive so `a.html` + `A.HTML` collide as one file, and the extension must be a key of `config('launchpad.types')` or the name is rejected. The folder ulid is never in any user-visible URL (the iframe URL carries the row id + token). `directory()` re-validates the 26-char ulid before any disk touch. Every folder removal (model `deleted` hook, failed create, replaced folder) goes through the shared `CleansAttachedFiles::deleteStoredDirectory()` — path-traversal guard, failures logged and never thrown, so a disk error cannot break a delete, a prune run or mask the original exception.

## 3. Grade 2 "private by Apache" + the path token (the core)

- The same public-disk code, PLUS one Apache rewrite line redirecting `/storage/launchpad/…` to the login-gated module page (never to a file route), PLUS the token route that reads the disk directly — the rewrite never affects it.
- Why plain grade 2 (session-cookie route) cannot work: the program opens in `<iframe sandbox="allow-scripts">`, which sends no login cookie, and the frame's relative CSS/JS sub-requests cannot carry a signed query string. So the authorized route sits OUTSIDE auth and carries an HMAC path token `{uid}-{exp}-{sig}` (sha256 of `launchpad|{id}|{uid}|{exp}` keyed by `app.key`, anchored-regex parse + `hash_equals`, TTL `config('launchpad.token_ttl_minutes')`): the token rides the PATH, which every relative sub-request inherits from the iframe `src` base. Token issued ONCE into a `#[Locked]` property on open, never in render. Lifetime (`token_ttl_minutes`, 240): the expiry is bucketed (`(intdiv(now, window) + 2) * window`), so the same viewer gets the SAME URL for a whole window and the browser can reuse files through ETag/304 instead of re-downloading the app on every open; a token is therefore valid between one and two windows (4-8 h). Trade-offs, accepted knowingly: the token sits in the URL path, so it shows in web-server access logs while valid, and a copied token keeps working after the owner of the session logs out until it expires (only deactivating, un-sharing or deleting the program, or deactivating the user, revokes it — the sandboxed frame has no cookie to tie it to a session); a viewer or workspace slide left open past it loses its sub-requests (blank frame) until reload, since a fresh module load issues a fresh token; the frame can navigate itself to an external site (CSP cannot restrict navigation from the artifact response) — risk is limited to phishing inside the sandbox by an authenticated uploader; a hard crash between file write and commit can orphan a folder (no sweeper). Lower the config value when log exposure matters more than long-lived slides. Never `temporaryUrl()`.
- `LaunchpadFileController`: every miss is the SAME empty 404 (`nosniff` + `no-store`), order: `Sec-Fetch-Dest: document` → token invalid/expired → row missing/not static/no directory → user missing or `!canView` → `storedName` null or file absent. Then ETag `hmac(folder|lowercased file|filemtime)` keyed by `app.key` (`filemtime` so a rewritten `data.json` is never answered 304) (so the response never reveals the storage folder name; 304 only here) and `response()->file()` with the type from `config('launchpad.types')` and CSP `sandbox allow-scripts; … {base}` where `{base}` = `{origin}/launchpad/{id}/{token}/` — never `'self'`. Access is re-checked on EVERY file request (two PK reads, no cache, instant revocation on deactivate/unshare/delete).
- Apache guard lines: `scripts/setup-container.sh` inserts idempotently `RewriteRule ^storage/launchpad/(.*)$ https://%{HTTP_HOST}/launchpad [R=302,L,NE]` next to the DMS line; `scripts/verify-health.sh` checks the rule is present and `curl`s the first stored folder expecting 302. The repo's own `public/.htaccess` carries no such rule — never upload it blindly (httpPattern.md §7, `temp/winterra/paas-setup.md` §5).

## 4. Limits

- Sizes live ONLY in `config/file_upload_limits.php`: per-file tier `launchpad` (10240 KB), whole-upload tier `launchpad_total` (51200 KB). Never a size value in `config/launchpad.php` or anywhere else.
- `config('launchpad.max_files')` must stay <= php.ini `max_file_uploads`; `LaunchpadForm::maxFiles()` clamps with `min()` at runtime. Ops: `upload_max_filesize = 10M`, `post_max_size = 56M`, `max_file_uploads = 60` — `scripts/setup-container.sh` writes `max_file_uploads=60` into `99-tuning.ini` beside the existing 250M upload sizes (PHP's default 20 would silently clamp the cap) and `scripts/verify-health.sh` prints the live value. Production creates the `launchpads` table by hand from the SQL in `temp/winterra/paas-setup.md` (a recorded migration skips the guarded block); that SQL now also carries `source` TEXT NULL (after `settings`) and `refresh_due_at` TIMESTAMP NULL + index, and a table created before Phase 2a.1 needs the matching `ALTER TABLE` from the same runbook.
- `Prunable` on expired rows: `prunable()` = `expire_at < today`, swept by the existing nightly `model:prune` (no new command); only `prunable()` lives inline in the model (framework-trait collision; there is no custom `prune()`), and soft-deleted rows WITHOUT an `expire_at` are never pruned (they keep their owner foreign key).

## 5. Badge

`UnseenLaunchpads` (`launchpad-controller`): lights for an audience member on a live row not in `seen_by`, never the owner; cleared by `markSeenBy` on open (raw update + explicit `StateService::flush()` after commit); `CreateLaunchpadAction` flushes AGAIN after its transaction commits (the model hook's flush fires inside the transaction, so a menu poll in that window could cache a state without the new row); `DeleteLaunchpadAction` has no wrapping transaction on purpose, so the `deleted` hook removes the folder only after the row is already gone (a failed delete can never leave a listed program with deleted files), unlit automatically by deactivation/expiry/unshare/delete because `scopeUnseenBy` rides `scopeLive` + audience. `HasLaunchpadHooks` flushes on created / `active` flips / deleted, only when `audience` is filled, and deletes `directory()` on delete. Badge-only — no nudge, no bell. Legend row in `BadgeLegendCatalog` (`compliance` group, `launchpad` subgroup).

(6) A refused redirect whose host is `google.com` or a subdomain (the sign-in page a now-private sheet answers with) = `denied` + `private_sheet`; any other host stays `redirect_refused` (`redirectReason()`). Trade-off of the zero-result rule: a single failed run blanks the dashboard until the next successful run, and the artifact then shows its failed state with the last update time; a hidden helper tab («help») disappears from the htmlview map and ends as `tab_missing`.
- One validated redirect (export only, `$hop = true`): the export always answers 307 with `Location` on `doc-<digits>-<letters>-sheets.googleusercontent.com`; `follow()` accepts it only when 301/302/303/307/308, `LaunchpadForm::urlAllowed()` passes (https, port 443 or absent, no userinfo), no `#`, and `isSheetsDownloadHost()` (`/^doc-[0-9a-z-]+-sheets\.googleusercontent\.com$/D`, lower-case only) matches; the hop re-runs the FULL guard in `call()` (resolve once, every IPv4 public, `CURLOPT_RESOLVE` pin, https only, no proxy, byte cap, same deadline) with `$hop = false`, so a second redirect, another host or a non-https target = `denied`. `CURLOPT_FOLLOWLOCATION` stays false everywhere (the `Location` is read via `CURLINFO_REDIRECT_URL`); every other source keeps "any 3xx is not followed". Parsing: private `csvGrid()` keeps full width (BOM stripped, quotes/commas/newlines kept, no trimming); `csvRows()` = grid + `trimRows()` (trailing empty cells per row, trailing empty rows dropped); `sliceRange($grid, $cells)` cuts the row/column bounds of the cells `rangeParts()` returned (upper-cased), then `trimRows()` (an empty interior row = `[]`, bounds past the grid are fine, the same as the Sheets API). The file is saved as `data = {valueRanges: [{range: <line>, values: <rows>}]}` in typed order, the same shape as google. Status mapping: htmlview or export 401/403, an HTML sign-in body (`^\s*<(!doctype|html)\b`, export only) or a disallowed redirect = `denied` (the sheet is not public); an unusable range line, a tab missing from the map or a non-UTF-8 body = `invalid`; network/timeout/429/5xx = `unreachable` with the usual retry; zero-result rule unchanged. Exposure: the sheet must be shared «هر کسی که لینک را دارد» as «بیننده», so anyone with the link can read it. The tab must still be copied exactly (mind the zero-width non-joiner in Persian names), now an error instead of the first tab. Never log URLs, bodies, sheet ids or gids. Not exercised against real Google in tests (no network). Output differs from the private (Sheets API) path: no `spreadsheetId` or `majorDimension`, `range` echoes the typed line instead of Google's normalised range, tab names match exactly, and hidden tabs are not in the htmlview map. Known limit: `dns_get_record` is not bounded by the deadline and the public path resolves up to 5 hosts (docs.google.com, the download host, ...), so a hanging resolver can still hit the 120 s job timeout.
- Replace/delete: replace keeps the stored source when «نوع منبع داده» stays on «بدون منبع داده», overwrites it (and re-arms `refresh_due_at = now()`) when filled, nulls both for a `link` kind, and COPIES the old `data.json` into the new folder only when the replaced row had a source (`refresh_due_at` not null) and the new upload carries no file of its own; the `deleted` hook nulls `source` + `refresh_due_at` through a raw update (a soft delete would otherwise keep the ciphertext). Who may attach a source: any creator (`canCreateIn`) because the guard blocks internal targets; refresh-now rides `canManage`. No new policy verb.
- `source` is read (decrypted) only by `RefreshLaunchpadAction::execute()`, by the manager-only `Main::showDetails()`/`openEdit()` and by `UpdateLaunchpadAction`; `RefreshLaunchpadAction::store()` skips the write when `refresh_due_at` is null (a manager removed the source while the fetch was in flight). A queued refresh is one per item (`ShouldBeUniqueUntilProcessing`), so a user-triggered dispatch while the nightly planner's delayed job is still pending is reused, not queued twice (the new data can arrive up to ~43 minutes later). Admin-panel activation uses plain `update()` and does NOT re-arm the refresh or check the access window. Never select `source` elsewhere: `Main::rows()`/`open()`/`save()`/`delete()`, `DeleteLaunchpadAction`, the replace lock in `CreateLaunchpadAction` and the Presenter list columns name their columns explicitly (the replace write only writes `source`, it never reads it); `RefreshLaunchpadAction::execute()` is the only reader. `source` is TEXT (65,535 bytes) while validation counts characters, so the free-text caps stay at `max:2000` per field; `Main::persist()` catches `QueryException` and shows a generic toast, never SQL or ciphertext. Known gap: the Filament table builds `select *`, so the ciphertext travels through the query but `$hidden` + the cast keep it out of `toArray()`, JSON, the column set and logs; never add a column or infolist entry that reads it.
- Secrets are write-only: the form never fills `sourceEnv` (header value, login body, keys) back, the values are cleared after save; the ordinary call `sourceBody` (the plain POST body) IS restored in the edit form, so never put credentials there. A refresh write is skipped when the saved source no longer matches the fingerprint the job fetched with (`RefreshLaunchpadAction::store()`), and the planner only moves `refresh_due_at` on rows that still have one; file names are de-duplicated by `Launchpad::storedName()` (NFC, same key as storage), nothing logs them, and the legend/admin guide say so. `data.json` content is visible to the whole audience and elevated roles (copy says it).
- Source field input hygiene (2026-11-17): the data-source inputs are `dir="auto"` with `style="unicode-bidi: plaintext"` (per-line direction; never a fixed `ltr`/`rtl`), and `LaunchpadForm::normalizeSource()` (called in `Main::save()` and `CreateLaunchpadAction::execute()` before `validate()`) strips invisible direction marks (U+061C, U+200E/F, U+202A-202E, U+2066-2069, U+FEFF) and trims every source value and every range line, so a right-to-left copy/paste cannot break validation; ZWNJ (U+200C) is KEPT because tab names contain it; `rangeParts()` also accepts the reversed `cells!tab` order.
- Tab matching (2026-11-18): the save-time `verifyTabs()` and the job (`exports()`, `gidSource()`) compare a typed tab with the real ones through ONE folder, `RefreshLaunchpadAction::tabKey()` (drops whitespace and ZWNJ, folds Arabic ي/ك to ی/ک, lower-cases); `tabGid()` tries the exact name first, then the folded one. The typed text is still what is stored (never rewritten); only the lookup is tolerant. `verifyTabs()` silently skips when the htmlview fetch fails (`sheetTabs()` null, 15 s budget), so a wrong tab can still be saved while Google is unreachable; the job then reports `tab_missing`. Row 1410 proof: its saved ranges were written before `verifyTabs()` existed.
- What NOT to do: no per-tenant or per-item schedule time, no placeholders or token cache, no `records`/transform step, no second scheduler line, no call from the scheduler or a request, no redirect following (except the one validated `doc-*-sheets.googleusercontent.com` hop of the public sheet export), no user-typed ports, no message/URL/body in any log or in `settings.refresh` (only the closed `status`/`reason` codes and the hashed-sheet gid cache), no source edit outside the §10 safe edit.

## 10. Safe edit (2026-11-18)

- Entry: the details dialog shows a tonal «ویرایش» button only when `details['manage']` (`canManage`, set by `LaunchpadPresenter::details()` together with `details['id']`); it runs `Main::openEdit($id)` (re-checks `canManage`, refuses `embed`; the classic list row also carries an `edit` icon, `launchpad-edit-action`, shown on `can_manage` and calling the same method, the compact side column does not), which fills `LaunchpadEditForm`, closes the dialog (`close-modal`) and sets the public `$editOpen` that the animated form modal `launchpad/edit.blade.php` (`<x-ui.modals.action wire:model="editOpen" action="saveEdit">`, shell mirrored from AI Report's block editor, viewPattern §8.42) entangles; the modal renders only while `#[Locked] $editId` is set, and `updatedEditOpen(false)`/`close()`/`open()`/`switchTab()` reset every edit property (`resetEdit()`).
- Editable: description, audience, the three dates, the data-source block. Read-only context (title, department and owner id via `$editContext`): never editable, because title + department is the replace key; files, kind, owner and the link site/path are never touched. The Action sets the form's `kind` from the locked row, so a forged `kind/title/department_id/files` changes nothing.
- One source of truth for validation: `LaunchpadEditForm::rules()` = `parent::rules()` minus title/department/kind/site/path/files, so the audience cap, date rules, `urlAllowed`, header/PEM/range rules, attributes and messages are the create ones; `LaunchpadForm::verifyTabs()` (moved out of `CreateLaunchpadAction`, error key prefixed with the form's property name) runs in both actions; `Main::date()` enforces the same Jalali range for the edit dates (`editFrom|editTo|editExpiry` + `Year|Month|Day`), except that a date left exactly as loaded is kept without the range check (`editLoaded`), so an old stored start date never blocks an unrelated edit. The same holds for the create rules a past-dated (expired) program would trip: `UpdateLaunchpadAction` copies the locked guard row's `accessible_to`/`expire_at` into `LaunchpadEditForm::$storedDates` (server-written, like `storedAuth`) and `rules()` drops `after_or_equal:today` for a field equal to its stored value, so an expired program stays editable (extend it by choosing a new date; leaving it untouched changes nothing). `Main::yearFloor()` lets a stored earlier Jalali year pass `date()` when that date is changed within its year, and `render()`'s `yearFloors` feeds the three edit date selects' `startYear` so the stored year is a real option instead of a blank select. `sourceRows()` prefixes its models with the form's own property name, so the same accordion markup serves both forms.
- Secrets stay write-only: `LaunchpadEditForm::load()` copies only non-secret source fields (type, url, method, call body, non-secret env), never `value`/`body` of login/`key`. While the type is unchanged the secret fields' `required` becomes `nullable` and an empty secret keeps the stored one (`LaunchpadForm::source($stored)` merges it, the Google private key reuses the stored email + PEM); `UpdateLaunchpadAction::assertSecrets()` re-checks against the LOCKED row so a forged `storedAuth` cannot save a secret-less source. Type `off` REMOVES the source (unlike replace, where `off` keeps it) and, when a nightly refresh has ever run (`settings.refresh` exists), also deletes the generated `data.json` of the program's folder through `CleansAttachedFiles::deleteStoredFiles` (`Launchpad::directory()` + `storedName(config('launchpad.refresh.file'))`) and clears `settings.refresh`; a program whose refresh never ran keeps its own uploaded `data.json`; a changed type or any changed value stores the new source and re-arms `refresh_due_at = now()` + `RefreshLaunchpadJob`; an unchanged source queues nothing, except a program that became live through the new dates and has a source is re-armed (like activate). The Action is the only other reader of `source` besides `RefreshLaunchpadAction::execute()` (it reads it under `lockForUpdate` to merge secrets).
- `UpdateLaunchpadAction`: guard read (`canManage`), validation, tab check (`verifyTabs()` only when the source computed from the form differs from the stored one — an edit that does not touch the connection never calls Google), then ONE transaction `lockForUpdate` + `canManage` + kind re-check; audience filtered like create (`visibleOnBoard`, owner excluded); `StateService::flush()` after commit when the audience was or is filled. Audience shrink needs no confirmation (owner decision pending); `seen_by` stays as is.
- Edit-only audience selection: the edit form renders the same `bulk` member-picker bound to `editForm.audience`, so both trait targets share one component and one behavior.
- Public program (2026-11-19, «برای همه کاربران»): `settings['public'] = true` (absent = private, no column) read through `Launchpad::isPublic()` (strict `=== true`). `LaunchpadAccessPolicy::canView` lets any active user see a public row while it is live/soon (so the file route, `/go`, `open`, details and workspace options follow with no extra check); `scopeVisibleTo` and the `shared` filter add `settings->public`. A public row never lights the dot: `markSeenBy` returns early, `scopeUnseenBy` excludes it, and its audience is always saved as `[]` (create, replace and `UpdateLaunchpadAction`; the picker is hidden while `form.public`/`editForm.public` is on and `max_audience` is validated only for private rows). The switch row (`launchpad-public-switch`, copy of the kind-switch layout) lives in create and the edit modal; replace/save keeps it only if the switch is on in that submission. The audience cell and details show «همهٔ کاربران»; the Filament audience column shows the same; admin cannot change it (monitoring). Selects that feed `canView`/`markSeenBy` must include `settings`.
