# JavaScript Architecture & PWA Strategy

## 1. Core Philosophy
A highly interactive PWA powered by Laravel Livewire and Alpine.js.

1. **Zero UI Flash (Reactive Hot-Swapping):** HTML renders before Alpine downloads — a centralized Proxy Hub eagerly registers component blueprints.
2. **Strict State Segregation:** UI interaction logic (toggling a modal) is separated from global app state (Dark Mode).
3. **PWA-First Routing:** The Service Worker aggressively caches fonts/css/js but never HTML (prevents CSRF token mismatches and Livewire hydration failures).

## 2. Directory Structure & Layers

```
resources/js/
├── app.js                      # Vite entry point: orchestrates initialization
├── sw.js                       # Service Worker: Workbox caching rules
├── core/                       # The engine room
│   ├── bootstrap.js            # Axios/Laravel CSRF setup
│   ├── theme-manager.js        # DOM manipulation for themes & view-transitions
│   ├── livewire-errors.js      # Livewire request-hook → global toast with precise error message + 419 session self-heal (§18)
│   └── tooltip.js              # Body-level singleton tooltip driven by `[data-tip]` holders (§17)
└── components/
    └── alpine/
        ├── main.js             # The Proxy Hub (eager registration)
        ├── stores/             # Global singletons (app-wide state)
        ├── data/               # Component factories (UI element logic)
        └── mixins/             # Cross-cutting reusable behaviors
```

## 2a. Testing (Vitest, added 2026-10-01 — supersedes the older scattered "no JS test runner in this project" notes below)

**Vitest is now configured** (`vitest.config.js`, repo root; `jsdom` environment; `npm test` runs once, `npm test:watch` watches). Before this, several entries further down this doc (fancybox caption XSS, `audioPlayer.js`) correctly stated "no JS test runner — enforced by code review discipline, not automation" **at the time they were written**; those entries are historical and left as-is (the specific files they describe still have no test), but the blanket claim is no longer true project-wide.

**Convention — mirrors the PHP `coreTestPattern.md` "one master file per class" rule:** one test file per Alpine data-component/mixin, colocated in a sibling `__tests__/` folder next to the source it tests — `resources/js/components/alpine/mixins/<file>.js` → `resources/js/components/alpine/mixins/__tests__/<file>.test.js`, same for `data/`. Not a parallel top-level test tree; not one giant file per folder. Only meaningfully important, pure-logic assertions — same bar as `coreTestPattern.md` ("would break behavior or silently kill a feature"), not line-coverage padding — so most files will never get one (a component that's 95% `$wire`/DOM calls has little worth unit-testing; don't force a file onto it for the sake of coverage).

**jsdom's own `requestAnimationFrame` is not reliable for a short test-level `await` — force-override it, don't guard with `if (!global.requestAnimationFrame)`.** All three files that exercise rAF-scheduled code (the scroll-handler RAF-throttle in `_bindViewport()`, `chatBase.js`'s `autoGrow`) install `global.requestAnimationFrame = (cb) => setTimeout(cb, 0)` unconditionally at the top of the file. **Wire-capture regression testing (`mixins/__tests__/_wireMock.js`, shared by all 3 files above):** `createWireMock(props)` builds a `$wire` double where `.$island(name)` memoizes a Proxy that auto-vends `vi.fn(() => Promise.resolve())` for any method name accessed, so a test can assert on `wire._islands.messages.someMethod` without the helper needing to know every possible island method up front. `installWireProbe(c, props, allowedAccesses = 1)` is the sharper tool: it makes `c.$wire` throw the instant it's read more than `allowedAccesses` times, proving a method captures `this.$wire` the expected number of times and reuses that reference rather than re-reading `this.$wire` after an `await`/`.then()` — the exact regression class this session fixed repeatedly (`backToList`, `doCancelInvite`, `toggleBrowse`, ...). `allowedAccesses` must be worked out BY READING THE SOURCE of the method under test, not guessed: 1 for a bare `const wire = this.$wire`, 2 if it also calls a helper like `_isl()` that reads `this.$wire` again before the same await point, 0 if an earlier short-circuit means `$wire` is never touched at all for that code path. Get the count wrong and the test either false-fails (too low) or silently stops proving anything (too high) — when a test's own setup legitimately produces two DOM elements with the same `id` (e.g. calling a `withTextarea()`-style helper twice in one test without clearing `document.body` between), `getElementById` quietly returns the stale first one and can make a later call re-enter a branch you already tested, which reads as a confusing "extra $wire access" failure that isn't about `$wire` at all — split into separate `test()` blocks (each gets a fresh DOM via `beforeEach`) rather than reusing one test for multiple input states. This is deliberately NOT timing/microtask-based (an earlier draft tried gating on a `queueMicrotask` tick and proved unreliable — test-runner machinery itself incurs microtask hops before a test body even starts, so "first tick after setup" doesn't reliably line up with "the first await inside the method under test"); count-based is deterministic.

**Listener cleanup, `AbortController` pattern (adopted 2026-10-01, Channel/Contact's `init()`/`destroy()`):** instead of storing each bound handler as `this._onXxx` and calling a matching `removeEventListener` per listener in `destroy()` (the older pattern, still present in some modules), create one `const ac = new AbortController()` in `init()`, pass `{ signal: ac.signal }` (alongside any other option like `{ passive: true }`) to every `addEventListener` call that component registers, and tear all of them down with a single `ac?.abort()` in `destroy()`. Strictly safer than the manual-tracking pattern — one call can't drift out of sync with however many listeners exist, and a newly-added listener only needs the `{ signal }` option, not a new paired removal line. Not yet retrofitted everywhere; prefer it for any new module's event-listener cleanup, and feel free to port it to an existing module opportunistically rather than all at once.

**Triage heuristic — deciding what's "test-worthy" before spawning a test-writing agent (established 2026-10-01, applied across data/mixins/stores/core):** this suite deliberately does NOT aim for 100% file coverage — only files with real, breakable logic get a test file. Before delegating a batch, triage by actually reading (or at minimum skimming) each candidate file, not by line count alone:
- **Worth it:** files with branching logic, math/string/date computation, state machines, localStorage persistence round-trips, retry/backoff loops, or anything a future edit could silently break without an obvious visual symptom. Examples from this session: every `data/*.js` component factory, all 15 `stores/*.js` files (even thin-looking ones like `app.js`/`chrome.js` got a small honest 1-test file rather than being skipped outright, since "turns out trivial" is a valid OUTCOME of triage, not a reason to skip triage), `core/theme-manager.js`/`core/tooltip.js`/`core/record-focus.js` (real DOM-state-resolution and retry logic).
- **Not worth it, skip:** pure visual/canvas/animation generators (`data/patterns/*.js` — no meaningful assertions, better verified by looking at them run), thin registration/wiring glue with zero branches (`alpine/modules/*.js` — literally 3-5 lines of "import X, register X", `core/bootstrap.js`/`core/filament.js`/`core/topbar-autohide.js` — 4-16 lines, no logic), and thin third-party wrappers (`mixins/fancybox.js`). Forcing a test file on these produces either padding (asserting a one-line passthrough does what it obviously does) or brittle canvas/DOM mocks that don't catch real bugs — net negative, not neutral.
- **When delegating a batch, tell the agent to verify the triage, not trust it:** line-count-based pre-sorting is a starting heuristic, not a verdict — a "promising" 100+ line file can turn out to be mostly dead wiring, and a "thin" 20-line file can hide a real retry/edge-case bug. Every batch prompt in this session instructed: read the file fully first, and if it's thinner than expected, write an honest smaller test file (or skip it and say why) rather than padding to hit an expected count.
- **Findings discipline:** every test-writing agent is told to flag suspected bugs in its final report, never silently fix them — the Lead reads each finding, independently verifies it against the actual source (not just the agent's claim) before proposing a fix, and the user decides whether it's worth fixing. This caught several real bugs this session (a crash-on-first-read in `password.js`, a wrong-field-length check in `report.js`, a wrong Unicode boundary in `mention.js`'s @mention matching, a DOM-cleanup leak and a floating-point display artifact in `accessibility.js`, a false-positive match in `activityReactionPicker.js`, a `null`-coerces-to-id-`0` quirk shared by `pinned.js`/`sound.js`) — most were worth fixing, two (`radio.js`'s unreachable offline branch, `background.js`'s tab-index offset) were traced and confirmed to be correct-as-is, not bugs, and left untouched specifically BECAUSE they were verified rather than assumed.

**Scope, deliberately narrow — pure logic only, never DOM/Livewire integration:** a Vitest unit test can call a data-component factory (`chatBase('contact')`, `contact()`) directly and assert on its plain-JS methods (debounce/backoff math, string/emoji classification, filter-token matching) with zero DOM, zero `$wire`, zero Alpine runtime. **It cannot and must not attempt to simulate Alpine directives, Livewire islands, or `$wire` calls** — `$wire`/`$el`/`x-on`/`x-show`/island morphing are a real browser's job, and this project's own `@island` rules (`app/Livewire/livewirePattern.md`) document multiple bug classes (bare-`$wire` island skip, `<template x-if>` morph-staleness, `x-ref` walk failures) that are invisible to ANY form of automated test, PHP or JS — the real-browser pass (`contactPattern.md`/`channelPattern.md` §14/§17) remains the only arbiter for island/DOM behavior. A passing Vitest suite is evidence the pure-logic branches are correct, never evidence an island or a click handler actually works in the browser.

## 3. The Alpine.js Ecosystem

### 3.1 The Proxy Hub (`main.js`)
Alpine crashes if an `x-data="calculator"` function isn't registered before Alpine boots. `main.js` imports every data component and store, hooking into `alpine:init` to register them deterministically.

```javascript
import registerThemeStore from './stores/theme.js'
import sidebar from "./data/sidebar.js";

export default function initAlpine() {
    document.addEventListener('alpine:init', () => {
        registerThemeStore(Alpine)
        Alpine.data('sidebar', sidebar)
    })
}
```
By the time Alpine looks for `x-data="sidebar"`, the blueprint is already in memory — instant hydration.

### 3.2 Global Stores (`stores/`)
Stores hold state that survives DOM-element destruction or is shared across components.

```javascript
export default (Alpine) => {
    Alpine.store('appTheme', {
        current: 'default',
        set(theme) { window.ThemeManager?.setTheme(theme); }
    });
}
```
*Usage:* `<div :class="$store.appTheme.current === 'dark' ? 'bg-black' : 'bg-white'">`

### 3.3 Component Factories (`data/`)
Strictly factories returning an object; they govern local UI interactions. **Naming rule:** the registered string key must exactly match the filename (`password.js` → `Alpine.data('password', password)`).

```javascript
export default () => ({
    visible: false,
    toggle() { this.visible = !this.visible }
})
```

### 3.4 Shared Mixins (`mixins/`)
Cross-cutting behaviors reused by several factories, as factories returning a plain object, spread into a data factory's return value with `...mixinName()`.

**`maximize.js`** — backs the per-widget "maximize" feature (`.max-widget` fixed overlay + hiding `#header/#navbar/#footer` via `.layout-hidden`, plus a `window resize` dispatch for charts). Exposes `applyMaximize(active)`; default `toggleMaximize()` toggles a single `max` boolean through it. `applyMaximize` also toggles `maximized` on `#content-shell` (the `layouts/app.blade.php` wrapper around `@yield('content')`) — every maximizer in the app funnels through this one method, so that class is the single global "is anything maximized" lever; `dashboard.css` consumes it with a mobile-only (`@media (width < 48rem)`) rule that tightens the maximized margins (0.5rem padding + 100dvh on `#content-shell`'s direct child, `!important` to beat the roots' Tailwind `px-4 py-4 h-[calc(100dvh-60px)]`), and a sibling mobile-only override shrinks `.max-widget`'s fixed frame itself from `inset: 1.5rem` to `0.5rem` (radius 1rem) — that frame is the visible margin in maximized full-page chats, since the widget becomes a fixed overlay the content-shell padding never touches. Both `.max-widget` and `.max-widget-column` carry `scrollbar-gutter: auto` (changed from `stable` 2026-09-23 on all viewports): the app's scrollbars are classic 8px-wide, transparent until hover, and `stable` reserved that strip permanently on the left edge (RTL), making the maximized panel's left side read as clipped/chipped; with `auto` the strip appears only while actually scrolling. Don't reintroduce `stable` on a maximize overlay. Desktop is untouched by construction — never add un-scoped rules off this class.

**Graceful close for `.max-widget` (added 2026-09-23) — `maxLeaving`, a second boolean alongside `max`.** Before this, `.max-widget`'s entrance played `slideScaleIn` (0.6s) but closing was a plain class removal — `max` flipped straight to `false`, instantly snapping the fixed overlay back to its resting layout with zero animation (a real, reported "jerky/broken-looking" close, unlike every other part of this app which already animates gracefully both ways). `toggleMaximize()` now branches on close: sets `maxLeaving = true`, calls `applyMaximize(false)` (unchanged — chrome un-hides immediately, no visual conflict since the widget is still `z-index:999999` on top of it), then a single `setTimeout(MAX_WIDGET_CLOSE_MS = 350)` before actually flipping `max = false` and clearing `maxLeaving`. Every consumer's class binding is `:class="{ 'max-widget': max || maxLeaving, 'max-widget-leaving': maxLeaving }"` (9 binding sites across `channel.blade.php`, `contact.blade.php`, `dms.blade.php`, `ths.blade.php`, `reservation/command-grid.blade.php`, `project.blade.php`, `tab/calendar.blade.php` ×3)

**`heroDeck.js` missed the 2026-09-23 rollout entirely (found+fixed 2026-09-29) — it doesn't spread `toggleMaximize` from the mixin.** `heroDeck()` spreads `...maximizeMixin()` for `applyMaximize`/`max`/`maxLeaving`, but overrides `toggleMaximize` with its own pane-keyed version (`maximizedPane` — one of N panes in a `x-for`, not a single boolean) that never set `maxLeaving`, so the home-page hero-pane maximize snapped shut instantly. Fixed to branch on close exactly like the mixin (`maxLeaving = true` → `applyMaximize(false)` → local `MAX_WIDGET_CLOSE_MS = 350` `setTimeout` before clearing `maximizedPane`/`maxLeaving`). **The class binding differs from the other 9 sites on purpose:** `tab/home.blade.php`'s pane is one of several `x-for`-looped elements sharing the single mixin-level `maxLeaving` boolean, so a bare `maximizedPane === pane || maxLeaving` would incorrectly leaving-flag EVERY pane once any one of them starts closing. Correct per-instance guard: `:class="{ 'max-widget': maximizedPane === pane, 'max-widget-leaving': maximizedPane === pane && maxLeaving }"` — AND, not OR, because (unlike the mixin's own `max`) `maximizedPane` stays equal to the closing pane for the entire leaving window (only nulled inside the timeout), so the AND form is exactly as robust as the 9 sites' OR form, just correctly scoped to one pane out of many. **Rule: any future multi-instance (`x-for`/list) consumer of this mixin must gate `max-widget-leaving` on `<instance-key-match> && maxLeaving`, never bare `maxLeaving`, to avoid leaking the leaving state across sibling instances.** Same-bug, coupled fix: `<x-ui.modals.max-backdrop state="maximizedPane" close="toggleMaximize(maximizedPane)"/>` previously passed `close="toggleMaximize(null)"` — since the new (and old) `toggleMaximize(pane)` compares `this.maximizedPane === pane` to decide the branch, calling it with a literal `null` while a real pane id was maximized took the wrong branch (opened instead of closed, leaving `#header`/`#footer` wrongly hidden after a backdrop click) — fixed to pass the live `maximizedPane` value, matching the escape-key handler on the same page which already did this correctly. — `.max-widget.max-widget-leaving` (higher specificity, `dashboard.css`) overrides just the `animation` property to `slideScaleOut` (350ms, Material `cubic-bezier(0.4,0,0.2,1)` — smoother than a sharp accelerate curve, which read as janky on a large fixed-position element) while `.max-widget`'s own positioning/sizing stays inherited. `.max-widget` also gained `will-change: transform, opacity` — promotes it to its own compositor layer so the scale animation doesn't force main-thread repaint on a viewport-sized element (this, not the easing curve, was the real fix for the reported jerkiness). `<x-ui.modals.max-backdrop>` mirrors the same idea: `x-bind:class="{ 'max-backdrop--leaving': typeof maxLeaving !== 'undefined' && maxLeaving }"` (guarded — several consumers use their own bespoke `maximizedWidget`/`maximizedColumn`/`maximizedFeed` state instead of this mixin's `max`/`maxLeaving`, e.g. `energy/chart.blade.php`, `taskboard/column.blade.php`, `tab/feeds/timeline.blade.php` — the `typeof` guard makes this a no-op there, zero regression risk) triggers `.max-backdrop--leaving`'s plain `opacity` CSS transition (350ms), fading in sync with the widget instead of both vanishing together. **Rule: any new `.max-widget` consumer must bind BOTH classes off `max || maxLeaving` / `maxLeaving` exactly like the 9 existing sites — binding off bare `max` alone silently loses the graceful close.**

**Persisted across reload/navigation (added 2026-10-05) — `maximizeMixin(scope)` now takes the consumer's own identity string, required to build a per-module-per-user `localStorage` key.** `maxStorageKey(scope)` returns `null` (persistence silently disabled, zero behavior change from before) when `scope` is falsy, when `document.documentElement.dataset.uid` is empty (guest/unauthenticated edge case — the `data-uid` attribute on `<html>` deliberately has NO `?? 0` fallback, since the literal string `"0"` is truthy in JS and would otherwise pass every guard as a "valid" uid, leaking a shared storage key across sessions), or when `window.self !== window.top` (an embedded `?embed` iframe, e.g. heroDeck's module previews, must never read/write the parent page's preference). Every consumer calls `this.initMaximize()` exactly once from its own `init()` — never relies on a mixin-level `init()`, since every consumer already defines its own and Alpine's spread-then-override would silently drop one or the other. **Two shapes, same contract:** the 7 plain `max`-boolean consumers (`channel`/`contact`/`dms`/`ths`/`project`/`reservation`/`calendar`'s `calendarView`) get the mixin's default restore (`initMaximize()` sets `max = true` + `applyMaximize(true)` when a key is found); the 4 named-target consumers (`energyChart`/`heroDeck`/`taskboard`/`feed` — see above, these never used the mixin's `max` anyway) each define their own `restoreMaximize(value)`, which `initMaximize()` calls instead when present. **Rule: every `restoreMaximize(value)` MUST validate the stored value against the LIVE DOM before trusting it** (`taskboard`/`feed` query `[data-column]`/`[data-feed]`; `heroDeck` checks `this.panes`; `energyChart` queries `[data-widget]`, added on the same date — a static `WIDGETS.includes(value)` array check was the first cut and shipped a real bug: `team`/`history`/`score`/`radar` are conditionally rendered in `energy/chart.blade.php`, so a stale value for a widget no longer on screen passed the array check, hid the chrome, and left no visible maximized panel or close button — recoverable only via the undiscoverable global Escape handler). On a validation miss, call `this._persistMaximize(null)` to self-heal the stale key, never leave it behind. **Write-timing rule: `_persistMaximize` is called at the moment intent is clear — synchronously on open, and synchronously at the START of a close (before any `setTimeout`/`maxTimer`), never inside the close callback** — so a reload mid-close-animation correctly restores "not maximized," and the close persisting doesn't depend on a timer that might never fire if the page unloads first. **Last-open-item persistence (added 2026-10-05) — `mixins/lastOpen.js`, a sibling of `maximize.js` with the identical guard shape, a different key prefix (`last:` not `max:`) and no boolean state.** Reloading `channel`/`contact`/`project` always reset to the default/empty pane regardless of maximize, since the server has no notion of "which conversation/project was open" to re-render on first load — `#[Url]` was considered and declined (accepted tradeoff: a brief flash of the default pane before Alpine restores the right one client-side). `lastOpenMixin(scope)` exposes `_lastOpenStorageKey` (`last:${scope}:${uid}`, same three guards as `maxStorageKey` — falsy scope, missing `data-uid`, framed `window.self !== window.top` — all collapse to a null key, persistence silently disabled), `_persistLastOpen(id)` (no-ops on a falsy id or null key, try/catch write), and `_readLastOpenId()` (try/catch read, `parseInt` back to a number or `null`). Each of the three consumers spreads `...lastOpenMixin(scope)` with the SAME scope string already passed to `maximizeMixin(scope)` in that file, and wires it at exactly two points: (1) inside its own `selectChannel`/`selectContact`/`selectProject(id)`, `this._persistLastOpen(id)` is the first side effect (mirrors `_persistMaximize`'s "write at the moment intent is clear" rule) — the method's trailing promise chain also gained a `return` it didn't have before, needed for point 2; (2) at the end of `init()`, `const lastId = this.$wire.<activeXId> ? null : this._readLastOpenId();` — the existing server-rendered "is something already active" property (`activeChannelId`/`activeUserId`/`activeProjectId`) is the override guard, so a restore never fights a genuine deep link (Project's `focusRecord()` included, since that path also lands in `activeProjectId` before Alpine mounts) — `if (lastId) this.selectChannel(lastId).finally(() => this.initMaximize()); else this.initMaximize();`. **Sequencing with maximize is the load-bearing part:** all 3 consumers are "plain `max`-boolean" (§ above) — `initMaximize()` synchronously hides `#header/#navbar/#footer` the instant it runs, with zero awareness of whether a conversation has actually loaded; calling it immediately alongside a kicked-off-but-unresolved restore would maximize around an empty/stale pane. Moving the original early `this.initMaximize()` call to the end of `init()` and gating it behind `.finally()` on the restore call (only when a `lastId` exists; otherwise called immediately, byte-for-byte the pre-existing behavior) delays the chrome-hide until the restored selection's full promise chain has settled — resolved or rejected, never left hanging. Moving `initMaximize()` later in each file's `init()` was checked against every statement it jumped past (pulse-channel/leader-election setup in `project.js`, DOM listener registration in `channel.js`/`contact.js`) and confirmed order-independent: nothing `initMaximize()`/`applyMaximize()` touches depends on any of them, and nothing moved-past depends on `initMaximize()` having already run.

**`mention.js` — the single source for `@mention` detect/filter/build/notify logic, spread by every composer that does `@mentions` (`channel.js`, `project.js`, `projectComposer.js`).** Four pure helpers: `mentionFilter(names, query)` (case-insensitive substring; empty query returns the full list), `mentionAtTerm(value, cursor)` → `{at, term}` or `null` (finds the active `@term` under the caret; closes on `/[\s@]/` inside the term and requires whitespace before `@` — the most-complete "channel-style" close, adopted as the canonical rule across all three composers), `mentionBuild(value, cursor, name)` → `{value, caret}` (splices `@name ` at the caret), and `mentionIsNotified(body, name)` (Unicode token-boundary regex `(?<![\p{L}\p{N}_])@name(?![\p{L}\p{N}_])` with the `u` flag; `name` is regex-escaped first, so `@Al` does not match `@Albert` and a metacharacter in a username can't break the pattern). **`formatCaption` is mandatory the moment any `data-fancybox` anchor carries `data-caption` from user-controlled text — never let Fancybox use its default caption renderer.** Fancybox v6 spreads `el.dataset` onto the slide config and renders `slide.caption` via `innerHTML`, not `textContent` — Blade's `{{ }}` escaping on the `data-caption` HTML attribute only prevents attribute-breakout at parse time, it does NOT stop the browser from decoding the attribute back to a raw string that Fancybox then treats as HTML at render time. `FANCYBOX_OPTIONS.formatCaption` closes this by building a `<span>` and setting `.textContent` (never `.innerHTML`) — returning an `HTMLElement` from `formatCaption` routes Fancybox through its safe DOM-append branch instead of the `innerHTML=` sink. **Tenant-driven backdrop mode (`stores/background.js` + `data/background.js`):** the quick-settings "dynamic background" images, cycling behavior, tint, and per-image CSS filters/inset are all tenant-config-driven, not hardcoded. `stores/background.js` reads one nested global, `window.__tenantBackdrop = { images, mode, opacity, blur, brightness, contrast, grayscale, width, fit }` (set by an inline `<script>` in `layouts/app.blade.php`, same ordering trick as `window.__moduleChunks` — see `config/tenantPattern.md`'s "Dynamic user-panel backdrops" for the full server side), destructured into module-level `BACKDROP_*` constants and exposed on the store 1:1 (`images`/`backdropMode`/`opacity`/`blur`/`brightness`/`contrast`/`grayscale`/`width`/`fit`, default `'cover'` when the tenant omits the key). `data/background.js` (the `x-data="background"` factory backing `components/dashboard/background.blade.php`) branches its `init()` on `$store.background.backdropMode`: `'tabs'` keeps the original per-tab crossfade (`updateState()` watching `$wire.activeTab`); `'time'` instead picks one fixed `activeIndex` for the whole session by matching the visitor's local hour to a `morning`/`noon`/`evening`/`night` bucket against each image URL's filename (`timeOfDayKey()`) and never registers the tab watcher — so a `'time'`-tenant's backdrop stays the same no matter which tab the user is on. `renderIndices` (a getter alongside `_baseFilter`) is what `background.blade.php`'s `x-for` actually iterates: all image indices in `'tabs'` mode (any of them can become active), just `[activeIndex]` in `'time'` mode (or `[]` if `images` is empty) — so a `'time'`-tenant's browser only ever fetches the one image it will actually show, not the full set. **`imageStyle(index)` (`data/background.js`) is the single place per-image inline style is computed — `background.blade.php` calls it once per `x-for` iteration instead of building `backgroundImage`/`filter`/inset inline in the template.** Three things it does, all data-driven rather than Tailwind-class-driven (a tenant tunes these purely through `config/tenants.php`, no template edit): (1) `backgroundImage: url(...)` for that index's image; (2) an optional `filter` string (built by the `_baseFilter` getter, reused by every call to `imageStyle`) assembled only from the non-neutral pieces (`blur(Npx)` if `blur` is truthy, `brightness(N)` if `brightness !== 1`, `contrast(N)` if `contrast !== 1`, `grayscale(N)` if `grayscale` is truthy) — a tenant at all-neutral values gets no `filter` property at all, zero extra style cost; (3) for the currently-`activeIndex` image only, an inset (`width`/`marginInline: auto`/`marginBlock: 1.25rem`) when `width !== '100%'` — this replaced a hardcoded `w-[85%] mx-auto my-5` that used to sit directly in `data/background.js`'s `ACTIVE_CLASSES` constant (now just the two animation classes), since a Tailwind arbitrary-value class is fixed at build time and can't follow a value that only exists in `config/tenants.php` at runtime. The overlay tint is separate from `imageStyle()` (it paints over every image, not per-index): `background.blade.php`'s tint layer binds `:style="{ opacity: $store.background.opacity }"` instead of a baked-in Tailwind alpha class (`bg-[...]/85`).

**`stores/background.js`'s `storage` resolution — probe once at module load, not per-call.** Rather than wrapping every `localStorage` access in its own try/catch (the older, more verbose idiom still used elsewhere in this codebase), this store resolves a module-level `storage` binding once: `storage = window.localStorage; storage.getItem('')` inside a `try`, falling back to a no-op stub (`{ getItem: () => null, setItem: () => {} }`) in `catch`. That one real `getItem('')` call — not just referencing the `localStorage` property — is load-bearing: some private-browsing/storage-partitioning states let you reference `window.localStorage` without throwing but throw on the first actual read/write, so a bare property check would miss them. **Still keep a per-call try/catch inside `readBool`/`readString`/`write` themselves** even with the stub fallback in place — `storage` can start out healthy at module load and still throw later (a live permission or storage-partitioning change mid-session is rare but not impossible), and these three are called synchronously while building the Alpine store object, where an uncaught throw would break the whole store's registration, not just degrade one read.

**Why persol's `opacity` differs from fateh's, and why that's the correct fix, not a workaround:** fateh's 0.85 tint was tuned for 8 small abstract shapes cycling behind a heavy translucent wash (deliberately a faint texture, not a recognizable image). Persol's backdrops are real photographs shown statically for the whole session — the identical 0.85 strength left only a sliver of the photo visible, reading as "barely showing / oddly blended." Since `opacity` already travels through config, not a shared Tailwind class, the fix was a one-line per-tenant value change, not a component rewrite; persol's exact figure is being hand-tuned live against the real photos (see `config/tenants.php` for its current value, not this doc). Any future `'time'`-mode tenant with photographic (not abstract) backdrops should start from persol's value.

**One `@php ... @endphp` block per script-tag JSON payload — never the `@php($expr)` single-statement shorthand for anything feeding a following block.** `layouts/app.blade.php` computes `$backdrop` (a plain array later echoed via `@json($backdrop)`) in a full `@php ... @endphp` block, not `@php($backdrop = [...])`. The inline single-argument form was tried first and silently corrupted the rest of the file: it compiles to a bare `<?php($expr)` with no trailing `;`/`?>`, so the PHP parser never closes that tag and everything after — including the next `@php ... @endphp` block computing `$moduleChunk`/`$viteEntries` for `@vite(...)` — gets swallowed into the same unterminated PHP region, surfacing as `Undefined variable $viteEntries` at a completely unrelated line. Confirmed via `app('blade.compiler')->compileString(...)` on the raw template. Rule: always use the block form when more than a trivial one-liner precedes a directive that depends on normal HTML/Blade parsing resuming afterward.

**One deliberate deviation from `links.js`'s `recordClick`: how the item object is built.** Links builds it inline in Blade via `@click="recordClick({ id: @js($link->id), title: @js($link->url_title), ... })"` — each field individually wrapped in `@js()` inside a JS object literal embedded in a double-quoted HTML attribute. DMS instead reads the item from the DOM: `x-on:click="recordClick({ id: $el.closest('tr').dataset.docId, title: $el.closest('tr').dataset.docTitle, url: $el.href })"`, with `data-doc-id`/`data-doc-title` set once on the `<tr>` (alongside the existing `data-rf="dms-{id}"`) via plain `{{ }}` Blade interpolation, matching the "DOM-sourced item key" `data-*` idiom already documented for taskboard column state. Reason: `@js($value)` JSON-encodes a string with hex-escaped inner quotes (`JSON_HEX_QUOT` etc.) so content *inside* the string is attribute-safe, but the JSON string's own delimiting `"..."` quotes are real characters — embedding that raw inside an already-double-quoted `@click="..."` HTML attribute means the JSON string's own opening quote prematurely closes the surrounding attribute the moment `@js()` runs on a value that itself needs quoting (which every string value does, being valid JSON). Document titles are free-text (uploaded/admin-entered), a materially more likely source of attribute-breaking characters than Links' curated `url_title` field, so the `data-*`-attribute route (zero embedded-quote risk, since values are read from the DOM at click time, never string-interpolated into the attribute itself) is the safer choice here — not a correction of Links (out of scope, untouched), just the reason DMS doesn't copy that one specific technique.

**Why the URL is captured and stored raw, not re-resolved server-side on reopen:** `route('secure-file', $doc->file)` (the DMS download route) is a plain named route behind auth middleware, NOT a signed/expiring URL (confirmed: no `URL::temporarySignedRoute` anywhere in its definition) — access is re-checked per-request server-side inside the controller action, not baked into the URL's signature. That makes it safe to cache the resolved URL client-side indefinitely; a card whose underlying doc was later deleted/access-revoked just degrades to a 403/404 on click, same as any stale bookmark would. This is what makes the feature purely client-side: `<a :href="doc.url" target="_blank">` reopens the exact same URL with zero Livewire call — same contract as Links' `item.url`.

**Wiring point: the real "open document" anchors, not the `confirmRead` button.** The real click points are the anchors/buttons in `dms/table.blade.php` (single-rendition, multi-rendition list, "مشاهده و تایید", "مشاهده مجدد") — each gets the sibling `x-on:click="recordClick(...)"`. **`<template x-if="...">` only ever renders its FIRST element child — a second sibling root is silently dropped, not an error.** Confirmed in Alpine's bundled source (`livewire.js`, `x-if`'s directive handler: `el.content.cloneNode(true).firstElementChild`) — it clones the `<template>`'s content and takes only `.firstElementChild`, discarding any further siblings entirely. Real bug, found 2026-09-10 in the hamburger menu (`components/dashboard/modal/menu.blade.php`): the grid view's `<template x-if="viewMode !== 'list'">` wrapped TWO sibling roots — the sliding page carousel and the pagination row below it — so the paginator silently never rendered in grid mode (list view was unaffected, since its `x-if` template already had a single root). **Fix: wrap multiple roots in one `<div class="contents">`** (CSS `display:contents` makes the wrapper itself layout-invisible — its children participate directly in the *real* parent's flex/grid context, so no spacing/sizing side effect) so the `x-if` template has exactly one child. **Rule: any `<template x-if="...">` (or `x-for`) with more than one top-level element inside needs this single-`contents`-wrapper pattern — Alpine gives no console warning when it silently truncates to the first child, so this class of bug reads as "half my conditional block vanished" with zero error trail.**

**Countdown resumption across a real time gap — persist an absolute target, not a relative remaining value:** `stopwatch.js`'s countdown persists `armedUntil` (an absolute `Date.now() + seconds*1000` epoch-ms timestamp), not `seconds` alone. On `restoreState()`, remaining time is recomputed as `armedUntil - Date.now()` — correct regardless of how long the gap was (a full-page reload, or the tab closed and reopened hours later), unlike persisting a raw seconds-remaining number which would silently keep counting down from a stale value once restored. If the recomputed remaining is `<= 0`, the alarm fires immediately on that page load — the countdown would have completed while the tab was gone. The same absolute-timestamp technique feeds the site-wide event-reminder feature (`window.__eventReminder` → `stopwatch.js`'s `armReminder()`) — see `app/Livewire/livewirePattern.md`'s "Calendar event reminder" section for the full cross-stack design (why a plain `window` global instead of a `CustomEvent`, DOM-init-order reasoning, conflict-avoidance with a manually-running timer).

**Scope — data factories only, not stores:** the mixin spreads into a `data/` factory's return object (Alpine component scope, where `this.$dispatch` and per-instance overrides live). Do NOT spread it into a `stores/` singleton. The one remaining bare `navigator.clipboard.writeText` lives in `stores/filament-menu.js`'s `share()` intentionally: admin-panel-only (always HTTPS in prod, localhost in dev → `isSecureContext` reliably true), with a `navigator.canShare?.()` primary path and `window.FilamentNotification` toast. Leave it.

**Named-slot variant:** when a page has several independently-maximizable widgets (energy chart, taskboard columns), one shared backdrop requires a single active slot rather than N booleans. The factory spreads `...maximizeMixin()` for `applyMaximize`, declares `maximized<Thing>: null`, and overrides `toggleMaximize(name)` to set the active slot and reuse `applyMaximize()`. The view binds one root `<template x-if="maximized<Thing>">` backdrop and each item's `:class="{ '…': maximized<Thing> === name }"`. Maximization is mutually exclusive by construction (two `position:fixed` overlays cannot coexist) and avoids the bug where a bare `@click="toggleMaximize"` passes the `MouseEvent` as `context`. Items carry no `x-data` — every expression resolves up to the single parent factory scope (Alpine scope inheritance): one source of truth.

**DOM-sourced item key + lifted per-item state:** for a repeated item (taskboard column) needing per-item state (collapse), don't give each item its own `x-data` with inline `localStorage`. Lift state to the parent factory as a map keyed by the item's DOM identifier (`collapsed: {}`), seed it from `localStorage` in `init()` by scanning `[data-column]` elements, expose `isCollapsed(name)`/`toggleCollapsed(name)`. The key is read from the DOM via `col(el)` = `el?.closest('[data-column]')?.dataset.column`; every Alpine expression uses `col($el)` (or `$el.dataset.column` on the item). This avoids the quoting pitfall where `{{ $column }}` interpolated *inside a nested JS string literal* (e.g. `'[data-column=\" {{ $column }}\"]'`) breaks the entire `:class`/`x-show` binding. Rule: put the PHP value only in a plain HTML attribute (`data-column="{{ $column }}"`), never inside an Alpine expression's string literal.

**Partial-width maximize:** `.max-widget` is full-screen (`inset: 1.5rem`), which collapses narrow items (a 280px taskboard column barely changes). Use `.max-widget-column` instead (centered, `width: clamp(60vw, 70vw, 75vw)`, `height: 85vh`, `z-index: 999999`) so the maximized item occupies 60–75% of the viewport.

**One reusable backdrop (`<x-ui.modals.max-backdrop/>`):** a single Blade component backs both modes. Two expression props — `state` (truthy-when-maximized, default `"max"`) and `close` (click handler, default `"toggleMaximize()"`) — render `<template x-if="{!! $state !!}"><div class="max-backdrop" @click="{!! $close !!}"></div></template>` (raw echo so quotes survive). Single-boolean modules (contact, dms) include it with no props. Named-slot modules (energy `maximizedWidget`, taskboard `maximizedColumn`) pass `state="maximized<Thing>" close="toggleMaximize(null)"`. The `close` default is an *explicit call* — a bare `@click="toggleMaximize"` makes Alpine inject the `MouseEvent` as the first argument, which `toggleMaximize(name)` would store as the active slot (the original silent-close bug).

**Endless/DB-driven list maximize (feeds):** named-slot + DOM-sourced-key compose for an infinite, server-paginated list (feeds carousel). Factory spreads `...maximizeMixin()`, declares `maximizedFeed: null`, overrides `toggleMaximize(name)`, adds `feed(el)` = `el?.closest('[data-feed]')?.dataset.feed`. Because the list is endless, the slot key is the feed **id** (`data-feed="{{ $feed->id }}"`), never a hardcoded name — and `data-feed` is kept **distinct** from other data attributes (`feeds` also has `data-feed-id` for the active-card tracker; `updateActiveItem()` reads `dataset.feedId`, so they never collide). Use the **partial-width** `.max-widget-column` on the per-item wrapper. `.max-widget-column` sets its own `transform: translate(-50%,-50%) !important`, which already overrides the carousel's resting `scale-105`/`scale-95` (non-important) — do **not** add `!scale-100` (two same-specificity `!important` transforms is fragile). The carousel wrapper's `grayscale`/`opacity` from its `:class` are not touched by `.max-widget-column`, so the maximize `:class` key cancels them: `'max-widget-column !grayscale-0 !opacity-100': maximizedFeed === feed($el)`. Rule: pick the maximize class whose own `!important` declarations cover as many resting visual effects as possible, then `!`-cancel only what it doesn't cover; never stack two `!important` transforms.

**The z-10 trap (no intermediate stacking-context ancestor):** `<x-ui.modals.max-backdrop>` (`position:fixed; z-999998`) and the maximized card (`z-999999`) must resolve at the **page-root** stacking context — like taskboard, whose root `<div x-data="taskboard()" class="... relative ...">` is `relative` with **no z-index** (not a stacking context). A `position:fixed` element's stacking-context parent is its nearest ancestor stacking context (fixed changes the containing block, *not* the stacking parent). Giving the feeds scroll container `x-ref="timeline"` a `z-10` makes it a stacking context that **traps** the fixed backdrop+card at page-root z-10 — under the prev/next buttons (z-40), sticky filters (z-20), etc. **Fix: `relative` (positioned, no z-index) instead of `z-10`** — `relative` is not a stacking context, so fixed backdrop/card escape to page-root (matching taskboard), while still painting the timeline above the decorative `z-0` absolute lines (DOM order). Dashboard chrome (`#navbar`/`#header`/`#footer`) is hidden by `maximizeMixin.applyMaximize` adding `.layout-hidden` (`visibility:hidden`). Rule: a maximize host must not put a z-index on the scroll container holding the maximized items.

**Hide sibling chrome ghosting through the semi-transparent backdrop:** once the trap is removed, prev/next scroll buttons (`absolute z-40`, siblings of the scroll container) resolve below the backdrop (`40 < 999998`) — but `.max-backdrop` is only 60% opaque (`color-mix(primary 60%, transparent)`), so anything at `z < 999998` shows through at 40% (faint ghost buttons). Fix: gate with `x-show="!maximizedFeed"` to remove them from layout on maximize. Same family as the sticky `z-20` filters (hidden via `:class`), but these are *siblings* of the scroll container (`x-show` is fine — no Livewire morph concerns).

**The `animate-fade` trap (tab modules only):** the working maximize modules (energy/taskboard/contact/dms) are standalone routes with **no `animate-fade`** on their root, so their fixed `.max-widget`/`.max-backdrop` escape to page-root and cover everything. A **tab** module (calendar, feeds) renders inside `livewire/dashboard/tabs.blade.php`, whose root `<div class="... relative isolate">` is a stacking context, with the left/right/bottom side-nav `<aside>`s (`z-50`/`z-[9998]`) as siblings of `<x-dashboard.tab>`. `animate-fade` = `animation: fadeIn 0.8s ease-out both` — the `forwards` fill keeps the root in a **persistent** stacking context (the animation stays in its fill phase after it ends), which traps the fixed `z-999999`/`z-999998` layers *below* those side-nav siblings (the root's stacking context resolves at `z-auto` in the `isolate` parent, under `z-9998`). Result: the side navs poke through the maximize overlay. **Fix: drop `animate-fade` from a tab module's root** (the per-view `slide-up` entrance still plays; the root fade is not load-bearing) so the fixed layers escape to the `isolate` context and outrank the side navs. Do **not** `x-teleport="body"` the Livewire content to escape it — teleporting `wire:`-bound content breaks Livewire morphing on every update (gallery/reports teleport only *static* image viewers with no `wire:` hooks), and teleporting just the backdrop layers it *above* the still-trapped content.

**Backdrop fade must match the card's entrance (`max-backdrop--sync`):** `.max-backdrop` fades in over `0.1s`, but `.max-widget-column` over `0.4s` — with a 0.1s backdrop and 0.4s card, the scene is fully dark at 0.1s while the card is 25% visible (reads as overlay, not backdrop). An opt-in `class` prop on `<x-ui.modals.max-backdrop>` (default `''`) lets a module pass `class="max-backdrop--sync"`; the scoped rule `.max-backdrop.max-backdrop--sync { animation-duration: 0.4s }` matches just that instance. `.max-widget-column`'s `transform: translate(-50%,-50%) !important` overrides `slideScaleIn`'s transform keyframes, so only the card's **opacity** animates — matching the backdrop's opacity-only `fadeIn` is the right coordination. Match the card duration (feeds/taskboard 0.4s; full-screen `.max-widget` 0.6s).

**Aggregate-emoji givers as a native tooltip:** hovering an aggregated emoji button (`@foreach($feed->reactions->groupBy('emoji') as $emoji => $reactions)`) reveals givers via `title="کسانی که واکنش دادند: {{ $reactions->pluck('user.name')->filter()->implode('، ') }}"`, **not** a positioned popover. The feed card root is `overflow-hidden` and body `overflow-y-auto`, so any `position: absolute` popover is clipped near edges; a native `title` floats free of every `overflow` ancestor. Givers are eager-loaded (`reactions.user` in the `Feeds` computed), so `pluck('user.name')` adds no queries. The button keeps `wire:click="toggleReaction(...)"` (different gestures, no collision). Rule: for a read-only hover reveal inside an `overflow`-clipped container, prefer a native `title` or the singleton tooltip (`viewPattern.md` §8.16 — text-only, `pointer-events:none`); reserve `ui.modals.popover` (click-toggle) for menus floating INTERACTIVE rich content (it is body-teleported since 2026-09-15, so clipping is no longer a reason to avoid it — see `viewPattern.md` §8.17).

**Hide the tab's own chrome on maximize:** feeds top chrome (page title + focus-chip + filters) is hidden by wrapping those includes in `<div :class="{ 'hidden': maximizedFeed }" class="flex flex-col gap-6">`. This is a feeds-local Alpine toggle (not the shared dashboard-shell hide), needed because the filters are `sticky top-0 z-20` — a stacking context above the timeline that would paint *over* the card. Use `:class` with Tailwind `hidden` (`display: none`), **not** `x-show`/`x-transition` (transition can leave the element visible if `transitionend` doesn't fire) and **not** `x-if` (fights Livewire morph, re-initializes filters' `x-data` on restore). `display: none` removes the chrome's space so the timeline expands into the focus view (the dashboard shell's `visibility: hidden` would leave a gap).

**Hero deck (`data/heroDeck.js`) — the home hero as a 3-slide module deck:** slide 0 is the live welcome content; slides 1/2 (`p2`/`p3`) are chrome-stripped module iframes the user pins from a picker (catalog single-sourced from `config/modules.php` — only entries carrying a `nav` mapping — via `TabPresenter::shortcuts()` minus `home`; every src suffixed `embed=1`, which gates away layout header/footer and the tabs-view navbars/background so the module renders chromeless in-frame). Reuses the aiAssistant iframe discipline exactly: `<template x-if="loaded.pN">` lazy-mounts the iframe so the module route is only HIT when the pane first opens, `src` is a plain data property set before `loaded` flips (never a method call in the binding), skeleton pulses until `@load` sets `frameReady`. Persistence is localStorage (`fateh_hero_gadgets`), not a store — the deck is home-local, nothing else consumes it (stores-first scan done: no existing store covers it). Maximize follows the named-slot override shape: `...maximizeMixin()`, `maximizedPane: null`, `toggleMaximize(pane)` calling `applyMaximize(!!this.maximizedPane)`; the picker modal is body-teleported at the shared dialog band `z-[100]` with a static `wire:key` (pure-Alpine content, no `wire:` hooks, so teleport is morph-safe — viewPattern §8.7/8.17) because the tabs root `isolate` trapped its former in-place `z-[9999]` under the sticky header (`z-50`)/navbar (`z-[51]`); its card carries a stable height (`h-[85dvh] sm:h-[680px]`, scroll body `flex-1 overflow-y-auto`) so live-searching the catalog never shrinks the modal, and `gadgetSearch` resets on every close path like the menu modal precedent. The maximized pane stays un-teleported (`z-999999` page-root escape via the `animate-fade` trap fix — the home root lost its fade).

**Height-keeping slide swap — never `x-show` the slide that carries the box's height:** the deck's slides 1/2 are `absolute inset-0` overlays of the hero box, whose ONLY height driver is slide 0's welcome content. `x-show` hides via `display:none`, which collapses that content — the hero box shrinks to the absolute layers' zero height and the panes' `inset:0` becomes an empty sliver. Fix: slide 0 stays in layout forever and swaps via `:class="slide === 0 ? 'opacity-100' : 'opacity-0 invisible'"` (+ `transition-opacity duration-300` in the static class) — `invisible` (`visibility:hidden`) keeps the box at full welcome height while fully non-interactive, so the embedded module always inherits the full-size hero. Rule: when a container's height is content-driven and sibling slides are absolute overlays, hide the height-carrying slide with `invisible`, never `x-show`; `x-show` stays correct for the overlay slides themselves (display:none does not reload an already-mounted iframe, so pane state survives slide switches). Known v1 limitation: a `wire:navigate` link inside an embedded page navigates without the `embed=1` param, so the in-frame page re-renders with full chrome — the Tabs gate itself is snapshot-stable (`#[Url] bool $embed` on `Tabs`, hydrated on mount and carried across `/livewire/update` re-renders — never gate tabs-view chrome on `request()`, which is absent on update POSTs), but a full in-frame navigation loses it.

**Input maximize — prop vs. direct trigger/overlay (the `$refs` rule):** `<x-ui.forms.textarea>` exposes a `maximizable` prop bundling the whole feature (`wire:ignore.self` root, `x-data="{ value: @entangle(...).live, fullscreen: false }"`, `pl-10` padding, `<x-ui.forms.maximize-trigger>` + `<x-ui.forms.maximize-overlay>`). For a **plain** input (comment *edit* box — no bespoke `x-data`, no `$refs`): `<x-ui.forms.textarea wire:model="commentForm.content" label="ویرایش نظر" :maximizable="true"/>`. For a **bespoke** input whose `<textarea>` is referenced by `$refs` (feeds main comment box: emoji picker calls `this.$refs.commentInput` for `insertEmoji`), **do not** swap it onto the component — the component's own `x-data` would sit between picker and `<textarea>`, and Alpine registers `x-ref="commentInput"` on the component's scope, so `$refs.commentInput` resolves `undefined`. Keep the bespoke `<textarea>` untouched and reuse only `<x-ui.forms.maximize-trigger>` + `<x-ui.forms.maximize-overlay>`, adding `value: @entangle(...).live, fullscreen: false` to the bespoke `x-data`. Rule: the `maximizable` prop is for plain inputs; a `$refs`-driven bespoke input reuses the trigger/overlay components directly — never nest a second `x-data` between a `$refs` consumer and its target.

**Feed blades stay clean — logic in dedicated factories, entangle spread inline:** the comment-input (`comments.blade.php`) and reaction strip (`actions.blade.php`) inline `x-data` moved to two `data/` factories registered in `main.js`: `feedComposer` (`showEmoji`, `fullscreen`, `panelStyle`, `emojis`, `toggleEmoji`/`insertEmoji`/`onEnter`/`autoGrow`) and `feedReactions` (`page`, `per`, `emojis`, `selected`, `next()`). Blades keep only markup + directive refs. The Livewire entangle stays **inline in the blade** and the factory is **spread** alongside it: `x-data="{ value: @entangle('newComments.<id>').live, ...feedComposer(<id>) }"`. Why spread, not `x-data="feedComposer(<id>, @entangle(...).live)"`: `@entangle` compiles to `Livewire.find(...).entangle(...)`, and Livewire's Alpine plugin recognizes an entangled property by scanning the `x-data` *expression string* for that call — entangle must appear directly in the object literal, not buried in a function argument. The factory deliberately omits `value`; it owns `fullscreen` and all methods. The reaction strip has no entangle: `x-data="feedReactions(<feedId>, '<selectedEmoji>')"`. The `$refs` rule still holds: `feedComposer`'s `insertEmoji`/`onEnter` use `this.$refs.commentInput`, so `<textarea x-ref="commentInput">` stays a direct child of the same `x-data` scope — no nested `x-data` between them.

**Emoji dictionary centralized in `stores/emoji.js`:** no blade re-declares emoji arrays. Alongside the categorized `emojis` export (used by `contact.js`), two hand-picked `const` exports serve feeds: `feedEmojis` (composer picker grid) and `feedReactions` (21 quick-reaction set). `feedComposer`/`feedReactions` import them directly. The old PHP `$emojis` reorder (float the user's current reaction to page 0) moved into `feedReactions`' object initializer, keyed by `selectedEmoji` passed from the blade (`$userReaction?->emoji`, PHP-sourced). Rule: emoji data has exactly one source (`stores/emoji.js`); feed blades/factories import it, never re-declare inline — neither as an Alpine array (`emojis: [...]`) nor as a PHP array (`$emojis = [...]`) through `json_encode`.

**Stores-first rule — analyze before introducing any new item.** Before introducing ANY new data item (emoji set, constant list, option array, helper collection, localStorage key/scope), first scan `stores/*` and `mixins/*` and reuse what already exists; never inline a hardcoded set a store or mixin already provides, and never spin up a parallel store for a scope an existing store already covers. This generalizes the emoji single-source rule to every store (`emoji`, `pinned`, `tagged`, `sound`, `push`, `density`, `colVisibility`, …) and every mixin (`clipboard`, `fancybox`, `maximize`, `persistentState`, `monthFilter`). Concretely: a new reaction picker does not re-declare five emoji inline — it imports `feedReactions` from `stores/emoji.js` into the module's `data/` factory and exposes it to the blade; a new per-row pin/tag/mute does not add a fourth store — it adds a scope to `pinned`/`tagged`/`sound`; a new copy action does not call `navigator.clipboard` directly — it spreads `...clipboardMixin()`. The check is mandatory and happens BEFORE the new item is written, not after review catches the duplication. The Project activity tab's store-backed reaction picker (replacing its earlier hardcoded five-emoji inline set) is the canonical recent application.

## 4. PWA & Service Worker
Workbox via the Vite PWA Plugin (`injectManifest` strategy).

### 4.1 The Service Worker (`sw.js`)
`injectManifest` (not `generateSW`) for manual control over the lifecycle. Vite's hashed assets are injected into Workbox's precache.

```javascript
import { precacheAndRoute, cleanupOutdatedCaches } from 'workbox-precaching'
import { clientsClaim } from 'workbox-core'

self.skipWaiting()
clientsClaim()
cleanupOutdatedCaches()
precacheAndRoute(self.__WB_MANIFEST)
```

### 4.2 Vite Configuration Rules
* **Precache static build assets:** `workbox.globPatterns: ['**/*.{js,css,html,ico,png,svg,woff,woff2}']` — Workbox precaches everything Vite emits into `public/build` matching that set. Vite emits no HTML into `public/build` here, so in practice only hashed JS/CSS/fonts/icons are precached.
* **No SPA fallback (`injectManifest`):** with `injectManifest` the SW is hand-written (`sw.js` calls only `precacheAndRoute(self.__WB_MANIFEST)`) — Workbox never injects a `navigateFallback`, so navigation/HTML requests always hit the server. Serving cached HTML for navigation would cause Livewire to fail (stale CSRF tokens, mismatched DOM diffing keys); the server must always handle HTML.

## 6. Absolute Anti-Patterns

❌ **Do not write `<script>` tags in Blade for Alpine logic.** Breaks CSP, can't be minified by Vite, litters the DOM. Extract to `js/components/alpine/data/`.

❌ **Do not cache HTML responses or `/api` routes in the Service Worker.** Causes 419 Page Expired errors and broken form submissions.

❌ **Do not use `window.Theme = 'dark'` for global state.** Alpine cannot react to plain Window mutations. Use `Alpine.store('appTheme').set('dark')`.

## 7. Modal Open Animation & Heavy Slot Content
The shared modal shell (`.custom-modal`) opens by animating **`width`/`height`** (geometry), not `transform` (see `resources/css/core/dashboard.css`). Geometry animation can't run on the compositor, so the browser re-runs layout on the modal subtree every frame for ~1s.

⚠️ **The slot stays laid-out while invisible.** `.custom-modal-content` is `visibility: hidden` + `opacity: 0` until geometry finishes, but `visibility: hidden` still performs layout (unlike `display: none`). A heavy form is reflowed ~60× during the open animation even though it isn't painted. Dominant cost: text re-wrapping at each intermediate width. A wider final layout (`!w-full` on `modal-inner-card` vs. default 66.666%) raises per-frame reflow cost.

✅ **Defer the slot's layout until geometry completes** — scope to the one form, leave the shared modal untouched:

```blade
<div class="modal-inner-card !w-full !max-w-none !p-5 md:!p-6" dir="rtl"
     x-data="{ tab: '{{ $defaultTab }}', ready: false }"
     x-effect="if (show && !ready) { setTimeout(() => { if (show) ready = true }, 1000) } else if (!show) { ready = false }"
     x-show="ready">
```

* `x-effect` reads the parent modal's entangled `show` (scope chain preserved through `x-teleport="body"`). 1000ms timer matches `.custom-modal-content`'s opacity delay (`ease 1s`); on close it resets `ready`.
* `x-show="ready"` keeps the form `display: none` during geometry → zero per-frame reflow. At 1s the form lays out **once**, exactly when scheduled to fade in. `wire:model` bindings stay intact.
* The timer re-checks `if (show)` so a close-during-pending or quick reopen can't leak a stale `ready = true`.
* **Adopters:** `livewire/dashboard/taskboard/form.blade.php`, `livewire/dashboard/tab/calendar/create.blade.php` (form modals — expanded sizing + defer on `modal-inner-card`); `livewire/dashboard/tab/status/about-me.blade.php` (defer on main content container only — its `max-w-2xl` profile frame and decorative absolute layers stay untouched); `livewire/dashboard/suggestion/create.blade.php` (defer on the flowchart modal's `w-full` image wrapper).
* **Do not** reach for `max-widget` (page-level fullscreen overlay) inside this modal — `.custom-modal` has `transform` + `contain: strict` + `overflow: hidden`, which re-contains a `fixed` descendant unpredictably. Expanding the card *within* the modal is the correct adaptation.

## 8. UI Sound Store (`stores/sound.js`) — outgoing send sound + per-chat mute
A single global Alpine store backs the outgoing (send) chat sound and per-chat mute for the contact, channel, and project modules. Registered like other stores (`import registerSoundStore from './stores/sound.js'` + `registerSoundStore(Alpine)` in `main.js`); auto-inits via `init()`.

**Three scopes, NOT assumed disjoint — one array + storage key per scope:** `mutedChannels: []` + `mutedContacts: []` + `mutedProjects: []` (array-backed, NOT `Set` — Alpine reacts to `Array` `splice`/`push` but not `Set.has`), each persisted to its own key (`KEYS = {channel: 'chat-muted-channels', contact: 'chat-muted-contacts', project: 'chat-muted-projects'}`). Every method takes `scope = 'channel'` (`_set`/`_key` pick list/storage-key via `KEYS[scope]`); contact/project callers pass `'contact'`/`'project'`. Channel and contact ids happen to be disjoint (channels vs. user ids), but project ids are a third, independent auto-increment sequence that CAN collide numerically with channel ids — a per-scope key is mandatory, not an optimization; collapsing project into the channel bucket (e.g. a stray ternary defaulting anything non-`'contact'` to `mutedChannels`) would silently cross-mute a channel and a project that happen to share an id. `pinned.js`/`tagged.js` mirror this with their own `KEYS`/`maps` objects (`contact`/`channel`/`project`/`task`, `tagged.js` also carries a `ths` scope, `pinned.js` also carries a `message` scope) — same rule: every new scope needs its own registered key, the shared `<x-ui.row-actions>` component silently no-ops (pin/tag) or cross-contaminates (mute, before this fix) for any scope missing from a store's registry.

**One sound, one cached `Audio`:** `_audio: null` lazily built on first play from `document.querySelector('[data-outgoing-sound]')?.dataset.outgoingSound` and cached (NOT a fresh `new Audio` per play — `currentTime = 0` restarts it, no per-send allocation/GC). `volume = 0.35`; `play().catch(() => {})` (send is a user gesture → autoplay unlocked). One `data-outgoing-sound` attr on each module root (`channel.blade.php`, `contact.blade.php`): `{{ asset('build/assets/audio/outgoing.mp3') }}` — URL-in-view precedent (same as `stopwatch.blade.php`'s `alarm.mp3`), no inline `<script>`. Asset copied by `vite-plugin-static-copy` (whole `resources/assets/audio` dir → `public/build/assets/audio`); standard name `outgoing.mp3`.

**Methods:** `isMuted(id, scope)` / `toggleMute(id, scope)` (push/splice + persist, `try/catch`-wrapped); `playOutgoing(id, scope)`.

**`playOutgoing` contract:** `id !== null && isMuted(id, scope)` → early return (per-chat mute; the active chat's id is passed so a muted chat is silent). `document.hidden` → early return. URL + `Audio` resolved lazily on first play (module root isn't in the DOM at `alpine:init`). Only one chat module is mounted at a time; both set the same URL, so the cache is valid across module switches.

**Caller-side fault isolation (mandatory):** `message-sent` handlers call `this.$store.sound?.playOutgoing(...)` with optional chaining, ordered **after** the critical UI state (a single `scrollToBottom`, no retry, + `sending = false`) — the sound is non-essential and must never strand the composer in `sending = true`. `$store.*` resolves inside `@island` (channel header/sidebar mute live in islands) because stores are global, not scope-bound.

**Incoming (receive) sound — built 2026-10-05, reverses the prior "evaluated and dropped" call below.** The original rejection (kept verbatim in the next paragraph for the historical reasoning) was specifically about `$watch('$wire.lastMessageId')` never firing, because Livewire's snapshot never serializes `#[Computed]` properties to the client. The shipped design never watches a Livewire property at all — it reads the already-rendered DOM, the exact same way `_pollTick`'s own `changed` flag already does for poll-interval adjustment, so the blocker below doesn't apply. Two trigger sites, covering both "viewing the thread" and "not viewing it," symmetric across `contact.js`/`channel.js`:
- **Open-thread case:** inside `_pollTick`, after `_isl().refreshActive()` resolves, compare `_readLastMessageMarker()` before/after (same comparison already feeding `changed`). If it moved AND a new helper `_lastMessageIsMine()` (reads the last row's `justify-start`/`justify-end` class — the existing `$msg['is_mine']` convention, zero new markup) says the new last message is NOT mine, call `this.$store.sound?.playIncoming(activeUserId|activeChannelId, SCOPE)`. The is_mine check is mandatory: without it, the poll tick would ALSO fire the sound for your own just-sent message (already covered separately by the `message-sent` → `playOutgoing` path), doubling the cue. `lastBefore !== null` additionally guards the very first tick after opening a thread, where "no marker yet → first marker" is ambiguous ("just loaded" vs "new message") rather than a genuine new arrival.
- **Unread-rise case (updated 2026-10-09):** `syncPushNotify()` — already firing `$store.push.notify(...)` on a `[data-total-unread]` increase via the existing `MutationObserver` — now also rings on EVERY increase, whether or not a thread is open (so a message from another conversation while one is open is audible). It passes the open id (or `null` when none is open: `null` skips the per-conversation mute check, so only `globalHush` gates it). Both trigger sites go through `chatBase`'s `_ringIncoming(id)`, which drops any ring within 1500 ms of the previous one (`_lastIncomingAt`).

**Real bug caught by independent review before shipping, fixed same day: the two cases above are NOT mutually exclusive, so a message arriving in the currently-open thread could ring twice.** `data-total-unread` counts messages whose read-state hasn't advanced, and `markRead`/`refreshUnread` only runs once on `selectContact`/`selectChannel` — it does not keep re-marking the open thread as read on every later poll tick. So a message landing in the thread you're actively viewing ALSO bumps the sitewide unread count that same tick, meaning `syncPushNotify()`'s unread-rose check and `_pollTick`'s own scoped last-message check could both fire for the identical message. Originally fixed by gating `syncPushNotify()` on nothing being open; superseded 2026-10-09 by the shared 1500 ms `_ringIncoming` dedupe (the gate also silenced messages from other conversations). The push browser-notification call is untouched (still fires either way; that one isn't scoped to a specific conversation's mute state the way the sound is).

**Second bug caught by the same review, also fixed: deleting the open thread's last remaining message could ring a false "incoming" chime.** The last-message-marker diff only checked `lastAfter !== lastBefore` — a deletion transitions `lastAfter` to `null` (no rows left) exactly like a genuinely new message transitions it to a new id, and `_lastMessageIsMine()` on an empty viewport returns `false` ("not mine"), so a pure removal read as "someone else sent something." Fixed with one added clause: the play only fires when `lastAfter !== null` too — a transition TO empty is a removal, never an arrival.

Both call sites reuse the EXISTING poll/DOM-mutation machinery — zero new Livewire methods, zero new `wire:poll`, zero new DB query of any kind. Mute/unmute already applies to both directions for free: `playIncoming`/`playOutgoing` share the same `isMuted(id, scope)` check and the same per-scope muted-id arrays, so toggling a chat's mute silences its incoming AND outgoing cue together — no separate incoming-mute UI needed. `playIncoming` deliberately has NO `document.hidden` guard (unlike `playOutgoing`) — a backgrounded tab is exactly when an incoming cue matters most; outgoing's hidden-tab skip exists because you're visibly present the moment you click send, a condition that doesn't apply to receiving. Uses its own cached `_incomingAudio` (separate from `_audio`) so an incoming and outgoing cue firing close together never cut each other off, resolved lazily from a new `data-incoming-sound` attr on each module root (`{{ asset('build/assets/audio/incoming.mp3') }}`) — the asset already existed in `resources/assets/audio/`, unused, before this.

**Original 2026 rejection (superseded above, kept for the historical reasoning):** incoming detection was evaluated and dropped. Contact side is blocked by Livewire's snapshot model — `#[Computed]` values (`lastMessageId`/`lastMessageIsMine`) are NOT serialized into the snapshot (only public properties, via `getPublicPropertiesDefinedOnSubclass`), so `$watch('$wire.lastMessageId')` never fires on the client; a correct fix needs `Livewire.hook('morph')` + per-row `data-mine` + switch/seed guards. Channel side is feasible (sidebar-poll piggyback reading `data-last-at`/`data-last-mine`) but would give inconsistent UX against a silent contact module. Outgoing-only is the deliberate minimal choice.

**Mute UI (both modules):**
- **Header toggle** (`channel/header.blade.php`, `contact/header.blade.php`): first control in the actions cluster, `:class="… ? '!bg-primary !text-on-primary' : 'hover:brightness-95'"` (muted = primary fill). Glyph swaps via `x-text` (`volume_off`/`volume_up`) — NOT Blade `{{ }}`. `aria-pressed` carries state; `aria-label`/`title` carry the **next action**. Channel uses `$header['id']`; contact uses `$activeContact->id` + `'contact'` scope. Client-only — no server round-trip, no IDOR.
- **Channel sidebar hover shortcut** (`channel/sidebar.blade.php`): the channel row is a `<div role="option" tabindex="0">` (NOT `<button>`) with `x-on:keydown.enter/space.prevent` → `selectChannel`, because a real mute `<button>` nests inside it (`<button>` content model forbids a `tabindex`/interactive descendant). The nested mute `<button>` (hover/focus-revealed via `opacity`/`scale` + `pointer-events-none` idle / `pointer-events-auto` on `group-hover`/`focus`/muted) carries `x-on:click.stop` + `x-on:keydown.enter.stop`/`x-on:keydown.space.stop` — `.stop` (no `.prevent`) stops keydown bubbling to the row's `selectChannel` WITHOUT suppressing the button's native synthesized click, so keyboard Enter/Space mutes (not selects). `pointer-events-none` on idle is mandatory: without it the invisible 24px target intercepts taps on touch devices (no `group-hover`), toggling mute instead of opening the channel. The icon `<span>` is `aria-hidden="true"`. The contact sidebar (`contact/sidebar.blade.php`) mirrors this identically: both sidebars are `@island(name: 'sidebar')`-wrapped inside the same `x-data="contact()"`/`x-data="channel()"` root, so the row calls the factory's `selectContact(id)` method (contact.js — which does `this.$wire.$island('messages').selectContact(id)` + `refreshUnread` + instant `scrollToBottom(false)`), the exact counterpart of channel's `selectChannel`. The row was converted from `<button wire:click="selectContact(...)">` to `<div role="option" tabindex="0" x-on:click="selectContact(...)" x-on:keydown.enter.prevent="selectContact(...)" x-on:keydown.space.prevent="selectContact(...)">` so the same per-row hover mute `<button>` (scope `'contact'`, labels 'بی‌صدا کردن مخاطب'/'باصدا کردن مخاطب') can nest inside — `<button>` cannot nest a `<button>`. ## 9. Browser push-notification opt-in store (`stores/push.js`) — foreground-only, zero backend
A minimal Alpine store gating the native `Notification` API behind a per-module toggle, scoped to **foreground/backgrounded-tab notifications only** — no Web Push subscription, no VAPID keys, no `push_subscriptions` table, no server-triggered send. Registered like `sound`/`theme` (`import registerPushStore from './stores/push.js'` + `registerPushStore(Alpine)` in `main.js`).

**Shape mirrors `sound.js`** — a single-flag-per-scope variant instead of an id-array variant, since `Notification` permission is browser-wide, not per-conversation: `supported` (feature-detected once, `typeof Notification !== 'undefined'`), `isEnabled(scope)` (true only when BOTH `Notification.permission === 'granted'` AND the per-scope flag in the reactive `enabled` object is true — the local flag lets a user opt back OUT without revoking the OS-level permission), `toggle(scope)` (requests `Notification.requestPermission()` only on enable; denied/dismissed leaves the flag unset), `notify(title, body, scope)` (fires `new Notification(...)` only when `document.hidden` is true AND `isEnabled(scope)` — the inverse of `sound.playOutgoing`'s hidden-tab guard; a foreground tab already has the in-app UI + outgoing sound, so it stays silent).

**Real bug fixed (2026-10-05): the toggle button never visibly updated after a click.** `isEnabled`/`toggle` originally read/wrote `localStorage` directly on every call, with no Alpine-tracked property behind them at all — every `:class`/`x-text`/`aria-pressed` binding in both sidebars calls `$store.push.isEnabled(scope)`, but Alpine only re-evaluates a binding when it reads a property its reactive proxy is tracking; a plain `localStorage.getItem()` inside a method call is invisible to that system. Clicking the toggle silently changed `localStorage` while the icon/pressed-state kept showing the old value until some UNRELATED state change elsewhere happened to force a re-render. `sound.js`'s `mutedChannels`/`mutedContacts` arrays never had this problem because they're genuine Alpine-reactive store properties (`isMuted()` reads them, `toggleMute()` reassigns them) — `push.js` just never got the same treatment. Fixed to match: an `enabled: {channel,contact,project}` reactive object, loaded from `localStorage` in `init()` (and now also the SAME cross-tab `storage`-event resync `sound.js`'s `mutedChannels` already had, previously missing here too) via a shared `_load(scope)` helper; `isEnabled()` now only ever reads `this.enabled[scope]` (never touches `localStorage`), and `toggle()` writes BOTH `localStorage` (for persistence across reloads) and `this.enabled[scope]` (so every dependent binding re-renders immediately). **Rule: any Alpine store value a Blade template reads through a method call (not a bare property) must be backed by a store-owned reactive property if a UI binding needs to react to it changing — a method that only reads an external source (`localStorage`, `Notification.permission`, etc.) on each call is invisible to Alpine's dependency tracker no matter how many times the UI calls it.**

**UI (both sidebars):** a `w-6 h-6` icon toggle placed immediately after the existing mute-all button in the title-row right cell (same 24px/14px-glyph sizing, same `bg-[var(--md-sys-color-surface-variant)]` idle / `!bg-primary !text-on-primary` active vocabulary). Guarded by `x-show="$store.push.supported"` (Notification API absent on some browsers/contexts) rather than `@if` — support is a client-only fact Blade can't know at render time. Glyph swaps `notifications_off`/`notifications_active` via `x-text`, `aria-pressed`/`aria-label`/`title` follow the same "next action" convention. Channel scope `'channel'`, contact scope `'contact'` — same disjoint-scope rationale as the sound store.

**Trigger wiring — two mechanisms, since Channel and Contact wire the push check differently even though both now share one JS poll loop:**
- **Channel** rides the poll's own `.then()`/`await` chain directly: `syncPushNotify()` reads the `data-total-unread="{{ $totalUnread }}"` attribute off the sidebar `<aside>` (same `querySelector('[data-*]')` idiom `syncChannelCount()` uses for `data-channel-count`), diffs against `this._lastUnread`, calls `$store.push.notify(...)` only on an increase. Also called once in `init()` to seed the baseline (guarded by `this._lastUnread !== undefined`, so page load never fires a spurious notification).
- **Contact** instead observes the same `data-total-unread` attribute (on `contact/sidebar.blade.php`'s `<aside>`) with a `MutationObserver({subtree: true, attributes: true, attributeFilter: ['data-total-unread']})` rooted at `document.body` — fires `syncPushNotify()` whenever a poll tick's morph patches that attribute. Rooted at `document.body` (not the specific `<aside>`) deliberately, so it survives Livewire ever fully replacing that element rather than patching it in place. Disconnected in `destroy()` alongside the module's other listener cleanup. (Historical note: Contact previously polled via a bare `wire:poll.10s` with no JS loop at all — superseded 2026-09-12 when it moved onto the same adaptive scheduler Channel uses, see `mixins/chatBase.js` below; the MutationObserver wiring here was kept as-is since it works unchanged regardless of what drives the underlying poll.)

**Adaptive poll scheduler (`mixins/chatBase.js`, 2026-09-12) — shared by `channel.js` and `contact.js`.** Both modules previously ran an independent flat `setInterval` (10s, forever, while the tab was visible). Replaced with one shared scheduler in the mixin: `startPolling()`/`stopPolling()` (now a self-rescheduling `setTimeout` chain, not `setInterval` — `stopPolling()` uses `clearTimeout`), `resetPollInterval()` (snap back to the `POLL_BASE_MS` floor, 10s), and `_applyPollResult(changed, ceilingMs)` (doubles `_pollIntervalMs` on no change, capped at the caller's ceiling; resets to base the instant something changed). `_schedulePollTick()` applies ±10% jitter per tick (mirrors `project.js`'s `_scheduleTick()` — kept for shape-parity even though the per-user synchronization risk it defends against is smaller here than in Project's shared-per-project-resource case) and, since a same-day fix (below), `clearTimeout(this._timer)` before assigning a fresh id — spec-safe no-op on a stale/null id, but the one thing that guarantees `_timer` can only ever track a single pending timeout regardless of which code path called this method. Each module supplies its own `_pollTick()` (does the actual `$wire.$island(...)` calls, diffs `data-total-unread` and the open conversation's last-message `data-rf` marker to decide "changed", then calls `_applyPollResult` with its own ceiling — `OPEN_POLL_CEILING_MS = 20000` when a conversation is open, `IDLE_POLL_CEILING_MS = 30000` for sidebar-only). Activity handling split in two, correction 2026-09-30 (see `contactPattern.md` §3.2 for the full writeup): composer `input` (typing) still just calls `resetPollInterval()` directly — cheap, no forced request, since a keystroke-cadence forced repoll would mean 2-3 serialized Livewire round-trips per character below the 200-message threshold. And `selectChannel`/`selectContact` call the single-flight-guarded `_repollNow(false)` — bare `resetPollInterval()` alone only affected the delay used to schedule the NEXT tick, it never canceled/hurried the ALREADY-pending `setTimeout`, so activity used to give close to zero real latency improvement despite calling it. `_repollNow(tick = true)` resets the interval, restarts the timer chain, and (when `tick`) forces an immediate tick via `_runPollTick(true)`; the select variant passes `false` since select already triggers its own island call + `markRead`. The `_pollInFlight`/`_repollQueued` guard exists specifically because a naive `stopPolling()`+`startPolling()` fired while a timer-driven tick is mid-`await` would leave two parallel polling chains running forever (a real bug caught before shipping, not a hypothetical). Visibility resume also now goes through `_repollNow(true)` instead of its own inline reset+restart+forced-tick three-liner — freshness the moment you look back, not a wait for the next tick (an enrichment Project's own scheduler lacked until the same date, see `data/project.js` below), same behavior as before, just centralized.

**Third same-day bug, distinct from the `_pollInFlight` guard above: a hide/show bounce landing mid-flight could leave TWO live timer chains instead of zero.** The `_repollNow()`-in-finally fix for the earlier "polling dies after hide/show" bug (full trace: `contactPattern.md` §3.2) introduced a new problem — its `startPolling()` call sets a fresh `_timer` id INSIDE `_runPollTick`'s finally block, but `_schedulePollTick()`'s own pending self-reschedule (a `.finally` microtask that runs immediately after) then ALSO saw a non-null `_timer` and scheduled its own second id, without clearing the first. Two interleaved chains, up to 2x poll requests, only occasionally deduped by luck when their timing collided. The `clearTimeout(this._timer)` guard above is the actual fix for this — not a defensive add, the load-bearing line that makes the hide/show recovery path safe.

**`sendMessage`/`saveEdit`/`deleteMessage` do NOT use `_repollNow(true)` — same-day correction after a real regression shipped.** They were wired that way first. Bug: all three are themselves `$wire.$island('messages').<method>()` calls, so their own request already re-renders the messages island correctly, in order; `_repollNow(true)`'s forced `_pollTick` then fired a SECOND, independent request to that same island right after, and — Livewire Islands being new/fragile enough that this codebase's `livewirePattern.md` `@island` section documents a long list of exactly this class of concurrent/out-of-order-response gotcha — the second response (built from a pre-edit snapshot) could land after the first and morph the DOM back to the pre-action content. Observed as: edit or delete a message, then immediately do it again, and the *first* change sometimes reappears. Fix: `_syncSidebarAfterOwnAction()` (`chatBase.js`) replaces `_repollNow()` at these three call sites — `_repollNow(false)` (timer reset/restart only) plus a direct, standalone `$wire.$island('sidebar').refreshUnread()` (the original pre-`_repollNow` line these three sites already had, reused as-is) — never a second forced fetch of the messages island, which doesn't need it since its own response already has the current content. Closing a real gap: Channel previously had no "refresh the open conversation" poll leg at all (only Contact did) — `refreshActive()` was added to `Channel\Main.php` (mirrors the `unset($this->messages, $this->groupedMessages)` invalidation already used by `send`/`saveEdit`/`deleteMessage`/`undoDelete` in that file) so both modules now behave identically here.

**Typing indicator (Channel + Contact, 2026-09-12) — leading-edge throttle + poll-tick piggyback, no WebSocket.** Client trigger: `chatBase.js`'s `pingTyping()` is a leading-edge throttle (first keystroke pings immediately, then suppressed for 3s even under continuous typing — NOT a trailing debounce, which would delay the signal instead of speeding it up), invoked from both composers' existing `x-on:input` (channel rides its already-named `detectMention()` method; contact's inline expression gets `pingTyping()` appended alongside `resetPollInterval()`). Server write: `#[Renderless] pingTyping()` on both `Main` components sets a short-TTL cache entry (Contact: scalar key `typing:dm:{sender}:{recipient}`, 8s TTL; Channel: a per-channel map `{userId: [name, expiresAt]}` under one key, so "who — plural — is typing" is one cache read, not a scan) — deliberately plain `Cache::` facade, no Redis-specific SET/ZSET, so it behaves identically on the dev `database` cache store and a prod `redis` one. Server read: a `#[Computed]` (`peerTyping()`/`typingMembers()`) rendered inside the existing header partial, replacing "last seen"/"owner name" with "در حال نوشتن..." while active; a `data-typing` DOM attribute carries the state. Clear: TTL alone handles "stopped typing" (no explicit signal — not worth the extra request); `send()` additionally clears the sender's own entry inline (an already-happening request) so the indicator can't linger after the message itself already rendered. **The one-line enrichment that makes idle-tab staleness a non-issue:** `_pollTick()` reads `data-typing` before/after each tick exactly like it reads the unread count and last-message marker — a peer starting to type counts as "something changed," which snaps the receiver's own backed-off interval back to the 10s floor immediately. Net effect: worst case is one slightly-delayed first notice while idle, not a persistently laggy indicator. Considered and rejected: inferring typing purely from Livewire's own deferred-model diffing with zero client ping (the composer's `wire:model.defer` body genuinely does ride along on the next poll tick for free, but only every ~10s+ — too slow and too lingering to be the primary signal on its own; kept only as a theoretical free reinforcement, not implemented, since the throttled ping alone already satisfies the timing budget) and per-row sidebar typing indicators (would need a read per row per tick — not worth it; only the open conversation shows it). **Animated dots (2026-09-12) — reused pre-existing dead CSS, wrote zero new styles:** `.animate-typing-dot-1/2/3` + the `typingBounce` keyframe already existed in `resources/css/core/animation.css` (three staggered 1.4s bounces, 0.2s apart) but were never referenced by any Blade file until this feature — the "در حال نوشتن" text in both headers is followed by three `h-1 w-1 rounded-full bg-current` dots carrying these three classes. **Contact's presence dot/last-seen text also now refreshes live** — `refreshActive()` additionally does `unset($this->activeContact)` (scoped to only this poll-triggered method, not `invalidateMessageCache()`'s other 8 call sites, to avoid forcing an extra query on unrelated actions like delete/edit) — the peer's online status updates on the same already-running poll tick with zero new requests. **Composer manual resize + always-visible remaining-count (2026-09-12), both Channel and Contact.** The `msg-ta` textarea was `resize-none` (auto-grow-only, JS-driven, capped 160px) — changed to `resize-y` (native browser drag-handle) with the cap raised to `max-h-[280px]` so the handle has real room. Zero server/DB cost — pure client-side, same as the rest of this file's mixins. ## 9.1 Sidebar pin store (`stores/pinned.js`) — client-only pin-to-top reorder

A minimal Alpine store backing per-row "pin" toggles in both the channel and contact sidebars, registered like `sound`/`push` (`import registerPinStore from './stores/pinned.js'` + `registerPinStore(Alpine)` in `main.js`). **Client-only — no server state, no round-trip, no IDOR** (the pin set never leaves `localStorage`).

**Shape — Set-per-scope (NOT array; diverges from `sound.js`):** `sets: {contact: new Set(), channel: new Set()}` (a third `message` Set is added by §9.3, plus `project`/`activity`; a sixth `menu` scope follows below), `Number`-cast on load/save, persisted to `localStorage['pinned-channels']` / `localStorage['pinned-contacts']` as JSON arrays (`JSON.stringify([...set])` on save, `new Set(arr.map(Number).filter(Number.isFinite))` on load). `_load`/`_persist` pick the Set + key by `scope = 'channel'` (contact callers pass `'contact'`); `isPinned(id, scope)` → `sets[scope]?.has(Number(id))`; `togglePin(id, scope)` → `.add()`/`.delete()` + persist (`try/catch`-wrapped); `getPinned(scope)` → `[...sets[scope]]`. Channel ids and contact user ids are disjoint, so two Sets. **Alpine 3 (`@vue/reactivity`) tracks `Set.has`/`add`/`delete`** — so the Set is fully reactive; this supersedes §8's "not `Set.has`" caveat (that note is the rationale `sound.js` chose arrays, NOT a real Alpine limitation — both `Array` and `Set` mutations are reactive in Alpine 3).

**Sixth scope `menu` — string ids, the one coercion exception (hamburger-menu module pins, 2026-09-10):** the menu modal pins its launcher tiles to page 1 through `KEYS.menu = 'pinned-menu-items'`, reusing `isPinned`/`togglePin` unchanged. Menu ids are strings (`'profile-controller'`), so the store's blanket `Number`-cast would turn every id into `NaN` and silently drop the whole set on load — coercion is now scope-aware: `STRING_SCOPES = new Set(['menu'])` + `coerceId(id, scope)` (`String(id)` for menu, `Number(id)` for every other scope — the five numeric scopes are byte-identical to before); `_load` filters with `Boolean` for menu vs `Number.isFinite` for numeric scopes. `menu.js` (`data/menu.js`) delegates — `isPinned(item)` → `$store.pinned.isPinned(item.id, 'menu')`, `togglePin(item, event)` → store toggle + a `_pinsVersion` bump that invalidates its memoized `sortedItems` cache (the getter's pinned-first partition sort runs once per pin/alpha change, then O(1); with no pins AND no alpha it fast-paths to `this.items` untouched — see the memo pattern there before adding any per-access sort to a factory getter). The pin button on grid tiles/list rows reuses the §9.1 vocabulary (`push_pin`, `font-fill rotate-45` when pinned, `primary-container` chip) and is gated by an explicit header **pin-edit mode** — a `pinEditMode` boolean on `menu.js` (transient: reset in `closeMenu()`, never persisted), toggled by a header button beside the recent-only one (same header button vocabulary; its glyph fills + tilts when active). Idle-state rule: a pin button renders ONLY when the item is pinned (its chip, always visible) or when `pinEditMode` is on (`x-show="pinEditMode || isPinned(item)"`) — an unpinned, non-editing view shows no pin chrome at all ("no visual noise"), which also settles the touch-device concern (a hover-revealed pin would be untappable; an edit-mode pin needs no hover). While editing, every icon box carries `animate-shiver` (§5.3 userStylesPattern) so the mode reads at a glance. Pinning also snaps `current = 0` so the user sees the item land on page 1.

**Layered memoized getters must invalidate by reference, never by re-deriving a parallel key from the inner getter's private cache field (real bug, fixed 2026-09-10).** A later optimization pass added memoization to `paginatedData`/`groupedItems` (both consume `sortedItems`'s output) by hand-building a cache-key string that included `this._sortedKey` — `sortedItems`'s own internal cache-key field — instead of actually calling `this.sortedItems`. Looks equivalent, isn't: `sortedItems` has an early-return path (`if (!this.sortAlpha && pins.size === 0) return this.items;`) that never touches `_sortedKey` at all, so that field stays at its initial `''` until a pin/sort-toggle happens to land on the *non*-early-return branch. Since `paginatedData`'s key-check read the stale field instead of invoking the getter, it never got a chance to notice a pin was added — the pin icon flipped (that binding calls the store directly, unaffected), but the item never actually reordered to page 1, silently, until something unrelated forced a fresh render. **Fix:** call the inner getter first (`const items = this.sortedItems;`), then compare the *returned array* by `===` reference against last time — the inner getter already returns the identical array reference when nothing changed and a new one when it did, so reference equality is both simpler and correct, where re-deriving an external key string is not. **Rule: when getter B is memoized on top of memoized getter A, invalidate B by reference-comparing A's return value, never by reading one of A's own private cache fields as a proxy — a field written only on A's non-early-return path can't be trusted to reflect A's up-to-date state.**

**The reorder mechanism is CSS `order` on flex items — NOT DOM reordering, NOT a server sort.** Each sidebar list container (`#channel-list` / `#contact-list`) is `flex flex-col` and each row binds `:style="{ order: $store.pinned.isPinned(id, scope) ? -1 : 0 }"`. Pinned rows (order `-1`) float above unpinned rows (order `0`); all pinned rows tie at `-1` and keep server (DOM) order among themselves (i.e. by last-message recency), so no per-pin ordering is stored — deliberate minimal. **Morph-safe:** `order` is a pure visual property re-applied by Alpine after every Livewire morph/poll; the DOM order stays server-rendered and the pin set is read fresh from the store each time, so a pin toggled in one tab is honored on the next poll re-render with no morph-hook fragility (the `Livewire.hook('morph', …)` DOM-move approach was rejected for the same timing reasons §8's sender-chip scrape was).

**Two load-bearing layout rules (both learned the hard way):**
- The container MUST be `flex flex-col` for `order` to take effect — `order` is inert on a block container (a `flex-col` class WITHOUT `flex` sets only `flex-direction`, not `display:flex`; that was the original "pin doesn't slide up" bug). Grid (`grid grid-cols-1`) also honors `order` and was tried as a non-flex alternative, but was rejected by the user — flex + `shrink-0` is the kept design.
- Each row carries `shrink-0` (`flex-shrink: 0`). Without it, flex-column items default to `flex-shrink: 1` and compress to fit the height-constrained sidebar, cramming the rows together and destroying the elegant per-row spacing the block layout had. `shrink-0` makes flex behave like block here: rows keep their natural `py-2.5` height and the list scrolls (`overflow-y-auto`) instead of cramming.

**No slide animation:** `order` is not an animatable property, so the reorder is instant (a FLIP animation pass was deliberately NOT added — minimal). The "slide up" is the conceptual move-to-top, not a tween.

**Pin UI (both sidebars):** the pin and mute buttons are wrapped together in ONE absolute cluster — `absolute top-1.5 end-1.5 z-10 flex items-center gap-1 pointer-events-none` — so they sit genuinely side-by-side as flex children (one anchor, no two separate `end-*` coordinates to collide or drift apart). Inside it, the pin button is first (corner-most in RTL) and the mute button second (beside it); each is a per-row hover-revealed `<button>` cloned from the mute button's exact vocabulary — `w-6 h-6`, 14px glyph, `opacity-0 scale-90 pointer-events-none` idle / `group-hover:`+`focus:`+active → `opacity-100 scale-100 pointer-events-auto`, `aria-pressed`, `aria-label`/`title` carry the NEXT action ('سنجاق کردن …' / 'برداشتن سنجاق …'), `x-on:click.stop` + `x-on:keydown.enter.stop`/`x-on:keydown.space.stop` (`.stop` no `.prevent`, same as mute — see §8). The wrapper is `pointer-events-none` so idle clicks pass through to the row; each button re-enables `pointer-events-auto` on hover/focus/active. Two deliberate divergences from the mute button: (1) the glyph is the **constant** `push_pin` (NOT an `x-text` swap) — only the **fill axis** toggles via `:class="isPinned ? 'font-fill rotate-45' : ''"` on an `inline-block transition-transform` `<span>` (filled + tilted = pinned, outlined + upright = not); (2) the **active pin gets a background chip** — `bg-[var(--md-sys-color-primary-container)] text-[var(--md-sys-color-on-primary-container)]` (the mute button stays bg-less, `text-primary` only) — so a pinned row "shows itself" at rest (always-visible, not just hover-revealed) while an unpinned row shows no pin at rest. The mute button keeps its original corner slot (it was NOT moved); the single-cluster wrapper was the fix for the user's "two different ends" complaint — two independent `absolute` buttons at `end-1.5`/`end-9` read as separated, one flex cluster reads as one tight group (the same shape the header action clusters use).

**Shared partial (`messaging/sidebar-row-actions.blade.php`):** the pin+mute cluster is identical between the two sidebars, so it is extracted into one partial in the shared `messaging/` family (alongside `header-actions` / `message-actions`), `@include`'d by both with four vars — `id`, `scope` (`'channel'`/`'contact'`), `pinNoun`, `muteNoun` (channel passes `گروه`/`گروه`; contact passes `گفتگو`/`مخاطب` — contact splits the noun because the pin label says "گفتگو" but the mute label says "مخاطب"). The partial builds the four full label strings (`سنجاق کردن {pinNoun}` / `برداشتن سنجاق {pinNoun}` / `بی‌صدا کردن {muteNoun}` / `باصدا کردن {muteNoun}`) in a `@php` block and the noun is the only per-module variable. **Every PHP→JS interpolation in the partial uses `@js()`, NOT `{{ }}`** — Alpine attributes (`x-on:click`, `:aria-pressed`, `:aria-label`, `:title`, `:class`, `x-text`) are evaluated as JS by Alpine, so a `{{ $var }}` inside a single-quoted JS string breaks out of the string (and is an XSS vector) if the value ever contains a quote; `@js()` JSON-encodes with `JSON_HEX_APOS`/`JSON_HEX_QUOT` and emits single-quoted JS strings (`@js('channel')` → `'channel'`, `@js(5)` → `5`), safe inside the double-quoted HTML attribute. This is the rule for ANY Alpine attribute that takes a JS expression: use `@js()` for PHP values, never raw `{{ }}`. (The sidebar's own `:style` order binding still uses `{{ $ch['id'] }}` because the id is a guaranteed-numeric int and the scope is a blade literal `'channel'` — no variable, no quote risk — but a string id or a variable scope there would need `@js()` too.)

**Feature-legend:** a `pin` tab (icon `push_pin`, label 'سنجاق') was added to `messaging/feature-legend.blade.php` with one shared-scope row explaining the hover→pin→floats-to-top behavior, the active-state cues (filled + tilted pin on a colored chip, always visible), and that it's per-browser only — the feature is otherwise undiscoverable (the user's own blocker was not finding how to pin).

## 9.2 Sidebar color-tag store (`stores/tagged.js`) — client-only row-background tint

A third Alpine store in the same family as `pinned`/`sound`/`push`, registered the same way (`import registerTaggedStore from './stores/tagged.js'` + `registerTaggedStore(Alpine)` in `main.js`, after `registerPinStore`). **Client-only — no server state, no round-trip, no IDOR** (the tag map never leaves `localStorage`). Lets a user color-tint the background of a sidebar row (channel, contact, project), a TaskBoard card (`task` scope), or a THS ticket row (`ths` scope, added 2026-09-14 as a port of the taskboard popover into a table row — the tag button beats the row's `wire:click` with `x-on:click.stop`; the popover opens `bottom-full mb-2` exactly like the taskboard card — a first draft used `top-full`, which clipped at the table's bottom edge because the `.overflow-x-auto` wrapper computes `overflow-y: auto`, caught in review and flipped; the row wash tint rides an overlay div inside the FIRST `<td>` — `absolute inset-0 -z-10` with the `<tr>` carrying `relative isolate` — the abspos containing block resolves to the `relative` tr because the td is static, and a div placed directly inside `<tr>` would be fostered out of the table by the HTML parser, so the td placement is load-bearing) so a busy record is easy to spot again — pure visual, rides no data, affects no ordering (orthogonal to the §9.1 pin `order`).

**Shape — object-map-per-scope, NOT array** (unlike `pinned`/`sound` which are arrays): `maps: { contact: {}, channel: {}, project: {}, task: {}, ths: {} }`, each an object keyed by `Number(id)` → color index `0..3`. Five localStorage keys (`tagged-contacts` / `tagged-channels` / `tagged-projects` / `tagged-tasks` / `tagged-ths`) persisted by `_persist(scope)`; `_load(key)` validates every saved entry as `Number.isInteger(idx) && idx >= 0 && idx < INK.length` and discards corrupt ones (defensive against hand-edited localStorage, and the reason a saved index ≥ new length is silently dropped on a palette shrink). Ids can collide across scopes (project ids are an independent auto-increment sequence that can match a channel or contact id), so per-scope keys — four maps — prevent cross-contamination; same rationale as §8's sound store. API: `palette` (the `INK` array, exposed so the popover `x-for` can iterate it); `getTag(id, scope)` → index or `null`; `isTagged(id, scope)` → bool; `setTag(id, color, scope)` (validates the index again before writing); `clearTag(id, scope)` (delete + persist); `solid(i)` → ink color for a swatch/icon; `tagBg(id, scope)` → opaque background color or `null`.

**One palette, 4 tool tones:** `INK` (`--tool-{amethyst|sapphire|sage|gold}-color`) for the swatch fills and the palette-icon glyph; `WASH` (`--tool-{tone}-bg`) for the row/card background. `tagBg` returns `WASH[t]` **directly** — the tool `-bg` tokens are already soft per-theme background tints, so no `color-mix` overlay is needed. (The previous MD3-container palette mixed each `*-container` to 55% over surface via `` WASH_BG = WASH.map(c => `color-mix(in srgb, ${c} 55%, var(--md-sys-color-surface))`) ``; retired because `primary-container` `#d1e7ef` and `secondary-container` `#d7e3f7` were near-identical light blues — the user's "two are very similar" complaint. The 4 tool tones are well-separated in every light/dark/accent variant and already match the TaskBoard label chips.) The palette icon (`palette`) uses `:style="$store.tagged.isTagged(@js($id), @js($scope)) ? { color: $store.tagged.solid($store.tagged.getTag(@js($id), @js($scope))) } : null"` so a tagged row's tag button shows its ink color at rest (a second always-visible cue, alongside the pin chip).

**The tint is an overlay layer, NOT an inline `:style` on the row** — the user's requirement was a background on the whole row record, and an inline `background-color` on the row div would clobber the active-row bg (`primary-container` + `border-r-2`) and the hover bg (`surface-variant`) beneath it. Instead the partial adds a first child `<div class="absolute inset-0 -z-10 rounded-md pointer-events-none transition-colors duration-200" :style="{ 'background-color': $store.tagged.tagBg(@js($id), @js($scope)) }">` and the row carries `isolate` (creates a stacking context so the negative `-z-10` scopes to the row, not the page). The overlay paints above the row's own background but below the content (avatar, name, unread badge). The active border (`border-r-2 border-primary`) still renders because it is the row's own border, not a background layer the overlay covers; the active/hover row background is replaced by the tint wash when tagged — accepted, since the whole point is "the row takes this color." `pointer-events-none` keeps clicks passing through to the row. `tagBg` returns `null` for untagged rows so the overlay is transparent (no CSS to undo on toggle-off).

**Popover (4 swatches + clear):** a per-row `x-data="{ tagOpen: false }"` on the row div drives a popover `absolute top-1.5 end-1.5 z-20` (same anchor as the cluster, higher z) shown via `x-show="tagOpen" x-cloak`, dismissed by `x-on:click.outside="tagOpen = false"` + `x-on:keydown.escape.window="tagOpen = false"`. Swatches are `x-for="(col, i) in $store.tagged.palette" :key="i"` (iterates the `palette` property, which is the `INK` array exposed on the store), each a `<button>` with `:style="{ 'background-color': col }"` and a selected ring (`:class="$store.tagged.getTag(@js($id), @js($scope)) === i ? 'border-[var(--md-sys-color-on-surface)]' : 'border-transparent'"`); click runs `$store.tagged.setTag(@js($id), i, @js($scope)); tagOpen = false`. A trailing `✕` button calls `$store.tagged.clearTag(@js($id), @js($scope)); tagOpen = false`. ## 10. Don't cache a `document.getElementById` reference across a conditional container's lifetime

`#msg-viewport` (both `channel.js` and `contact.js`) sits inside a Blade `@if`/`@elseif` branch (`activeChannelId && activeChannel` / `activeContact`), sibling to create/browse/empty branches — it is destroyed and a fresh node is mounted every time the user leaves and re-opens a conversation. The outer `x-data="channel()"`/`x-data="contact()"` Alpine root lives on the page wrapper and is never re-`init()`'d by that inner swap (both modules swap the messages pane via `@island(name: 'messages')` re-render), so a field like `_vp: null` set once in `init()` and read via `this._vp || document.getElementById(...)` goes stale silently: `_vp` holds a non-null reference to the now-detached old node, so the `||` never falls through to a fresh lookup, and `scrollToBottom()`/cleanup calls quietly become no-ops after the first "back to list → reopen" cycle. `getElementById` is already a browser-optimized O(1) lookup — there's no real perf case for caching it, so `scrollToBottom()`/`destroy()`/`_updateQuoteChip()` all call it fresh on every invocation. **Rule: never cache a DOM reference by field on an Alpine component whose target element lives inside a conditionally-rendered branch, unless the cache is actively invalidated on every transition that can swap that branch — for a plain `getElementById`, querying fresh is both simpler and correct.**

**Correction/second instance of the same bug class, found by an independent review and fixed 2026-10-01: `_msgViewportEl` (a SEPARATE cached field from the `_vp` above, used for the scroll LISTENER itself plus `_readLastMessageMarker()`/`_quoteChipFromSelection()`/`_selectionChip()`) was never covered by the §10 fix above.** Unlike `scrollToBottom()`'s plain read (fixed), `_msgViewportEl` is set ONCE in `init()` (`this._msgViewportEl = document.getElementById(MSG_VIEWPORT_ID)`) and never refreshed — stale/null forever if mounted with no conversation open (the common case — `#msg-viewport` doesn't exist until one is selected), or pointing at a detached node after the first close-then-reopen cycle. Silently broke: the scroll-triggered auto-`loadOlder`/`loadMoreMessages`, the scroll-to-bottom FAB's show/hide threshold, and the quote-chip feature (all read `_msgViewportEl`), plus degraded (not broke — `refreshActive()`'s server-side stamp-probe is still correct) the poll's client-side "did anything visibly change" marker check. A plain re-fetch-on-every-read (the §10 fix's own remedy) doesn't work HERE because the scroll *listener itself* must be re-attached to whichever element currently exists, not just read fresh — a dangling reference doesn't un-break an event listener that was never attached to the right node in the first place. Fixed with a dedicated `_bindViewport()` method (re-queries the element, re-attaches the scroll listener via its own `AbortController` so repeated calls replace rather than stack the listener) called from `init()` AND from the end of every `selectContact()`/`selectChannel()` resolution — `backToList()` additionally nulls `_msgViewportEl` so no stale read can happen while no conversation is open. **Rule, generalized from §10's: a cached DOM reference needs re-binding at EVERY point its target element's lifetime can restart, not just a one-time fix at the original cache site — audit every field that caches an element living inside a conditional branch, not just the first one found.**

**Third pass (2026-10-01, second fresh-eyes audit): the `_bindViewport()` correction above was itself incomplete on the Channel side.** `selectChannel()` was the only re-bind call site, but Channel (unlike Contact) has FOUR more transitions that re-mount `#msg-viewport` (`joinChannel`, `createChannel`, `toggleBrowse` closing back to an active channel, `closeCreate`) and two that destroy it (`leaveChannel`, `doDeleteChannel`) — all left the field stale or dangling. Fixed via `channel.js`'s `_afterPaneSwap()` (`$nextTick` → `_bindViewport()` + conditional `scrollToBottom()`) chained into all six wrappers. Contact needs no port — its only pane transitions are select/backToList, both already covered. The §10 generalized rule stands verbatim: audit EVERY lifetime-restart point, including ones added later.

Both `syncPushNotify()` implementations are otherwise identical (read attribute → diff → notify → update baseline) — the only difference is what triggers the read.

**Load-older scroll jump fixed 2026-10-22 — `chatBase.loadOlderKeepingPlace(load)`.** The old scroll-triggered path compensated with `vp.scrollTop += (scrollHeight after − before)` AND relied on `vp.style.overflowAnchor = 'none'`; but Livewire's morph strips that JS-set inline style (see §11 theory 2), so the browser's native scroll anchoring also kept the reader's place and the manual delta was added on top — the view jumped DOWN by the height of the freshly loaded page ("it keeps scrolling to the bottom, load-more looks broken"). The «پیام‌های قدیمی‌تر» button had no compensation at all. Both paths (Contact `loadMoreMessages`, Channel `loadOlder`, each also reachable from `<x-ui.buttons.load-more :keep-place="true">`) now call the one method, which records `scrollHeight` before the island call and, after `$nextTick`, adds `(added height − LOAD_OLDER_PEEK_PX)` to `scrollTop`: the reader keeps the message they were on and ~96px (two lines) of the freshly loaded page peek in above it, the same cue chat apps give. This is only deterministic because `#msg-viewport` now carries the blade class `no-anchor` (`overflow-anchor: none`, `dashboard.css`) in BOTH modules — the old JS `style.overflowAnchor = 'none'` write was removed (Livewire's morph strips inline styles, so native anchoring silently came back after the first re-render and double-counted). The relative delta also preserves any scrolling the user does while the request is in flight (the first version of this routine set an absolute position and snapped inertia scrolls back). `_loadingOlder` is the single re-entry guard. Page size is `Main::LOAD_STEP` = 25 in both components (was 10). Auto-load is upward-scroll only and skipped while `_programmaticScroll` is set (`markProgrammaticScroll`, `SCROLL_SETTLE_MS` = 150; `record-focus.js` dispatches a bubbling `programmatic-scroll` event before its jump), and `loadOlderKeepingPlace` drops the restore if the conversation id changed mid-flight. Opening/switching a conversation scrolls instantly (seq-guarded, FAB/`newBelow` reset); smooth scroll remains only for the FAB click and near-bottom new-arrival follow. `destroy()` clears the settle timer and disconnects the viewport `ResizeObserver` (re-pins on keyboard resize; meta viewport `interactive-widget=resizes-content`). Bubble stagger is end-anchored, capped at 10 steps × 0.04s per day group (`BuildsMessageGroups`/`ContactPresenter`). Tests: `chatBase.test.js` (`loadOlderKeepingPlace …`).

## 12. Density store (`stores/density.js`) + FOUC head-script — zero-backend, CSS-driven compact mode

**Three pieces, each minimal:**

1. **`stores/density.js`** — `Alpine.store('density', { compact: false, init() {…}, toggle() {…} })`, registered like the other stores (`import registerDensityStore from './stores/density.js'` + `registerDensityStore(Alpine)` in `main.js`). `init()` reads `localStorage` and mirrors it onto `document.documentElement.classList` (`'app-density-compact'`); `toggle()` flips `compact`, writes `localStorage`, and re-toggles the class. 2. **`public/js/prefs-manager.js`** — a tiny plain-IIFE script loaded **synchronously in `<head>` before `@vite`** (mirrors `public/js/mode-manager.js` for dark/light mode; this file is a merge of the density IIFE and the column-visibility IIFE from §13 below — both are user-panel-dashboard-only concerns always loaded together, so they share one file, distinct from `mode-manager.js` which the admin panel also needs standalone). It toggles the same `html` class from `localStorage` **pre-paint**, because Alpine boots at `alpine:init` (after the bundle parses) — without this head script, the page would render comfortable then flash to compact once Alpine's `init()` runs (FOUC). The store's `init()` is idempotent over the class the head script already set, so the two never fight. Rule: any `$store` whose state drives a visible class on first paint needs this paired FOUC head-script; Alpine alone is too late.
3. **CSS in `dashboard.css` `@layer components`** — `.app-density-compact <consumer> { @apply … }`. Consumers carry stable marker classes (`dms-doc-table`, `taskboard-card`, `taskboard-card-description`, `taskboard-column-list`) and the html-class selector drives all compact styling. `@apply` works inside `@layer components`. Compact overrides use `!`-important utilities (e.g. `@apply !py-0`, `@apply !gap-2 !p-2.5 !pt-5`) to reliably beat the resting Tailwind utilities on the same elements; the `md:` responsive override is a nested `@media (min-width:768px) { .app-density-compact .taskboard-card { @apply !p-3 } }` so the compact padding still responds to breakpoint.

**Consumer binding (DMS `table.blade.php`, TaskBoard `tools.blade.php`):** a single icon button with `@click="$store.density.toggle()"`, `:class` swapping primary-fill vs container-idle, `:title`/`:aria-label` carrying the **next** action («نمایش عادی»/«نمایش فشرده»), and `x-text` swapping `view_comfy`/`view_compact` glyphs — the exact vocabulary TaskBoard's old Livewire toggle used, so the UI/UX is identical, only the mechanism changed. TaskBoard's server-rendered `$density` conditionals were converted to CSS marker classes (`taskboard-card`/`taskboard-card-description`/`taskboard-column-list`) so the html-class CSS drives compact FOUC-free; the old `Main.php` `$density` property + `setDensity()` action + `preferences.taskboard_density` read/write were deleted (and their two server-side tests with them — the behavior is now client-side, untestable via Livewire).

**Why a store, not a manager:** `mode-manager.js` is a plain window-level manager (no Alpine reactivity needed — dark mode has no toggle button bound through Alpine). Density needs a reactive `compact` for toggle buttons' `:class`/`x-text`, so it gets an `Alpine.store` **plus** the paired FOUC head-script — the store for reactivity, the head-script for pre-paint. This is the template for any future toggle that both drives first-paint classes and has Alpine-bound controls.

## 13. Column-visibility store (`stores/colVisibility.js`) + FOUC head-script — CSS-mask, no DOM move

A per-user column show/hide mask on the DMS doc table — and, since 2026-09-14, the THS ticket table, plus the reservation Command Grid table since 2026-09-15 — **fully client-side** and **morph-safe by construction**: hiding is a pure-CSS `display:none` driven by an injected `<style>` element, NOT a per-cell Alpine `x-show`/`:class` binding and NOT a DOM reorder. Because the cell DOM never moves and the table always renders the server's default column order, Livewire morph matches cells by position cleanly (no corruption, no keyed-move revert, no popover-state loss). The `<style>` lives in `<head>` outside the Livewire component, so morph never touches it — a masked column stays hidden across every sort/filter/loadMore/confirmRead with **zero re-apply logic** (unlike a reorder, which would need a post-morph re-apply).

**Three pieces, mirroring §12 — scope-aware since 2026-09-14:**

1. **`stores/colVisibility.js`** — `Alpine.store('colVisibility', { maps: { dms: [], ths: [], reservation: [], taskboard: [] }, … })`, registered like density (`import registerColVisibilityStore` + `registerColVisibilityStore(Alpine)`). Scope registry (4 scopes since 2026-10-16): `KEYS = { dms: 'dms-col-hidden', ths: 'ths-col-hidden', reservation: 'reservation-col-hidden', taskboard: 'taskboard-col-hidden' }` (localStorage) + `SCOPES = { dms: '.dms-doc-table', ths: '.ths-ticket-table', reservation: '.reservation-command-table', taskboard: '.taskboard-card' }` (CSS selector; the `taskboard` scope masks card sections via `data-col` markers, not table columns); the literal `maps`/`KEYS`/`SCOPES` must stay in lockstep with the `DOMAINS` array (loops run to `DOMAINS.length` — never a hardcoded count). `init()` reads each key (JSON array; guarded by `try/catch` + `Array.isArray`); getters `hidden`/`thsHidden`/`reservationHidden` expose `maps.dms`/`maps.ths`/`maps.reservation` so the DMS blade's legacy `$store.colVisibility.hidden` bindings keep working unchanged; every method takes `scope = 'dms'` as trailing default (`isHidden(k, scope)`, `toggle(k, scope)`, `reset(scope)`), which is the whole DMS backward-compat story. `render()` (re)writes `#dms-col-visibility-style`'s `textContent` to one rule per hidden key per scope: `SCOPE_SELECTOR [data-col="KEY"]{display:none!important}`. `textContent` (not `innerHTML`) on the `<style>` — no XSS surface; keys are string literals from the blade, filtered to `typeof === 'string'` in the head-script for tamper hygiene. THS consumer: `data-col` on 4 hideable th/td pairs (`status`/`domain`/`requester`/`assignee`; شناسه/تاریخ and موضوع always visible) + a `view_column` popover in the actions `<th>` — a straight port of the DMS popover, with `'ths'` passed to every store call.
2. **`public/js/prefs-manager.js`** — the paired FOUC head-script, loaded **synchronously in `<head>` before `@vite`** (alongside `mode-manager.js`; also carries the density IIFE from §12 above in the same file). It reads ALL localStorage keys (same `Array.isArray` guard, parallel `keys`/`tables` arrays mirroring the store's `KEYS`/`SCOPES`, looped by `keys.length` — never a hardcoded count; the arrays carry all 4 scopes including `taskboard-col-hidden` / `.taskboard-card`) and creates `#dms-col-visibility-style` with every scope's rules **pre-paint**, so masked columns never flash visible on load. The store's `init()` finds that same element by id and rewrites it (idempotent) — the two never fight, and the tag id keeps its `dms-` name even though it now serves all scopes (renaming would orphan the head-script's element; the shared single-tag invariant is the point).
3. **`data-col="…"` on every `<th>` + `<td>`** in `dms/table.blade.php` (7 keys: `title`, `code`, `dept`, `status`, `details`, `desc`, `action`), scoped by the table's existing `dms-doc-table` class. No per-cell CSS/class change — the attribute is static, so morph never diffs it. A toolbar button (`view_column`, at `right-[7.25rem]`, a 4th absolutely-positioned chip flush with maximize/density/resetSort) opens a popover listing the 7 columns as `check_box`/`check_box_outline_blank` toggle rows + a «نمایش همه» reset (disabled when `hidden.length === 0`); a red count badge on the button shows how many are hidden. The button + popover are wrapped in ONE `x-data="{ open: false }" @click.away="open = false"` scope (button inside the wrapper) so clicking the toggle never trips `@click.away` — the same wrapper pattern the in-table popovers use.

**Why visibility (mask) over reorder (drag):** reordering columns on a Livewire-morphed, Alpine-popover-bearing table has no minimal+safe path — moving `<td>`s needs per-cell `wire:key` + a post-morph re-apply (else content corruption or every popover snapping shut on each update), and a CSS-`order`/flex refactor fights the tuned table layout (widths, `first:`/`last:` rounded corners, status `inset` shadow, `overflow-x-auto`). Visibility sidesteps all of it: DOM static → morph-safe; CSS in `<head>` → persists with no re-apply; FOUC head-script → no flash. The tradeoff is a one-frame load cost only the head-script already solves. See [[project_col_visibility_mask]] for the decision record.

## 14. Calendar Alpine Components — pointer-event DnD, now-line, view-swap scroll memory

Four factories in **one file** `data/calendar.js` (`calendarDrag`, `calendarResize`, `calendarNow`, `calendarView`), registered in `main.js` inside the existing `alpine:init` listener — `import { calendarDrag, calendarResize, calendarNow, calendarView } from './data/calendar.js'` (named exports — curly braces mandatory; the existing `import sidebar from './data/sidebar.js'` default-import form is for one-binding-per-file only) + `Alpine.data('calendarDrag', calendarDrag)` + `Alpine.data('calendarResize', calendarResize)` + `Alpine.data('calendarNow', calendarNow)` + `Alpine.data('calendarView', calendarView)`. String keys == export names (Proxy Hub convention).

**(a) `calendarDrag({eventId, locked, isOwner})`** — pointer-event DnD (unify mouse+touch via `pointerdown`/`pointermove`/`pointerup`, NOT HTML5 `dragstart` which is desktop-only and breaks Livewire morph). `init()`: `_isDestroyed=false`; if `locked || !isOwner` → no-op (read-only pill); else set `$root.style.touchAction='none'` (so the vertical drag can't trigger a scroll gesture during the dead-zone, same as `calendarResize`) and attach `pointerdown` on `$root` — **only `pointerdown` is attached here**; the `pointermove`/`pointerup`/`pointercancel` listeners are attached to `window` lazily inside `handleDown` (per-gesture) so the drag keeps tracking after the pointer leaves the pill mid-drag, and removed in `handleUp`/`destroy()`. `handleDown(e)`: guard `e.button !== 0 || dragging` (re-entrancy: a second pointerdown mid-drag is ignored), capture `startY=e.clientY`, `startTop=$root.offsetTop`, `hourHeight=parseFloat($root.dataset.hourHeight)||60`, `dragging=true`, **`dragStarted=false`** (reset per-gesture so the dead-zone guard is re-armed for the next drag), then attach `pointermove`/`pointerup`/`pointercancel` to `window` (the ghost is created lazily in `handleMove` once past the dead-zone, not here). `handleMove(e)`: if `!dragging` return; `offsetY=e.clientY-startY`; **dead-zone** — if `!dragStarted` and `|offsetY| < DEAD_ZONE_PX` (5px) return BEFORE any `preventDefault`/ghost/lock (a click, not a drag); once past it set `dragStarted=true`, clone a full-opacity ghost pill (pointer-events-none, drop-shadow, appended to `$root.parentElement`), hide the original (`$root.style.opacity='0'`, restored on `pointerup`/`destroy`), and `lockBodyInteractions('grabbing')` (shared module helper — sets `document.body` cursor + `userSelect='none'` + `pointerEvents='none'` so the drag can't select text or fire stray handlers; restored by `unlockBodyInteractions()` on `pointerup`/`pointercancel` — both route to the same `handleUp` release path — and in `destroy()`; `calendarResize` reuses the same pair with `'ns-resize'`). Then `e.preventDefault()`, `pendingOffsetY=offsetY`, and rAF-render the ghost top (throttled to one rAF per frame via the module `raf`/`caf` helpers; `offsetY===lastOffsetY` cancels the pending frame). `handleUp(e)`: `dragging=false`, remove the three window listeners, `unlockBodyInteractions()` (idempotent — on a dead-zone click `lockBodyInteractions` was never called, so this just restores `''` no-ops); **then check `if (dragStarted)` BEFORE resetting it** — if a real drag started remove the ghost, restore opacity, and commit immediately (no debounce) — set an optimistic `style.top` to the snapped slot, then compute `dateJalali` (from target day-column `data-date` Jalali `Y-m-d`) + `timePart` (`H:i` from snapped minutes) + `clientMtime` (`$root.dataset.mtime || new Date().toISOString()` — the pill renders `data-mtime` from the event's `updated_at` so the server's optimistic-concurrency compare matches; `new Date().toISOString()` is only a fallback when `data-mtime` is blank); `this.$wire.moveEvent({id, dateJalali, timePart, clientMtime}).then(res => { if(!res||!res.ok){ window.dispatchEvent(new CustomEvent('revert-event-'+this.eventId, {detail: res?.revertTo||{}})); this.$dispatch('toast', {message: res?.reason==='locked' ? 'این رویداد از طریق سیستم رزرو مدیریت می‌شود؛ برای تغییر آن به تب رزرو مراجعه کنید.' : 'جابجایی ناموفق بود.', type:'error'}); } else { this.$dispatch('toast', {message:'رویداد جابجا شد.', type:'success'}); } })` (note `res?.revertTo||{}` — optional chaining on the whole `res`, since `!res` admits null/undefined into the block); **only after the check** set `dragStarted=false` (belt-and-suspenders — `handleDown` already re-arms it per-gesture, so this trailing reset is redundant but harmless). `destroy()`: `_isDestroyed=true`, **`cancelGhostFrame()`** (cancels the pending `requestAnimationFrame` from `handleMove` so a mid-drag Livewire morph can't fire a stale rAF on a detached ghost), `removeEventListener` pointerdown (from `$root`) + pointermove/pointerup/pointercancel (from `window`), reset `$root.touchAction`/`opacity`, `unlockBodyInteractions()`, `removeGhost()`. Per-item state keyed by DOM `data-*` (`data-event-id`, `data-hour-height`, `data-date`) — mirrors `taskboard.js`'s per-item DnD exemplar.

**(b) `calendarNow({startIso, spanHours})`** — `init()`: `_isDestroyed=false`, `computeNowTop()`, `_timer=setInterval(()=>this.computeNowTop(), 60000)`, `document.addEventListener('visibilitychange', _visHandler=()=>{ if(!document.hidden) this.computeNowTop(); })`, auto-scroll container to now-line on mount (`$root.parentElement.scrollTop = nowTop px`), schedule midnight-rollover check. `computeNowTop()`: `now=new Date()`, `start=new Date(this.startIso)`; if `now<start || now>start+spanMs` → hide (`nowTop=-1`); else `nowTop=((now-start)/spanMs)*100` (`spanMs=(spanHours||18)*3600*1000` — the visible grid is 06:00–24:00 = **18h, NOT 24h**; blade passes `spanHours` via the `now-line` include); if day rolled over since last tick → `Livewire.dispatch('refresh-calendar')` (ONE soft reload, NOT per-minute round-trips — the 60s interval only recomputes the now-line client-side). `destroy()`: `_isDestroyed=true`, `clearInterval(_timer)`, `document.removeEventListener('visibilitychange', _visHandler)`. Mirrors `channel.js`'s `setInterval` polling + `visibilitychange` pause/resume + `destroy()` exemplar.

**(c-bis) `calendarResize({eventId, startMinutes, durationMinutes, isOwner, locked})`** — bottom-edge handle resize (extends/shortens an event's `duration_minutes`). The `x-data` lives on the **handle element** (a thin `h-1.5 cursor-ns-resize` strip absolutely positioned at the block's bottom, rendered only when `draggable && heightPx >= 30`), and `init()` resolves the actual block via `this.$root.closest('[data-event-id]')` — so the handle owns the gesture but mutates the parent block's `style.height`. `init()`: if `locked || !isOwner || !block` → no-op; else set `this.$root.style.touchAction='none'` (so the vertical drag doesn't scroll the page) + attach `pointerdown` on the handle. `handleDown(e)`: `e.preventDefault()` + `e.stopPropagation()` (the stopPropagation is critical — without it the block's `calendarDrag` `pointerdown` also fires and a resize would start a move), capture `startY`, `startHeightPx = block.offsetHeight`, `startDuration = durationMinutes`, set `dragging=true` + `dragStarted=false` (re-arms the dead-zone per-gesture, mirroring `calendarDrag`), attach `pointermove`/`pointerup`/`pointercancel` to `window`. `handleMove(e)`: `offsetY = e.clientY - startY`; **dead-zone** — if `!dragStarted` and `|offsetY| < DEAD_ZONE_PX` (5px, shared module const with `calendarDrag`) return (a tap on the handle is not a resize); once past the dead-zone set `dragStarted=true` and `lockBodyInteractions('ns-resize')` (shared helper: sets `document.body` cursor + `userSelect='none'` + `pointerEvents='none'` so the drag doesn't select text or trigger stray handlers — restored by `unlockBodyInteractions()` on release/cancel/destroy). Then `deltaMinutes = round(((e.clientY-startY)/hourHeight)*60/SNAP)*SNAP` (`SNAP=15`), write the closure-scoped `pendingDuration = clampDuration(startDuration + deltaMinutes)` where `clampDuration` caps at `min(MAX_DURATION=480, DAY_END=1440 - startMinutes)` and floors at `MIN_DURATION=15` (so a late-night event can't extend past midnight), rAF-render `block.style.height = pendingDuration*hourHeight/60` — `pendingDuration` is **live-render state only**, never read by the commit path. `handleUp(e)`: release listeners, then `commitResize(e.clientY - startY)` — `commitResize(deltaY)` **re-derives** `deltaMinutes = round((deltaY/hourHeight)*60/SNAP)*SNAP` and `newDuration = clampDuration(startDuration + deltaMinutes)` from the `deltaY` argument (independent of `pendingDuration`, so the commit is deterministic even if a rAF frame was dropped); if `newDuration === startDuration` restore `block.style.height = startHeightPx` and bail (no round-trip for a no-op drag); else `$wire.resizeEvent(eventId, newDuration, clientMtime)` (`clientMtime = block.dataset.mtime || new Date().toISOString()`) and on `!res.ok` restore `block.style.height = startHeightPx` + toast «تغییر مدت ناموفق بود.» (or the locked-specific message). `handleCancel()`: release + restore height, **no commit** (pointercancel = user aborted / palm / scroll intruded). `destroy()`: `_isDestroyed=true`, cancel any pending rAF, remove `pointerdown` (from handle) + reset `touchAction`, remove window listeners, `unlockBodyInteractions()`; if `destroy()` fires mid-drag (`dragging`) it also restores `block.style.height = startHeightPx` (parity with `handleCancel` — belt-and-suspenders, since a Livewire morph would re-render the block with the server's authoritative height anyway and `@revert-resize-{id}.window` restores on any server rejection). Mirrors `calendarDrag`'s owner-guard + `clientMtime` optimistic-concurrency + revert-on-failure contract; the server-side `ResizeEventAction` is the move action's sibling (same rate-limit/owner/locked/stale/bounds shape, see `livewirePattern.md`).

**(c) `calendarView()`** — view-swap scroll memory via `scrollMemory[mode]` + `localStorage('calendar-scroll-memory')` (persistentStateMixin try/catch pattern). `init()`: `_isDestroyed=false`, `this.view=this.$wire.get('view')||'month'`, `this.scrollMemory={}`, `$watch('$wire.view', (v)=>{ this.saveScroll(this.view); this.view=v; this.$nextTick(()=>this.restoreScroll(v)); })`, restore from localStorage. `saveScroll(mode)`: `this.scrollMemory[mode]=this.$root.scrollTop`, `try { localStorage.setItem('calendar-scroll-memory', JSON.stringify(this.scrollMemory)) } catch {}`. `restoreScroll(mode)`: if `this.scrollMemory[mode]` set `this.$root.scrollTop`. `destroy()`: `_isDestroyed=true`, `saveScroll(this.view)`. It is a **data component** (not a new store) — no `stores/` file, keeping ownership inside the single `calendar.js` + `main.js` pair. It also spreads `...maximizeMixin()` (§3.4 single-boolean pattern) so the whole pane maximizes via `max`/`toggleMaximize()` — each of the 3 view containers carries `:class="{ 'max-widget': max }"` + a shared `<x-ui.modals.max-backdrop state="max" close="toggleMaximize()"/>` + `@keydown.escape.window="if(max) toggleMaximize()"`. Control split: the `<x-ui.title>` actions hold ONLY the view-toggle (month/week/day) + the two legend buttons (help + notifications) — like every other module's heading; the range-label chip + prev/today/next nav + the maximize button live **inside each view card** via a shared `view-header.blade.php` partial (the nav's original home was inside the month grid — keep controls *in the grid*, not in a sub-header row above it), so they maximize with the pane and the maximize button stays reachable when maximized. The calendar root has **no `animate-fade`** (see the `animate-fade` trap note in §3.4) so the fixed `.max-widget`/`.max-backdrop` escape to the dashboard `isolate` tab container and cover the side navs (left/right/bottom `<aside>`, z-50/z-9998); un-maximize is ESC/backdrop, matching the project-wide `.max-widget` z-999999 viewing-mode pattern where modals open in normal mode.

**Real race condition fixed (2026-10-05), found by an independent module-wide audit, same shape in both `commitMove` and `commitResize`.** Dragging (or resizing) the SAME event, releasing, then immediately dragging it again before the first `$wire.moveEvent`/`resizeEvent` call resolved had no guard at all — `startTop`/`startHeightPx` are closure-scoped across the whole `calendarDrag`/`calendarResize` instance (one instance per event block, reused for every gesture on that event over its lifetime), so a SECOND gesture's `handleDown` overwrites them before the FIRST gesture's async response arrives. If the first (now-stale) response lands after the second's — plausible on any two quick adjustments to the same event, not an exotic timing window — its failure-revert branch would snap `$root.style.top`/`block.style.height` back using whatever `startTop`/`startHeightPx` happen to hold BY THEN (the second gesture's own start position, not the true original), silently overwriting the second gesture's already-applied, possibly-server-confirmed result. Fixed with the same sequence-counter guard `contact.js`'s `selectContact`/`channel.js`'s `selectChannel` use (same-day fix, see `livewirePattern.md`'s Contact/Channel sections): a closure-scoped `moveSeq`/`resizeSeq` bumped to a local `seq` at the very start of `commitMove`/`commitResize`, plus the revert target itself snapshotted into a local (`revertTop`/`revertHeightPx`) at that same moment rather than read later from the (by-then possibly-reassigned) shared variable; both the `.then()` and `.catch()` bodies early-return when `seq` no longer matches the live counter, so only the LATEST gesture's response is ever allowed to touch this event's DOM or show a toast. Regression-guarded (added same day, superseding the prior "no test added" state): `calendar.test.js`'s two new `describe` blocks simulate a full two-gesture race via real `pointerdown`/`pointermove`/`pointerup` events on a constructed fixture, proving a stale failure response neither reverts the DOM nor re-toasts once superseded, while a genuine single-gesture failure still reverts and toasts correctly (the regression-guard half of each pair).

**Pitfalls (calendar-specific):**
- **Never cache `getElementById` across `x-show` swap** — query fresh each time; an `x-if`/`x-show` toggle can stale a cached node reference. The view containers are sibling `x-show` + `x-cloak` (NOT `x-if`) so DOM persists and scroll memory survives morph.
- **`@entangle` stays inline in the `x-data` object literal** — never bury it in a factory arg (the factory is a pure data factory, not a closure over Livewire state).
- **PHP→JS via `data-*` attrs + `$el.dataset`** for live per-item values (`data-event-id`, `data-date`, `data-hour-height`, `data-start-iso`); `@js()` only for one-shot init scalars passed into the factory call (`@js($event['locked'])`, `@js($event['is_owner'])`, `@js($startIso)`, `@js($spanHours)`). Never put `@js()` inside an Alpine expression string for live data.
- **No `<script>` in Blade** for Alpine logic — extract to `data/calendar.js`; the blade partials (`event-block`, `now-line`, etc. — **no `_` prefix**, per project convention) only wire `x-data="{ ...calendarDrag({...}) }"` + `data-*` attrs.
- **`destroy()` is mandatory** with a `_isDestroyed` guard, timer clears, and `removeEventListener` — the calendar partials re-render on Livewire morph and orphaned listeners/timers are the #1 leak source here.

## 15. Canvas rAF-loop performance conventions — pause guards, invariant hoisting, geometry caching

Applies to every canvas-based ambient/decorative animation (`data/patterns/*.js`, `data/ambient.js`'s "angry" effect, `data/occasion.js`'s confetti). Apply whichever of the three is relevant per file — never all three reflexively, and never at the cost of a visible/timing change:

1. **Pause guard (mandatory for anything not already covering it):** every `requestAnimationFrame` loop must stop doing real work when the tab is hidden (`document.visibilitychange` → a `paused` flag) and, if the element isn't a full-viewport fixed background, when it scrolls out of view (`IntersectionObserver`, no explicit `threshold` — default `0` only flips false once fully out of view, so a partially-visible element keeps animating). The loop itself keeps ticking (`requestAnimationFrame` reschedules even while paused) — only the expensive draw body is skipped; this is the existing convention in 13 of the 15 `patterns/` files and is the pattern to copy for anything new. `data/ambient.js`'s card-border effect was the one file missing it (bound to a specific card, not a full-viewport background, so it needed both guards) — fixed by seeding `paused` from the current `document.visibilityState` on init (not just future `visibilitychange` events) plus an `IntersectionObserver` on the card container.
2. **Hoist per-frame invariants out of the reactive Alpine object.** A pure helper called via `this.foo()` many times per frame pays an Alpine reactive-proxy trap on every access; move it to module scope (outside the factory) and call it directly from the hot loop, keeping an identically-named delegating method on the returned object only for external callers. Reference: `data/ambient.js` (`random`/`noise2D`/`octavedNoise`/`getCornerPoint`/`getRoundedRectPoint` hoisted), `patterns/cyber.js` (per-column color template strings hoisted the same way).
3. **Cache geometry/style objects that are invariant between the events that actually change them** (resize, theme `MutationObserver`) — not invariant "forever." `patterns/snow.js` bakes each flake's fixed-for-its-lifetime multi-arm path into a `Path2D` at creation (mirrors `patterns/cloud.js`'s existing `Path2D` idiom); `patterns/gradient.js` caches `createLinearGradient` objects, rebuilt only on resize + theme mutation. Before caching this way, confirm every code path that can change the cached value's inputs — including DPR changes from browser zoom or moving the window between differently-scaled monitors — actually goes through the same invalidation trigger.

**`Alpine.raw()` for a hot reactive array — narrow, verify the template before reusing.** `data/occasion.js`'s confetti loop mutates `this.particles` many times per frame across dozens of particles; wrapping it once per frame with `Alpine.raw(this.particles)` and mutating the raw array bypasses the reactive proxy for every per-particle write. Safe ONLY when nothing in the consuming blade reads reactive state derived from that array's contents (no `x-for` over it, no computed depending on its length/shape) — `report.js` is the other existing precedent for this technique.

## 16. Lazy per-route Alpine chunks + hover-warm prefetch

The Proxy Hub (`main.js`, §3.1) eagerly registers **every** `data/*` factory at `alpine:init` so Alpine never sees an unregistered `x-data`. The cost: one `app.js` bundle parses + executes on **every** route, even routes that use only one heavy module factory. The home/dashboard shell and its tabs (calendar, feeds, gallery, links, reports, faqs, filters, status) need many factories; a separate-route module (`/dms`, `/ths`, `/tasks`, `/projects`, `/channels`, `/contacts`, `/reservation`, `/profile`, `/analytics`, `/energy`) needs only its own. So the partition is by DOM presence, not by guesswork: a factory is **eager** iff its `x-data` appears in the home shell/tabs; it is **lazy** iff it appears only on its own module route.

**Lazy chunk contract (`resources/js/components/alpine/modules/<name>.js`):** each lazy module gets a tiny Vite entry — import the factory(ies), register via `components/alpine/module-runtime.js`: `registerModuleData({ dms })`. The entry is loaded only on its route (see layout wiring below). One entry can register several factories that share a route: `components/alpine/modules/project.js` registers `project`, `projectComposer`, **and** `projectAnalytics` (the `/projects` route has a project-analytics tab that uses `projectAnalytics`); `components/alpine/modules/analytics.js` registers `analytics` for the standalone `/analytics` route. The two factories are deliberately **separate files, not a shared factory** — the project tab stays decoupled from the `/analytics` module so disabling that module must not break the project tab. Both import `chartBuilderMixin` from `mixins/chartBuilder.js` for the common `getCssVar`/`buildOptions`/`buildData`/`resolveColor` chart helpers, and Vite auto-extracts that mixin into a shared chunk loaded by whichever side needs it (the global `analytics` factory passes `data` raw because `HrAnalyticsService` emits literal hex — `resolveColor` no-ops on hex, so `buildData` would be wasted work; the project `projectAnalytics` factory calls `this.buildData(data)` because its datasets use `var(--…)` MD3 tokens that must be resolved at render time). Mixins (`maximize`, `clipboard`, `mention`, `fancybox`, `monthFilter`, `kanbanDrag`, `taskForm`, `persistentState`, `chartBuilder`, `highlightMatch`) are NOT listed in the entry — they ride along via the factory's static imports; a mixin shared between an eager tab factory and a lazy module factory (e.g. `fancybox`, used by eager `gallery` AND lazy `contact`/`channel`) becomes a Vite shared chunk auto-loaded by whichever side needs it. `suggestion` has no `data/*` factory (Livewire-driven flowchart), so it gets no chunk. `main.js` drops both the import and the `Alpine.data(...)` line for every moved factory — the two edits are a pair; an import removed without removing its registration (or vice-versa) throws a `ReferenceError` inside the `alpine:init` callback that aborts registration of every factory listed after it.

**Gotcha — a bare `document.addEventListener('alpine:init', ...)` registration only works on a hard page load; it silently dies on the second `wire:navigate` cross-module transition, in EITHER direction.** `alpine:init` is dispatched by Alpine exactly once per real page load (Livewire calls `Alpine.start()` once; `wire:navigate` never reloads the JS realm). On the very first hard load this works because the lazy chunk's listener attaches before that one-time event fires. But navigating `/tasks` → `/projects` via `wire:navigate` injects a brand-new `components/alpine/modules/project.js` `<script type="module">` — Livewire's navigate correctly defers Alpine's tree-walk of the swapped body until this script has fully loaded (`preventAlpineFromPickingUpDomChanges` + `nowInitializeAlpineOnTheNewPage`, confirmed in `vendor/livewire/livewire/dist/livewire.esm.js`), so there's no execution-order race — but `alpine:init` itself already fired, permanently, back on the first page's load. The listener the new chunk just attached will never be called, `Alpine.data('project', project)` never runs, and Alpine throws `ReferenceError: project is not defined` walking the freshly-swapped `x-data="project()"` root — which (per the spread-getter rule elsewhere in this doc) aborts init for that whole subtree, so the page renders its Blade HTML but stays visually dead/blank (`x-cloak` never lifts, nothing is interactive). Confirmed to hit **every** lazy module, in both directions, the moment two different module routes are visited via `wire:navigate` in the same tab session. **Fix — `components/alpine/module-runtime.js`:** check `window.Alpine` (set once, globally, forever, from the very first page load) before falling back to the `alpine:init` listener:
```js
export default function registerModuleData(entries) {
    const register = () => {
        for (const [name, factory] of Object.entries(entries)) window.Alpine.data(name, factory)
    }
    if (window.Alpine) register()
    else document.addEventListener('alpine:init', register, { once: true })
}
```
`window.Alpine` is actually already set by the time any Vite module chunk executes even on a hard load — `layouts/app.blade.php` puts `@livewireScripts` (a classic, non-deferred `<script>`) near the end of `<body>`, which runs and sets `window.Alpine` before the deferred `type="module"` chunk scripts in `<head>` get their turn — so in practice the `if (window.Alpine)` branch fires every time, on hard load and on `wire:navigate` alike. The `alpine:init`-listener `else` branch is kept purely as defensive future-proofing against a script-ordering change, not as an active path today. Either way registration happens strictly before `Alpine.start()` walks any tree (`Livewire.start()` → `Alpine.start()` always runs after every deferred module script has executed, and after `preventAlpineFromPickingUpDomChanges`/`nowInitializeAlpineOnTheNewPage` on `wire:navigate`), so there's no ordering hazard regardless of which branch fires. **Rule: every `resources/js/components/alpine/modules/<name>.js` entry calls `registerModuleData({...})`, never a raw `document.addEventListener('alpine:init', ...)` directly** — the raw form only happens to work by coincidence of current script ordering and breaks the instant a second lazy module route is visited via `wire:navigate` in the same tab.

**Blast radius isn't just in-page links — every `redirect($target, navigate: true)` call hits this too.** `Dashboard\Navbar\CommandPalette` (the user-panel's global search, both its `'navigate'` static-module mode via `NavigationService` and its `'content'` real-record mode via `ContentService`) resolves every result to `$this->redirect($target, navigate: true)` — the identical cross-module navigate path as a sidebar chip or `<a wire:navigate>` link. Same for any nudge/notification link built with `route(..., ['open' => $id])`. None of these needed a separate fix — they all go through the same lazy-chunk-registration choke point `registerModuleData` closes — but it's the reason this bug reads as "random" reports from unrelated features (search, notifications, sidebar links) rather than one obviously-connected symptom. Anything that can land the user on a lazy-module route via `wire:navigate`, from anywhere in the app, was affected identically.

**Layout wiring (`layouts/app.blade.php`):** route name → chunk key → conditional entry, all in one `@vite` call (never a second `@vite` — in dev that double-injects the Vite client): `@php($moduleChunk = match(request()->route()?->getName()) { 'dms'=>'dms','ths'=>'ths','tasks'=>'taskboard','projects'=>'project','channels'=>'channel','contact'=>'contact','reservation'=>'reservation','profile'=>'profile','analytics'=>'analytics','energy'=>'energy','tasksheet'=>'tasksheet','tasksheet.shared'=>'tasksheet', default=>null })`, then `$viteEntries = ['resources/css/app.css','resources/js/app.js']; if ($moduleChunk) $viteEntries[] = "resources/js/components/alpine/modules/{$moduleChunk}.js";` and `@vite($viteEntries)`. The route names are the **exact** `->name(...)` values from `routes/web.php` (`'dms'`, `'tasks'`, `'projects'`, `'contact'`, `'channels'`, …) — NOT dotted (`dms.index`); a `match` arm that doesn't match the real name silently falls through to `default => null` and the chunk never loads. On `/dashboard` and home tabs `moduleChunk` is `null` → only `app.js` loads.

**Hover-warm prefetch (`components/alpine/module-runtime.js`'s `initModulePrefetch()`, called from `app.js` — explicit-init, not an import side-effect, so the 11 separate module-chunk bundles importing `registerModuleData` from this same file don't each re-bind these listeners and duplicate them on every module page):** a single delegated `pointerover`/`focusin` listener on `document` for `[data-module]` → injects a deduped `<link rel="prefetch" as="script" crossorigin="anonymous">` for `window.__moduleChunks[name]`. `pointerover` unifies mouse-hover and touch-tap warm; `focusin` covers keyboard. Dedup via a module-level `Set`. The URL map is emitted by `<x-dashboard.module-chunks/>` (`@json` of `Vite::asset("resources/js/components/alpine/modules/{module}.js")` per module, `try/catch`-guarded so a missing manifest entry never 500s the page) — a classic inline `<script>` in `<head>` that runs **before** the deferred `@vite` module scripts, so `window.__moduleChunks` exists when the listener fires. **Tag every module-link surface with `data-module="<chunk>"`**: static `data-module="taskboard"`/`"dms"`/`"ths"`/`"project"` on the left-nav `<a>`s; `:data-module="item.module"` on the menu modal `<a>` (`menu.js`'s `BASE_ITEMS` carry a `module:` field per lazy-route item — `processItem` spreads `...item` so the field survives; items without a lazy factory omit it and Alpine omits the attribute). One declarative attr per link, one global listener, no per-component JS.

**Never prefetch route HTML or Livewire payloads.** The established PWA rule (§4/§6) forbids serving cached HTML — a stale CSRF token → 419. The login worker already warms data; this layer warms only the **immutable hashed JS chunks** (SW-safe, the real parse-cut win), composable with that worker. `link rel=prefetch` warms the SW precache / HTTP cache for the chunk so the new-tab click (`target="_blank"`) reads it instantly; even with zero prefetch the route's own `@vite` entry guarantees synchronous registration, so the prefetch is a pure optimization, never a correctness dependency.

## 17. Tooltip singleton (`core/tooltip.js`) — one body-level node for every `<x-ui.modals.tooltip>` in the app

**Why it exists:** tooltip popovers rendered as absolutely-positioned spans inside their trigger's DOM subtree are physically clipped by any `overflow:hidden` ancestor (table cells, clipped cards) regardless of z-index — the concrete case was the reminder trigger clipped inside several modules' cards/rows after its 6-module rollout. The fix replaces per-instance popup DOM with ONE `position: fixed` singleton living at `<body>` level, so no clipping context can ever contain it. Blade keeps only an invisible contract holder (see `viewPattern.md` §8.16 for that half); this file owns resolution, placement, and lifecycle.

**Mechanics.** A single delegated `document.addEventListener('mouseover', …, true)` (capture, so `stopPropagation` consumers can't shield targets) walks from `e.target` up to `<body>`: first a direct-child holder via `el.querySelector(':scope > [data-tip]')` (the component is contractually placed as a direct child of its trigger — the holder itself is `display:none` and can never be the hover target, so it must be found by descent from an ancestor, never by identity-checking the walked element itself), then a `.group`-ancestor fallback via `el.querySelector('[data-tip]')` — the fallback preserves the old CSS `group-hover:` semantics where hovering anywhere on a reminder row showed that row's tooltip. Placement recomputes only when the resolved holder CHANGES (`holder === active` early-out), positions off `holder.parentElement.getBoundingClientRect()` with a 12px gap and 8px viewport padding-clamp, and plays the same fade+nudge entrance as the old CSS via a double-rAF (`set opacity:0 + nudge transform`, two frames later `opacity:1, transform:none`).

**Perf + lifecycle rules baked in:** the `.group` fallback's subtree scan is memoized per group element in a `WeakMap` (moving inside the same dense row/card never rescans; entries die with morphed-away elements, self-healing via an `isConnected` re-scan on a stale hit); the singleton is (re)appended lazily inside `show()` when `!tip.isConnected`, which is what survives Livewire's `wire:navigate` body swaps without any `@persist` or listener re-registration; `hide()` (mouse leaving any holder scope, plus `scroll` with `{capture:true}` — capture catches non-bubbling scroll on nested scroll containers — and `resize`) cancels both pending rAFs (`killFrames`) so a mid-entrance hide can't leave a ghost frame finishing on a stale anchor, and the double-rAF callback itself re-checks `active === holder` and re-reads the holder text at frame time (covers `x-text`-driven holders like the Google-translate footer chip changing label while hovered). Tooltip text is written with `textContent` only — never `innerHTML` — so slot/`x-text` content can't inject markup even if blade escaping were bypassed.

**Native `title=` adoption (2026-09-15, project-wide consistency).** The same walk also claims plain `title` attributes: on hover the attribute is migrated to `data-title` (and mirrored into `aria-label` when absent, so icon-only buttons keep their accessible name), removed from `title`, and shown through the singleton at `top` — HTML's own default placement. This kills the last native-vs-styled inconsistency and makes every hover label in BOTH panels clip-proof; migration is idempotent under Livewire morphs that re-add the attribute. Two hazards are handled in-code: **`title` is a LIVE binding** — ~20 blades rebind it via Alpine `:title` (row-actions pin/mute/tag), so the `data-title` branch re-reads a re-appearing `title` attribute and re-syncs instead of trusting the stale dataset value (without this you'd get a frozen label AND a double native+styled tooltip); **IFRAMEs are skipped** — an iframe's `title` is its accessible name, not a hover hint. Rule: never set both a `x-ui.modals.tooltip` holder child AND a `title` on the same trigger — the holder wins the walk and the native title silently survives (see `viewPattern.md` §8.16).

**Touch (tap) tooltips (2026-10-14).** The walk used to run on `mouseover` only, so on a phone a tooltip only appeared if the browser happened to emulate a hover. A second capture listener on `pointerdown` now handles `pointerType === 'touch'`: tapping a holder shows it, tapping the SAME holder again (or anywhere with no tooltip) hides it, and a `lastTouch` timestamp makes the emulated `mouseover` that follows within 600 ms a no-op so a just-hidden tooltip is not re-shown. A tap that lands inside an `a[href]` or `button` is skipped entirely (the tooltip must never sit over the action being tapped). Every other `title`/`data-tip` in the app (the avatar's dot and status badge included) gets mobile tooltips from this one change; scroll/resize still hide. Pinned in `core/__tests__/tooltip.test.js` ("touch (tap) toggling" — that group waits 650 ms between tests because the guard is module state).

**Admin panel wiring.** The singleton is needed on admin too (utilities/palette render hooks use the component), but admin never loads `app.js` — so `tooltip.js` self-invokes at module bottom behind a module-level `booted` guard (the `theme-manager.js` precedent): the explicit `initTooltip()` call in `app.js` is a no-op second boot, while the standalone admin registration — `resources/js/core/tooltip.js` in `FilamentServiceProvider::registerCoreScripts()` AND in `vite.config.js` inputs (its own `tooltip-*.js` bundle) — boots it on first import. The appearance classes must ALSO compile into `filament.css`: Tailwind v4's `@source '../**/*.js'` only covers `app.css`, so `resources/css/core/filament.css` carries an explicit `@source "../../../resources/js/core/tooltip.js"` line — without it the admin tooltip renders as an unstyled fixed div.

## 18. Livewire error toast bridge (`core/livewire-errors.js`) — precise Persian error messages in the user panel

**Why it exists:** a Livewire request that dies on a real exception (DB constraint, model missing, anything non-validation) previously failed silently from the user's perspective — Livewire v4's built-in behavior is a `console.error` plus a generic "an error occurred" modal, with the actual cause buried in `storage/logs`. The server half of this lives in `bootstrap/app.php` (see `bootstrap/bootstrapPattern.md`): a `withExceptions()` renderable turns any Livewire-request exception into JSON `{message}` built by `App\Services\ExceptionPresenter` — precise Persian title + body + `ERR-…` reference, same single source the admin Filament base pages use for their notifications.

**Mechanics.** The module registers one Livewire request hook behind a `booted` guard, self-invoking at module bottom (`tooltip.js` precedent) so the `app.js` init call is a no-op second boot. **The `fail` phase payload is `{status, content, preventDefault}` — NOT `{response, body, …}`** (verified: Livewire v4's dist maps `content: body`, `status: response.status` and never passes the response object — destructuring the wrong names silently kills the whole pipeline and shows only the hardcoded fallback). **422s pass through untouched** — validation is Livewire's own domain (inline field errors; `preventDefault()` would swallow the error-bag mapping). **419 became the session-self-heal (2026-10-15, production incident):** the earlier "let Livewire's page-expired modal handle it" stance turned out to be how a 3,000-entry CSRF storm was born — Oct 12's mass session death left stale tabs polling Livewire every 60 s (`:08`-second heartbeat cadence in the log) with dead tokens; each 419 was silently ignored and re-fired forever, logging an ERROR per poll until the tab was closed days later. Now the first 419 `preventDefault()`s Livewire's modal (which a background poll can't visibly surface anyway), toasts «نشست شما به پایان رسید؛ در حال بارگذاری مجدد…» once (module-level `reloading419` guard — burst requests share the one reload), and `window.location.reload()`s after 1.2 s; the reload lands on a GET (never 419s), so the user lands on login cleanly and the error storm dies with the first tick. Still scoped to the user panel only — admin keeps its existing behavior. Everything else gets `preventDefault()` (suppresses Livewire's generic modal), a `console.error` for developers, and the shared global toast (`window.dispatchEvent(new CustomEvent('toast', …))` with `type: 'error'`) — no new UI primitive, the existing `x-ui.modals.toast` component renders it. **User panel ONLY — not registered on the Filament admin panel (decision 2026-09-21):** the renderable in `bootstrap/app.php` skips `admin*` Livewire requests (`return null`), so admin Livewire failures keep Livewire's default modal (styled error page / Whoops) — never register this module for admin without removing that exclusion first, and never remove the exclusion without registering the module, or admin Livewire failures dump raw `{"message":…}` JSON into the default modal. Admin's precise-message path is the trait notifications, not this bridge.

## 19. Tool-widget z-stacking (`stores/toolStack.js`) — shared `backdrop.blade.php`, no per-widget wiring

**Bug found in QA re-audit (2026-10-02):** `radio`/`calculator`/`stopwatch` each render `<x-ui.modals.backdrop x-show="open">` — a `fixed inset-0` div hardcoded at `z-50`, declared as DOM siblings in a fixed order (`global.blade.php`). Opening a second tool while one was already open never brought the new one to front — paint order was decided by static DOM position, not by which was opened last, so the earlier-in-markup tool silently stayed on top while the one the user just opened kept running invisibly underneath.

**Fix is entirely in the shared component, zero changes to any of the three widgets' own `.js`/`.blade.php`.** `backdrop.blade.php` dropped its hardcoded `z-50` class for `:style="'z-index:' + ($store.toolStack.top === $el ? 50 : 49)"` plus `x-init="$watch(() => open, (v) => { if (v) $store.toolStack.top = $el })"`. `stores/toolStack.js` (one line, `Alpine.store('toolStack', { top: null })`, registered in `main.js` next to the other stores) holds a single shared reference — whichever backdrop's `open` most recently flipped true claims `top`, so it renders at 50 while every other backdrop drops to 49, below it but still under the navbar's `z-[51]` (never touch that relationship — the navbar staying clickable above any tool modal is intentional). Reactivity needs no manual listener/cleanup: writing to a `$store` property is itself tracked, so every mounted backdrop's `:style` binding re-evaluates automatically the instant `top` changes, including backdrops that aren't the one that just opened.

**Why a store and not a window CustomEvent:** a plain store write is inherently reactive to every reader with no dispatch/listen pair to register or leak-guard: each backdrop's `x-init` only ever touches its OWN scope (`$watch` on its own `open`), never reaches into a sibling — any 4th consumer of `backdrop.blade.php` gets correct stacking for free, no new listener to wire.

**Blast radius checked before shipping:** `backdrop.blade.php` has exactly 3 consumers (`calculator.blade.php`, `radio.blade.php`, `stopwatch.blade.php` — grepped, confirmed) plus `lightbox.blade.php`'s unrelated same-named `backdrop` *prop* (a different component, not a 4th caller). All three widgets' own test suites re-run clean after the change (138/138) — the fix is pure Alpine/CSS stacking order with no behavioral surface a JS unit test can exercise; verified by code trace instead (same standard as the earlier `confirmation.blade.php` `firing`-guard fix).

**Regression this introduced, found live (2026-10-04): a string `:style` clobbers `x-show`'s `display:none` on every OTHER mounted backdrop.** The original fix above bound `:style` to a STRING (`'z-index:' + (...)`). Alpine applies a string-valued `:style` by replacing the element's entire `style` attribute (`el.setAttribute('style', value)`), not by patching the one property — so whenever `$store.toolStack.top` changes (any tool opening), the `:style` effect re-runs on *all three* backdrops, including the two whose `open` is still `false` and whose `display:none` (set directly by `x-show`) lived in that same attribute. The write wipes it, and the closed widgets pop visible with no real `open` state change — then their close button, which only flips `open` (already `false` → `false`, a no-op), can never make `x-show` re-run to hide them again. Symptom matched exactly: opening one tool cascaded the other two open, un-closeable by their X.

**Fix: bind `:style` as an OBJECT, not a string** — `:style="{ zIndex: $store.toolStack.top === $el ? 50 : 49 }"`. Alpine's object form patches only the named CSS properties via individual `style.setProperty` calls and never touches `display`, so it can't fight `x-show` on the same element. This is the same pattern already used elsewhere in the codebase (`select.blade.php`'s `zIndex:9999`, `row-actions.blade.php`'s `background-color`) — **rule: any element carrying both `x-show` and a `:style` binding must use the object form, never a string, or a shared-store (or any other) write that re-triggers the binding will silently clobber the show/hide state.** The earlier "no behavioral surface a JS unit test can exercise" claim above was wrong in practice — this exact class of bug is real and was only caught by live reproduction, not code trace.

**4 more latent instances of this exact bug class found and fixed (2026-10-05), via a strict QA audit explicitly looking for the same `x-show` + string-`:style` shape elsewhere in the codebase:**
- `tab/calendar/now-line.blade.php` — `x-bind:style="'top:' + nowTop + '%'"` paired with `x-show="nowTop >= 0"` on the SAME element, both driven by the identical `nowTop` value. Highest-confidence live bug of the four: every time the now-line leaves its visible window (midnight rollover, or any day not containing "now"), both effects fire off the same change, and if `:style`'s effect ran after `x-show`'s, the clobber would make the line reappear with no real `nowTop>=0` state. Fixed → `x-bind:style="{ top: nowTop + '%' }"`.
- `components/dashboard/modal/menu/player.blade.php`'s hover-progress time tooltip — `:style` depended on `hoverProgress`, the SAME value gating its own `x-show="hoverProgress !== null"`. Same shape as the now-line case, same live-bug confidence. Fixed → `:style="{ left: \`clamp(24px, ${hoverProgress * 100}%, calc(100% - 24px))\` }"` (the object form's VALUE can still be a computed template literal — only the outer string-vs-object shape matters for the clobber).
- `tab/status/chart.blade.php`'s org-chart drag-cursor-hint (`:style` on `mouseX`/`mouseY`, paired with `x-show="hovering && !toolsOpen"`) and its 4-direction pan compass (`:style` on `toolsX`/`toolsY`, paired with `x-show="toolsOpen"`) — lower live-bug confidence than the two above since their `:style` dependencies (mouse position / pan offset) don't change in lockstep with their OWN `x-show` condition the way the two above do, but still the same risky shape and fixed identically for consistency with the now-documented rule.
- `livewire/dashboard/reminder/list.blade.php`'s teleported snooze popover (`:style` a fixed-position template literal on `top`/`left`, paired with `x-show="open"`) — lowest confidence (its `top`/`left` are only ever written in the same handler that also sets `open=true`, so no observed path triggers the clobber today) but the same latent shape, fixed proactively.

No JS unit-test surface for any of the four (pure Blade/Alpine attribute syntax, no `.js` file involved) — verified instead by re-running each affected module's Feature test class (`CalendarTest`, `StatusTest`, `ReminderTest`, `NavbarTest` — all green) to confirm the attribute-syntax change didn't break Blade compilation or rendering.

**Server-side exclusions (mirror rule):** `bootstrap/app.php`'s renderable deliberately lets `ValidationException`, `AuthenticationException`, and Filament's `Halt`/`Cancel` bubble — the two Filament exceptions never surface as errors (they're control flow), and validation/auth have their own handling. If a new "not really an error" exception type starts flowing through Livewire, add it to the renderable's exclusion list — never handle it client-side.

## 20. Race-condition checklist — client-driven async chains (companion to `.claude/skills/laravel-performance/SKILL.md`'s PHP-side version)

**The shape to watch for:** an Alpine method fires an async `this.$wire`/`this.$wire.$island(...)` call (or any Promise), then its `.then()`/post-`await` code mutates `this.*` state, DOM, or fires a follow-up call — using the `id`/closure data captured when the method was FIRST invoked. If the same method can be invoked again before the first call resolves, the first (now-stale) call's resolution can still fire and clobber state a second, newer invocation has already moved past. Symptom a user actually sees: a confirmation box closing itself, or the screen briefly flashing back to the wrong item, when clicking/switching quickly more than once.

**Before adding any guard code, rule out what's already safe — check these two first (full reasoning + Livewire-source line numbers: `app/Livewire/Dashboard/Channel/channelPattern.md`'s 2026-10-05 entries near the `selectChannel` fix):**
1. **Plain `wire:click="method()"` with no `$wire.$island()` wrapping needs no guard.** Livewire queues same-component actions itself — a second click's action is deferred until the first's request/response cycle completes, so they always resolve in click order. This is why tab-switching via `<x-ui.buttons.tab-selector>` (used by every module) is safe with zero JS-side protection.
2. **A button already carrying `wire:loading.attr="disabled" wire:target="methodName"` needs no guard either**, even for an island-scoped call — Livewire's loading/target matcher keys off the method NAME only, not the island, so every button sharing that target name (any row, any id) is disabled app-wide for the full duration one matching request is in flight. Confirmed real-world: `deleteMessage`/`doCancelInvite`/`doDeleteChannel` were all audited for this exact race and found already fully covered by their existing `wire:target` buttons — no code changed.

**Only when NEITHER applies** — a hand-rolled async chain with no disabling mechanism in front of it — add a closure-scoped sequence counter ("ticket"):
```js
export default function myFactory() {
    let fooSeq = 0;                       // one shared counter, OUTSIDE the returned object
    return {
        fooMethod(id) {
            const seq = ++fooSeq;          // this call's own ticket, frozen now
            this.$wire.$island('x').foo(id)
                .then(() => {
                    if (seq !== fooSeq) return;   // a newer call already moved the counter on — bail
                    this.someFlag = null;         // only the latest call's resolution ever gets here
                });
        },
    };
}
```
Each independent race-prone method gets its OWN dedicated counter — never reuse one method's counter for an unrelated method, or an unrelated action would spuriously invalidate an in-flight call it has nothing to do with.

Full Project-side narrative: `app/Livewire/Dashboard/Project/projectPattern.md`.

## 21. Declutter mode wiring — one localStorage pref, one html class, one window event (2026-10-05)

Companion to `viewPattern.md` §8.32 (the Blade/CSS side). Three JS pieces:

1. **`data/menu.js` — `toggleDeclutter()`**: `declutter: false` state, loaded in `init()` via `_loadState('menu_declutter', false)` (`persistentStateMixin` stores JSON — the head script's `=== 'true'` string compare matches the serialized boolean). The toggle flips the state, mirrors it onto `document.documentElement.classList` ('declutter'), persists via `_saveState`, and dispatches `window.dispatchEvent(new CustomEvent('declutter', { detail: { on: this.declutter } }))` — the established cross-component channel (same shape as `audio-pause-request`). No Alpine store: the only reactive consumer is the toggle button's own `:class`/`x-text`/`:aria-pressed` inside the same `menu()` instance.
2. **`public/js/mode-manager.js` — pre-paint assertion**: `localStorage.getItem('menu_declutter') === 'true'` toggles `html.declutter` in the same head IIFE that asserts dark/theme (§8.3 in viewPattern.md). Without it, a decluttered reload flashes the full navbar before Alpine boots. One head script per app — the key was ADDED to mode-manager, no new `<script>` tag.
3. **`data/mobile.js` — the bottom-navbar listener**: factory-scoped `_declutterAc` (`AbortController`, created in `init()`, aborted in `destroy()`) signals the `window.addEventListener('declutter', ...)` — the standard window-listener cleanup idiom for data factories. Handler contract: bail unless `e.detail.on !== undefined`; ON → stash the current `labelPreset` in `_preDeclutterPreset` (only if not already smart) and `setLabelPreset('smart')`; OFF → restore the stashed preset, or fall back to `'all'` when nothing is stashed (the reload case: declutter persists via `menu_declutter` but the in-memory stash does not, so a fresh instance de-decluttering after reload must still land on a plain non-smart preset — user decision 2026-10-05), then clear the stash either way; a second declutter-ON after a manual preset change re-stashes the NEW preset (session-scoped by design since `setLabelPreset` itself persists to `btm-labels`).

**Glyph note (updated 2026-10-15):** the toggle was switched to `unfold_less` / `unfold_more` with the same `rotate-90` as the three chat surfaces' declutter pills/chips — identical iconography across the hamburger modal and channel/contact/project (the former `top_panel_close` / `top_panel_open` glyphs were verified present in the SERVED font (`public/build/assets/material-symbols/material-symbols-rounded.woff2`, fontTools `getGlyphOrder()`), never the 0-byte decoy under `resources/assets/fonts`; the current glyphs are proven in production via the modules themselves). Any new Material Symbols ligature goes through that same served-font check before shipping. **Chat-header bridge (2026-10-15):** this event now also collapses the channel/contact/project headers programmatically — see the `headerDeclutter.js` menu-bridge note in the chatBase test entry (§ tests). **Forced-collapse never persists (2026-10-15):** the bridge's `apply(on)` sets `_menuForced` and `headerDeclutter` at runtime only (persisting solely on OFF), and `_persistChatSettings` in `chatBase.js` and `data/project.js` stores `headerDeclutter && !_menuForced` — the menu-forced `true` must never reach `chat-settings:project|channel|contact`, otherwise an OFF issued in another tab/page (the menu opens modules via `target="_blank"`, and the `declutter` event is per-window) leaves the header collapsed forever, since boot only mirrors `menu_declutter === 'true'`. The header's own `toggleHeaderDeclutter()` clears `_menuForced`, so manual choices stay per-module and persist normally.

**Table toolbar mixin (2026-10-15):** `mixins/tableTools.js` — `tableToolsMixin(scope)` composes `persistentStateMixin()` + the untouched `headerDeclutterMixin()` (same composition shape as `data/taskboard.js`), adds `initTableTools()` (loads the bare-boolean key `table-tools:{scope}`; no key = expanded on every breakpoint (phones included, so the floating search stays reachable); then creates `_tableToolsAc` (an `AbortController`) and registers `headerDeclutterMenuBridge(signal)` — the bridge's `signal` argument is optional, so the chat modules keep calling it bare) and `_persistChatSettings()` writing `headerDeclutter && !_menuForced`, so the hamburger-forced collapse is never stored while a manual collapse/expand and the bridge OFF are. `destroyTableTools()` clears the pending `_declutterTimer` and aborts `_tableToolsAc` (detaching the `declutter` window listener); every consumer calls it from its own `destroy()`. Test: `mixins/__tests__/tableTools.test.js` (10 tests, one master file).

**Maximize trap — root cause and rule (2026-10-16):** a `.max-widget` / `.max-widget-column` / `.max-backdrop` is `position: fixed`, which resolves against the nearest ancestor with a non-`none` `transform` (also `filter`, `perspective`, `will-change: transform`, `contain`, `content-visibility`). The structural entrance rules `.page-wrapper > div > *:nth-child(1|2|3)` (and their `> div > *:nth-child(1|2|3)` grandchildren) in `dashboard.css` (inside `@layer components`) used `animation: slideUpFade … both`; fill-mode `both` keeps the finished animation applied, so those wrappers (TaskBoard columns 1-3 via `.spotlight-item`, the Reservation avantgarde root) stayed containing blocks and confined the overlay (computed `matrix(1,0,0,1,0,0)`; a `to { transform: none }` keyframe does NOT help — the filled animation still yields an identity list). Fix: those six rules use fill-mode `backwards`. **Rule:** entrance animations on wrapper elements use `backwards`; only exit keyframes (`fadeOut`, `slideFadeToLeft`, `slideScaleOut`) keep `forwards`; a maximizable element must be the animated grandchild itself (DMS/THS) or sit outside that selector (Channel/Contact/Project). Guard test: `mixins/__tests__/maximizeCss.test.js` (no `both`/`forwards` in `.page-wrapper` animation rules). Do NOT reintroduce JS that rewrites ancestors' inline styles (a removed 2026-10-16 workaround: it ran with `$el` = the clicked button, never reverted, and hid the CSS bug). Dropped `will-change` from `.max-widget` and `#header, #navbar, #footer` (permanent compositor layers; the transitions/animations promote on their own). **Restore timing (2026-10-16):** `initMaximize()` now runs the restore inside `$nextTick`. Modules whose content is lazy-loaded (TaskBoard, Energy chart, Feed/Home panes) are initialised by Livewire's morph BEFORE their children are attached, so a `restoreMaximize` that looks up `[data-widget]`/`[data-column]` at init saw none and its "not found" branch deleted the stored `max:<scope>:<uid>` key — the maximized widget never survived a reload. The deferred restore also lets Reservation's stale-max guard (same tick, registered after it) see the final DOM. Test: `maximize.test.js` "deferred restore". **Local declutter footer:** `headerDeclutterMenuBridge()` toggles `html.declutter-local` (initial sync + `$watch('headerDeclutter')`, cleared on the AbortController abort and on `livewire:navigating`); `dashboard.css` hides the footer's `data-declutter-hide` children for `html.declutter-local #footer`, so every consumer (Project/TaskBoard/Channel/Contact/DMS/THS/Reservation) loses the footer under its own header-collapse as well as the hamburger declutter. Test: `tableTools.test.js` "local declutter hides the footer". The Reservation `init()` also guards a stale restored `max`: when no `.reservation-command-table` is on the page (classic view), it clears `max`, the persisted key and the layout classes.

**Profile settings panel (2026-10-16):** the «جدول‌ها» tab (`data/settings.js`) is a per-module control panel. `TABLE_MODULES` (`dms`, `ths`, `reservation`, `taskboard`; each `{ id, label, cols, colsLabel? }`) drives `refreshTableState()`, a `tableState` snapshot (`modules[id] = { hiddenCols, toolbarCollapsed, maximized }`, plus `compact` and `menuDeclutter`) rendered as state chips; `resetTableModule(id)` resets the column mask, `table-tools:{id}` and `max:{id}:{uid}`; `resetDensity()` / `resetDeclutter()` (writes `menu_declutter=false`, drops `html.declutter`, dispatches the `declutter` window event that `menu.js` listens to and mirrors into its own `declutter` flag) and `resetTables()` (all of them). `EXPORT_KEYS` carries the four `*-col-hidden` and `table-tools:*` keys plus `menu_declutter`. Test: `data/__tests__/settings.test.js`.
