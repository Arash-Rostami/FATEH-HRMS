# View Layer Architecture

Structural organization of the view layer: boundaries between reusable UI primitives, domain components, and page-level compositions.

---

## 1. Components (`resources/views/components/`)

```
components/
├── admin/
├── auth/
├── dashboard/
└── ui/
```

### 1.1 UI Components (`components.ui.*`)
Design system primitives with zero business logic. Dedicated subdirectories for variant families (`ui/buttons/`, `ui/modals/`, `ui/forms/`); root `ui/` for singletons.

| Criterion | UI Location | Domain Location |
|-----------|-------------|-----------------|
| Cross-domain utilization | Required | Prohibited |
| Business logic coupling | None | Present |
| Eloquent model dependency | None | Allowed |
| `config()` or `auth()` references | None | Allowed |

```blade
<x-ui.buttons.form variant="primary">Submit</x-ui.buttons.form>
<x-dashboard.modal.badge-legend :groups="$badgeLegendGroups" />
```

#### 1.1.1 Opt-in Behavior Composition (`maximizable`)
Share a stateful Alpine/Livewire behavior across multiple `ui.forms.*` primitives without duplicating it per-component. Two small partials — `ui.forms.maximize-trigger` and `ui.forms.maximize-overlay` — are included by any host that declares the shared `x-data` scope. The host (`input`, `textarea`, `search`) takes a `maximizable` prop (default `false`); only when true, wraps its root with `x-data="{ value: @entangle($attributes->wire('model')->value() ?? '').live, fullscreen: false }"` plus `wire:ignore.self` — deriving the entangled property from the `wire:model` attribute already on the tag (same technique `select.blade.php` uses), so no separate `model` string prop is needed. Apply only to genuinely long-form free text (bio, descriptions, decision notes) — never short structured fields.

```blade
<x-ui.forms.textarea label="شرح پیشنهاد" name="form.descriptionSelf" wire:model="form.descriptionSelf" :rows="5" :maximizable="true"/>
```

#### 1.1.2 Image gallery maximize (teleported fullscreen viewer)
Click any image in a media grid to open it fullscreen with prev/next navigation. Multi-image grid+prev/next lives in `livewire/dashboard/tab/feeds/media.blade.php`; single-image fullscreen variants (`tab/posts/details.blade.php`, `tab/reports/cards.blade.php`) use a simpler `imageViewer` bool with no prev/next.

- Per-grid Alpine scope `x-data="{ open: false, index: 0 }"`; each cell `@click="index = N; open = true"` with `cursor-zoom-in`. Videos stay inline (`<video controls>`) and are **excluded** from the viewer.
- Viewer is the shared `<x-ui.modals.lightbox>` component (§8.15) — `state="open" z="z-[99998]" backdrop="bg-[var(--md-sys-color-primary)]/90"`, so never clipped by ancestor `overflow-hidden`. Close via `@click.self` backdrop, close button, or `@keydown.escape.window`.
- `FeedPresenter::mediaGrid()` splits `$items` (all, for the grid) and `$images` (non-videos, for the viewer). Walk `$items` with an image-only counter so each click target equals its position in `$images`; gate each cell with the global `isVideo($url)` helper on the loop variable — videos get `<video controls>` and are skipped from `$images`.
- Grid sizing: `grid-cols-2` alone leaves rows auto-sized to intrinsic height, so a 4-image set's second row overflows `overflow-hidden`. Fix with explicit `grid-rows-{{ $rows }}` plus definite height (`h-[400px]` multi-row, `h-[320px]` single) so rows share space equally (`minmax(0,1fr)`).
- Multi-image prev/next wrap modularly: `index = (index - 1 + total) % total` / `index = (index + 1) % total`; render arrows only when `count($images) > 1`. Per-include `x-data` means each card has its own independent viewer. Reuse `animate-lightbox-in`.

### 1.2 Domain Components (`components.{admin,auth,dashboard}.*`)
Controller-less Blade compositions for specific business contexts. May interact with services, repositories, or Presenters; not for cross-domain reuse. Flat structure by default; as soon as a cluster outgrows one or two related partials, nest them in the shell's own subfolder — the shell/entry component itself stays at the domain root (nesting `menu.blade.php` inside `menu/` would force the double-tag `<x-dashboard.modal.menu.menu>`), and partials drop their shell-prefix inside the folder (`menu-item` → `menu/item`). Canonical: `components/dashboard/modal/menu/{item, player, audio-toggle}.blade.php` under the `modal/menu.blade.php` shell.

## 2. Livewire Components (`resources/views/livewire/`)

Mirrors `App\Livewire\` namespace: `livewire/{admin,auth,dashboard}/`.

| Aspect | Convention |
|--------|------------|
| **Primary view** | `livewire/{domain}/{Module}.blade.php` — stays at the parent level, never moves into the partials folder |
| **Controller** | `App\Livewire\{Domain}\{Module}.php` |
| **Partials** | **Cardinal rule**: any partial belonging to `{Module}` lives in a same-named sibling folder — `livewire/{domain}/{module}/{partial}.blade.php` — never flat-prefixed co-location (`{module}-{partial}.blade.php`), and never gated by a file-count minimum; even a single partial gets the subfolder. The partial's filename drops the module prefix entirely, since the folder already supplies that context (`report/summary.blade.php`, not `report-summary.blade.php`). Matches `tab/posts/`, `tab/reports/`, `project/report/`, `project/analytics/`, `project/activity/`, `project/calendar/`, `project/kanban/`. |

Extract a partial only when the component exceeds 150 lines, a section needs conditional inclusion, or logic is reused within the same domain — that threshold decides whether to extract a partial at all, never where an already-extracted partial goes (always the module's own subfolder, per the cardinal rule above). Anti-pattern: strict separation under 100 lines creates navigation friction.

---

## 3. Error Views (`resources/views/errors/`)

HTTP error pages (401/403/404/405/419/429/500/503) extend `errors.layout` — a dedicated standalone HTML shell with its own theme bootstrap + Vite CSS, **not** `layouts.app`. Using a separate shell avoids recursive failures in shared chrome (e.g., database-dependent navigation) when the error itself stems from that chrome. Domain error views outside the HTTP set (e.g. `document-not-found.blade.php`) extend `layouts.app` with `@section('minimal_layout', true)` to suppress header/sidebar/footer.

---

## 4. Layouts (`resources/views/layouts/`)

Centralized orchestration for HTML document structure, asset pipeline inclusion (Vite, Livewire), global component injection, and render slot flexibility.

```blade
@isset($slot)
    {{ $slot }}
@else
    @yield('content')
@endisset
```

The `@else` branch is a legacy yield for backward compatibility — kept so non-component views still resolve `@section('content')`.

Layout auto-includes cross-cutting concerns: confirmation modals, toast notifications, background elements, and header/footer (unless `minimal_layout` is set).

**Auth layout per-browser background (`layouts.auth`, the single ⚙ "تنظیمات پس‌زمینه" dropdown).** One button, one panel at the former wallpaper-panel width (`min-w-[250px]`): the personal-background content first (browser-local note, تصویر/ویدیو pickers with sizes + delete, caps note, error note), then a hairline divider, then the two video settings in order — `video-loop` switch first, brightness slider last. The separate `wallpaper` icon is gone. Users upload a personal login-page image/video stored as a raw Blob in IndexedDB (`auth-media` DB, `media` store, keys `image`/`video`) — never sent to the server, per-browser only, so it does NOT follow the account across devices. IndexedDB, not localStorage, is load-bearing: localStorage caps at ~5MB and stores strings only, which kills video; IndexedDB holds Blobs at hundreds of MB. Caps live in `pickMedia()` (5MB image / 20MB video — deliberately tight; the check runs before the blob is ever written to IndexedDB, so an oversized pick is rejected with a note and stored nowhere). The persisted `video-loop` pref (`loopVideo`, default on) works via the single `if (!this.loopVideo) return;` guard at the top of `swap()` — both end paths (the `@ended` handler and `check()`'s near-end fade trigger) route through `swap`, so one lever stops ALL looping; with loop off the video plays once and freezes on its last frame (toggling loop back on after the freeze does not auto-resume; pause/play restarts it). Custom video replaces the `videos` array (the 2-element crossfade handles a single entry — `preroll` falls back to the same index and crossfades to itself); custom image binds over the default `<img :src>`; delete restores `mediaDefaults`. The `init()` order `loadMedia().finally(() => initVideo())` matters: `mediaDefaults` snapshots the config video list synchronously on the first line of `loadMedia()`, before the first `await`, so `clearMedia('video')` can never observe a null default list. Three review-caught gotchas: (1) the background `<img>` carries BOTH the static `src` and the `:src` override — stripping the static `src` moves the page's LCP fetch behind Alpine's deferred boot, delaying paint on every login for a feature one browser in thousands uses; Alpine overwrites `src` with the identical default URL on init, so the pair costs nothing. (2) `initVideo(revokeUrl)` revokes a replaced video's old object URL only after the new source's `play()` resolves — revoking earlier leaves a prerolled `preload='auto'` element mid-fetch on a dead URL (WebKit breaks mid-progressive-fetch). Both the replace path (`pickMedia`) and the delete path (`clearMedia`) pass the old URL through this param. Accepted residual: when `initVideo` early-returns (no default videos, or video paused), the passed URL is never revoked — bounded by the login page's short lifetime, accepted over a revoke-then-swap hazard. (3) `initVideo()` pauses both `<video>` elements and `clearTimeout`s the crossfade's `_t1`/`_t2` before restarting — that pause is what makes a stale in-flight `swap()` benign: a pending `play()` promise rejects (AbortError) when paused, routing the continuation into `swap()`'s `.catch` instead of letting it pause the newly-started video and flip `active` to a stale index. Buffer-readiness gating (2026-09-08, the haphazard-stutter fix): first play always goes through a `canplay` listener (never a `readyState >= 3` fast path — assigning `v.src` does not synchronously reset `readyState` in Chromium, so a fast path fires against the PREVIOUS resource on the media-replacement re-init) and `check()` only fires the crossfade when the NEXT element also has `readyState >= 3` — `@ended="swap(i)"` stays as the last-resort fallback; without the gate, a cold-cache crossfade lands on an unbuffered element that freezes mid-fade. `canplay` (state 3), not `canplaythrough` (state 4), matches the crossfade gate — canplaythrough can hang indefinitely on throttled networks. The `error` listener is a FALLBACK, not a start retry: it flips `useVideo = false` so the static `<img>` renders instead of a black background. The old `revokeUrl` is revoked in `play().finally()`, not `.then()` — a rejected `play()` (autoplay denial) must not leak the replaced video's blob. The source mp4s must keep moov-at-front (`ffmpeg -movflags +faststart` remux, byte ~36): a moov-at-end file forces the browser to download the whole file before the first frame, which reads as the same stall and a reload appears to "fix" it via HTTP cache. **Bandwidth budget (2026-09-08):** the two default `fateh` loops were re-encoded from ~4.4–5.1Mbps down to ~2.5–3.1Mbps (`ffmpeg -crf 23 -preset slow -an -movflags +faststart`, audio dropped since the `<video>` tag is always `muted`) — the prior bitrate demanded near-5Mbps sustained throughput just to keep up in real time, and `preroll()` used to be called unconditionally right after wiring the `canplay`/`error` listeners, so the *next* video started fetching in the same tick as the *first*, roughly doubling that demand on cold load. `preroll(1)` now fires from inside `start()` (i.e. only once the current video's `canplay` has actually gated it into playback) instead of immediately after listener wiring — the two videos no longer race for bandwidth on the initial load. Any future default video added to `config/tenants.php` should be encoded the same way (CRF ~23, no audio, faststart) rather than dropped in at whatever bitrate the source export used.

## 7. Anti-Patterns to Avoid

1. Deep nesting: max 3 levels (`domain/sub-component/file`)
2. `.index` suffix: use `footer.blade.php`, not `footer/index.blade.php`
3. A generic `partials/` subfolder, or flat-prefixed co-location (`{module}-{partial}.blade.php`) instead of the module's own same-named subfolder (§2's cardinal rule) — every partial goes in `{module}/`, regardless of count
4. Business logic in UI: move to domain or Livewire controller
5. Generic naming: `components.partials.card` → `components.ui.card`
6. `rounded-full` on an icon-container badge (a small box wrapping one Material Symbol icon — lock overlays, status/disabled overlays, decorative icon chips): this app's icon-container convention is the soft-rounded scale (`rounded-lg`/`rounded-xl`/`rounded-2xl`, sized to the box), never a full circle. `rounded-full` itself is fine and common elsewhere (toggle tracks/knobs, avatars, dots, pill-text badges) — the anti-pattern is specifically an icon-container badge defaulting to circular, a recurring drift corrected 2026-09-11 in `navbars/top/ai-assistant.blade.php` and `modal/{menu,menu-item}.blade.php`'s lock badges.
7. **Hand-rolling markup that a `components/ui` family already expresses** — raw `md3-btn` buttons, `md3-input-group` floating-label stacks, `animate-pulse` shimmer divs, teleported fullscreen/lightbox shells, filter-popover wrappers, duplicated cross-module search inputs. **Before writing any such markup, grep `resources/views/components/` first — if a component expresses it, adopting is mandatory; a copy-paste divergence is a defect** (the 2026-09-14 audit found 5 such copy-paste families, all extracted to `<x-ui.modals.lightbox>`, `<x-dashboard.timeline-{date-bubble,caption}>`, `<x-ui.forms.date-span-popover>`, `<x-dashboard.member-search>` — see §8.15). If no component fits but the same shape appears in (or is destined for) more than one module, promote it to the right component family rather than leaving it in one module's folder. Enforced mechanically by `tests/Feature/ViewConventionTest.php` — a tripwire that scans every `livewire/`+`layouts/` blade file for the known bypass smells and fails on any file not in the committed baseline allowlist (the known legacy bypasses: raw auth forms, inline module shimmers, kanban/taskboard input groups). A new bypass makes the suite red until either adopted or allowlisted with a justified reason. **Visible checkboxes are in this family since 2026-09-21 (§8.22): a styled `<input type="checkbox">` in a user-panel view must be `<x-ui.forms.checkbox>` (inline/settings rows) or `<x-dashboard.member-picker>` (member-selection lists) — hand-rolling either is the same defect class as a raw `md3-btn`. Switches are in the family too (§8.23, same day): a sr-only-checkbox toggle track must be `<x-ui.forms.switch>`. Only `sr-only` checkboxes driving custom visuals (cards/chips, not switch tracks) and the allowlisted taskboard checklist survivor are exempt. Modal/panel/widget close buttons joined the family the same day too (§8.22/§8.24): any `<button>`/`<div>`/`<span>` whose job is "close this overlay" must be `<x-ui.modals.close-button>` — the audit that added this found instances with no `<button>` tag at all (not keyboard-focusable) and one with raw inline `style="...rgba(...)..."` plus a hardcoded Tailwind color instead of an MD3 token (`ai-assistant.blade.php`), which is also a §"Anti-Patterns" #8 violation below, not just a component-family bypass. `ViewConventionTest.php`'s `'-space-x-1.5 rtl:space-x-reverse'` smell row guards the overlapping-avatar-stack shape (§8.21) the same way.**
8. **Glassmorphic card/panel styling (`backdrop-blur-*` + translucent `bg-[...]/NN%`, `rounded-3xl`, diffuse colored shadows) outside its two deliberately-scoped homes.** The default card/panel language everywhere else in the user panel is a flat, opaque MD3 surface: `rounded-2xl`, solid `bg-[var(--md-sys-color-surface)]`/`bg-[var(--md-sys-color-surface-container-low)]` header fill, flat `shadow-sm`, full-opacity `border-[var(--md-sys-color-outline-variant)]`/divider tokens (no `/NN%` fade) — this is what Report/Kanban/Activity/Workflow/TaskBoard/Calendar's own tables all use. Glass/blur is reserved for: (a) Project Calendar's month-grid day-cells + overdue banner (a separate, deliberately-documented design from the 2026-08-27 UI rework — colored depth shadows, not blur), and (b) the shared `.analytics-card` CSS class (`dashboard.css`) used identically by both Project's and the sitewide HR analytics dashboards. **A new card/table/panel defaults to the flat style; reach for glass only if extending one of those two named exceptions, never as a fresh design choice** — Project Calendar's 3 tabular panels (timeline/agenda/Gantt) drifted into glass independently of the rest of the module and were flattened back to match Report on 2026-09-21 specifically because of this; that one stays fully flat.

**Third named exception, user-decided (2026-09-21): the GLOBAL shared-events calendar (`tab/calendar.blade.php`, `App\Livewire\Dashboard\Tab\Calendar` — NOT Project's own Calendar tab above, a different module) keeps a translucent bg + colored shadow, but deliberately drops `backdrop-blur`.** It was flattened the same day as part of a broader sweep; the user asked to see the glass version again, kept the translucent `bg-[color-mix(in_srgb,var(--md-sys-color-surface)_92%,transparent)]` + colored `shadow-[0_8px_32px_color-mix(in_srgb,var(--md-sys-color-primary)_25%,transparent)]` + dark-mode override (`dark:bg-[var(--md-sys-color-surface)] dark:shadow-[0_12px_40px_rgba(0,0,0,0.6)]`) for the visual weight, but had `backdrop-blur-xl` removed once side-by-side comparison showed it wasn't the load-bearing part of the look — translucency + the primary-tinted glow shadow alone read as "impressive" against this module's plain, mostly-static background, at a fraction of the compositor cost (`backdrop-blur` forces its own paint layer, re-composited on every scroll/repaint behind it; a translucent bg + `box-shadow` do not). Radius was also normalized (`rounded-[2rem]` → `rounded-2xl`). Final state across all 3 view panels (month/week/day): translucent bg + shadow + `rounded-2xl`, no blur. **Do not add `backdrop-blur` back here, and do not flatten the bg/shadow to fully opaque either** — both were deliberate, explicitly-tested decisions, not drift. Don't confuse this module with Project's own Calendar tab (different file, different module, fully flat, no exception at all).

## 8. Shared component patterns

### 8.1 Shared empty-state (`<x-ui.empty>`)
One design-system component for **all** user-panel empty-states. Props: `icon` (required), `title` (required), `description?`, `variant?` (only `'welcome'` is special-cased; `'list'`/`'filtered'`/`'search'`/`'default'` all fall through to the default list style), `fill?` (bool — `h-full w-full` instead of default `h-64`), `watermark?`, `animate?`. With no extra props it renders byte-equivalent to the original inline empty-states, so adopting is a pure substitution. Keep genuinely special cases inline (gallery filtered-overlay, contact welcome panel). Profile onboarding/credentials wrap it in a dashed-border card. Reach for `<x-ui.empty>` first; fall back to inline only when the empty-state has structure the component cannot express. Its icon badge uses `rounded-2xl` (never `rounded-full` — same no-round icon-container rule as the rest of the panel; 2026-09-14). Settled conventions (2026-09-14 consistency sweep): (a) main-content **thread/conversation empties** use `<x-ui.empty>` like every other module (`ths/workspace` reply thread, `tab/feeds/comments`, `taskboard/form` conversation) — only field-level/control-level empties that are too small for the `h-64` illustration stay compact inline (e.g. `taskboard/meta-fields` custom-data, dropdown rows); (b) the member-picker exhaustion notice ("کاربر فعال دیگری برای افزودن وجود ندارد." in `channel/create`, `channel/manage-members`, `project/form`) also uses plain `<x-ui.empty icon="group">` — the former `x-dashboard.empty-member-options` component was deleted in the same sweep; the one-notice component is now `<x-ui.empty>` itself.

### 8.2 Solid-button dropdown for filters
The gallery month filter is a **solid button opening a dropdown on click** — not chips, not native `<select>`. Wrapper: `x-data="{ open: false }" @click.outside="open = false"`; button `@click="open = !open"` with `:class="open || month ? 'primary-bg' : 'surface-container-highest'"`; popup `x-show="open" x-transition x-cloak` listing options that set the Alpine `month` var and `open = false`. Matches the reports card/list solid segmented-toggle visual language. Use this shape for any single-dimension filter picking one value from a short list.

### 8.3 Pre-paint theme bootstrap (`public/js/mode-manager.js`)
Dark mode is class-based (`@variant dark (&:where(.dark, .dark *))` in `app.css`, palette vars in `core/theme.css` keyed on `:root.dark` / `[data-theme='x'].dark`), so the page is dark **only when `.dark` is on `<html>`**. The toggle in `resources/js/core/theme-manager.js` loads as a deferred `type="module"` via `@vite` — executing *after* first paint, causing a light→dark flash (FOUC) on cold load, hard refresh, and `wire:navigate` transitions. Fix: `public/js/mode-manager.js` — a standalone IIFE that reads `localStorage('user-mode')` (fallback `matchMedia('(prefers-color-scheme: dark)')`) and `localStorage('user-theme')` (fallback `'default'`) and sets `.dark` + `data-theme` on `documentElement` synchronously. Included in `layouts/app.blade.php` `<head>` as a **plain classic `<script src>` before `@vite`** (`<script src="{{ asset('js/mode-manager.js') }}"></script>`) — never via `@vite` (would emit `type="module"` deferred → re-introduce flash). Filament admin gets the same tag at `PanelsRenderHook::HEAD_START` in `FilamentServiceProvider::registerThemeBootstrap()`. Auth layout is intentionally not covered. The file lives directly under `public/js/` (NOT `public/build/`, NOT a `viteStaticCopy` target, NOT a Vite entry) so Laravel's web server serves it at `/js/mode-manager.js` in dev and prod with no build step, manifest, or hashing. Classic head scripts re-execute on `wire:navigate`, so SPA nav is covered. `ThemeManager` stays unchanged — re-applies idempotently, owns Alpine-store sync and cross-tab `storage` listeners. Rule: any client-resolved, paint-affecting state must be asserted by a render-blocking classic script in `<head>` before the deferred `@vite` bundle; ship as a static `public/` asset (not through Vite); reuse existing storage keys, never add a parallel mechanism.

### 8.4 In-page tools survive navigation (`@persist` + new-tab module links)
Dashboard tools (radio/calculator/stopwatch in `components/dashboard/tools/*`, Alpine `x-data` whose minimized pills `x-teleport="#tool-dock"`) live in the **layout** via `components/dashboard/global.blade.php` (included by `layouts/app.blade.php`), outside the page slot — so in-place tab swaps (`switch-tab`) never touch them. Rule: **a module either opens in-page (SPA, tools preserved) or in a new tab (full reload, originating tab's tools untouched) — never a same-tab full reload that kills the tools.** (1) The **menu modal** (`components/dashboard/modal/menu.blade.php`) uses plain `<a href>`, so route items get `:target="item.disabled || item.href === '-' ? '_self' : '_blank'"` + `rel="noopener"` — in-page tools (`href:'-'`, which `handleItemClick` `preventDefault`s + `$dispatch`es) stay `_self`; every route item opens a new tab, leaving the dashboard tab's radio playing. Matches the left-sidebar (`navbars/left.blade.php`) and account-dropdown `target="_blank"` convention. (2) **SPA navigation** (command palette `navigate:true`, `wire:navigate` chips, profile back-to-dashboard link) swaps the body and would re-init tools — so the 3 tool includes + `#tool-dock` are wrapped in `@persist('dashboard-tools') ... @endpersist` inside `global.blade.php`; Livewire v4 caches that subtree across `wire:navigate`, preserving Alpine state, window listeners, and the detached `new Audio()` (radio audio keeps playing). `#tool-dock` MUST stay inside the same `@persist` region as the tools. Toast/occasion stay outside `@persist`. ### 8.7 `<x-ui.hover-popover>` — `@click.away` across `x-teleport` (real bug, fixed 2026-08-30)
The popover's body renders via `<template x-teleport="body">`, physically reparenting that DOM node to be a direct child of `<body>` — outside the wrapper `<div>`'s subtree. Putting `@click.away="open = false"` on the wrapper (as originally written) breaks the instant the body holds anything interactive: Alpine's `.away` semantics close whenever the click target isn't a descendant of the element carrying the directive, and after teleport nothing inside the popover body qualifies as a descendant of the wrapper anymore — so clicking a `<select>`, a button, anything inside the popover closes it immediately. Symptom reported by a user as "the popover doesn't stay open / jumps the instant you click." **Fix:** put `@click.away` on the teleported div itself instead, guarded against the trigger: `@click.away="if (!$refs.trigger.contains($event.target)) open = false"`. Alpine's teleport preserves the original component's scope (`$refs` still resolves across the reparented node), and `Node.contains()` includes the element itself, so a second click on the trigger while open doesn't double-fire a close. Any future consumer of this component with clickable content in the `body` slot relies on this fix — don't move `@click.away` back to the wrapper.

**Known limitation, not yet fixed:** the teleported body is `position: fixed` with `left`/`right`/`top` computed once from `getBoundingClientRect()` at open time and a fixed `w-*` width — there is no viewport-clamping. A trigger near a screen edge on a narrow viewport can push the popover partially off-screen with nothing to reflow it back. Pre-existing, app-wide (affects every consumer: `taskboard/card.blade.php`, `taskboard/column.blade.php`, `project/kanban.blade.php`, `tasksheet/header.blade.php`, `tasksheet.blade.php`), not something any single consumer should patch around locally — fix once in the shared component if it becomes a live complaint.

**Content accuracy rule:** copy must be re-derived from the actual gating code (`@if($isOwner)` guards, model scopes, enum `getLabel()`/policy classes) each time — e.g. `reservation/legend.blade.php`'s `CancelledAdmin` row text is sourced from `CancelAction::execute()`'s `$user->hasElevatedRole()` branch, not a guess.

### 8.8 `<x-ui.modals.base>` never visually opens a modal that starts already-open on first paint (real bug, fixed 2026-08-30)

`components/ui/modals/base.blade.php`'s `x-init` only sets the `active` class via `$watch('show', v => { if (v) requestAnimationFrame(() => requestAnimationFrame(() => active = true)) ... })` — and Alpine's `$watch` callback fires only on a subsequent reactive *change*, never for the value a property already holds at initialization. `.custom-modal` itself is `width:0;height:0` and its content `opacity:0` until `.active` is added (`dashboard.css`), so as long as `show` transitions `false → true` after mount (the ordinary case: a `wire:click` sets `isModalOpen = true` on an already-rendered page), the watcher fires and the modal appears correctly. But when a component mounts with the bound property **already `true` on its very first render** — e.g. a `#[Lazy]` component's real (post-placeholder) mount, or any server-side code path that sets `isModalOpen = true` before the first paint — `show` is `true` from the start, no change ever fires, `active` stays `false` forever, and the modal sits in the DOM with correct Livewire state (`isModalOpen: true`, `editingTaskId` populated, etc. — verified in a live repro, including via the modal's own entangled Alpine data) but is permanently invisible and non-interactive. Symptom as reported by a user: "the modal isn't opening," while the underlying page source showed it was. **Fix:** `x-init` now also runs the same double-`requestAnimationFrame` immediately when `show` is already truthy at init, in addition to keeping the `$watch` for later changes — covers both the "opens later via a click" and "already open on first paint" cases with one code path, no new state. Any future consumer of `<x-ui.modals.base>` (used by the create/edit/view task modal, the hamburger menu, and others) inherits this fix automatically — do not special-case it per consumer. **`components/ui/modals/confirmation.blade.php` carries an independent copy of the identical `$watch('show', ...)`-only pattern** (its own separate `x-data`, not built on `<x-ui.modals.base>`) — fixed the same way, same turn. Its `show` starts as a plain literal `false` (not `@entangle()`-bound to a server property), so the pre-true-at-mount scenario couldn't happen through this component alone as of this writing, but the fix was applied anyway for consistency and defense-in-depth against a future caller driving it from bound state. **Audited and confirmed clean**: every other `<x-ui.modals.base>` consumer (`reservation/cards.blade.php`, `suggestion/create.blade.php`, `tab/status/about-me.blade.php`) and Project's Report/Analytics tab drill-downs — none had a plausible pre-true-at-mount path, and none showed the `TaskAccessPolicy::canView()`-style permission gap either (Report's own query already scopes through the identical `Project::visibleTo()` rule). **Related lesson**: this is exactly why TaskBoard's search deep-link fix (see `taskboardPattern.md`'s "Deep links into `/tasks?open={id}`..." section) deliberately narrows the board to one card instead of auto-opening the modal on mount — even with this CSS bug fixed, mounting a modal pre-opened is a fragile pattern to lean on; prefer a state that's reachable by a normal in-page click.

### 8.7 Single-line `@php(...)` with a `fn () =>` arrow breaks Blade compilation

Never put an arrow function inside the single-line `@php(...)` directive — e.g. `@php($x = collect($t)->contains(fn ($i) => isset($i['route'])))`. Blade's `@php(...)` close-paren matcher mis-counts the `fn`'s nested parens, emits `<?php(...)` with no `;`/`?>` and the outer parens kept, which swallows the rest of the file into PHP mode and leaves every later `@if`/`@foreach`/`@endif` un-compiled (orphaning `endif`s → `syntax error, unexpected token "endif"` at render). `php artisan view:cache` does NOT catch this — it compiles Blade→PHP and writes the file but never `php -l`s the output, so it reports success while the page 500s. Use a `@php … @endphp` block instead (simple open/close, no paren-matching): `@php\n    $x = collect($t)->contains(fn ($i) => isset($i['route']));\n@endphp`. **Rule: any expression with an arrow function or deeply nested parens goes in a `@php` block, never single-line `@php(...)`.**

### 8.10 `x-if` templates render only their FIRST root element (menu-modal paginators bug, fixed 2026-09-10)

Alpine's `x-if` mounts only `el.content.cloneNode(true).firstElementChild` (livewire.js bundle, `directive("if", …)`). A `<template x-if>` with two sibling roots silently drops every root after the first — no console warning. Real case: the menu modal's grid template held the slider viewport plus the paginator row; the paginators never entered the DOM and the grid showed no page dots/prev-next (looked like a padding/overflow problem — it wasn't). **Rule: `<template x-if>` gets exactly one root; when two siblings must both toggle together, wrap them in `<div class="contents">` (display:contents, layout-transparent).**

### 8.11 `<x-ui.scroll-panel>` — viewport-capped scrollable module shell, and a real Blade component-tag attribute-parsing bug (fixed 2026-09-10)

`components/ui/scroll-panel.blade.php` (`@props(['maxHeight' => 'max-h-[calc(100svh-10rem)]', 'gap' => 'gap-4'])`) extracts the "cap a module to the viewport and let only its body scroll" shell — `relative w-full max-w-[88rem] mx-auto h-screen overflow-x-visible overflow-y-clip flex flex-col {gap} {maxHeight}` on the root (originally `overflow-hidden`; split per-axis 2026-09-10 so rail-arrows rows pushed outward past the shell's box aren't clipped — see §8.12's clipping gotcha), consumer supplies the literal `max-height="max-h-[calc(...)]"` string (JIT-safe, never interpolated) and its own inner `flex-1 min-h-0 overflow-y-auto custom-scrollbar` wrapper(s) around whichever view(s) should scroll. Consumed by `tab/gallery.blade.php` and `tab/feeds.blade.php` (both previously duplicated the exact class combo correctly). The bug this fixes: `tab/status.blade.php`'s org-chart tab had the `max-h-[...]` cap but was **missing** `h-screen overflow-hidden flex flex-col` entirely — so the cap was never enforced (no `overflow` rule means oversized content just renders past the boundary in normal flow instead of clipping/scrolling), and the org chart's own horizontal scrollbar (`.orgc-depts`, `overflow-x:auto`) ended up wherever that unbounded growth put it — far down the page for a deep tree. Client-reported as "the scrollbar is positioned too far down."

**Real bug, caught while wiring it up: Blade's `<x-component>` tag attribute parser cannot safely carry a large multi-line `x-data="{ ...object literal with methods... }"` value — a plain native HTML tag can.** `status.blade.php` originally had its whole multi-method `x-data` object (view/collapsed/toggleDept/scroll helpers) on a plain `<div>`; moving that same attribute onto `<x-ui.scroll-panel x-data="{...}">` corrupted Alpine's initialization silently (no thrown error visible in the request/response cycle — this is a client-side Alpine parse failure, not a server exception) and **both** the grid and chart views stopped rendering, because `x-show="view === 'grid'"` / `x-show="view === 'chart'"` both evaluate false when `view` never gets set. Symptom as reported: "previously we saw one of them active, now nothing happens." A native HTML tag never goes through Blade's component-attribute tokenizer at all — Blade only compiles the `@js()`/`{{ }}` fragments inline and leaves the rest of the tag untouched for the browser/Alpine to read — so it has no trouble with nested braces/colons/multi-line content. Blade's `<x-...>` tag compiler, by contrast, has to tokenize each attribute into the `$attributes`/`@props` bag, and chokes on that same complexity. **Rule: `<x-ui.scroll-panel>` (or any custom Blade component) is safe for simple `x-data` values (a bare identifier or single-line function call, e.g. `x-data="gallery()"`, `x-data="feed"` — both fine, see Gallery/Feed) but NOT for an inline multi-line object-literal `x-data`. When a consumer's Alpine scope is that complex, keep it a plain native `<div>` and apply the shell's classes directly instead of routing through the component** — exactly what `status.blade.php` does; do not "fix" it back to the component without first moving the complex `x-data` to a dedicated named Alpine `data()` factory (a single-line `x-data="orgChart(...)"` call would then be component-tag-safe again).

### 8.12 `<x-ui.buttons.rail-arrows>` — the shared in-flow x-axis pan row (extracted 2026-09-10, redesigned in-flow same day)

The chevron pair that pushes a horizontal rail (`scrollPrev`/`scrollNext` in the consumer's Alpine scope) was duplicated in `tab/gallery/timeline.blade.php`, `tab/feeds/timeline.blade.php` (both inside `<template x-teleport="body">` + `pointer-events-none` wrappers), and `tab/reports/cards.blade.php` (an inline, hover-revealed absolute pair — an upgrade, not a byte-identical extraction) — all three now consume `<x-ui.buttons.rail-arrows />` with zero props. The org chart (`tab/status/chart.blade.php` — the "client can't reach the horizontal scrollbar on a tall chart" fix) consumes it with props: `prev="pan(1)" next="pan(-1)" prev-show="canEnd" next-show="canStart"`.

**The mid-viewport design died; the row is absolute, edge-flush, space-free.** Attempt 1: `position: fixed` chevrons floating over the rail's center — invisible in practice on tall content, and overlapping content (the client explicitly wanted zero overlap). Attempt 2: an in-flow dedicated band above the rail — worked, but consumed vertical space and the client wanted the arrows pinned at the tab header's columns instead. Final design: the component emits `hidden md:flex absolute top-0 inset-x-0 items-center justify-between z-20` — absolutely pinned to the TOP corners of its containing view block, zero flow space consumed, so the content below starts naturally at its own padding. **The host view block must be `relative`** (the filmstrip blocks in `tab/gallery.blade.php`/`tab/feeds.blade.php`, the card container in `tab/reports.blade.php`, the x-data wrapper in `tab/status/chart.blade.php`) — the buttons then land flush at the block's outer edges, horizontally aligned under the `<x-ui.title>` icon (right button) and count chip (left button), i.e. outside the content's `px-4 md:px-12` width. The old teleport/pointer-events-none wrappers were deleted with the redesign — don't reintroduce them. **Clipping gotcha (real bug, fixed 2026-09-10): the outward-pushed arrows (`relative -right-10`/`-left-10`) sit OUTSIDE the shell's box** — a shell with `overflow-hidden` clips them to nothing (arrows invisible in gallery/feeds/status while reports, whose root is a plain no-clip div, showed them fine). `hidden` cannot pair with a visible axis (spec forces the other axis to `auto`), but `clip` can: the scroll shells now use `overflow-x-visible overflow-y-clip` — vertical capping identical to before, horizontal escape allowed. Do not "simplify" this back to `overflow-hidden` on any shell that hosts a rail-arrows row.

**Props:** `prev`/`next` (click expressions, defaults `scrollPrev`/`scrollNext`), `prevShow`/`nextShow` (optional `x-show` expressions — when present the button also gets `x-cloak` so nothing flashes pre-Alpine), `position` (default `null` = the edge-flush outward-pushed row above). Button semantics are screen-side, not reading-direction: **`prev` is the right-side button** (`chevron_right`, the RTL "back" direction), **`next` is the left-side button** (the row itself hardcodes `dir="rtl"` so this holds even inside the LTR `.orgc-chart`) — that's the established RTL-page vocabulary, so an LTR rail like the org chart (`.orgc-chart` has `dir="ltr"`) passes its handlers swapped (`prev="pan(1)"` scrolls rightward). The default row is `hidden md:flex` — desktop-only by design; mobile pans rails natively.

### 8.13 Org chart horizontal nav, take two: drag-to-scroll instead of pan-arrow buttons (2026-09-10)

Since the rail-arrows retry above stayed undiagnosed and reverted, the org chart's "too wide, hard to reach the scrollbar" complaint was solved a different way: `.orgc-depts` (`tab/status/chart.blade.php`) got native click-and-drag panning — a plain `x-data="{ down, dragged, startX, startScroll, hovering, mouseX, mouseY }"` on the row itself (a native `<div>`, not a `<x-...>` component tag, so §8.11's component-tag attribute-parser bug doesn't apply) with `@mousedown`/`@mousemove`/`@mouseup`/`@mouseleave` setting `scrollLeft = startScroll - (clientX - startX)`. No `ResizeObserver`, no `x-init`-with-`this`, no teleport — none of §8.12's failure surface is present, so this is a structurally different, much smaller mechanism, not a retry of the same pattern.

**Two-axis drag, added same day:** the client asked for the same grab-drag to also pan vertically, not just horizontally. `startY`/`startPageY` were added alongside `startX`/`startScroll`, captured from `(document.scrollingElement || document.documentElement).scrollTop` at `@mousedown` (the page itself scrolls vertically here — `.orgc-depts` has no `overflow-y` of its own — so the Y-axis target is the document's scrolling element, not `$el`), and `@mousemove` sets both `$el.scrollLeft` (X, unchanged) and `document.scrollingElement.scrollTop` (Y) from the same single drag gesture. The `dragged` threshold check now trips on either axis (`Math.abs(dx) > 5 || Math.abs(dy) > 5`), so the click-after-drag guard below still catches a vertical-only drag, not just a horizontal one. The legend copy was updated from "moves horizontally" to "moves in any direction" to match.

**Click-triggered "compass" D-pad, added 2026-09-11 — the client reported the vertical drag itself as unreliable and asked for a click-based alternative.** The cursor-hint `<span>` became a real `<button>` (`.orgc-cursor-hint`, `cursor: pointer` instead of `pointer-events: none`, hover scale); clicking it sets `toolsOpen = true` and freezes `toolsX`/`toolsY` from the *current* `mouseX`/`mouseY` at that instant — this is the load-bearing detail: `mouseX`/`mouseY` keep updating on every `@mousemove` (they still drive the hint button's own live position), so the popup's `:style` binding MUST read from separate frozen `toolsX`/`toolsY`, not the live pair, or it would jitter/flee the cursor as the user tries to reach its buttons. `.orgc-compass` is a 3×3 CSS grid (`grid-template-columns/rows: repeat(3, 2.1rem)`) clipped to a circle (`border-radius: 9999px; overflow: hidden`) with only the 4 edge cells + center populated (`grid-column`/`grid-row` per `--up`/`--left`/`--center`/`--right`/`--down` class) — a plus/compass shape, not a plain button row, chosen over the flat-row default for a more map-control-like feel. Each direction calls a shared `pan(dx, dy)` method added to the same `x-data` object: horizontal via `$root.scrollBy({left: dx, behavior: 'smooth'})` (`$root` — valid Alpine magic for the element carrying `x-data`, i.e. `.orgc-depts` itself, reachable from any nested button's `@click.stop` in the same component scope), vertical originally via `document.scrollingElement.scrollBy({top: dy, behavior: 'smooth'})` — the same target the two-axis drag paragraph above claims, just driven by a click instead of a drag delta. Closes via its own center `close` button, `@click.outside`, or the existing `@mouseleave` on `.orgc-depts` (extended to also reset `toolsOpen`). All 5 buttons use `@click.stop` so a plain click never reaches the row's `@click.capture="if (dragged) {...}"` guard or bubbles into `toggleDept`/the about-me modal.

**Root cause of "vertical drag did not work" found in review (2026-09-11): `document.scrollingElement` was always the wrong target.** The two-axis drag paragraph's premise — "the page itself scrolls vertically here" — is false: `<main>` (`layouts/app.blade.php`) is `overflow-hidden`; the element that actually has `overflow-y-auto` and does the real scrolling is the inner wrapper in `components/dashboard/tab.blade.php` (`class="... overflow-y-auto custom-scrollbar ..."`), several DOM levels above `.orgc-depts` but below `<html>`/`<body>`. `document.scrollingElement` (i.e. `<html>`) never had any overflow to scroll, so both the original vertical drag and this compass's up/down buttons silently no-op'd — exactly the client's report. Fixed by caching the real ancestor once in `init()` (`vBox: null`, `init() { this.vBox = this.$root.closest('.custom-scrollbar') || document.scrollingElement || document.documentElement }`) and reading/writing `vBox.scrollTop` / `vBox.scrollBy(...)` everywhere the drag handlers and `pan()` previously touched `document.scrollingElement` directly. `.closest()` walks from `.orgc-depts` upward and correctly resolves to `tab.blade.php`'s wrapper (the nearest `.custom-scrollbar` ancestor) even though that class is reused by ~40 unrelated scroll containers elsewhere in the app — `closest()` only sees this instance's own ancestor chain. Caching in `init()` also avoids re-running `closest()` on every `mousemove`.

**Click-after-drag gotcha (real bug, caught in review):** the handlers alone don't distinguish "dragged the row" from "clicked a card" — releasing the mouse after panning still fires a native `click` on whatever dept/member card the cursor lands on, wrongly opening the "about me" modal or toggling a department. `cursor: grab`/`.is-dragging { cursor: grabbing }` on `.orgc-depts` (`dashboard.css`) is the ambient affordance. **The legend's "جابه‌جایی افقی نمودار" tip was rewritten to describe drag-to-pan** — the arrow-button copy it previously carried never matched shipped behavior even before this change (the arrows were reverted, the legend wasn't).

**Visual hint, evolved through three shapes — landed on two triggers at once, not one.** Two early designs — a centered glass badge that faded in once, then a one-shot left-right wiggle on the row — were both gated on `hinted = (view === 'chart' && $el.scrollWidth > $el.clientWidth)` via `x-effect`, and the client never saw either fire. **Real bug, caught by the client clicking and getting nothing: bare data-property identifiers inside an `x-data` method body do NOT resolve to the component, unlike bare magics.** `openTools(e) { toolsOpen = true; toolsX = e.clientX; toolsY = e.clientY }` silently failed — the compass never opened, because that assignment never touched the reactive `toolsOpen` at all. The mechanism (confirmed against Livewire's bundled Alpine, `vendor/livewire/livewire/dist/livewire.js`): the `x-data="{...}"` object-literal expression is evaluated once via `with(dataProviderContext) { return {...} }` (`generateEvaluatorFromString`/`normalEvaluator`), where `dataProviderContext` holds only the injected **magics** (`$root`, `$el`, `$refs`, etc.) — never the object's own sibling keys, since those don't exist until the object literal finishes constructing. A method defined inside that object literal (`pan(dx, dy) { ... }`, `openTools(e) { ... }`) is a function expression lexically nested inside that `with` block, so per normal JS closure rules it keeps that `with(dataProviderContext)` in its scope chain forever — meaning a **bare magic** like `$root` resolves correctly every time the method is later called (found on `dataProviderContext`), but a **bare plain-data identifier** like `toolsOpen` is NOT on `dataProviderContext` and falls through to the global scope, silently creating/writing `window.toolsOpen` instead (non-strict mode) — invisible to Alpine's reactivity. Magics are ALSO injected directly onto the final reactive object after construction (`injectMagics(data2, el)`), which is why `this.$root`/`this.vBox` work too — magics are reachable both ways, plain data only via `this.`. **Rule: inside any method defined in an `x-data` object literal, magics (`$el`/`$root`/`$refs`/`$dispatch`/`$nextTick`/`$watch`) may be referenced bare, but every sibling data property MUST use `this.` — bare `toolsOpen = true` compiles and runs with no error, it just silently does nothing to the component.** (Directive-attribute strings like `@click="toolsOpen = false"` are unaffected — those re-evaluate through the *current* live scope on every call via `generateEvaluatorFromString`'s per-invocation `mergeProxies([...dataStack])`, not a construction-time closure, so bare identifiers there are correct as already used throughout this file.) Fixed: `openTools(e) { this.toolsOpen = true; this.toolsX = e.clientX; this.toolsY = e.clientY }`.

**Teleported the cursor-hint/compass out of `.orgc-depts` (client-initiated), and hit §8.10's exact gotcha again for a different directive.** The client wrapped the cursor-hint button + compass in `<template x-teleport="body">` so they escape the row's own stacking/clipping context. `<template x-teleport>` clones via `el.content.cloneNode(true).firstElementChild` (confirmed in `vendor/livewire/livewire/dist/livewire.js`) — **identical mechanism to `x-if`'s single-root limitation in §8.10**, just for a different directive: a template with two sibling roots silently teleports only the first, dropping the rest with no warning. **Compass open/close must be click-only, never hover-driven — a real gotcha caught by the client, not obvious from the diff.** `@mouseleave="down = false; hovering = false; toolsOpen = false; ..."` on `.orgc-depts` looked like reasonable cleanup (reset everything when the mouse leaves the row) but it silently closed the compass on ANY mouseleave — including the mouse crossing from the row toward the compass's own buttons if the click happened near the row's edge, or simply glancing off the row while trying to reach a teleported, `fixed`-positioned compass that can render anywhere on screen. **Rule: `hovering` (controls the ambient cursor-icon's visibility) and `toolsOpen` (controls the toolbox itself) must reset independently — never fold a hover-reset and a click-driven toggle into the same handler.** Fixed by dropping `toolsOpen = false` from `@mouseleave`, leaving exactly three ways to close the compass, all click-based: the center `close` button (`@click.stop="toolsOpen = false"`), `@click.outside`, and (implicitly) opening it again elsewhere just moves it. `hovering = false` still resets on `@mouseleave` — that's correct and unaffected, since the ambient cursor-icon hint is *supposed* to be hover-driven, only the toolbox itself is not.

### 8.16 `<x-ui.modals.tooltip>` — invisible data-holder in Blade, all display owned by the JS singleton (2026-09-15, clipping fix)

The component renders ONLY a hidden marker (`<span class="hidden" data-tip="..." data-tip-pos="..." role="tooltip">`), never the visible popover. The actual tooltip is one `position: fixed` singleton node created and parked at body level by `resources/js/core/tooltip.js` (`initTooltip()`, booted from `app.js`; see `scriptPattern.md` §17 for the JS side). **Why:** the previous implementation was an absolutely-positioned span inside the trigger's subtree — any ancestor with `overflow:hidden` (table cells, clipped cards, scroll panes) physically clips it and no z-index can escape that, which is exactly what bit the reminder trigger once rolled into 6 modules. A body-level fixed node is outside every clipping context by construction.

**Holder contract:** place the component as a DIRECT child of its trigger (the `relative` element) — that is the primary resolution path (`:scope > [data-tip]` walking up from the hover target); the tooltip anchors at `holder.parentElement`. Fallback: a `.group` ancestor containing a holder also resolves it (preserves the old `group-hover:` "row hover reveals the tooltip" behavior of the `corner`/`inline` reminder variants). Text comes from the `data-tip` attribute, else the holder's live `textContent` — the latter is what keeps slot content (`auth.blade.php`) and a merged `x-text` attribute (`footer/google.blade.php`) working. Positions are physical rects (RTL-safe by construction). Valid `position` values: `top|right|bottom|left`; anything else falls back to `bottom`.

**Rules:** never hand-roll a second absolutely-positioned tooltip span in a blade — go through this component; plain `title=` attributes are equally fine (the JS singleton adopts them at `top`, HTML's default placement — see `scriptPattern.md` §17), but never combine BOTH on one trigger: the holder wins the walk and the orphaned `title` falls back to the native OS tooltip; the appearance classes live ONLY in the JS singleton (Tailwind v4 scans `resources/js` via `@source '../**/*.js'`, so they compile); don't strip the seemingly-dead hidden holder — it IS the API. Accepted minors: a morph that replaces the hovered holder mid-hover can leave the tooltip visible until the next mouse/scroll event (the old in-DOM version vanished with the morph); hovering dead space of a `.group` with several holders resolves DOM-first (the old CSS revealed ALL of them simultaneously — the single-read replacement is deliberate, one label at a time).

**Rule — which one to reach for (2026-09-15, mandatory decision matrix):** all three label mechanisms render through the same clip-proof singleton (`scriptPattern.md` §17), so styling/placement-clip never decides this — only capability does. **(1) Plain `title=`** — the default for simple static text labels: icon buttons, truncated names, hover hints on plain elements. Zero component overhead, always shows at `top` on the element itself; keep Alpine `:title` rebinding exactly as-is (the singleton re-syncs it). **(2) `<x-ui.modals.tooltip>`** — when plain title can't express it: placement other than top (`position="left|right|bottom"`, e.g. navbar side icons), anchoring on a PARENT element (holder child inside a larger trigger, e.g. a tiny icon whose label should center on the whole button), row-level reveal via a `.group` ancestor (reminder `corner`/`inline` variants — hover anywhere on the row shows the label), or live content via slot/`x-text` (auth layout, Google-translate chip). **(3) Popovers, not tooltips** — the moment content is rich or INTERACTIVE (buttons, forms, click-able items), a tooltip is wrong: it is `pointer-events:none` text-only. Use `<x-ui.hover-popover>` (§8.7) for hover-revealed rich content and `<x-ui.modals.popover>` (§8.17) for click-toggle menus; both are body-teleported and equally clip-proof. Never downgrade an interactive menu into a tooltip, never build a third tooltip/popover mechanism outside these four.

### 8.17 `<x-ui.modals.popover>` (click-toggle menu) — now body-teleported like `hover-popover` (2026-09-15, clipping fix)

Same disease as the tooltip (§8.16): the click-toggle menu was `position: absolute` inside its trigger's subtree — clipped by any `overflow` ancestor (its posts-details consumer lives inside the slideover's scrollable panel). Converted to the exact `hover-popover` mechanism (§8.7): `@click` captures `$refs.trigger.getBoundingClientRect()`, `<template x-teleport="body">` renders the panel as `position: fixed` from those coords, `@click.away` guards `!$refs.trigger.contains($event.target)`, cross-teleport `$refs` work by Alpine's `_x_teleportBack` hop. **Two gotchas that differ from hover-popover:** (1) the `bottom-full` (above-trigger) case needs the panel's own height, which is only measurable after `x-show` restores display — measured via `$refs.panel.offsetHeight` inside `$nextTick` right after `open = true`; the enter transition's `opacity-0` start masks the same-microtask settle, so no flash; (2) **the teleported panel must carry `z-[110]`, not the old in-DOM `z-50`** — teleporting lifts it OUT of the slideover's (`z-[100]`) containing tree, so DOM order no longer saves it; reviewer-caught, would otherwise render under the very overlay that spawned it and read as a dead feature. Props/slots/width/surfaces/transitions are unchanged; `alignment`'s `bottom-full`/`left-0`/`right-0`/`origin-*` tokens are parsed into computed style (the absolute classes themselves are gone). Known limitation shared with §8.7: no viewport-edge clamping, no scroll-follow.

**Searchable modals keep a stable outer height (2026-09-18):** a modal whose card only caps with `max-h-*` hugs its content, so typing into an in-modal search/filter shrinks the whole dialog as the result list narrows — reads as broken. Rule: any modal filtering a list live must pin its size — either the card gets an explicit `h-[...]` with scroll body `flex-1 overflow-y-auto` (hamburger menu, Ctrl+K palette `h-[75vh]`, home gadget picker), or the filtered list itself gets a fixed `h-*` instead of `max-h-*` (channel manage-members `md:h-64`, project form member picker `h-72`). `max-h` caps, it does not stabilize.

**`x-transition` on an element different from the one carrying `x-show` is dead code (hero gadget picker bug, fixed 2026-09-18):** Alpine only runs `x-transition` when the element bearing it is the one `x-show` toggles; transitions on a *child* of the toggled wrapper never fire — the picker popped in abruptly for weeks with perfectly-written `x-transition:enter-start="opacity-0 scale-95"` classes that did nothing. Fix there was to drop both wrappers' `x-transition` sets and put the registered `.animate-slide-down` class on the overlay div instead — a CSS animation restarts whenever the hidden-by-`display:none` subtree becomes visible, so it works regardless of which ancestor `x-show` toggles (the hamburger menu already proves this pattern). Rule: either put `x-transition` on the exact element with `x-show`, or use a registered `.animate-*` utility inside the toggled subtree.

**Two modal families exist BY DESIGN — do not unify (2026-09-18):** (1) the plain overlay family — translucent `bg-[var(--md-sys-color-primary)]/60` backdrop + `.animate-slide-down` entrance (hamburger menu, command palette, `<x-ui.modals.dialog>`, hero gadget picker, pdf/video viewers); (2) the cinematic `.custom-modal` family in `dashboard.css` — solid-primary backdrop expanding from a center line (width 0→100%, height 2px→100%, then content fade), used by release notes, taskboard create/edit, profile documents and `<x-ui.modals.confirmation>` as a deliberate "special moment" treatment. Only the overlay family is the target when asked to normalize modal entrances; leave family 2's mechanism untouched.

**RTL flips grid column order (2026-09-18):** under the dashboard's global `dir="rtl"`, a CSS grid's first DOM cell renders at the RIGHT viewport edge. A fixed-position schematic whose cells carry directional English labels (the home blueprint's LEFT/RIGHT wireframe) therefore shows "LEFT" on the right side, and its zone filter highlights the opposite edge. Don't re-order the DOM to compensate (semantic order then lies); pin the diagram row to `dir="ltr"` so DOM order equals the labeled visual order.

**Display numbers render Persian digits — convention (2026-09-18 sweep, 27 spots across 12 modules):** every user-facing number emitted as display text in a dashboard view goes through `{{ convertToPersian($x) }}` (helper at `app/Helpers/index.php` — strtr `0-9`→`۰-۹`, null-safe, and identity on already-Persian input, so an accidental double-wrap is harmless). Scope is DISPLAY STRINGS ONLY — never inside `x-text`/`x-show`/`:class` or any Alpine expression, never in `data-*`/`aria-*` attributes, `<option value>`, input values, or `wire:click`/`wire:model` arguments (an `<option>`'s label text IS fair game; only its value attribute stays Latin). Font rule: the moment an element's digits go Persian, drop `font-mono`/`tabular-nums` from it — those fonts/tabular glyph variants don't cover Persian digits and the count renders broken; converted numbers ride the app's default font. When matching an existing file's idiom, note some files cast explicitly (`convertToPersian((string) $score)` in energy/chart), others pass the raw int — either is safe. `<x-ui.title>` converts its `count` prop internally (2026-09-18), so every consumer must pass a RAW int — never pre-wrap a count passed to it.

### 8.14 A Blade `:`-prefixed component attribute is server-side PHP, never Alpine (audio-player tooltip fatal, 2026-09-11)

Inside a Blade component invocation, `:text="..."` / `:anything="..."` is evaluated by PHP at render time — the same syntax Alpine uses for reactive `:class`/`:style` on plain elements, but on a component tag it never reaches the browser as an Alpine expression. Writing Alpine there (`:text="!menuOpen && audioPlaying ? '…' : '…'"` on `<x-ui.modals.tooltip>` in `top/hamburger.blade.php`) throws `Undefined constant "menuOpen"` from PHP and takes the whole page down with a 500 on every navbar render — no Blade compile error, no JS error, just a dead page. Rule: component attributes are PHP expressions only (pass `$title`/`@js(...)`/`{{ }}`-safe values); Alpine reactivity on a component's internals must be expressed with plain `x-` directives or `x-data` on the surrounding element, or via a `CustomEvent` when the two sides live in different scopes (the audio chip's `audio-play-state` window event is the worked example — see `resources/js/scriptPattern.md`'s `audioPlayer.js` entry).

### 8.9 Global AI Assistant widget (`components.dashboard.ai-assistant` + `navbars.top.ai-assistant`) — cross-origin iframe, own boolean state machine

**Trigger is a header icon button, not a floating FAB.** `components/dashboard/navbars/top/ai-assistant.blade.php` follows `top/hamburger.blade.php`'s exact shape (`w-10 h-10 rounded-xl` transparent-hover button, `<x-ui.modals.tooltip>`) and sits first in `top.blade.php`'s hamburger/home group — a real nav-grade control, not a bobbing round circle sitting alone on the page (rejected explicitly: a floating `animate-float` FAB read as a "childish" toy, out of place next to this app's flat header icon-button language; round shapes in this app are reserved for the bottom-right dock tools' minimized pills, not primary navigation triggers). Icon is `auto_awesome` (the sparkle glyph already used app-wide as the "AI/smart" marker — see any `guide/*.blade.php` under `filament/resources/*`), not `smart_toy`.

The button and the panel live in different parts of the DOM (header vs. `global.blade.php`'s persisted block), so they can't share one `x-data` scope — wired via the same `window`-level `CustomEvent` mechanism `menu.js`'s `BASE_ITEMS`/`handleItemClick` dispatch + `calculator.js`'s `window.addEventListener('calculate', ...)` already use (no dedicated section in this doc for that mechanism yet — see those two files directly): the button does `@click="$dispatch('ai-assistant')"`, and `aiAssistant()`'s own `init()` (Alpine auto-calls a data method literally named `init`, no `x-init` attribute needed — unlike `calculator.blade.php`'s redundant explicit `x-init="init()"`, don't copy that) does `window.addEventListener('ai-assistant', () => this.openChat())`.

The panel itself iframes a sibling Node.js chat app on a separate origin (`AI_ASSISTANT_URL`, via `config('services.ai_assistant.url')`), opening as a corner card at `bottom-24 left-4 md:left-6` (mounted in `components/dashboard/global.blade.php` inside the existing `@persist('dashboard-tools')` block, §8.4, so it survives `wire:navigate` — but is **not** one of the 3 dock tools: no `x-teleport="#tool-dock"`, no minimize-to-pill). Its two states are `open` (closed ↔ panel) and `maximized` (small corner card ↔ near-fullscreen inset via `:class`), toggled by its own header-bar buttons inside the panel, not `<x-ui.modals.backdrop>` (that component's full-screen scrim would block reading the page while chatting — the opposite of what this widget is for).

**Deliberately does not use the shared `maximize.js` mixin** (`resources/js/scriptPattern.md` §3.4) — that mixin's `.max-widget` takeover hides `#header`/`#navbar`/`#footer` entirely, built for full-page modules (e.g. `dms`) going fullscreen. This widget's "maximized" state stays an inset overlay (`inset-4 md:inset-10`) with the rest of the dashboard still visible at the edges — a different UX, so it carries its own `maximized` boolean in `aiAssistant.js` instead of forcing the mixin's chrome-hiding behavior onto a floating panel.

**Plan-tier access gate:** both the panel and its header trigger check `config('app.ai_assistant_access')` (per-tenant `config/tenants.php` key `ai_assistant`, see `config/tenantPattern.md`'s "Plan-tier feature flags" section — a three-state flag, not a bool). `=== true` renders the full working widget (same as before this gate existed); `=== 'lock'` renders only the header icon, dimmed, with a small lock badge and an "upgrade your plan" toast on click — the panel itself never renders in this state even if `AI_ASSISTANT_URL` is configured; anything else (`false`, or the key simply absent from the active tenant — the default) renders nothing at all, not even the header icon. This is a separate gate from the `AI_ASSISTANT_URL` check below — both must pass for the working widget to appear.

**The module title/summary string is not a signal of widget availability (real test bug, fixed).** `config/modules.php`'s `ai-assistant` entry — added so the feature shows up in the informational module guide — renders **unconditionally** on the dashboard Home tab (`App\Livewire\Dashboard\Tab\Home::modules()` returns `Config::get('modules', [])` verbatim, no per-tenant filtering) regardless of `ai_assistant_access`. A test asserting `assertDontSee('دستیار هوش مصنوعی')` to prove the widget is hidden will fail even when the widget genuinely is hidden, because that exact title string is still printed by the guide catalog. Assert on something specific to the actual functional widget instead — the iframe's `?user=` src substring — not the shared title text.

**Identity:** iframe `src` carries `?user={{ Str::slug(config('app.name_en')) }}_{{ auth()->id() }}` — the active tenant's `name_en` (`config/app.php`, tenant-resolved via `config/tenants.php`), not a hardcoded app name, so the same codebase deployed under a different tenant (`persol` → `WinterrA`) automatically gets a distinct, non-colliding identity prefix on the receiving app's side without a code change. The receiving app trusts this value verbatim (no signature) — accepted for v1, confined to that app's own chat-history namespace, never Fateh session/CSRF data (never crosses the origin boundary).

**Language:** the same `src` also carries `&lang={{ config('app.ai_assistant_lang') }}` — an explicit signal, not an inference, and tenant-controlled (per-tenant `config/tenants.php` key `ai_assistant_lang`, default `'fa'`, env override `AI_ASSISTANT_LANG` — same three-layer resolution shape as `ai_assistant_access`, see `config/tenantPattern.md`'s "Plan-tier feature flags" section). Deliberately **not** `app()->getLocale()` — that governs Fateh's whole-app UI locale, a different concern that could diverge from which language a given tenant wants the AI chat to open in. The sibling AI app is shared by multiple consuming apps (BMS, ETEQ, future ones), so its own greeting logic must not assume every embedding app wants Farsi just because it's embedded; Fateh states it explicitly instead. A consuming app that omits `lang` gets the AI app's own English default — this param is what keeps that default from being silently overridden by a hardcoded "restricted mode = Farsi" assumption on the AI app's side.

**Primary color + light/dark mode:** the `src` also carries `&theme={name}&mode={light|dark}` — but unlike `user`/`lang`, neither is Blade-computed. Both the active color theme (`grey`, `midnight`, `jade`, ... — see `resources/js/components/alpine/stores/theme.js`'s `THEME_COLORS`) and the light/dark mode live client-side only, in `localStorage`'s `user-theme`/`user-mode` keys (`ThemeManager`, see `resources/js/scriptPattern.md`), invisible to Blade at render time. So `aiAssistant()`'s factory takes the Blade-computed `user=`/`lang=` base string as a constructor arg (`aiAssistant(@js($aiAssistantBaseSrc))`), and `openChat()` — the same click handler that flips `open`/`loaded` true — computes the full URL once, synchronously, into a plain `src` data property (`x-bind:src="src"` on the iframe), reading `window.ThemeManager.getUserTheme()`/`getUserMode()` at that moment via a small `readSetting` helper. **Deliberately not** a reactive `x-bind:src="someMethod()"` calling a function inside the binding — an earlier version did that, and while the value it computed was always correct (verified via logging), evaluating it as part of `<template x-if="loaded">`'s clone-and-bind step, concurrent with the panel's own CSS enter-transition, made the actual page-load timing hard to reason about and read as "sometimes blank" under real network latency. A plain property, set before `loaded` even flips true, removes that entirely — the iframe is created with its final `src` already resolved, no function call involved at creation time. Both `theme`/`mode` are captured once per page load (guarded by `if (!this.src)` in `openChat()`), never recomputed on a later reopen or kept live-synced while the panel stays open — matches how `lang` already behaves; the user confirmed this is the wanted behavior, not a gap. The sibling app maps the theme *name* to a predefined primary-color-only palette on its own side (`public/assets/css/modules/base.css`, `[data-color-theme="name"]`) — only the 15 names the picker actually exposes are mirrored, and only the single `--primary-color` role, not the full MD3 palette (secondary/tertiary/error/etc. deliberately not synced). `mode` reuses the sibling app's own existing `data-theme="dark"`/`"light"` attribute and `localStorage` key verbatim — no new attribute needed on that side, just a value the app's own toggle already understands. Both params are optional and independently safe to omit: an embedding app that sends neither gets the sibling app's own untouched defaults (native blue primary color, its own remembered/system light-dark preference) — see `public/assets/js/scriptPattern.md` (AI repo) for the fallback mechanics.

**Visibility guard:** `@if(auth()->check() && config('services.ai_assistant.url'))` — renders nothing for guests or when the env var is unset, so the widget is silently absent on any environment that hasn't wired up the sibling app yet.

**`loading="lazy"` was removed from the iframe too, but was a red herring, not the actual fix (see §"Primary color + light/dark mode" above for the real cause/fix).** During debugging this looked like the culprit — native lazy-loading defers fetching until the browser's intersection check considers the element visible, and the iframe was entering via the panel's own `opacity-0` CSS transition, a plausible race. Removing it did not resolve the issue on its own; the actual bug was the reactive `x-bind:src="someMethod()"` timing described above. Left removed anyway since `loading="lazy"` provided no real benefit here regardless — the iframe doesn't exist in the DOM at all until the user has already explicitly clicked to open it, so it's already effectively on-demand. **Don't re-add `loading="lazy"` here assuming it was neutral** — it was ruled out as *the* cause, not proven harmless; no reason to reintroduce it.

**`100vw` on a `position:fixed` element causes a page-wide horizontal scrollbar (real bug, fixed).** The panel's small-screen width was originally `w-[calc(100vw-2rem)]` at `left-4` — `100vw` resolves to the full viewport width *including* the scrollbar's own reserved space, which is wider than the actually-visible area on any browser/OS with a non-overlay scrollbar. Combined with the `left-4` offset, the panel's right edge landed past the true visible edge, forcing the whole page into `overflow-x`, but only while the panel was open (`x-show`, `display:none` when closed contributes no overflow) — read by the user as "the page sometimes gets wide." Fixed by anchoring both edges to real viewport edges instead of computing a width from `vw`: `inset-x-4` (both `left-4` and `right-4`, width implied) on small screens, `md:inset-x-auto md:left-6 md:w-[400px]` to restore the fixed-width pinned-left card at `md`+. **Rule: never size a `position:fixed` element with `calc(100vw - Npx)` or Tailwind's `w-screen`; anchor with `left`/`right` (or `inset-x-*`) so the box can never exceed the real scrollable viewport.**

**Header-bar maximize/close buttons de-inline-styled (2026-09-21).** Both buttons previously used raw inline `style="width:40px;height:40px;background:rgba(255,255,255,.10);"` plus a hardcoded `hover:bg-red-500/50` on close — a violation of `userStylesPattern.md` §7's "no static hex/rgba, use MD3 tokens" rule, found during an app-wide close-button consistency sweep. Both are now plain Tailwind using `--md-sys-color-on-primary`-based tokens (`w-10 h-10 rounded-xl bg-[color-mix(...on-primary_15%...)]`); the close button specifically now renders via the shared `<x-ui.modals.close-button tone="on-primary" size="lg">` (§8.22 below), with the maximize button hand-styled to match it exactly for a consistent toolbar pair.
